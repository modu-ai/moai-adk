# UPDATE

`/moai update` (`$moai update` in Codex CLI) updates the current project: its MoAI-managed files, its settings, and state left by the earlier Go generation of MoAI (user decision of 2026-11-13 on #2634, Issue #2696). Every write goes through a preview the user sees and an apply bound to that preview's digest, through the same commands PROJECT uses; this route adds no writer of its own.

The user layer — the installed skill, the binary and the global instructions under HOME — is the shell command `moai update`, and this route never runs it. When the user asks for that, tell them to run it in a terminal: it previews like `moai update-plan`, asks once, and moves an earlier, Go-era `moai` skill folder aside only after they confirm its backup preview (`moai update-apply --confirm-backup-replace`), with `moai recovery-plan` as the way back for a host left pending.

## Input

The current project, its `project.yaml` and the baselines under `manifests/` in its state folder (`.moai/` once `state_root.generation` is `rust`, otherwise `.moai-cli/`), and the user's answers.

## Output

The one preview the user saw, then for each step either its applied receipt or the reason it was skipped; at the end, whether the preview now reads `all_unchanged`.

## Procedure

1. **Preview everything once.** Run `moai project-update-plan <project>`. It writes nothing (Issue #2936). Show the user every phase and every step in one view, in the order printed: for each step its `state`, `reason` and `preview` — the go-state `items`, `go_backup`, `state_moves`, `restores`, `root_files` and `warnings`; the profile `delta`; the generation `files`; the settings `action` and `conflicts`; the GitHub `files`. The phases follow the user's update flow: `backup` (the earlier generation's state moves aside; the phase `reason` names what it does not cover yet), `install` (this generation's profile, managed files and settings), `merge` (asking which backed-up settings and instructions come back; `not_run` in this version — say so). When every install step reads `needs_decision` with `run /moai project`, the project has no profile of this generation: when the backup phase has a move, do it first (steps 2–4), then send the user to SETUP (or `/moai project`) and stop; only when there is no profile and no Go-generation state is there nothing to update.
2. **Ask.** Ask once for the `ready` steps as a whole, then a separate yes for each `needs_decision` step that prints a command. The go-state move is one: follow PROJECT step 2 (the Go `.moai/` is kept whole as `.moai-backup`, or `.moai-backup-<UTC>` when that name is taken, and a new `.moai/` is made; with only `legacy_root` the earlier `.moai-cli/` state moves into a new `.moai/`). A no skips that step and nothing of it is written. A go-state step that reads `blocked` prints no command: the earlier state stays where it is — `state_root.generation` is `mixed`, `unknown` or `refuse` (`refuse` covers a `.moai` that is a link or not a folder), or Go or `.moai-cli/` state cannot move (settings reference `.moai/`, a worktree or nested checkout is inside it, no usable Go manifest). It is reported with its `reason` and nothing is moved (a link is never followed): say what was found and let the user decide outside this route. A generation step that reads `needs_decision` because project agents or skills cannot be rebuilt from the stored state prints no command: send the user to `/moai project` to regenerate them; nothing is removed. A file or managed part the user edited is planned as `conflict` and kept; report it and let the user decide. For the Claude Code settings, a key MoAI manages that the user set themselves (for example their own `statusLine`) is a conflict and nothing is written; when the preview offers `confirm_replace`, the step reads `needs_decision` and its printed command is that replacement (`apply.argv` ends with `--confirm-replace <token>`, `apply.stdin` is the keys MoAI owns): show the user the key with its current and new value, and run `claude-settings-apply … --confirm-replace <token>` only after their explicit confirmation: the existing file is first kept byte for byte under `settings-backups/` in the state folder, only that key changes, and the answer names the `cp` command that puts the original back (Issue #2383). A `blocked` step names its cause in `reason`; nothing of it is written, and the other steps still stand.
3. **Apply in order.** Run each approved step in the printed order, exactly as printed: the words of `apply.argv` (the first is the `moai` command) with `<permission-reference>` replaced by the user's permission reference, and `apply.stdin` on stdin (nothing when it is `null`). Report each receipt. Stop at the first failure and report what was applied and what was not.
4. **After the backup phase, preview again first.** After a go-state apply, run `moai project-update-plan <project>` again before anything else: until then every install step reads `blocked` with `re-run after the backup phase`, because its preview would be stale. Report the receipt and the way back, `moai go-state-revert-plan <project> --backup <UTC>` and `moai go-state-revert <project> --backup <UTC> --plan-digest <digest> --permission-reference <ref>`. When the go-state step reads `needs_decision` with a `reason` naming state_root `interrupted`, a move stopped midway and the step prints no command: show `moai go-state-revert-plan <project> --backup <UTC>` and move nothing else until the user decides. The same rule follows a profile apply: the generation step reads `re-run after the profile apply` until the preview is run again.
5. **Re-run and report.** Run `moai project-update-plan <project>` once more and report what is left. The project is up to date only when `all_unchanged` is `true`: a re-run plans `unchanged` for every step (a `skip`, such as GitHub templates the project did not choose, counts as nothing to do). Anything else is reported as what is left, never as done.

## Exceptions and Permissions

A running session that reads `.claude/` or writes `.moai/` cannot be detected: ask the user to close such sessions before an apply. Never write a target whose current state could not be read, nor one under a recorded HOLD. A changed project refuses an old digest; preview again instead of retrying. Never edit `project.yaml`, a managed section or a Go-era file by hand to get past a conflict, and never delete what a step moves: it is kept where the step's receipt says (`.moai-backup`, `.moai/backups/` or `.moai-cli/backups/`).

In a project, run the read-only `moai go-state-plan <project>` and show the user every warning it gives about `.worktreeinclude`: a line there that selects secret files such as `.env` makes Claude Code copy them into every new worktree, including the worktrees of the `moai-impl` and `moai-audit` agents (Issue #2670). Name the line and let the user decide; never edit that file for them.

## Completion Check

Report each step as applied (with its receipt), skipped (with the reason, including the user's no), conflicted (with the files) or blocked (with its reason). The project is up to date only when the re-run of `moai project-update-plan <project>` reads `all_unchanged`. Host use of `/moai update` for this route is verified only after the installed skill carries this version (not_run until then).
