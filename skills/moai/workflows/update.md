# UPDATE

`/moai update` (`$moai update` in Codex CLI, `/skill:moai update` in OMP) updates the current project: its MoAI-managed files, its settings, and state left by the earlier Go generation of MoAI (user decision of 2026-11-13 on #2634, Issue #2696). Every write goes through a preview the user sees and an apply bound to that preview's digest, through the same commands PROJECT uses; this route adds no writer of its own.

The user layer — the installed skill, the binary and the global instructions under HOME — is the shell command `moai update`, and this session runs it for the user (user decision 2026-11-16, card C-51): never tell the user to run it in a terminal. When the user asks for that, or a counterpart in step 1 reads `user layer after moai update`, run the preview `moai update --json` with stdin closed (`</dev/null`), because with a terminal on stdin and stderr the command asks `[y/N]` itself (it writes nothing), show what it would change, and ask; it writes under the real HOME, a `guarded` setting, so nothing is applied without the user's pick. After the pick run `moai update --confirm <plan_digest>` with that preview's `plan_digest`. Its separate parts each get their own pick and run, one at a time, with a new preview between them: `moai update --confirm-cleanup <token>` (the preview's `cleanup.confirm_token`: the Go leftovers it lists are archived) and `moai update --confirm-home <token>` (the preview's `home.confirm_token`: the Go generation's `~/.moai` items it lists move to `~/.moai-go-retired/<UTC>/`); the two cannot be combined in one run. An earlier, Go-era `moai` skill folder moves aside only after the user picked its backup preview: `moai update-apply … --confirm-backup-replace <token>`, with `moai recovery-plan` as the way back for a host left pending.

The applied result of `moai update` also carries `models` (card C-47; a preview does not): for each tool (`claude`, `codex`, `omp`, `glm`) and role (`leader`, `agent`) the model, the effort and the source (`saved` from `config/launcher.yaml`, or `default`), and under `unsupported` the saved entries outside the support table by key path (they are kept, never changed). Read it out with the receipt. On the person's own terminal, after the update part, the command itself asks the tool pick, then the leader and agent model and effort of each picked tool and one save question; a yes saves the values and the result then carries a `receipt` id (`models-…`) for the saved file: the text before the write is kept in the receipts folder of the state folder, and the command `moai models-revert <HOME> --receipt <that receipt id> --permission-reference <ref>` puts it back: run it only when the person asks for the undo and only with a permission reference the person gave (never one you made up); it answers `reverted` (the earlier file is back, byte for byte) or `skipped` with the reason `changed_since_apply` (the file changed after the save, so it is left alone), and a refusal exits 1 with an error envelope and changes nothing; this session never answers those questions for the person, and apart from that undo it has no command to change the values from here: when the person wants other values, say they are asked at their next `moai update` in a terminal.

Every question of this route is asked as `internal/questions` says (read it before step 2): a selection through the host's question tool, the recommended option first, never an open question when the options can be listed. Below, "a yes" is the user picking the option that runs the step as printed, and "a no" the option that skips it.

## Input

The current project, its `project.yaml` and the baselines under `manifests/` in its state folder (`.moai/` once `state_root.generation` is `rust`, otherwise `.moai-cli/`), and the user's answers.

## Output

The one preview the user saw, then for each step either its applied receipt or the reason it was skipped; at the end, whether the preview now reads `all_unchanged`.

## Procedure

1. **Preview everything once.** Run `moai project-update-plan <project>`. It writes nothing (Issue #2936). Show the user every phase and every step in one view, in the order printed: for each step its `state`, `reason` and `preview` — the go-state `items`, `go_backup`, `state_moves`, `restores`, `root_files`, `counterparts`, `after_move` and `warnings`; the profile `delta`; the generation `files`; the settings `action` and `conflicts`; the GitHub `files`. Read `counterparts` and `after_move` out before the user answers about the move: each moved kind reads `reinstalled by <step>`, `user layer after moai update` or `no counterpart — will be gone` (those files exist only in the backup afterwards); `after_move` names the folders that end up empty, the include or ignore lines that name a moved path and, when the settings file moves, the hook entries and deny rules that go with it; `unknown: true` means a bounded read gave up and the lists may be incomplete. When the preview has `settings_move`, the Go manifest proves `.claude/settings.json` the earlier generation's: it moves into the backup even when the Go `.moai/` folder stays, last of all, and the files only it named (`freed_by` on their items, `freed` in `settings_move`) move with it. Read out the counts it prints (Go hook entries, deny rules, a status line, files) and say that the install phase writes MoAI's status line and hook set while `claude-settings-merge` offers the rest back; `settings.local.json` and secret-named files stay in place. Settings the install phase has written (the Rust settings receipt owns a key in them) are not offered for a second move, even though the Go manifest still records the path; the one exception is a file that is byte for byte the settings a reverted apply moved, so after `go-state-revert` puts the Go settings back the preview proposes the move again (a restored file the user changed by even one character stays). When the preview has `backup_ignore`, the Go folder stays and the backup area's own `.gitignore` (`file`, for example `.moai-cli/backups/.gitignore`) already exists, but git does not ignore the backup copies (`state` `not_ignored`, `examples` name paths git would offer) or git could not say (`state` `unknown`): the go-state step reads `needs_decision` with no printed command, every install step waits behind it, and the apply would refuse before it writes anything. Read out the file name and the paths, say that the copies include the settings and may hold a token and that no `moai` command edits that file, and ask as a selection: add the line `*` to it (recommended), remove it so that the apply writes one, or stop; after the pick make that one change yourself, then preview again. Never change it without the pick. The phases follow the user's update flow: `backup` (the earlier generation's state moves aside; the phase `reason` names what it does not cover yet), `install` (this generation's profile, managed files and settings), `merge` (the `agents-local-merge` step: the text of the project's `AGENTS.local.md` comes back into `AGENTS.md`, outside the managed section, Issue #2936 R10; the `claude-settings-merge` step: the user's earlier `settings.json` values come back into the new one, Issue #2936 R8; other backed-up instructions do not come back in this version — say so). For the merge step show its `preview.body` (the whole text), `preview.target.starts_at_line` and `preview.commit_notice` (the text goes into `AGENTS.md`, a committed file, while `AGENTS.local.md` may be personal) before asking; a step that reads `blocked` because of `secret_suspects` lists only line numbers and kinds — that file is personal and may hold a secret, so you never open or edit it: ask as a selection whether the user has removed those lines from `AGENTS.local.md` ("I removed them, preview again (recommended)") or leaves this merge out, and preview again after the first. The `claude-settings-merge` step (Issue #2936 R8) offers back what the user had set in the Go generation's `.claude/settings.json`, read from the copy the go-state move left in its backup: show the `preview.candidates` as a table with each key's `state` (`mergeable` — the user may take it; `kept_in_backup` or `go_generated` — it stays in the backup and is not carried, `hooks` is MoAI's as a whole key; `blocked` — named, never shown) and its `summary`, and the `preview.commit_notice` (a merged value goes into `.claude/settings.json`, usually a committed file; permission rules and `env` entries become part of it). When every install step reads `needs_decision` with `run /moai project`, the project has no profile of this generation: when the backup phase has a move, do it first (steps 2–4), then go on to the PROJECT route in this session once the user picks that, and never send the user to type another command; only when there is no profile and no Go-generation state is there nothing to update.
2. **Ask.** Ask about the steps in the printed order, and never about a step that reads `blocked` or `re-run after …` behind an earlier one: the backup phase lists `go-settings` before `go-state`, so a `ready` `go-settings` step (its printed `go-settings-apply` clears the `.moai/` references the Go tool wrote into `.claude/settings.json`, after a backup of that file) is picked and applied first, and the go-state step is asked about in the preview run after it. Ask once for the `ready` steps as a whole, then a separate yes for each `needs_decision` step that prints a command. That yes belongs to the preview run the user was shown and covers only the steps that read `ready` in it (and, with its own yes, a `needs_decision` step that printed a command). A step that read `blocked`, `skip` or `re-run after …` in that run was not shown with its content, so no earlier yes covers it: when a later run makes it `ready`, show that run and ask again. An answer such as "continue" or "install" is not an approval of a step the user has not seen. The merge is one of them: the receipt folder under the state folder's `receipts/` is owner-only and keeps a copy of a personal file that is read in place, so never copy that folder into a repository; the source file stays, `moai agents-merge-revert <project> --receipt <id> --permission-reference <ref>` puts the earlier `AGENTS.md` back while it is unchanged. The go-state move is one: follow PROJECT step 2 (the Go `.moai/` is kept whole as `.moai-backup`, or `.moai-backup-<UTC>` when that name is taken, and a new `.moai/` is made; with only `legacy_root` the earlier `.moai-cli/` state moves into a new `.moai/`). The go-state preview says in `layout` whether the Go folder moves or stays (`folder_moves`, `folder_stays`, `legacy_into_new` or `nothing`): read it out first. `backup_to` is where the backup would go (the apply fills in `<UTC>`) and is `null` when nothing moves; `go_backup` is `null` unless `layout` is `folder_moves`. A `folder_stays` or `nothing` layout with `backup_to` `null` means no backup is made and no step waits for a confirmation on it. A no skips that step and nothing of it is written. The settings merge is one, and it is the user's choice key by key: ask which of the `mergeable` keys to take, as one several-of selection that lists each key with its `summary` (where the host's tool takes one of only: all of them, none, or choose key by key). All of them is the printed command as it is (`apply.stdin` carries the owned keys plus every carriable candidate). Only some: run `moai claude-settings-plan <project>` with a stdin of `apply.stdin` minus the keys they declined, then the apply that plan prints. Nothing is taken on a no, and nothing is lost either: the Go generation's file stays in its backup (`preview.backup`). A go-state step that reads `blocked` prints no command: the earlier state stays where it is — `state_root.generation` is `mixed`, `unknown` or `refuse` (`refuse` covers a `.moai` that is a link or not a folder), or Go or `.moai-cli/` state cannot move (settings the Go manifest does not prove reference `.moai/`, a worktree or nested checkout is inside it, no usable Go manifest). It is reported with its `reason` and nothing is moved (a link is never followed): say what was found and ask as a selection whether to go on with the steps that do not depend on it (recommended) or stop here; this route changes nothing of that state. A generation step that reads `needs_decision` because project agents or skills cannot be rebuilt from the stored state prints no command: offer, as a selection, to regenerate them in this session through PROJECT step 6; nothing is removed. A file or managed part the user edited is planned as `conflict` and kept; report it with its difference and ask as a selection what to do with it, keeping the user's version first (recommended), and never overwrite it by hand. For the Claude Code settings, a key MoAI manages that the user set themselves (for example their own `statusLine`) is a conflict and nothing is written; when the preview offers `confirm_replace`, the step reads `needs_decision` and its printed command is that replacement (`apply.argv` ends with `--confirm-replace <token>`, `apply.stdin` is the keys MoAI owns): show the user the key with its current and new value, and run `claude-settings-apply … --confirm-replace <token>` only after their explicit confirmation (a selection that lists keeping their own value first): the existing file is first kept byte for byte under `settings-backups/` in the state folder, only that key changes, and the answer names the `cp` command that puts the original back (Issue #2383). A `hooks` step reads `ready` when `.claude/settings.json` still runs Go-generation hook scripts: its printed `go-hooks-apply` moves those scripts into a receipt folder, takes the Go entries out of `hooks` and installs the MoAI hook set; `permissions` is not touched. After a go-state move that left the scripts the settings name, this is the step that replaces them. When the proven Go settings themselves moved into the backup (a committed `go-state-apply` that is not reverted), no Go entry is left and the step reads `ready` with `hooks-apply --host claude` instead: the MoAI hook set goes into the new settings. The settings, hooks and merge steps each bind the bytes of `.claude/settings.json`, so apply one, run `moai project-update-plan <project>` again and ask again for the next. It reads `needs_decision` without a printed command when other tools' hook entries share `hooks` (show its `reason` and ask as a selection whether to go on with the other steps (recommended) or stop here; this route never rewrites another tool's hook entries), and `unchanged` when nothing of the Go generation is left. A `codex-skill` step copies the `moai` skill into the project's Codex skill folder only when the user's own Codex skill folder under HOME has no `moai` skill: it reads `skip` when HOME already has one (the project needs no copy) or when no skill package came with this binary, and `needs_decision` with no command when HOME is not set; its printed `project-skill-apply` always carries `--plan-digest` and `--permission-reference`, and a project folder MoAI did not make is `blocked` and kept; so is a project that is the user's HOME or lies in a host configuration folder under it. A `blocked` step names its cause in `reason`; nothing of it is written, and the other steps still stand.
3. **Apply in order.** Run each approved step in the printed order, exactly as printed: the words of `apply.argv` (the first is the `moai` command) with `<permission-reference>` replaced by a permission reference this session composes from the user's pick (one line of at most 128 bytes that names the step and the pick, for example `user-pick:go-state`; it records the pick and is not an authorization check — user decision 2026-11-16, card C-51), and `apply.stdin` on stdin (nothing when it is `null`). Never ask the user to type a reference or a command. Report each receipt. The `hooks` step and the `claude-settings` step rewrite the same `.claude/settings.json`: while the settings step has a command to run, `hooks` reads `blocked` with `re-run after the claude-settings apply`, so apply the settings step, run `moai project-update-plan <project>` again and ask again for the `hooks` step that run makes `ready`. Stop at the first failure and report what was applied and what was not.
4. **After the backup phase, preview again first.** After a go-state apply, run `moai project-update-plan <project>` again before anything else: until then every install step reads `blocked` with `re-run after the backup phase`, because its preview would be stale, and the user has not seen those steps' content: the yes given before the backup phase does not carry over, so ask again for the install steps this new run makes `ready`. Report the receipt and the way back (when the settings moved and an install step already wrote a new `.claude/settings.json`, the revert plan reads `set_aside_then_restore` for it: the revert moves that file into `replaced-by-revert/<UTC>/` of the backup area, keeps it there byte for byte, and puts the earlier one back; nothing is deleted, so never remove it yourself; a link or a folder at that path still reads `conflict` and the revert refuses; `go-hooks-revert` does not remove files the settings and hook steps wrote): `moai go-state-revert-plan <project> --backup <UTC>` and `moai go-state-revert <project> --backup <UTC> --plan-digest <digest> --permission-reference <ref>`. When the go-state step reads `needs_decision` with a `reason` naming state_root `interrupted`, a move stopped midway and the step prints no command: run the read-only `moai go-state-revert-plan <project> --backup <UTC>`, show its result, and ask as a selection whether to run the revert it prints or stop here; move nothing else until the user has picked. The same rule follows a profile apply: the generation step reads `re-run after the profile apply` until the preview is run again, and its files are shown and approved in that new run, not by the yes that covered the profile.
5. **Re-run and report.** Run `moai project-update-plan <project>` once more and report what is left. The project is up to date only when `all_unchanged` is `true`: a re-run plans `unchanged` for every step (a `skip`, such as GitHub templates the project did not choose, counts as nothing to do). Anything else is reported as what is left, never as done. Offer every step that does not read `unchanged` at the end once, in one selection: run it now (recommended when it reads `ready`) or leave it; a step run from there is shown and applied as steps 2–4 say. A `blocked` step is not offered: report it with what unblocks it (its `reason`). The final report follows core rule 18 (`internal/core-rules`): it ends with the checks to try themselves and the decisions made for them, each with how to undo it.
6. **Taking it back.** Undo only in the printed order, last applied first, with the commands exactly as printed: a project's `undo_order` (in the `moai project-update-plan` result; fill each `<…>` from the receipt or backup id the step's apply result printed, `<digest of that plan>` from the plan run just before it) and the user layer's `revert_order` (in the `moai update --confirm` result: the keys of `revert` in the order to run them; the terminal screen prints the same order). Another order does not fail loudly: a revert can answer `reverted` while its result holds a `skipped` entry, and then that part is **not** undone (for example Codex's `~/.codex/AGENTS.md` keeps the `moai-routing` section when routing is reverted before style). Read every revert result's `skipped` and `conflict` and report them as what is left, never as done. A step that prints no command (`codex-hooks`, `codex-config`, `omp-hooks`, or hooks written by `hooks-apply --host claude`) has no revert: say so, and list the `stays` text of `undo_order` as what remains; never remove those files unless the user picked exactly that removal in a selection that named each file.

## Exceptions and Permissions

A running session that reads `.claude/` or writes `.moai/` cannot be detected, and this session cannot close another one: before an apply say so and ask as a selection, "I closed them, continue (recommended)" or "Stop here". Never write a target whose current state could not be read, nor one under a recorded HOLD. A changed project refuses an old digest; preview again instead of retrying. Never edit `project.yaml`, a managed section or a Go-era file by hand to get past a conflict, and never delete what a step moves: it is kept where the step's receipt says (`.moai-backup`, `.moai/backups/` or `.moai-cli/backups/`).

In a project, run the read-only `moai go-state-plan <project>` and show the user every warning it gives about `.worktreeinclude`: a line there that selects secret files such as `.env` makes Claude Code copy them into every new worktree, including the worktrees of the `moai-impl` and `moai-audit` agents (Issue #2670). Name the line and ask as a selection: remove that line (recommended: it stops the copying), or keep it; after the pick make that one change yourself. Never edit that file without the pick (user decision 2026-11-16, card C-51).

## Completion Check

Report each step as applied (with its receipt), skipped (with the reason, including the user's no), conflicted (with the files) or blocked (with its reason and what unblocks it). A cancelled, empty or unanswered question is reported as open, never as a no or a yes. The project is up to date only when the re-run of `moai project-update-plan <project>` reads `all_unchanged`. Host use of `/moai update` for this route is verified only after the installed skill carries this version (not_run until then).
