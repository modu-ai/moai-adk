# UPDATE

`/moai update` updates the current project: its MoAI-managed files, its settings, and state left by the earlier Go generation of MoAI. Every write goes through a preview the user sees and an apply bound to that preview's digest, through the same commands PROJECT uses; this route adds no writer of its own.

Moving state of an earlier MoAI generation is this route's job, not the job of `/moai project`, which only names `/moai update` when such state is found.

**Always ask after the preview.** Right after the preview is shown in `/moai update`, ask the user one selection through the host's question tool, the recommended option first, and record the answer for the report. When something is ready the options are "Apply what is ready (recommended)" and "Leave everything as it is"; when nothing is to apply, say `nothing to apply — no change` and still ask, with "Nothing to do, finish (recommended)" first; when a step reads `blocked`, say `blocked: <its reason>` and ask whether to apply the rest, "Apply the rest (recommended)" first and "Stop here" second. Never run an applying command — `moai update --confirm`, `--confirm-cleanup`, `--confirm-home` or the apply of any step — in a turn where this question has no answer; a cancelled, empty or unanswered question is reported as open, never as a yes, and an earlier "continue" does not answer a new preview. An undo the person asked for by name (`moai models-revert`, step 6) is not an apply of this preview and does not wait for this question. This question is the one ask of step 2 for the `ready` steps as a whole, never a second one, and where the host cannot ask it as a selection, ask it as numbered plain-text choices with the recommended one first, as `internal/questions` says.

The user layer — the installed skill, the binary and the global instructions under HOME — is the shell command `moai update`, and this session runs it for the user: never tell the user to run it in a terminal. When the user asks for that, or a counterpart in step 1 reads `user layer after moai update`, run the preview `moai update --json` with stdin closed (`</dev/null`), because with a terminal on stdin and stderr the command asks `[y/N]` itself (it writes nothing), show what it would change, and ask; it writes under the real HOME, a `guarded` setting, so nothing is applied without the user's pick. After the pick run `moai update --confirm <plan_digest>` with that preview's `plan_digest`. Its separate parts each get their own pick and run, one at a time, with a new preview between them: `moai update --confirm-cleanup <token>` (the preview's `cleanup.confirm_token`: the Go leftovers it lists are archived) and `moai update --confirm-home <token>` (the preview's `home.confirm_token`: the Go generation's `~/.moai` items it lists move to `~/.moai-go-retired/<UTC>/`); the two cannot be combined in one run. An earlier, Go-era `moai` skill folder moves aside only after the user picked its backup preview: `moai update-apply … --confirm-backup-replace <token>`, with `moai recovery-plan` as the way back for a host left pending.

The applied result of `moai update` also carries `models` (a preview does not): for each tool (for example `claude` or `glm`) and role (`leader`, `agent`) the model, the effort and the source (`saved` from `config/launcher.yaml`, or `default`), and under `unsupported` the saved entries outside the support table by key path (they are kept, never changed). Read it out with the receipt. On the person's own terminal, after the update part, the command itself asks the tool pick, then the leader and agent model and effort of each picked tool and one save question; a yes saves the values and the result then carries a `receipt` id (`models-…`) for the saved file: the text before the write is kept in the receipts folder of the state folder, and the command `moai models-revert <HOME> --receipt <that receipt id> --permission-reference <ref>` puts it back: run it only when the person asks for the undo, with a one-line permission reference this session composes from that request as the apply step below does (it records the request and is not an authorization check; never ask the person to type one); it answers `reverted` (the earlier file is back, byte for byte, or removed when there was none) or `skipped` with the reason `changed_since_apply` (the file changed after the save, so it is left alone), and a refusal exits 1 with an error envelope: read its message out, and when it says the settings file `read back differently` after the revert, the file may already be touched, so tell the person to check the file; this session never answers those questions for the person, and apart from that undo it has no command to change the values from here: when the person wants other values, say they are asked at their next `moai update` in a terminal.

Every question of this route is asked as `internal/questions` says (read it before step 2): a selection through the host's question tool, the recommended option first, never an open question when the options can be listed. Below, "a yes" is the user picking the option that runs the step as printed, and "a no" the option that skips it.

## Input

The current project, its `project.yaml` and the baselines under `manifests/` in its state folder (`.moai/` once `state_root.generation` is `rust`, otherwise `.moai-cli/`), and the user's answers.

## Output

The one preview the user saw, then for each step either its applied receipt or the reason it was skipped; at the end, whether the preview now reads `all_unchanged`.

## Procedure

Closing-commit snapshots. In a git work tree, before the first apply of any kind in this route (the first printed `apply.argv` that step 3 runs, or the go-state move's `go-settings-apply` when that comes first), take a snapshot: run `git status --porcelain=v1 -z --untracked-files=all` in the project folder and, for each path it lists, record its content digest: `git hash-object -- <path>` for a file, `link:` and the link text for a symlink (git would follow it, or fail on a dangling one), `dir` for a folder (a nested repository is listed as a folder), `deleted` for a path that no longer exists, and `unreadable` when `git hash-object` fails; `unreadable` counts as changed and never switches step 8 off. Pass each path to a command as one argument, never inside a shell string: a path may hold a space or a newline. After each apply, take it again and give every path that is new, whose status changed or whose digest changed since the last snapshot to that apply; the digest catches a file that was already untracked or modified before the route and that the apply changed further. Never read the paths from an apply's result: a result may name none of the files it wrote (`project-apply` names none). A path whose status and digest are the same in every snapshot is never given to an apply. A path the user edits while the route runs is given to the next step after the edit; step 8 shows it in the list, and the user can leave it uncommitted. Step 8 uses these snapshots. When git cannot answer, take none and step 8 asks nothing.

1. **Preview everything once.** Run `moai project-update-plan <project>`. It writes nothing. Call the step whose id is `generation` "Project harness" in English and "프로젝트 맞춤 하네스" in Korean, and translate that name for any other conversation language; the id stays `generation` for the commands and the JSON, never as the name you say to the user. Show the user every phase and every step in one view, in the order printed: for each step its `state`, `reason` and `preview` — the go-state `items`, `go_backup`, `state_moves`, `restores`, `root_files`, `counterparts`, `after_move` and `warnings`; the profile `delta`; the project harness `files`; the settings `action` and `conflicts`; the GitHub `files`. Read `counterparts` and `after_move` out before the user answers about the move: each moved kind reads `reinstalled by <step>`, `user layer after moai update` or `no counterpart — will be gone` (those files exist only in the backup afterwards); `after_move` names the folders that end up empty, the include or ignore lines that name a moved path and, when the settings file moves, the hook entries and deny rules that go with it; `unknown: true` means a bounded read gave up and the lists may be incomplete. When the preview has `settings_move`, the Go manifest proves `.claude/settings.json` the earlier generation's: it moves into the backup even when the Go `.moai/` folder stays, last of all, and the files only it named (`freed_by` on their items, `freed` in `settings_move`) move with it. Read out the counts it prints (Go hook entries, deny rules, a status line, files) and say that the install phase writes MoAI's status line and hook set while `claude-settings-merge` offers the rest back; `settings.local.json` and secret-named files stay in place. Settings the install phase has written (the Rust settings receipt owns a key in them) are not offered for a second move, even though the Go manifest still records the path; the one exception is a file that is byte for byte the settings a reverted apply moved, so after `go-state-revert` puts the Go settings back the preview proposes the move again (a restored file the user changed by even one character stays). When the preview has `backup_ignore`, the Go folder stays and the backup area's own `.gitignore` (`file`, for example `.moai-cli/backups/.gitignore`) already exists, but git does not ignore the backup copies (`state` `not_ignored`, `examples` name paths git would offer) or git could not say (`state` `unknown`): the go-state step reads `needs_decision` with no printed command, every install step waits behind it, and the apply would refuse before it writes anything. Read out the file name and the paths, say that the copies include the settings and may hold a token and that no `moai` command edits that file, and ask as a selection: add the line `*` to it (recommended), remove it so that the apply writes one, or stop; after the pick make that one change yourself, then preview again. Never change it without the pick. The phases follow the user's update flow: `backup` (the earlier generation's state moves aside; the phase `reason` names what it does not cover yet), `install` (this generation's profile, managed files and settings), `merge` (the `agents-local-merge` step: the text of the project's older personal file `AGENTS.local.md` is copied into `CLAUDE.local.md`, the personal file Claude Code reads, and in a git project the `.gitignore` line for it is added; the `claude-settings-merge` step: the user's earlier `settings.json` values come back into the new one; other backed-up instructions do not come back in this version — say so). For the merge step show its `preview.body` (the whole text), `preview.target.starts_at_line`, `preview.commit_notice` (the text goes into `CLAUDE.local.md`, a personal file that stays out of git; the notice says so when git tracks it), `preview.gitignore` and every line of `preview.warnings` (which files Claude Code stops reading and the official setting that keeps both read) before asking: read the warnings out in plain words. A preview that has `needs_confirmation` also has a `confirm_token`: it is the user's yes to those warnings, so never pass it without asking and never by default, and never ask the user to type it; a step that reads `blocked` because of `secret_suspects` lists only line numbers and kinds — that file is personal and may hold a secret, so you never open or edit it: ask as a selection whether the user has removed those lines from the personal file ("I removed them, preview again (recommended)") or leaves this merge out, and preview again after the first. The `claude-settings-merge` step offers back what the user had set in the Go generation's `.claude/settings.json`, read from the copy the go-state move left in its backup: show the `preview.candidates` as a table with each key's `state` (`mergeable` — the user may take it; `kept_in_backup` or `go_generated` — it stays in the backup and is not carried, `hooks` is MoAI's as a whole key; `blocked` — named, never shown) and its `summary`, and the `preview.commit_notice` (a merged value goes into `.claude/settings.json`, usually a committed file; permission rules and `env` entries become part of it). When every install step reads `needs_decision` with `run /moai project`, the project has no profile of this generation: when the backup phase has a move, do it first (steps 2–4), then go on to the PROJECT route in this session once the user picks that, and never send the user to type another command; only when there is no profile and no Go-generation state is there nothing to update.
2. **Ask.** Ask about the steps in the printed order, and never about a step that reads `blocked` or `re-run after …` behind an earlier one: the backup phase lists `go-settings` before `go-state`, so a `ready` `go-settings` step (its printed `go-settings-apply` clears the `.moai/` references the Go tool wrote into `.claude/settings.json`, after a backup of that file) is picked and applied first, and the go-state step is asked about in the preview run after it. The backup phase's last step `reports` is read out with its `preview` counts (`to_move`, `skipped_existing`, `tracked_left_alone`, `destination`, `examples`) and asked about like any other `ready` step: its printed `reports-move-apply` moves the report files git does not track out of `.moai-cli/reports` and `.moai/reports` to the user-level reports folder (tracked files stay, a name already there is kept, nothing is overwritten), and while it has a command the go-state step reads `re-run after the reports apply`. Ask once for the `ready` steps as a whole, then a separate yes for each `needs_decision` step that prints a command. That yes belongs to the preview run the user was shown and covers only the steps that read `ready` in it (and, with its own yes, a `needs_decision` step that printed a command). A step that read `blocked`, `skip` or `re-run after …` in that run was not shown with its content, so no earlier yes covers it: when a later run makes it `ready`, show that run and ask again. An answer such as "continue" or "install" is not an approval of a step the user has not seen. The `agents-picks` step is one, and it asks for one pick about the older instruction files as a selection: `move` (recommended: the managed section goes into `CLAUDE.md`, the text written in `AGENTS.md` below it and the text written in `AGENTS.local.md` into `CLAUDE.local.md`) or `leave` (nothing is written). Deleting the older files is a later, optional step: once their text is in the CLAUDE files the same step offers `remove-originals`, asked about only on the user's own pick (see the picks paragraph below). `AGENTS.md` and `AGENTS.local.md` stay unchanged by `move` and `leave`, and the standalone personal-file merge (`agents-local-merge`) waits while a pick is pending, so ask about it only when the picks step reads `unchanged` or `skip`. The receipt folder under the state folder's `receipts/` is owner-only and keeps copies of the files a pick or a merge changed, so never copy that folder into a repository; `moai agents-merge-revert <project> --receipt <id> --permission-reference <ref>` puts the earlier files back while they are unchanged and names a file that changed since, which stays as it is. The go-state move is one: follow the go-state move section below (the Go `.moai/` is kept whole as `.moai-backup`, or `.moai-backup-<UTC>` when that name is taken, and a new `.moai/` is made; with only `legacy_root` the earlier `.moai-cli/` state moves into a new `.moai/`). The go-state preview says in `layout` whether the Go folder moves or stays (`folder_moves`, `folder_stays`, `legacy_into_new` or `nothing`): read it out first. `backup_to` is where the backup would go (the apply fills in `<UTC>`) and is `null` when nothing moves; `go_backup` is `null` unless `layout` is `folder_moves`. A `folder_stays` or `nothing` layout with `backup_to` `null` means no backup is made and no step waits for a confirmation on it. A no skips that step and nothing of it is written. The settings merge is one, and it is the user's choice key by key: ask which of the `mergeable` keys to take, as one several-of selection that lists each key with its `summary` (where the host's tool takes one of only: all of them, none, or choose key by key). All of them is the printed command as it is (`apply.stdin` carries the owned keys plus every carriable candidate). Only some: run `moai claude-settings-plan <project>` with a stdin of `apply.stdin` minus the keys they declined, then the apply that plan prints. Nothing is taken on a no, and nothing is lost either: the Go generation's file stays in its backup (`preview.backup`). A go-state step that reads `blocked` prints no command: the earlier state stays where it is — `state_root.generation` is `mixed`, `unknown` or `refuse` (`refuse` covers a `.moai` that is a link or not a folder), or Go or `.moai-cli/` state cannot move (settings the Go manifest does not prove reference `.moai/`, a worktree or nested checkout is inside it, no usable Go manifest). It is reported with its `reason` and nothing is moved (a link is never followed): say what was found and ask as a selection whether to go on with the steps that do not depend on it (recommended) or stop here; this route changes nothing of that state. A generation step that reads `needs_decision` because project agents or skills cannot be rebuilt from the stored state prints no command: offer, as a selection, to regenerate them in this session through PROJECT step 6; nothing is removed. A file or managed part the user edited is planned as `conflict` and kept; report it with its difference and ask as a selection what to do with it, keeping the user's version first (recommended), and never overwrite it by hand. For the Claude Code settings, a key MoAI manages that the user set themselves (for example their own `statusLine`) is a conflict and nothing is written; when the preview offers `confirm_replace`, the step reads `needs_decision` and its printed command is that replacement (`apply.argv` ends with `--confirm-replace <token>`, `apply.stdin` is the keys MoAI owns): show the user the key with its current and new value, and run `claude-settings-apply … --confirm-replace <token>` only after their explicit confirmation (a selection that lists keeping their own value first): the existing file is first kept byte for byte under `settings-backups/` in the state folder, only that key changes, and the answer names the `cp` command that puts the original back. A `hooks` step reads `ready` when `.claude/settings.json` still runs Go-generation hook scripts: its printed `go-hooks-apply` moves those scripts into a receipt folder, takes the Go entries out of `hooks` and installs the MoAI hook set; `permissions` is not touched. After a go-state move that left the scripts the settings name, this is the step that replaces them. When the proven Go settings themselves moved into the backup (a committed `go-state-apply` that is not reverted), no Go entry is left and the step reads `ready` with `hooks-apply --host claude` instead: the MoAI hook set goes into the new settings. The settings, hooks and merge steps each bind the bytes of `.claude/settings.json`, so apply one, run `moai project-update-plan <project>` again and ask again for the next. It reads `needs_decision` without a printed command when other tools' hook entries share `hooks` (show its `reason` and ask as a selection whether to go on with the other steps (recommended) or stop here; this route never rewrites another tool's hook entries), and `unchanged` when nothing of the Go generation is left. A `blocked` step names its cause in `reason`; nothing of it is written, and the other steps still stand.
3. **Apply in order.** Run each approved step in the printed order, exactly as printed: the words of `apply.argv` (the first is the `moai` command) with `<warning-confirmation>`, when the step prints it, replaced by the preview's `confirm_token` only after the user said yes to that step's warnings (leave the apply unrun when the answer is no or missing), and `<permission-reference>` replaced by a permission reference this session composes from the user's pick (one line of at most 128 bytes that names the step and the pick, for example `user-pick:go-state`; it records the pick and is not an authorization check), and `apply.stdin` on stdin (nothing when it is `null`). Never ask the user to type a reference or a command. Report each receipt. The `hooks` step and the `claude-settings` step rewrite the same `.claude/settings.json`: while the settings step has a command to run, `hooks` reads `blocked` with `re-run after the claude-settings apply`, so apply the settings step, run `moai project-update-plan <project>` again and ask again for the `hooks` step that run makes `ready`. Stop at the first failure and report what was applied and what was not.
4. **After the backup phase, preview again first.** After a go-state apply, run `moai project-update-plan <project>` again before anything else: until then every install step reads `blocked` with `re-run after the backup phase`, because its preview would be stale, and the user has not seen those steps' content: the yes given before the backup phase does not carry over, so ask again for the install steps this new run makes `ready`. Report the receipt and the way back (when the settings moved and an install step already wrote a new `.claude/settings.json`, the revert plan reads `set_aside_then_restore` for it: the revert moves that file into `replaced-by-revert/<UTC>/` of the backup area, keeps it there byte for byte, and puts the earlier one back; nothing is deleted, so never remove it yourself; a link or a folder at that path still reads `conflict` and the revert refuses; `go-hooks-revert` does not remove files the settings and hook steps wrote): `moai go-state-revert-plan <project> --backup <UTC>` and `moai go-state-revert <project> --backup <UTC> --plan-digest <digest> --permission-reference <ref>`. When the go-state step reads `needs_decision` with a `reason` naming state_root `interrupted`, a move stopped midway and the step prints no command: run the read-only `moai go-state-revert-plan <project> --backup <UTC>`, show its result, and ask as a selection whether to run the revert it prints or stop here; move nothing else until the user has picked. The same rule follows a profile apply: the generation step reads `re-run after the profile apply` until the preview is run again, and its files are shown and approved in that new run, not by the yes that covered the profile.
5. **Re-run and report.** Run `moai project-update-plan <project>` once more and report what is left. The project is up to date only when `all_unchanged` is `true`: a re-run plans `unchanged` for every step (a `skip`, such as GitHub templates the project did not choose, and an `optional` step, such as `remove-originals`, count as nothing to do). Anything else is reported as what is left, never as done. Offer every step that does not read `unchanged` at the end once, in one selection: run it now (recommended when it reads `ready`) or leave it; a step run from there is shown and applied as steps 2–4 say. Offer them in the order the plan prints: phase `backup`, then `install`, then `merge`, each phase in the order of its steps. A step waits behind an earlier one with the reason the plan prints: `go-state` reads `re-run after the go-settings apply`, `hooks` reads `re-run after the claude-settings apply`, and the merge steps read `re-run after the backup phase` while the backup phase still has a move to make and `re-run after the install phase` behind the install phase; a waiting step is reported with that reason and asked about only after the earlier step is applied and the plan is run again. A `blocked` step is not offered: report it with what unblocks it (its `reason`). A `skip` step and a `needs_decision` step that prints no command are reported with their `reason`, not offered; a step whose target is under a recorded HOLD is left out of the offer and reported as held; an offer that holds any case-(2) step is a case-(2) question as a whole (`internal/questions`, rule 3). The final report follows core rule 18 (`internal/core-rules`): it ends with the checks to try themselves and the decisions made for them, each with how to undo it.
6. **Taking it back.** Undo only in the printed order, last applied first, with the commands exactly as printed: a project's `undo_order` (in the `moai project-update-plan` result; fill each `<…>` from the receipt or backup id the step's apply result printed, `<digest of that plan>` from the plan run just before it) and the user layer's `revert_order` (in the `moai update --confirm` result: the keys of `revert` in the order to run them; the terminal screen prints the same order). Another order does not fail loudly: a revert can answer `reverted` while its result holds a `skipped` entry, and then that part is **not** undone. Read every revert result's `skipped` and `conflict` and report them as what is left, never as done. A step that prints no command (for example hooks written by `hooks-apply --host claude`) has no revert: say so, and list the `stays` text of `undo_order` as what remains; never remove those files unless the user picked exactly that removal in a selection that named each file.
6a. **Name the read deny preview (SPEC-20261122-secret-file-deny-rules).** When the user asks which files Claude Code is kept from reading, or after the report of step 5 when the project holds a `.claudeignore` file (Claude Code does not read that file), tell them that the read-only preview `moai secret-deny-plan <project>` lists the `Read` deny rules it could add, each with the files it matches, and writes nothing; running it is the user's call. This step applies nothing: choosing rules and writing them belong to `/moai project`, which offers the preview as one selection, so name that route and stop. The update route runs no command that writes a deny rule and moves no `.claudeignore` file.
7. **Leftover space (a preview; it carries the retired OPTIMIZE route).** When the user asks how much space the repository's leftovers hold and which of them could go, show it with this step. It is a preview only: this step deletes, moves and writes nothing.
   - **Integration ref.** Use the local ref of the integration branch (for example `origin/<branch>`). The preview reads no network; when the ref may be stale, say so instead of judging around it.
   - **Observations.** Read from the forge, read-only, and write one JSON file in an ignored folder of the project: `schema_version` 1, `audits` {`source`, `items` [{`pr`, `head`, `verdict_comment`, `verdict`}]} with the 40-hex head each verdict names and `PASS` or `FAIL`, `claims` {`source`, `items` [{`issue`, `claim_comment`}]} for every live claim, and `holds` {`source`, `items` [{`issue`}]} for Issues on HOLD or `needs:decision`. A part you could not read stays out of the file; the preview then keeps the rows that need it.
   - **Build roots.** Ask which folders outside the worktrees hold build output to list (for example `/tmp` for `/tmp/moai-rc-target-*`). There is no default root; list none the user did not name. The agent build folders under `~/.moai/build/` are always listed: a row is a candidate only when its owner record proves the worktree gone or its branch merged.
   - **Run.** `moai optimize-plan <project> --integration-ref <ref> [--build-root <dir>]… [--observations <file>]`, with `--retention-days` only when the user gives one (default 7). Quote the envelope's `ok`; a failure is reported as it is.
   - **Show.** One table: kind, path, size, last change, retention, action, reasons and how to restore it; then `totals` with `freeable_bytes`. Show the envelope's `warnings` lines as they are: one appears when the repository has more than 200 worktrees, the primary one counted. Say plainly that a worktree is a `remove` row only with an audit `PASS` for its exact HEAD, that a squash merge counts as merged only in this preview, and that time alone never makes a worktree a candidate.
   - **Stop.** Apply nothing in this step. When the user wants space back, name the next step and wait for their yes: worktree rows go through `moai worktree-gc-plan` and then `moai worktree-gc-apply` with that plan's digest and the user's permission reference — it counts only ancestor merges, so a squash-merged worktree stays there; build folders outside the worktrees and reports have no apply step yet, and are never removed by a shell command instead. Agent build folders under `~/.moai/build/`, left from before builds moved into the worktrees (the RUN workflow, step 1), go only as the rows the user picks, and only while a fresh `moai optimize-plan` preview still marks each one `trim`.
   - The table shown is the output of one `optimize-plan` run on the named ref and observations, quoted with its `preview_digest`. Never report space as freed, or any write, by this step.

8. **Offer the closing commit.** Run it after the re-run of step 5 has been reported on and before the final report, so the commit holds what the steps wrote. Read `git status --porcelain=v1 -z --untracked-files=all` in the project folder: without the last option git shows an untracked folder as one entry and no name check can see inside it. List every changed path under the apply that moved or wrote it (the snapshots of steps 1 to 5 give each path to a step, for example `go-settings-apply`, `go-state-apply`, `project-apply`, the `generation` apply, `claude-settings-apply`, `worktree-move-apply`, `hooks-apply`); a path `go-state-apply` moved or deleted is listed one by one, not as a count. Mark every listed path that `git ls-files` shows as tracked. A listed path that was already changed before the route carries the note "includes changes from before this route", because staging it takes the whole file; a path no step gave goes under "not from this route". A path under `.moai-backup/`, `.moai/backups/`, `.moai/receipts/`, `.moai-cli/backups/`, `.moai-cli/receipts/`, `.moai.rust-*` or a `.before/` folder goes under "kept local" and is never staged: those hold copies of earlier state and local logs. A move that is not committed comes back: a tracked file that a step moved returns at the next `git checkout`, `git stash pop` or `git switch`, and in every worktree made from that branch, so say this before the question. When no path belongs to this route, ask nothing. When `git status` or a snapshot fails (not a repository, or git cannot answer), show git's message and ask nothing. Before the selection, show the proposed commit (the listed paths) as a dry-run diff; the approval covers the commit alone: it never implies a push, changes of the user outside the list are not swept in, and an existing commit is never amended. Otherwise ask one selection: "Commit these changes (recommended)" or "Leave them uncommitted". ## Exceptions and Permissions

A running session that reads `.claude/` or writes `.moai/` cannot be detected, and this session cannot close another one: before an apply say so and ask as a selection, "I closed them, continue (recommended)" or "Stop here". Never write a target whose current state could not be read, nor one under a recorded HOLD. A changed project refuses an old digest; preview again instead of retrying. Never edit `project.yaml`, a managed section or a Go-era file by hand to get past a conflict, and never delete what a step moves: it is kept where the step's receipt says (`.moai-backup`, `.moai/backups/` or `.moai-cli/backups/`).

Deleting is a `guarded` choice: only the user decides it, after seeing the leftover-space preview of step 7. Never touch the real HOME, keys or global settings, never delete a file, branch or worktree from that step, and never stand in for the missing apply step with `rm`, `git worktree remove` or `git clean`. A forge read that failed is reported as unread, never as an empty list.

In a project, run the read-only `moai go-state-plan <project>` and show the user every warning it gives about `.worktreeinclude`: a line there that selects secret files such as `.env` makes Claude Code copy them into every new worktree, including the worktrees of the `moai-impl` agent; the audit worktree is made by the lander with plain git, which Claude Code does not create, so that file does not reach it. Name the line and ask as a selection: remove that line (recommended: it stops the copying), or keep it; after the pick make that one change yourself. Never edit that file without the pick.

## Completion Check

Report each step as applied (with its receipt), skipped (with the reason, including the user's no), conflicted (with the files) or blocked (with its reason and what unblocks it). A cancelled, empty or unanswered question is reported as open, never as a no or a yes. The project is up to date only when the re-run of `moai project-update-plan <project>` reads `all_unchanged`. Host use of `/moai update` for this route is verified only after the installed skill carries this version (not_run until then). The closing commit is reported as committed (with its id and the way back), left uncommitted by the user's pick, or not offered with its reason.
