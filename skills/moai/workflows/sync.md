# SYNC

## Input

A candidate that passed the checks of RUN, its SPEC, the latest base, the document revisions, and the allowed effects.

## Output

The SPEC's `## Result` and status, a document and `@cc:` comment diff, an integration receipt, and a closure. The receipt's field contract is below. In 2026.11.0-rc.1 it is produced by this procedure with `git` and `moai card`, not by a dedicated command, and it is carried in a note on the card rather than in a file; every field that was not measured is written as `not_run`. Per-file apply receipts are a different record and stay under the project state directory's `receipts` folder.

## States

`ready → reconciling → document_proposed → authorized → publishing → confirmed → closed`. A run stops in `needs_rebase` (the candidate does not contain the latest base), `needs_amendment` (the SPEC itself must change), `conflict`, `blocked` (a gate, permission or independent verdict is missing) or `publish_unknown` (an external write ended without a confirmed result). A stop state is reported as it is; it is never rounded up to a pass.

## Before the audit

The order of the stages is the one `internal/sdd` gives: SYNC writes, AUDIT checks. On the candidate branch, before the audit, SYNC makes the SPEC, the documents and the `@cc:` comments match the code: it writes `## Result` from the VERIFY results (each AC met with its evidence, withdrawn with the reason, or what is missing), sets the status, fixes the document mismatches of step 3, keeps the `@cc:` comments true to the code and adds those the change calls for (agents and tools add and link them automatically), runs `moai spec check`, and commits these with the `Moai-Spec` trailer. A requirement without code or tests, or a change outside the SPEC's Scope, is reported and stops the step; it is never written as met. Only after the landing, which closes the card (step 5): the SPEC is archived and the release note written.

## Procedure

1. **Base.** The base depends on the flow. In NeXT-Flow the integration branch is the local branch of `work_flow.integration_branch`: a lane fetches nothing, never chases its tip and only records the base its checks ran on (`flows/next-flow`). The fetch below is for a release pull request, whose base is the remote integration branch. Fetch the integration branch (`<integration>`: the target saved at first setup) and test whether the candidate contains its tip:
   `git fetch origin <integration>` then `git merge-base --is-ancestor "$(git rev-parse origin/<integration>)" <candidate_sha>`. Exit 0: up to date. Exit 1: `needs_rebase` — merge the base into the candidate branch (never rebase a published branch), resolve conflicts keeping both sides' intent, and treat the result as a new candidate. Any other exit is an error, not a result. A PASS measured on an earlier tree is never copied to the new one. On a card the lane only records the base its checks ran on and never merges a moved tip (no tip chase, `flows/next-flow`); the lander deals with a moved tip once, at landing. The merge above is for a release pull request.
2. **Verify the exact tree.** On the exact candidate tree that the lane's ready note names, run the repository's full check set and record each command with its exit code (the RC1 set: `cargo test --offline --locked`, `cargo clippy --offline --locked --all-targets -- -D warnings`, `cargo fmt --check`, `python3 -m unittest discover -s tests -p '*_test.py'`, `git diff --check`, `git diff --cached --check`). A check that did not run is `not_run`; a check that could not run is `blocked` with the reason. A lane's head has no CI run to cite; a merge-only delta of the release pull request may cite its exact-head CI run instead of the local full suite only under the check-run rules in the RUN workflow (section "Check-run rules").
3. **Classify differences** between the implementation and the approved SPEC: an *omission* (the SPEC asks for something the candidate lacks: implement it or report it), an *amendment* (the requirement itself has to change: write an amendment record with the original SPEC digest, the change and "re-approval required", and never lower an acceptance criterion quietly), or a *document mismatch* (only the text is behind: diff the managed documents, preserving user edits). Four further drift kinds are reported the same way when present — each as `(kind, ground, proposed_action)`, separately, and never resolved by weakening the approved SPEC (REQ-B1-01: an approved intent change goes through a SPEC amendment with a new revision and a regression test; an unexplained difference is blocked for review):
   - `spec_oracle_conflict` — the SPEC wording and a test oracle contradict each other. Ground: quote both lines. Proposed action: a SPEC amendment decided by the host, never auto-edited.
   - `broken_reference` — a deletion or rename severed a reference (file path, Issue, release pull request or SPEC id, workflow name). Ground: the dangling target. Proposed action: re-point the reference or restore the target.
   - `done_but_stale_evidence` — an Issue or record claims completion while its cited evidence is missing or stale (the audited or receipt sha is no longer the current HEAD, or the cited check predates the latest change). Ground: the stale reference against the current state. Proposed action: re-run the check and re-attach the evidence.
   - `explicit_link_unreviewed` — an explicit link (References/Closes/same-as/supersession) exists whose meaning was never reconciled. Ground: the link and both ends. Proposed action: review and record the link's semantics before relying on it.
   The basis is the design's seven drift kinds (top design §5: a requirement with no implementation or test link; an implementation change with no requirement or approval; a SPEC/oracle conflict; a broken reference; a done Issue with missing or stale evidence; an approved design change not yet in the SPEC or documents; an explicit link whose meaning was never reviewed). The three kinds above and these four cover all seven, and they report against the RC1 state vocabulary: receipt `pending|committed|recovered`, RUN admission `ready|stale|blocked`, claim `ACTIVE_STATES`. The kind-by-kind correspondence is `docs/design-review/appendix/state-vocabulary-crosswalk.md` (section "SYNC drift"). An explicit REQ link is never, by itself, proof of meaning.
4. **Effects, one permission each.** Push, the release pull request's creation, Issue comment, merge and release are separate effects. Each has its own permission check and operation ID, and approving one never approves another. When a release or release candidate is prepared, run `internal/versioning` `## At every release` before asking for the release effect. Record each external effect with a stable operation marker and an outbox: `effect-intend` before the send, `effect-confirm` after the response. The marker's project slot is the repository id (`gh api repos/<owner>/<repo> --jq .id`), never the repository name, which a rename or transfer changes. The work ledger is the project's card ledger, read and written with `moai card` as the WORK workflow does; Issues are not the work ledger. Without the `moai` command there is no card ledger: the ledger is reported as unavailable (`blocked`) instead of falling back to another store.
5. **Landing and the release pull request.** A card lands as the flow reference says (`flows/next-flow`). A lane only commits, on its own branch in its own worktree, and adds its ready note with its head and the base its checks ran on; it pushes nothing, opens no pull request and merges no moved tip. Only after a passing verdict is recorded on the card (the audit contract, its section "Who records the verdict") does the lander land the head, once, with `moai card land <card> --head <40 hex> --by leader`, which moves the integration branch and closes the card in the same call; when the tip moved after the lane's base, the lander merges the head onto the tip once in a worktree of its own and lands that merge. Builds for local testing and installation are made from the integration branch tip; a broken tip is repaired with a revert commit, landed the same way. A release pull request is the only pull request: only for a real deployment, the lander creates `release/v{head}.{yearweek}.{build}` from the integration branch and opens one pull request to the remote's integration branch (full CI on Linux, macOS and Windows, independent audit by a session with no commits in the range). No pull request goes per card or per lane. Whoever opens that release pull request renders the body with `moai pr-body-render` and opens it with `gh pr create --base <integration> --body-file <file>`; the base is always named, because without `--base` gh uses the repository default branch. The body carries `Refs #<n>` (never `Closes`, `Fixes` or `Resolves`: on a non-default base GitHub ignores them, so closing an Issue is the integration report's job), the exact base and candidate SHAs, the checks with exit codes, the independent review slot, what was not run, and the operation marker `<!-- moai-op pr_create:<repository_id>:<task_key>:<epoch> -->` (`docs/pr-contract.md`; for example `<!-- moai-op pr_create:123456789:08-A:1 -->`). Check the opened PR: `gh pr view <n> --json baseRefName,headRefOid,body` must show `<integration>`, the candidate SHA, and no closing keyword before `#`.
6. **CI evidence.** Query the checks recorded for the release pull request's exact candidate: `gh api repos/<owner>/<repo>/commits/<candidate_sha>/check-runs --jq '.check_runs[] | {name,status,conclusion,head_sha}'`. A `pull_request` run builds the release pull request's merge ref, so record both the head SHA and the merge SHA the run reports. When a merge conflict kept the run from starting, the CI field is `not_run`, not a pass.
7. **Independent review.** Hand a separate session or subagent the approved SPEC digest, the exact candidate SHA and diff, the check results and the questions to answer. Without a verdict from a separate context the state is `blocked`: no card lands and no release pull request is published. A verdict binds only the SHA it names.
8. **Release pull request merge (the integration owner, not the author).** A card is integrated by its landing (step 5); this step is for the release pull request alone. Read the verdict's first line and confirm the pull request head equals the audited SHA. The release pull request merges when its current head has a successful `ci`, read from the head's check runs, and a non-author PASS that cites that run, with no conflict; merge it with the audited head as the expected head, so that a newer push is refused. A new push needs its own CI and a delta re-audit. Never merge the tip into it just to follow it: that invalidates the audit and buys nothing.
9. **Reconcile, then report.** Read every external result back (the release pull request's state and head, comment text, merge commit) before announcing it. After a timeout, do not repeat the write: run `effects-reconcile`, which looks the operation marker up and moves the uncertain effect to confirmed or not_performed without ever re-creating it; only a not_performed effect may be attempted again, as a new intent. Report successes, failures, `not_run`, `blocked`, the remaining work and artifact retention.

## Base agents

Skip this section when you are a base agent yourself: base agents never start other agents.

`moai` installs five base agents into the host's user folder: `moai-plan`, `moai-research`, `moai-impl`, `moai-audit` and `moai-docs`. When this route hands a step to one of them:

- Give it one block, `task`, `scope`, `base` and `refs`, plus `head` where the route's own text below asks for it, and nothing else; it assumes no conversation context.
- Decide on its first line, `RESULT <role> <ok|blocked|not_run> <target>`, then check the rest yourself: the files it lists and the commands and exit codes it reports. An agent's `ok` is not evidence.
- Start agents only from this session, one level deep.
- Use only what the host itself offers. Never stand in for a missing feature with extra sessions, folders or scripts: name the feature as not supported on this host, with the reason, and use the fallback given below.
- When the agent is not installed on this host, do the step in this session and say so.

SYNC hands the writing before the audit — the SPEC's `## Result` and status, the document mismatches of step 3 and the `@cc:` comments — to one `moai-docs` with the host's agent tool, with `scope` naming only those paths; do not write them yourself when the agent is installed. It starts after `moai-impl` has returned, runs in this worktree and never beside `moai-impl`, and you wait for its `RESULT` line before the effects below. The effects in steps 4 to 9 (push, the release pull request, comments, merge) stay with this session: the agent writes files and reports, and never sends anything. Step 7's independent review goes to `moai-audit` as the AUDIT workflow describes, not to the agent that wrote the change.

## Integration receipt fields

One JSON object, `schema_version` 1: `task_id`, `attempt`, `base_sha`, `candidate_sha`, `merge_base`, `spec_digest` (or `null` with "unapproved draft"), `audit_verdict_ref`, `local_checks[]` (`argv`, `exit_code`, `started`, `ended`), `ci_checks[]` (`name`, `head_sha`, `merge_sha`, `status`, `conclusion`, or `not_run`), `effects[]` (`kind`, `operation_id`, `status`), `status` (one of the states above). Generating it twice from the same inputs gives the same bytes and repeats no effect.

## Resume

Read the SPEC's `## Result`, `moai spec check` and the card's notes afresh, and continue at the first state of the list under "States" that is not confirmed. An external write whose result was not read back is reconciled by step 9, never repeated.

## Exceptions and Permissions

SYNC does not merge, release, change branch protection or rulesets, or approve deployment by itself. Repository settings are admin effects and stay with the user.

## Completion Check

Bind the output to the task and the exact snapshot. Never report a verification or external effect that was not performed as complete.
