# SYNC

## Input

A candidate that passed VERIFY, its SPEC, the latest base, the document revisions, and the allowed effects.

## Output

The SPEC's `## Result` and status, a document and `@cc:` comment diff, an integration receipt, and a closure. The receipt's field contract is below. In 2026.11.0-rc.1 it is produced by this procedure with `git` and `gh`, not by a dedicated command, and it is carried in the PR body rather than in a file; every field that was not measured is written as `not_run`. Per-file apply receipts are a different record and stay under the project state directory's `receipts` folder.

## States

`ready → reconciling → document_proposed → authorized → publishing → confirmed → closed`. A run stops in `needs_rebase` (the candidate does not contain the latest base), `needs_amendment` (the SPEC itself must change), `conflict`, `blocked` (a gate, permission or independent verdict is missing) or `publish_unknown` (an external write ended without a confirmed result). A stop state is reported as it is; it is never rounded up to a pass.

## Before the audit

The order is PLAN → RUN → VERIFY → SYNC → AUDIT → merge (`internal/sdd`): SYNC writes, AUDIT checks. On the candidate branch, before the audit, SYNC makes the SPEC, the documents and the `@cc:` comments match the code: it writes `## Result` from the VERIFY results (each AC met with its evidence, withdrawn with the reason, or what is missing), sets the status, fixes the document mismatches of step 3, keeps the `@cc:` comments true to the code and adds those the change calls for (agents and tools add and link them automatically), runs `moai spec check`, and commits these with the `Moai-Spec` trailer. A requirement without code or tests, or a change outside the SPEC's Scope, is reported and stops the step; it is never written as met. Only after the merge: the card is closed, the SPEC archived and the release note written.

## Procedure

1. **Base.** Fetch the integration branch (`<integration>`: the target saved at first setup) and test whether the candidate contains its tip:
   `git fetch origin <integration>` then `git merge-base --is-ancestor "$(git rev-parse origin/<integration>)" <candidate_sha>`. Exit 0: up to date. Exit 1: `needs_rebase` — merge the base into the candidate branch (never rebase a published branch), resolve conflicts keeping both sides' intent, and treat the result as a new candidate. Any other exit is an error, not a result. A PASS measured on an earlier tree is never copied to the new one.
2. **Verify the exact tree.** On the candidate tree that will be pushed, run the repository's full check set and record each command with its exit code (the RC1 set: `cargo test --offline --locked`, `cargo clippy --offline --locked --all-targets -- -D warnings`, `cargo fmt --check`, `python3 -m unittest discover -s tests -p '*_test.py'`, `git diff --check`, `git diff --cached --check`). A check that did not run is `not_run`; a check that could not run is `blocked` with the reason. A merge-only delta may cite the exact-head CI run instead of the local full suite only under the check-run rules in the VERIFY workflow (section "Check-run rules").
3. **Classify differences** between the implementation and the approved SPEC: an *omission* (the SPEC asks for something the candidate lacks: implement it or report it), an *amendment* (the requirement itself has to change: write an amendment record with the original SPEC digest, the change and "re-approval required", and never lower an acceptance criterion quietly), or a *document mismatch* (only the text is behind: diff the managed documents, preserving user edits). Four further drift kinds are reported the same way when present — each as `(kind, ground, proposed_action)`, separately, and never resolved by weakening the approved SPEC (REQ-B1-01: an approved intent change goes through a SPEC amendment with a new revision and a regression test; an unexplained difference is blocked for review):
   - `spec_oracle_conflict` — the SPEC wording and a test oracle contradict each other. Ground: quote both lines. Proposed action: a SPEC amendment decided by the host, never auto-edited.
   - `broken_reference` — a deletion or rename severed a reference (file path, Issue/PR/SPEC id, workflow name). Ground: the dangling target. Proposed action: re-point the reference or restore the target.
   - `done_but_stale_evidence` — an Issue or record claims completion while its cited evidence is missing or stale (the audited or receipt sha is no longer the current HEAD, or the cited check predates the latest change). Ground: the stale reference against the current state. Proposed action: re-run the check and re-attach the evidence.
   - `explicit_link_unreviewed` — an explicit link (References/Closes/same-as/supersession) exists whose meaning was never reconciled. Ground: the link and both ends. Proposed action: review and record the link's semantics before relying on it.
   The basis is the design's seven drift kinds (top design §5: a requirement with no implementation or test link; an implementation change with no requirement or approval; a SPEC/oracle conflict; a broken reference; a done Issue with missing or stale evidence; an approved design change not yet in the SPEC or documents; an explicit link whose meaning was never reviewed). The three kinds above and these four cover all seven, and they report against the RC1 state vocabulary: receipt `pending|committed|recovered`, RUN admission `ready|stale|blocked`, claim `ACTIVE_STATES`. The kind-by-kind correspondence is `docs/design-review/appendix/state-vocabulary-crosswalk.md` (section "SYNC drift"). An explicit REQ link is never, by itself, proof of meaning.
4. **Effects, one permission each.** Push, PR creation, Issue comment, merge and release are separate effects. Each has its own permission check and operation ID, and approving one never approves another. When a release or release candidate is prepared, run `internal/versioning` `## At every release` before asking for the release effect. Record each external effect with a stable operation marker and an outbox: `effect-intend` before the send, `effect-confirm` after the response. The marker's project slot is the repository id (`gh api repos/<owner>/<repo> --jq .id`), never the repository name, which a rename or transfer changes. The work ledger is forge Issues only: there is no local TODO list to move over, and without a connected forge the ledger is reported as unavailable (`blocked`) instead of falling back to a local store (user decision 2026-11-10).
5. **Pull request.** M-Flow (user decisions 2026-11-20; one canonical text, put once per file): (1) Lane: commits on its own card branch and pushes it; gets the independent audit (tier 2: the leader starts it). (2) Lane: after PASS, makes the merge of its head onto the current LOCAL integration branch tip (the primary branch saved at first setup; v2026.11.0 here) in its own worktree, runs `moai check affected <tip>..<merge>` with the binary built in that worktree, and posts `MERGE-READY <card> merge=<40-hex> base=<40-hex> checks=<one line>` on the card. (3) Fast-forward: one at a time under a lock (`~/.moai/locks/<project>-<branch>.lock`), the primary checkout of the integration branch is fast-forwarded with `git merge --ff-only` to that merge. Where the host isolates a lane session to its worktree (Claude Code), the leader's supervision round does this step and writes `MERGED-LOCAL`; where a moai primary-checkout guard is on, the single fixed command `git -C <primary> merge --ff-only refs/moai/lane-merge` is the one allowed (hook-config allow_commands). If the base moved, the lane redoes step 2 on the new tip. (4) Local test and install: builds for local testing and installation are made from the verified LOCAL integration branch tip (not from the remote branch); the leader checks the local tip as a whole from time to time and repairs a broken tip with a revert commit. The statusline shows the branch with commits ahead (↑) and behind (↓) its upstream so local merges are visible. (5) Release: only for a real deployment the leader creates `release/v{head}.{yearweek}.{build}` from the local integration branch and opens one pull request to the remote integration branch (full CI on Linux, macOS and Windows, independent audit by a lane with no commits in the range). No pull request per card, per bundle or per integration. (6) A card that landed locally is closed with `card done` on the local landing evidence, not a pull request. Whoever opens that release pull request renders the body with `moai pr-body-render` and opens it with `gh pr create --base <integration> --body-file <file>`; the base is always named, because without `--base` gh uses the repository default branch. The body carries `Refs #<n>` (never `Closes`, `Fixes` or `Resolves`: on a non-default base GitHub ignores them, so closing an Issue is the integration report's job), the exact base and candidate SHAs, the checks with exit codes, the independent review slot, what was not run, and the operation marker `<!-- moai-op pr_create:<repository_id>:<task_key>:<epoch> -->` (`docs/pr-contract.md`; for example `<!-- moai-op pr_create:123456789:08-A:1 -->`). Check the opened PR: `gh pr view <n> --json baseRefName,headRefOid,body` must show `<integration>`, the candidate SHA, and no closing keyword before `#`.
6. **CI evidence.** Query the checks recorded for the exact candidate: `gh api repos/<owner>/<repo>/commits/<candidate_sha>/check-runs --jq '.check_runs[] | {name,status,conclusion,head_sha}'`. A `pull_request` run builds the PR merge ref, so record both the head SHA and the merge SHA the run reports. When a merge conflict kept the run from starting, the CI field is `not_run`, not a pass.
7. **Independent review.** Hand a separate session or subagent the approved SPEC digest, the exact candidate SHA and diff, the check results and the questions to answer. Without a verdict from a separate context the state is `blocked` and nothing after the PR is published. A verdict binds only the SHA it names.
8. **Integration (the integration owner, not the author).** Read the verdict's first line, confirm the PR head equals the audited SHA and the merge base equals the base tip (otherwise update the branch and re-audit), post the `moai/audit` status on that head (until the ruleset requires the `audit-gate` check instead; that job reads the same verdict, and after a verdict is posted its run is re-run), then merge pinned to it: `gh pr merge <n> --auto --merge --match-head-commit <candidate_sha>`. A new push invalidates the status. Right before merging, run step 1 again; a moved base makes the receipt stale.
   - **Merge train (integration gate of user decision U6, 2026-11-12).** The latest-tip requirement is off: a pull request whose current head has a successful `ci`, read from the head's check runs, and a non-author PASS that cites that run merges without re-merging the tip when it has no conflict and no file both sides changed (a shared file only under `docs/**` that `git merge-tree` merges without conflict, keeping the lines both sides added, does not count; decision D7). A published candidate therefore runs step 1's base merge only when the tip conflicts with it or changed a file it changed — through the leader's update-branch, or its own merge when the leader asks — and the new head needs its CI and a delta re-audit. Never merge the tip just to follow it: the update invalidates the audit status and buys nothing. A branch that was never pushed may merge the tip once before its first push, and a lane opening its own pull request merges the tip first only when `git merge-tree` shows a conflict or a shared file outside that `docs/**` exception (MODE-AGENT workflow, `pr-gate` step).
   - **Pre-stacking on the PR ahead.** When the leader announces it, a candidate may merge the exact audited head of the PR ahead of it (a merge commit, never a rebase) before its turn, and be audited on that stacked tree. Stack only on a predecessor that itself merges into the current tip without conflict; a stacked candidate inherits its predecessor's conflict, and a conflicting PR runs no `pull_request` CI. At the turn, merge the base once as usual: when nothing but the predecessor landed, `git diff <audited head> <new head>` is empty and the re-audit is a tree-identity delta; otherwise the diff is exactly what else landed, and the re-audit covers that diff. While stacked, `lane-handoff-check` (`rev-list --no-merges base..HEAD`) lists the predecessor's commits under `trailers`, and `scope-check` (`base...HEAD`) lists its files; both are expected until the predecessor merges and are recorded as such, not repaired. `claim-verify` already skips them (`--first-parent`). If the predecessor's head changes, re-stack once on the new head.
   - **Docs-only insertion.** While a code PR waits on a repair, the leader may insert a ready docs-only PR into the gap without a train number. A docs-only PR changes no Rust source, test, tool script, CI workflow definition or schema; Markdown documents, skill workflow text and the PR template are docs.
9. **Reconcile, then report.** Read every external result back (PR state and head, comment text, merge commit) before announcing it. After a timeout, do not repeat the write: run `effects-reconcile`, which looks the operation marker up and moves the uncertain effect to confirmed or not_performed without ever re-creating it; only a not_performed effect may be attempted again, as a new intent. Report successes, failures, `not_run`, `blocked`, the remaining work and artifact retention.

## Base agents

Skip this section when you are a base agent yourself: base agents never start other agents.

`moai` installs five base agents into the host's user folder: `moai-plan`, `moai-research`, `moai-impl`, `moai-audit` and `moai-docs`. When this route hands a step to one of them:

- Give it one block, `task`, `scope`, `base` and `refs`, and nothing else; it assumes no conversation context.
- Decide on its first line, `RESULT <role> <ok|blocked|not_run> <target>`, then check the rest yourself: the files it lists and the commands and exit codes it reports. An agent's `ok` is not evidence.
- Start agents only from this session, one level deep.
- Use only what the host itself offers. Never stand in for a missing feature with extra sessions, folders or scripts: name the feature as not supported on this host, with the reason, and use the fallback given below.
- When the agent is not installed on this host, do the step in this session and say so.

SYNC may hand the writing before the audit — the SPEC's `## Result` and status, the document mismatches of step 3 and the `@cc:` comments — to one `moai-docs` at a time, with `scope` naming only those paths. The effects in steps 4 to 9 (push, pull request, comments, merge) stay with this session: the agent writes files and reports, and never sends anything. Step 7's independent review goes to `moai-audit` as the AUDIT workflow describes, not to the agent that wrote the change.

## Integration receipt fields

One JSON object, `schema_version` 1: `task_id`, `attempt`, `base_sha`, `candidate_sha`, `merge_base`, `spec_digest` (or `null` with "unapproved draft"), `audit_verdict_ref`, `local_checks[]` (`argv`, `exit_code`, `started`, `ended`), `ci_checks[]` (`name`, `head_sha`, `merge_sha`, `status`, `conclusion`, or `not_run`), `effects[]` (`kind`, `operation_id`, `status`), `status` (one of the states above). Generating it twice from the same inputs gives the same bytes and repeats no effect.

## Exceptions and Permissions

SYNC does not merge, release, change branch protection or rulesets, or approve deployment by itself. Repository settings are admin effects and stay with the user.

## Completion Check

Bind the output to the task and the exact snapshot. Never report a verification or external effect that was not performed as complete.
