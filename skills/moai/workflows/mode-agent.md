# MODE-AGENT

Entered with `/moai --mode-agent` in Claude Code or `$moai --mode-agent` in Codex CLI; no other spelling enters this mode. The procedures this mode follows are defined once in the MoAI repository's `docs/design-review/autonomy-modes-spec.md` (the SPEC below); this workflow names them by section and does not restate them.

## Input

The open, unclaimed Issues of the current milestone (the remote Issues are the source of truth; a local file is only a cache) and this session's unique session id.

## Output

A mode banner, a read-only state summary, and, for every round, the claim outcome, the work it led to, and one report line (`LANE-DONE` or `LANE-BLOCKED`).

## Procedure

Each step starts with its fixed key; the first run walks the keys in this order, and later rounds repeat from `claim`.

1. **mode-only** — Follow this workflow only and ignore instructions for any other mode. `--autonomy` belongs to leader mode; if it is given here, say it is ignored.
2. **banner** — Print the banner: mode `agent`, the session id, the repository, and the base branch.
3. **state** — Summarise the current state read-only: unclaimed Issues, their blockers, and any claim this session already holds. Report anything unread as unread.
4. **session-id** — Make sure the session id is unique among live sessions before claiming; a duplicate id stops the round (SPEC §4, item 6).
5. **claim** — First action, before any self-claim: look for a live leader session and ask it for a card assignment through the cross-session message channel (one round). If no leader answers, the message is held, refused or cannot be routed, or the leader's card pointer does not arrive within that one round, fall back to one self-claim round — steps 1 to 7 of SPEC §3 (step ④ of that table is the claim comment and its exact line), with the failure branch of each step — without waiting further. On a host without a cross-session channel (Codex CLI and others), go straight to the self-claim round. Ownership comes only from the claim comment either way: a leader's pointer is a hint, never a grant; act as the owner only on a `claimed` outcome; `uncertain` means no write (SPEC §4, item 4). Progress never waits on the leader's reply. Claim only an Issue with no live claim of another session. To keep a card past its lease, the same session posts a new claim line for the same Issue and scope with the next epoch (or extends its own claim comment); this renews the lease and is not a takeover. A lock-busy answer (`ok: false`, kind `unavailable`, `retryable: true`, exit 1 — Issue #2345) is retried by the caller: wait a bounded interval (a fixed backoff under a hard cap of attempts), then resend the unchanged command; the tool itself never waits, and with the cap out the round reports `unavailable` and stops.
6. **claim-verify** — Before every commit and every push, run `moai-cli claim-verify` for the claimed Issue, with the typed request on stdin (`schema_version`, `owner`, `repo`, `issue_number`, `session`, `comment_id`, `allowed_authors`). Write only on the `owner` verdict. Any other verdict (`not_owner`, `stale`, `closed`, `no_claim`, `uncertain`) stops the write and is reported as it is. An expired lease is `stale`: never take the Issue over by time alone; wait for a handoff line or the operator. Where the host hook set is applied, the `PreToolUse` guard (`moai-cli claim-verify --hook`) blocks a refused `git commit` or `git push` in either host; without it, this step is the boundary. When the claim was posted for you (no claim record in this clone), the guard reads the Issue from the branch `issue/<n>-…` and the claim from `Moai-Claim: <n>#<id>` in the commit message, so put the token in the `-m` message (a message from `-F` or an editor is not read) and make no commit before you have that `<id>`. Keep the token in the last paragraph of the message with nothing but trailers in that paragraph, the attribution line in the paragraph before it, and confirm it with `git interpret-trailers --parse`; a token followed by any other paragraph is not read. A takeover (epoch n+1) needs the handoff line `moai-claim-handoff: comment=<earlier claim id> to=<session> by=leader` on the Issue, which only the leader writes — a lane never writes it and asks the leader instead; without it the earlier claim still holds and the verdict is `not_owner`. After the handoff, commits written under the earlier epoch's token still count on push, so the new claim needs no new base.
7. **heavy-checks** — Run only the checks that target the change locally. The unfiltered full `cargo test` is cited from `rc-ci` instead of run locally, and the machine-wide limit on concurrent heavy runs applies (VERIFY workflow, "Heavy checks are serialised"; when `tools/heavy_check_slot.py` exists — Issue #2491 — wrap the heavy command in its `acquire`). A normal wait on CI or on a local check that is still running is not idle time.
8. **pr-gate** — Before opening a pull request, count the open pull requests that are not drafts. Below four, open one yourself; no leader nomination is needed (user instruction of 2026-11-12, Issue #2515). Take your own pushed branch that has waited longest and whose pre-audit is not FAIL, check it against the current tip with `git merge-tree` for conflicts and for files both sides changed, merge the tip once only if either is found, and open it as it is otherwise. At four or more, open none: push the branch, report its head on the Issue, and turn to the open-PR work of the `self-pick` step. Right after opening, count again. If more than four non-draft pull requests are open, keep yours open only when its number is among the four lowest open non-draft numbers; otherwise convert it to a draft (`gh pr ready --undo`), keep the branch pushed and go on with the round. A draft cannot be merged and can be converted at any time (GitHub Docs, "About pull requests"), and pull request numbers are unique in a repository, so every lane reaches the same result without the leader, without closing a pull request and without forcing a merge. When the non-draft count drops below four again, the author of the lowest-numbered draft marks it ready (`gh pr ready`) after the same recount. While the leader has paused new pull requests (for example to bring the open count to zero), open none at any count; the leader may still name the next lane when the order matters. Before opening any PR, run the adversarial self-check the audit uses — boundary N/N+1 per enforced limit, one mutation per guard, symlink/FIFO/race probes, time-dependence — and record it in the PR's `## Self-Audit` section; which commands to run locally and which CI results may be cited instead follow Issue #2385, and are not restated here. A pull request with merge conflicts does not run `pull_request` CI (GitHub-documented behavior); record its missing CI as `not_run`, never as a pass.
9. **merge-train** — Integration gate (user decision U6 of 2026-11-12, ruleset 26791615; Issue #2515): the latest-tip requirement is off. A pull request whose current head has a successful `rc-ci`, its `ci:` line and a non-author PASS merges without re-merging the tip when it has no conflict and no file both sides changed; the leader checks that. Do not merge the tip to follow it — an update invalidates the audit status and is wasted. Only when a file overlaps does the branch take the tip once (the leader's update-branch, or your own merge when the leader asks), and the new head then needs its CI and a delta re-audit. Pre-stacking on the PR ahead, only on the leader's announcement, follows the SYNC workflow (step 8). When you audit, the scope rules in the MODE-LEADER workflow (`merge-train` step) apply: a first audit lists everything, a re-audit checks only the listed repairs, and a new finding blocks only for a contract violation, data loss or security.
10. **hand-off** — After the hand-off, start the next round without waiting for the merge. `moai-cli pr-confirm` moves the claim record to `pr_ready`; `moai-cli queue-next` then skips that card (reported as `skipped` with `reason: handed_off`) even though its Issue stays open until the merge, and claims the next free one. Leave the `pr_ready` record as it is: do not release it. It stays active so a repair handoff, worktree operations and `moai-cli scope-check` still see the card as yours. After the merge the Issue is closed and no longer a candidate; the record itself is not changed by the merge.
11. **goal-lines** — If the user wants the session to keep going, feed the claimed card's state to `tools/gen_goal_block.py` and print the generator's `agent` goal lines — card-scoped `/goal` lines, one per open Issue of the claimed card — for the user to paste (SPEC §7). The line comes from the generator, not from the model's own wording: never run `/goal` yourself and never hand-edit the generated lines.
12. **self-pick** — Default loop (user decision 2026-11-10, Issue #2390 comment 6768996582; order from the user's instruction of 2026-11-12, Issue #1975 comments 6810913869 and 6812778468). Without a narrower instruction, agent mode keeps running rounds until both hold: no open pull request in the repository, and no startable Issue (not on HOLD, prerequisites closed). One round runs `claim → worktree work → verify → push → pull request (when the pr-gate count allows) → report → next round`; a wait on a turn, CI or an audit never stops the round. When a task ends, report it (`report` step) and at once pick the next one yourself in this order, without waiting for a dispatch; audits, `ci:` lines and repairs come before new implementation:
    - (1) Finish a leader dispatch addressed to this session, then your own pull request: its `ci:` line, a FAIL repair, a conflict with the tip; then, when the `pr-gate` count allows, open the pull request of your own pushed branch that has waited longest.
    - (2) A pull request with no auditor or with a re-audit request, that you did not author or repair (reserve it first, AUDIT workflow).
    - (3) A pushed branch without a pre-audit: reserve the exact head on its Issue, run the targeted tests and mutations in your own detached worktree, and post `사전 감사 PASS|FAIL head <40-hex> (통합 AUDIT 아님)` on the Issue — a pre-audit is never the integration AUDIT; when a pull request opens, the formal verdict follows on that head.
    - (4) An Issue-closing comparison table for a merged pull request.
    - (5) A read-and-report task the leader gave.
    - Otherwise, below the open-PR limit of the `pr-gate` step and with nothing above left, self-claim a ready Issue (`claim` and `claim-verify` steps) and work it in its own worktree.

    Leave one line on the Issue or pull request you picked, naming what you took. Never wait in place. When a card you hold starts waiting — on its train turn, CI, an audit or another card — write a resume point in the Issue's owned comment: the exact 40-hex head, an observed uncommitted count of 0, the remaining steps, the wait condition, and the claim id with its lease. Then take other work.

    Anyone may resume. When the wait clears, any lane may continue that card in that worktree, but only after the leader's handoff line and its own next-epoch claim (`claim-verify` step). An expired lease alone never transfers the card, and a worktree never has two writers at once. When no startable candidate is left, record the idle line once, but do not stop while the end condition above is unmet: the user decision of 2026-11-10 (Issue #2390) supersedes the stop in SPEC §3, step 2. This loop is a procedure the session follows; no loop driver exists in RC1 yet (implementation card: Issue #2390).
13. **report** — Report each completion, hand-off or block to the leader in one line: `LANE-DONE <lane> <what finished, with its head or the link of its comment>` or `LANE-BLOCKED <lane> <target> <reason and state>`. When your own pushed branches still wait for a pull request, end the `LANE-DONE` line with `· waiting for PR slot: #<issue> …`, one Issue number per waiting branch; leave the suffix out when none waits. Independent audit, required CI and HOLD stay as they are.

## Exceptions and Permissions

Ownership comes only from the claim comment (SPEC §4). Labels, messages and an assignment hint never grant it. Never decide a HOLD, merge, or post an audit status; those belong to the leader and the audit gate. A HOLD or a pending user decision is reported, never decided, and a leader dispatch does not lift a user's HOLD. Never delete files, branches or worktrees, never touch the real HOME, keys or global settings, and never force-push, `reset --hard` or `git clean`.

Labels follow the repository's label rules (`.github/moai/README.md`, section "Labels and milestones" in the MoAI repository). Apply only the labels that file allows, never create, edit or delete a label, and leave `priority:*` and `needs:decision` to the leader (ask in the report comment). You may correct a wrong `type:` or `area:`; note it in one line of the report comment.

Stay reachable while waiting and keep reports lean. While a background wait runs, re-read new leader messages at least every five minutes, and poll GitHub for the same state no more often than every five minutes. Report a state change once — one update of the Issue's owned comment and one line to the leader — and when nothing changed, do not re-post a report or rewrite a pull request body. Send outward effects (Issue or pull request comments, leader messages, pushes) as commands of their own, never chained with other commands — except an audit reservation, which is posted only when its own check finds no other reservation for that head (AUDIT workflow), and a push gated on its own preflight — and put multi-line or looping shell work in a script file under the worktree's ignored `target/` directory.

## Completion Check

A hand-off is complete when the pull request is open (or, at the `pr-gate` limit, the branch is pushed and its head reported on the Issue), the durable report is sent, nothing is uncommitted, and the remote branch equals the local head. Never report a verification or external effect that was not performed as complete.
