# MODE-AGENT

Entered with `/moai --mode-agent` in Claude Code or `$moai --mode-agent` in Codex CLI; no other spelling enters this mode. The procedures this mode follows are defined once in the MoAI repository's `docs/design-review/autonomy-modes-spec.md` (the SPEC below); this workflow names them by section and does not restate them.

## Input

The open, unclaimed Issues of the current milestone (the remote Issues are the source of truth; a local file is only a cache) and this session's unique session id.

## Output

A mode banner, a read-only state summary, and, for every round, the claim outcome and the work it led to.

## Procedure

1. Follow this workflow only and ignore instructions for any other mode. `--autonomy` belongs to leader mode; if it is given here, say it is ignored.
2. Print the banner: mode `agent`, the session id, the repository, and the base branch.
3. Summarise the current state read-only: unclaimed Issues, their blockers, and any claim this session already holds. Report anything unread as unread.
4. Make sure the session id is unique among live sessions before claiming; a duplicate id stops the round (SPEC §4, item 6).
5. First action, before any self-claim: look for a live leader session and ask it for a card assignment through the cross-session message channel (one round). If no leader answers, the message is held, refused or cannot be routed, or the leader's card pointer does not arrive within that one round, fall back to one self-claim round — steps 1 to 7 of SPEC §3, with the failure branch of each step — without waiting further. On a host without a cross-session channel (Codex CLI and others), go straight to the self-claim round. Ownership comes only from the claim comment either way: a leader's pointer is a hint, never a grant; act as the owner only on a `claimed` outcome; `uncertain` means no write (SPEC §4, item 4). Progress never waits on the leader's reply. A lock-busy answer (`ok: false`, kind `unavailable`, `retryable: true`, exit 1 — Issue #2345) is retried by the caller: wait a bounded interval (a fixed backoff under a hard cap of attempts), then resend the unchanged command; the tool itself never waits, and with the cap out the round reports `unavailable` and stops.
6. Before every commit and every push, run `moai-cli claim-verify` for the claimed Issue. Write only on the `owner` verdict. Any other verdict (`not_owner`, `stale`, `closed`, `no_claim`, `uncertain`) stops the write and is reported as it is. An expired lease is `stale`: never take the Issue over by time alone; wait for a handoff line or the operator. Where the host hook set is applied, the `PreToolUse` guard (`claim-verify --hook`) blocks a refused `git commit` or `git push` in either host; without it, this step is the boundary. When the claim was posted for you (no claim record in this clone), the guard reads the Issue from the branch `issue/<n>-…` and the claim from `Moai-Claim: <n>#<id>` in the commit message, so put the token in the `-m` message (a message from `-F` or an editor is not read) and make no commit before you have that `<id>`. A takeover (epoch n+1) needs the handoff line `moai-claim-handoff: comment=<earlier claim id> to=<session>` on the Issue; without it the earlier claim still holds and the verdict is `not_owner`. After the handoff, commits written under the earlier epoch's token still count on push, so the new claim needs no new base.
7. After the hand-off, start the next round without waiting for the merge. `moai-cli pr-confirm` moves the claim record to `pr_ready`; `moai-cli queue-next` then skips that card (reported as `skipped` with `reason: handed_off`) even though its Issue stays open until the merge, and claims the next free one. Leave the `pr_ready` record as it is: do not release it. It stays active so a repair handoff, worktree operations and `scope-check` still see the card as yours. After the merge the Issue is closed and no longer a candidate; the record itself is not changed by the merge. When no startable candidate is left, record the idle line once, but do not stop while step 10's end condition is unmet: the user decision of 2026-11-10 (Issue #2390) supersedes the stop in SPEC §3, step 2.
8. Merge-train discipline (Issue #2388): integration order is fixed by the leader's public train record, and a candidate merges the base once, at its own train turn. Do not chase the base outside the turn — an out-of-turn update invalidates the audit status and is wasted, because the base moves again before the turn arrives. When the leader announces the turn, merge the base once and treat the result as a new candidate for re-audit. Pre-stacking on the PR ahead, only on the leader's announcement, follows the SYNC workflow (step 8). A pull request with merge conflicts does not run `pull_request` CI (GitHub-documented behavior); record its missing CI as `not_run`, never as a pass. Before opening any PR, run the adversarial self-check the audit uses — boundary N/N+1 per enforced limit, one mutation per guard, symlink/FIFO/race probes, time-dependence — and record it in the PR's `## Self-Audit` section; which commands to run locally and which CI results may be cited instead follow Issue #2385, and are not restated here. Open implementation PRs are capped at 5 (user decision 2026-11-10); above the cap, self-claim audits and repairs instead of new implementation cards — docs-only PRs (as defined in the SYNC workflow, step 8) and flake-repair PRs are exempt. When you audit, the scope rules in the MODE-LEADER workflow (step 8) apply: a first audit lists everything, a re-audit checks only the listed repairs, and a new finding blocks only for a contract violation, data loss or security.
9. If the user wants the session to keep going, feed the claimed card's state to `tools/gen_goal_block.py` and print the generator's `agent` goal lines — card-scoped `/goal` lines, one per open Issue of the claimed card — for the user to paste (SPEC §7). The line comes from the generator, not from the model's own wording: never run `/goal` yourself and never hand-edit the generated lines.
10. Default loop (user decision 2026-11-10, Issue #2390 comment 6768996582). Without a narrower instruction, agent mode keeps running rounds until both hold: no open pull request in the repository, and no startable Issue (not on HOLD, prerequisites closed). Each round, in order:
    - (a) Finish a leader dispatch addressed to this session first.
    - (b) At or above the open-PR cap (step 8), audit or re-audit a pull request you did not author, or repair your own; open no new implementation PR.
    - (c) Below the cap, self-claim a ready Issue (steps 5 and 6), work it in its own worktree, verify, open the PR, and move to the next round without waiting for the merge (step 7).

    Never wait in place. When a card you hold starts waiting — on its train turn, CI, an audit or another card — write a resume point in the Issue's owned comment: the exact 40-hex head, an observed uncommitted count of 0, the remaining steps, the wait condition, and the claim id with its lease. Then take other work.

    Anyone may resume. When the wait clears, any lane may continue that card in that worktree, but only after the leader's handoff line and its own next-epoch claim (step 6). An expired lease alone never transfers the card, and a worktree never has two writers at once.

    Report each completion, hand-off or block to the leader in one line. Independent audit, required CI and HOLD stay as they are. This loop is a procedure the session follows; no loop driver exists in RC1 yet (implementation card: Issue #2390).

## Exceptions and Permissions

Ownership comes only from the claim comment (SPEC §4). Labels, messages and an assignment hint never grant it. Never decide a HOLD, merge, or post an audit status; those belong to the leader and the audit gate.

Labels follow the repository's label rules (`.github/moai/README.md`, section "Labels and milestones" in the MoAI repository). Apply only the labels that file allows, never create, edit or delete a label, and leave `priority:*` and `needs:decision` to the leader (ask in the report comment). You may correct a wrong `type:` or `area:`; note it in one line of the report comment.

Stay reachable while waiting and keep reports lean. While a background wait runs, re-read new leader messages at least every five minutes. Report a state change once — one update of the Issue's owned comment and one line to the leader — and when nothing changed, do not re-post a report or rewrite a pull request body. Send outward effects (Issue or pull request comments, leader messages, pushes) as commands of their own, never chained with other commands — except an audit reservation, which is posted only when its own check finds no other reservation for that head (AUDIT workflow) — and put multi-line or looping shell work in a script file under the worktree's ignored `target/` directory.

## Completion Check

A hand-off is complete when the pull request is open, the durable report is sent, nothing is uncommitted, and the remote branch equals the local head. Never report a verification or external effect that was not performed as complete.
