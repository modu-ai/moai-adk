# WORK

`/moai agent` makes this session an agent (a lane): the session that takes a card from the ledger and works it, not one of the skill's base agents (moai-plan, moai-research, moai-impl, moai-audit, moai-docs) and not a host subagent. It takes one card at a time through the whole flow and repeats until no card is left. Each stage is its own route; this text orders the stages and names the card commands between them.

`/moai agent` sets a mode and is not a command: text after it is never run, and the session says in one line, in the user's conversation language, that instructions come as a message. While a leader is registered, wait for that leader's message once the mode is set; the instruction, the card and its scope arrive in the dispatch (`flows/team-messages`). With no registered leader, take `moai card next` as the take step says.

A session whose name does not already start with `agent-` (it was not started with `moai cc -a`) gives the user the one line `/rename agent-<english name>` once, in the user's conversation language, and reads its own name from the first line of `ListAgents` before it goes on. If that name is not the wanted one after the user's reply, or the user gives none, go on under the name the session has, address others and be addressed by the short id, and write one ledger note that says so.

## Input

The project's card ledger, read with `moai card next`, the SPEC each card names and the worktree each card is worked in. Read the flow reference `flows/next-flow` before the first take: how a lane works, what it submits and how a card lands.

## Output

For every card: the take outcome, what each stage produced, and either the landed head or the blocked note, each recorded as a note on the card (`moai card note`) and on the screen.

## Procedure

1. **take** — First run `pwd` and confirm that the folder and the `project_id` of the `moai card next` answer are the project this session was started for; when they are not, stop with one line. Run `moai card next` and take the card its `next` names: a card in `mine` first (it is already yours), else the first `ready` one. Reserve it with `moai card take <card> --scope <p> --worktree <w> --branch <b>` and keep the `generation` it answers; every later write of the card gives `--generation <g>`. Name the branch `spec/<slug>-<yyyymmdd>`: the slug of the card's SPEC, then its date, the reverse of the SPEC id `SPEC-<yyyymmdd>-<slug>`; `SPEC-20261125-card-no-file-locks` gives `spec/card-no-file-locks-20261125`, and `spec/20261125-card-no-file-locks` is wrong. A branch the dispatch names is used as given. Read the state afresh each time (`moai card next`) — never what you remember, so a restart, a usage-limit stop or a compacted conversation misses nothing. Ownership comes only from your own reservation; an empty or failed output is not a count. Read the HOLD and the prerequisites of a card before you create a worktree for it: a card that `moai card next` lists in `skipped` with the reason `hold` or `prerequisite`, or whose shown record carries a `hold` or an unfinished entry in `prerequisites`, is not taken and gets no worktree; leave it, take the next card, and never lift a HOLD yourself, because only a person lifts it with the unhold command. Read the project's flow and the integration branch from its profile with `moai work-flow-plan --project .` (its `profile` holds both; a profile with no `work_flow` names none) and name both in the first note you write on the card; never type their values from memory.
2. **worktree** — Run `git worktree add -b <branch> <primary checkout>/.claude/worktrees/<name> <integration branch>` from outside every card worktree and enter the result with `EnterWorktree` and its absolute `path`; the paragraph below that begins "Make a card's worktree" gives the order and the reasons.
3. **plan** — Run the PLAN route for the card, which hands the draft to `moai-plan` after `moai-research` has settled each open fact: its SPEC, the acceptance criteria and the task order. A tier 2 change (deleting, permissions, gates, HOME) whose SPEC the user has not approved goes no further than the blocked note below; for every other card the body and criteria are the design, and the lane waits for no approval.
4. **impl** — Run the RUN route in the card's worktree, which hands each planned change to `moai-impl`, one at a time: the test that fails first, then the change and its checks. Before you hand a change over and again before every commit, run `moai card check <card> --generation <g> --path <p>` with every path the change touches; write only when it answers `allowed: true`. Any other answer (another holder, a stale generation, an ended lease, a path outside the scope) stops the write and is reported as it is.
5. **docs** — Run the SYNC route on the same branch, which hands the SPEC Result, the document mismatches and the `@cc:` comments to `moai-docs` after `moai-impl` has returned: the SPEC Result and the documents, and each criterion of the card marked with `moai card criterion <card> <n> --generation <g> --met --evidence <ref>`, or `--withdraw --reason <text>` for one that no longer applies. Commit everything the change and the documents touched.
6. **submit** — Run `moai card submit <card> --generation <g>` (`--mutants <file>` at tier 2) on the clean worktree with every criterion marked: it refuses an unclean worktree or an open criterion by name, runs the fast gates before any long step, quotes or runs the `check affected --card` receipt, writes the READY note, sends the card to review and gives the paths back; a failing step leaves the ledger unchanged and names the step and its log. When this build answers that `submit` is not a card action, do its parts by hand in this order: run `moai check affected --card <base>..<head>` bare, on the checkout at the head, with the session id unset; write the READY note with `moai card note`, whose first line is `LANE-READY-INTEGRATION <card> head=<40 hex>` and which carries the receipt's summary line, each criterion as met, not met or not_run, one `leftovers:` line and one `audit-tier: 0|1|2 <reason>` line; then run `moai card review <card> --generation <g>`.
7. **message** — With a registered leader, send it the one completion message `LANE-DONE <card> <state> head=<10 hex> (<name>)` as the paragraphs below say, then leave the worktree with `ExitWorktree(keep)` and write the same `LANE-DONE` line as the last line of the turn.
8. **wait** — A READY note or a `LANE-DONE` line is not the start signal: with no registered leader, take the next card once, when the ledger shows the previous card done or released (`flows/next-flow`); with a registered leader, wait for that leader's dispatch. Go back to the take step until no card is left: `moai card next` names no card you can take. Handing a card back ends your work on it, not the card: only the landing closes it, and you never end a reservation by hand. With no registered leader the flow ends at the submission: this lane audits and lands nothing. Then report the cards handed back and the blocked ones, each with its reason, and end.

Whenever you start a background run or begin to wait (for an agent, a check or the leader's message), first write one line: what is running, what you wait for and what comes next.

The READY note is the submission signal that starts the independent audit; the ledger state `ready` only says a card can be taken (step 1), and the two are never one signal. When a card is handed back, write the READY or REPAIRED note and give the card back first; only then, with a registered leader, send it one cross-session message (`flows/next-flow`, "Completion message"). Read its session id with `moai session-register --show --name leader`, match that id to a row of the host's session list (`ListAgents`) and address exactly that row, never a row picked by name; with no matching row, send nothing. Any other session is addressed by its listed name, or by the short id when two rows share the name. An agent may also message another agent to check a fact; a verdict, a decision and a repair request go to the ledger as well (`flows/team-messages`). With no leader, no live lease or no channel, write the ledger note only. Send one message per finished card, never a retry; `LANE-DONE` is your last line, after the message when one is sent. The message is a notice, not proof: never send `/clear` to yourself and never take the next card on your own while a leader is registered.

Before you write the READY, REPAIRED or blocked note, read `git status --short` in the worktree: it must print nothing, so commit what is uncommitted first and the head the note names holds it. After a READY or REPAIRED note you make no commit, because the note names the head its checks ran on. After the note, giving the card back and the message to the leader (when one is sent), leave the card's worktree with `ExitWorktree(keep)`, and never remove the worktree or move out of it with a shell `cd`. Write `LANE-DONE` as the last line of the turn, after that tool call. The next card starts outside every card worktree: enter the worktree the leader made with `EnterWorktree` and its `path`, or leave the current one first before you make a new one.

Make a card's worktree from outside every card worktree, with an absolute path, in this order. If you entered a worktree with `EnterWorktree`, leave it with `ExitWorktree(keep)` first, because the host refuses a `git worktree add` into the shared checkout from inside it. Read the primary checkout's path from the first entry of `git worktree list --porcelain`, then run `git worktree add -b <branch> <primary checkout>/.claude/worktrees/<name> <integration branch>`; never give it a relative path, which git resolves against the folder you stand in and so nests the new worktree inside another one. Read `git worktree list --porcelain` again and call `EnterWorktree` with that same absolute `path` only when the path is listed and its folder exists; the host asks the person about a path that does not exist, so an unlisted path is fixed at its creation and never entered. Never make a card worktree with `EnterWorktree` and a `name`: it branches from the remote default branch, not from the integration branch.

Where the project offers lane commands that run a card in a lane of its own, a step may run there; if the lane commands are missing, say so and run the step in the current session.

## When a step stops

| What happened | Next action |
| --- | --- |
| `moai card check` answers anything but `allowed: true` | Write nothing. Note the answer as it is on the card; when the path is needed, write `LANE-BLOCKED kind=decision <card> …` that names the path, and take no other route. |
| a check or a test is red | Read the failing step's log, fix it on the same branch, commit and run that check again; after the third failure of the same step write the blocked note and stop. |
| `moai card submit` refuses | It names the step and its log and leaves the ledger as it was: fix that step and run the command again. |
| the card needs a decision its body and criteria do not give | Write the `LANE-BLOCKED kind=decision` note and go to step 8: with a registered leader wait for its answer, with none take the next card. |
| the leader sends `REPAIR <card> fail head=<head>` after a first FAIL | Run `moai card reopen <card> --generation <g>`, repair on the same branch, and submit again from step 6; the second FAIL goes to the leader. |
| the leader sends `AUDIT-REQUEST <card> ready head=<head>` for a card you did not write | Run the AUDIT route on that exact head and record the verdict with `moai card verdict` from your own session; the author of a change never audits it. |

## Base agents

Skip this section when you are a base agent yourself: base agents never start other agents.

`moai` installs five base agents into the host's user folder: `moai-plan`, `moai-research`, `moai-impl`, `moai-audit` and `moai-docs`. When this route hands a step to one of them:

- Give it one block, `task`, `scope`, `base` and `refs`, plus `head` where the route's own text below asks for it, and nothing else; it assumes no conversation context.
- Decide on its first line, `RESULT <role> <ok|blocked|not_run> <target>`, then check the rest yourself: the files it lists and the commands and exit codes it reports. An agent's `ok` is not evidence.
- Start agents only from this session, one level deep.
- Use only what the host itself offers. Never stand in for a missing feature with extra sessions, folders or scripts: name the feature as not supported on this host, with the reason, and use the fallback given below.
- When the agent is not installed on this host, do the step in this session and say so.

A lane hands each card's plan, implementation and documents to the base agents in turn with the host's agent tool; do not do them yourself when the agents are installed. Start `moai-research` for every open fact first, several at once in one message and one question each, then one `moai-plan`, then `moai-impl` for each planned change one at a time, then one `moai-docs`, and start each only after the previous one's `RESULT` line is in. They work in this worktree (`moai-impl` sets `isolation: none`), so give each only paths that `moai card check` allowed. The agents write files and report; the commits, every `moai card` command, the submit and every message stay with this session.

## Exceptions and Permissions

A card that needs a user decision goes to the ledger: write `LANE-BLOCKED kind=decision <card> <the decision, its options and the default>` as a note on the card, never a question to the user. A session that works a card never opens a selection prompt for the person; whatever it needs decided goes in that note. With no registered leader, take the next card; with a registered leader, leave the blocked card as its note and wait for that leader's dispatch. A HOLD or a `guarded` choice is reported the same way and never decided here. Without the `moai` command there is no card ledger: take nothing and report it once.

## Completion Check

Every card taken in this run is landed with its head named, handed back with the note that names its head (not called done), or carries its blocked note with the reason. Never report a stage, a landing or a check that was not performed as complete.
