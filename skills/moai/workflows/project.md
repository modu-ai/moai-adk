# PROJECT

`/moai project` (`$moai project` in Codex CLI) describes the current project for MoAI: it tells a new project from an existing one, runs the matching interview, records what it detected, and offers the code map. It extends SETUP and keeps SETUP's approval rules. The project facts live in `project.yaml` in the project's state folder — `.moai/` once the project's state is this generation's, otherwise the earlier `.moai-cli/` — and in the AGENTS.md managed section; no product, structure or tech documents are written.

`/moai project` only describes the project; moving the earlier generation's state aside and installing or merging MoAI's managed files belongs to `/moai update`. This route reads the earlier generation's state, says that it is there, and moves nothing.

Every question of this route is asked as `internal/questions` says (read it before the first ask): a selection through the host's question tool, the recommended option first, never an open question when the options can be listed. The session runs every command itself after the user's pick and never tells the user to run one; where a command takes `<ref>` or `<permission-reference>`, this session composes that permission reference from the pick (one line of at most 128 bytes naming the step and the pick; it records the pick and is not an authorization check). Below, "a yes", "agrees" and "approves" mean the user picked the option that runs the step.

## Input

The current folder, the user's request, and the existing `project.yaml` in the state folder when there is one. A folder that a first launch already initialized (`git init`, the profile, AGENTS.md) is still a new project when it holds no code.

## Output

A complete profile for `project-plan` (the detected facts and the interview decisions), the applied profile after the user approves the plan, the managed section and any project agents and skills the user picked, and one suggested `index-build` command. Nothing is written before the plan is approved.

## Procedure

Closing-commit snapshots. In a git work tree, before the first apply of any kind in this route (step 3's `project-apply` or step 4's `generation` apply, whichever runs first), take a snapshot: run `git status --porcelain=v1 -z --untracked-files=all` in the project folder and, for each path it lists, record its content digest: `git hash-object -- <path>` for a file, `link:` and the link text for a symlink (git would follow it, or fail on a dangling one), `dir` for a folder (a nested repository is listed as a folder), `deleted` for a path that no longer exists, and `unreadable` when `git hash-object` fails; `unreadable` counts as changed and never switches the closing commit off. Pass each path to a command as one argument, never inside a shell string: a path may hold a space or a newline. After each apply, and after the "Track it" edit of step 3, take it again and give every path that is new, whose status changed or whose digest changed since the last snapshot to that apply or edit; the digest catches a file that was already untracked or modified before the route and that the apply changed further. Never read the paths from an apply's result: a result may name none of the files it wrote (`project-apply` names none). A path whose status and digest are the same in every snapshot is never given to an apply. A path the user edits while the route runs is given to the next step after the edit; the closing commit shows it in the list, and the user can leave it uncommitted. The closing commit uses these snapshots. When git cannot answer, take none and the closing commit asks nothing.

1. **Detect.** Run `moai project-detect <project>`. It reads the folder and writes nothing. Read `result.detected`:
   - `project_kind` is `new` when no manifest and no code file is found, else `existing`.
   - `manifests`, `languages`, `lsp`, `mcp_servers` and `databases` are facts found in the project's own files. `lsp` names the language servers the languages call for; it does not say a server is installed. `mcp_servers` names servers already configured in the project; MoAI never creates or edits an MCP configuration.
   - Detection reads the project root only for manifests, the dependencies that name `databases`, `prisma/schema.prisma` and the MCP configuration files. A subfolder's `package.json` and a `docker-compose.yml` database image are not read; `languages` alone also counts code files down to three folder levels. The interview fills in what root detection does not see.
   - `project_kind` speaks of code only. A folder with nothing but `prisma/schema.prisma` or `.codex/config.toml` is `new`, and its `databases` and `mcp_servers` are still recorded: they are configuration facts the new-project interview starts from.
   - When `result.profile` is `null`, the folder has no profile yet and `next_actions` names its path (`.moai/project.yaml` or `.moai-cli/project.yaml`) and says to create the profile first. A folder with no MoAI state at all gets `.moai/` and its marker `.moai/moai.json` from that first profile; a folder that already has `.moai-cli/` keeps using it. Create it in this session through the SETUP route (`project-plan`, then `project-apply` after the user's pick) unless a first launch already did, then run `project-detect` again. Never write a profile by hand, and never send the user to type another command for it.
   - `result.versioning` is the versioning scheme the project already shows, read only and never recorded in the profile by detection: `scheme` (`semver`, `calver`, `headver`, `mixed` or `none`), `latest` (the highest version, by version order and not by date), `evidence` (the five highest tag names and the version in the root `Cargo.toml`, `package.json` and `pyproject.toml`, each with the `shape` it was read as) and `tags` (`read`, `no_repository`, or `unavailable` with a `tags_reason`). Step 2 offers keeping it.
   - `result.go_state` and `result.state_root` report earlier-generation project state, read only and without following links: `go_state.moai_dir` is `absent`, `folder`, `link` or `other`, and `state_root` says whose `.moai/` this is (`generation` is `none`, `go`, `rust`, `mixed`, `empty`, `unknown`, `refuse` or `interrupted`) and whether the project still keeps its state in the earlier `.moai-cli/` (`legacy_root`). They sit beside `detected` and never enter the profile. When the earlier generation's state is there, say so once and that `/moai update` moves it; do not preview or move it here. When `generation` is `mixed`, `unknown`, `empty` or `refuse`, show its `reason` and ask as a selection whether to go on with the interview (recommended) or stop here.
2. **Interview by kind.** Read before you ask: what `project-detect`, the profile or the project's own files already answer — the build and test commands in the manifests, the CI files under `.github/`, an existing `AGENTS.md` — is confirmed with the user, not asked, as a selection with the detected value first. A value that reading already knows is confirmed with the user, not asked. Ask only what is left, as `internal/questions` says: at most three questions per call and at most four calls, one axis per question, each a selection with the recommended option first and its options taken from the question bank (`internal/interview`), through the host's question tool whenever the host lists it; plain text is only the fallback that reference states.
   - Every project, new or existing: what must never be touched, what counts as done (a check the user will run themselves), which mistakes a review should always stop, and what may run without asking against what must be asked. Record each answer in `decisions` with `"source": "user"`.
   - Writing language: when the profile has no `language`, ask three questions with `moai language-setup <project>` — the conversation language, the language of commit messages and the language of documents (reports and SPEC documents). Relay the `--questions` set through the host's question tool as one call of three selections, each from the set's `options` with its `suggested` value first and marked recommended, never printed as a bullet list. When the set's `conversation_source` is `installer`, the conversation language is the one the installer saved: show it as a confirmation, not as a question to answer from scratch. Pass the picks back with `--answers` and put its `result.profile` language into the plan of step 3 (after a move of the earlier generation's state its suggested answers come from the backup the move made, listed in `result.go_backup`; nothing is copied), so it is stored in the project profile through `project-plan`/`project-apply` and nowhere else. Everything else is English without asking: instruction files, skills and rules, messages between agents, code comments, issue and PR records. A later run reads the stored value and does not ask again. The generated `AGENTS.md` and `REVIEW.md` managed sections are written in the conversation language (English or Korean; another code falls back to the request language with a warning).
   - New project: the users, tools and languages to start with, development method, hosts, and the collaboration rules. The project's purpose is not asked: draft it from the request and the files and show it in the plan of step 3.
   - Existing project: confirm the detected tools, languages and databases instead of asking for them; then ask for development method, hosts, and what must not change. The purpose is drafted from the README, the manifests and the code layout and shown in the plan of step 3.
   - Work flow: when the profile has no `work_flow`, ask the `work_flow` row of the question bank (`internal/interview`, section "Git work flow") before the versioning rows: m-flow first and recommended, then the other flows the row lists, with the integration branch as a follow-up selection. Put the pick into the plan of step 3 as the profile's `work_flow`.
   - Versioning: when the profile has no `versioning`, ask the `versioning` row of the question bank as `internal/versioning` says (read it before asking that row). When `result.versioning.scheme` names one scheme, keeping it is the first and recommended option, shown with the detected scheme and `result.versioning.latest` so the user can correct a wrong reading; otherwise SemVer is first and recommended, then HeadVer (labelled "suggested with m-flow" when the work flow is m-flow), then CalVer. Ask the CalVer format or the HeadVer head only when the pick needs it. Put the pick into the plan of step 3 as the profile's `versioning`; the managed section of step 4 then carries it as one line.
   - Work ledger: the development method is TDD or preserve-then-change only, recommended by project kind as the question bank says; the work ledger is the local card ledger (`moai card`): it is not asked, it is never recorded under `development_methods`, and GitHub Issues are not offered as a ledger or a method. Which ledger is used is what is not asked; creating it writes under the real HOME and waits for its own pick after the read-only `moai ledger-register-plan <project>` preview. GitHub templates stay an optional opt-in.
   - An axis still unanswered after the last round is recorded in `decisions` as `{"id": "<axis>", "topic": "<axis>", "value": "HOLD", "source": "default", "scope": "project"}` and is asked again on the next run. It is never guessed.
3. **Plan and apply.** Put the answers into `result.profile` (purpose, tools, development methods, hosts, language, versioning, work flow, decisions) and pass it on stdin to `moai project-plan <project>`. Show the plan as the files it will write — each new file with its first lines and each changed file as its difference, the drafted purpose included — and ask for approval only after the user has seen them, as a selection: apply it (recommended), change an answer, or stop. After the user approves it, run `moai project-apply <project> --plan-digest <result.plan_digest> --permission-reference <ref>` with the plan output's `result` object on stdin, not the whole response: the envelope is refused as `invalid typed JSON input`. A re-run with the same facts and answers plans `unchanged`.
   - A plan of `action: conflict` on a profile that has no baseline yet (no `manifests/profile-baseline.json` in the state folder, for example a `schema_version` 1 file) means the tool cannot tell an interview answer from a hand edit, so every changed key is held. Apply in two steps: first plan and apply `result.profile` with every existing value kept and only the detected facts added — that writes the baseline — then plan the interview answers again; they now apply as `update`. Never edit `project.yaml` by hand to get past the conflict.
   - Profile tracking: after `project-apply`, ask git whether the profile file it wrote (`project.yaml` in the state folder, as step 1 names it) is tracked, running in the project folder `git ls-files --error-unmatch -- <profile>`. Exit 0 means tracked and nothing more is asked. On exit 1 run `git check-ignore -q -- <profile>`: exit 1 means the file is only untracked (the closing commit lists it under `project-apply`, whether or not this route changed it), exit 0 means git ignores it. When either command exits with neither 0 nor 1 (128 is not a repository, or git cannot answer), show git's message and ask nothing about tracking. When git ignores the profile, run `git check-ignore -v -- <profile>`, show the file, line and rule it names, and ask one selection: "Track it (recommended)" adds the one line `!<profile path>` at the end of the root `.gitignore` (which is after the rule it names, and outside any block MoAI manages, so a later regeneration does not rewrite it), runs `git check-ignore -q` again and, when git still ignores the profile (a rule on a whole folder cannot be undone by one line), removes exactly that line and reports the rule that still ignores it; "Keep it local" changes nothing and says that a fresh clone will not have the profile. A rule in `.git/info/exclude` or in the global excludes file is not edited — a negation line (one that starts with an exclamation mark) outranks both — and you never edit the global excludes file, which is the user's own setting. A cancelled, empty or unanswered question is "Keep it local". The way back for "Track it" is deleting that one line.
4. **Refresh the managed section.** When AGENTS.md exists, regenerate its managed section so it reflects the applied profile: run `moai project-update-plan <project>` and use its `generation` step. Ask about the `generation` step only when it reads `ready` in that run. While the `profile` step still reads `ready`, `generation` reads `blocked` with `re-run after the profile apply`: apply the profile step the user already agreed to, run `moai project-update-plan <project>` again and ask from that new run, because an earlier yes does not cover a step the user has not seen. A `generation` step that reads `re-run after …` for a step this route does not run (the earlier generation's state still to move) is not asked: report it with the reason the plan prints and leave it to `/moai update`. Show its `preview.files`, and after the user approves run its printed `apply.argv` with `apply.stdin` on stdin and the permission reference composed from their pick in place of `<permission-reference>`. The same plan carries a `REVIEW.md` section when the interview recorded `review_blocks` or `protected`: the mistakes review must stop and what must not change without asking, one line each; an unanswered axis is never written as a rule. Text outside the markers is never touched. On a later `/moai project`, a managed part the user edited by hand is planned as `conflict` and never overwritten — nothing is applied until the user decides; the same holds for generated agent and skill files (`generation-plan`).
5. **Offer project agents and skills.** After the profile is applied, offer project agents and skills built from the answers as one several-of selection, the ones built from a confirmed command first (recommended). There is no fixed count. How the proposals are made is set by the harness proposal; offer none until it is. Each agent is one `native_roles` entry of `generation-plan` with a one-line purpose; its `role_id` is `prj-<name>` for the project's own job: `generation-plan` refuses a name without the prefix, so a project agent never shadows a user-layer `moai-*` agent. Only Claude Code and Codex CLI have an agent file `generation-plan` writes (a Markdown file in the Claude Code agents folder of the project, a TOML file in the Codex CLI one); for any other host, say that none is written. Each project skill is one `project_skills` entry `{"id": "prj-<name>", "purpose": "…"}` whose body `generation-plan` builds from the recorded answers (test and build commands, what review must stop, what must not change); it writes the skill folder Claude Code reads and the one Codex CLI reads, and an unanswered axis is never written. Show the planned files, apply with `generation-apply` only after the user agrees, and on a later run an agent file the user edited by hand is never overwritten: it is planned `unchanged` while the answers stay the same, and `conflict` once they change too.
6. **Offer the code map.** `result.next_actions` carries `moai index-build <project>` (stdin `{"protocol_version":1}`). Offer it as a selection (build it now, recommended; or skip) and run it only after the user agrees. Detection never builds an index.
7. **Offer the closing commit.** Run it just before the final report, so the commit holds what the user wrote; it follows the code map of step 6. Read `git status --porcelain=v1 -z --untracked-files=all` in the project folder: without the last option git shows an untracked folder as one entry and no name check can see inside it. List every changed path under the apply or edit that the snapshots of the Procedure gave it (for example `project-apply`, the `generation` apply, `generation-apply` or the "Track it" edit). The profile file of step 3 and, in the same state folder, its `moai.json` marker and its `manifests/profile-baseline.json`, when git shows them untracked, are listed under `project-apply`, each even when its digest did not change: a fresh clone cannot read the profile without them. A listed path that was already changed before the route (it is in the first snapshot) carries the note "includes changes from before this route", because staging it takes the whole file. A path no snapshot gave to a step goes under "not from this route". A path under `.moai-backup/`, `.moai/backups/`, `.moai/receipts/`, `.moai-cli/backups/`, `.moai-cli/receipts/` or a `.before/` folder goes under "kept local" and is never staged: those folders hold copies of earlier state and local logs. When no path belongs to this route, ask nothing. When `git status` or a snapshot fails (not a repository, or git cannot answer), show git's message and ask nothing. Otherwise ask one selection: "Commit these changes (recommended)" or "Leave them uncommitted". On the commit, first read the index with `git diff --cached --name-only -z` and show any path outside the list as "already staged by you" (it stays staged and is not committed); then stage exactly the listed paths of this route with `git add -- <path>`, one at a time (never `-A`, `.` or a path under "not from this route" or "kept local"), and run `git commit -- <path>` with every listed path of this route after the `--` (a plain `git commit` would take the whole index) and a message in the project's language setting (core rule 7 of `internal/core-rules`) that names the steps, and report the commit id and `git reset --soft HEAD~1` as the way back; the commit does not push. A path with a secret-looking name anywhere in it (a file or folder named like `.env*`, `*.key`, `*.pem`, `*credentials*` or `*secret*`) is listed with that reason and never staged. When `git add` or `git commit` fails, show git's message, name every path already staged, and do not retry in a loop. A cancelled, empty or unanswered question is "Leave them uncommitted" and writes nothing.

When `moai project-update-plan` still shows a step that does not read `unchanged`, end with this one line: "Run `/moai update` to finish the remaining updates."

Final report: before the final report, show one table with a row for every setting the interview or the profile set (the writing language: conversation, commit messages and documents, versioning, work flow, hosts, project agents and skills, the closing commit), with the columns setting, value, written to (the file or key it landed in) and state: `applied`, `default`, `HOLD` or `not applied: <reason>`. A setting the user chose that has no place it was written to is shown as `not applied: <reason>`, never left out, so the user can see that nothing was silently dropped.

## Exceptions and Permissions

Detection reads only files inside the project, never follows symbolic links, and stops at a fixed depth and file count. It never reads HOME, never probes PATH and never starts a program, because `project.yaml` is tracked and holds project facts only. That holds for `result.versioning` too: the tag names are read from the files of the project's own `.git` (the file names under `refs/tags` and the lines of `packed-refs`), never from a git object or the git configuration, and no link inside it is followed. The one exception to "inside the project" is a linked worktree: a `.git` that is a file is followed only for a linked worktree, that is when its `gitdir:` pointer names an admin folder that is `<common>/worktrees/<name>` of the common folder its `commondir` file names and whose `gitdir` file names this folder back (relative pointers, as `git worktree add --relative-paths` writes them, are read too). The tags are then read from that common folder, which is outside the project; the admin and common folders must be real folders, but links in the path leading to them are followed. A submodule's pointer, a pointer to another repository, an admin folder anywhere else, a `.git` that is a link, and a `refs`, `refs/tags` or `packed-refs` that is not a plain folder or file give `tags: unavailable` with the reason, and so do the limits: more than 2,000 entries under `refs/tags`, a `packed-refs` over 4 MiB, and a pointer file over 4,096 bytes. Tag names of more than four `/`-separated parts are skipped (deeper folders are not entered), a name longer than 64 bytes or with anything but ASCII letters, digits and `. - _ + / @` is never considered or shown, and no parent folder's repository is read. MCP configuration files are read for server names only; commands, environment values and tokens are dropped and never reach the output. A profile written by hand in general YAML is refused by `project-plan` until it is reviewed.

## Completion Check

The applied profile's digest matches the approved plan, `detected` matches a fresh `project-detect`, no MCP configuration was created or changed, no index was built without approval, and every unanswered axis is recorded as HOLD. No earlier-generation state was moved by this route. Report a cancelled, empty or unanswered question as open, never as an answer. The final report carries the applied-settings table and follows core rule 18 (`internal/core-rules`): it ends with the checks to try themselves and the decisions made for them, each with how to undo it. Host use of `/moai project` is verified only after the Rust skill replaces the installed one (not_run until then).
