# PROJECT

`/moai project` (`$moai project` in Codex CLI, `/skill:moai project` in OMP) describes the current project for MoAI: it tells a new project from an existing one, runs the matching interview, records what it detected, and offers the code map. It extends SETUP and keeps SETUP's approval rules. The project facts live in `project.yaml` in the project's state folder — `.moai/` once `state_root.generation` is `rust` (Issue #2725), otherwise the earlier `.moai-cli/` — and in the AGENTS.md managed section; no product, structure or tech documents are written (user decision 16 = B, Issue #2496).

Every question of this route is asked as `internal/questions` says (read it before the first ask): a selection through the host's question tool, the recommended option first, never an open question when the options can be listed. The session runs every command itself after the user's pick and never tells the user to run one; where a command takes `<ref>` or `<permission-reference>`, this session composes that permission reference from the pick (one line of at most 128 bytes naming the step and the pick; it records the pick and is not an authorization check). Below, "a yes", "agrees" and "approves" mean the user picked the option that runs the step (user decision 2026-11-16, cards C-51 and C-52).

## Input

The current folder, the user's request, and the existing `project.yaml` in the state folder when there is one. A folder that a first launch already initialized (`git init`, the profile, AGENTS.md — Issue #2481) is still a new project when it holds no code.

## Output

A complete profile for `project-plan` (the detected facts and the interview decisions), the applied profile after the user approves the plan, and one suggested `index-build` command. Nothing is written before the plan is approved.

## Procedure

1. **Detect.** Run `moai project-detect <project>`. It reads the folder and writes nothing. Read `result.detected`:
   - `project_kind` is `new` when no manifest and no code file is found, else `existing`.
   - `manifests`, `languages`, `lsp`, `mcp_servers` and `databases` are facts found in the project's own files. `lsp` names the language servers the languages call for; it does not say a server is installed. `mcp_servers` names servers already configured in the project; MoAI never creates or edits an MCP configuration.
   - Detection reads the project root only for manifests, the dependencies that name `databases`, `prisma/schema.prisma` and the MCP configuration files. A subfolder's `package.json` and a `docker-compose.yml` database image are not read; `languages` alone also counts code files down to three folder levels. The interview fills in what root detection does not see.
   - `project_kind` speaks of code only. A folder with nothing but `prisma/schema.prisma` or `.codex/config.toml` is `new`, and its `databases` and `mcp_servers` are still recorded: they are configuration facts the new-project interview starts from.
   - When `result.profile` is `null`, the folder has no profile yet and `next_actions` names its path (`.moai/project.yaml` or `.moai-cli/project.yaml`) and says to create the profile first. A folder with no MoAI state at all gets `.moai/` and its marker `.moai/moai.json` from that first profile (Issue #2696); a folder that already has `.moai-cli/` keeps using it. Create it in this session through the SETUP route (`project-plan`, then `project-apply` after the user's pick) unless a first launch already did, then run `project-detect` again. Never write a profile by hand, and never send the user to type another command for it.
   - `result.versioning` is the versioning scheme the project already shows (card C-69), read only and never recorded in the profile by detection: `scheme` (`semver`, `calver`, `headver`, `mixed` or `none`), `latest` (the highest version, by version order and not by date), `evidence` (the five highest tag names and the version in the root `Cargo.toml`, `package.json` and `pyproject.toml`, each with the `shape` it was read as) and `tags` (`read`, `no_repository`, or `unavailable` with a `tags_reason`). Step 3 offers keeping it.
   - `result.go_state` reports Go-generation project state, read only and without following links: `moai_dir` is `absent`, `folder`, `link` or `other`, and `go_manifest` says whether the folder holds the Go `manifest.json`. It sits beside `detected` and never enters the profile.
   - `result.state_root` says whose `.moai/` this is (Issue #2725), read only and without following links: `generation` is `none`, `go`, `rust`, `mixed`, `empty`, `unknown`, `refuse` or `interrupted`, with the Go markers it found, the state of the Rust marker `.moai/moai.json` (or the earlier name `.moai/moai-cli.json`, still read; `marker_file` says which one decided), and `legacy_root` when the project still keeps its state in the earlier `.moai-cli/`. When `generation` is `mixed`, `unknown`, `empty` or `refuse`, move nothing in step 2: show its `reason` and ask as a selection whether to go on with the interview (recommended) or stop here. `interrupted` is handled in step 2.
2. **Earlier-generation state (when `state_root.generation` is `go`, or `none` with `legacy_root`).** Do not ask before previewing: the previews are read-only and run without asking (user decision 2026-11-16, card C-51), and the one ask comes after the preview is shown. First run `moai project-update-plan <project>` and follow its backup phase in the printed order, where `go-settings` comes before `go-state`: when the `go-settings` step reads `ready`, show its `preview` (the `.moai/` references the Go tool wrote into `.claude/settings.json`, which its printed `go-settings-apply` clears after a backup of that file), ask for that step alone, run its printed `apply.argv`, and preview again; never ask about a step that reads `blocked` or `re-run after …` behind an earlier step. Then show the go-state preview as the next items say and ask once, after the preview is shown, whether to move the earlier MoAI generation's state aside now. With `none` and `legacy_root`, the state is in the earlier `.moai-cli/` and no Go folder is involved: the same commands below move it into a new `.moai/` (the preview shows a `.moai-cli` item and `state_moves`; Issue #2696). Without a yes, skip this step; nothing moves. When `generation` is `interrupted`, a move stopped midway: run the read-only `moai go-state-revert-plan <project> --backup <UTC>` (the stamp is the folder name under `.moai/backups/`), show its result, ask as a selection whether to run the revert it prints or stop here, and move nothing else until the user has picked.
   - Run the read-only preview `moai go-state-plan <project>` and show its `items` (`move` and `leave`, each with its reason), `go_backup` (the name the Go folder gets), `state_moves` (what moves from `.moai-cli/` into the new `.moai/` and what stays), the `restores` (the user's data folders such as `specs`, `plans`, `docs` and `memory` copied from the Go backup into the new `.moai/`; a file that is not copied says why in `reason`: a secret name is never opened, a config-shaped file (`.json`, `.toml`, `.yaml`, `.yml`) and anything under `specs` is also read for content that looks like a credential, and any other document is checked by its name and size only, never by its content), `root_files`, `counterparts` and `after_move`, and read them out before asking (what this generation puts in place of each moved kind, which kinds are gone for good, the folders left empty, the include or ignore lines that name a moved path), and every `warnings` line. Running sessions that read `.claude/` or write `.moai/` cannot be detected, and this session cannot close another one: say so, and let the one selection carry it — "I closed other sessions, move it" first (recommended when the preview has no warning and no `unknown: true`), then "Leave it where it is".
   - The preview's `layout` says whether the Go folder moves or stays (`folder_moves`, `folder_stays`, `legacy_into_new` or `nothing`): read it out first. `backup_to` is where the backup would go (the apply fills in `<UTC>`) and is `null` when nothing moves; `go_backup` is `null` unless `layout` is `folder_moves`. A `folder_stays` or `nothing` layout with `backup_to` `null` means no backup is made and no step waits for a confirmation on it.
   - Apply only after the user picked the move in the selection that followed that preview: `moai go-state-apply <project> --plan-digest <result.plan_digest> --permission-reference <ref>`. The Go `.moai/` is kept whole as `.moai-backup` (or `.moai-backup-<UTC>` when that name is taken; nothing is overwritten), a new `.moai/` becomes this generation's folder, and its marker `.moai/moai.json` is written last. The proven `.claude/` files go to `.moai/backups/<UTC>/go-state/`, the root instruction files `CLAUDE.md`, `AGENTS.md` and `AGENTS.local.md` are moved to `.moai/backups/<UTC>/root-files/` together with a copy of `.claude/settings.local.json` (the original settings file stays), and nothing is deleted. The backup folders are owner-only and `.moai/backups/.gitignore` keeps them out of git (when the Go folder stays, the area is the earlier root's `.moai-cli/backups/`, which gets the same `.gitignore`). A changed project refuses the digest; preview again instead of retrying.
   - A `root_files` row with `action` `move` is no longer in the project root after the apply: `CLAUDE.md`, `AGENTS.md` and `AGENTS.local.md` are gone from it until the install step writes new ones (`user_choice` is `keep`). A row with `action` `leave` (a link, a file of this generation, a `user_created` file or a `conflict`) stays where it is. After the apply, tell the user where each moved file is and that it is not in the root now, and ask what to do with each as a selection, leaving it in the backup first (recommended: the install step writes a new one); change none of them without their pick (the revert puts them back).
   - Tell the user the receipt path and the way back: `moai go-state-revert-plan <project> --backup <UTC>` shows it, and `moai go-state-revert <project> --backup <UTC> --plan-digest <that plan_digest> --permission-reference <ref>` runs it; this session runs both, the second only after they pick it. The revert sets the new `.moai/` aside as `.moai.rust-<UTC>` (nothing is deleted) and renames the backup back to `.moai`. A `.claude/settings.json` written after the move is moved aside into `replaced-by-revert/<UTC>/` of the backup area first (`set_aside_then_restore` in the revert plan), never deleted.
   - While `.claude/settings.local.json`, or a `.claude/settings.json` the Go manifest does not prove the earlier generation's (not recorded, `user_created`, a link), still names a path under `.moai/`, the preview keeps the whole folder (`leave`). Report that, and do not edit the settings to get past it. A proven `.claude/settings.json` moves into the backup itself (the preview's `settings_move`), whether the folder moves or stays. After a revert, the Go settings that were put back are proposed for the move again, although the install step's settings receipt still owns keys, as long as the file is byte for byte what the reverted apply moved; one changed character and they stay.
   - When the Go folder stays and `.moai-cli/backups/.gitignore` already exists, the preview asks git whether it ignores the backup copies. If not (`backup_ignore` with `state` `not_ignored`, naming the file and example paths) or if git cannot say (`unknown`), no apply is printed and nothing moves: the copies hold the settings and may hold a token. Tell the user the file name and that no `moai` command edits that file, and ask as a selection: add the line `*` to it (recommended), remove it so that the apply writes one, or stop; after the pick make that one change yourself, then preview again. When the file does not exist, the apply writes `*`; a project outside git is not stopped.
3. **Interview by kind.** Read before you ask (Issue #2639): what `project-detect`, the profile or the project's own files already answer — the build and test commands in the manifests, the CI files under `.github/`, an existing `AGENTS.md` — is confirmed with the user, not asked — as a selection with the detected value first. Ask only what is left, as `internal/questions` says: at most three questions per call and at most four calls, one axis per question, each a selection with the recommended option first and its options taken from the question bank (`internal/interview`), through the host's question tool whenever the host lists it; plain text is only the fallback that reference states.
   - Every project, new or existing: what must never be touched, what counts as done (a check the user will run themselves), which mistakes a review should always stop, and what may run without asking against what must be asked — that last answer is sorted the way SKILL.md sorts an open question. Record each answer in `decisions` with `"source": "user"`.
   - Writing language (Issue #2706): when the profile has no `language`, ask it item by item with `moai language-setup <project>` (relay the `--questions` set through the host's question tool — each item a selection from the set's `options` with its `suggested` value first and marked recommended, at most three items per call, never printed as a bullet list — and pass the picks back with `--answers`) and put its `result.profile` language into the plan of step 4 (after a Go-state move its suggested answers come from `.moai-backup/config/sections/language.yaml`, listed in `result.go_backup`; nothing is copied — Issue #2817), so it is stored in the project profile through `project-plan`/`project-apply` and nowhere else. A later run reads the stored value and does not ask again. The generated `AGENTS.md` managed section is written in the stored `instruction_files` language (English or Korean; another code falls back to the conversation language with a warning).
   - New project: purpose, users, tools and languages to start with, development method, hosts, and the collaboration rules.
   - Existing project: confirm the detected tools, languages and databases instead of asking for them; then ask for purpose, development method, hosts, and what must not change.
   - Versioning (card C-69): when the profile has no `versioning`, ask the `versioning` row of the question bank as `internal/versioning` says (read it before asking that row). When `result.versioning.scheme` names one scheme, keeping it is the first and recommended option, shown with the detected scheme and `result.versioning.latest` so the user can correct a wrong reading; otherwise SemVer is first and recommended, then HeadVer, then CalVer. Ask the CalVer format or the HeadVer head only when the pick needs it. Put the pick into the plan of step 4 as the profile's `versioning`; the managed section of step 5 then carries it as one line.
   - Work ledger (user decision 2026-11-16, card C-51): the development method is TDD or DDD only, recommended by project kind as the question bank says; the work ledger is the local card ledger (`moai card`): it is not asked, it is never recorded under `development_methods`, and GitHub Issues are not offered as a ledger or a method. Which ledger is used is what is not asked; creating it writes under the real HOME and waits for its own pick after the read-only `moai ledger-register-plan <project>` preview. GitHub templates stay an optional opt-in.
   - An axis still unanswered after the last round is recorded in `decisions` as `{"id": "<axis>", "topic": "<axis>", "value": "HOLD", "source": "default", "scope": "project"}` and is asked again on the next run. It is never guessed.
4. **Plan and apply.** Put the answers into `result.profile` (purpose, tools, development methods, hosts, versioning, decisions) and pass it on stdin to `moai project-plan <project>`. Show the plan as the files it will write — each new file with its first lines and each changed file as its difference — and ask for approval only after the user has seen them, as a selection: apply it (recommended), change an answer, or stop. After the user approves it, run `moai project-apply <project> --plan-digest <result.plan_digest> --permission-reference <ref>` with the plan output's `result` object on stdin, not the whole response: the envelope is refused as `invalid typed JSON input`. A re-run with the same facts and answers plans `unchanged`.
   - A plan of `action: conflict` on a profile that has no baseline yet (no `manifests/profile-baseline.json` in the state folder, for example a `schema_version` 1 file) means the tool cannot tell an interview answer from a hand edit, so every changed key is held. Apply in two steps: first plan and apply `result.profile` with every existing value kept and only the detected facts added — that writes the baseline — then plan the interview answers again; they now apply as `update`. Never edit `project.yaml` by hand to get past the conflict.
5. **Refresh the managed section.** When AGENTS.md exists, regenerate its managed section so it reflects the applied profile: run `moai project-update-plan <project>` and use its `generation` step (Issue #2936) — show its `preview.files`, and after the user approves run its printed `apply.argv` with `apply.stdin` on stdin and the permission reference composed from their pick in place of `<permission-reference>`. The same plan carries a `REVIEW.md` section when the interview recorded `review_blocks` or `protected` (Issue #2639): the mistakes review must stop and what must not change without asking, one line each; an unanswered axis is never written as a rule. Text outside the markers is never touched. On a later `/moai project`, a managed part the user edited by hand is planned as `conflict` and never overwritten — nothing is applied until the user decides; the same holds for generated agent and skill files (`generation-plan`).
6. **Offer project agents (Issue #2639).** After the profile is applied, offer, as one several-of selection with the ones built from a confirmed command first (recommended), at most three project agents built from the answers, for example a test runner whose purpose names the confirmed test command, or a reviewer whose purpose names the mistakes review must stop. Each is one `native_roles` entry of `generation-plan` with a one-line purpose; its `role_id` is `prj-<name>` for the project's own job (leader design, Issue #2706): `generation-plan` refuses a name without the prefix, so a project agent never shadows a user-layer `moai-*` agent. Only Claude Code and Codex CLI have an agent file `generation-plan` writes (a Markdown file in the Claude Code agents folder of the project, a TOML file in the Codex CLI one); for any other host, say that none is written. Offer project skills the same way: each is one `project_skills` entry `{"id": "prj-<name>", "purpose": "…"}` whose body `generation-plan` builds from the recorded answers (test and build commands, what review must stop, what must not change); it writes the skill folder Claude Code reads and the one Codex CLI reads, and an unanswered axis is never written. Show the planned files, apply with `generation-apply` only after the user agrees, and on a later run an agent file the user edited by hand is never overwritten: it is planned `unchanged` while the answers stay the same, and `conflict` once they change too.
7. **Offer the code map.** `result.next_actions` carries `moai index-build <project>` (stdin `{"protocol_version":1}`). Offer it as a selection (build it now, recommended; or skip) and run it only after the user agrees. Detection never builds an index.

## Exceptions and Permissions

Detection reads only files inside the project, never follows symbolic links, and stops at a fixed depth and file count. It never reads HOME, never probes PATH and never starts a program, because `project.yaml` is tracked and holds project facts only. That holds for `result.versioning` too: the tag names are read from the files of the project's own `.git` (the file names under `refs/tags` and the lines of `packed-refs`), never from a git object or the git configuration, and no link is followed. A `.git` that is a file is followed only for a linked worktree, a `gitdir:` pointer whose folder holds a `commondir` file and names this folder back; a submodule's pointer, a pointer to another repository, a `.git` that is a link, and a `refs/tags` or `packed-refs` over its limit (2,000 entries, 4 MiB) or not a plain folder or file give `tags: unavailable` with the reason, and no parent folder's repository is read. MCP configuration files are read for server names only; commands, environment values and tokens are dropped and never reach the output. A profile written by hand in general YAML is refused by `project-plan` until it is reviewed.

## Completion Check

The applied profile's digest matches the approved plan, `detected` matches a fresh `project-detect`, no MCP configuration was created or changed, no index was built without approval, and every unanswered axis is recorded as HOLD, and Go-generation state moved only after the user agreed to the preview it was shown (with its receipt and revert command reported). Before the final report, offer once, in one selection, every step the user left out or that does not read `unchanged` in a last `moai project-update-plan <project>`: run it now (recommended when it reads `ready`) or leave it; report a `blocked` step with what unblocks it, and a cancelled, empty or unanswered question as open, never as an answer. The final report follows core rule 18 (`internal/core-rules`): it ends with the checks to try themselves and the decisions made for them, each with how to undo it. Host use of `/moai project` is verified only after the Rust skill replaces the installed one (not_run until then).
