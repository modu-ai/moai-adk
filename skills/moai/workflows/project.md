# PROJECT

`/moai project` (`$moai project` in Codex CLI) describes the current project for MoAI: it tells a new project from an existing one, runs the matching interview, records what it detected, and offers the code map. It extends SETUP and keeps SETUP's approval rules. The project facts live in `project.yaml` in the project's state folder — `.moai/` once `state_root.generation` is `rust` (Issue #2725), otherwise the earlier `.moai-cli/` — and in the AGENTS.md managed section; no product, structure or tech documents are written (user decision 16 = B, Issue #2496).

## Input

The current folder, the user's request, and the existing `project.yaml` in the state folder when there is one. A folder that a first launch already initialized (`git init`, the profile, AGENTS.md — Issue #2481) is still a new project when it holds no code.

## Output

A complete profile for `project-plan` (the detected facts and the interview decisions), the applied profile after the user approves the plan, and one suggested `index-build` command. Nothing is written before the plan is approved.

## Procedure

1. **Detect.** Run `moai project-detect <project>`. It reads the folder and writes nothing. Read `result.detected`:
   - `project_kind` is `new` when no manifest and no code file is found, else `existing`.
   - `manifests`, `languages`, `lsp`, `mcp_servers` and `databases` are facts found in the project's own files. `lsp` names the language servers the languages call for; it does not say a server is installed. `mcp_servers` names servers already configured in the project; MoAI never creates or edits an MCP configuration.
   - Detection reads the project root only for manifests, the dependencies that name `databases`, `prisma/schema.prisma` and the MCP configuration files. A subfolder's `package.json` and a `docker-compose.yml` database image are not read; `languages` alone also counts code files down to three folder levels. The interview fills in what root detection does not see.
   - `project_kind` speaks of code only. A folder with nothing but `prisma/schema.prisma` or `.codex/config.toml` is `new`, and its `databases` and `mcp_servers` are still recorded: they are configuration facts the new-project interview starts from.
   - When `result.profile` is `null`, the folder has no profile yet and `next_actions` names its path (`.moai/project.yaml` or `.moai-cli/project.yaml`) and says to create the profile first. Run SETUP (or let a first launch create it), then run `project-detect` again. Never write a profile by hand.
   - `result.go_state` reports Go-generation project state, read only and without following links: `moai_dir` is `absent`, `folder`, `link` or `other`, and `go_manifest` says whether the folder holds the Go `manifest.json`. It sits beside `detected` and never enters the profile.
   - `result.state_root` says whose `.moai/` this is (Issue #2725), read only and without following links: `generation` is `none`, `go`, `rust`, `mixed`, `empty`, `unknown`, `refuse` or `interrupted`, with the Go markers it found, the state of the Rust marker `.moai/moai-cli.json`, and `legacy_root` when the project still keeps its state in the earlier `.moai-cli/`. When `generation` is `mixed`, `unknown`, `empty` or `refuse`, move nothing in step 2: show its `reason` and let the user decide. `interrupted` is handled in step 2.
2. **Go-generation state (only when `state_root.generation` is `go`).** Ask the user whether to move the earlier MoAI generation's state aside now. Without a yes, skip this step; nothing moves. When `generation` is `interrupted`, a move stopped midway: show `moai go-state-revert-plan <project> --backup <UTC>` (the stamp is the folder name under `.moai/backups/`) and move nothing else until the user decides.
   - After a yes, run the read-only preview `moai go-state-plan <project>` and show its `items` (`move` and `leave`, each with its reason), `go_backup` (the name the Go folder gets), `state_moves` (what moves from `.moai-cli/` into the new `.moai/` and what stays), the `restores` (the Go SPECs copied into `.moai/specs`, secrets excluded), `root_files`, and every `warnings` line. Running sessions that read `.claude/` or write `.moai/` cannot be detected, so say so and ask the user to close them first.
   - Apply only after a second yes to that preview: `moai go-state-apply <project> --plan-digest <result.plan_digest> --permission-reference <ref>`. The Go `.moai/` is kept whole as `.moai-backup` (or `.moai-backup-<UTC>` when that name is taken; nothing is overwritten), a new `.moai/` becomes this generation's folder, and its marker `.moai/moai-cli.json` is written last. The proven `.claude/` files and the copies of `CLAUDE.md` and `AGENTS.md` go to `.moai/backups/<UTC>/`, and nothing is deleted. A changed project refuses the digest; preview again instead of retrying.
   - `CLAUDE.md` and `AGENTS.md` themselves stay as they are (`user_choice` is `keep`). After the apply, tell the user where the copies are and ask what to do with each file; change neither without their answer.
   - Tell the user the receipt path and the way back: `moai go-state-revert-plan <project> --backup <UTC>` shows it, and `moai go-state-revert <project> --backup <UTC> --plan-digest <that plan_digest> --permission-reference <ref>` runs it after they agree. The revert sets the new `.moai/` aside as `.moai.rust-<UTC>` (nothing is deleted) and renames the backup back to `.moai`.
   - While `.claude/settings.json` or `settings.local.json` still names a path under `.moai/`, the preview keeps the whole folder (`leave`). Report that, and do not edit the settings to get past it.
3. **Interview by kind.** Read before you ask (Issue #2639): what `project-detect`, the profile or the project's own files already answer — the build and test commands in the manifests, the CI files under `.github/`, an existing `AGENTS.md` — is confirmed with the user, not asked. Ask only what is left, three or four questions at a time and at most three rounds, one axis per question, with the host question tool when there is one, else in the conversation.
   - Every project, new or existing: what must never be touched, what counts as done (a check the user will run themselves), which mistakes a review should always stop, and what may run without asking against what must be asked — that last answer is sorted the way SKILL.md sorts an open question. Record each answer in `decisions` with `"source": "user"`.
   - Writing language (Issue #2706): when the profile has no `language`, ask it item by item with `moai language-setup <project>` (the host question tool takes the `--questions` set and returns `--answers`) and put its `result.profile` language into the plan of step 4, so it is stored in the project profile through `project-plan`/`project-apply` and nowhere else. A later run reads the stored value and does not ask again. The generated `AGENTS.md` managed section is written in the stored `instruction_files` language (English or Korean; another code falls back to the conversation language with a warning).
   - New project: purpose, users, tools and languages to start with, development method, hosts, and the collaboration rules.
   - Existing project: confirm the detected tools, languages and databases instead of asking for them; then ask for purpose, development method, hosts, and what must not change.
   - An axis still unanswered after the last round is recorded in `decisions` as `{"id": "<axis>", "topic": "<axis>", "value": "HOLD", "source": "default", "scope": "project"}` and is asked again on the next run. It is never guessed.
4. **Plan and apply.** Put the answers into `result.profile` (purpose, tools, development methods, hosts, decisions) and pass it on stdin to `moai project-plan <project>`. Show the plan as the files it will write — each new file with its first lines and each changed file as its difference — and ask for approval only after the user has seen them. After the user approves it, run `moai project-apply <project> --plan-digest <result.plan_digest> --permission-reference <ref>` with the plan output's `result` object on stdin, not the whole response: the envelope is refused as `invalid typed JSON input`. A re-run with the same facts and answers plans `unchanged`.
   - A plan of `action: conflict` on a profile that has no baseline yet (no `manifests/profile-baseline.json` in the state folder, for example a `schema_version` 1 file) means the tool cannot tell an interview answer from a hand edit, so every changed key is held. Apply in two steps: first plan and apply `result.profile` with every existing value kept and only the detected facts added — that writes the baseline — then plan the interview answers again; they now apply as `update`. Never edit `project.yaml` by hand to get past the conflict.
5. **Refresh the managed section.** When AGENTS.md exists, regenerate its managed section through `agents-plan` and `agents-apply`, so it reflects the applied profile. The same plan carries a `REVIEW.md` section when the interview recorded `review_blocks` or `protected` (Issue #2639): the mistakes review must stop and what must not change without asking, one line each; an unanswered axis is never written as a rule. Text outside the markers is never touched. On a later `/moai project`, a managed part the user edited by hand is planned as `conflict` and never overwritten — nothing is applied until the user decides; the same holds for generated agent and skill files (`generation-plan`).
6. **Offer project agents (Issue #2639).** After the profile is applied, offer at most three project agents built from the answers, for example a test runner whose purpose names the confirmed test command, or a reviewer whose purpose names the mistakes review must stop. Each is one `native_roles` entry of `generation-plan` with a one-line purpose; its `role_id` is `prj-<name>` for the project's own job (leader design, Issue #2706): `generation-plan` refuses a name without the prefix, so a project agent never shadows a user-layer `moai-*` agent. Only Claude Code and Codex CLI have an agent file `generation-plan` writes (a Markdown file in the Claude Code agents folder of the project, a TOML file in the Codex CLI one); for any other host, say that none is written. Offer project skills the same way: each is one `project_skills` entry `{"id": "prj-<name>", "purpose": "…"}` whose body `generation-plan` builds from the recorded answers (test and build commands, what review must stop, what must not change); it writes the skill folder Claude Code reads and the one Codex CLI reads, and an unanswered axis is never written. Show the planned files, apply with `generation-apply` only after the user agrees, and on a later run an agent file the user edited by hand is never overwritten: it is planned `unchanged` while the answers stay the same, and `conflict` once they change too.
7. **Offer the code map.** `result.next_actions` carries `moai index-build <project>` (stdin `{"protocol_version":1}`). Offer it and run it only after the user agrees. Detection never builds an index.

## Exceptions and Permissions

Detection reads only files inside the project, never follows symbolic links, and stops at a fixed depth and file count. It never reads HOME, never probes PATH and never starts a program, because `project.yaml` is tracked and holds project facts only. MCP configuration files are read for server names only; commands, environment values and tokens are dropped and never reach the output. A profile written by hand in general YAML is refused by `project-plan` until it is reviewed.

## Completion Check

The applied profile's digest matches the approved plan, `detected` matches a fresh `project-detect`, no MCP configuration was created or changed, no index was built without approval, and every unanswered axis is recorded as HOLD, and Go-generation state moved only after the user agreed to the preview it was shown (with its receipt and revert command reported). Host use of `/moai project` is verified only after the Rust skill replaces the installed one (not_run until then).
