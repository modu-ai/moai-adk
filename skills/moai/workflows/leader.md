# LEADER

`/moai leader` makes the window that types it the registered coordination window of the project; the window holds no standing role, and when it ends the lanes go on from the ledger alone. With no registered leader the flow ends at the submission: nothing is audited or landed, and no lane takes that over. Round after round it reads the ledger, answers the lanes, sends audits and lands audited heads.

`/moai leader` sets a mode and is not a command: text after it is never run, and the window says in one line, in the user's conversation language, that instructions come as a message. Before any other action run `pwd` and `moai session-register --names`: its `project` and `leader` say which project this folder belongs to and what this window is called. When the folder is not the project the user or the ledger names, say `another repository` in one line, in the user's conversation language, and stop: the window takes and writes nothing.

A window whose name does not already start with `leader-` (it was not started with `moai cc -l`) gives the user the one line `/rename leader-<project name>` once, in the user's conversation language, with `<project name>` the `project` that `--names` printed, and reads its own name from the first line of `ListAgents` before it goes on. If that name is not the wanted one after the user's reply, or the user gives none, go on under the name the window has, address the lanes and be addressed by the short id, and write one ledger note that says so.

## Input

The project's card ledger (`moai card inbox`, `moai card wait`, `moai card next`), the registry entry of the leader (`moai session-register --show --name leader`) and the lanes' notes. Read the flow reference `flows/next-flow` before the first round: its "Completion message" and "Transition" sections say what a lane sends and what this window does with it.

## Output

For every round: the entry this window holds, the notes it answered, the heads it sent to audit and the heads it landed, each recorded as a note on the card (`moai card note`) and on the screen.

## Procedure

1. **register** — Read the entry with `moai session-register --show --name leader` first. When it answers `free`, register this session with `moai session-register . --name leader --mode leader` and keep the `instance` the answer returns. When it answers `held` and its `session` is this window's own host session id, register nothing again: renew that entry as step 2 says, with the `instance` the answer shows. When another session holds the entry, or the registration is refused with `conflict`, stop with one line that names the holder's lease end and register nothing; a refusal of any other kind is an error to report, not an answer to who leads.
2. **round** — Once per round, before you read the ledger, renew the registration with `moai session-register . --name leader --mode leader --instance <instance>`; the mode is stored only when given, so pass `--mode leader` with every renewal. Then run `moai card orchestrate plan`: it reads the ledger and the registry and changes nothing, and its `actions` list the `clear`, `dispatch`, `audit` and `blocked` items of this round, while `land_queue` and `attention` list the audited heads that wait to land and what waits for the user. Read the ledger with `moai card inbox`, `moai card wait` and `moai card next`; a lane's completion message is a notice that you check against the ledger before you act, as the "Completion message" and "Transition" sections of `flows/next-flow` say. Then do steps 3 to 5 for what the plan lists, in that order; when it lists nothing, wait for the next ledger change and start the round again at this step.
3. **dispatch** — Send the next card's dispatch with the host's message tool; no `moai` command sends a cross-session message yet. The dispatch is the `DISPATCH <card> ready head=<tip>` line and the scope (`flows/team-messages`); address a lane by its listed name. Before every send run `moai session-register --lane-check <listed name>` with the listed name of the receiving session and send only when it answers `lane`; on `not_lane`, or when two rows share the name send to neither and write one ledger note that names the row and the answer. Only when that channel is missing, refused or held, send with `moai lane-send` (it reads the screen first and sends only to a lane that is working or idle) or with the lane-terminal manager's own messaging (its adapter reference names the commands), and when neither exists write the ledger note alone. The lane-terminal manager otherwise stays for `/clear` and for reading a screen. Write each dispatch and answer in the user's conversation language; a message is a notice, so the receiving lane reads the ledger before it acts. Next: step 4 for a head that waits for an audit, otherwise step 2 of the next round.
4. **audit** — Send the audit of a head to a session that wrote none of the change (the AUDIT route); the author of a change never audits it. Name the auditor with `moai card assign <card> --auditor <session id> --by leader` (a lane name is refused, and so is a session that ever held the card), then send `AUDIT-REQUEST <card> ready head=<head to audit>` with the caps and the receipt to cite. The auditor records the verdict with `moai card verdict` from its own session; you read it in the ledger and never write it for the auditor. Next: a `PASS` for that exact head goes to step 5; a `fail` goes to the table below.
5. **land** — Land that head with `moai card land <card> --head <40 hex> --by leader` only after a verdict `PASS` for that exact head; the command accepts only `--by leader` today, so this window is the caller. Use `moai card land-batch C-n=<head> ... --by leader` for 2 to 4 audited heads, which runs the wide check once on their join, and `moai card land` alone only for one head with a risk or an exception. A refusal or a moved tip goes to the table below. A branch that is no card head (such as `main`) enters only through `moai card land-sync <branch> --spec <SPEC-ID> --by leader`, for a branch `work_flow.sync_sources` lists and an approved SPEC; it refuses `conflicts`, `check_failed`, `not_full_pass`, `stale_base` and `drift`, and its answer says whether the branch moved. After the answer says landed, send `LANDED <card> landed head=<10 hex>` to the lane concerned, and send `/clear` and the next dispatch only as the "Transition" section of `flows/next-flow` says. Next: step 2 of the next round.
6. **end** — When the route ends, release the registration with `moai session-register . --name leader --release --instance <instance>`. A window that is closed releases nothing: its lease ends by itself (four hours by default), and the lanes then write the ledger note only. Until then the entry can be freed with `moai session-register . --name leader --release --by leader --instance <instance>`, taking the `instance` from `moai session-register --show --name leader`.

## When a head does not land

| What the ledger or the command says | What it means | Next action |
| --- | --- | --- |
| a first `fail` verdict | the auditor found one of the four blocking kinds | Write the findings as a note on the card and send `REPAIR <card> fail head=<audited head>` to the author; the author takes the card back with `moai card reopen <card> --generation <g>` and repairs on the same branch; the re-audit goes to the first auditor. |
| a second `fail` of the same card | the repair did not meet the criteria | Do not send a re-audit. Decide it as a note on the card: split the card, change the criteria through the user, or hand it to another author. |
| `no_pass` from `moai card land` | no independent `PASS` of that exact head is on the card | Land nothing. Read the card for the newest verdict: when none names this head, return to step 4; a verdict of another head does not count. |
| `stale_base` | the head does not have the tip on its first-parent line | Merge the head onto the tip once, in a worktree of your own, as the "Landing" section of `flows/next-flow` says, then land that merge. |
| `tip_moved` | the branch moved between the read and the move; nothing changed | Read the tip again and run the same landing again; a new tip that is not under the head answers `stale_base`. |
| a head in `dropped` of `moai card land-batch` | it could not be joined or failed the wide check alone | Land the others as the answer says; send the dropped head back as a `fail` with the check's log as a note on the card. |
| `tip_kept_moving` from `moai card land-batch` | the tip moved after three joined checks; nothing landed | Run the same batch again on the new tip. |
| a card held by a session that is gone | the reservation still names the old session, and nobody else may write the card | Run `moai card release <card> --generation <g> --by leader --reason <what was found>` from this window: it ends the reservation when the lease ended or every early proof holds (launcher exited, worktree clean, no process) and the card returns to `ready`. `not_leader`: this session is not the registered leader. `lease_live`: a proof is missing, so the reservation of a live session stays. `verdict_pass`: land the head instead. |
| `reclaim_limit` from `moai card reclaim` | the card used its three reclaims | Release it as the row above says, then any lane takes it with `moai card take`; the limit stays at three. |

## Exceptions and Permissions

A `LANE-BLOCKED kind=decision` note is sorted in the order of the skill entry's paragraph that begins "Sort an open question", case by case: this window decides and records as a note on the card what that order leaves to the leader, and what it sends to the user goes to the user as a selection with the recommended option first and waits for the pick. A timer that repeats the round is armed only as `internal/loop` says. Without the `moai` command there is no registry and no ledger: register nothing and report it once.

## Completion Check

Every round names what it read, answered, sent and landed. A head is called landed only when `moai card land` or `moai card land-batch` answered so, and a message from a lane is never taken for a ledger state.
