# Internal: interview

When to read: before you ask the user about a project, in the PROJECT route or when a plan needs facts only the user has.

This note is the procedure only; the PROJECT workflow (`workflows/project.md`) runs it. The question bank is the table at the end (Issue #2639). How a question reaches the user is in `internal/questions`: read it before the first ask.

1. Read first. Run `moai project-detect` and read the repository; never ask what the files, the build and test commands, CI or an existing `AGENTS.md` already answer.
2. Ask only what reading cannot tell — the project's purpose and users, the places that must not be touched, what "done" means, the mistakes review must always catch, and what may be done without asking — at most three questions per call, each a selection with the recommended option first, through the host's question tool whenever the host lists it (user decision 2026-11-16, cards C-51 and C-52).
3. Show the plan before anything is written: the files that would be created with their first lines, and the difference for each file that would change (`project-plan`).
4. Write only after the user approves the plan, and only through `project-apply`. A later run reports hand edits as differences and never overwrites them.
5. Record each answer with where it came from: the user's words, or the file and line that answered it.

## Question bank (Issue #2639)

Go down the table and skip every row that reading already answered; when reading answered it, record that instead with `"source": "repo"` and the file and line. Ask the rest at most three per call. Every row is a selection (user decision 2026-11-16, card C-51): offer the options its `Options` cell names, detected candidates before general ones, the recommended one first and marked; the host's own "Other" takes an answer the options miss, so never add one. A row marked profile fills that profile field; every other answer is a `decisions` entry `{"id": "<id>", "topic": "<id>", "value": "<the picked option's text, or the user's words>", "source": "user", "scope": "project"}`. Keep the row id as the decision id, so a later step finds the answer by it.

The work ledger is not a row: it is the local card ledger (`moai card`), it is not asked, and GitHub Issues are not offered as a ledger or a method (user decision 2026-11-16, card C-51).

The `decision_model` row (card C-54) is recorded as the `decisions` entry `decision_model` with the value `off` (not used), `typesafe` (Jev) or `openai` (OpenAI). `off` is the default and makes no network call. A provider pick is followed by the key question of `workflows/project.md`: the key itself is never asked here and never passes through the question tool.

The three `versioning` rows (card C-69) fill one profile field: `versioning` is `{"scheme": "semver" | "headver" | "calver" | "custom"}` with `"format"` from `versioning_format` or `"head"` (a number) from `versioning_head`. Read `internal/versioning` before you ask them: it states the three schemes and when keeping the existing one is the recommendation. The second and third row are asked only when the pick needs them, in the call after the pick. The keep option names the detected scheme and `versioning.latest`, the highest version by version order, so the user can correct a wrong reading. An answer through the host's "Other" to the `versioning` row is recorded as `{"scheme": "custom", "format": "<the user's words in one line>"}` and neither follow-up row is asked; the text rules it must pass, credential shapes included, are in `internal/versioning`. An "Other" answer to `versioning_format` stays CalVer when it is a format the profile takes (`internal/versioning`, CalVer: two to four dot-joined tokens, one per unit, in calendar order, the year first), and otherwise the whole answer becomes `custom` with those words as `format`. The profile refuses custom words over 128 characters, or with a control character, `<`, `>`, a backtick, `[`, `]`, `*`, `_`, `/`, `\`, a leading `#` or a hidden character (`internal/versioning` lists them): reword them with the user instead of cutting them.

## Git work flow (SPEC-20261117-mflow-project)

The `work_flow` row fills `work_flow` with `{"flow": "m-flow" | "github-flow" | "trunk-based" | "git-flow", "integration_branch": "<branch>"}`; name the integration branch from the repository (the branch the open pull requests target, else the current branch) as the first option of a follow-up selection, and leave it out when there is none. m-flow is the recommended default (user decision 2026-11-17). The four flows:

- **m-flow** — MoAI's work flow: one integration branch; each SPEC gets its own worktree and branch `spec/<yyyymmdd>-<slug>` started from the integration branch's HEAD (never the remote default branch when it differs, so Claude Code sessions need `worktree.baseRef: head`; Codex CLI and OMP already start worktrees from HEAD) — one SPEC, one branch, one pull request, and no card number in a branch, a commit or a pull request (decision 2026-11-17); tests first; when the work is done, push the branch and open a pull request (recommended); an agent other than the author audits the exact head; the leader merges after CI and a PASS; the local cards stay each person's own todo list.
- **GitHub flow** — short branches from the default branch, a pull request per change, merge after review and CI, the default branch always deployable.
- **trunk-based** — everyone commits to one trunk in small steps, often directly or through very short branches; unfinished work hides behind flags.
- **git-flow** — `develop` for integration, `feature/*` branches from it, `release/*` and `hotfix/*` branches, and `main` holding only released versions.
