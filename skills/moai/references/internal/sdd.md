# Internal: sdd

When to read: before PLAN writes or changes a SPEC, before RUN starts a change to the repository, and in SYNC and AUDIT when they hold the SPEC against the code.

MoAI works spec-driven: the SPEC is the design, plan and contract of one change, kept in git and shared; cards stay personal to-do items.

1. **When.** Every change that modifies the repository has a SPEC; research and questions that change nothing use a card only. One SPEC = one branch `spec/<slug>-<yyyymmdd>` = one pull request (a branch of the older form `spec/<yyyymmdd>-<slug>` is still read, and either form may end in a repair suffix `-r<N>`). Larger work splits into several SPECs linked by `parent`.
2. **Form.** The file is `.moai/specs/SPEC-<yyyymmdd>-<slug>/spec.md`. Start minimal: `moai spec new <slug> --title <title> --minimal` writes Intent, Requirements, Acceptance, Scope and Plan. Without `--minimal` it adds Non-goals, Risks and Decisions; once Non-goals or Risks is present, both are required. Headings stay English; the body follows the conversation language. Above 12 requirements or 400 lines `moai spec check` warns: split the SPEC.
3. **Requirements.** One per line, `- REQ-<n>: <sentence>`, each with exactly one `shall`. GEARS: `[Where …] [While …] [When …] <subject> shall <behavior>`. An unwanted behaviour is `- REQ-<m> (REQ-<n>): IF <condition>, THEN <subject> shall <behavior>`, linked to the `When` requirement it covers. Every `When` requirement has such an IF requirement or ends with `· failure: none — <reason>`.
4. **Acceptance.** `- AC-<n> (REQ-<a>, REQ-<b>…REQ-<c>): <result>` followed by `verify: <command>`. A criterion nobody can check is not written as met.
5. **Open questions.** Write `[NEEDS CLARIFICATION: <question>]` where the answer is missing. RUN does not start while one is open; `moai spec check` reports it as a warning in a draft and as an error once approved.
6. **Approval.** Only the user's in-session selection approves a SPEC. Record it in the frontmatter as `approval: {by: user, at: <YYYY-MM-DD>, basis: "<the selection>", digest: "<the digest moai spec show prints>"}`, set `status: approved`, and repeat the digest in the pull request body. A draft has no `approval` key. Changing an approved SPEC raises `revision` and needs a new approval.
7. **Commands on this build.** `moai spec new` writes one SPEC folder; `moai spec check (<id> | --all) [--closure]`, `moai spec list` and `moai spec show <id>` only read and run nothing (`verify:` commands are read, never run). `moai spec take <SPEC-ID> [--card <card>]` starts the work: it creates or switches to `spec/<slug>-<yyyymmdd>` (a SPEC that already has a local branch of the older form `spec/<yyyymmdd>-<slug>` keeps it; refused while other changes are uncommitted, when the branch carries another SPEC, when the SPEC has a branch in both forms, when its older branch exists only on a remote, or when the new name reads as two SPEC ids) and prints the trailer, push and draft pull request commands; only `--push` and `--draft-pr` run them. `moai spec close <SPEC-ID> [--card <card> --generation <n>]` ends it after the merge: an approved SPEC whose work is reachable from the base and whose `## Result` passes `--closure` gets status `completed` (a draft is refused: approval is the user's), `--card` runs `card done`, and the commit is printed, not run. Link each card to its SPEC: `moai card spec <card> <SPEC-ID>` writes the link in the local ledger (the SPEC must pass `moai spec check` without an error; the same link again writes nothing) and `moai card spec <card> --unlink` removes it. `moai card next` and `moai card take` print the linked SPEC's status and warn while a card that changes the repository has no approved SPEC; `moai card take --require-approved-spec` refuses that card instead — approved means new form, a recorded approval, status `approved` or `completed`, no errors; a Go-generation SPEC never counts.
8. **Order: PLAN → RUN → VERIFY → SYNC → AUDIT → merge.** PLAN writes or updates the SPEC and gets the approval → RUN follows it: only its Scope, tests first for new behaviour, preserve-then-change for existing code → VERIFY runs each AC's `verify:` command → SYNC, on the same branch, writes `## Result` (`- AC-<n>: met — <evidence>`, `withdrawn` with the reason, or what is still missing; `--closure` accepts only `met` and `withdrawn`), the status, the documents and the `@cc:` comments so they match the code, then runs `moai spec check` → AUDIT reads only and FAILs on any drift between the SPEC, the code, the tests, the documents and the `@cc:` comments → merge. After the merge only: `moai spec close` completes the SPEC and closes the card, then the SPEC is archived and the release note written.
9. **`@cc:` comments.** Agent Context Comments in code: `@cc:later`, `@cc:careful`, `@cc:proves`. Agents and tools add them and link them automatically; SYNC keeps them true to the code. Old `@MX:` and `@MOAI:` tags are read, never written.
10. **Shared places.** Card numbers (`C-<n>`) never appear in a SPEC, branch name, commit message or pull request: cards are personal. Commits carry the trailer `Moai-Spec: <SPEC-ID>` and the `Moai-Session: <session>:<worktree key>` trailer (when the host gives a session id; otherwise `Moai-Spec` only, and the report says why): print both with `moai trailers --spec <SPEC-ID>` (never type them) and check a branch with `moai trailer-check <base>..HEAD` before asking for an audit; `internal/commit-trailers` has the rules.
