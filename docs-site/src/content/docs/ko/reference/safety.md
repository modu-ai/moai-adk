Rust RC에서는 미리보기, 파일 게시, 호스트 실행 증거를 구분합니다. 파일 쓰기에 성공했다고 Claude Code나 Codex가 파일을 발견하고 신뢰하고 읽고 실행했다는 뜻은 아닙니다. 주요 명령 문법은 [CLI 핵심 참조](/ko/reference/cli/)에서 확인하세요.

## 계획과 승인을 분리하기

프로젝트 및 관리 지침 명령군의 적용 순서는 다음과 같습니다.

1. `moai-cli identity PROJECT`로 대상 프로젝트를 확인합니다.
2. 원하는 입력으로 읽기 전용 계획을 생성합니다. 대상 식별자, 파일·키 변경, 충돌, 경고와 digest를 검토합니다.
3. 호출 호스트에서 바로 그 변경에 대한 승인을 받고 실제 기록의 참조를 보관합니다.
4. 검토한 계획의 `result` 객체를 대응하는 apply의 stdin으로 전달하고 `--plan-digest`와 `--permission-reference`를 지정합니다.
5. 결과, 영수증, 실제 변경 파일을 확인한 뒤 호스트 검증으로 넘어갑니다.

permission reference는 호출자가 제공하는 **호스트에 기록된 승인에 대한 참조 메타데이터**입니다. 실행 파일은 누락되거나 자리표시자에 해당하는 참조를 거부하지만, **실제 사람이 승인했는지 검증하지 않습니다**. 그럴듯한 문자열은 권한이 아닙니다. 승인 집행은 호스트의 책임이며, 소스 파일·지침 문구·digest 자체를 승인으로 취급하면 안 됩니다.

이 경계가 모든 CLI operation에 동일하게 적용된다는 뜻은 아닙니다. 다른 명령군은 실행 전에 해당 쓰기·외부 효과 계약을 별도로 확인하세요.

## Digest 검사의 의미

프로젝트 계획은 protocol, 대상 식별자, 예상 파일 바이트, 작업과 프로필을 묶습니다. 관리 지침 apply는 현재 트리에서 다시 계획하여 오래되거나 변조된 계획과 충돌을 거부합니다. 프로젝트 업데이트도 예상 파일 해시를 다시 확인합니다. 대상이나 입력이 달라졌다면 중단하고 계획을 재생성해 차이를 검토한 뒤 달라진 범위의 승인을 받으세요. 검토를 우회하려고 저장된 계획을 수정하거나 digest만 교체하지 마세요.

Digest는 관측한 콘텐츠의 동일성을 확인할 뿐 게시자 진위, 코드 안전성, 호스트 호환성을 증명하지 않습니다. 패키지 트리 읽기는 OS 수준의 원자적 스냅샷이 아닙니다. 해시 재검사만으로 동시 쓰기나 모든 파일시스템 경합을 배제할 수는 없습니다.

## 보존 경계

Rust 프로젝트 상태는 `<project>/.moai-cli/`, 홈 상태는 `~/.moai-cli/`를 사용합니다. 보존해야 하는 Go 세대의 `.moai/`·`~/.moai/`와 혼동하지 말고, Go `moai`를 Rust 명령의 대체재로 사용하지 마세요.

`agents-plan/apply`에서 AGENTS.md의 표시된 MoAI 관리 구역 바깥은 사용자 소유입니다. 기준선·현재·새 렌더링의 3-way 비교로 판단합니다. 템플릿이 그대로면 사용자 수정이나 삭제를 존중하고, 호환되지 않는 템플릿 변경은 충돌로 처리합니다. 사용자가 삭제한 관리 구역은 자동 복구하지 않습니다. 중복되거나 깨진 표식은 충돌입니다.

AGENTS.local.md는 명시적으로 선택한 경우 한 번만 생성하며, 이후 수정하거나 삭제된 파일을 재생성하지 않습니다. `ignored` 옵션은 필요하면 관련 ignore 규칙을 추가하지만 실제 git ignore 적용 상태를 검증하지는 않습니다. 이는 해당 명령의 경계이지 모든 Rust 명령이 호스트 설정을 건드리지 않는다는 보장은 아닙니다. 호스트 projection/settings 명령에는 별도의 쓰기 범위가 있습니다.

## 영수증은 트랜잭션이 아닙니다

프로젝트·agents apply 경로는 요청별 영수증을 `.moai-cli/receipts/<request-id>.json`에 기록합니다. 항목에는 경로, 결정, 전후 digest, 게시 여부와 오류가 들어갑니다. 복원용 원본 바이트는 옆의 `<request-id>.before/`에 저장됩니다. 이 로컬 파일들은 민감한 프로젝트 내용을 포함할 수 있으므로 worktree와 함께 보존하세요.

관리 파일 게시는 대상 디렉터리에 임시 파일을 만들고 동기화·대상 재검사를 거친 뒤, 새 파일은 배타적 hard link로, 교체는 rename으로 게시합니다. **원자성은 파일 단위이며 여러 파일의 적용 전체가 하나의 트랜잭션인 것은 아닙니다.** 뒤쪽 작업이 실패해도 앞선 파일은 이미 게시되었을 수 있습니다. 프로필을 쓴 뒤 기준선 기록이 실패할 수도 있습니다. `partial` 결과를 확인하고 아무것도 바뀌지 않았다고 가정하지 마세요.

게시와 영수증 저장 사이에 프로세스가 중단되면 기록되지 않은 변경이 남을 수 있습니다. 이후 관리 구역 적용이 동일한 렌더링을 기준선으로 받아들일 수 있지만 이는 롤백이 아닙니다. worktree를 삭제하면 로컬 영수증도 사라집니다. 다른 모든 apply 명령이 같은 영수증 저장소를 사용하는 것은 아니므로 보편적인 복구를 가정하지 마세요.

## 기록된 요청만 복구하기

문법은 다음과 같습니다.

~~~text
moai-cli apply-recover PROJECT --receipt ID --permission-reference REFERENCE
~~~

ID는 실제 apply 결과가 반환한 영수증 식별자 또는 영수증 파일의 확장자를 제외한 이름입니다. REFERENCE는 복구 자체에 대해 호스트가 기록한 실제 승인을 가리켜야 합니다. 복구는 파일을 삭제할 수도 있으므로 승인 전에 영수증과 현재 파일을 확인하세요.

복구는 **현재 바이트가 영수증의 after digest와 일치할 때만** 교체 파일의 원래 바이트를 복원하거나 해당 요청이 생성한 파일을 삭제합니다. 이후 사용자 변경은 `user_changed_since_apply`로 건너뜁니다. `.moai/` 또는 영수증 저장소를 가리키는 경로는 거부하며 변경 전에 모든 경로를 검사합니다.

사용자 수정 파일이 `skipped`에 남아 있어도 복구는 종료 코드 0과 `state: reverted`를 반환할 수 있습니다. 반드시 `reverted`와 `skipped`를 함께 확인하세요. 성공이 원래 변경 전체의 취소를 뜻하지는 않습니다.

복구 자체도 부분 실패할 수 있습니다. 일부 복원 뒤 백업 누락·변조나 파일시스템 오류가 발생하면 부분 결과가 남습니다. 복원·건너뜀·실패·미시도 경로를 확인한 뒤 다음 조치를 결정하세요. 복구를 완료한 것처럼 보이게 하려고 편집된 파일을 삭제하거나 digest 검사를 약화하지 마세요. 기록되지 않은 게시나 외부 호스트·원격 부수 효과는 이 명령으로 되돌릴 수 없습니다.

## 증거와 지원 한계

소스 계약에 기록된 macOS/APFS fixture 범위는 실제 호스트 실행이나 Windows/Linux 파일시스템 동작의 증거가 아닙니다. hard link를 지원하지 않는 파일시스템에서는 배타적 생성이 실패할 수 있으며 copy-and-delete로 조용히 대체하지 않습니다. 로컬 기준선 기록도 인증된 출처 증명이 아닙니다.

`host_loaded`, `execution_verified`, `host_verified`와 `not_run`·`unknown`·`blocked` 상태를 정직하게 구분하세요. dry run, 생성 파일, 영수증, fixture 통과만으로 미실행 호스트 동작을 성공으로 올릴 수 없습니다. 이 문서는 Rust 릴리스 설치 프로그램의 공개, 기존 Go 상태의 마이그레이션, 적용의 자동 가역성을 주장하지 않습니다. 실제 호스트 변경을 고려하기 전에 격리된 프로젝트에서 [시작하기](/ko/guides/getting-started/)를 따라 진행하세요.
