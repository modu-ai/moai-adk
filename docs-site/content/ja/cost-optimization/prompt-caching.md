プロンプトキャッシングは、同一のプロンプト接頭辞を複数のリクエストで再利用し、90% 割引の
コストで推論コストを削減します (基本コストの 0.1 倍)。MoAI-ADK トークノミクスの
「コンテキストダイエット」軸が常時ロードコンテキストを減らす側だとすれば、プロンプト
キャッシングは残ったコンテキストを安く再利用する側です。このガイドでは損益分岐ルール、
キャッシュのメカニズム、そして MoAI プロジェクトでキャッシングをいつ有効化すべきかを説明します。

## 損益分岐ルール

**1 時間キャッシュは、セッションで 2 つ以上の連続 API リクエストが発生する場合にのみ有効化してください。**

単一リクエストのセッション (ワンショットクエリ、シングルターンコマンド) は 2 倍の書き込みプレミアムが発生し、
キャッシュ再利用の利得がないため、リクエストあたりのコストがキャッシングなしのベースラインよりむしろ
高くなります。逆に 1 時間以内に複数ターンのやり取りや反復的な SPEC 分析があるなら、
キャッシングは 2 番目のリクエストでコストを相殺し、後続のリクエストで 67% 以上を削減します。

### コスト比較

Claude Opus 4.5 を基準に:

| シナリオ | キャッシングなし | 1 時間キャッシュあり | 削減 |
|---------|----------|-----------------|-------|
| 1 リクエスト、10K トークン | $0.05 | $0.0625 | -25% (プレミアム) |
| 2 リクエスト、10K + 10K | $0.10 | $0.0625 + $0.005 = $0.0675 | 32% 削減 |
| 3 リクエスト、10K + 10K + 10K | $0.15 | $0.0625 + 2×$0.005 = $0.0725 | 52% 削減 |
| 5 リクエスト、10K + 10K + 10K + 10K + 10K | $0.25 | $0.0625 + 4×$0.005 = $0.0825 | 67% 削減 |

損益分岐点は **2 リクエスト** です: 最初のリクエストの 2 倍の書き込みプレミアムは、1 時間 TTL ウィンドウ内の後続リクエストの 90% 割引キャッシュ読み取りで回収されます。

## キャッシュ制御の動作原理

プロンプト接頭辞でキャッシュ制御を有効化すると、キャッシュライフサイクルは次のパターンに従います:

1. **最初のリクエスト (キャッシュ書き込み)**: API レスポンスの完了後、接頭辞がキャッシュに書き込まれます。コスト: `接頭辞トークン × 2.0 (1 時間キャッシュ) または 1.25 (5 分キャッシュ)`。
2. **後続リクエスト (キャッシュ読み取り)**: 接頭辞が同一で TTL 内にあれば、キャッシュから検索します。コスト: `接頭辞トークン × 0.1`。
3. **自動バックトラッキング**: システムは直近 20 メッセージからキャッシュ済み接頭辞の一致を確認します。見つかれば読み取りコストが適用されます。

### キャッシュ配置のベストプラクティス

キャッシュ制御のブレークポイントは、**リクエスト別データの前の最後の安定ブロック** に配置してください:

```python
# 正しい: 安定したシステムプロンプト (キャッシュ可能)
response = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": "あなたはコードレビュアーです...",
            "cache_control": {"type": "ephemeral", "ttl": "1h"}
        }
    ],
    # 以下は変化するリクエスト別データ (キャッシュしない)
    messages=[{"role": "user", "content": user_query}]
)

# 間違い: キャッシュブレークポイントが変化するデータにある
# 現在時刻: {timestamp}
cache_control={"type": "ephemeral"}
# ^ タイムスタンプがリクエストごとに変わるため、絶対に一致しない
```

## 設定: session_ttl と spec_ttl

MoAI のキャッシングは `.moai/config/sections/cache.yaml` で設定されます:

```yaml
cache:
  enabled: false  # キャッシングを有効化するには true に設定
  session_ttl: "1h"  # セッションレベルのキャッシュ TTL
  spec_ttl: "5m"     # SPEC 本文のキャッシュ TTL
  min_cacheable_tokens: 2048  # キャッシュ書き込みの最小トークン
```

### session_ttl: "off" によるオプトアウト

特定のセッションでキャッシングを無効化するには (例: ワンショットリクエストが支配的な場合):

```yaml
cache:
  enabled: true
  session_ttl: "off"  # このセッションでキャッシュを無効化
  spec_ttl: "5m"      # SPEC 本文のみキャッシュを使用
```

`session_ttl: "off"` の場合:
- セッションレベルのキャッシュ書き込みがスキップされる
- `spec_ttl` が構成されていれば SPEC 本文のキャッシュは引き続き適用
- 単一リクエストが一般的な中断ベースのワークフローに有用

## キャッシュパフォーマンスのモニタリング

`moai doctor` を使ってキャッシュヒット率を確認し、キャッシングの有効化を判断してください:

```bash
moai doctor --cache-metrics
```

出力例:

```
キャッシュパフォーマンス (直近 7 日):
  キャッシュヒット率: 67%
  総キャッシュ読み取り: 450K トークン
  総キャッシュ書き込み: 150K トークン
  削減: $2.15 (キャッシングなしと比較して 68% のコスト削減)

シングルターンリクエスト比率: 12%  ⚠️ 警告: リクエストの 12% がシングルターン
                            (これらに対するキャッシュ利得なし)。
```

MoAI statusline にもキャッシュヒット率 (cache_hit) セグメントが表示され、コンテキスト
ダイエットとキャッシング設定の効果をセッション中にすぐ確認できます。

### メトリクスの解釈

- **ヒット率 > 60%**: キャッシュが効果的です。有効化を維持してください。
- **ヒット率 30-60%**: 中程度の利得。セッションがマルチターン中心なら有効化を検討してください。
- **シングルターン比率 > 30%**: キャッシングの利得は限定的です。2 リクエスト以上の前提が維持されているか確認してください。
- **最小トークンしきい値の警告**: `min_cacheable_tokens` を構成して小さなプロンプトのキャッシングを避けてください (オーバーヘッド > 削減)。

## キャッシュミスが発生する場合

キャッシュヒットには次が必要です:

- ✓ ブレークポイントまで同一のプロンプト接頭辞
- ✓ TTL ウィンドウ内 (1 時間または 5 分)
- ✓ 同一のワークスペース/組織コンテキスト
- ✓ ブレークポイント前のすべてのブロックに変更なし (ツール、システム、最上位パラメーター)

キャッシュミス (一般的な原因):

- ✗ ツール定義の変更 (ツールパラメーターが異なる)
- ✗ Web 検索トグルのオン/オフ
- ✗ 接頭辞への画像の追加または削除
- ✗ 拡張思考設定の変更
- ✗ ブレークポイント前のコンテンツが異なる (空白を含む)

## 最小トークンしきい値

キャッシュ書き込みは、接頭辞が言語モデルごとの最小値を超える場合にのみ発行されます:

- **Claude Opus 4.5、4.7、4.8、Haiku 4.5**: 最小 2,048 トークン
- **Claude Opus 4.1、Sonnet モデル、その他の Haiku バージョン**: 最小 1,024 トークン

最小値未満のリクエストはキャッシングなしで処理されます (エラーなし — 自動フォールバック)。

## 事前ウォーミング (高度)

最初のユーザーインタラクションのキャッシュミスレイテンシーを排除するには:

```python
# キャッシュの事前ウォーミング (ユーザー到着前)
client.messages.create(
    model="claude-opus-4-8",
    max_tokens=0,  # 出力トークンの請求なし
    system="長いシステムプロンプト (5000 トークン)...",
    cache_control={"type": "ephemeral", "ttl": "1h"},
    messages=[{"role": "user", "content": "warmup"}]
)
# コスト: system_tokens × $2.0/MTok (キャッシュ書き込み)

# 後で: ユーザーリクエストがウォーミング済みキャッシュにヒット
client.messages.create(
    model="claude-opus-4-8",
    max_tokens=1024,
    system="長いシステムプロンプト (同一)...",
    cache_control={"type": "ephemeral", "ttl": "1h"},
    messages=[{"role": "user", "content": user_input}]
)
# コスト: system_tokens × $0.1/MTok (ウォーミングからのキャッシュ読み取り)
```

## まとめ

- **キャッシュ有効化**: 1 時間以内に 2 つ以上の連続 API リクエストがあるセッション
- **キャッシュ無効化**: ワンショットクエリまたは中断ベースのワークフロー
- **モニタリング**: `moai doctor --cache-metrics` と statusline の cache_hit セグメントで実際のヒット率を測定
- **最適化**: キャッシュブレークポイントは安定したコンテンツ (システムプロンプト、指示) に配置し、変化するデータ (クエリ、タイムスタンプ) には配置しない

詳細は [Anthropic プロンプトキャッシングドキュメント](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)を参照してください。
