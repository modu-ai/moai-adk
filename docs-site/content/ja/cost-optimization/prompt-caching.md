プロンプトキャッシングは同一のプロンプト接頭辞を複数のリクエストで再利用し、90% 割引の
コストで推論コストを削減します (基本コストの 0.1 倍)。MoAI-ADK トークノミクスの
「コンテキストダイエット」軸が常時ロードコンテキストを減らす側だとすれば、プロンプト
キャッシングは残ったコンテキストを安く再利用する側です。このガイドでは損益分岐ルール、
キャッシュのメカニズム、そして MoAI プロジェクトでキャッシングをいつ有効化すべきかを説明します。

## 損益分岐ルール

**1 時間キャッシュは、セッションで 2 つ以上の連続 API リクエストが発生する場合にのみ有効化してください。**

単一リクエストのセッション (ワンショットクエリ、単一ターンコマンド) は 2 倍の書き込みプレミアムが発生し、
キャッシュ再利用の利得がないため、リクエストあたりのコストがキャッシングなしの基準線よりむしろ
高くなります。逆に 1 時間以内に複数ターンの相互作用や反復的な SPEC 分析があれば、
キャッシングは 2 番目のリクエストでコストを相殺し、後続のリクエストで 67% 以上を削減します。

### コスト比較

Claude Opus 4.8 を基準に:

| シナリオ | キャッシングなし | 1 時間キャッシュ含む | 削減 |
|---------|----------|-----------------|-------|
| 1 リクエスト、10K トークン | $0.05 | $0.0625 | -25% (プレミアム) |
| 2 リクエスト、10K + 10K | $0.10 | $0.0625 + $0.005 = $0.0675 | 32% 削減 |
| 3 リクエスト、10K + 10K + 10K | $0.15 | $0.0625 + 2×$0.005 = $0.0725 | 52% 削減 |
| 5 リクエスト、10K + 10K + 10K + 10K + 10K | $0.25 | $0.0625 + 4×$0.005 = $0.0825 | 67% 削減 |

損益分岐点は **2 リクエスト** です: 最初のリクエストの 2 倍の書き込みプレミアムは、1 時間 TTL ウィンドウ内の後続リクエストの 90% 割引キャッシュ読み込みで回収されます。

## キャッシュ制御の動作原理

プロンプト接頭辞でキャッシュ制御を有効化すると、キャッシュのライフサイクルは次のパターンに従います:

1. **最初のリクエスト (キャッシュ書き込み)**: API 応答が完了した後、接頭辞がキャッシュに書き込まれます。コスト: `接頭辞_トークン × 2.0 (1 時間キャッシュ) または 1.25 (5 分キャッシュ)`。
2. **後続リクエスト (キャッシュ読み込み)**: 接頭辞が同一で TTL 内にあれば、キャッシュから検索します。コスト: `接頭辞_トークン × 0.1`。
3. **自動遡り検索**: システムは直近 20 個のメッセージからキャッシュされた接頭辞の一致を確認します。見つかれば読み込みコストが適用されます。

### キャッシュ配置のベストプラクティス

キャッシュ制御ブレークポイントを **リクエスト別データの前の最後の安定したブロック** に配置してください:

```python
# 正しい: 安定したシステムプロンプト (キャッシュ可能)
response = client.messages.create(
    model="claude-opus-4-8",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": "あなたはコードレビュアーです...",
            "cache_control": {"type": "ephemeral", "ttl": "1h"}
        }
    ],
    # 以下は変更可能なリクエスト別データ (キャッシュしない)
    messages=[{"role": "user", "content": user_query}]
)

# 間違い: キャッシュブレークポイントが変更データにある
# 現在時刻: {timestamp}
cache_control={"type": "ephemeral"}
# ^ タイムスタンプが毎リクエスト変わるので決して一致しない
```

## 設定: session_ttl と spec_ttl

MoAI キャッシングは `.moai/config/sections/cache.yaml` で設定されます:

```yaml
cacheStrategy:
  enabled: false  # キャッシングを有効化するには true に設定
  session_ttl: "1h"  # セッションレベルのキャッシュ TTL — 許可値: 1h · 5m · off
  spec_ttl: "5m"     # SPEC 本文のキャッシュ TTL
  min_cacheable_tokens: 2048  # キャッシュ書き込みの最小トークン
```

### session_ttl: "off" によるオプトアウト

特定のセッションでキャッシングを無効化するには (例: ワンショットリクエストが支配的なとき):

```yaml
cacheStrategy:
  enabled: true
  session_ttl: "off"  # このセッションでキャッシュ無効化 (許可値: 1h · 5m · off)
  spec_ttl: "5m"      # SPEC 本文のみキャッシュ使用
```

`session_ttl: "off"` のとき:
- セッションレベルのキャッシュ書き込みがスキップされる
- `spec_ttl` が構成されていれば SPEC 本文のキャッシュは引き続き適用
- 単一リクエストが一般的な中断ベースのワークフローに有用

## キャッシュパフォーマンスのモニタリング

MoAI statusline のキャッシュヒット率 (cache_hit) セグメントでリアルタイムのヒット率を
確認し、キャッシング有効化の可否を決めてください。このセグメントはセッションが進行する
間、キャッシュ読み込み対書き込みの比率を表示するので、コンテキストダイエットとキャッシング
設定の効果をセッション中にすぐ確認できます。

### メトリクスの解釈

- **ヒット率 > 60%**: キャッシュが効果的です。有効化を維持してください。
- **ヒット率 30-60%**: 中程度の利得。セッションがマルチターン中心なら有効化を検討してください。
- **単一ターン比率 > 30%**: キャッシングの利得が限定的です。2 つ以上のリクエスト前提が維持されるか確認してください。
- **最小トークン閾値の警告**: `min_cacheable_tokens` を構成して小さなプロンプトのキャッシングを避けてください (オーバーヘッド > 削減)。

## キャッシュミスが発生する場合

キャッシュヒットには次が必要です:

- ✓ ブレークポイントまで同一のプロンプト接頭辞
- ✓ TTL ウィンドウ内 (1 時間または 5 分)
- ✓ 同一のワークスペース/組織コンテキスト
- ✓ ブレークポイント前のすべてのブロックが変更なし (ツール、システム、トップレベルパラメータ)

キャッシュミス (一般的な原因):

- ✗ ツール定義の変更 (ツールパラメータが異なる)
- ✗ Web 検索トグルのオン/オフ
- ✗ 接頭辞への画像の追加または削除
- ✗ 拡張思考設定の変更
- ✗ ブレークポイント前のコンテンツが異なる (空白を含む)

## 最小トークン閾値

キャッシュ書き込みは接頭辞が言語モデル別の最小値を超えるときのみ発行されます:

- **Claude Opus 4.7 / 4.8、Haiku 4.5**: 2,048 トークン最小
- **Sonnet 系列およびその他の Haiku バージョン**: 1,024 トークン最小

最小値未満のリクエストはキャッシングなしで処理されます (エラーなし — 自動フォールバック)。

## 事前ウォーミング (上級)

最初のユーザー相互作用のキャッシュミスレイテンシを除去するには:

```python
# キャッシュ事前ウォーミング (ユーザー到着前)
client.messages.create(
    model="claude-opus-4-8",
    max_tokens=0,  # 出力トークン課金なし
    system="長いシステムプロンプト (5000 トークン)...",
    cache_control={"type": "ephemeral", "ttl": "1h"},
    messages=[{"role": "user", "content": "warmup"}]
)
# コスト: system_tokens × $2.0/MTok (キャッシュ書き込み)

# 後で: ユーザーリクエストがウォーミングされたキャッシュにヒット
client.messages.create(
    model="claude-opus-4-8",
    max_tokens=1024,
    system="長いシステムプロンプト (同一)...",
    cache_control={"type": "ephemeral", "ttl": "1h"},
    messages=[{"role": "user", "content": user_input}]
)
# コスト: system_tokens × $0.1/MTok (ウォーミングからのキャッシュ読み込み)
```

## 要約

- **キャッシュ有効化**: 1 時間内に 2 つ以上の連続 API リクエストがあるセッション
- **キャッシュ無効化**: ワンショットクエリまたは中断ベースのワークフロー
- **モニタリング**: statusline cache_hit セグメントで実際のヒット率を測定
- **最適化**: キャッシュブレークポイントを安定したコンテンツ (システムプロンプト、指示) に配置し、変更データ (クエリ、タイムスタンプ) には配置しないでください

詳しい内容は [Anthropic プロンプトキャッシングドキュメント](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching) を参照してください。
