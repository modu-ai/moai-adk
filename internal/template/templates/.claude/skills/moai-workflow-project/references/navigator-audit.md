# Navigator Audit — Drift / Completeness Mode (`--audit`)

> Level-3 reference for the Project Navigator audit. The deterministic core is
> `${CLAUDE_SKILL_DIR}/scripts/navigator-audit.sh` (sibling to `navigator-regen.sh`).
> This document specifies the algorithm, the matching heuristic, the
> header-driven column resolution, the override-file schema, and the fail-open
> semantics. Invoke the audit via `/moai project --audit`.

## What the audit diffs

Two input surfaces, both already existing in the project — the audit
introduces no new inputs:

| Surface | Source | What it represents |
|---------|--------|--------------------|
| **design-intent** | `.moai/project/{product,structure,tech}.md` (the project-context triple generated by `/moai project` + hand-edited by the user) | Features the project intends to have — the "plan". |
| **capability-map** | `.moai/project/navigator/capability-map.md` (generated by `navigator-regen.sh`) | Features the project actually tracks as SPECs — the "implementation rollup". |

The audit computes the bidirectional diff and emits two output files under
`.moai/project/navigator/`:

- **`audit-report.md`** — human-readable, grouped into `## Missing SPECs`,
  `## Orphan SPECs`, `## Matched` (in that order).
- **`audit-report.json`** — machine-readable, stable schema.

It is a READ-ONLY consumer of both input surfaces; it never modifies either.

## Output schema

### `audit-report.json` (stable, 6 top-level keys)

```json
{
  "audit_at": "<ISO-8601 from git log HEAD committer date>",
  "audit_commit": "<HEAD SHA>",
  "inputs": {
    "design_docs": ["product.md", "structure.md", "tech.md"],
    "capability_map": "capability-map.md",
    "override_file": "audit-known-matches.yaml"   // or null
  },
  "missing": [
    {
      "design_name": "Real-time Collaboration",
      "source": { "file": "product.md", "heading_path": "Product > Core Features" },
      "closest_match": null
    }
  ],
  "orphan": [
    { "spec_id": "SPEC-X-999", "title": "Legacy CRM Integration", "implementation_path": "internal/crm" }
  ],
  "matched": [
    { "design_name": "Authentication", "spec_id": "SPEC-AUTH-001", "match_basis": "exact" }
  ]
}
```

`closest_match` is a reserved always-null field for forward-compatibility —
the current match predicate is binary (matched / not matched), not a
nearest-neighbor ranking.

### `audit-report.md`

Three sections in fixed order: `## Missing SPECs`, `## Orphan SPECs`,
`## Matched`. Each section is either a markdown table or the placeholder
`_(none — ...)`. Every row carries provenance (design-doc file + heading path
for Missing; spec-id + title + implementation-path for Orphan; design name +
spec-id + match-basis for Matched).

## The algorithm

### Step 1 — extract design-intent features

For each of `product.md`, `structure.md`, `tech.md`:

1. Parse markdown headings (`#`, `##`, `###`, `####`) into a heading path stack.
2. Identify "feature-listing" sections by sentinel phrases in the heading
   text: `Core Features`, `Features`, `Capabilities`, `Modules`,
   `Functionality`, `Subsystems`, `Components`. The sentinel set is closed
   and documented here; the user extends coverage via the override file, not
   by editing the script.
3. Inside a feature-listing section, treat each bolded bullet
   (`- **<name>** ...`) as a named feature. The feature name is the bolded
   text (without `**`); trailing parenthetical (e.g. ` (moai init)`) stays
   inline in the bullet but is not stripped into a separate field.
4. Record each feature as `(name, source_file, heading_path)`.

### Step 2 — extract capability-map features (header-driven)

The capability-map column order is **NOT** frozen at the SPEC level. The
audit parses the header row (the line above the first `|---|---|` separator)
and resolves columns **by name** (case-insensitive, with `-` / `_` / space
treated as equivalent):

- **feature/name column** — recognized under any spelling: `capability`,
  `name`, `feature`, `title`.
- **spec-id column** — `owning-spec`, `spec-id`, `spec_id`.
- **status column** — `status`.
- **implementation-path column** — `implementation-path`, `path`,
  `module-path`.

If the header lacks a required column (no feature/name column OR no spec-id
column), all data rows are skipped and a warning is logged to
`.moai/logs/navigator-warnings.log`. Otherwise each data row is extracted by
**header-resolved position** (not fixed index), and rows whose status is
`superseded`, `archived`, or `rejected` are filtered out (those represent
retired features; flagging them as orphans would be noise).

The header-driven design is what makes the audit robust to upstream schema
variations: it consumes whatever the capability-map ships, without coupling
to a specific column order.

### Step 3 — load overrides (if present)

If `.moai/project/navigator/audit-known-matches.yaml` exists, the audit loads
its `match` and `ignore` entries BEFORE applying the heuristic. The schema is
small enough that a pure awk extractor suffices (no `yq` / `jq` dependency).

### Step 4 — compute the diff

For each design feature `D` and each capability-map row `C`:

1. **Override match**: if `(D.name, C.spec_id)` is in `override.match` →
   record as `matched` with `match_basis: override`. Apply BEFORE heuristic.
2. **Override ignore**: else if `D.name` OR `C.spec_id` is in `override.ignore`
   → skip (emitted in neither `missing`, `orphan`, nor `matched`).
3. **Heuristic** (see below): else apply the matching heuristic.

If no heuristic match for `D` after iterating all `C` rows and no override →
`D` is a **Missing SPEC** candidate. If no heuristic match for `C` after
iterating all `D` features and no override → `C` is an **Orphan SPEC**
candidate.

### Step 5 — emit the report

Render `audit-report.md` (3 sections in order) + `audit-report.json` (6-key
schema) and write both via atomic-rename (`.tmp` → `mv`).

## The matching heuristic

Both design-doc feature names and capability-map title-column values are
normalized to **lowercase kebab tokens** (strip punctuation, lowercase,
collapse whitespace runs to single hyphens, strip leading/trailing hyphens).
A match holds when ANY of:

- **(a) exact** — normalized-title equality.
- **(b) substring** — one normalized string is a substring of the other AND
  the shorter is ≥4 characters.
- **(c) module-token** — the last path segment of the capability-map row's
  `implementation-path` column (the path token) appears as a substring of the
  normalized design-doc feature name AND that path token is ≥4 characters.

The ≥4-character floor in (c) rejects trivially short segments (`cmd`, `pkg`,
`src`, `crm`) that would otherwise produce false positives on unrelated
design-doc features. The heuristic is deliberately conservative: it produces
**candidates**, not verdicts. The override file is the authoritative escape
hatch for divergence the heuristic cannot resolve; the user is always the
final adjudicator.

The `match_basis` field in `audit-report.json` records which basis produced
each match: `exact` / `substring` / `module-token` / `override`.

## Override file schema

`.moai/project/navigator/audit-known-matches.yaml` is OPTIONAL and
user-authored. It records features whose design-doc name deliberately
diverges from the SPEC title (e.g. a feature called "Autonomy Loop" in
`product.md` but implemented as `SPEC-AUTONOMY-WORKFLOW-001`).

```yaml
# Optional user-authored override file for the Navigator audit.
# The audit loads this BEFORE applying its matching heuristic.
match:
  - design_name: "Autonomy Loop"
    spec_id: "SPEC-AUTONOMY-WORKFLOW-001"
ignore:
  - "SPEC-DEPRECATED-001"   # design-doc reference still present, deliberately ignored
  - "Old Feature Name"      # design-doc bullet that is no longer a real feature
```

- `match` — list of `{design_name, spec_id}` pairs considered matched
  regardless of the heuristic. Loaded BEFORE the heuristic.
- `ignore` — list of design names OR spec-ids excluded from BOTH the
  missing-candidate and orphan-candidate lists.

## Idempotence, fail-open, read-only contracts

- **Idempotent**: two runs over the same design docs + capability-map +
  override file (or same absence) produce byte-identical output. The only
  time field (`audit_at`) is sourced from `git log --format=%cI` for HEAD
  (NOT wall-clock), mirroring the regeneration script's idempotence contract.
- **Fail-open**: when ANY of the three inputs is missing (no design docs, no
  capability-map, no `.moai/specs/SPEC-*` directories), the audit exits 0,
  writes a minimal `audit-report.md` containing the literal
  `no inputs available — <naming the missing input>` placeholder, emits a
  valid empty `audit-report.json`, and appends a warning line to
  `.moai/logs/navigator-warnings.log`. The audit never aborts non-zero on
  missing inputs.
- **Read-only over inputs**: the audit NEVER modifies design docs, the
  capability-map, the progress-map, `navigator.md`, or SPEC frontmatter. The
  audit script's process tree contains NO invocation of `navigator-regen.sh`
  — the capability-map the user sees in the report is exactly what was on
  disk before the audit ran.

## Boundary — non-overlap with adjacent subsystems

The audit operates strictly on:

- `.moai/project/{product,structure,tech}.md`
- `.moai/project/navigator/capability-map.md`
- `.moai/specs/SPEC-*/spec.md` frontmatter (best-effort; not load-bearing for
  the diff algorithm — the capability-map encodes the SPEC inventory)
- the optional override file
- `git log` for provenance

It NEVER reads or writes:

- Any LSEL surface (`.moai/lessons-inbox.jsonl`, `.moai/state/lsel/`,
  `memory/feedback_*.md`, `hns-lsel-*`)
- Any tree-sitter / AST surface (separate concern, owned by a follow-up)
- Any design-doc / capability-map / SPEC-frontmatter mutation path

The write set is exactly `{audit-report.md, audit-report.json}` under
`.moai/project/navigator/` plus an append to `.moai/logs/navigator-warnings.log`.

## Template neutrality + 16-language neutrality

The audit surfaces (this reference, the script, the skill body) are
template-distributed: they ship to every user project on `moai init` /
`moai update`. They MUST NOT carry internal SPEC IDs, internal REQ/AC tokens,
internal dates, or commit SHAs (the C2/C3/C7 forbidden content classes). The
audit's algorithm is language-neutral: it operates on markdown design docs +
markdown capability-map + SPEC frontmatter, with no Go-specific (or any
language-specific) assumption. A Python-only project, a Rust project, a
Flutter project — all audit identically modulo their own design-doc +
capability-map content.

## When to use

- **After `/moai project` or `/moai sync`** — the capability-map is fresh, so
  the audit's drift report reflects the current state. Recommended order:
  `/moai project` → `/moai project --audit`.
- **When onboarding onto a new project** — run the audit once to see which
  design-named features never became SPECs and which SPECs have drifted out
  of the design narrative.
- **Before a release cut** — surface design-vs-implementation drift for
  human adjudication before the release.
- **NOT as a hook** — the audit is on-demand. Its output can be large and is
  not latency-sensitive; auto-firing on every session or every commit would
  violate Advisory-Check Discipline.

The audit is ADVISORY. It surfaces Missing SPEC and Orphan SPEC candidates.
It NEVER auto-creates a SPEC, NEVER auto-retires a SPEC, and NEVER modifies
SPEC frontmatter. Adjudication (genuine gap vs deliberate divergence) is the
sole prerogative of the user, who reads the report and decides.
