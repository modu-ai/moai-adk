moai-adk 배포 형식 비교
바이너리 vs 플러그인 vs 글로벌 심링크 하이브리드

TL;DR — 플러그인도, ~/.claude 전면 글로벌화도 바이너리를 대체하지 못한다. 전면 글로벌화는 skills 우선순위 역전(personal > project)과 전 프로젝트 스코프 오염이라는 구조적 결함이 있어 비권장. 최선안은 ~/.moai 글로벌 저장소 + 프로젝트별 심링크 옵트인 — 공식 문서가 명시적으로 지원하는 패턴이며, 중복 제거·프로젝트 최소화·버전 고정·팀 부트스트랩을 모두 만족한다.

기능 층 분해 — 무엇이 어디로 옮겨질 수 있는가

비교의 전제: moai-adk의 기능은 두 층으로 나뉘며, 어떤 배포 형식도 바이너리 층은 대체 불가하다. 따라서 실제 선택지는 "자산 층(skills/agents/rules)을 어디에 두고 어떻게 갱신하느냐"이다.

3가지 배포 형식 분석

각 안을 사용자 관점(설치 마찰 · 업데이트 UX · 커스터마이징 · 팀 공유 · 버전 관리)에서 평가한다.

A 현행 — 바이너리 + moai init 템플릿 복사

강점: 단일 도구 하나로 전부 해결(brew install → moai init). 템플릿·바이너리·hook이 같은 버전으로 원자적 배포되어 버전 스큐가 구조적으로 불가능. .claude/ 파일이 프로젝트에 실재하므로 사용자가 열어 보고 수정 가능 — user-owned harness(hns-*) 커스터마이징 철학이 이 위에 성립. 팀원은 clone만으로 동일 harness 획득.

약점: moai update의 overwrite-vs-preserve 매트릭스가 상시 위험 표면(실제 dev-custom 대량 회귀 사고 이력). 프로젝트마다 수백 개 파일이 복사되어 git 노이즈와 중복 저장 발생. 마켓플레이스 발견성 없음.

B 플러그인 하이브리드 — 바이너리 + Claude Code 플러그인

강점: 플러그인 갱신 한 번으로 모든 프로젝트의 skills/agents 동기화. 프로젝트 디렉터리가 깨끗해짐. 마켓플레이스 발견성 + /plugin install 설치 마찰 감소.

약점: 2-스텝 설치(바이너리 + 플러그인)로 하프-인스톨 상태가 신규 지원 부담. 플러그인 vN + 바이너리 vM 조합의 버전 스큐가 신규 결함 클래스로 등장(현재는 존재하지 않는 문제). 플러그인 skills는 plugin:skill 네임스페이스의 read-only 성격이라 user-owned 수정 모델과 충돌. rules와 .moai/ config는 여전히 프로젝트 배포가 필요해 배포 채널 2개를 병행 유지하게 됨.

C 전면 글로벌 — ~/.claude user 스코프 이동

공식 지원 확인: skills(~/.claude/skills/) · agents(~/.claude/agents/) · rules(~/.claude/rules/) · CLAUDE.md(~/.claude/CLAUDE.md) 모두 user 스코프가 공식 지원된다. 그러나 두 가지 구조적 결함이 있다.

결함 1 — skills 우선순위 역전: 이름 충돌 시 skills는 personal이 project를 이긴다(enterprise > personal > project). moai skills를 글로벌로 옮기면 특정 프로젝트에서 같은 이름으로 로컬 오버라이드가 불가능해진다. agents는 반대로 project가 이기므로(managed > CLI > project > user > plugin) 자산별 동작이 비대칭.

결함 2 — 전 프로젝트 스코프 오염: ~/.claude 자산은 머신의 모든 프로젝트에 로드된다. moai를 쓰지 않는 프로젝트에서도 moai skills 메타데이터(개당 ~100토큰 × 수십 개), paths: 없는 always-loaded rules(수만 토큰), agents 카탈로그가 매 세션 주입된다. per-project 옵트아웃은 claudeMdExcludes를 비-moai 프로젝트마다 설정해야 하므로 "프로젝트 최소화" 목표가 역전된다.

결함 3 — 팀 공유 소멸: ~/.claude는 머신 로컬. 현재는 git clone만으로 팀 전체가 동일 harness를 받지만, 글로벌 모델에선 팀원마다 별도 셋업이 필요하다.

D 권고 — ~/.moai 글로벌 저장 + 프로젝트 심링크 옵트인

실체는 ~/.moai/assets/<version>/에 머신당 1벌만 저장하고, 각 프로젝트의 .claude/skills/·.claude/rules/에는 심링크만 둔다. 공식 문서가 skills·rules 양쪽에서 심링크를 명시적으로 지원한다(rules 문서는 ln -s ~/shared-claude-rules .claude/rules/shared 패턴을 직접 예시).

  • 중복 제거: moai update는 ~/.moai/assets만 갱신 — user-owned 파일 overwrite 사고 클래스가 구조적으로 소멸.
  • 스코프 오염 없음: 심링크가 있는 프로젝트에만 로드. 비-moai 프로젝트 무영향.
  • 커스터마이징 보존: 자산이 project 스코프에 남으므로 skills 우선순위 역전 회피. user-owned hns-*는 실파일로 공존.
  • 버전 고정: 심링크를 버전 디렉터리(~/.moai/assets/v3.1/)로 걸면 프로젝트별 핀 가능.
  • 스큐 없음: 자산과 바이너리가 같은 moai update 채널 — 플러그인안의 스큐 문제 원천 차단.

약점: (1) Windows 심링크는 관리자 권한/개발자 모드 필요 → 복사 폴백 필요. (2) 심링크를 git에 커밋하면 ~/.moai 없는 팀원에게 깨진 링크 → .gitignore + "clone 후 moai init 1회" 부트스트랩으로 해결. (3) 기존 프로젝트의 복사본→심링크 마이그레이션 비용.

디렉터리 구조 비교

│   ├── skills/moai-*/          # 복사본 (프로젝트 N개 = N벌)
│   ├── agents/moai/*.md        # 복사본
│   ├── rules/moai/**/*.md      # 복사본
│   └── settings.json           # 렌더됨
├── .moai/config/ · specs/ · state/
└── CLAUDE.md

~/go/bin/moai                   # 바이너리 (머신당 1개)
# 플러그인 + 바이너리 2채널 — 스큐 위험
~/.claude/plugins/moai-adk@marketplace/
├── skills/ · agents/ · hooks/  # read-only, plugin:skill 네임스페이스

project/
├── .claude/rules/moai/         # rules는 여전히 프로젝트 복사 필요

핵심 판단 기준 — 배포 형식의 우열은 "파일이 어디 있느냐"가 아니라 ① 이름 충돌 시 누가 이기는가(오버라이드 가능성) ② 자산이 어느 스코프에 로드되는가(오염 반경) ③ 바이너리와 자산이 같은 채널로 갱신되는가(스큐) 세 가지로 갈린다. D안만이 셋 모두를 통과한다.

권고안

  • 채택: D안 — ~/.moai/assets/<version> 글로벌 저장소 + 프로젝트 심링크 옵트인. 마이그레이션 비용은 moai init/update 배포 로직 변경 + Windows 복사 폴백 + 기존 프로젝트 복사본→심링크 전환.
  • 보완: 발견성이 필요하면 skills 몇 개 + 설치 안내만 담은 게이트웨이 플러그인을 마켓플레이스에 별도 등록 (스큐 위험 최소화하며 B안의 유일한 장점만 취함).
  • 기각: C안(전면 ~/.claude 글로벌) — skills 우선순위 역전 + 전 프로젝트 오염 + 팀 공유 소멸. 설정으로 우회 불가한 구조적 결함.
  • 기각: B안(전면 플러그인화) — 배포 채널 2개 병행 + 버전 스큐 신규 결함 클래스 + user-owned 커스터마이징 모델 충돌.

FAQ

플러그인이 바이너리까지 배포할 수는 없나?

불가. Claude Code 플러그인은 skills/agents/commands/hooks/MCP 서버 정의를 배포하는 메커니즘이며 실행 파일 설치·PATH 등록·프로젝트 파일 스캐폴딩 기능이 없다. moai CLI(session/handoff/statusline/worktree/glm)와 .moai/ 상태 시스템은 어떤 안에서도 바이너리로 남는다.

rules를 글로벌에 두고 paths: 스코핑으로 오염을 막을 수는 없나?

불충분. paths:는 파일 글롭 패턴이라 "이 프로젝트가 moai 프로젝트인가"라는 조건을 표현할 수 없다. moai의 핵심 rules(askuser-protocol, session-handoff 등)는 의도적으로 always-loaded라 paths:를 붙이면 기능이 깨지고, 안 붙이면 전 프로젝트에 주입된다.

심링크 대신 rules 문서의 심링크 공유 패턴을 skills에도 그대로 써도 되나?

된다. skills 문서는 "enterprise·personal·project 위치의 <skill-name> 엔트리가 디스크 다른 곳을 가리키는 심링크일 수 있다"고 명시하며, 같은 타깃이 여러 경로에서 도달 가능해도 1회만 로드한다. 라이브 변경 감지도 심링크 대상에 적용된다.

D안에서 팀원이 ~/.moai 없이 clone하면?

심링크를 .gitignore에 두면 clone 직후엔 harness가 비어 있고, moai init 1회가 바이너리 설치 확인 + ~/.moai/assets 채우기 + 심링크 생성을 수행한다. 현행의 "clone만으로 완결" 대비 1스텝 추가가 D안의 팀 공유 비용이다.

글로벌 일괄 업데이트가 오히려 위험하지 않나?

버전 디렉터리(~/.moai/assets/v3.1/)로 해소된다. moai update는 새 버전 디렉터리를 만들고 현재 프로젝트의 심링크만 전환한다. 다른 프로젝트는 기존 버전에 핀된 채 남으므로 blast radius가 프로젝트 단위로 제한된다 — C안(디렉터리 1개 공유)에는 없는 속성.
