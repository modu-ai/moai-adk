1. 무엇을 확인했나

원본의 구현 방식뿐 아니라 테스트가 실제로 무엇을 확인하는지도 읽었다. 전수 독해는 코드를 끝까지 검토했다는 뜻이지, 실계정에서 모든 기능을 실행했다는 뜻은 아니다.

2. 이번에 고친 원인

Agent 호출에는 description과 prompt가 필수였다. GPT가 description을 빠뜨리자 기존 코드는 도구 입력 오류를 세션을 중단해야 하는 오류로 처리했다. 실패한 세션 상태가 남아 후속 요청도 거부됐다.

기존수정
schema 오류 → 일반 실패 → turn 중단 → failed barrier권한 검증 통과 + schema 오류 → GPT에 실패 피드백 → 같은 turn에서 인자 교정
다음 요청도 recovery_required유효한 호출만 Claude Code에 한 번 전달
인자 오류와 권한 오류가 같은 실패 경로다른 thread·미등록 도구·교정 예산 초과는 계속 차단
flowchart TD
  A[App Server 도구 호출] --> B{소유권과 도구 등록 유효?}
  B -->|아니오| C[명시적 거부]
  B -->|예| D{인자 schema 유효?}
  D -->|아니오| E[최대 3회 실패 피드백]
  E --> A
  D -->|예| F[Claude Code가 도구 실행]
  F --> G[같은 turn에 결과 반환]

실제 검증 예: 응답 텍스트를 이미 보낸 상태에서 잘못된 Agent 호출이 발생해도, 실패 피드백 1회 뒤 교정된 Agent 호출 1개만 전달하고 HTTP200으로 완료했다. 이 검사는 가짜 App Server peer를 사용했다. 실제 GPT가 반드시 교정한다는 보장은 아니다.

3. 원본에서 가져올 것과 가져오지 않을 것

원본의 장점은 상태 경계를 명시하고 교차 요청을 시험하는 방식이다. 제공자별 우회 구현까지 옮기면 사용자 모델 선택과 도구 실행 의미가 달라질 수 있다.

흡수할 계약그대로 가져오지 않을 구현
소유자·세대별 연속성, 오래된 완료의 상태 변경 금지잘못된 identity를 무조건 stateless로 처리하여 MoAI receipt 검증 완화
의미 있는 출력 전후를 나누는 재시도·완료 판정이미 실행한 도구 재생, 빈 응답 11회 재시도 정책
첫 출력과 실제 생성 시간·usage 구분Kimi/Cursor의 전체 응답 버퍼링
mock을 통한 실제 HTTP 경로·후속 입력 검증어떤 timeout 결과도 통과시키는 assertion을 성공 증거로 사용
보조 요청이 메인 연속성을 오염시키지 않는 계약모든 summary를 같은 요청으로 간주하거나 무조건 소형 모델로 대체

메인 모델 하나와 서브에이전트별 지정 모델이라는 제품 개념을 유지한다. plan/run/routine별 메인 세션을 만들지 않는다. Factory는 lead+lane 구조이고 Kanban은 되살리지 않는다. 원본 이미지 모델은 gpt-image-2이므로 요청한 gpt-image-2.5 지원 근거가 될 수 없다.

5. 실시간 관측과 남은 문제

첫 byte가 빠르다고 추론이 빠른 것은 아니다. 스트림 시작 이벤트·이미 대기 중인 도구 segment·실제 새 텍스트 생성을 구분해야 한다.

  • 04c54aae…: 첫 byte 16.230초, Agent 필수 인자 누락 후 실패. 새 수정은 미배포.
  • d17bf130…: 첫 턴 40 tool results 중 오류 0. 별도 away_summary는 first byte 2.549초 후 finished. agent_summary 해결 근거는 아니다.
  • eefd29ac…: agent_summary scope mismatch 5건 재발. 38.893초 first-byte 구간에는 native exec의 30초 sleep이 포함됐다. 순수 생성 지연으로 해석하지 않는다. 17:08:25.875Z 세션 종료 관측.

새 세션의 native sleep 합계는 85.950초로 App Server turn 145.006초의 59.3%였다. 실행 지침의 실제 적용과 대기 감소는 수정 후보 운영 검증이 필요하다.

아직 해결됐다고 할 수 없는 것

실제 agent_summary의 정확한 거부 분기, 모든 Claude Code 기능, 실제 GPT 인자 교정의 운영 수락, 이미지 2.5, 구독 ToS 판정. 새 설치본 배포와 활성 세션 재시작도 하지 않았다.

6. 다음 개선과 확인할 기준

  1. 오류를 입력·권한/이력·전송·취소·자원 한도로 나누고, 실패 fixture부터 추가한다.
  2. main/child/sibling/summary/clear의 소유권과 세대를 교차 검증한다.
  3. 부분 출력 후 재실행·도구 중복·가짜 성공 terminal이 없는지 기존 테스트를 확장한다.
  4. 요청별 upstream 대기·첫 텍스트·tool 대기·완료·usage를 연결한다. 계측 없는 TPS는 미상으로 둔다.
  5. 실제 새 후보 빌드로 운영 수락을 확인한 뒤 설치본 교체를 결정한다.

직접 확인할 것: 실행 BuildID가 바뀌었는지, 실패한 요청이 main인지 summary인지, 수정 검사가 mock인지 실제 GPT인지. 이 세 가지가 섞이면 같은 장애를 고쳤다고 오판하기 쉽다.
