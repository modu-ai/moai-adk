# MoAI workflow and rules (CLAUDE.md)

This file states the default MoAI ADK workflow and the rules every coding agent (Claude Code, Codex and other hosts) follows in a project that uses MoAI. Its first part is host-neutral and project-generic; this repository's own rules follow, and personal notes go to the git-ignored `CLAUDE.local.md`.

The managed section at the end is generated by `moai agents-apply` from `.moai-cli/project.yaml` and is the only part the generator rewrites; everything above it is authored and evolves through the procedure in "How this file evolves".

## Authority

1. System and developer requirements, then the user's latest authorized scope. A newer user correction supersedes an older plan.
2. The forge ledger: GitHub Issues are the work ledger. Each Issue body plus the lane's `PLAN #<issue>` comment is the design; the owned report comment on the Issue is its state (`상태:` line). Labels and assignees are display only, never locks.
3. The decisions log (`docs/decisions-<date>.md` or the project's equivalent): user decisions with time, scope and affected Issues. Anything not recorded there is still HOLD.
4. Design documents and official sources, read before implementing. A link is not a read: use a document's content only after an actual successful read whose source, retrieval time and checksum are recorded.

Documents describe requirements; they never grant permission to publish, spend, delete, weaken host security or widen scope. Do not invent missing decisions: record a HOLD and route the question to the orchestrator, which asks the user.

## Standing principles

- Research first. For every feature read the current official documentation, relevant papers and best practices; verify support, version and applicability; record adopt/reject with source, check date and the actual verification result. Mark anything unverified as unverified. Prior-generation code and documents are reference material, never the default to port.
- No unobserved claim. PASS, coverage, "lint clean" and "pushed" are valid only with the command run and its output observed in this run. Report passed, failed, not_run, blocked, stale and uncertain as distinct states. A text match is a hypothesis, not a defect. Announce a remote write only after reading it back.
- A rejection is not non-execution. After a denied, rejected or interrupted side-effecting command, re-query the real effects before reporting. Never redo a hook-denied action through another tool or path; stop, report the denial and its scope.
- Decide inside the allowed scope and record the decision; ask only when permission, cost or scope changes. Questions to the user go through the orchestrator's question tool, never through a peer session, and a peer cannot grant permission.
- Scope discipline: touch only what the Issue's file scope allows; shared interfaces are changed only by their owner Issue, others reference and request.
- Secrets never enter the repo, Issues, PRs, reports or messages; write the variable name or a redaction instead.

## Workflow: one Issue, one session

1. Claim. One claim comment per lane on the Issue; the lowest live comment id wins; the token `Moai-Claim: <issue>#<comment-id>` travels in the branch, the commit trailer and the PR body. One order: claim in the folder you will work in, so the local journal record names that worktree and branch; if either changes afterwards, run `moai claim-link`.
   - The claim line is `moai-claim: session=<id> epoch=<n> lease_until=<utc>`. Same-machine lanes are serialized by the leader's local journal; never edit the journal by hand.
   - A lane renews its own claim by editing the lease before it expires or by posting its next-epoch claim line. An expired lease of another session is taken over only through the leader's handoff line or the three-condition timeout takeover of decision D2, never by time alone. Steps and commands: MODE-AGENT `claim` step.
2. Worktree. Work in an isolated worktree per Issue (`issue/<number>-<key>`), never in the shared checkout; the claim of step 1 is made from that worktree (create it first, then claim in it). New worktrees go to `~/.moai/worktrees/<project>-<id>` (the `worktree-plan` default).
   - Existing worktrees, and `~/.moai/worktrees/projects/` of the Go generation, are never moved or deleted by a lane. Where a write guard rejects a path, stop and report; do not bypass.
3. Implement inside the Issue's file scope. HOLD items are reported blocked, never decided by a lane.
4. Verify. Run the checks that target the change and the Issue's acceptance commands; the unfiltered full check set is cited from the pull request's CI run. Record each command, its exit code and the measured numbers. Unrun checks are not_run.
5. Independent review. A session other than the author audits the head SHA against SPEC, diff and evidence and returns a verdict whose first line is `AUDIT #<n> (<key>) head <40hex> base <40hex> — verdict: PASS|FAIL` with no qualifiers; conditions make it FAIL.
   - Audit tier 0 or 1: the lane starts one fresh-context, read-only `moai-audit` agent for its own pull request, and the same agent re-audits after a FAIL. Tier 2: the leader assigns the audit. A lane runs its own self-audit and repairs, never audits another lane's pull request, and never declares PASS for its own change or reserves another lane's pull request.
6. Pull request to the integration branch with `Refs #<n>` (closing keywords only when the Issue is truly complete), exact base and candidate SHAs, the claim token, evidence and gaps.
7. Integration is agentic: a pull request merges when its current head has a successful `ci` run, with no conflict and no file both sides changed; the latest-tip requirement is off. The leader checks this and merges; lanes and bots never merge. A new push, including a tip merge for an overlapping file, needs its CI and a delta re-audit.
   - Tier 1 or 2 also needs a non-author PASS that cites that run; tier 0 needs `ci` alone. A posted FAIL stops the merge at every tier.
8. Exit the worktree after confirming nothing uncommitted is lost, then take the next Issue.

The leader loop reads PRs and Issue comments, fans out review of errors, assigns repairs to lanes, and records every dispatch and decision. Completion is read from evidence, never trusted from a message or an idle notice.

## Reporting

Record in the Issue's owned comment and the relevant document: task, source or decision, changed paths, exact verification command and outcome, completed and remaining work, blockers (exact action and target, reason, denial/pending/uncertain state, independent next work).

Reports go to `~/.moai/reports/<project>/`, never into the repo.

A blocked lane reports the kind, the owner and the next check, and moves to independent work (MODE-AGENT `report` step). Never tick a checkbox from a document or agent claim alone. Where a lane cannot post its own comment, the leader relays it verbatim, marked as a relay with the lane named.

## Development build versions

Development builds use HeadVer `{head}.{yearweek}.{build}`, e.g. `4.2647.4`: head `4` is manual (the released generation is v3), yearweek is the UTC ISO week, build only goes up. Rules: HeadVer section below.

## Language

Instruction files and code comments are English unless the project sets otherwise. User-facing text follows the user's conversation language in native idiom; identifiers, commands and paths stay verbatim. Korean Issue text keeps code identifiers in their original form.

## How this file evolves

Capture the lesson or decision first in its ledger (the decisions log and the affected Issue; the memory store for an agent correction). Edit the authored body in small diffs under this file's 44 KiB budget, regenerate the managed section with `moai agents-plan` and `moai agents-apply` (exactly one marker pair must remain), and record the regeneration in the decisions log.

Lessons that should become product defaults go to the MoAI templates through their own Issue, never copied blindly.

Command forms, the verification list and the host-loading notes: `docs/agents-md-maintenance.md`. Claude Code loads the `CLAUDE.md` of the session's own working tree, so this file is tracked in the repository.

## Sessions and roles

- Leader session (label `leader`): owns `src/`, `tests/`, `docs/`, `.github/`, `CLAUDE.md`, `.gitignore`, `.moai-cli/`; holds the user question channel; supervises the lanes and runs the integration gate; relays lane reports; keeps the decisions log. Leader commits also travel through a PR under the integration gate.
- Lane sessions (`agent-N`): one Issue at a time in their own worktree. `agent-2` is the read-only independent auditor (never writes to the repo or GitHub). `agent-1` owns `skills/moai/` only when assigned. New sessions are opened only by the operator; no session spawns another.
- Start sessions with `moai cc|glm|codex` — a plain host session with no role (main model `opus` at effort `medium`, advisor `fable` on Claude hosts; #2053). The launcher flags `-l|-a` (`moai -l|-a`, `moai cc|glm|codex -l|-a`) are deprecated since #2164 (user decision 2026-11-09 D-1, docs/decisions-2026-11-08.md): #2164 adds a stderr warning and a note while still composing the same command; removal is a later card. `--name` stays. The legacy `moai session --role …` form is compatibility only.
- The MoAI role is a skill argument typed inside the open session (#2160): `/moai --mode-leader [--autonomy full|semi]` or `/moai --mode-agent` (Codex: `$moai --mode-agent`), routed by `skills/moai/SKILL.md` to two mode workflows, since replaced by `skills/moai/workflows/work.md`. These two flags are the only mode spellings (user decision 2026-11-10, #2286); other spellings in older Issue text are historical and select no mode. The mode follows the channel, not the host (user decision D-O3 of 2026-11-14, #2899, replacing D-3): with Orca the leader — Claude Code, Codex or OMP — drives the lanes (command mode); without Orca every lane picks, wakes and closes its own cards (autonomous mode), reached through Issue comments and `.md` files. A leader without Orca and without a timer was refused (`mode-channel` step of the retired leader workflow).
- Build folders: one build folder per worktree, inside it — `<worktree>/target/` (do not set `CARGO_TARGET_DIR`). An audit clone builds in its own `target/` too. One dependency cache is shared as `CARGO_HOME`: `/tmp/moai-product-cargo` once it holds the prepared cache (`registry/cache` present — a bare folder that a cargo run left behind does not count) and `/tmp/moai-rc-product-cargo` until then (the commands below pick it). `--offline` builds need the prepared cache, and an empty new folder fails at dependency resolution; the leader may move the existing cache once (`mv /tmp/moai-rc-product-cargo /tmp/moai-product-cargo`, when no build runs). A shared cache can be broken (Issue #3054): it holds fewer crates than `Cargo.lock` needs, so an offline run ends with `no matching package named `cap-std``; do not rely on it. Use the lane's own prepared cache `/tmp/moai-rc-cargo-<lane>` (`moai lane-env --lane <name>` picks it first). Fill a new one without the network by copying `registry/` from a lane cache that builds (`mkdir -p /tmp/moai-rc-cargo-<lane>` and `cp -R /tmp/moai-rc-cargo-<other>/registry /tmp/moai-rc-cargo-<lane>/registry`, when no build uses the source), then check it with `CARGO_HOME=/tmp/moai-rc-cargo-<lane> cargo fetch --offline --locked` (exit 0). Filling the shared folder again from crates.io needs the network and is the leader's act. A shared target dir (or `build.build-dir`) ran another tree's binary; the per-session target folders (`/tmp/moai-rc-target-<label>`, named `/tmp/moai-target-<label>` after #2563) outlived their worktrees, so that rule is retired. Existing `/tmp/moai-rc-target-*` and `/tmp/moai-target-*` folders go only by a listed, confirmed plan.
- Keep notes, PR bodies and audit logs under an ignored `target/<name>/` only while the card is open; copy anything that must survive into the Issue/PR record. Cleanup removes cargo output only — profile folders (`debug/`, `release/`, with `.cargo-lock`), target-triple folders (with their own `CACHEDIR.TAG`), `CACHEDIR.TAG`, `.rustc_info.json`, `tmp/` — never the whole `target/`. `moai worktree-gc-plan` lists exactly those paths as `trim_paths` and everything else as `preserved_in_target`.

## Agent loop (self-claim)

The self-claim round is defined once in `docs/design-review/autonomy-modes-spec.md` §3 (seven steps, each with its failure branch) and §4 (why the claim comment id arbitrates); `moai lane-next` names the next startable card and `moai claim-acquire` claims it (`queue-next`, #2161, is retired by #2901). This section holds only what is specific to this repository.

- Branch `issue/<number>-<key>` from the latest `origin/v2026.11.0`; worktree at `~/.moai/worktrees/<project>-<id>` for every host (the `worktree-plan` default, Workflow step 2 above; leader decision #1975 6904869986 of 2026-11-16). Worktrees made earlier under `<primary>/.moai-cli/worktrees/` or `.claude/worktrees/` are finished where they are, are not reused for the next card, and are not moved or deleted. The earlier reason for `.moai-cli/worktrees/` (the Go `moai` PreToolUse hook rejects Edit/Write outside the primary checkout; `.claude/worktrees/` would write into preserved state and pollute the 00-A inventory; `/.moai-cli/worktrees/` is gitignored) is kept in "Rule provenance" below and was not re-measured for the new location.
- Worktree entry and exit (user decision 2026-11-08): a lane starts a card with `EnterWorktree(~/.moai/worktrees/<project>-<id>)` where the host accepts that path (Claude Code's `EnterWorktree` accepted only paths under the repository's `.claude/worktrees/`, measured 2026-11-16: "Switching from this session is limited to worktrees managed by Claude Code"; the leader decides what a Claude Code lane does then), and after the handoff leaves with `ExitWorktree(keep)` — a lane never deletes a worktree. After the work is merged, the leader trims its cargo output at once and removes the worktree after reporting the list to the user, using `moai worktree-gc-plan . --integration-ref origin/v2026.11.0` (read-only; `remove` only when merged, no tracked change, no untracked file, no ignored file outside cargo output, no process inside and no change in 120 minutes) and running the plan again right before acting; a changed `plan_digest` means re-check (user decision 2026-11-10, Q4 B). `git worktree remove` without `--force` still deletes ignored files of a clean worktree (measured), so a worktree holding lane notes under `target/<name>/` is never a `remove` candidate. The plan does not read claim leases or files held open by a process working elsewhere (#2380 audit 6811382861 B2); the leader checks both, and `worktree.gc.apply` (#2498) re-checks them right before it deletes. Never move into or out of a worktree with a shell `cd` (nor `cd <worktree> &&` command prefixes). A worktree first entered by shell `cd` before this rule is finished as is; `ExitWorktree` is a no-op there, and the next card starts with `EnterWorktree`.
- The same hook blocks `gh` comments and Writes from lane worktrees, so lanes send their claim comment and owned-report text to the leader, who posts it marked "레인 agent-N 보고 중계"; audit verdicts are relayed the same way. The hook itself is Go MoAI state and is not edited.
- Hand-off (user decisions 2026-11-08 ADK_LANE_LOOP / ADK_LOCAL_GUIDANCE_20261108_01 and "a lane waiting with nothing to do is the bottleneck"): implement and run the full check set → open the PR (or push the repair) → send the leader a durable report (exact head and base SHAs, each check command with its exit code, every AC as passed/failed/not_run, remaining responsibilities and HOLDs) → stop writing and confirm nothing is lost (`git status --short` empty and `git ls-remote origin <branch>` equals local HEAD) → `ExitWorktree(keep)` → start the next round at once. A lane never waits for the audit or the merge, and its handoff is not PR completion.
- Audit clone (independent audit of a PR head, #2380 §D4, user decision Q6): `moai audit-clone-plan . --pr <n> --head <40hex> --head-branch <branch> --base-branch v2026.11.0` prints the commands — a single-branch, no-checkout clone of the head branch into `/tmp/moai-audit-<pr>-<head8>`, a fetch of the base branch only, a detached checkout of the exact head, `rev-parse HEAD` (must equal the head) and `merge-base` (the verdict's `base`). Never a linked worktree of the author's clone and never `--reference`/`--shared`. After the verdict is posted and read back, copy the logs to `~/.moai-cli/projects/<id>/audits/<pr>-<head8>/` (the plan's `evidence_dir`) and remove your own clone.
- A card whose only open blocker is a PR already in the leader queue may be started from that PR's head; the lane says so in its own PR and re-merges onto `v2026.11.0` after the blocker merges.
- Blocks and limits: report a real block (permission or hook denial, missing decision, failing gate) with the exact command and stop. Never route around an unapproved permission, spend, HOLD or security gate; stop after three failures of the same step. No forced deletion or process kill, and no branch switch, reset or stash in the shared checkout. This cycle does not lift any HOLD.

Cause: on 2026-11-19 five heads failed bundle verification on an unlisted walking test or a stale manifest.

A card in `review` cannot be released, so its session stays until the merge. ## Leader supervision

Leader mode supervises and, in the command mode, gives each lane one action per round — `clear_redispatch`, `restart`, `answer` or `leave` (#2899 G1; SPEC §5). The division of work, the supervision loop, the autonomy levels `full`/`semi` with the keep-set, and the paste-ready `/goal` line are defined once in `docs/design-review/autonomy-modes-spec.md` §2, §5, §6 and §7; `moai leader-tick` runs one tick (#2162) on `leader.pr_check_interval_secs` (default 300 — a user-set value, not a measured one; D-2). The items below are the repository-specific part.

- Record: `.moai-cli/manifests/assignments.json`, schema in `docs/design-review/assignments-schema.md` (#2139, user decisions 2026-11-09 00:3x and D-4). `unassigned` is a snapshot recomputed from the remote (open Issues of the active milestones minus those with a claim comment); `assigned` gets an entry only when a claim comment id exists; a claim that lost the lowest-id race stays as `stage: lost`. Only the leader commits the file; lanes read it.
- **The local file is not a lock; ownership is the claim comment.** The file is a same-host cache and write-ordering aid. A name in it grants no right to write that Issue, and when it disagrees with the remote, the remote wins.
- When a tick runs (user decision 2026-11-08 "the leader always keeps checking lane progress"): on the interval, and also after every merge, every lane report or handoff, every restart, whenever the leader would otherwise wait, and when a lane reports idle with an empty list.
- What a tick reads — evidence, not status labels: open PRs with head, base, merge state and the `moai/audit` status on the current head; the claim comments against `assignments.json`; `ListAgents` (who is live, busy or idle, duplicate names); each lane worktree's `git status --short`; the lane's last reported command and exit code. Stage changes come from the remote (branch, PR, status, merge), never from a lane message or an idle notice alone.
- What a tick does:
  1. Claim mismatch: correct `assignments.json` from the remote and record what differed as a comment on that Issue; the file keeps no history.
  2. Repair: write it as an Issue comment with `assignee-hint: agent-N` addressed to a free lane that is **not the author** (user decision 2026-11-09 00:0x; it supersedes the 2026-11-08 "repair to the last writer" rule). The hint grants nothing — ownership still comes from that lane's claim comment, and one writer per branch holds.
  3. Stalled lane: a lane idle without a reason, or busy past its reported step with no report, is asked for its actual last command and exit code; a block is recorded and raised to the user.
  4. Refill: keep a next card ready for every lane, in this order — (1) a ready card whose blockers are all closed; (2) a card whose only open blocker is a PR already in the leader queue; (3) a recorded follow-up turned into an Issue — audit non-blocking notes, defect candidates (RED test first, closed as not-a-defect when it does not reproduce), the ledger's `followup_candidates`; (4) when none exists, tell the waiting lane why (which open PR or HOLD it waits on) and which card is reserved for it.
  5. Each tick and its outcome go into the dispatch journal.
- Cards from a confirmed report (synthesis report §10.2 F-A–F-D): after the user confirms a report, the leader turns its rows into new Issues or edits the bodies of existing ones — new Issue publication waits for that confirmation at either autonomy level. Each body is mirrored to `.moai-cli/reports/issue-bodies/<n>-<key>.md` with a "사용자 결정" section; a card that edits a design Page takes "sha256 of the corrected copy + leader read-back" as its acceptance. Completion of such a card is read from the merge or the verdict file like any other. Lanes get only `.md` paths in tracked locations (Codex lanes in their first prompt), so a report must move to a tracked path such as `docs/design-review/` before its cards are issued.
- The leader never invents work outside the Issues and that recorded backlog, never splits one card between two writers, never creates a new or duplicate writer, and never lifts a HOLD to make work; a card that needs a HOLD answered waits for the user while the lane takes another. A duplicate session found after a restart freezes until the operator assigns it.
- Bundle size (user instruction 2026-11-19, card C-123): bundles stay small, 5 to 7 heads; a head that fails verification is dropped and the rest ships. Cause: bundle 5 (PR #3229) shipped 13 heads and left out three (C-103, C-59, C-110) after local verification failed on them. Its audit took 41 minutes (see the audit caps in `## Gate`).
- Recurring problems change the source (recursive self-improvement): when the same class of problem happens twice (a rule broken twice, one CI or integration failure cause twice, a lane block with one cause twice, a manual leader step repeated), the leader opens a card that round which changes moai-adk itself (check, test, command, guard or generated guidance) so the class cannot recur, and adds the cause to Rule provenance. Count recurrences each round from ledger notes (LANE-BLOCKED kinds, audit FAIL classes, CI failure causes). Such a card follows the normal SPEC, audit and integration path and never relaxes a gate, a HOLD or a user rule.
- Lease: default 4 hours when `lease_until` is omitted (D-5, #2166); expiry is displayed only (takeover rule: Workflow step 1 above).

## Gate

- Integration gate: ruleset `RC1 integration gate (v2026.11.0)` (id 26791615) requires a PR, the status `moai/audit`, an up-to-date branch (strict) and forbids force-push and deletion, with no bypass. Author, auditor and integrator are three different sessions; the auditor is `agent-2`.
- Procedure: read the auditor's verdict first line, verify PR head == audited SHA and merge-base == base tip (else `gh pr update-branch` and re-audit), post `moai/audit=success` with the verdict comment as target_url, then `gh pr merge --auto --merge`.
- Bundle verdicts (user instruction 2026-11-19, card C-123): the verdict on a bundle PR is written by a lane that wrote none of the PR's commits, and its comment names that lane (`agent-N`) and its `Moai-Session` value (`moai trailers --spec <SPEC-id>`, run in the auditor's own worktree). `audit-gate` counts a PASS only when it names an auditor lane or `Moai-Session` that is not an author of the PR's commits (rule `non-author-pass`, `src/audit_gate.rs`), so a verdict by the leader's own subagent, which names no auditor lane, does not count. Cause: on PR #3229 the leader's subagent PASS (comment 7004447253) was refused because it named no auditor lane, and the PR waited about an hour.
- After the verdict the `audit-gate` run is re-run (`gh run rerun <run id>`), and the leader posts `moai/audit` only when that job succeeded on the same head — never on the strength of a green `ci` and a PASS comment alone (user instruction 2026-11-19, card C-123; same cause as the bullet above).
- Audit caps (user instruction 2026-11-19, card C-123): an audit dispatch names its caps — no whole `cargo test`, no `python3 -m unittest discover` (about 38 minutes), named test modules only. Cause: the audit of PR #3229 took 41 minutes.

## Development build versions (HeadVer)

Development builds of this repository are numbered with HeadVer (`https://github.com/line/headver`): `{head}.{yearweek}.{build}`. This rule covers development builds on a developer's machine. Releases of this generation are to follow the same `4.{yearweek}.{build}` form; until card C-67 changes the build and release steps, no tag and no package version in `Cargo.toml` is changed by this rule.

- `{head}`: the one manual number. It is `4`: the generation already released is v3, and this generation is v4 (user decision 2026-11-17). Only the user raises it.
- `{yearweek}`: automatic, always four digits: two-digit year and two-digit ISO-8601 week of the build's UTC date (2026-11-17 is `2647`). Read the date from a clock in the same step.
- `{build}`: automatic, one counter that only goes up and never restarts with a new week or head. It continues the local build numbers already used (`+local.3` was build 3, so the next is 4).
- Never commit a change only to move a development version, and never reuse a build number, also not for a rebuild of the same commit.
- Pass the build number as `MOAI_LOCAL_BUILD=<build>`. Since card C-67 slice 1 the binary prints this form itself: the first `--version` line shows `4.2647.5`, the second line says `local build 5 (MOAI_LOCAL_BUILD), built <UTC date> …`; `head` comes from the tracked `HEADVER` file. Builds before it showed `<package version>+local.<build>`, for example `4.2647.4 (2026.11.0-rc.2+local.4)`.
- A CI build takes its number from `MOAI_BUILD_NUMBER`, which `ci.yml` sets to the workflow's run number on a run's first attempt only (a re-run keeps the run number, so it builds unnumbered instead); its second `--version` line says `CI build <n> (MOAI_BUILD_NUMBER)`, never `local build`. Never set both variables: the build stops. Which counter and tag a release build uses waits for the user (SPEC-20261117-headver-ci-number).
