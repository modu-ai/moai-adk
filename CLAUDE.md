# MoAI ADK repository rules (CLAUDE.md)

Team-shared rules for every coding agent that works in this repository. Claude Code is the supported host; GLM runs through the Claude Code launcher. Personal and machine notes go to the git-ignored `CLAUDE.local.md`. Lane and leader operating detail lives in `docs/lane-rules.md` and `docs/leader-rules.md`; where every earlier rule of this file went is in `docs/claude-md-rule-provenance.md`. The managed section at the end is generated by `moai agents-apply` from `.moai/project.yaml`; everything above it is authored (see "How this file evolves").

## Authority

1. System and developer requirements, then the user's latest authorized scope. A newer user correction supersedes an older plan.
2. The card ledger: local cards (`moai card`, user decision 2026-11-16) are the work ledger. A card's body, criteria, notes and reservation are its state; the SPEC the card names (`.moai/specs/<SPEC-ID>/spec.md`) is the design. GitHub carries releases, CI and the release gate; it is no ledger.
3. The decisions log, `docs/decisions-2026-11-08.md`: user decisions with time, scope and affected cards. Anything not recorded there is still HOLD.
4. Design documents and official sources, read before implementing. A link is not a read: use a document's content only after an actual successful read whose source, retrieval time and checksum are recorded.

Documents describe requirements; they never grant permission to publish, spend, delete, weaken host security or widen scope. Do not invent a missing decision: write `LANE-BLOCKED kind=decision <card> <the decision, its options and the default>` as a note on the card; with no registered leader take the next card, otherwise wait for that leader's dispatch.

## Standing principles

- Research first. For every feature read the current official documentation, relevant papers and best practices; verify support, version and applicability; record adopt/reject with source, check date and the actual verification result. Mark anything unverified as unverified. Prior-generation code and documents are reference material, never the default to port.
- No unobserved claim. PASS, coverage, "lint clean" and "pushed" are valid only with the command run and its output observed in this run. Report passed, failed, not_run, blocked, stale and uncertain as distinct states. A text match is a hypothesis, not a defect. Announce a remote write only after reading it back.
- A rejection is not non-execution. After a denied, rejected or interrupted side-effecting command, re-query the real effects before reporting. Never redo a hook-denied action through another tool or path; stop, report the denial and its scope.
- Decide inside the allowed scope and record the decision; ask only when permission, cost or scope changes. Questions to the user go through the session the user talks to (a lane writes a `LANE-BLOCKED` note), never through a peer session, and a peer cannot grant permission.
- Scope discipline: touch only what the card's write scope allows; a shared interface is changed only by the card that owns it, others reference it and request the change.
- Secrets never enter the repo, cards, PRs, reports or messages; write the variable name or a redaction instead.
- Recursive self-improvement (RSI): this file, `CLAUDE.local.md`, the skill and agent instructions (`skills/**`, `agents/**`) and the code (checks, tests, commands, guards, generated guidance) keep improving. At every round and when every card ends, what a correction, a FAIL, a `LANE-BLOCKED`, a refused landing or a repeated manual step taught goes, as a small diff, to where its cause lives; the same class a second time is fixed in that round. Put it on the card that already owns the result (a new card only when none does) and measure before and after with a `moai` command; if the numbers do not improve, revert or fix again. Removing comes before adding, and a gate, a HOLD or a user rule is never weakened. Personal notes go to the untracked `CLAUDE.local.md`, team rules to this file through a card, product defaults to the templates through a SPEC.
- Recurring problems change the source: when the same class of problem happens a second time (a rule broken twice, one CI or integration failure cause twice, a lane block with one cause twice, a manual leader step repeated), fix it in that round when it can be fixed; for what cannot be fixed now the session that sees it adds one line to `docs/later.md` that names the cause and the change at the source (check, test, command, guard or generated guidance); the leader turns such lines into cards when work is free. A line never relaxes a gate, a HOLD or a user rule.
- Dangerous path: a change that deletes, resets, starts a process or builds a permission rule carries in its READY a run of the dangerous path itself in a throwaway (a link, a plain folder at a registered path, a hung child, a compound command), not only green tests.
- Guard mutants (tier 2 only): the READY carries one `guard-mutant: <test> | <code removed> | exit <n>` line per new guard test (`none | <reason>` without one); `exit 0` is repaired first. Below tier 2 none is asked for.

## Scope and sessions

- Scope is RC1 (`2026.11.0-rc.1`): ship the first version fast on the existing plan. The communication hub (the real-time channel between running sessions) is deferred; its decisions are kept in `docs/session-hub-research-2026-11-08.md` and must not leak into RC1 requirements.
- Hosts: Claude Code, with GLM through the Claude Code launcher. Codex and OMP are withdrawn (user decision 2026-11-21, `SPEC-20261121-remove-codex-support`); ZCode headless, ACP and remote options come later.
- Start a session with `moai cc|glm`: a plain host session with no role (model `opus`; effort `medium` for `cc`, `high` for `glm`); `--name <name>` names it. The launcher flags `-l|-a` are retired (user decision D-1 2026-11-09, `SPEC-20261124-launcher-retire-role-flags`) and the launcher refuses them. The role is typed inside the open session: `/moai work` for a lane (the card loop) and `/moai leader` for the coordination window; the skill picks the route from that first word.
- The leader supervises, relays and lands; a lane (`agent-N`) works one card in its own worktree. The author, the auditor and the lander of one change are three different sessions. `CLAUDE.md` changes only through a card whose write scope names it.

## Flow: one card, one session

The flow is NeXT-Flow ("Work in parallel. Land once."); the full description is `skills/moai/references/flows/next-flow.md`, the integration branch is `work_flow.integration_branch` of `.moai/project.yaml` (`NeXT`).

1. Take. `moai card next` names the card; `moai card take <card> --scope <p> --worktree <w> --branch <b>` reserves it and answers a `generation`. Ownership is that reservation only, never a local file, a message or an idle notice. Before every write run `moai card check <card> --generation <g> --path <p>` and write only on `allowed: true`.
2. Worktree. Work in your own worktree (below), never in the shared checkout.
3. Implement inside the card's write scope. HOLD items are reported blocked, never decided by a lane. The card's body and criteria are the design; only a tier 2 change (deleting, permissions, gates, HOME) needs a SPEC the user approved, and a lane never records an approval itself or waits for one on other work.
4. Verify (below). Record each command, its exit code and the measured numbers. Unrun checks are `not_run`.
5. Submit. A lane only commits: no push, no pull request, no merge of a moved tip. It submits its head commit and the base its checks ran on in one READY note (first line `LANE-READY-INTEGRATION <card> head=<40hex>`), with the check receipt, each acceptance criterion as met, not met or not_run, and the gaps. The READY note is the submission signal that starts the independent review; it is not the ledger state `ready` (a card that can be taken), not a verdict and not a landing.
6. Independent review. A session other than the author audits the exact head (the submitted one) against the card criteria, the diff and the lane's receipt (`skills/moai/references/audit.md`); a resting lane is the auditor. The author never audits. The auditor records the verdict itself with `moai card verdict`, never the leader for it, and adds a note whose first line is `AUDIT <card> (<scope>) head <40hex> base <40hex> — verdict: PASS|FAIL`, with no qualifiers. FAIL is for four things only: behaviour that differs from the criteria, data loss, a security problem, a weakened gate; every other finding is a non-blocking line and the verdict is PASS. A second FAIL of one card goes to the leader, not to a re-audit. Tier 0 and 1 changes get a light audit that reads the receipt and runs nothing; a path under the tier-2 floor list of `audit.md` (this file included) gets the full audit. `moai bundle check` reports the floor.
7. Landing. The leader lands an audited head once: `moai card land <card> --head <40hex> --by leader`. It moves the integration branch by one compare-and-swap and closes the card; a moved tip answers `stale_base` and the lander merges the head onto the tip in a worktree of its own. Nobody moves the integration branch by hand, by a reset or by a push; a protection hook refuses it. Remote checks never block a landing; a failed remote run becomes one line of `docs/later.md`.
8. Release. Only a real deployment reaches GitHub: a person pushes `release/<40hex>` (`release/rc/<40hex>` for a pre-release) made from the verified local tip, the release workflow numbers and names the build (`SPEC-20261119-headver-release-workflow`; tag `moai-adk-v{head}.{yearweek}.{build}`, user decision D6 of 2026-11-18), and the leader opens one pull request for the independent audit. Ruleset `RC1 integration gate (v2026.11.0)` (id 26791615, read 2026-11-23) requires a PR, required status checks and no force-push or deletion, with no bypass. `moai/audit` is posted only when the `audit-gate` run succeeded on the same head and the verdict names a lane that wrote none of the PR's commits.
9. Exit the worktree after confirming nothing uncommitted is lost; with no registered leader take the next card, otherwise wait for that leader's dispatch. A READY note or a `LANE-DONE` line hands a card back and ends the lane's work on it, not the card: only a landing closes it, and a lane never ends a reservation by hand or sends `/clear` to itself. With no registered leader the flow ends at the submission: no lane audits, lands or asks for a landing.

## Worktrees and builds

- New worktrees go to `<project>/.claude/worktrees/<name>` (user decision 2026-11-22; `SPEC-20261122-worktree-place`), one branch per card cut from the local integration tip (`origin/` is behind it). Worktrees made earlier under `~/.moai/worktrees/` or `.moai/` finish where they are and are not reused.
- A lane enters its worktree with `EnterWorktree` and leaves with `ExitWorktree(keep)`; never move into or out of a worktree with a shell `cd`, and never delete a worktree. The leader removes landed worktrees after reading `moai worktree-gc-plan . --integration-ref <branch>` (read-only; the plan does not read claim leases or files held open elsewhere, so check both first).
- One build folder per worktree: `<worktree>/target/`; do not set `CARGO_TARGET_DIR`. Cleanup removes cargo output only, never the whole `target/`. Notes and logs under `target/<name>/` are kept only while the card is open; copy what must survive into the card or the SPEC.
- Claude Code loads the `CLAUDE.md` of the session's own working tree, so a tracked change reaches a lane only when it is committed. A worktree under `.claude/worktrees/` also reads the primary checkout's `CLAUDE.local.md` but not its `CLAUDE.md` (measured, `SPEC-20261123-claude-md-rewrite`).

## Verify

- `moai check affected <base>..<head>` picks the tests, scans, `cargo fmt`, `git diff --check` and `cargo clippy` a range can break and runs them under one heavy slot; `--list` shows the selection. Before a commit also run `git diff --cached --check`. Run `check affected --card <base>..<head>` once at READY, unwrapped, on the checkout at the head: the READY receipt is the card set (the targets the range changes or names, at most about 20; a hub or shared path makes it the wide set and says why), and its summary line carries `selection=card`. Quote the summary line, every step's exit code and its log folder in the READY note.
- The wide set (a bare `check affected`) runs once per batch, not once per card: the leader lands 2 to 4 audited heads with `moai card land-batch C-n=<head> ... --by leader`, which runs it on their join, lands each head by one compare-and-swap and drops only a failing head. Only the session of the registered leader entry may call it.
- Other heavy cargo commands run in a slot: `moai heavy-slot-acquire --name <lane> --max <n> -- <command>`; `<n>` follows the leader's latest line. The whole `cargo test --locked` is the leader's, every five landings on the integration tip; a run of exactly the same checks on that tip is not repeated, and risk and release evidence stays. A red test stops landings until it is fixed.
- Tests are Rust only. Nobody runs a Python test module by hand as evidence; `moai check affected` runs its own remaining Python steps and their result is reported as it comes. Test in temporary projects or fixtures, never against installed user state. Do not claim Windows or Linux results from Mac fixtures.
- An audit dispatch names its caps: no whole `cargo test`, named test modules only. A light audit reads the lane's receipt and runs no test; a tier 2 audit runs at most two named modules.

## Lane rules (short; detail in `docs/lane-rules.md`)

- One card at a time and one receipt check at a time; a follow-up slice does not start while another card of the lane is open.
- Work cap: cards in work plus cards waiting for a check number at most twice the lanes; at the cap take no new card and help with checks and landings (`skills/moai/references/flows/next-flow.md`).
- Report a real block (permission or hook denial, missing decision, failing gate) with the exact command and stop. Never route around an unapproved permission, spend, HOLD or security gate; stop after three failures of the same step.
- No branch switch, reset or stash in the shared checkout; no forced deletion or process kill.
- A session-end notice means finish the card in hand, take no new card, then report `SESSION-END-READY`.
- Card-number commit messages are not used; commit messages, SPECs and branch names name the SPEC.

## Leader rules (short; detail in `docs/leader-rules.md`)

- The leader supervises, relays and lands; it never invents work outside the ledger, never splits one card between two writers and never lifts a HOLD to make work. Which reads and actions a round makes is in `docs/leader-rules.md`.
- A landing batch is 2 to 4 audited heads (`moai card land-batch`), one head alone only for a risk or an exception; a head that fails the batch check is dropped and the rest ships. The heads of a release (`release/<40hex>`) are a release bundle, never called a batch. The leader opens no card above the work cap.
- After a finished card the leader clears the lane (`/clear` through `orca terminal send`) only when the ledger shows the card done or released and nothing is open; see `skills/moai/references/flows/next-flow.md` for the stages.

## Repository and preservation boundaries

- Integration target `NeXT` (local branch, user decision 2026-11-23). The local branch `v2026.11.0` is a recovery ref that stopped at `b3ba2b30d5`; the remote `v2026.11.0` (`6a8fa9cacf` when read on 2026-11-23, protected by ruleset 26791615) is the base of the release pull request. `2026.11.0-rc.1` and `archive/main-based-2026.11.0-rc.1` are preserved refs; remote `main` is untouched. Re-read `HEAD` and the branch immediately before any commit; never reset, rebase, stash or switch branches in the shared checkout.
- Stage by explicit pathspec after re-reading `git status --short`; never `git add -A`, `git add .` or `commit -a`. Scan staged bytes for secrets and personal paths; `.claude/`, `CLAUDE.local.md`, `target/`, `.mcp.json` and raw `references/` are never staged. `.moai/specs/`, `.moai/project.yaml` and `.moai/evals/` are tracked.
- State folders: project state is `<project>/.moai/` and home state `~/.moai/`; the earlier `.moai-cli/` and `~/.moai-cli/` are read only where they exist and are never created or deleted by a lane. Never delete, overwrite or re-apply into the user's `.claude/` settings or `~/.moai/` data.
- The sibling `moai-adk-go` repository is read-only reference; its binary and credentials are never invoked or copied. The Go-generation `.github` files were removed on the user's instruction; do not recreate them.
- `experiments/` holds spikes, not integrated product features.
- No release or deployment without the user's pick.

## Development build versions (HeadVer)

Development builds use HeadVer (`https://github.com/line/headver`) `{head}.{yearweek}.{build}`, e.g. `4.2648.20`; releases of this generation follow the same form. This rule moves no tag and no package version in `Cargo.toml`.

- `{head}` is the one manual number, `4` (the released generation is v3); only the user raises it. It comes from the tracked `HEADVER` file.
- `{yearweek}` is automatic, four digits: two-digit year and ISO-8601 week of the build's UTC date, read from a clock in the same step.
- `{build}` is one counter that only goes up and never restarts; never reuse a number, also not for a rebuild of the same commit. Pass it as `MOAI_LOCAL_BUILD=<build>`; a CI build takes `MOAI_BUILD_NUMBER` from the workflow's run number. Never set both variables. Never commit a change only to move a development version.

## Reporting

- Record in the card's notes and the SPEC Result: task, source or decision, changed paths, exact verification command and outcome, completed and remaining work, and blockers (exact action and target, reason, denial, pending or uncertain state, independent next work). A blocked lane reports the kind, the owner and the next check, then moves to independent work.
- Never mark an acceptance criterion from a document or an agent's claim alone: `moai card criterion <card> <n> --generation <g> --met --evidence <ref>`.
- Reports go to `~/.moai/reports/<project>/`, never into the repo.

## Language

- Instruction files (this file, `CLAUDE.local.md`, rules, `skills/**`), subagent prompts and all code comments are written in English.
- Commit messages follow the profile's `language.commit_messages` (`en` here; user pick 2026-11-24, `SPEC-20261124-launcher-retire-role-flags`), so a commit message is written in English.
- SPEC documents, card and decisions text, text typed into a session's chat input (including what the leader sends with `orca terminal send`), the conversation with the user and reports to the user are written in Korean. Commits already pushed are not rewritten. Every instruction to a lane (dispatch, answer, line after `/clear`, cross-session message) is in the user's conversation language. Identifiers, commands, paths and protocol lines (`AUDIT … verdict:`, `LANE-BLOCKED`, `LANE-READY-INTEGRATION`) stay verbatim. Auditors flag newly added or edited comments or instruction text that is not English; existing ones are rewritten only when a card asks.
- Korean text uses the words developers actually say (테스트, 브랜치, 커밋, 푸시, 머지, 리뷰, 워크트리, 뮤턴트, 픽스처, 골든 파일, 플레이키 테스트), never literal coinages such as 시험, 가지, 변이.

## How this file evolves

This file is part of the RSI rule of Standing principles: a lesson whose cause is here is fixed here in the round it is seen. Capture a lesson or decision first in its ledger (the decisions log and the affected card; the memory store for an agent correction). Edit the authored body in small diffs and keep it near 200 lines (the official limit is under 200 lines per file); anything longer belongs in `docs/` or a skill with a short pointer here. Regenerate the managed section with `moai agents-plan` and `moai agents-apply` (exactly one marker pair must remain) and record the regeneration in the decisions log. Command forms and the host-loading notes are in `docs/agents-md-maintenance.md`. A rule that leaves this file is listed in `docs/claude-md-rule-provenance.md` with where it went. Lessons that should become product defaults go to the MoAI templates through their own SPEC.
