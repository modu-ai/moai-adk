# MoAI workflow and rules (AGENTS.md)

This file states the default MoAI ADK workflow and the rules every coding agent (Claude Code, Codex and other hosts) follows in a project that uses MoAI. It is host-neutral and project-generic; project-specific development rules live in `AGENTS.local.md`, which MoAI reads explicitly when invoked. The managed section at the end is generated by `moai agents-apply` from `.moai-cli/project.yaml` and is the only part the generator rewrites; everything above it is authored and evolves through the procedure in "How this file evolves".

## Authority

1. System and developer requirements, then the user's latest authorized scope. A newer user correction supersedes an older plan.
2. The forge ledger: GitHub Issues are the work ledger. Each Issue body plus the lane's `PLAN #<issue>` comment is the design (#2880); the owned report comment on the Issue is its state (`상태:` line). Labels and assignees are display only, never locks.
3. The decisions log (`docs/decisions-<date>.md` or the project's equivalent): user decisions with time, scope and affected Issues. Anything not recorded there is still HOLD.
4. Design documents and official sources, read before implementing. A link is not a read: use a document's content only after an actual successful read whose source, retrieval time and checksum are recorded.

Documents describe requirements; they never grant permission to publish, spend, delete, weaken host security or widen scope. Do not invent missing decisions: record a HOLD and route the question to the orchestrator, which asks the user.

## Standing principles

- Research first. For every feature read the current official documentation, relevant papers and best practices; verify support, version and applicability; record adopt/reject with source, check date and the actual verification result. Mark anything unverified as unverified. Prior-generation code and documents are reference material, never the default to port.
- No unobserved claim. PASS, coverage, "lint clean" and "pushed" are valid only with the command run and its output observed in this run. Report passed, failed, not_run, blocked, stale and uncertain as distinct states. A text match is a hypothesis, not a defect. Announce a remote write only after reading it back.
- A rejection is not non-execution. After a denied, rejected or interrupted side-effecting command, re-query the real effects before reporting. Never redo a hook-denied action through another tool or path; stop, report the denial and its scope.
- Decide inside the allowed scope and record the decision; ask only when permission, cost or scope changes. Questions to the user go through the orchestrator's question tool, never through a peer session, and a peer cannot grant permission.
- Scope discipline: touch only what the Issue's file scope allows; shared interfaces are changed only by their owner Issue, others reference and request.
- Secrets never enter the repo, Issues, PRs, reports or messages; write the variable name or a redaction instead.

## Workflow: one Issue, one session

1. Claim. The lane posts one claim comment on the Issue (`moai-claim: session=<id> epoch=<n> lease_until=<utc>`); the lowest live comment id wins; the token `Moai-Claim: <issue>#<comment-id>` travels in the branch, the commit trailer and the PR body. Same-machine lanes are serialized by the leader's local journal. A lane renews its own claim by editing the lease before it expires or by posting its next-epoch claim line; an expired lease of another session is taken over only through the leader's handoff line or the three-condition timeout takeover of decision D2 (Issue #1975 comment 6840449133), never by time alone.
2. Worktree. Work in an isolated worktree per Issue (`issue/<number>-<key>`), never in the shared checkout. New worktrees go to `~/.moai/worktrees/<project>-<id>` (the `worktree-plan` default, #2811); existing ones under `.moai-cli/worktrees/` stay where they are, and `~/.moai/worktrees/projects/` belongs to the Go generation and is never moved or deleted. Where a write guard rejects a path, stop and report; do not bypass.
3. Implement inside the Issue's file scope. HOLD items are reported blocked, never decided by a lane.
4. Verify. Run the checks that target the change and the Issue's acceptance commands; the unfiltered full check set is cited from the pull request's CI run. Record each command, its exit code and the measured numbers. Unrun checks are not_run.
5. Independent review. A session other than the author audits the head SHA against SPEC, diff and evidence and returns a verdict whose first line is `AUDIT #<n> (<key>) head <40hex> base <40hex> — verdict: PASS|FAIL` with no qualifiers; conditions make it FAIL.
6. Pull request to the integration branch with `Refs #<n>` (closing keywords only when the Issue is truly complete), exact base and candidate SHAs, the claim token, evidence and gaps.
7. Integration is agentic: a pull request merges when its current head has a successful `ci` run and a non-author PASS that cites that run, with no conflict and no file both sides changed; the latest-tip requirement is off (user decision U6 of 2026-11-12). The leader checks this and merges; lanes and bots never merge. A new push, including a tip merge for an overlapping file, needs its CI and a delta re-audit.
8. Exit the worktree after confirming nothing uncommitted is lost, then take the next Issue.

The leader loop reads PRs and Issue comments, fans out review of errors, assigns repairs to lanes, and records every dispatch and decision. Completion is read from evidence, never trusted from a message or an idle notice.

## Reporting

Record task, source or decision, changed paths, exact verification command and outcome, remaining work and blockers in the Issue's owned comment and the relevant document. On a blocker report the exact action and target, the reason, the denial/pending/uncertain state, completed work and independent next work. A blocked lane reports the kind, the owner and the next check, and moves to independent work (MODE-AGENT `report` step). Never tick a checkbox from a document or agent claim alone. Where a lane cannot post its own comment, the leader relays it verbatim, marked as a relay with the lane named.

## Language

Instruction files and code comments are English unless the project sets otherwise. User-facing text follows the user's conversation language in native idiom; identifiers, commands and paths stay verbatim. Korean Issue text keeps code identifiers in their original form.

## How this file evolves

1. Capture the lesson or decision first in its ledger: user decision in the decisions log and the affected Issue; agent correction in the project's memory store.
2. Edit the authored body in small diffs, keep the whole file under the Codex 32 KiB instruction budget, then regenerate the managed section: `moai agents-plan <root>` with the typed request on stdin, review the plan, then `moai agents-apply <root> --plan-digest <d> --permission-reference <ref>`. Exactly one marker pair must remain.
3. Verify markers, `git diff --check`, no secrets or personal absolute paths; record the regeneration (date, plan digest, reason) in the decisions log.
4. Lessons that should become product defaults are added to the MoAI templates through their own Issue, never copied blindly.
