한 줄 결론 — 그래프의 70%는 이미 갖춰져 있습니다. 부족한 건 edges.jsonl 하나로 저장하는 것과, 그 위를 걷는 도구 하나뿐이에요. 서버도 데이터베이스도 필요 없습니다.

왜 하나 — LLM은 정확성·일관성·설명가능성에 한계가 있습니다. 온톨로지와 지식그래프는 그걸 대체하는 게 아니라 보완해요. 역할이 갈립니다 — LLM은 추출·요약·자연어 인터페이스를 맡고, 온톨로지/KG는 논리·추론·정확성·근거를 맡습니다.

진화 방향: LLM + 온톨로지 + KG + GraphRAG.

1. 세 가지 개념 — 먼저 말부터

용어가 셋인데 자주 섞여 쓰입니다. 하는 일이 다르니 갈라서 봐야 해요.

용어무엇인가비유
온톨로지
(ontology)		 개념·관계·규칙을 기계가 이해할 수 있게 적어둔 스키마. TBox(클래스·속성) + ABox(인스턴스)로 나뉘고, RDF/OWL/SHACL로 표현합니다. "저장소가 아니라 의미 레이어"예요 도서관의 분류 규칙 — 책이 아니라 책을 어떻게 나눌지의 약속
지식그래프
(KG)		 온톨로지를 실제 데이터로 채운 것. 엔티티(노드) + 관계(엣지). Triple 기반이라 참·거짓 추론과 근거 추적이 됩니다 규칙대로 실제로 꽂아둔 책들과 그 사이의 상호참조
GraphRAG KG + 문서 + LLM을 결합한 검색. 벡터 유사도가 못 잇는 구조적 관계를 엣지로 연결해 환각을 억제하고 근거를 제시합니다 "비슷한 책"이 아니라 "이 책이 인용한 책"을 따라가는 검색

핵심 차이 하나만 기억하면 됩니다. 벡터 검색은 닮은 것을 찾고, 그래프는 이어진 것을 찾습니다. "이 함수를 고치면 어디가 깨지나"는 닮음으로는 답할 수 없어요 — 연결을 따라가야 합니다.

2. 기술 지형 4계층

도입한다고 하면 넷을 다 만들어야 할 것 같지만, 실제로는 2계층에서 가장 가벼운 선택지 하나만 고르면 시작됩니다.

계층선택지
① 구축 LLM 추출: GraphRAG / LightRAG · 코드: tree-sitter · SCIP · CodeQL
② 저장·쿼리 기본 = edges.jsonl (서버 0 · cgo 0 · git-diff 가능) → 순수 Go modernc.org/sqlite(recursive CTE) → 옵션 Kùzu/LadybugDB · Neo4j(서버형)
Kùzu는 2025-10 archived, 후속 LadybugDB는 C++ 코어라 Go 바인딩에 cgo가 붙습니다. 가벼운 순서로 갑니다
③ 검색 엔티티 중심 서브그래프 · 멀티홉 · HippoRAG PageRank · GraphRAG 커뮤니티
④ 에이전트 통합 그래프를 도구(Cypher) · 메모리 · 작업분해 DAG · 추적성/임팩트 그래프로 노출
★

edges.jsonl이 기본인 이유는 성능이 아니라 운영 비용입니다. 한 줄에 엣지 하나인 텍스트 파일이라 git이 diff를 낼 수 있고, 서버가 없으니 죽을 것도 없고, cgo가 없으니 크로스 컴파일이 깨지지 않아요.

그래프 DB는 한계에 부딪힌 뒤에 올라가면 됩니다.

5. 도입 방법 — 가장 가벼운 첫걸음

원칙은 다섯입니다 — 작게 시작 → 반복 → 하이브리드 → 스키마 제약 추출 → 지속 평가. 하이브리드란 사람이 스키마를, LLM이 인스턴스를 맡고 SHACL/owlrl로 검증하는 분업이에요.

Tier 0 — 권장 첫 단계 (서버 없음)

★

IP-2를 이렇게 시작합니다: codemaps의 출력(go list -deps · --format json)을 edges.jsonl로 저장하고, find_callers / blast_radius를 ~50줄짜리 순수 Go BFS 도구로 노출합니다.

서버 0 · DB 0 · cgo 0. 에이전트가 파일을 직접 읽으므로 토큰도 아낍니다.

6. 2026-08-17 추가 실측 — todo 쪽 현황
※

이 절만 원본(7/29)에 없던 내용입니다. 백로그를 실제로 세어본 결과예요.

원본은 SPEC과 코드 쪽을 다뤘는데, todo 백로그도 같은 문제를 갖고 있습니다 — 다만 방향이 반대예요. SPEC은 구조가 필드에 있고, todo는 구조가 산문에 있습니다.

그런데 todo.md는 [HARD]로 이렇게 적습니다 — "Not a task tracker. No priorities, no assignees, no due dates, no dependencies." 그리고 "An item is one line of intent."

규칙이 금지한 것을 운영이 79% 하고 있습니다. 이건 온톨로지를 도입할지의 문제가 아니라, 이미 쓰고 있는 어휘를 밖으로 꺼낼지의 문제예요.

산문이라서 지금 못 하는 것

  • "t85를 막는 게 뭐지?"를 물을 수 없습니다 — 34장을 사람이 다시 읽어야 해요
  • 순서를 매번 다시 도출합니다 — 편성할 때마다 의존을 읽어 재구성
  • 중복을 못 잡습니다 — t6·t7·t18이 "전제 반증" · "t20으로 흡수"로 DROPPED 됐는데 전부 수동 발견이었습니다

★

선행 조건 하나 — todo.md의 [HARD] 규칙을 먼저 고쳐야 합니다. 지금 필드를 추가하면 규칙 위반이 명문화됩니다.

7. 위험
위험내용
엔티티 해석 오류과잉 병합(다른 것을 같다고) · 과소 병합(같은 것을 다르다고)
스키마 진화 비용클래스·관계가 바뀌면 기존 인스턴스를 전부 손봐야 함
LLM 인덱싱 비용추출을 LLM에 맡기면 그 자체가 토큰 비용
거짓 엣지 전파틀린 관계 하나가 멀티홉 질의로 증폭됨
생성 Cypher 쓰기 권한 금지. LLM이 만든 질의는 읽기 전용 + 검증을 거칩니다
과잉 엔지니어링Tier 0으로 충분한데 Tier 2를 먼저 만드는 것
★

가장 조용한 위험은 "거짓 엣지 전파"입니다. 그래프가 낡으면 틀린 답을 자신 있게 내놓아요.

저장소에 이미 증거가 있습니다 — t6는 "전제 반증", t7은 "t3로 대체", t18은 "t20으로 흡수"로 관계가 실제로 바뀌었습니다. 자동 유지 수단이 없으면 그래프가 카드보다 먼저 썩습니다. 필드를 2개로 제한하는 게 그래서 중요해요 — 적을수록 틀릴 여지가 적습니다.
