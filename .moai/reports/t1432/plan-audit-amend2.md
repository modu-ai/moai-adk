### 2.6 Design analysis (hierarchy, interleavings), read against the actual tree code

Code read: `internal/harness/retention.go` at HEAD (`openStateFile` L198-L244, `healStateEntry` L249-L258, `removeStateEntryIfUnchanged` L264-L282, `pruneExclusive` L145-L158, `pruneLocked` L163-L181) plus the draft model `.moai/reports/t1432/amend-drafts/proto/heallock_proto.go` and its `healStateEntry` diff.

- **Lock hierarchy.** The heal lock is taken inside `healStateEntry`, held across `Lstat`+`os.Remove` only, and released (the model's `defer release()`, the plan's step 4) before `openStateFile` creates the replacement and before `lockfile.Lock(sf)` locks the state file (`pruneExclusive` L152). No path holds the heal lock while waiting on the state-file lock, and no path holds the state-file lock while requesting the heal lock (`pruneLocked` never reaches `openStateFile`). No cycle, no inversion, no deadlock. The state-file waiter keeps its pre-existing unbounded wait (F6, unchanged).
- **Interleavings checked against the removal rule** (remove only if the path still holds the inspected entry by identity, type, mode and mtime, `retention.go:L272`): (1) winner W removes E, releases, creates F exclusively; waiter B takes the lock afterwards and finds either an absent path (nothing to remove, then an `O_EXCL` creation race whose loser sees `ErrExist` and re-inspects) or F (identity differs, mode differs, no removal); (2) a third process C that inspected E earlier behaves like B; (3) an attacker re-plants a faulty E2 between W's removal and W's creation: W's `O_EXCL` fails, W re-inspects and heals E2 under the lock again (bounded by `maxStateInspections = 3`); (4) F is a 0644 regular file while E was a symlink or a 0400 file, so a reused inode number is still refused by the mode comparison. No interleaving removes a state file created by a lock-honouring healer.
- **New in 0.4.1 (REQ-HRH-016 treats a failed create, open or lock as "cannot be used"; the wrap clause; `LOCK_EX`).** Failing closed returns before any stamp is written, so the next hook event retries rather than waiting an interval (spec §B D4.c item 4); the error returned by `healStateEntry` passes through `openStateFile` and `pruneExclusive` unwrapped, so `errors.Is` holds at the caller (my E-048c/d runs show it). A held lock that never releases (a stalled holder) costs each hook event up to 2 s then a warning, which §F item 3 discloses; a lock file deleted from under a holder lets a second healer lock a new inode, disclosed as 3c. Neither breaks the guarantee for honouring processes.
- **Windows.** `healStateEntry` returns at the ownership check on Windows before any heal-lock call, so the twin is unreachable and no Windows heal window exists; this is a reading of the code (build and vet only, runtime not observed).
- **Hook budget.** Worst waited-then-pruned case about 2 s + 1.79 s = 3.8 s (arithmetic on the SPEC's two cited figures, both reported by the t1425 lane and not re-measured by me), under the 5 s kill, per acquisition; not measured under load.
- **Leader's load-measurement design (plan M10, DoD 15, B15).** Compliant with `.claude/rules/local/gitflow-lane-protocol.md` §8 and AGENTS.md §4: the load is CPU-busy goroutines inside the test process, bounded by a 120 s `context` deadline, stopped by `t.Cleanup`, the whole `go test` wrapped by `timeout 180` (`/opt/homebrew/bin/timeout` exists on this machine), the package slot lease held, no other process, no trailing `kill`. The 5 s comparison and the stated-unmeasured list are honest. Two details are left to the run phase (D5 below).
