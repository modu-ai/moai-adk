공식 문서는 이 상태의 결과를 명확히 적습니다 — 이름을 붙인 서브에이전트가 teammate로 뜨고, teammate는 출력 없이 idle 알림만 보냅니다. 그래서 "서브에이전트 결과를 기다리는 오케스트레이션 흐름이 멈출 수 있다"고 명시돼 있어요. MoAI의 칸반·팬아웃이 정확히 그 흐름입니다.

1. 치명 — 지금 잘못될 수 있는 것

치명 F-1. Agent Teams가 켜진 채 배포되고 있습니다

실측: .claude/settings.json:360과 internal/template/templates/.claude/settings.json.tmpl:386 둘 다 "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1". 템플릿에 있으므로 모든 배포 사용자가 켠 상태로 받습니다.

독트린과 정반대입니다. CLAUDE.md §15는 "Agent Teams RETIRED — Mode 3은 tombstone"이라 선언하고, orchestration-mode-selection.md는 Mode 3을 "결정 트리가 절대 선택하지 않음"이라 적습니다.

공식 문서가 경고하는 결과:

"while agent teams are enabled, a subagent that Claude names launches as a teammate, so teams can form even when you didn't ask for one"

"An orchestration flow that waits on subagent results can stall."

"Subagents: Claude receives the subagent's result when it completes. Teammates: the idle notification reports that the teammate stopped, without its output."

MoAI의 Agent 도구에는 name 파라미터가 있고, 칸반과 교차세션 메시징 규칙은 이름 기반 주소지정을 권장합니다. 즉 반장이 이름 붙은 워커를 스폰하면 teammate가 되어 결과를 못 받습니다.

게다가 이 값은 하위 스코프에서 되돌릴 수 없습니다 — 프로젝트·로컬 설정과 managed settings가 사용자 설정보다 나중에 적용되므로, 어느 한 곳의 "1"이 이깁니다.

조치: 값을 "0"으로 바꾸거나 키를 제거합니다. 문서상 세션 재시작이 필요 없습니다 — 설정 파일의 env는 저장 시 즉시 반영되고, 다음 스폰마다 다시 읽습니다. 팀 기능을 의도적으로 쓰려면 독트린 쪽을 고쳐야지 설정만 켜둔 채로는 안 됩니다.

2. 중대 — 선언이 런타임과 어긋남

중대 F-2. 백그라운드 서브에이전트에는 Task 도구가 없습니다

실측: MoAI 에이전트 11개 전부가 tools:에 TaskCreate, TaskUpdate, TaskList, TaskGet을 선언합니다.

그런데 공식 문서의 백그라운드 서브에이전트 도구 목록에 Task 계열이 없습니다. 유지되는 것은 Read · Grep · Glob · Bash · PowerShell · Edit · Write · NotebookEdit · WebFetch · WebSearch · TodoWrite · Skill · ToolSearch · EnterWorktree · ExitWorktree · Monitor · TaskStop · SendMessage · Artifact뿐이에요.

그리고 v2.1.198부터 서브에이전트는 기본이 백그라운드입니다(CLAUDE.md §14도 이를 적고 있음). 즉 선언한 Task 도구가 런타임에서 제거된 상태로 도는 게 기본입니다.

영향: manager-kanban의 TaskList 기반 조율, 각 에이전트의 진행 추적이 조용히 동작하지 않을 수 있습니다. 도구가 없으면 호출이 실패하지 오류가 나지 않아요.

조치: (a) Task 조율이 필요한 에이전트는 background: false를 명시하거나 (b) Task 도구 의존을 걷어내고 파일 기반 진행 기록으로 대체합니다. 어느 쪽이든 먼저 실측해야 합니다 — 실제로 제거되는지 확인 없이 고치면 헛수고입니다.

근거 · docs/en/sub-agents "Second filter (background subagents only)" · 실측 11/11 에이전트 선언

중대 F-3. 서브에이전트는 Workflow 도구를 못 씁니다

공식 문서의 첫 번째 필터(모든 서브에이전트에서 제거)에 Workflow가 포함됩니다. AskUserQuestion · ScheduleWakeup · EnterPlanMode · TaskOutput도 함께요.

결론: sweep(대량 팬아웃)은 메인 세션 전용입니다. 반장을 서브에이전트로 만들면 sweep을 못 씁니다. 반장은 반드시 세션이어야 해요.

부수 효과 하나는 이득입니다 — 서브에이전트에서 AskUserQuestion이 런타임 차원에서 제거되므로, MoAI의 "서브에이전트는 사용자에게 묻지 않는다" 규칙은 프롬프트 규율이 아니라 이미 기계적으로 강제되고 있습니다.

근거 · docs/en/sub-agents "First filter (removed from all subagents)"

중대 F-4. 서브에이전트는 출력 스타일을 받지 않습니다

공식 문서: "What doesn't transfer: Output style". auto memory와 컨텍스트 창 크기도 전달되지 않아요.

영향 두 갈래. 나쁜 쪽은 산출물 톤·형식이 메인 세션과 달라진다는 것이고, 좋은 쪽은 출력 스타일 32,342 B가 서브에이전트 프리픽스에서 빠진다는 겁니다.

제가 앞서 추정한 프리픽스 39K 토큰(룰 136,345 B + CLAUDE.md 19,040 B ÷ 4)은 출력 스타일을 이미 제외한 값이라 방향은 맞습니다. 다만 CLAUDE.md는 전 레벨이 전달된다고 문서가 명시하므로 그 부분은 확정입니다.

3. 제 이전 주장 중 정정할 것

감사는 자기 주장도 대상입니다. 이번에 문서를 다 읽고 보니 제가 앞서 드린 지적 셋이 근거를 잃었습니다. 그대로 적습니다.

정정 C-1. "N=8은 근거 없다"는 제 지적이 약합니다

저는 t85의 N=8을 두고 "문서 상한 3-5를 초과"라고 했습니다. 그 3-5의 출처를 확인해 보니 agent-teams 문서의 팀 크기 권고였어요 — "Start with 3-5 teammates for most workflows."

그런데 그건 teammate 얘기지 서브에이전트 팬아웃이 아닙니다. 실제 한도는 다릅니다:

대상한도
Agent Teams teammate3-5 권고 (하드 리밋 없음)
동시 서브에이전트20 (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS)
워크플로 동시 에이전트16 (CPU 적으면 감소), 런당 1,000

따라서 N=8은 런타임 한도(20) 안이고, 서브에이전트 팬아웃에 3-5를 적용할 직접 근거가 없습니다. 오라버니가 8을 유지한 판단이 문서상 더 지지받습니다.

다만 MoAI 규칙 orchestration-mode-selection.md가 3-5를 명시하고 5 초과를 anti-pattern으로 적어둔 것은 사실이므로, 규칙 쪽 근거를 다시 세우거나 상한을 올리거나 둘 중 하나를 해야 합니다. 지금은 규칙과 운영이 어긋난 상태예요.

근거 · docs/en/agent-teams "Choose an appropriate team size" · docs/en/sub-agents "Concurrent limit"

정정 C-2. 시차 스폰은 워크플로에서 이미 자동입니다

저는 "시차 스폰 규율을 지시문에 명문화하라"고 했는데, 워크플로 런타임이 이미 합니다.

"When a fan-out starts several matching agents at once, Claude Code holds all but the first until the first agent's response begins, then releases the held agents together so their first requests read the shared prefix." — CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS, 기본 5000ms

즉 sweep을 쓰면 프리픽스 재지불(F-2 지적)이 자동으로 해결됩니다. 같은 model·effort·agent type·tools·schema·cwd를 공유하는 형제 에이전트만 해당돼요.

단, 이건 워크플로 문서의 서술입니다. Agent 도구를 직접 여러 번 부르는 fanout에도 같은 hold가 걸리는지는 문서에 명시가 없어 미확인입니다. fanout에는 여전히 수동 규율이 필요할 수 있습니다.

근거 · docs/en/workflows "Prompt caching in a fan-out"

반증 C-3. 이미 쓰고 있는 것 둘을 "미사용"으로 적을 뻔했습니다

실측하니 제가 제안하려던 둘이 이미 채택돼 있었습니다:

  • .worktreeinclude — 저장소 루트에 1,055 B로 존재. gitignore된 파일을 워크트리로 자동 복사하는 기능을 이미 씁니다

실측 없이 "안 쓰고 있다"고 적었으면 없는 결함을 만들어낼 뻔했습니다.

4. 문서가 답을 준 미해결 카드 2건

해결 t41 — moai worktree done rc=128 lock의 원인

카드 t41은 "세션이 시작 시 스스로 건 lock이 원인"이라 적으면서 원인 미확인으로 남겨뒀습니다. 공식 문서에 그대로 있습니다:

"While an agent is running, Claude runs git worktree lock on its worktree so that concurrent cleanup cannot remove it. The lock is released when the agent finishes."

"The sweep also releases a lock Claude Code set for a session whose process has exited, so a killed background session doesn't leave its worktree permanently locked." — v2.1.210 이전에는 수동 git worktree unlock이 필요했음

즉 lock은 버그가 아니라 설계된 동작이고, 죽은 세션의 lock 자동 해제는 v2.1.210부터입니다. t41의 조치(“git stderr 그대로 전달 + lock 감지 시 안내”)는 여전히 유효하지만, 원인 조사 단계는 이 인용으로 끝납니다.

근거 · docs/en/worktrees "Clean up subagent and background-session worktrees"

정정 env -u 거부의 진짜 원인

kanban-dispatch.md는 env -u VAR cmd가 거부되는 이유를 "argv[0]이 env일 때 가드가 나머지 argv를 env 플래그로 스캔하는 인자 경계 오파싱"이라 설명합니다.

공식 문서를 보면 워크트리 격리의 네 번째 검사가 더 정확한 근거입니다:

"Command shape: Claude Code blocks a Bash or Monitor command it can't verify stays inside the worktree... It refuses shell constructs it can't statically trace, such as brace expansion and heredocs with unquoted delimiters. You can't turn this check off."

규칙이 채택한 우회(unset … && cmd 한 줄, 서브셸 금지, 스크립트 파일 금지)는 여전히 정답입니다 — 정적 추적이 가능한 형태라서요. 다만 설명을 이 근거로 교체해야 재발 시 진단이 빨라집니다.

근거 · docs/en/worktrees "How Claude Code enforces isolation"
5. 안 쓰고 있는 네이티브 기능 7가지

전부 이미 있는 기능이라 새로 만들 게 없습니다. 이득이 큰 순서예요.

기능무엇칸반에 어떻게
loop.md .claude/loop.md(프로젝트) 또는 ~/.claude/loop.md가 bare /loop의 기본 프롬프트를 대체합니다. 25,000 B 제한, 수정이 다음 반복부터 즉시 반영 반장의 "큐 폴링 → 픽 → 스폰 → 증거 수집" 루프를 여기에. /loop 한 번으로 반장이 돕니다
Monitor 도구 백그라운드 스크립트를 돌리며 출력 줄을 스트리밍. 문서가 "폴링을 아예 없애고 종종 더 토큰 효율적"이라 명시 큐 파일 변경 감시에 폴링 대신. 반장이 idle 대기 없이 즉시 반응
백그라운드 세션 "Backgrounding the session carries /loop tasks over to a background session, which keeps running without a terminal" 반장을 터미널 없이 운영. 오라버니가 창을 닫아도 돕니다
스킬 disallowed-tools 스킬 활성 동안 도구를 풀에서 제거. 문서가 든 예가 정확히 "자율 루프에서 AskUserQuestion 제거" 반장 루프 스킬에서 사용자 질문을 기계적으로 차단. 지금은 프롬프트 규율로만 막습니다
스킬 context: fork 스킬을 포크된 서브에이전트에서 실행. agent·background 필드와 함께. 포크는 두 도구 필터를 모두 건너뜁니다 무거운 스킬을 메인 컨텍스트 밖으로. 단 포크는 프롬프트 캐시를 공유하므로 비용 특성이 다릅니다
workflowSizeGuideline small(<5) / medium(<15, 기본) / large(<50) / unrestricted. 25 에이전트 초과 시 Large workflow 경고 sweep 규모를 카드 클래스에 맞춰 고정. 지금은 설정 없이 기본값에 맡기고 있습니다
Explore 오버라이드 내장 Explore/Plan은 CLAUDE.md와 git status를 건너뜁니다. 자체 정의로 덮어써 haiku 등 저가 모델로 돌릴 수 있음 조사 작업의 프리픽스가 이미 싼데, 모델까지 낮추면 가장 싼 팬아웃 단위가 됩니다
네이티브 /goal과 MoAI /moai goal — 금지는 타당하나 이유가 다릅니다

MoAI는 네이티브 /goal 사용을 금지하고 자체 stop-goal 평가자를 씁니다. 문서를 읽어 보니 금지 자체는 타당하지만 근거를 정확히 해야 합니다.

평가자small fast model(기본 Haiku). 도구를 호출하지 않음 — 대화에 드러난 것만 판단 shell 명령 실행 가능 — exit code로 기계 판정

핵심 차이는 "평가자가 도구를 못 쓴다"입니다. 네이티브는 대화에 드러난 것만 보므로 go test exit code 같은 기계 조건을 직접 확인할 수 없습니다. MoAI 평가자는 명령을 실행하므로 더 강해요.

다만 "human-only라서 금지"라는 서술이 있다면 정정해야 합니다 — 문서상 -p로도 arm할 수 있습니다. 금지 근거는 평가 능력의 차이여야 합니다.

그리고 유용한 사실 하나 — 네이티브는 서브에이전트나 백그라운드 셸이 실행 중이면 그 턴의 평가를 건너뜁니다. MoAI 평가자도 같은 처리를 하는지 확인할 가치가 있습니다.

6. 명령 표면 — 진입점을 -k 하나로

지적하신 대로 --chief를 따로 만들면 진입 경로가 둘이 됩니다. 세션 등록과 소켓 바인딩이 갈라지면 서로를 못 찾아요. -k가 유일한 문이어야 합니다. 

# 공장장 — 백엔드는 런처가 정하고, 역할은 -k 가 정한다
moai cc  -k N     # Claude 공장장
moai glm -k N     # GLM 공장장

# 진입 직후 공장장이 출력하는 안내 (SessionStart)
#   ① 기본 — 추가 세션 없음. 카드는 Agent 작업자가 처리
#   ② Claude 판정이 필요할 때
#      moai cc  -k --name judge
