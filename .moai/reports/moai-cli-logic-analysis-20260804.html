요약. moai init는 임베디드 템플릿을 새 프로젝트 트리에 배포하고 manifest·profile·config를 최초로 쓰는 스캐폴딩 명령이다. moai update는 두 축으로 나뉜다. 하나는 GitHub Releases에서 최신 바이너리를 받아 체크섬 검증 후 원자적 교체하는 바이너리 자기 갱신(internal/update/), 다른 하나는 새 버전 템플릿을 기존 프로젝트에 3-way 병합으로 동기화하는 템플릿 동기화(update_template_sync.go + update/ 서브패키지)이다. moai web은 루프백 전용 HTTP 서버로 profile·config 섹션을 편집하는 브라우저 기반 설정 에디터로, 외부 DB나 인증 없이 동작한다. 세 명령은 template.Deployer/Renderer, config.Loader/Manager, profile 스토어, manifest.Manager 네 하위 시스템을 각자의 목적에 맞게 읽거나 쓴다. init/update는 템플릿·manifest에 쓰기 접근하지만 web은 그렇지 않고, profile·config는 셋 모두가 공유한다.

2. moai init — 프로젝트 스캐폴딩

목적

Cobra 서브커맨드로 새 MoAI 프로젝트를 스캐폴딩한다. 프로젝트 루트를 결정하고, 인터랙티브 위자드(또는 플래그 전용 모드)를 돌린 뒤, 임베디드 템플릿을 배포한다. 기본은 core-only slim 모드이고 --all 플래그로 전체 배포할 수 있다. .moai/manifest.json을 쓰고, git hook을 설치하며, post-init 안내를 출력한다. PhaseExecutor(detect → methodology → validate → init)로 흐름을 조립한다.

보안 모델

루프백 전용 바인드

bind(server.go:167)가 127.0.0.1:<port>만 허용. 0.0.0.0 바인드는 금지(REQ-WC-002). bind가 유일한 주소 구성 지점이다.

2-layer 쓰기 안전

hostCheckMiddleware(app.go:164)가 POST/PUT/PATCH에 대해: (1) Host 헤더 loopback 검사(DNS-rebinding 차단, REQ-WC-009), (2) Sec-Fetch-Site: same-origin 강제(CSRF 차단, REQ-SEC-002). GET은 게이트 안 함. per-process CSRF 토큰 인프라는 의도적 미사용.

profile 이름 순회 가드

IsValidProfileName이 slash/backslash/선행점/절대경로 거부. GET/POST 양 경로에서 게이트 → ../../etc 순회 차단(REQ-SEC-001/REQ-WC11-034). default·active 프로필 삭제 거부는 웹 전용 경계 로직.

GLM key anti-leak

GLM key는 schema FieldDef 집합에서 의도적 배제(D-2). computeGLMKeyHint가 뷰모델 진입 전 trailing-4로 truncate. full key는 절대 뷰모델 진입 안 함(REQ-GKI-004). line-break in body → reject, surrounding whitespace → trim, empty → preserve.

atomic reject (EC-2). 7개 validator 중 하나라도 실패하면 영속상태 불변, 폼 per-field 에러와 함께 400 재렌더. empty=preserve (EC-1): 빈 제출값은 기존값 유지. 이 두 계약이 "부분 저장"을 원천 차단한다.

6. 핵심 설계 원칙

① thin CLI entry → internal/ 패키지가 로직 소유

web.go:71 runWeb은 session-worktree 진입 + findProjectRoot + ensurePortFree 후 web.Run에 블로킹 위임한다. 템플릿·manifest를 건드리지 않는다. init의 runInit도 PhaseExecutor에 실제 스캐폴딩을 위임한다. CLI 진입점은 얇고, 도메인 로직은 별도 패키지가 소유하는 구조가 세 명령에 일관되게 적용된다.

② 동일 검증 경로를 터미널 wizard와 web console이 공유

web의 handleSave는 terminal profile wizard와 동일한 profile.ReadPreferences/WritePreferences, SyncToProjectConfig, settings.*OptionValues() 스키마 SSOT를 재사용한다(AP-2). 핸드 미러 금지. profile 이름 검증(IsValidProfileName)도 양쪽에서 동일 술어를 쓴다. 이로써 두 진입점에서 영속화되는 데이터의 무결성이 보장된다.

③ namespace isolation doctrine (user-owned vs template-managed)

hns-*, harness-*, my-harness-* 접두의 파일과 .claude/agents/harness/, .moai/harness/ 등은 user-owned로 분류해 moai update가 절대 덮어쓰지 않는다(CLAUDE.local.md §24). 반면 moai* 접두의 template-managed 파일은 forceUpdate로 덮어쓴다. 백업은 보수적(모호하면 백업), 분류·검증은 엄격하게 동작해 안전망을 만든다.

④ slim 기본값 + --all opt-in

init은 기본적으로 core-tier만 배포하는 slim 모드로 동작한다(SPEC-V3R4-CATALOG-002). --all 플래그 또는 MOAI_DISTRIBUTE_ALL=1 환경변수로만 전체 배포(opt-in). 이는 새 프로젝트의 초기 풋프린트를 줄이고, 사용자가 필요한 optional pack만 나중에 추가할 수 있게 한다. SlimFS가 fs.FS 수준에서 non-core 엔트리를 숨겨 실수로 배포되는 일을 막는다.

⑤ 체크섬 강제 자기 갱신 (CWE-345 봉쇄)

바이너리 자동 업데이트는 체크섬 없는 다운로드를 세 지점에서 원천 차단한다: checksums.txt 부재, 다운로드 실패, Checksum 공백. buildVersionInfo는 @MX:ANCHOR + 회귀 테스트로 "절대 빈 Checksum을 생산하지 않는다"는 계약을 고정한다. 다운로드 후에도 스트리밍 SHA256을 재계산해 매직 바이트로 포맷을 검증하고, ELF/Mach-O/PE만 승인한다. 실패 시 자동 롤백.

⑥ 루프백 전용 no-auth web

moai web은 외부 인프라(DB, 인증 서버) 없이 동작한다. 127.0.0.1 전용 바인드 + Host 헤더 loopback 검사(DNS-rebinding 차단) + Sec-Fetch-Site: same-origin 강제(CSRF 차단) 2-layer로 보안을 유지한다. per-process CSRF 토큰은 의도적 미사용 — 루프백 + same-origin이면 충분하다는 설계 판단이다. atomic reject(EC-2)와 empty=preserve(EC-1)로 부분 저장을 원천 차단한다.
