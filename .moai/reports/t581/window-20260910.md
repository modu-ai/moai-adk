## Evidence — develop merge, three attempts

Command every time, from the develop worktree: `git merge --no-ff --no-edit WT-seam-bypass-mutant`.
Before every attempt: HEAD `6f7166cd7`, no MERGE_HEAD, branch tip `90658a408`. After every attempt:
HEAD `6f7166cd7`, no MERGE_HEAD, working tree identical to before.

| attempt | time | exit | output (verbatim, complete) |
|---|---|---|---|
| 1 | 16:44:34 | 128 | `error: could not write index` / `fatal: stash failed` |
| 2 | 16:46:42–43 | 128 | `error: could not write index` / `fatal: stash failed` |
| 3 | 16:47:47–48 | 128 | `error: could not write index` / `fatal: stash failed` |

**Another actor's uncommitted file in the develop worktree was not touched.** The worktree holds a
modified, uncommitted `internal/cli/mcp_build_identity_test.go` that is not this lane's. Because
the output mentions a stash, the lane stopped before retrying and checked:

- `merge.autostash`, `rebase.autostash`, `merge.autoStash`: all unset (each exit 1).
- `git stash list`: 19 entries, newest dated 2026-08-25 — none created that day, before or after
  any attempt.
- Across all six merge logs of the window, "stash" appears only in these failures; the successful
  t611 develop merge printed no stash activity.
- The file, re-checked after each attempt: `git hash-object` always
  `057aaf20f2d2a4179037aae89580c14597ea3510`; mtime always `09-10 13:38:12`, earlier than every merge
  attempt of the window. A stash round trip would have rewritten the file and moved its mtime, so
  neither these failures nor the earlier successful t611 merge touched it.

The mechanism of `stash failed` is unverified. The working hypothesis is that, with a dirty tracked
file present, the merge performs an extra index-writing state save, and that write lost to
concurrent index activity. Three identical failures make momentary contention alone a weaker
explanation.
