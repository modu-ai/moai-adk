실행 요약

⚠️ 핵심 진단 — "감사 단계가 생산성을 갉아먹는다"는 사실임

유지보보자의 호소는 구조적 사실로 확인됐다. 동일한 test·lint·coverage·build 차원이 sync 한 사이클에 최대 4회 반복 실행되고(Phase 7 병렬 검증 → sync-auditor Craft 차원 → sync-phase-quality-gate.sh Stop 훅 → manager-docs §E), 각 단계가 별도 콜드 캐시 서브에이전트 스폰으로 직렬 연결돼 있다. sync는 6-단계 직렬 콜드-스폰 체인 + 2개의 명명된 HUMAN GATE + 7개 인라인 AskUserQuestion 결정점 + 1개 블로킹 Stop 훅으로 구성된다.

분석 결과, 속도 병목은 "감사가 느리다"가 아니라 세 가지 구조적 결함에서 온다:

  1. 중복 검증(redundant verification) — 동일 차원을 2~4개의 독립 게이트가 각각 재실행. snapshot 공유 한 번으로 제거 가능.
  2. 직렬 콜드-스폰 체인 — 한 단계가 끝나야 다음 단계가 스폰되어 매번 시스템 프롬프트·룰·스킬을 재적재. 병렬화·바인딩 승격·사전 단축으로 완화.
  3. 흐름을 끊는 인라인 게이트 — Implementation Kickoff Approval(점수 무관 강제), sync 9개 결정점, ac_converge의 "테스트 어설션 실패 = 즉시 인간 에스컬레이션"이 자율 루프를 매 턴 끊음. HTML 대시보드 + 자율성 티어로 치환.
🎯 핵심 권장 방향 (6축, v3)
  1. 자율성 3모드 — 반자동(기본)·자동(auto)·완전자율(bypass+sandbox). 네이티브 프리미티브 번들로 정의하고 moai init/moai web에서 선택. → §3.1

  3. 계층 에이전트팀 — Agent 도구를 포함한 leader 역할 신설(유일 예외), worktree 격리 병렬 writer, milestone별 Context-Folding. → §3.3

✓ 연구가 뒷받침하는 불변 (변경 금지)
  • 코딩은 직렬 단일 에이전트 — Anthropic: "대부분의 코딩 작업은 병렬화에 부적합". run-phase(manager-develop) 동시성 상한을 올리지 않는다. 병렬은 READ(감사·연구·검증)에만. [R1,R4]

2.1 멀티에이전트 토큰 경제학 [R1,R4,R5]

멀티에이전트 연구 = 단일 채팅 대비 ~15× 토큰 (단일 에이전트 ≈ 4×). 토큰 사용량이 BrowseComp 성능 분산의 ~80% 설명.

Anthropic 자체 연구 시스템(LeadResearcher + 전문 subagents + CitationAgent)이 채팅 대비 ~15× 토큰 소비. 도구 호출 + 모델 선택이 나머지 20%. Opus-4-lead + Sonnet-4-sub가 내부 연구 eval에서 단일 Opus 4 대비 90.2% 우수. READ(연구·분석·감사·검증)에는 병렬이 가치 있고, WRITE(코드 생성·리팩터·순차 상태 의존 작업)에는 부적합 — "대부분의 코딩 작업은 진정 병렬화 가능한 서브태스크가 적다"(Phil Schmid 요약). 3-5 병렬 subagent, 각 3+ 도구 병렬 실행이 복잡 쿼리 시간을 ~90% 단축.

적용: MoAI 기존 설계 정당화 — run-phase(manager-develop 코딩)는 직렬 단일 에이전트 유지, Mode 4(3-5)는 plan 연구 fan-out·sync 읽기전용 감사·run 검증 배치에만. 위임 맵(delegation.yaml)이 지배적 비용 레버 — 라우팅 레저 → harness-learning으로 진화시킬 것(Meta Context Engineering과 정합, §2.5).

2.2 Claude Code 런타임 프리미티브 [R2]

권한 모드는 6개 — default(Manual v2.1.200+) · acceptEdits · plan · auto · dontAsk · bypassPermissions. 결정적 사실: deny 규칙 + 명시적 ask 규칙 + requiresUserInteraction은 bypassPermissions를 포함한 모든 모드에서 바인딩.
  • auto 모드 = "자동" 티어의 부재 중간: 백그라운드 분류기 모델(Sonnet 5 기본)이 per-tool 프롬프트 제거하되 파괴 행위는 블로킹. 결정 순서: allow/ask/deny 규칙 → 읽기전용+작업디렉토리 편집 자동승인 → 나머지 분류기. 3 연속 또는 20 총 블록 후 프롬프트로 폴백(임계값 비설정 가능). 단, defaultMode:'auto'는 user/managed 설정에서만 인정(project/local은 v2.1.142+ 무시) — 저장소가 스스로 auto 부여 불가.
  • native /goal = prompt Stop 훅 + Haiku 판사: 매 턴 후 소형 고속 모델이 조건 평가. "auto 모드는 단일 턴 내 툴 호출을 승인하지만 새 턴을 시작하지 않고, /goal은 턴마다 조건을 검사하는 별도 평가기" — 둘의 보완 관계가 무인 스택의 정석.
  • Stop 훅 8-연속-block 캡(CLAUDE_CODE_STOP_HOOK_BLOCK_CAP 기본 8)이 goal 상한보다 먼저 선점 → 목표 판정 없이 조용히 종료 가능. 모든 Stop 훅은 stop_hook_active 파싱 후 early exit 필수.
  • 3가지 훅 결정 메커니즘: command(결정적 셸) · prompt(1턴 Haiku 판정) · agent(다턴 subagent, 60s/50턴). 메커니즘 선택 자체가 자율성 티어 레버.
  • 동시성/세션 캡: CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS 기본 20(ultracode 면제) · CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION 기본 200 · workflow는 16 동시 / 1000 총 별도. MoAI Mode 4(3-5)는 20 런타임 캡 안에 안전.
  • 서브에이전트 permissionMode 비대칭: 부모 bypassPermissions/acceptEdits가 우선(자식이 더 안전 모드로 스코프 불가). 스폰 시점 mode 파라미터는 v2.1.213+ 무시. → 티어 안전성은 (a) deny/ask 규칙 + (b) tools: allowlist + 도구생략(Explore)에서 옴.
  • 설정 우선순위: Managed > CLI > Local > Project > User. 권한 규칙은 override가 아니라 merge. defaultMode는 단일 값(최고 스코프). 관리자 kill-switch: managed disableBypassPermissionsMode·disableAutoMode.

2.3 자율성 사다리 & HITL 게이트 [R4]

자율성은 랭킹이 아니라 스태핑 결정 — "높을수록 좋다"가 아니다. 대부분 팀의 실질 천장은 L2-L3이며, 도구 한계가 아니라 "'완료'를 얼마나 잘 정의했는가"가 결정.

Osmani L0-L5 사다리(Agency × Orchestration 2축) — L0 제안만 · L1 감독 행동(승인 피로가 실패 모드) · L2 범위 위임+증거검증 · L3 목표주도 자율(측정 가능 정지조건 필수 — "품질 개선"은 기각) · L4 격리 슬라이스 병렬 위임 · L5 예외관리 소프트웨어 공장. 모든 agent run이 8-필드 계약을 휴대해야 함: goal, scope, non-goals, tools/permissions, stopping condition, evidence, escalation path, budget. 3개 검증 질문이 핵심: "얼마나 빨리 틀렸는지 알 수 있는가? 얼마나 깔끔하게 되돌릴 수 있는가? 무엇이 옳음을 증명할 것인가?"

Galileo bounded autonomy: 전략 계획(인간 승인) vs 전술 실행(자율) 분리. 4 에스컬레이션 신호 — 신뢰도 임계치 · 컨텍스트/위험 클래스 · 행위 가역성(되돌릴 수 없는 것은 동기 승인, 가역적은 비동기 감사) · 멀티에이전트 체인 복잡도(체인 길이·신뢰도 감쇠·에이전트 간 불일치 모니터링).

3.6 moai 자체 MCP 서버 — thin CLI 코어 래퍼

오해 정정 먼저 — "대시보드를 위해 MCP 서버를 개발?" → 아니다

두 표면은 방향이 다르다: 웹 대시보드는 브라우저→moai(인간용), moai MCP 서버는 AI→moai(AI용). 대시보드는 moai web(이미 internal/web/에 board.go SPEC 보드 존재)에 WebSocket만 추가하면 끝 — MCP 서버 불필요. 웹 라이브 보드는 이번 scope에서 제외, v3.1 배포 타깃(별도 메모리 저장 완료). moai MCP 서버는 AI 통합용 별개 가치로 P2.

핵심 설계 — 같은 코어, 두 표면

MCP 서버를 CLI와 별개 코어로 새로 짜지 않는다. CLI의 Cobra 핸들러가 부르는 같은 internal/ 함수(internal/spec·internal/session·internal/goal·internal/verify)를 래핑하는 thin JSON-RPC 레이어. 이건 업계 정석 — Anthropic 자체(context7·playwright MCP), 그리고 Codex도 codex CLI와 codex mcp-server를 동시 제공한다.

왜 이게 마비를 끝내는가

마비 원인은 "브랜치 옮길 때마다 변경을 어찌할까" + "SPEC마다 세션 조각남"이었다. 단일 worktree 브랜치 + commit-as-you-go + progress.md SSOT + INFINITE-GOAL(auto-compact 무한)로 그 질문이 두 번 다시 나오지 않는다. diverged(16/10)도 worktree 격리로 1회 해결.

즉시 다음 단계 (승인 후 연속 진행)

  1. AUDIT-SNAPSHOT plan-audit verdict 대기 — plan-auditor 백그라운드. verdict(PASS/PASS-WITH-DEBT/FAIL + score) 오면 즉시 검토.
  2. Implementation Kickoff Approval — AUDIT-SNAPSHOT run 진입 전 사용자 게이트(이 보고서 + plan-audit verdict + OQ 해소 제시).
  3. AUDIT-SNAPSHOT run — 승인 시 manager-develop(cycle_type=tdd)이 A1→A2→A3→A4 순 구현(M1 해시+skip → M2 4dim 바인딩 → M3 snapshot wiring → M4 검증).
  4. AUDIT-SNAPSHOT sync — manager-docs(sync-phase-quality-gate·sync-auditor 소비, 같은 브랜치).
  5. STOPCHAIN-TRIM plan 병렬 착수 — AUDIT-SNAPSHOT과 독립, 같은 브랜치 commit-as-you-go.
  6. 이후 임계 경로 따라 INFINITE-GOAL → P1(AUTONOMY-TIERS·GOAL-HTML-FLOW·AUDIT-MULTI-MODEL) → P2 순.

제6장 — 리스크 · 공개 질문

리스크
  • verification-claim-integrity 훼손 위험: 검증 재실행을 snapshot 소비·diff-check로 치환 시 증거 귀속(§2)이 약화될 수 있음. → snapshot 키를 트리 상태(HEAD SHA)에 엄격히 바인딩, 재실행은 attributable diff-check로만 치환(자동 제거 無).
  • 완전자율 + bypassPermissions 보안: prompt-injection 보호 없음. → sandbox/컨테이너 증명 강제, deny/ask 규칙으로 비가역 행위 핀, 관리자 disableBypassPermissionsMode kill-switch. 웹 셀렉터는 sandbox 증명 없이 완전자율 비활성화.
  • Codex experimental 상태: codex mcp-server 변경 가능성, 도구명 커뮤니티 소싱. → 설치 시 툴 표면 프로브, fail-open 필수.
  • 계층 팀 컨텍스트 폭발: leader가 worker 반환을 축적. → Context-Folding + workflow script 변수 격리 + 1-2K 요약 반환 강제(R1·R5 sidechain).
  • 8-블록 캡 조용한 종료: 모드 인지 훅이 stop_hook_active 파싱 누락 시 goal 판정 없이 종료. → 모든 Stop 훅 early-exit 필수(AC로 검증).
  • 믿음 격차(METR): 자율화가 "빠르다"는 착각. → goal 평가기의 1차 신호를 기계 검증(exit code·테스트 출력)으로, agent 자가보고 불가.
