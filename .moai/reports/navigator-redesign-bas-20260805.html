1. 왜 다시 설계하는가 — 핵심 테제

이 보고서 전체를 한 문장으로: "시작은 아름답지만 끝이 고통스러운 이유는, 방향과 길을 잃은 LLM에게 제대로 된 지도를 주지 않아서다." BAS는 그 지도를 만들고, 코드가 바뀌어도 지도가 어긋나지 않게 붙잡는 시스템이다.

오라버니가 짚은 핵심 통찰 — "LLM은 토큰을 아끼려 필요한 줄만 읽는다 → 큰 그림을 놓친다 → 청사진이 필요하다" — 은 이 설계의 철학적 기둥이다. 주목할 점은 외부 레퍼런스가 이 통찰을 독립적으로 검증한다는 것이다. Augment Code의 SDD 가이드는 한 작업 사례를 요약하며 이렇게 쓴다:

"각 에이전트가 덜어낸 관련 없는 컨텍스트가 적을수록 결과가 더 좋았다. 백만 토큰의 코드베이스 컨텍스트는 보기와 달리 장점이 아니다. 에이전트는 정밀하고 작업에 관련된 컨텍스트에서 더 잘 동작한다."

즉 청사진(지도)의 가치는 토큰을 늘려서가 아니라, 토큰을 줄이면서도 큰 그림을 잃지 않기 때문에 생긴다. 이게 BAS 설계의 모든 결정을 관통한다 — 지도는 정밀해야 하고(더 큰 컨텍스트가 아니라 더 정확한 컨텍스트), 코드와 어긋나면 즉시 드러나야 한다(어긋난 지도는 지도가 아니다).

이 보고서가 답하는 세 물음. Q1 코딩 전에 세밀한 설계를 끝내는 법 · Q2 codewiki식 소스 분석으로 설계+기능정의를 동시에 만드는 법 · Q3 중간에 설계가 바뀌면 코드와 문서를 어떻게 같이 갱신하는가. 각 물음에 대한 직접 답은 §5에, 구현 로드맵은 §6에 있다.

2. 현 상태 진단 — 열려 있는 고리

Project Navigator(SPEC-001/002/003, 최근 3-phase close)는 이미 강력하다 — tree-sitter 14문법 심볼 추출, header-driven 결합, provenance 모델까지 갖췄다. 문제는 세 부분이 각자 단방향으로만 흐른다는 것. 어느 쪽이 바뀌어도 반대편이 모른다.

3. 제안 — BAS (Blueprint-Anchored Synchronization)

BAS는 세 부분으로 이루어진다: (A) SSOT 결합 토큰으로 design↔SPEC↔code를 하나의 그래프로 잇고, (B) 4-tier 지도로 LLM이 먼저 읽는 청사진을 세우며, (C) Falconer 3요소(detect·route·fix)로 어느 쪽이 바뀌어도 반대편이 따라잡게 한다. 핵심은 처음부터 다시 짜는 게 아니라 현 자산 위에 결합층을 얹는 것이다.

3.1 (A) SSOT 결합 토큰 — 주소 가능 그래프

현재 @MX:SPEC:<id> 토큰이 코드→SPEC 역포인터로 존재하나 Navigator 어느 chain도 소비하지 않는다(001 §B.3, 003 §B.6이 명시적으로 제외). BAS는 design 결정에도 ID를 부여해 그래프를 닫는다.

design decision  ──@NAV:DEC-042──▶  SPEC  ──@MX:SPEC:NAV-SYNC-001──▶  code symbol
     (ADR)                           (REQ/AC)                           (@NAV:SYM:Handler.Parse)

  ←───────────── 하나의 주소 가능 그래프로 join ─────────────→

이렇게 하면 어떤 design 결정이 어떤 코드 심볼로 실현되는지, 어떤 코드 변경이 어떤 설계 결정에 영향을 주는지를 기계적으로 추적할 수 있다. falconer의 "코드를 건 엔지니어에게 관련 doc 섹션을 알려주는 work routing"이 이 그래프 위에서 동작한다.

3.2 (B) 4-tier 지도 — LLM이 먼저 읽는 청사진

오라버니 통찰과 CodeWiki/Kiro 양식의 합류점. LLM이 "필요한 줄만 읽기 전에" 가장 먼저 보는 4개 층. 아래로 갈수록 세밀하고, 위에서부터 읽는다.

Tier 0Contract
빌드와 CI가 이미 강제하는 계약 — moai-adk가 가진 실제 표면. //go:embed all:templates + catalog.yaml(템플릿 구조가 바뀌면 컴파일이 실패) · SPEC frontmatter 스키마(moai spec audit가 위반을 잡음) · template-neutrality CI(내부 SPEC ID·REQ 토큰·commit SHA 누출을 CI가 차단) · mirror-parity 테스트(규칙 파일의 바이트 정합을 테스트가 강제). 어긋나면 기계가 붙잡는다 — 문서에 따로 적지 않아도 지켜진다. BAS는 이 표면들을 Navigator의 한 축으로 끌어올려 활용한다.
외부 레퍼런스가 보여주는 같은 원리 (도입 아님). Tauri tauri.conf.json capability allowlist · OpenAPI · Protobuf schema — 모두 "계약을 먼저 쓰면 빌드가 어긋남을 잡는다"는 contract-first 사례다. BAS는 이 원리를 moai-adk가 이미 가진 위 네 표면에 적용한다는 뜻이지, Tauri·OpenAPI·Protobuf를 moai-adk에 새로 도입하자는 게 아니다. 오라버니가 Orca vs Paseo(데스크탑 앱) 글에서 짚은 Tauri 맥락은 이 원리의 사례일 뿐 BAS의 대상이 아니다.
Tier 1Blueprint
LLM의 진입 지도. module_tree.json(구조적 색인) + overview.md(서술). CodeWiki의 산출물 양식이 증명된 형태. 핵심 전환: 코드 뒤에 "생성"하는 게 아니라 코드 앞에 "저술"한다(Q1의 답).
Tier 2Decision
불변 결정 기록(ADR). "편집하지 않고 대체한다" — 결정이 바뀌면 새 ADR를 써서 이전 것을 supersede. "어느 버전이 진실인가" 문제가 사라진다. log4brains의 다중 패키지 지원이 프론트/백/네이티브가 나뉜 데스크탑 앱에 자연스럽다.
Tier 3Symbol
심볼 그래프. 현재 astx(tree-sitter 14문법) → 향후 SCIP로 확장 경로. flat 목록에서 docstring·시그니처·find-refs까지(Q2의 답). 2-tier 원칙: 결정론적 구조층(astx/SCIP) + LLM 서술층.

왜 비중척 계약을 그대로 두는가. 세 SPEC이 분리 가능한 변경성(separable changeability)을 위해 의도적으로 비중척을 설계했다. 이를 깨면 기존 자산의 독립성이 사라진다. BAS는 그 위에 통합층을 올려 각 chain의 산출물을 소비하기만 한다 — 기존 계약을 위반하지 않고 그래프를 닫는다.

5. 오라버니의 세 물음에 대한 직접 답

Q1 · 코딩 전에 세밀한 설계를 어떻게 끝내는가

Tier 1 Blueprint를 "생성"이 아니라 "저술"한다. /moai project에 blueprint-first 모드를 추가: module_tree + contract + ADR을 코드 전에 먼저 쓴다.

검증된 양식이 이미 있다. Kiro의 Design 섹션 목록 — 컴포넌트 아키텍처 다이어그램 · 데이터 흐름 · 데이터 모델 · 에러 처리 · 테스트 전략 · 구현 접근 · 마이그레이션 전략. 오라버니가 데스크탑 앱(Tauri·Electron) 맥락에서 말씀하신 "코딩 전 설계 도면"이 바로 이 양식이다. BAS는 이 설계-도면 사고방식을 moai-adk의 Navigator에 적용한다 — Tauri·Electron이 BAS의 대상이 아니라, 그 도면을 먼저 그린다는 발상을 빌려온다.

Fowler의 spec-anchored 수준을 채택 — 코딩 전에 쓰고 코딩 후에도 유지한다. spec-first(코드 뒤 삭제, 변경 추적 불가)도, spec-as-source(MDD 함정, 빠져나오기 비싸)도 아닌 가역적 최적점. Fowler가 다른 두 수준을 비판하며 남긴 살아남는 유일한 길이다.

Q2 · codewiki식 분석으로 설계+기능정의를 동시에 만드는가

astx를 flat 목록에서 per-symbol docstring/시그니처/호출맥락으로 확장 + CodeWiki식 hierarchical decomposition.

2-tier 원칙이 핵심: 결정론적 구조층(astx → 향후 SCIP) 위에 LLM 서술층. 순수 LLM(DeepWiki)은 시스템 언어에서 측정가능하게 약하다(CodeWikiBench: C/C++ −3.15% vs DeepWiki). 구조층을 올리면 LLM의 약점을 구조층이 보완한다.

CodeWiki의 --update / --compare-to <commit> + metadata.json 증분 모델이 "갱신"의 검증된 기법 — Fix 요소가 이 패턴을 가져온다.

Q3 · 중간에 설계가 바뀌면 코드와 문서를 어떻게 같이 갱신하는가

Falconer 3요소(detect·route·fix) + SSOT 그래프. 계층별로 다른 동기화 전략을 쓴다:

  • Tier 0 Contract — 빌드가 강제. drift 자체가 불가능 (코드와 계약이 어긋나면 빌드 실패).
  • Tier 1·3 Blueprint/Symbol — detect→route→fix 루프. CodeWiki --compare-to로 변경된 하위 트리만 재생성.
  • Tier 2 ADR — "편집 대신 대체". 결정이 바뀌면 새 ADR를 써서 supersede. "어느 버전이 진실인가" 문제 자체가 발생하지 않는다.

단일 패턴이 세 물음을 다 풀지는 못한다. 레퍼런스의 합의는 포트폴리오다 — contract-first는 계약 가능한 표면(IPC·API·스키마)을, spec-anchored는 동작을, ADR은 결정을, living-doc detect는 서술을, CodeWiki식 재생성은 개요/지도를. 각자 다른 방식으로 실패하고, 함께 서로의 빈틈을 덮는다.

6. 구현 로드맵 — 마일스톤

BAS는 한 SPEC이 아니라 Epic 규모다. 각 마일스톤이 독립 SPEC으로 plan→run→sync를 밟는다. 순서의 핵심: Detect(M1)를 먼저 — 가장 가치가 크고, Fix(M3)는 Detect가 검증된 뒤에才有. 의존성 그래프를 따라 직렬·병렬이 섞인다.
M0

SSOT 토큰 + 그래프 결합층 스키마

새 SPEC · plan-phase · 모든后续 마일스톤의 전제

@NAV:DEC / @NAV:SYM 토큰 정의, @MX:SPEC 흡수, 결합 그래프 산출물 포맷. 임계 경로의 출발점 — 이것 없이는 어느 마일스톤도 그래프 위에서 동작할 수 없다.

M1

Detect — PostToolUse 변경 감지 훅

run-phase · M0에 의존 · 가치 최대

changed file path → affected doc rows 매핑. audit의 토큰 정규화 매칭을 훅으로 옮긴다. advisory를 넘어 실시간 영향 범위 표시. 이것만으로도 "어디가 바뀌었는지 모르는" 현 상태의 가장 큰 고통이 사라진다.

M2

Route — audit 권고 → 작업 항목 승격

run-phase · M1과 병렬 가능 · 002 확장

002 audit의 missing/orphan을 actionable work item으로. owner를 code path에 결합(falconer의 "담당자를 자원봉사자가 아니라 코드 경로에"). M1과 병렬 — 같은 audit 자산의 다른 표면.

M3

8. 리스크 그리드

spec-as-source 함정
SPEC을 코드의 원천으로 삼으면 MDD(모델 주도 개발)의 경직성과 LLM의 비결정성을 둘 다 물려받는다(Fowler 경고). 완화: spec-anchored 고정 — SPEC은 코드 후에도 살아있되 원천은 아니다.
heavy up-front spec 부담
설계 도면이 너무 무거우면 팀이 우회한다(Fowler: Verschlimmbesserung, "고치려다 더 망치는 것"). 완화: SPEC을 싸게 쓰고 싸게 진화시킨다 — 도면이 자전거 보조바대지 장갑차여야 한다.
brownfield 적합성
GitHub Spec Kit은 신규 기능에 최적화(#1191, 기존 SPEC 갱신 곤란). 이미 코드가 있는 데스크탑 앱은 brownfield. 완화: M5 역추출 경로를 명시적으로 둔다.
SCIP 인덱서 미성숙
SCIP는 정확하나 언어별 인덱서 성숙도가 다르다. 완화: astx + 빌드 그래프 먼저, SCIP는 인덱서가 성숙한 언어부터 점진 — 결정론적 기반을 먼저 확정한다.
단방향 습관
팀이 "한 번 생성하고 잊는" 현 패턴에 익숙하면 detect 신호를 무시한다. 완화: M1을 먼저, fix는 나중 — 가장 큰 가치(detect)를 먼저 체감시키고, fix는 그 습관이 붙은 뒤.
다이어그램≠문서
CodeWiki형 도구가 "한 번 생성 = 끝"으로 포지셔닝하지만 falconer가 반박 — 생성은 스냅샷일 뿐. 완화: BAS의 Fix 요소가 생성 위에 갱신 인프라를 강제 — 생성 자체는 충분조건이 아니다.
