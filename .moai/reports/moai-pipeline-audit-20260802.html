1. 이 검증이 무엇을 했나

팬아웃 (fan-out) — 일을 여러 조각으로 나눠 여러 일꾼에게 동시에 맡기는 방식입니다. 혼자 8칸을 순서대로 하면 8칸만큼 걸리지만, 4명이 2칸씩 나눠 하면 2칸만큼만 걸립니다. MoAI 파이프라인에도 이 장치가 준비돼 있는지, 그리고 실제로 돌아가고 있는지를 확인한 것이 이번 검증입니다.

3. 검증 결과 — 미검증 3건 전부 확정

V1. 팬아웃 10개는 거의 발동되지 않았다

세션 기록 761개를 뒤져 스크립트가 실제로 지정되어 실행된 적이 있는지를 셌습니다. “문서에 이름이 언급됐다”가 아니라 실행 인자로 넘어갔는지를 본 것이 핵심입니다.
항목실측
plan-research-fanout.js 실행 지정0회
sync-audit-4dim.js 실행 지정0회
Workflow 도구 자체 호출 (전부 일회성 ad-hoc 스크립트)102회
Phase 4 모드 선택 기록 SPEC166건
└ 순차(sub-agent) 선택66
└ 병렬(parallel/workflow) 선택7
실제로 돌린 판정 명령
grep -c 'scriptPath[^"]*"[^"]*plan-research-fanout' *.jsonl → 0
grep -c 'scriptPath[^"]*"[^"]*sync-audit-4dim'      *.jsonl → 0
grep -ho '"name":"Workflow"' *.jsonl | wc -l          → 102
Workflow 도구는 102번 쓰였지만, 실제 지정된 스크립트는 모델-effort 설계·템플릿 리뷰·스킬 감사 같은 일회성 작업이었습니다. 파이프라인에 붙어 있는 두 스크립트는 그중에 없었습니다.

V2. 증거 스냅샷 CLI는 만들어졌지만 한 번도 호출되지 않았다

스냅샷 (snapshot) — 테스트·린트 같은 검사 결과를 한 번 재두고, 코드가 그대로면 다음 단계에서 다시 재지 않고 그 값을 그대로 쓰는 장치입니다. MoAI에는 moai verify라는 이름으로 이미 Go 코드까지 구현돼 있습니다.
항목실측
스냅샷 저장 디렉터리 .moai/state/verify/snapshots/부재 → 기록 0회
“이 스냅샷을 써라”는 지시가 적힌 곳3곳 (run P15 · sync P1 · sync P7)
스냅샷 키 구성 (internal/verify/key.go:32)HEAD-SHA : sha256(작업트리 상태)
유효 시간(TTL) 기본값10분
추가로 발견한 구조적 결함
키에 HEAD-SHA(마지막 커밋 번호)가 들어 있습니다. 그래서 커밋을 한 번만 해도 키가 바뀌어 스냅샷이 무효가 됩니다. 
run Phase 15  → 스냅샷 기록
run Phase 19  → 커밋 (여기서 키가 바뀜)
sync Phase 1  → 스냅샷 조회 → 항상 불일치(miss)
즉 문서에 적힌 3개 소비 지점 중 run → sync 홉 2개는 구조적으로 절대 성립하지 않습니다. 성립 가능한 유일한 구간은 sync Phase 1 → sync Phase 7(사이에 커밋이 없음)입니다.

V3. plan 감사와 run 감사는 캐시를 공유하지 않는다

plan에서 문서 감사를 통과했는데 run에 들어가자마자 또 감사를 받는지를 확인했습니다. run 쪽에는 “24시간 안에 같은 문서면 감사 생략” 캐시가 있는데, 이 캐시를 누가 채우는지가 관건이었습니다.
항목실측
스트림 A — plan 단계 감사 리포트 (-review-N.md)124건
스트림 B — run 게이트 감사 리포트 (-YYYY-MM-DD.md)60건
캐시 키(plan_artifact_hash) 보유 — B스트림7 / 60
캐시 키 보유 — A스트림4 / 124
실제 캐시 적중 audit_cache_hit: true7건
캐시 불발 audit_cache_hit: false3건

plan-auditor의 리포트 출력 서식에 plan_artifact_hash 필드가 아예 없습니다. 그래서 plan에서 아무리 통과해도 run 쪽 캐시는 비어 있고, run 진입 시 감사를 다시 받습니다. 현재 캐시는 “같은 run을 다시 돌릴 때”만 작동합니다.

5. 최종 업데이트 계획

순서가 중요합니다. M1은 문서만 고치는 작업이라 위험이 0이고, 나머지 셋의 전제가 됩니다. M1의 첫 항목(인덱스)을 두 번째 항목(승격)보다 먼저 하는 것도 같은 이유입니다 — 보이게 만든 뒤에 켜야 합니다.

M1 — 활성화

문서만 · 위험 0 · 새 코드 0줄

  1. 팬아웃 인덱스 표를 plan.md/run.md/sync.md 라우터에 각 1개 추가 (D-2 해소 전제)
  2. 팬아웃 10곳 MAY → 조건 충족 시 실행으로 승격 (기존 fail-open 폴백 문장 유지)
  3. plan-auditor.md:392 재감사 범위 모순 정정 (D-1)
  4. Tier 크기 예산 추가 — S: REQ/AC ≤ 8 · M: ≤ 16 · L: ≤ 25

M2 — 스냅샷 실효화

문서 + CLI 판단 1건

  1. 키 정책 결정 — 커밋으로 무효화되는 현행 키를 유지할지, HEAD 동일 + 작업트리 clean 조건에서만 완화할지
  2. plan 팬아웃 렌즈 → verify record 훅 추가
  3. run Section C 사전점검 → verify check 훅 추가 (재측정 금지)
  4. run Phase 19 커밋 직후 재기록 훅 추가 (끊긴 sync 홉 복구)

M3 — 감사 구조 완성

스크립트 1개 신설

  1. plan-audit-4dim.js 신설 — sync-audit-4dim.js 복제 후 차원만 교체
  2. 필수통과 항목(MP-1~7)을 grep 배치로 선처리 — 에이전트 불필요
  3. 반증 단계를 공통 패턴으로 신설, blocking 등급에만 적용 (D-3)

M4 — 감사 스트림 통합

필드 추가만

  1. plan-auditor 출력 서식에 plan_artifact_hash 필드 추가
  2. plan Phase 11 통과 시 run 게이트 일자 리포트도 함께 기록 → run Phase 1 캐시 적중

8. 아직 확인하지 못한 것

① 인라인 MAY 8곳의 정확한 발동 횟수 — 기록 의무가 없어 키워드 흔적(shard 0 · drafter 2 · lens 8 · 4dim 2)이 약한 증거에 그칩니다. 정확한 집계는 트랜스크립트의 동시 스폰 패턴 분석이 필요합니다.
② 스냅샷 키 완화의 안전성 — “HEAD 동일 + clean tree” 조건이 충분한지는 코드 레벨 검토를 하지 않았습니다.
③ M2-1은 CLI 동작 변경을 수반하므로 별도 SPEC 대상입니다.

직접 확인해 보실 수 있는 것

  • 팬아웃이 켜졌는지 — ls .moai/state/verify/snapshots/가 “디렉터리 없음”이 아니게 되면 M2가 작동 중입니다.
  • 모순이 남았는지 — grep -n "Full audit" .claude/agents/moai/plan-auditor.md가 0건이면 D-1 해소.
  • 인덱스가 붙었는지 — grep -c "Fan-Out Index" .claude/skills/moai/workflows/*.md가 3이면 M1-1 완료.
