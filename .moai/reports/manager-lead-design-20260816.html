1. 왜 리드가 먼저 차는가

먼저 용어 하나. 컨텍스트 윈도우 (context window)는 AI가 한 번에 기억하고 있을 수 있는 대화의 총량입니다. 책상 넓이라고 생각하면 됩니다 — 서류를 계속 올려두면 언젠가 자리가 없어지고, 자리가 좁아질수록 일도 굼떠집니다. 공식 문서 표현으로는 “가장 중요하게 관리해야 할 자원”입니다.

리드 세션은 구조적으로 모든 것이 지나가는 유일한 통로입니다. 카드 한 장이 보드를 건너갈 때 리드가 손대는 지점을 세어 보면 이렇습니다.

과장하지 않기 위해 먼저 밝힐 것

위 12 / 9 / 2는 실제로 세어 본 숫자가 아닙니다. 규칙 문서에 적힌 “한 카드는 이런 순서로 움직인다”는 정의에서 산술로 뽑은 값입니다. 방향은 믿을 만하지만, 크기는 실측으로 다시 확인해야 합니다.

2. 이름 바꾸기 — 무엇을 손대야 하나

리네임 (rename)은 그냥 문자열 치환처럼 보이지만, 이 프로젝트에서는 아닙니다. 파일 이름 자체가 가드 테스트 (guard test) — 규칙이 깨졌는지 자동으로 검사하는 테스트 — 안에 문자열 그대로 박혀 있기 때문입니다. 순서를 틀리면 빌드가 빨간불이 됩니다.

3. manager-lead 는 무엇을 갖고 무엇을 못 갖는가

경계를 제가 정한 게 아닙니다. 이미 정해져 있습니다. 에이전트에게 허용된 도구 목록에 SendMessage(다른 세션에 말 걸기)가 없습니다. 그러니 이 에이전트는 구조적으로 다른 세션에 직접 지시를 보낼 수 없습니다. 판단하고 문안을 써서 넘길 뿐입니다.

4. 완료 보고 배경 흡수 — 실제로 얼마나 아끼나

솔직하게 먼저. “보고서를 배경에서 처리해 리드 책상에 안 올리기”는 절반만 가능합니다. 다른 세션이 보낸 메시지는 하위 에이전트 (subagent)가 직접 받을 수 없습니다. 반드시 리드 세션에 먼저 도착합니다. 그러니 메시지 자체의 비용은 0으로 못 만듭니다.

그럼 아낄 수 있는 건 뭘까요. 메시지가 “가서 읽어라”라고 가리킨 그 대상입니다. 두 항목은 성질이 완전히 다릅니다.

① 메시지 도착 못 줄임

상한이 고정돼 있습니다. “포인터만 보내라”는 규약을 지키면 카드당 몇 줄로 끝납니다. 이건 남는 비용입니다.

② 증거 읽기 전량 흡수

상한이 없습니다. 진행 기록 + 검증 로그 + 코드 변경분 + CI 상태 JSON. 카드가 클수록 무한정 커집니다. 여기가 진짜 절감처입니다.

왜 evidence 줄이 필수인가

verdict: PASS만 돌려받으면, 리드는 “통과했다더라”라는 말을 검증 없이 믿는 셈이 됩니다. 이 저장소 규칙(verification-claim-integrity.md)이 정확히 그걸 금지합니다 — “증거의 부재는 성공의 증거가 아니다.” 그래서 어느 파일이 무엇을 보여줬는지 한 줄이 반드시 따라붙습니다.

5. 리드 컨텍스트 방어 기제 7개

가성비 순 — “아끼는 양 ÷ 만드는 비용”이 큰 것부터입니다. 4개는 오늘 당장 가능하고, 3개는 만들어야 합니다.

순기제아끼는 것드는 비용 / 깨지는 것가용
1보드 상태를 디스크에서 읽기
기억하지 않는다		 기억할 상태가 0이 됨. /clear 후 복귀가 6블록 붙여넣기 → 명령 1줄 매 턴 파일 읽기(소량) / SPEC 상태가 틀리면 보드도 틀림오늘

지금: /clear 하면 리드는 어디까지 했는지 잊습니다 → 6블록짜리 복귀 메시지를 붙여넣어야 함.

제안: 리드가 아무것도 기억하지 않습니다. 대신 moai todo list로 대기 카드를 읽고, SPEC 파일 맨 위의 status:로 어느 컬럼인지 알아냅니다. 복귀 메시지는 필요 없습니다.

이미 절반은 이 설계입니다. 규칙 문서가 이미 “clear 뒤 컬럼 위치는 SPEC 상태에서 다시 유도한다”라고 적고 있습니다. 나머지 절반(붙여넣기)이 그와 모순될 뿐입니다. 필요한 도구 moai todo·moai handoff는 실행해서 존재를 확인했습니다.

6. 활용 시나리오 — 이 저장소의 실제 상황으로

S-1. 이번 리네임 작업 그 자체

파일 65개 · 도메인 4개(에이전트 / Go / 규칙·스킬 / docs-site) · 단계 6개. Tier L 기준 (마일스톤 3개 이상 그리고 파일 10개 이상 그리고 도메인 교차)을 세 조건 모두 충족합니다. manager-lead 가 S1은 단독·원자로, S3~S6은 병렬로 워커를 배치합니다. S1만은 절대 병렬화 금지.

S-2. docs-site 4개 언어 동기화

언어마다 워커 1개(en / ko / ja / zh). 단, _meta.yaml과 사이드바 main.yaml은 4개 언어가 공유하는 파일이라 워커에게 주지 않습니다 — 네 워커가 같은 파일을 동시에 쓰면 서로 덮어씁니다. manager-lead 가 마지막에 혼자 처리합니다.

S-3. sync 레인 완료 판정

sync 세션이 “SPEC-X 완료, 진행 기록 참조” 한 줄을 보냅니다. 리드는 경로만 뽑아 manager-lead 에 넘기고, manager-lead 가 진행 기록 + 검증 로그 + 코드리뷰 상태를 읽고 한 줄로 답합니다. 리뷰가 rate limited로 안 돌았다면 GAP — 카드는 그 자리에 머뭅니다.

S-4. 백로그 잔여 카드 분류

moai todo list 결과를 넘기면 A/B/C 등급과 라우팅 표가 돌아옵니다. 리드는 표만 받아 운영자에게 선택지로 제시합니다 — 묻는 일은 오케스트레이터 몫이니까요.

S-5. README.ko.md 누락 줄 채우기

S-2 과정에서 발견된 결함입니다. 파일 1개 · 줄 1개 · 회귀는 CI가 잡음 → A급. 파이프라인 3단계를 태울 이유가 없고, 워커 하나로 끝냅니다.
