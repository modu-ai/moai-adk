1. 왜 이걸 만드나

지금 moai web은 설정값을 고치는 화면 하나와 SPEC 목록 하나가 전부입니다. 그런데 실제로 개발하는 동안 궁금한 건 설정값이 아니라 “지금 무슨 일이 벌어지고 있나”입니다.

특히 MoAI-Kanban — 하나의 작업을 다섯 개 터미널 세션에 나눠 태우는 개발 방식 — 을 쓰기 시작하면서 이 필요가 뚜렷해졌습니다.

Opus 5 · high"]

GLM-5.2 · xhigh"]

토큰을 아끼는 원리

역할마다 필요한 판단의 깊이가 다릅니다. 그래서 역할별로 모델과 과금 방식을 다르게 겁니다.

#역할모델effort과금
0LeadOpus 5mediumClaude Max (정액)
1PlanOpus 5highClaude Max (정액)
2RunGLM-5.2xhighAPI 종량
3ReviewOpus 5mediumClaude Max (정액)
4SyncGLM-5.2highAPI 종량

설계와 판단이 걸린 자리(Plan·Review)는 Opus에 두고, 분량이 많고 기계적인 자리(Run·Sync)는 GLM으로 내립니다. 그리고 세션을 나누는 것 자체가 절약입니다. 한 세션이 계획부터 커밋까지 다 하면 대화가 계속 불어나 매 턴마다 그 전부를 다시 읽지만, 역할을 나누면 각 세션이 자기 단계에 필요한 만큼만 들고 갑니다.

콘솔이 답해야 할 질문 네 개.
  • 지금 카드가 어느 역할에 있나? 누가 일하고 누가 노나?
  • 각 세션이 어떤 모델로 돌고, 대화를 얼마나 썼나?
  • 어디서 막혔나 — 다음 역할 세션이 안 떠 있진 않나?
  • 이번 체인이 종량 과금을 얼마나 태웠나?

3. 좋은 소식 — “MCP 연동”은 거의 공짜입니다

MCP (Model Context Protocol) — Claude가 외부 도구를 부를 때 쓰는 규약. moai는 이걸로 17개 도구를 노출합니다.

처음엔 웹이 MCP 서버에 말을 걸어 데이터를 받아와야 한다고 생각하기 쉽습니다. 그런데 코드를 열어보니 MCP 도구 17개가 전부 내부 Go 패키지를 얇게 감싼 껍데기였습니다.

MCP 도구실제로 부르는 함수
session_listsession.QueryActiveWork
goal_statusgoal.LoadGoal
spec_progressspec.ListDocs
verify_snapshotverify.Load

moai web도 같은 바이너리 안의 Go 코드입니다. 그러니 웹이 자기 자신에게 MCP로 말을 걸 이유가 없습니다 — 같은 패키지를 읽으면 그게 곧 동기화입니다. 실제로 지금 SPEC 보드가 이미 그렇게 하고 있습니다(board.go:89).

따라서 남는 신규 작업은 하나뿐입니다. 동기화는 이미 돼 있고, “파일이 바뀐 걸 브라우저에 알리는 채널”만 만들면 됩니다. 이걸 SSE (Server-Sent Events — 서버가 브라우저로 소식을 밀어 보내는 단방향 통로)로 구현합니다. Go 표준 라이브러리만으로 되고 외부 의존성이 0이라, 오프라인 원칙을 깨지 않습니다.

4. 어떻게 나눠서 만드나 — 3단계

한 번에 완성되지 않습니다. 뒤에 나오는 데이터 공백 때문에 1단계는 지금 바로 되고, 2·3단계는 상태 기록 쪽을 먼저 고쳐야 합니다.

  • 1단계 · 선행조건 없음

    지금 데이터로 되는 것 전부

    개요 · SPEC 목록/상세 · 설정 이동 · 칸반 뷰 B(SPEC 파이프라인) · SSE 채널. 이 단계만으로도 콘솔은 충분히 쓸모가 있습니다.

  • 2단계 · Record.role 추가 후

    칸반 뷰 A 기본형

    기동 여부 · 역할 · 백엔드(정액/종량) · 마지막 활동 시각. 위 그림의 왼쪽 절반이 채워집니다.

  • 3단계 · 상태 층 개편 후

    칸반 뷰 A 완성형

    모델 · effort · 컨텍스트 사용률 · 비용. 위 그림이 전부 채워집니다.

5. 나쁜 소식 — 지금 기록되지 않는 것 세 가지

칸반 뷰 A를 만들려면 세션마다 역할·모델·사용량을 알아야 하는데, 셋 다 디스크에 남지 않습니다. 파일을 직접 열어 확인한 사실입니다.

1. 역할이 저장되지 않습니다
plan-tjq3pi 같은 라벨은 실행할 때 읽히지만 어떤 상태 파일에도 안 남습니다. kanban.Record에도 active-sessions.json에도 role 필드가 없습니다. → 어느 세션이 Plan인지 콘솔이 알 방법이 없습니다.
2. 컨텍스트 사용률은 단일 슬롯입니다
context-usage.json이 프로젝트당 파일 하나이고, 상태줄을 그리는 세션이 매번 통째로 덮어씁니다. 5개 세션 사용량을 여기서 읽는 건 구조적으로 불가능합니다.
3. 모델·effort가 저장되지 않습니다
상태줄이 보여주는 Opus 5 / medium은 런타임에서 실시간으로 읽는 값이라 디스크에 안 남습니다. Backend(claude/glm)만 유일하게 저장됩니다.
4. 단계 상태는 아직 어디에도 없습니다
완료/작업중/대기는 지금 리드 세션의 판단으로만 존재합니다. 하트비트로 추정해서 시작하고(추가 작업 0), 정확한 기록이 필요해지면 리드가 남기는 방식으로 올리기를 권합니다.
2번은 문서를 쓰는 중에 눈앞에서 관측했습니다. 처음 읽었을 때 session_id 368a2bd9… / 260000 토큰이었는데, 잠시 뒤 다시 보니 session_id e463a3c9… / 0 토큰으로 다른 세션이 통째로 덮어썼습니다. 추측이 아니라 실제로 벌어진 일입니다.

이 세 가지를 메우는 작업은 웹 UI가 아니라 상태 기록 쪽이므로, 웹 SPEC과 분리해서 별도로 진행하기를 권합니다. 한 SPEC에 소비자와 생산자가 섞이면 어느 쪽이 막혔는지 구분이 어려워집니다.

6. 지키기로 한 원칙

원칙이유
모니터링 화면은 읽기 전용
(카드 드래그 이동 없음)		 SPEC 상태 전이는 소유자가 정해져 있습니다 — draft→in-progress는 manager-develop, in-progress→implemented는 manager-docs. 웹에서 손으로 바꾸면 그 규율이 무너지고 감사 로그에 소유자 없는 전이가 남습니다.
네트워크 요청 0 지금 콘솔의 불변식입니다. SSE도 fsnotify도 전부 로컬이라 이 원칙을 깨지 않습니다.
확인된 사실과 추정을 구분 세션 목록에는 이미 죽은 프로세스가 남을 수 있고, 단계 상태도 추정으로 시작합니다. 구분하지 않으면 화면이 조용히 거짓말을 합니다.
빌드 스텝 추가 금지 Node·번들러 없이 손으로 쓴 CSS 한 장과 순수 JS로 유지합니다.

7. 성공 기준

  • 세션을 열고 개요 한 화면만 봐도 지금 상태가 파악된다.
  • 칸반 체인에서 미기동 역할이 있으면 즉시 눈에 띈다.
  • 파일이 바뀌면 새로고침 없이 화면이 따라온다.
  • 실시간이 끊기면 끊겼다고 말한다 (조용히 낡은 화면을 보여주지 않는다).
  • 설정 편집의 폼 계약(name 속성·저장 경로)이 하나도 바뀌지 않는다.

9. 지금 바로 시작할 수 있는 것

디자인 시안을 기다리지 않아도 되는 작업이 있습니다. 화면 없이 성립하는 것들입니다.

작업파일디자인 의존
SSE 실시간 채널internal/web/events.go (신규)없음
fsnotify 감시 + 디바운스같은 파일없음
Record.role 추가internal/kanban/record.go없음
진입 시 역할 기록internal/cli/cc.go · glm.go없음
뷰모델 조립 로직overview.go · kanban.go · monitor.go없음
라우트 골격internal/web/app.go없음
화면 템플릿*.templ있음 — 시안 대기

즉 데이터를 만들어 내보내는 층까지는 지금 다 짤 수 있고, 그걸 그리는 층만 시안을 기다리면 됩니다. 뷰모델이 먼저 확정되면 시안 작업도 실제 데이터 모양을 보고 할 수 있어 오히려 낫습니다.
