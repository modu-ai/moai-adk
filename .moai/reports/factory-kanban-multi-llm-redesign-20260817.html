판정: 아이디어 유효 · 제출 설계는 목표 역행

오라버니 아이디어는 실용성이 있습니다. 그것도 재료가 이미 거의 다 갖춰져 있어요 — audit_multi(3백엔드 교차검증), codex_task(OpenAI 위임), glm_audit(z.ai 직결), moai glm/cg가 전부 구현돼 있습니다.

그런데 제출된 GLM 설계는 그 목표와 반대 방향입니다. 핵심 제안인 "터미널 레인 → Agent() 워커 통합"은 모든 워커를 단일 Claude 계정 할당량에 집중시킵니다. Agent()는 부모 세션의 백엔드·크레덴셜을 그대로 씁니다. N=8 팬아웃은 5시간 창과 주간 캡을 8배 빠르게 태웁니다.

결정적 발견 하나로 문제가 풀립니다 — moai glm 세션에서 스폰한 Agent()는 z.ai 토큰을 씁니다. 즉 lead 팀 전체를 GLM 백엔드에 올리면 Agent 팬아웃의 처리량을 얻으면서 Claude 할당량은 한 톨도 쓰지 않습니다. 이게 재설계의 축입니다.

1. 목표 정렬 검사 — 무엇을 풀려고 했나

감사의 첫 단계는 성능이 아니라 목표 대조입니다. 설계가 아무리 정교해도 다른 문제를 풀고 있으면 소용이 없으니까요.

요약하면 — 제출 설계는 처리량 문제를 잘 풀었습니다. 다만 오라버니가 1순위로 요구한 비용·가용성 문제는 손대지 않았고, 핵심 제안이 그 문제를 악화시킵니다.

2. 감사 소견 — 결함 3건

치명 F-1. 백엔드 단일화 — 토큰 분산 수단을 스스로 제거

주장: "카드 실행 엔진은 이미 Agent()로 충분하다."

문제: 터미널 레인의 구조적 장점은 처리량이 아니라 레인마다 다른 백엔드·크레덴셜을 붙일 수 있다는 점입니다. Agent()는 부모 세션의 환경을 그대로 상속하므로 워커 N개가 전부 같은 계정에서 차감됩니다.

Claude 리밋은 롤링 5시간 창 + 고정 주간 캡이고, 모든 프롬프트·툴콜·파일읽기·thinking이 같은 할당량에서 빠집니다. Claude Code와 Claude 채팅이 같은 통을 씁니다. N=8 팬아웃은 그 통을 8배 속도로 비웁니다.

설계 §4가 "GLM 절감 워커는 하이브리드 변형으로"라고 적은 것은 1순위 목표가 부록으로 밀렸다는 자백입니다.

근거 · Agent 도구 model enum = sonnet|opus|haiku|fable (GLM·codex 없음) · Claude 공식 리밋 구조(5h 롤링 + 고정 주간, 채팅과 공유)

중대 F-2. 프리픽스 재지불 — N을 키울수록 단위 비용이 오른다

서브에이전트는 스폰할 때마다 항상 로딩되는 프리픽스를 처음부터 다시 읽습니다. 이 저장소 실측으로 룰 136,345 B + CLAUDE.md 19,040 B = 155,385 B, 토큰으로 약 39K (추정)입니다.

게다가 동시 스폰은 서로의 캐시를 읽을 수 없습니다 — 첫 워커가 캐시를 쓰는 중이라 나머지가 읽을 게 없어요. 그래서 N개 전부가 쓰기 요금(1.25×)을 냅니다. 이건 저장소 규칙 cache-aware-execution.md가 이미 명시한 사항이고, 같은 규칙이 시차 스폰(stagger)을 지시합니다.

방식프리픽스 비용 (추정)비고
N=8 동시 스폰8 × 39K ≈ 312K 토큰전부 콜드 쓰기
N=4 시차 스폰39K + 3×3.9K ≈ 51K 토큰1개만 쓰기, 3개는 캐시 읽기(0.1×)

제출 설계의 정량표에는 토큰 열이 아예 없습니다. 처리량만 세고 비용을 세지 않으면 "개선"이 어느 방향인지 알 수 없습니다.

근거 · 실측 wc -c always-loaded 룰 136,345 B · CLAUDE.md 19,040 B · cache-aware-execution.md 지시문 2 (stagger-spawn)

중대 F-3. 교차 검증 부재 — 이미 있는 기계를 안 씀

설계는 검수를 "S급 리드 직접 / M급+ review Agent()"로 나눴습니다. 그런데 review Agent는 같은 모델의 자기 검증이에요. 같은 학습·같은 편향이라 같은 곳을 놓칩니다. 게다가 Claude 토큰을 추가로 씁니다. — 두 번 나쁩니다.

정작 필요한 기계는 이미 구현돼 있습니다: audit_multi가 codex와 glm을 병렬로 돌리고 세션의 claude 판정과 융합합니다. 독립성도 구조적으로 강제돼 있어요 — codex/glm 고루틴은 claude 분석을 절대 받지 않습니다. 백엔드가 없으면 inconclusive로 fail-open 하고요.

즉 검증을 audit_multi로 돌리면 교차 검증과 토큰 분산을 한 번에 얻습니다. 설계는 이 도구를 언급조차 하지 않았습니다.

3. CT 계층 제안 평가

오라버니가 추가로 제안하신 CT(Control Tower) 계층 — 사용자와 대화하는 세션을 lead 위에 두고, 거기서 todo를 만들어 각 lead에게 내리는 구조 — 를 따로 감사했습니다. 결론부터: 방향은 옳고, 통신 방식만 고쳐야 합니다.

3.1 살릴 것

채택 사용자 창구 단일화는 실질 이득

lead가 여럿이면 오라버니가 여러 세션과 각각 대화해야 합니다. 제출 설계 §1이 지적한 "운영자 개입 3회"도 결국 그 문제예요. CT는 토큰이 아니라 사람의 주의력을 아낍니다 — 이건 별개의, 그리고 실제인 이득입니다.

덤으로 질문 채널이 하나로 모입니다. 저장소 규칙상 사용자 질문은 오케스트레이터만 할 수 있는데, lead가 여럿이면 그 창구가 여럿이 됩니다. CT는 이걸 정리해요.

채택 todo 생성·우선순위를 한 곳에서

큐가 SSOT인 건 제출 설계도 옳게 봤습니다. CT가 큐의 유일한 생산자가 되면 카드 클래스 판정(A/B/C)과 우선순위가 일관됩니다. lead들은 소비자로만 두면 경합이 사라집니다.

3.2 고칠 것

치명 C-1. 메시지를 위임 채널로 쓰면 안 됩니다

CT → lead 지시를 세션 간 메시지로 보낸다면, 공식 문서가 명시한 제약을 전부 받습니다:

  • 배달이 보장되지 않습니다 — 수신 세션 설정에 따라 hold/refuse될 수 있고, 기본값에서도 승인 대화상자가 뜨면 5분 뒤 폐기됩니다
  • 수신 측 할당량을 씁니다 — 배달된 메시지는 "오라버니가 타이핑한 프롬프트와 동일하게" 과금됩니다
  • 승인이 되지 않습니다 — CT가 lead의 권한 게이트를 대신 통과시킬 수 없습니다
  • 평문만, 세션당 대기 50개 상한, 반복 메시지 rate limit

해법: 큐(디스크)가 위임 채널이고, 메시지는 "큐 봤어?" 알림(nudge)일 뿐이라고 못박습니다. 이건 새 원칙이 아니라 저장소가 이미 채택한 규율이에요 — kanban-dispatch.md가 "완료는 읽어서 확인하지, 보고를 믿지 않는다"로 같은 말을 합니다. lead는 메시지가 안 와도 폴링으로 큐를 집습니다.

중대 C-2. "Control Tower"는 이름이 역할과 어긋납니다

오라버니 설명에서 모니터링은 lead가 합니다 — "lead가 지속적으로 레인 상태를 모니터링". 그런데 관제탑(Control Tower)의 은유는 바로 그 감시예요. CT가 실제로 하는 일은 접수 · 기획 · 배분입니다.

게다가 MoAI에는 이미 lead가 있어서 리더십이 2층이 되면 헷갈립니다.

추천 — Desk. 언론사의 "데스크"가 정확히 이 역할입니다: 기자들에게 일을 배분하고, 올라온 기사를 검수하고, 바깥과 소통하는 자리. 한국어에서 이미 통용되는 직책명이라 번역투가 아니고, 짧고, lead와 층위가 안 겹칩니다.

후보장점단점
Desk 추천역할과 정확히 일치, 한국어 통용, 짧음, 충돌 없음은유가 약간 밋밋
Dispatcher배분 의미가 직접적kanban-dispatch.md에서 lead가 dispatch를 수행 — 용어 충돌
Control Tower다중 레인 은유가 선명관제는 lead의 일 — 이름-역할 불일치, 리더십 2층 혼동
Conductor지휘 은유MoAI의 orchestrator와 의미 중복

경미 C-3. 칸반에 Desk를 두는 실익은 조건부입니다

칸반은 카드 1장이 4컬럼을 통과하는 구조라 lead 하나면 충분합니다. Desk를 얹어도 중간에 한 층이 늘 뿐이에요.

실익이 생기는 경우는 하나 — 칸반 런을 동시에 여러 개 돌릴 때. 그때는 Desk가 런 간 우선순위와 자원 배분을 맡아야 합니다.

다만 주의할 게 있어요. kanban-dispatch.md는 "백로그 진입은 운영자의 행위"를 [HARD]로 못박고 있습니다. Desk가 카드를 자동 승격하면 이 규칙을 어깁니다. Desk는 오라버니와 대화해 고르는 것까지만 하고, 선택 자체는 여전히 오라버니 몫으로 남겨야 합니다.

4. 결정적 발견 — GLM lead 팀
★

moai glm 세션에서 스폰한 Agent()는 z.ai 토큰을 씁니다.

근거: moai glm은 ANTHROPIC_BASE_URL·ANTHROPIC_AUTH_TOKEN을 프로세스 환경에 주입합니다. 서브에이전트는 같은 프로세스에서 같은 환경으로 API를 호출하므로 요청이 통째로 z.ai로 나갑니다.

모델 티어 이름도 안전합니다 — ANTHROPIC_DEFAULT_OPUS_MODEL / _SONNET_ / _HAIKU_ / _FABLE_ 네 개가 티어 이름을 GLM 모델 id로 매핑합니다.

이 하나로 제출 설계의 딜레마가 풀립니다. 설계는 "Agent 팬아웃(처리량)"과 "GLM 절감(비용)"이 배타적이라고 보고 후자를 포기했는데, 배타적이지 않습니다. GLM 세션 위에서 Agent를 팬아웃하면 둘 다 얻습니다.

7. 리스크

GLM 품질 미달로 재작업 높음

저가 백엔드가 카드를 망치면 재작업 비용이 절감분을 삼킵니다. 최악은 Claude로 다시 하는 것 — 그럼 두 번 냅니다.

완화 — 카드 클래스 라우팅을 엄격히. 설계 판단이 있는 C급은 GLM에 보내지 않는다. M1 실증에서 재작업률을 먼저 잰다.

fail-open의 조용한 통과 높음

audit_multi는 백엔드가 없으면 inconclusive로 열어줍니다. 크레덴셜이 만료돼도 실패 신호가 안 뜨고, 검증이 사실상 claude 단독으로 퇴화합니다.

완화 — inconclusive 비율을 계측하고 임계 초과 시 경고. "증거 없음은 통과가 아니다"는 저장소 규율 그대로.

Desk 계층의 정보 손실 중간

Desk → lead → Agent 3층이라 요약이 두 번 일어납니다. 전달될 때마다 맥락이 깎여요.

완화 — 카드는 포인터로만 전달(SPEC id · 경로 · 계약 절). 본문을 복사해 내리지 않는다. 이건 칸반 규칙이 이미 요구하는 형태.

크레덴셜 3벌 관리 중간

Claude · z.ai · OpenAI 각각 만료·한도·요금이 따로 돕니다. 하나 끊기면 그 레인만 조용히 멈춥니다.

완화 — moai doctor에 3풀 헬스체크 추가. codex_setup이 이미 codex 쪽 선례를 만들어 뒀다.

GLM도 리밋이 있다 중간

z.ai 역시 무한이 아닙니다. GLM에 전부 몰면 병목이 옮겨갈 뿐이에요.

완화 — codex를 예비 레인으로 상시 배선. M6 계측이 풀별 소진 속도를 보여주면 Desk가 옮긴다.

모델 id 불일치 낮음

GLM 세션에서 Claude 모델 id를 넘기면 z.ai가 서빙하지 못합니다. mcp_glm.go가 이미 이 경우를 인지하고 있어요.

완화 — GLM 세션에서는 모델 오버라이드 금지, 티어 이름(ANTHROPIC_DEFAULT_* 매핑)에만 의존.
