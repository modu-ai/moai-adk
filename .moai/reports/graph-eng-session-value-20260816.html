문서 1 — 그래프 엔지니어링

그래프 엔지니어링 (graph engineering)이란, AI 에이전트 하나가 혼자 도는 반복 작업으로는 감당이 안 될 때 여러 에이전트를 하나의 흐름도로 엮는 것을 말합니다. 저자의 표현으로는 "병렬 분기, 검증자, 핸드오프, 정지 조건을 갖춘 하나의 오케스트레이션".

저자가 솔직하게 짚는 점 하나 — 이건 새 개념이 아닙니다. Apache Airflow 같은 워크플로 엔진이 10년 넘게 해온 구조예요. 채팅창이 그 질문(어디를 병렬로? 상태는 어떻게 공유? 누가 거부권을?)을 미루기 쉽게 만들었을 뿐이라는 겁니다.

이 글에서 가장 값진 한 문장 — "organized nonsense"

같은 모델을 쓰는 에이전트 여러 개가 같은 결함 있는 컨텍스트를 읽으면, 서로 다른 답이 아니라 사이좋게 똑같이 틀린 답을 냅니다. 다수결로 검증하면 통과해버려요. 저자의 처방은 하나입니다 — "증거 일부는 에이전트 시스템 바깥에서 와야 한다. 실제로 돌아간 테스트. 실제로 입금된 돈."

이 프로젝트에 대입하면
Mode 4 fan-out으로 Opus 워커 4개를 동시에 띄웠다고 해봅시다. 넷 다 같은 210KB 룰 프리픽스를 읽고, 같은 모델이고, 같은 코드를 봅니다. 넷이 같은 결론을 냈다고 해서 그게 독립적인 4표가 아니에요. 사실상 1표를 4번 센 것에 가깝습니다. 반면 go test ./...의 exit code는 모델이 몇 개든 상관없이 바깥에서 오는 진짜 증거고요.

문서 2 — Claude Code 세션 가치 극대화

Anthropic이 꼽은 비용을 좌우하는 순서는 이렇습니다.

  1. 모델 — 큰 모델일수록 토큰당 비쌈
  2. 세션 길이 — 누적된 대화를 매 턴 다시 보냄
  3. effort — 생각(thinking) 토큰 양
  4. 명령 출력량 — 시끄러운 명령이 대화를 부풀림

2번에 붙은 설명이 특히 아픕니다 — "40번째 턴은 앞의 39턴을 다시 읽고 있다." 그래서 긴 세션 하나가 같은 일을 나눈 짧은 세션 여러 개보다 비싸고, 생각보다 훨씬 비싸다는 거예요.

3. 이미 갖춘 것 — 새로 만들 필요 없는 7가지

정직하게 말하면, 문서 1이 권하는 것은 moai-adk가 이미 대부분 하고 있습니다. 없는 걸 있다고 하지 않는 것만큼, 있는 걸 또 만드는 것도 낭비니까 먼저 확인했어요.

문서가 말하는 것이 프로젝트의 대응 표면

들여다볼 수 있는 상태칸반의 progress.md — 대화가 아니라 파일에 상태가 남음

재미있는 관찰
문서 1이 "이상적"이라고 말하는 형태 — 들여다볼 수 있는 상태, 명시적 핸드오프, 노드마다 정지 조건 — 는 사실 칸반 모드가 이미 구현한 것입니다. 카드가 backlog → plan → run → review → sync → done을 지나고, 상태는 대화가 아니라 progress.md에 남고, 리드는 그 파일을 읽고 전진하죠. 칸반은 채팅 기반 오케스트레이션이 아니라 이미 그래프예요.

4. 갭 — 실제로 적용할 7건

아래가 실제 작업 목록입니다. 우선순위는 비용 절감 크기 × 위험도로 매겼어요.

G1 · always-loaded 룰 다이어트 High
210KB가 모든 세션에 실리고 /clear마다 재지불됩니다. cache-aware-execution.md가 스스로 "룰 트리가 자랄수록 /clear가 비싸진다"고 인정하지만 수치 근거는 없었습니다 — 이번에 쟀습니다.
G2 · fan-out에 크로스모델 검증 없음 High
audit_multi는 감사관 전용입니다. Mode 4로 동시에 띄우는 워커 3~5개는 같은 모델·같은 룰 프리픽스라, organized nonsense 조건과 정확히 일치합니다.
G3 · @-mention / /context 규율 부재 Medium
전 룰 grep 0건. 둘 다 비용이 0에 가까운 습관인데 어디에도 안 적혀 있습니다.
G4 · 명령 출력 관리가 파편적 Medium
agent-common-protocol의 파일 리다이렉트(50줄/2KB)는 검증 배치 한정입니다. 일반 Bash 노이즈와 BASH_MAX_OUTPUT_LENGTH(30,000자) 규율이 없어요.
G5 · 상용 명령이 quiet 형태로 안 적혀 있음 Medium
make build, go test ./internal/<pkg>/... 같은 매일 쓰는 명령을 실제로 타이핑하는 형태 그대로 + 조용한 플래그 포함으로 기록하면 세션마다 한 턴과 수백 줄 출력을 아낍니다.
G6 · "세션 길이 = 비용" 축이 doctrine에 없음 Medium
현재 /clear 트리거는 스트림 스톨 위험으로만 정당화됩니다. 비용으로는 정당화되지 않아, 위험이 없으면 세션을 늘려도 된다고 읽힐 여지가 있어요.
G7 · 모델/effort 캐시 파괴 명시 Low · 문서화
agent-common-protocol의 "스폰마다 model 명시"와 cache-aware-execution의 "세션 모델 상속"이 겉보기에 충돌합니다. 실제로는 축이 달라요 — 전자는 서브에이전트(별도 컨텍스트), 후자는 메인 세션. 한 줄 주석으로 해소됩니다.

G1 자세히 — 가장 비싼 항목

kanban-dispatch.md는 21,003바이트인데 칸반 리드 세션에서만 쓰입니다. 파일 스스로 "세션은 SessionStart 컨텍스트에서 자기가 리드인 걸 알게 되므로 paths: 제한으로는 도달할 수 없다"고 정당화해요. 그 논거 자체는 맞습니다. 다만 그 논거가 다루지 않는 게 하나 있어요 — 리드가 아닌 세션이 21KB를 내는 비용입니다.

선택지방법평가
① 훅 조건부 주입SessionStart 훅이 MOAI_KANBAN 환경변수를 볼 때만 주입 (이 변수는 이미 존재)깔끔하나 훅 코드 변경 필요
② 스킬로 이전리드가 Skill()로 명시 로드리드가 로드를 잊으면 조용히 실패
③ 스텁 + 지연 동반 파일 권장바인딩 절만 스텁에 남기고 상세는 -detail.md로선례 있음 — goal-directive.md v2.1.0이 정확히 이 패턴

③은 이 프로젝트에서 이미 검증된 패턴이라 가장 안전합니다.

5. 칸반 / 팀모드에 루프를 적용하면?

질문 주신 부분입니다. 결론부터 — 리드에는 넣지 말고, 워커에 넣으세요. 그리고 시간 간격 루프가 아니라 조건 루프여야 합니다. 이유를 하나씩 볼게요.

먼저, "루프"는 두 개의 다른 물건입니다

네이티브 /loop <간격>/moai goal
언제 발동벽시계 간격 (5분마다 등)직전 턴이 끝날 때 Stop hook이 평가
컨텍스트설정한 세션의 전체 대화를 매번 재전송같은 세션 연속 턴 — 캐시가 따뜻함
1시간 지나면캐시 미스까지 추가해당 없음(연속이라)
어떻게 멈추나사용자가 취소조건 충족 / 상한 30턴 / 블록 상한 8 / 정체 감지
승인 게이트없음Implementation Kickoff Approval 유지
문서 2의 원문 경고
"/loop는 설정한 세션에서 하나의 온전한 턴으로 발동하며, 매번 그 대화 전체를 함께 끌고 간다. 마지막 턴으로부터 1시간이 지났다면 캐시 미스까지 얹힌다." → 그래서 Anthropic의 권고는 "루프는 새 세션에서 시작하라"입니다.

칸반 리드에 네이티브 /loop를 걸면 안 되는 이유 4가지

  1. /clear 요구와 정면충돌. kanban-dispatch.md는 페이즈가 끝날 때마다 리드가 운영자에게 /clear를 요청하도록 [HARD]로 규정합니다. 그런데 /clear는 사람이 직접 타이핑해야 하는 명령이고, 루프는 세션이 살아 있어야 발동해요. 둘은 같이 못 삽니다.
  2. 비용이 가장 나쁜 지점에 걸립니다. 리드의 컨텍스트 = 210KB 룰 + 누적 대화 전부. tick마다 이걸 전액 재전송합니다.
  3. 백로그 진입 [HARD] 위반. backlog는 소유 세션이 없고, 카드를 꺼내는 건 운영자의 결정이라고 규정돼 있습니다. 루프가 자동으로 카드를 승격하면 리드가 일을 스케줄링하는 게 아니라 생성하게 돼요 — 명시적으로 금지된 상태입니다.
  4. 판정 근거가 오히려 약해집니다. 리드는 companion이 남긴 progress.md와 증거를 읽고 카드를 전진시킵니다. 루프는 읽을 게 없어도 시간이 되면 발동하니, 의미 없는 tick이 쌓입니다.

그럼 어디에 넣나 — 올바른 배치

자리넣을 것왜
companion run 세션 /moai goal (ac_converge) 캐시가 따뜻하고, 승인 게이트가 유지되고, 조건이 충족되면 스스로 끝납니다. run.md § Run-phase Autonomy가 이미 이 배선이에요.
팀모드 in-session fan-out /moai goal 같은 세션 안에서 턴이 이어지므로 재전송 비용 자체가 발생하지 않습니다.
CI 감시 / 드리프트 탐지 네이티브 /loop — 전용 얇은 세션에서 cadence-bridge.md 레시피와 정합. 컨텍스트가 가벼워 재전송이 싸고, 읽기 전용이라 HARD 불변식을 지킵니다.
리드 → companion 완료 감지 루프 아님 — cross-session-messaging 이미 있는 기능입니다. 폴링보다 알림이 정확하고 쌉니다.
주의 — goal을 배선할 때 걸리는 함정 하나

goal의 턴 상한은 기본 30인데, 런타임의 연속 블록 상한은 기본 8입니다. 무인 실행에서는 8이 먼저 걸려서 판정문(verdict) 없이 종료돼요. goal.md §22가 이미 경고하고 있으니, 배선할 때 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP을 올리거나 ceiling을 8 이하로 낮춰야 합니다. "판정문이 없다"를 "수렴했다"로 읽으면 안 됩니다.

6. 리스크

룰 다이어트가 규율 도달성을 깬다
잘라낸 규율이 필요한 순간에 로드되지 않으면 실패가 조용합니다 — 규율이 없는 줄도 모른 채 진행돼요. 스텁+지연 분할로 바인딩 절은 인라인 유지, 그리고 held-in/held-out 검증 필수.
크로스모델 검증이 fan-out 이득을 상쇄
모든 워커에 붙이면 병렬화 이득이 사라집니다. 결론이 갈리는 지점에만 적용해야 해요.
66K 토큰은 추정치
바이트/4 환산입니다. 우선순위를 잘못 매길 수 있으니 /context 실측으로 대체해야 합니다.
goal 블록 상한 < 턴 상한
goal.md가 이미 경고 중. 배선 시 상한 조정으로 해소.

8. 검증하지 않은 것 (Gaps)

이 프로젝트 규칙상, 관측하지 않은 것을 관측한 척하면 안 됩니다. 그래서 이번에 재지 않은 것을 그대로 적습니다.

  • 66K 토큰은 추정치입니다. 바이트÷4 환산이고 /context 실측이 아닙니다. 도구 스키마·스킬 목록·시스템 프롬프트·메모리가 빠져 있으므로 실제 baseline은 이보다 큽니다.
  • 문서 2의 정량 수치는 원문 인용입니다. 캐시 배수·유효시간·30,000자 임계를 이번 세션에서 재현 측정하지 않았습니다.
  • audit_model 기본값 미확인. 설정 파일에 키가 없다는 것만 확인했고(grep 0건), Go 기본값 코드는 열어보지 않았습니다.
  • G2의 "fan-out에 크로스모델 검증 없음"은 배선 부재 관측(감사관 tools 목록에만 audit_multi 존재)에 근거합니다. Mode 4 실행 로그로 재확인이 필요합니다.
  • stop-goal 훅을 실행해보지 않았습니다. 파일 존재(internal/cli/hook_stop_goal.go, handle-stop-goal.sh)만 확인했습니다.
  • 이 보고서는 제안이며, 어떤 룰 파일도 수정하지 않았습니다.

9. 남는 위험

  • 룰 다이어트는 always-loaded 규율의 도달성을 바꿉니다. 조용한 실패가 가장 비싼 실패 형태라, 잘라내기 전에 held-in(원래 문제가 해결되는지) / held-out(기존 가드가 여전히 통과하는지) 양쪽 검증이 필요합니다.
  • 문서 2는 구독/API 과금 모델을 전제합니다. 이 프로젝트의 실제 과금 조건에서는 배수가 다를 수 있습니다.
