도출된 4가지 결론

  1. sonnet-5 max는 Claude 계열 최악의 가성비. opus-4.8 max보다 비싸고($26.40 vs $13.22) 점수는 낮다(54% vs 59%). 원인: 268 스텝·214k 토큰 — 최고 effort에서 과도한 재시도 루프. → "높은 effort ≠ 높은 가치". 실행 에이전트에 sonnet을 쓸 때 xhigh/max로 올리는 것은 비용·속도·가용성 모두에서 손해일 개연성이 크다.
  2. API 가성비 1위는 Opus 4.8 ($22.4/해결과제). 품질 1위는 Fable 5 (70%, +11%p). Fable의 프리미엄은 해결과제당 +$8.5.
  3. 가용성(토큰 소모) 관점에서도 fable(170k) < opus(229k) < sonnet-5(396k). 구독 주간 한도는 토큰 기반이므로, "싼 모델로 돌리면 쿼터가 절약된다"는 통념은 성립하지 않는다 — 약한 모델은 스텝을 3배 돌며 오히려 쿼터를 더 태운다. 단, 구독 쿼터 차감에 모델별 가중치(Opus 가중)가 있다는 점은 감안 필요.
  4. 스텝 수 = 속도. fable 88 < opus 120 < sonnet-5 268. 벽시계 시간에서도 상위 모델이 유리.
한계 고지 (검증 불가 영역): 리더보드에는 Claude 모델의 effort 변형(low/medium/high/xhigh) 데이터가 없다(전부 max). 따라서 "sonnet xhigh vs high 품질 차이", "fable low의 가성비"는 직접 실증 불가. 본 설계의 effort 하향은 (a) sonnet-5 max의 루프 낭비 실측, (b) Opus 4.8 기본 effort가 high라는 Anthropic 공식 포지셔닝, (c) effort는 출력토큰에 준선형이라는 일반 특성에서 추정한 것이다. 도입 후 `.moai/state/verify/` 실측으로 보정을 권장.

2. 재설계 원칙

  1. 추론 집중 배치: 설계·계획·감사·자문(spec, plan-auditor, sync-auditor, design, advisor)에 최상위 모델 + high 이상. 이 단계 품질이 하류 재작업(=토큰 낭비)을 결정.
  2. 실행은 high 상한: 구현·수행(develop, harness)은 sonnet high(xhigh 아님). 좋은 plan이 주어지면 실행 난도는 낮아지고, max-effort 루프 낭비를 차단.
  3. 기계 작업은 최저가: docs/git은 sonnet low — 추론 불필요.
  4. 가용성 = 토큰/해결과제 최소화: 재시도 루프를 만드는 조합(약한 모델 + 높은 effort)을 배제.

3. Plan A — API 종량제 (3-tier) rev2

rev2 수정: 단가는 sonnet($3/$15)이 opus($5/$25)의 절반이지만 과제당 비용은 opus $13.22 < sonnet $26.40으로 역전(sonnet이 토큰 1.6배·스텝 2.2배 소모). 따라서 API에서는 실행도 opus — sonnet은 기계 작업에만 배치. 추론=Fable(품질 1위), 실행=opus(과제당 비용 1위), 기계=sonnet low.

· A-max: 추론 전체 fable — 리더보드 품질 1위(70%)·토큰 효율 1위(170k/해결). develop까지 fable high(과제당 토큰이 sonnet의 43%라 체감 비용 격차는 명목가보다 작음). xhigh는 advisor 단 1곳(교착 해소 전용).
· A-medium(권장): 계획·설계는 fable, 감사·실행은 opus — $/해결과제 1위($22.4) 모델을 소비량이 큰 실행에 배치. rev2에서 실행을 sonnet high→opus high로 전환(과제당 비용 역전 실측 반영).
· A-low: fable 프리미엄 제거, 추론·실행 전부 opus(가성비 1위), effort로만 차등.
· rev2 한계 고지: opus medium vs sonnet high 품질 동등성은 미실증(effort 변형 데이터 부재) — 과제당 토큰 효율 격차(135k vs 214k)가 effort 하향에서도 유지된다는 구조적 가정.
· Plan B는 rev2 비적용: 구독은 쿼터 구조가 제약 — Opus 시간은 가중 차감되는 희소 자원(Max 5x: Sonnet 140–280h vs Opus 15–35h)이라 실행은 Sonnet 시간으로 돌리는 opusplan 구조 유지.

4. Plan B — 구독 요금제 (3-tier, 가용성 최우선)

구독의 제약은 달러가 아니라 주간 토큰 쿼터(전 모델 공유) + Opus 가중 차감. 목표는 "쿼터당 해결 과제 수" 극대화 = 재시도 루프 배제 + Opus는 추론에만.

티어별 논거
· B-max(권장): Anthropic 공식 opusplan 패턴("계획은 Opus, 실행은 Sonnet")의 정밀 버전. 추론 6개는 opus high(Opus 4.8 공식 기본 effort), 실행은 sonnet high — 종전 설계의 sonnet xhigh를 high로 하향(sonnet-5 max 루프 낭비 실측 반영: 품질 이득 불확실 vs 토큰·시간 손해 확실). Opus 주간 한도(Max 20x 기준 24–40h)는 추론 단계만으로는 충분.

· B-low(Pro): 검증 결과 Pro도 Opus 4.8 사용 가능하나 주간 한도가 작음. opusplan 골격만 보존 — 진입점 2곳(spec의 계획 수립, advisor의 교착 해소)만 opus medium, 나머지 추론은 sonnet high. 전면 sonnet이 아니라 "Opus를 가장 레버리지 높은 지점에만" 배치.

6. 구현 매핑 (spawn-time 라우팅 파생 규칙)

workflow.yaml model_routing_profiles 36-cell은 위 표에서 기계적으로 파생한다:

  • phase→대표 에이전트 매핑: plan→manager-spec, run→manager-develop, sync→manager-docs, mx→manager-git
  • SPEC Tier(S/M/L)는 effort ±1단만 조정 (예: B-max의 L-plan = opus high, S-plan = opus medium; run은 전 Tier sonnet high, S-run만 medium)
  • 선행 조건: validRoutingModels(internal/config/model_routing.go)에 "fable" 추가, agentModelMap/agentEffortMap(internal/template/model_policy.go)을 plan_type×tier 단일 프로파일 구조로 통합
