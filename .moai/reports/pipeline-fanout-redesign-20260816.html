1. 무엇이 문제인가

먼저 용어 하나. 컬럼 (column) 은 칸반 보드에서 카드가 지나가는 칸이고, 칸마다 그 일을 맡는 세션이 하나씩 붙어 있습니다. 지금은 plan → run → review → sync 네 칸입니다.

1.1 review 칸은 sync 와 하는 일이 겹칩니다

확인해 보니 /moai review 와 sync 단계의 품질 게이트가 같은 심판(에이전트)을 씁니다.

확인한 곳내용
review.md:23agents: ["sync-auditor"] — review 가 sync 게이트의 심판을 직접 호출
sync.md:6agents: ["manager-docs", "manager-git"] — sync-auditor 가 여기엔 없음
CLAUDE.md §5sync (manager-docs) → sync-audit (sync-auditor) — 중복은 단계 사슬에서 성립
sync.md:81순조로운 경로에선 4차원 판정이 확정이고 sync-auditor 는 예비 심판
kanban-dispatch.md:28review 칸은 보드에만 따로 추가돼 있음
정밀화 — 초판이 뭉뚱그린 곳 초판은 “둘이 같은 심판을 쓴다”고만 적었는데, 그것만 보고 sync.md 를 열면 sync-auditor 가 안 보여서 막힙니다. 정확히는 — review 트리거가 sync 게이트의 심판을 그대로 호출하고, sync 쪽에서는 그 심판에 단계 사슬을 통해 도달합니다(순조롭지 않은 경로의 예비 심판). 결론은 그대로지만, 이렇게 안 적으면 다음 사람이 헛짚습니다.

코드가 아직 4역할(internal/kanban/bootstrap.go:25)인 것은 아직 안 고친 것이지 반증이 아닙니다.
주의할 점 다만 /moai review 에는 렌즈가 있습니다 — --security(보안만 집중), --deep(다단계 정밀), --lean(과잉설계 점검) 등. sync 게이트에는 이 선택지가 없습니다. 그래서 칸을 없앨 때 렌즈는 sync 디스패치의 인자로 옮겨야 기능이 안 빕니다.

1.2 lead 가 병목입니다

카드 한 장이 칸을 하나 지날 때마다 lead 는 세 가지를 합니다 — 지시 보내기, 완료 증거 읽기, /clear 요청하기.

형태지시증거 읽기/clear합계
현행 4칸44412
3칸3339
팬아웃 (카드 1장)1102

게다가 진행 중인 카드는 칸마다 1장으로 묶여 있어서, 처리 속도가 가장 느린 칸에 발이 묶입니다.

1.3 lead 의 컨텍스트가 제일 먼저 찹니다

컨텍스트 윈도우 (context window) 는 Claude 가 한 대화에서 기억할 수 있는 총량입니다. 책상 넓이라고 보시면 됩니다 — 서류를 계속 올리면 언젠가 자리가 없고, 꽉 차기 전부터 이미 손이 굼떠집니다.

“Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills.” — 공식 best-practices 문서

그리고 세션끼리 주고받는 메시지는 공짜가 아닙니다. 공식 문서는 도착한 메시지가 “사용자가 직접 친 프롬프트처럼 사용량에 잡힌다”고 적습니다. 모든 지시와 모든 보고가 lead 를 거치니, lead 의 책상이 제일 먼저 찹니다.

1.4 /clear 할 때마다 이름을 다시 붙이는 이유

이건 원인이 예상과 달랐습니다. 공식 문서는 이렇게 적습니다:

“/clear: start fresh with an empty context. You keep a name you set with --name or /rename in the new conversation, but not an AI-generated session title”

그리고 저장소를 확인하니 MoAI 는 그 이름을 실제로 넘기고 있었습니다 — internal/cli/kanban.go:360 의 leadNameArgs 가 --name lead-<run-id> 를 claude 인자로 붙입니다.

즉 /clear 는 이름을 지우지 않습니다. 다시 붙여야 했던 진짜 이유는 이름이 역할이 아니라 그때 하던 작업을 담고 있었기 때문입니다. 작업이 바뀌면 이름이 틀려지니 손이 갑니다.

2. 공식 문서가 준 원칙 4가지

재설계를 제 취향으로 하지 않기 위해, 판단의 기준을 공식 문서에서 먼저 뽑았습니다. 아래 4개가 그 기준입니다.
#원칙근거 인용
P1컨텍스트가 가장 근본적인 제약 “The context window is the most important resource to manage.”
P2문맥은 대화가 아니라 산출물이 나른다 “Once the spec is complete, start a fresh session to execute it. The new session has clean context … and you have a written spec to reference.”
P3신선한 컨텍스트가 리뷰를 개선한다 “A fresh context improves code review since Claude won't be biased toward code it just wrote.”
P4조사는 별도 컨텍스트로 밀어낸다 “Subagents run in separate context windows and report back summaries”
헷갈리기 쉬운 곳 P3 를 보고 “리뷰는 따로 있어야 하는 것 아닌가” 싶지만 반대 근거가 아닙니다. P3 가 요구하는 건 리뷰하는 쪽이 코드를 쓴 쪽과 다른 컨텍스트일 것이고, sync 세션은 run 세션과 애초에 별개입니다. 그러니 review 칸을 없애도 신선함은 그대로 유지됩니다.

3. 재설계 — 결정 3가지

D1. 파이프라인은 3단계

plan → run → sync. review 는 sync 가 흡수하고, 렌즈는 sync 지시문의 인자로 넘깁니다.

D2. lead 는 기억하지 않고 읽습니다

보드 상태를 디스크에서 다시 만들어 냅니다 — 백로그 파일 + SPEC 상태 + progress.md.

이미 절반은 그렇게 돼 있음 kanban-dispatch.md 는 이미 “column position is … re-derived from SPEC status after a clear” 라고 적어 뒀습니다. 그런데 동시에 6블록짜리 핸드오프를 붙여넣게 하고 있죠. 두 지침이 서로 어긋납니다. 붙여넣기를 명령 한 줄로 바꾸면 모순이 사라지고 /clear 비용이 0 에 수렴합니다.

D3. 세션 이름은 역할에 고정

plan / run / sync, 겹치면 -1. 카드 정보는 이름에 넣지 않습니다.

발견한 함정 Claude Code v2.1.232 이상은 살아있는 세션과 이름이 겹치면 두 단어짜리 접미사를 제멋대로 붙입니다 — 예: plan-graceful-unicorn. 그러니 -1 은 MoAI 가 실행 전에 미리 배정해야 하고, 충돌 처리를 런타임에 맡기면 원하는 이름을 못 얻습니다. 이 제약은 기존 카드 t56 에 추가해야 합니다.

4. 핵심 — 두 가지 실행 형태를 갈라 쓴다

지금까지는 모든 카드를 한 줄로 세워 보냈습니다. 그런데 카드에는 두 종류가 있습니다 — 설계 판단이 들어가는 것과 그냥 고치면 되는 것. 둘은 다른 방식으로 처리해야 합니다.
파이프라인 (칸반)팬아웃 (팀)
형태카드 1장이 3단계를 통과워커 N 이 각자 카드 1장을 끝까지
맞는 카드C급 — 설계 변경A급 직접 종료 · B급 원인 미확인 결함
처리량1장 / 파이프라인 지연N장 / 카드 지연
카드당 lead 접점92
단계 간 인수인계3회0회
격리카드당 worktree워커당 worktree (필수)
세션 이름plan/run/syncworker-1…worker-N
왜 팬아웃이 싼가 빠른 이유가 “병렬이라서”가 아닙니다. 단계 경계가 없어서입니다. 경계가 하나 생길 때마다 지시 1회 + 증거 읽기 1회 + /clear 왕복 1회가 따라붙는데, 팬아웃에는 그 경계가 0개입니다. 그래서 시간뿐 아니라 lead 의 컨텍스트도 아낍니다.

5. 통신 규약 — 메시지는 초인종, 진실은 디스크

세션끼리 보내는 메시지는 생각보다 약한 채널입니다. 공식 문서가 명시한 한계를 그대로 옮기면, “메시지를 믿고 진행”하는 설계는 성립하지 않습니다.
공식 문서가 말하는 한계그래서 생기는 결론
배달이 보장되지 않음 (전달 / 보류 / 거부 셋 중 하나)메시지 도착을 전제로 진행하면 안 됨
답신 경로가 보장되지 않음회신을 기다려 멈추면 조용히 정지함
반복 메시지 제한 · 세션당 미열람 50건 상한메시지로 상태를 폴링하면 안 됨
텍스트만 건너감 (대화 이력도 파일도 안 감)맥락은 메시지가 아니라 디스크가 날라야 함

그래서 규칙은 세 줄입니다.

  1. 지시는 포인터만 — 카드 번호 / SPEC 번호 / 실행 명령 / worktree 경로 / 완료 증거 위치. 설명 산문 금지.
  2. 완료는 디스크에서 읽는다 — 메시지는 “가서 확인해라”는 초인종일 뿐.
  3. 회신이 안 와도 진행이 막히지 않아야 한다.

6. 이행 순서

  • M1 · review 칸 폐지 → 3단계
    규모 S · 신규
    렌즈(--security 등)를 sync 지시문 인자로 이전. 이걸 빼먹으면 기능이 빕니다.
  • M2 · 세션 이름을 역할에 고정
    규모 S~M · 기존 카드 t56 (제약 추가)
    -1 접미사를 MoAI 가 실행 전에 선배정. 런타임에 맡기면 무작위 접미사가 붙습니다.
  • M3 · 보드 상태를 디스크에서 파생
    규모 M · 기존 카드 t55
    /clear 후 6블록 붙여넣기 → 명령 한 줄로 복귀.
  • M4 · 팀 모드 -t N (팬아웃)
    규모 M · 기존 카드 t57
    lead + worker-1..N. 워커마다 worktree 를 반드시 따로.
  • M5 · 메시지 형식 강제
    규모 S~M · 기존 카드 t58
    전달 항목 고정 + 길이 상한 + 설명 산문 금지.

순서는 강제됩니다. M3 의 “한 줄 복귀”는 이름이 안정적(M2)이어야 성립하고, M2 는 단계가 정리된 뒤(M1)라야 무엇이 역할인지 확정됩니다.

7. 위험

R1 · 렌즈 유실review 를 없애면서 보안·정밀 렌즈 선택지가 같이 사라질 수 있음→ M1 범위 안에서 sync 인자로 이전
R2 · 무작위 접미사이름 충돌 처리를 런타임에 맡기면 plan-graceful-unicorn 같은 이름이 붙음→ MoAI 가 실행 전 -1 선배정
R3 · worktree 공유팬아웃 워커가 같은 작업 트리를 쓰면 병렬이 아니라 직렬 + 충돌→ 워커당 worktree 필수, launcher 경유
R4 · Windows 불가네이티브 Windows 는 세션 간 메시징 자체가 안 되어 두 모드 모두 성립 안 함 (WSL2 만 가능)→ 카드 t61 로 문서화
R5 · 상태 정확성 의존디스크 파생 보드는 SPEC 상태값이 정확해야만 맞음→ 상태 전이 소유권 준수 확인

9. 아직 확인 못 한 것

접점 숫자(12 / 9 / 2)는 측정값이 아닙니다. kanban-dispatch.md 의 주기 정의에서 세어 낸 구조적 계산입니다. 실제 운용에서는 재지시나 블로커로 더 늘어날 수 있습니다.

/rename 반복의 실제 경로는 재현하지 않았습니다. 공식 문서와 kanban.go:360 상으로는 이름이 유지되어야 하므로, 버전 차이 같은 다른 원인이 있을 수 있습니다. M2 착수 전 1회 재현을 권합니다.

/moai review 의 렌즈가 sync 게이트에서 실제로 동작하는지 미확인. M1 에서 확인이 필요합니다.

팬아웃의 처리량 이득은 워커가 서로 다른 worktree 를 점유할 때만 성립합니다. 같은 트리를 공유하면 병렬로 보여도 직렬입니다.
