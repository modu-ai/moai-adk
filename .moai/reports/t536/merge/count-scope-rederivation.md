# 계수 스코프 재유도 — 카드 t536 (리드 지적 대응)

리드 실측 `t528=3` 과 내 보고 `t528=1` 은 **서로 다른 것을 센 두 참값**이다.
파일은 같다 — CHANGELOG blob 동일성 확인:
```
git rev-parse HEAD:CHANGELOG.md        = 6d236fb3d4cb28c58e108f1e09aaa1a3949af974  (WT-home-fallback @ ca8638ede)
git rev-parse 08609c198:CHANGELOG.md   = 6d236fb3d4cb28c58e108f1e09aaa1a3949af974  (develop 병합 커밋)
```

## 세 스코프의 실측 (같은 파일, 같은 명령 계열)

| 스코프 | 명령 | t536 | t528 | t563 | t538 |
|---|---|---|---|---|---|
| A. SPEC-id 항목 형태 (내가 센 것) | `grep -c '\*\*\[<SPEC-ID>\]'` | 1 | **1** | 1 | — |
| B. SPEC-id 토큰 (줄) | `grep -c '<SPEC-ID>'` | 1 | **1** | 1 | — |
| C. 카드-id 토큰 (줄, 리드가 센 것) | `grep -c '<card-id>'` | 1 | **3** | 1 | 1 |

## t528 이 C 에서만 3 인 이유

카드 id `t528` 이 세 줄에 나타난다 — 항목 본문 1줄 + 하위 불릿 2줄:
```
379: - **[SPEC-AC-COLLECTOR-ANCHOR-001](...)** — ... card t528 ...   ← 항목 자체
380:   - **CLI hard-error gate ...**                                  ← 하위 불릿(본문에 t528 언급)
381:   - Coverage: `zz_t528_anchor_probe_test.go`, `zz_t528_grammar_test.go`, ...  ← 파일명이 t528 을 담음
```
즉 C 는 **테스트 파일명 안의 카드 id 까지** 센다. 다른 세 카드는 하위 불릿이 없어 1 이다.

## 판정

내 병합 검증의 주장은 「양쪽 보존 — 남의 항목을 삼키지 않았다」이고, 그 판정식은 **A(항목 형태)** 가 맞다.
A 에서 t536/t528/t563 이 각 1 이므로 세 항목이 모두 살아 있다 — 결론은 선다.
다만 내가 보고문에 스코프를 명시하지 않아 리드의 C 측정과 충돌하는 것처럼 보였다. **틀린 것은 인용 방식이지 판정이 아니다.**

## 일반형

**계수를 인용할 때는 스코프를 함께 인용한다.** 같은 파일에서 `grep -c` 는 무엇을 패턴으로 주느냐에 따라 다른 참값을 낸다 —
SPEC-id 항목 형태 / SPEC-id 토큰 / 카드-id 토큰은 서로 다른 집합이고, 카드-id 는 **파일명 안에도** 산다.
스코프를 명시하면 3 과 1 이 둘 다 참인 서로 다른 측정이 되고, 명시하지 않으면 하나가 그냥 틀린 수로 남는다.

덧붙여: `grep -c` 는 **줄**을 센다. 같은 줄에 토큰이 두 번 있으면 1 이다 — 실제로 항목 줄마다 SPEC-id 가 2회(링크 텍스트 + 경로) 나오므로, 발생 수로 세면(`grep -o | wc -l`) 세 SPEC 모두 2 다.
