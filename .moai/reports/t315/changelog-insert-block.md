  - **What this changes for a project that never edited its git config (card t315, D7a release-note duty).** Both keys shipped in previous versions and they disagreed: the shipped default for the retired `github.spec_git_workflow` was `main_direct` (`system.yaml.tmpl:31` as of `v3.1.2`), while the shipped default for the canonical `git_strategy.{mode}.workflow` was, and remains, `github-flow` (`git-strategy.yaml.tmpl:13/45/81`, all three modes). The retired key was the one actually read, so **a project that edited neither file was running `main_direct` and now runs `github-flow`** — nothing on the user's side changed, the key being read did. Precisely: (a) **on the main branch, for a Tier S/M SPEC without `--pr`, nothing changes** — the sync commit is still pushed directly to the main branch and no pull request is created; (b) **on any branch other than main, a pull request is now created** — `main_direct` previously pushed to the main branch and opened no pull request "regardless of branch name", and worktree delivery follows the same new route; (c) **a branch state matching no route now stops the delivery step** — the unconditional `main_direct` push previously completed from any branch state including a detached HEAD, so **a sync that used to finish may now halt**, deliberately, rather than pushing to the main branch from a state nobody chose. To keep the previous behavior on non-main branches, set `git_strategy.{mode}.workflow` explicitly for the active mode; note that `main_direct` is no longer a strategy value — the value axis is the two-member domain `{github-flow, git-flow}`, and direct-to-main delivery is the `github-flow` main-branch route in (a).
