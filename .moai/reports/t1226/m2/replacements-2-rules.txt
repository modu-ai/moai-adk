## Parallel Execution

Run independent tool calls in parallel; go sequential only for dependencies.

Rules:
- Independent agents launch in one message (sub-agent mode: multiple Agent() calls in a single message)
- fanout bounds: hard bound is the runtime subagent cap (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20 per turn); MoAI's 3-5 is a cache/coordination ADVISORY for fan-out, distinct from the 3-5 TEAM-SIZE advisory that binds agent-team teammates only. SSOT: orchestration-mode-selection.md §C.2
- Team mode: spawn teammates with the Agent tool's `name` parameter (the team forms on first spawn — one team per session, no setup); team agents share TaskList, sub-agents return results directly
- Spawn multiple subagents in one turn when fanning out across independent items or files; never spawn one for work completable in a single response
- Three primitives — **sub-agents**, **Agent Teams**, **dynamic workflows** — chosen by who holds the plan; coding-heavy work prefers sequential sub-agents, workflow-scale fan-out is for genuinely parallel high-volume tasks. Intermediate results per primitive: `.claude/rules/moai/workflow/dynamic-workflows.md`.

## Detection Heuristics

Usage is estimated **state-file-first** from `<projectDir>/.moai/state/context-usage/<session-id>.json`,
the per-session snapshot the statusline writes each render (prefer its `raw_pct` and `stage` over
any proxy; per-session, so no cross-session validity check). If absent or unparseable, estimate
from cumulative output bytes, system-reminder volume, large tool results and completed `Agent()`
returns — under-estimating when uncertain (a premature `/clear` costs one paste, a missed one a
stalled stream).

**Trust.** The snapshot relays the percentage Claude Code computed (upstream metering changes reach
it unrecomputed), and measured within about a percentage point of occupancy rebuilt from the
transcript, with no double-counting either way. Trust it to about a point, and **re-derive rather
than cite it when a verdict needs a number**. Sample size, command, distribution, dated baseline:
`context-window-management-detail.md` § Snapshot confidence.

The statusline's two-stage `/clear` marker is a signal, not a guarantee: auto-compact often
pre-empts the hard stage. Snapshot fields and the guide-gated advisory:
`context-window-management-detail.md` § Detection Heuristics.

@@ * | workflow/cross-session-messaging.md | What the channel is
## What the channel is

A per-session inbox socket plus two tools: `ListAgents` (discover reachable agents) and `SendMessage` (plain text to one, by name). A message carries text and a reply address — never history, never files — and may carry an opt-in `notify_when_idle` request (§ An idle notice is a scheduling hint).

Three properties bound everything below:

- **Same machine is direct; beyond it goes through Anthropic servers.** Another of your machines or a cloud session is addressed by name the same way, and may be **opened** rather than only answered — from Claude Code v2.1.225, only where it appears in the listing. A send from a session not connected to Remote Control arrives with **no reply address** (one-way); a cloud session receives but cannot message back.
- **A message is not consent.** The receiver is told the text came from another session, not the user: it cannot answer a permission prompt or change configuration, and a slash command in it arrives as inert text.
- **Filesystem visibility gates reach.** Sessions find each other through files on disk: a container and its host cannot message each other; two sessions in one container can.
@@END

"On with nothing to enable" holds only where the platform provides the channel; five axes bound where it (and thus Kanban nudges) exists, with one diagnostic separating "absent" from "blocked": **operating system**, **provider**, **runtime version**, **feature-flag evaluation** (the four opt-out env vars), and **the shared machine-global flag slot** third-party-backend sessions inherit and can lose mid-session.

> Detail (approach comparison, condition authoring, T1-T4 templates, MoAI Integration Notes, Native `/goal` Prohibition rationale): `goal-directive-detail.md` — load it when arming a goal or choosing between `/moai goal` and `/moai loop`.

@@ * | workflow/goal-directive.md | What It Is
## What It Is

`/moai goal "<condition>"` registers and arms a completion condition for the session. The text is parsed into `conditions[]` mixing **mechanical** conditions (a shell command's exit code decides) and **model** conditions (a claim the transcript must demonstrate). The `moai hook stop-goal` Stop-hook evaluator loads the goal state at each turn-end and blocks until the goal converges or a bound fires.

Prefix a condition with `model:` or `cmd:` to declare its tier. Unprefixed, the tier comes from an English substring test that reads a claim in any other language as a shell command — which never exits 0, so the goal blocks every turn until its bound.

State: `.moai/state/goal/<session-id>.json`, one file per session. A turn ceiling (default 30) bounds the loop; at it the evaluator emits a 5-section verdict and stops blocking. The runtime's consecutive-block cap (default 8, `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`) overrides first on an unattended run — the effective bound is `min(ceiling, cap)`, and a missing verdict is not convergence. A stagnation guard halts after N consecutive no-progress iterations.

`/moai goal` is **arm-only** (§ Goal-Presentation Timing). Verbs: `/moai goal "<condition>"` (register + arm), `/moai goal status [--all]`, `/moai goal clear`; full surface, progression-mode axis and safety invariants: `.claude/skills/moai/workflows/goal.md`.

Needs hooks enabled (the evaluator IS a Stop hook): unavailable under `disableAllHooks` or `allowManagedHooksOnly`; no runtime-version floor of its own.
@@END
@@ * | workflow/goal-directive.md | Goal-Presentation Timing
## Goal-Presentation Timing

**`/moai goal` is arm-only.** Arming records the condition and makes the `stop-goal` evaluator block turn-end until it holds; it starts no work. A goal armed with nothing running spins idle turns to the ceiling, so arming is always paired with a work-starting action and never substitutes for one — which is why a paste-ready resume keeps a work-starting command (`/moai run SPEC-X`) as Block 5's single primary action (`.claude/rules/moai/workflow/session-handoff.md` § Canonical Format (Block 5)).

**The goal is presented at the Implementation Kickoff Approval gate** as the **autonomous vs semi-autonomous progression-mode axis**, DISTINCT from approve/decline, and armed only after the gate passes (`.claude/skills/moai/workflows/goal.md` § Progression Mode).

**Arming a goal does not authorize autonomous run-phase entry.** The Kickoff human gate stays required in both modes; the axis only selects what happens AFTER it passes and is never a bypass or relaxation. An armed goal never authorizes a PR or a destructive operation — the evaluator decides only whether the turn continues.
@@END

@@ * | workflow/main-checkout-branch-guard.md | Mechanical Enforcement
## Mechanical Enforcement

A PreToolUse hook applies this doctrine conditionally (a static `settings.json` deny cannot scope to
the primary checkout and would lock out worktree flows):

- **Opt-in, inert by default.** `Workflow.BranchGuard.Enabled` gates it; distributed default
  `false` (the hazard does not apply to single-developer repos). Disabled, no `git rev-parse` runs.
- **Deny sentinel.** Every deny is prefixed `BRANCH_GUARD_VIOLATION:`, matchable without parsing
  the reason.
- **Query-vs-mutate.** The `git branch` matcher denies every mutating form and passes read-only
  queries; an unclassifiable form under-matches and passes (the accepted fail-open direction).
- **Fail-open.** Deny only on positive evidence — primary checkout confirmed, a branch-state pattern
  matched, agent not exempt; any uncertainty allows and appends to `.moai/logs/branch-guard-audit.log`.
- **The identity exemption IS reachable from a spawned agent** (measured on a live runtime): Claude
  Code populates `agent_type` on PreToolUse for an Agent-tool spawn, in the snake_case spelling
  `HookInput` decodes, with the spawn name verbatim — so an agent spawned as `manager-git` passes
  the guard in the primary checkout. Deliberately left un-narrowed (narrowing may withdraw a live
  path): the bypass **exists** — never route around the guard through it; use a worktree.
- **The sentinel axis is separate and was not re-tested.** `MOAI_BRANCH_GUARD_EXEMPT=1` is read from
  the hook process's own environment, spawned before the guarded command, so exporting it inside the
  command is a no-op; reading a `BRANCH_GUARD_VIOLATION` as "the exemption is broken" remains a
  misdiagnosis — use a worktree.
