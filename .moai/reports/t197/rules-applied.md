## 규칙 1 — `citation-sweep.sh` 를 보고에서 판정으로

### 무엇이 바뀌었나

이전 판은 인용을 **나열** 하고 무조건 rc 0 으로 끝났다. 새 판은 다섯 가지를 **판정** 하고 실패 시 rc 1 을 낸다.

| 검사 | 내용 |
|---|---|
| C1 | 산문의 살아 있는 커밋 핀 == 전사본이 스스로 찍은 핀 |
| C2 | 인용한 줄 범위가 전사본 길이 안에 있는가 |
| C3 | 그 인용이 `citation-manifest.txt` 의 행에 묶여 있는가 (미선언 인용 = 실패) |
| C4 | **그 줄 범위가 실제로 그 주장의 근거 토큰을 담고 있는가** |
| C5 | 더 이상 인용되지 않는 manifest 행이 남아 있지 않은가 |

C4 가 iter7 F1 이 지적한 층이다 — 줄 번호는 유효한데 그 줄이 주장을 보여주지 않는 형태.

스크립트 머리말에 **판정하지 않는 것** 도 적었다: 산문이 그 근거의 올바른 해석인지는 기계가 보지 않는다. 이전 판이 실제로 하는 일보다 크게 서술돼 있었던 것이 F2 의 절반이었으므로, 한계를 명시하는 것이 수정의 일부다.

### 실패를 실제로 관측했다 — `gate-selftest.sh`

다섯 검사마다 통과해서는 안 되는 입력을 주입하고, 게이트가 비영 rc 로 **거부하는 것을 관측** 한 뒤, 건드린 파일을 백업에서 되돌리고 바이트 동일을 확인한다.

```
$ bash .moai/reports/t197/gate-selftest.sh; echo "rc=$?"

        FAIL: .moai/reports/t197/measurement.md:101 L9990-9999 out of bounds (transcript has 316 lines)
caught: [C3 undeclared citation] rc=1

        FAIL: .moai/specs/SPEC-CODEX-INIT-001/spec.md:47 L211-214 does NOT contain /writeAtomic\(/ — the range is valid but does not show the claim
caught: [C5 stale manifest row] rc=1
        FAIL: .moai/reports/t197/measurement.md L271-272 is in the manifest but nothing cites it any more (stale row)

        ok: both files byte-identical to the backup

SELFTEST PASS — every injected fault was rejected
```

### 이 단계가 실제로 결함을 하나 잡았다

첫 실행에서 **C4 만 통과해 버렸다** (`MISS: [C4 unsupported citation] gate exited 0`). 원인은 게이트가 (파일, 범위) 에 대해 **첫 번째로 매칭된 manifest 행에서 멈춘 것** 이었다 — 그래서 더 엄격한 두 번째 행이 manifest 에 앉아 아무것도 지배하지 않았다. 매칭된 **모든** 행을 검사하도록 고친 뒤 C4 가 잡혔다.

즉 규칙 1 은 서류 절차가 아니라 이번 라운드에 **내 게이트의 실제 구멍을 하나 찾아냈다**. 규칙이 없었다면 "게이트를 만들었다" 로 보고됐을 것이고, 그 게이트는 자기 이름이 붙은 결함을 통과시키고 있었을 것이다.

### 재현

```
bash .moai/reports/t197/citation-sweep.sh    # rc 0 (190 checks)
bash .moai/reports/t197/gate-selftest.sh     # rc 0 (5/5 rejected)
```

## 규칙 2 — 27개 AC 전수 mutant 시험

### 1차: 적대적 mutant 작성 (독립 감사)

두 SPEC 의 모든 AC 에 대해 "그 AC 의 단언을 문자 그대로 만족하면서 인용된 REQ 를 위반하는 구현" 을 실제로 작성 시도했다. 내가 쓴 AC 를 내가 공격하면 같은 사각이 반복되므로, 이 단계는 독립 감사에 맡겼다. 산출물: `mutants-launcher.md` · `mutants-init.md`.

**결과: 27/27 전부 MUTANT-WRITABLE.** MUTANT-FREE 0건.

가장 넓은 것 하나는 두 SPEC 을 관통했다 — **M-SPAWN**: 이 SPEC 들의 모든 음성 판정이 `exec 0회` 로 기동 부재를 증명하는데, 기동 seam 은 `exec` 과 `spawnLaunch` **둘** 이다. 게이트를 `if !opts.Spawn` 로 감싸면 `exec` 은 영원히 0 이므로 INIT 의 AC 5개를 **동시에** 만족하면서 `--spawn` 으로 미배선 세션을 새 창에 띄운다.

나머지도 형태가 몇 개로 수렴한다:

| 형태 | 예 |
|---|---|
| 호출은 세는데 결과 사용을 안 본다 | AC-CL-015 의 "직접 호출 ≥1건" 은 단언 없는 명목 호출로 충족 |
| 축을 하나 안 곱한다 | AC-CI-002 의 8칸에 동사 열이 없어 `app` 만 디스크 재분류하는 구현이 통과 |
| 거부는 보는데 순서를 안 본다 | AC-CI-011 이 leaf 만 조작해 부모 성분 심링크 탈출이 시험 공간 밖 |
| 열거로 금지한다 | AC-CI-011 의 비정규 파일 4종 열거에 소켓·디바이스 노드 누락; AC-CL-016 의 금지 grep 3종을 `open -b` 가 통과 |
| 부재로 인한 0 을 성공으로 읽는다 | `-run 'Codex'` 는 함수명에서 `Codex` 를 빼면 0 케이스 실행 rc 0 |
| 문자열 부재로 성질을 대리 측정한다 | AC-CL-010 의 "로그아웃 단정 없음" 을 `no credentials found` 가 우회 |

### 2차: 조인 뒤 다시 mutant 를 쓴다

각 AC 를 조인 다음, **조인 텍스트에 대해 다시** mutant 작성을 시도하게 했다. 이 2차 통과가 추가 조임을 강제한 AC:

| SPEC | 2차가 더 조이게 만든 AC |
|---|---|
| 런처 | **16개 중 14개** — 예: 진단 바이트 동등만으로는 복사본이 통과해 "그 리터럴이 비시험 원본에 정확히 1회" 를 더했고, 오류 어휘 목록은 `broken` 이 빠져나가 상태 토큰 폐집합으로 바꿨다 |
| INIT | 11개 중 **2개** — AC-CI-007 의 내용 복사 삽입(참조 0건이면서 이중 로드), AC-CI-011 의 어휘적 정규화 선행 |

1차 제안만으로 충분했던 것은 런처 2건뿐이다. **조임은 한 번으로 끝나지 않는다** 는 것이 이 라운드의 관측이다.

### 조인 결과 — 칸 수

| SPEC | 이전 | 이후 |
|---|---|---|
| INIT 표 시험 칸 합계 | 명시 없음 (12+8+10+10+6+12) | **219** (AC-CI-009 가 내역표로 하한을 못 박음) |

### 규칙 2 가 실제로 한 일

3라운드 연속 정체하던 INIT 의 지적 3건(주입에 동사 축 없음 / 거부 순서 미증명 / 타입 집합 미소진)은 **전부 1차 mutant 표에 나왔다.** 감사관이 이미 이 방법을 쓰고 있었고, 내가 안 쓰고 있었다. 규칙을 도입한 뒤 같은 방법으로 **27개 전수** 를 훑으니 지적된 3건이 아니라 **27건** 이 나왔다 — 지적을 하나씩 소비하는 방식이 왜 수렴하지 않았는지가 이 숫자다.

## 예측 (Lessons Protocol `prediction:` / `verified:` 짝)

절차 결함 카드에 적은 대로, 규칙 도입은 검증되지 않은 예측을 동반한다. 다음 라운드에 확인할 형태로 적는다.

> **prediction**: 이번 라운드 이후의 감사 지적에서 아래 두 계열이 **사라진다**.
> - (P1) "검사를 만들었는데 실패를 관측하지 않았다" 계열 — 판정하지 않고 보고만 하는 게이트.
> - (P2) "AC 를 통과하면서 REQ 를 위반하는 mutant 가 있다" 계열 중 **1차 mutant 표에 이미 나온 형태**.
>
> **반증 조건**: P2 계열 지적이 다시 나오되 그것이 1차 표에 없던 **새 형태** 라면 예측은 반증되지 않는다 — 규칙은 아는 형태를 소진할 뿐 미지 형태를 만들어내지 않기 때문이다. 1차 표에 **있던** 형태가 다시 지적되면 반증이다.
>
> **verified: 부분 반증 — P1 은 같은 라운드 안에서 이미 깨졌다.**
>
> 확정 감사(`verdict-iter8.md` D1)가 관측했다: 게이트 본체는 판정하는데, **그 게이트를 검증하는 self-test 의 복원 검사** 가 판정하지 않고 보고만 했다. 백업본과 복원본을 비교하는 형태라 구조적으로 통과만 할 수 있었고, 실제로는 추적 파일 하나를 수정된 채 남겨 그 트리에서 게이트가 rc 1 이 됐다. 두 감사가 동시에 self-test 를 돌리면서 서로의 백업을 오염시킨 것이 방아쇠였다.
>
> **P1 의 정확한 형태는 "게이트를 만들면" 이 아니라 "검사 층을 하나 만들 때마다" 였다.** 규칙 1 을 게이트에는 적용하고 게이트의 검사기에는 적용하지 않았다 — 결함이 사라진 것이 아니라 **한 겹 위로 이동** 했다. 이것이 iter7 절차 결함 카드가 적은 "같은 원리를 인접 항목에 옮기지 못한다" 의 세 번째 재현이다.
>
> 수정: 주입을 코퍼스 사본에 하고(공유 가변 상태를 순서 제어가 아니라 **제거**), 복원 판정을 스크립트가 기억하는 파일 목록이 아니라 **`git status --porcelain` 전후 비교** 로 바꿨다. 관측: `SELFTEST PASS — every injected fault was rejected, working tree untouched`, rc 0, 실행 후 `git status` 가 실행 전과 동일.
>
> P2 는 다음 라운드가 있어야 판정된다. 이번 감사의 잔여 지적 중 1차 mutant 표에 **있던** 형태가 하나 있다(런처 AC-CL-012 — 열거식 관측 범위. 1차 표가 "세 트리 열거" 를 지적했고, 조인 결과가 "격리 홈 트리 전체" 라는 **한 겹 넓은 열거** 였다). 이건 P2 의 반증에 해당한다 — 형태를 알고도 같은 형태로 답했다.

이 라운드 안에서 이미 한 번 관측된 것: 규칙 1 은 도입 즉시 **자기 게이트의 결함 하나**(첫 매칭 행에서 멈춤)를 잡았고, 규칙 2 는 **27/27** 을 잡았다. 둘 다 규칙 없이는 "만들었다" 로 보고됐을 지점이다.

## 이 라운드가 만든 새 결함 하나 — 그리고 그 처리

인용 게이트에 코드펜스 필터를 넣었다. 이 문서 자체가 게이트 자가시험의 **가짜 출력**(주입한 가짜 핀과 범위 밖 인용)을 위 블록에 그대로 담고 있어서, 게이트가 그것을 살아 있는 인용으로 재판정하고 깨끗한 트리를 거부했기 때문이다. 펜스 안은 인용이 아니라 **인용된 출력** 이라는 판단이다.

**대가는 실재한다**: 이제 사람이 펜스 안에 쓴 인용은 게이트가 보지 않는다. 스크립트 머리말에 그렇게 적어 뒀다 — 조용히 좁히지 않기 위해서다. 주장은 산문에 쓰는 것이 맞으므로 이 교환은 받아들일 만하지만, **펜스가 인용이 검사되지 않는 자리가 됐다** 는 것은 사실이고 그 사실이 기록돼야 한다.

펜스 밖의 실제 인용 10건(F1 표의 이전/이후 범위들)은 manifest 에 선언했다. 게이트가 그 10건을 미선언으로 거부한 것 — 그게 C3 이 하는 일이다.
