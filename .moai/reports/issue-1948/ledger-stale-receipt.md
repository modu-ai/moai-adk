# Ledger: DONE on a stale receipt after the move back (issue-1948)

Lane-18, worktree `af-core-claim-runner`, start HEAD `2e5e2ee2a6`. RED `9e9efe274c`, GREEN `f04b45a934`. Local only, nothing pushed. Scope: `internal/agenticfactory/ledger/**` (core/** was not touched).

## Claim
1. **Reproduced: yes.** The previous fix (`120a3cf4b0`, stage check in `factsTx`) looked only at the stage the card is in. A card whose candidate c1 landed, taken back to BUILDING by any of IMPLEMENT, FIX or SPEC (SPEC through the parked FIX and an adopted revision) and handed off again to REVIEWING with the old c1 receipt, reached DONE on the old receipt and the landed row with nothing recorded after the move back.
2. **Root cause.** Three parts. (i) `factsTx` withheld `merged/closed/settled` by position (`Stage != BUILDING`); once the card left BUILDING (E03 hand-off, which the old green+gate pair still satisfies) the position carried no trace of the rework. (ii) The ledger could not say whether evidence came before or after a move: `evidence.id` and `transitions.seq` are separate sequences and `at` has millisecond resolution, so ties cannot be ordered. (iii) Separately, `Enqueue` refuses every landed row ("has landed"), so a reworked card with a new commit c2 had no way to the trunk (reproduced, see Evidence).
3. **Fix.**
   - Schema 2: `transitions.evidence_mark` = id of the card's newest evidence when the move was written (`insertTransition`, `claim.go`). Evidence a `Move` carries is inserted before its transition, so it precedes the mark.
   - `landingStands` (`queue.go`): the landed candidate finishes the card unless the card went back into BUILDING after its newest `enqueue` transition (`reworkMark`: latest transition into BUILDING from a non-BUILDING stage, `seq` greater than the newest enqueue) AND no passing `green` or `gate` run of the landed commit has an id above that move's mark. This replaces the positional check; `TestMove_DoneRefusedForALandedCardBackInBuilding` stays green on it.
   - `Enqueue` replaces a landed row only when all hold: different commit, same card epoch as the row, and the card went back into BUILDING after the offer (`reworkMark`). The landing of c1 is kept as a `decision` note. The same commit, a later-epoch holder (N3) and a card never taken back are refused as before.
4. **Verdict for rebuilding the SAME commit (c):** the same commit measured again after the move back (passing green or gate on c1, recorded after the move) finishes the card. Rationale: the trunk holds exactly what was measured, nothing is lost, and refusing it would strand a card whose rework changed no commit (Enqueue refuses the landed commit, and no new work exists to queue). What does not count: a gate on another commit, a failing run of c1, a review of c1, and anything recorded before the move back (tests `TestMove_DoneIgnoresEvidenceThatIsNotTheLandedCommitMeasuredAgain`, `TestMove_DoneNeedsWorkRecordedAfterTheMoveBack`).
5. **Persistence (d):** the basis is `evidence_mark`, `transitions.seq` and the `enqueue` actor, all rows of the ledger file. Every refusal/acceptance row in the table runs both in the same process and after `Close`+`Open` of the file; v1 files migrate (below).

## Residual-risk
- **N3 unchanged, not better, not worse.** `TestA1Done_WithdrawnLanded_ReclaimedStrands` still fails with the same text as before this change: `enqueue: ledger: invalid argument: t1 has landed`, `REVIEWING -> DONE: ... accepted-receipt-finished needs merged, closed, settled`, `FINDING: work in the trunk, row landed, card REVIEWING: no path to DONE at the new epoch`. The Enqueue exception requires the row's card epoch to equal the card's, so a reclaimed holder is still refused. A reclaimed card that also went through BUILDING is still stranded.
- **Design change to review: Enqueue now replaces a landed row** in one case (same epoch, different commit, moved back into BUILDING after the offer). `TestEnqueue_NeverReplacesALandedRow` and `TestQueueUpdate_LockHolderSettlesAnOlderLandingRow` ("a landed row is final") stay green because the card in those tests was never in BUILDING after its offer; they state the invariant for that case and the new rule leaves it. If the leader wants landed rows to stay fully final, revert the `Enqueue` case in `f04b45a934` (`queue.go`) and `TestRework_ANewCommitGoesThroughTheQueueLandsAndFinishes` / `TestEnqueue_ALandedRowIsNotReplacedByACardNotTakenBackForRework` go with it; the DONE fix does not depend on it.
- A card that offers c2 from REVIEWING without having gone through BUILDING after the offer (the audit's `...NewCommitNeverLands` path) is still refused "has landed". It is not stuck: BUILDING/FIX or IMPLEMENT, c2 green and gate, hand-off to REVIEWING, Enqueue works (tested). The ledger cannot tell a skipped rework from an unrelated commit.
- Rolling back to a binary that knows only schema 1 now fails to open a ledger written by this code (`the file has schema 2, this code knows 1`). The deploy of this build to a ledger that already exists is a one-way step.
- The migration orders old evidence against old moves by the database's millisecond timestamps, and counts same-millisecond evidence as before the move (withholds DONE). A pre-migration card moved back and re-measured within one millisecond would need one more measurement; no such card is expected.
- A holder that moves back, re-measures c1 and finishes is accepted by decision (c); the ledger cannot tell a real rework that changed nothing from none at all.
