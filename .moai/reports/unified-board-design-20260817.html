① 모드 이름: 숫자(Mode 1~6)를 버리고 동시성 축 하나로 정렬된 4개 이름을 씁니다. 현행 이름은 축이 뒤섞여 있어 parallel(4)과 sub-agent(5)가 서로를 구별하지 못합니다 — 둘 다 서브에이전트를 씁니다.

1. 왜 이름을 바꾸는가

이름은 장식이 아닙니다. 고를 때 무엇을 고르는 건지 알려주는 장치예요. 지금 이름은 그 일을 못 합니다.

1.1 현행 6개 — 축이 뒤섞여 있습니다

#이름이름이 가리키는 축문제
1trivial작업 크기문제 없음
2background실행 위치런타임 기본값에 흡수됨 (v2.1.198부터 서브에이전트는 기본 백그라운드) — 고를 게 없음
3agent-team조직 형태RETIRED인데 숫자를 점유 — 4·5·6이 밀려 있음
4parallel동시성5와 같은 축의 다른 값인데 이름이 다른 축을 가리킴
5sub-agent실행 주체4도 서브에이전트를 씁니다 — 이름이 4와 5를 구별하지 못함
6workflow도구 이름무엇이 다른지가 이름에 없음

가장 큰 문제는 4와 5입니다. 실제 차이는 동시에 몇 개를 스폰하는가(여럿 vs 하나)인데, 이름은 parallel(동시성)과 sub-agent(주체)로 서로 다른 축을 가리켜요. 이름만 보고는 뭐가 다른지 알 수 없습니다.

그리고 숫자가 아무 의미를 안 나릅니다. "Mode 4"는 순서도 크기도 알려주지 않아요. 3번이 은퇴한 채 숫자를 붙들고 있어서 순서마저 어긋나 있습니다.

1.2 새 이름 — 축 하나로 정렬

기준을 "한 번에 몇 갈래로 일이 나뉘는가" 하나로 통일합니다. 그러면 이름이 저절로 순서를 갖습니다.

agent-team은 이미 RETIRED입니다. 숫자를 회수하고 각주로만 남깁니다 — --team 플래그가 오면 여전히 거절하고 serial로 떨어뜨립니다(동작 불변).

2. 보드 통합 — 카드가 경로를 고른다

지금은 팩토리와 칸반이 다른 명령입니다. 그런데 그 차이의 근거가 곧 사라져요.

2.1 모드를 갈랐던 것은 세션 구조였습니다

기존Agent 실행 엔진 이후
팩토리터미널 N개 (워커마다 하나)반장 1세션 + Agent N
칸반터미널 4개 (컬럼=세션)반장 1세션 + Agent
세션 구조가 같아집니다. 모드를 가르던 건 "터미널을 몇 개 어떻게 띄우나"였는데, 그게 없어지면 명령이 둘일 이유가 없습니다.

2.2 남는 차이는 경로 길이 하나뿐

카드 클래스가 이미 경로를 규정하고 있습니다. 새로 만들 게 아니라 이름을 붙여주면 됩니다.

클래스성격경로모드
A 한 파일 한 줄, 설계 판단 없음, CI가 회귀를 잡음 run → PR
1스테이지		 fanout — 카드 N장이 수평으로 동시에
B 결함인데 원인 미상 run → sync
2스테이지		 fanout
C 설계 결정 포함, 여러 서브시스템 plan → run → sync
3스테이지		 serial — 1장이 수직으로 이동
★

모드 이름이 경로 이름과 같아집니다. A/B급은 fanout으로, C급은 serial로 돕니다. 그러면 "팩토리"와 "칸반"이라는 모드 이름 자체가 불필요해져요 — 하나의 보드에 두 경로가 있고, 경로 이름은 오케스트레이션 모드 이름 그대로입니다.

2.3 그래도 팩토리 경로는 없앨 수 없습니다

"칸반에 Agent()를 넣으면 팩토리가 불필요하지 않나"는 절반만 맞습니다. 카드당 리드 접점을 세어 보면 이유가 보여요.

형태디스패치증거 읽기/clear합
현행 4컬럼 (세션)44412
3단계 (세션)3339
3단계 (Agent)3306
fanout (Agent)1102

Agent()가 지우는 건 /clear 왕복입니다 — Agent는 카드 단위 수명이라 세션 위생이 필요 없으니까요. 하지만 디스패치와 증거 읽기는 남습니다. 단계 경계가 있는 한 사라지지 않아요.

선행 문서가 그 이유를 정확히 적어놨습니다 — "팬아웃이 빠른 이유는 병렬이어서가 아니라 단계 경계가 없어서다."

그래서 6 대 2, 3배 차이가 남습니다. A급 카드를 3단계에 태우면 의례 비용을 세 배 물어요. 통합은 표면에서 하고, 경로는 갈라 둡니다.

통신 규약 — 메시지는 초인종, 디스크가 진실

세션 간 메시지는 배달이 보장되지 않고, 배달되면 수신 측 할당량을 프롬프트처럼 소모하며, 승인을 대신할 수 없습니다. 그래서:

  1. 위임은 큐로. 메시지는 "가서 읽어라" 알림일 뿐입니다
  2. 완료 판정은 디스크에서. 보고를 믿지 않고 증거를 읽습니다
  3. 회신이 안 와도 진행이 막히지 않아야 합니다 — 반장은 폴링으로 큐를 집습니다
  4. 디스패치는 포인터만. 카드 id · SPEC id · 실행 명령 · worktree 경로 · 증거 위치. 설명 산문 금지
5. 실행 규율 3가지
규율내용근거
시차 스폰 작업자를 동시에 띄우지 않습니다. 첫 워커가 출력을 시작한 뒤 나머지를 스폰해요. 동시 스폰은 서로의 캐시를 못 읽어 전부 쓰기 요금을 냅니다 N=8 동시 312K vs 시차 66K 토큰 (프리픽스 39K/에이전트 추정)
증거는 포인터로 작업자 보고는 branch + SHA + RED/GREEN + 증거 경로로 제한. 서술 금지. 공장장은 의심될 때만 경로를 엽니다 리드 컨텍스트 압박의 가장 싼 처방
재작업 상한 2회 FAIL이 2회 반복되면 같은 워커에 다시 맡기지 않고 공장장으로 에스컬레이션합니다 무한 왕복 방지 · 3회 동일 실패는 별도 진단 신호
6. 명령 표면
# 공장장 — 대화 · 큐 · 판정 (Claude)
moai cc --chief

# 반장 — 경로 실행 (GLM). 동시 카드 수는 N
moai glm -k N

# -f 는 폐지. 경로는 카드 클래스가 정하므로 모드 플래그가 필요 없다.

기존 -k는 4역할 companion을 손으로 띄우는 형태였습니다. 새 -k N은 반장 1세션 + 동시 카드 N장이고, companion 세션은 필요 없어요 — 단계는 Agent() 스테이지가 됩니다.

8. 리스크

접점 수가 측정값이 아님 높음

12 / 9 / 6 / 2 는 디스패치 주기 정의에서 나온 구조적 계산입니다. 통합의 근거가 이 숫자인데 재본 적이 없어요.

완화 — S0을 선결로. 실측이 계산과 크게 어긋나면 통합 판단 자체를 재검토합니다.

클래스 오판 높음

통합 후 유일한 분기점이 공장장의 클래스 판정입니다. C급을 fanout에 태우면 설계 판단이 검토 없이 나가고, A급을 serial에 태우면 3배 낭비예요.

완화 — 애매하면 serial로. 낭비는 회복되지만 검토 없이 나간 설계 변경은 회복이 어렵습니다.

렌즈 유실 중간

review 흡수 시 --security / --deep 등 렌즈 선택이 사라질 수 있습니다. 게다가 sync 게이트에서 렌즈가 실제로 동작하는지 미확인이에요.

완화 — S2 범위 안에서 sync 디스패치 파라미터로 이전하고, 착수 전에 동작을 먼저 확인합니다.

두 명명 체계 공존 중간

숫자 참조가 한 군데라도 남으면 "Mode 4"와 fanout이 같이 돌아다닙니다. 새 이름의 목적이 정확히 그 혼란 제거인데 역효과가 나요.

완화 — S1을 일괄 치환 한 번으로. 잔여 숫자 참조 0건을 grep 가드로 확인합니다.

GLM 품질 미달 재작업 중간

저가 백엔드가 카드를 망치면 재작업 비용이 절감분을 삼킵니다. 최악은 Claude로 다시 하는 것 — 두 번 냅니다.

완화 — 클래스 라우팅을 엄격히. C급 plan은 공장장이 직접. 재작업률을 계측해 임계 초과 시 라우팅 조정.

공장장 컨텍스트 압박 낮음

계층이 줄면 판정이 공장장에 몰립니다. N장 증거가 한 곳으로 들어와요.

완화 — 증거 포인터화(§5)가 1차 방어. 부족하면 별도 Claude 판정 세션을 분리합니다.
