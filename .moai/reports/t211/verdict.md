# t211 — statusline temp-file leak

Class B, plan skipped. Cause was supplied by the lead and confirmed here, not re-diagnosed.

## Claim

The statusline wrapper leaked one temp file per render. It no longer creates a temp file at all,
on any of its four exec branches, and a regression test asserts that behaviourally.

## Cause (confirmed, not re-derived)

`internal/template/templates/.moai/status_line.sh.tmpl` opened `temp_file=$(mktemp)` with
`trap 'rm -f "$temp_file"' EXIT`, then handed control away with
`exec moai statusline < "$temp_file"`. `exec` replaces the shell process, so the EXIT trap never
fires. The template's own line 20 comment already said `exec` makes following code unreachable;
what was missed is that the trap is following code.

## What was chosen, and why

The buffer was removed entirely: stdin is now inherited by the exec'd process
(`exec moai statusline`, no redirect). The alternatives considered were an unlink-before-exec with
an open fd, and dropping `exec` for a plain call.

The buffer had no reader left to justify it. It existed so several exec candidates could each read
the same stdin, but only one exec ever runs, and every branch before it (`command -v`, `[ -f ]`)
tests paths rather than reading input. `moai statusline` reads `os.Stdin` directly
(`internal/cli/statusline.go:144` returns `os.Stdin` whenever stdin is not a character device), so a
pipe from Claude Code behaves identically with or without the intermediate file. Removing it is the
only option under which no cleanup can be forgotten again — there is nothing to clean up.

Applied to **all four** exec branches: PATH, `ResolvedMoaiPath`, `$HOME/go/bin`, `$HOME/.local/bin`.

One hardening rider: `source "$HOME/.moai/.env.glm"` now runs with `</dev/null`. With no buffer in
front of it, an env file containing a stdin read would otherwise eat the JSON.

## The regression test

`internal/template/status_line_tmpfile_test.go` — `TestStatusLineLeavesNoTempFile`. It is structural,
not a string grep: it renders the real embedded template, writes it to disk, and **runs** it with a
stub `moai` on PATH, then asserts the isolated temp directory is empty and that the stub received the
stdin JSON byte-for-byte.

Two things the test had to get right, both found by it failing for the wrong reason first:

- **PATH must keep the inherited entries.** With `PATH=<stubdir>` alone the script's own `mktemp` and
  `cat` were not found, the leak silently did not happen, and the assertion passed while measuring
  nothing.
- **BSD `mktemp` ignores `$TMPDIR`.** On macOS, bare `mktemp` writes to the per-user Darwin temp dir
  regardless of `$TMPDIR` — measured: `TMPDIR=/tmp/t211probe mktemp` →
  `/var/folders/kt/.../T/tmp.Vh79O3kqVc`, which is exactly where the field leak accumulated. The test
  therefore shadows `mktemp` on PATH so any temp file the script requests lands in the inspected
  directory, on both macOS and Linux.

## Template-First

Template edited first, then `make build`, then the local mirror.

`.moai/status_line.sh` (tracked) was a **drifted older rendering**: it still carried a
`DEBUG_STATUSLINE` logging block and lacked the `ResolvedMoaiPath` branch the template has had since
`c4a42bc11`. That drifted file is the one that actually ran on this machine and produced the observed
leak. It was regenerated from the fixed template rather than patched; the debug block was dropped
because it exists in no template and the next `moai update` would remove it regardless.

`catalog.yaml` was regenerated by `make build` and came out unchanged.

## Collateral change

`TestStatusLineEveryExecGuarded` matched the PATH exec branch by literal string
(`exec moai statusline < "$temp_file"`). Updated to `exec moai statusline`. The invariant it asserts —
every exec is reached only behind a `command -v` or `[ -f ]` guard — is unchanged.
