먼저 — 이 문서에 계속 나오는 말들

codex-cli — OpenAI가 만든 터미널용 AI 코딩 도구예요. Claude Code와 같은 자리에 있는 경쟁 도구라고 보면 됩니다. moai는 이 둘 양쪽에 붙는 것을 목표로 해요.

배선 (wiring) — moai가 codex 쪽 설정 파일에 자기 정보를 써 넣어, codex가 moai를 알아보게 만드는 일. 전기 배선처럼 "연결해 두는 작업"입니다.

훅 (hook) — 특정 순간마다 자동으로 불려 나가는 작은 프로그램. "세션이 시작되면 이걸 실행해라" 같은 약속이에요.

TOML — 설정 파일을 적는 문법 하나. codex는 JSON이 아니라 이걸 씁니다.

deprecated — "아직 동작하긴 하는데, 이제 쓰지 마세요"라고 공식적으로 표시된 상태. 곧 사라질 수 있다는 예고입니다.

한눈에

이 카드는 운영자 지시 "codex 최신 공식 문서를 기반으로 moai codex 기능을 다시 개발하라"의 1단계입니다. 뭘 만들지 정하기 전에, codex가 실제로 무엇을 제공하는지부터 공식 문서로 확정하는 일이에요.

중요한 배경 하나. 앞선 조사가 "codex는 ~/.codex/prompts로 커스텀 커맨드를 읽는다"고 썼다가 출처가 없어 철회했습니다. 그래서 이번엔 근거를 리포 안에서 찾지 않고, 리포 밖 공식 문서에서 가져왔습니다.

결론 일곱 줄:

커버리지 한 장

축별로 "codex가 공식적으로 제공하는 표면" 대비 "moai가 실제로 쓰고 있는 양"입니다. 막대가 짧을수록 안 쓰고 있는 표면이 넓다는 뜻이고, 그게 곧 확장 여지예요.

축 1 · 커스텀 프롬프트 / 커맨드 표면

묻는 것: /moai plan 같은 moai의 슬래시 커맨드 16본을 codex 쪽에도 그대로 노출할 수 있을까? 그러려면 codex가 "사용자가 만든 커맨드"를 어디서 읽는지 알아야 합니다.

답: 그런 자리는 있었지만 지금은 쓰지 말라고 공식적으로 표시돼 있고, 대신 스킬을 쓰라고 합니다.

공식 문서가 말하는 것

Deprecation Status: Custom prompts are deprecated. The documentation explicitly states: "Use skills for reusable prompts."

Directory Location: Custom prompts are stored in ~/.codex/prompts/.
Invocation Syntax: /prompts:promptname in both the Codex CLI and IDE extension.
Placeholder Rules: $1–$9, named $FILE (KEY=value), $ARGUMENTS, $$ for a literal $.

Custom prompts "require explicit invocation and live in your local Codex home directory... they're not shared through your repository."

스킬 쪽 호출 규약은 이렇습니다:

In Codex, invoke skills explicitly using the $ sigil: $skill-name or /skills to browse available skills.

현재 moai와의 차이

차이가 아니라 정합입니다. moai는 ~/.codex/prompts에 아무것도 쓰지 않고(M1 = 0히트), 그게 문서 권고와 같은 방향이에요.

실제로 확인한 것 — 이 머신의 ~/.codex/ 안

~/.codex/prompts는 없습니다(ls → No such file or directory). 대신 ~/.codex/skills와 ~/.codex/plugins가 있습니다. 문서가 말하는 이동 방향("프롬프트 → 스킬")이 실제 디스크에도 그대로 찍혀 있는 셈이에요.

다만 이건 이 머신 한 대의 관측입니다. 규약 판정은 문서 인용에 기댔습니다.

앞선 조사는 왜 틀렸나

되풀이하지 않기 위한 기록

앞선 Explore는 "~/.codex/prompts/*.md가 그 메커니즘"이라 썼다가 출처 없음으로 철회했습니다. 이번 조사 결과, 그 진술은 절반만 틀렸습니다.

그런 메커니즘은 실재했고 지금도 문서에 남아 있습니다. 다만 deprecated고 스킬로 대체됐죠. 즉 철회는 옳았지만 이유가 달랐습니다 — 근거가 없던 것이지, 사실이 없던 것이 아니었어요.

실패의 원인은 근거를 리포 안에서 찾으려 한 것입니다. codex의 규약은 codex 쪽 문서에 있지 moai 리포에 있을 이유가 없거든요. 이 카드가 리포 밖으로 나간 이유가 그것입니다.

축 2 · 훅 이벤트 전체 목록

묻는 것: codex가 "이 순간에 프로그램을 불러 준다"고 약속하는 순간이 총 몇 개이고, moai는 그중 몇 개를 잡고 있나?

답: 공식 12개, moai가 열거한 건 11개. 빠진 하나는 Interrupt입니다.

공식 문서가 말하는 것

The documentation lists these hook events: SessionStart, SessionEnd, SubagentStart, SubagentStop, PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, UserPromptSubmit, Stop, and Interrupt.

훅이 어디서 읽히고, 어떤 모양으로 적히는지 (원문 인용)

Codex discovers hooks from these paths: ~/.codex/hooks.json, ~/.codex/config.toml, <repo>/.codex/hooks.json, <repo>/.codex/config.toml.

"If more than one hook source exists, Codex loads all matching hooks." · "Higher-precedence config layers don't replace lower-precedence hooks."

설정 파일 안에 직접 적는 형태:

[[hooks.SessionStart]]
matcher = "startup|resume"

[[hooks.SessionStart.hooks]]
type = "command"
command = "python3 ~/.codex/hooks/session_start.py"

동기(기본)는 "Codex waits for a command hook to finish", 배경("async": true)은 끝나면 다음 안전한 지점에 결과를 전달하며 세션당 동시 8개가 상한입니다.

훅이 받는 공통 입력: session_id, transcript_path, cwd, hook_event_name, model, permission_mode. 돌려주는 판정은 종료코드 0=성공 / 2=차단이고, 차단은 이런 모양입니다:

{ "hookSpecificOutput": {
    "permissionDecision": "deny",
    "permissionDecisionReason": "reason text" } }

현재 moai와의 차이 — 4가지

차이 1 — Interrupt가 없습니다.

워크드 예시 — "없다"를 어떻게 증명했나

부재는 증명하기 까다롭습니다. 검사가 고장 나도 똑같이 "없음"이 나오거든요. 그래서 두 번 셌습니다.

$ grep -rn 'EventInterrupt' internal/
→ 0히트                          ← 찾는 것

$ grep -rn 'EventStop\b' internal/hook/*.go
→ internal/hook/audit_test.go:493 …   ← 대조군: 반드시 있어야 할 것

대조군이 검출됐으니 검사 자체는 살아 있습니다. 그러므로 첫 줄의 0히트는 진짜 0입니다. moai가 열거한 11종은 internal/codexadapter/events.go:52-64에 있고, 공식 12종과 대조하면 정확히 Interrupt 하나가 빕니다.

차이 2 — adapted 6종은 문서 기준이 아니라 측정 기준입니다. 이건 결함이 아니에요. 소스 주석(events.go:40-51)이 직접 밝힙니다: 나머지 5종을 뺀 것은 "상대가 없어서"가 아니라 측정 커버리지에 대한 판단이고, SubagentStop은 발화하지 않는 것으로 측정됐다고요(위임이 tool_name이 collaboration으로 시작하는 PostToolUse로 나타남).

이 서술은 문서에 SubagentStop이 정식 이벤트로 남아 있는 사실과 모순되지 않습니다 — 문서는 이벤트의 존재를, 주석은 이 배선에서의 발화 여부를 말하니까요. 다만 그 측정은 0.152.1 이전 것이라 0.153.4에서 다시 잴 가치가 있습니다.

차이 3 — 커맨드 형태는 정합. internal/codexwiring/hooks.go:104가 moai hook <arg> --harness codex를 .codex/hooks.json에 씁니다. 문서의 type="command" 규약, 파일 경로 규약과 모두 맞습니다.

차이 4 — async / matcher 미사용. moai가 발행하는 핸들러에 이 둘이 실린다는 근거를 찾지 못했습니다. 다만 없다고 단정하지는 않습니다 — 판정서 §Gaps에 미관측으로 남겼습니다.

축 3 · [[skills.config]] 규약

묻는 것: moai의 스킬들을 codex에 보이게 하려면 [[skills.config]]라는 설정 항목을 써야 하나?

답: 아니요 — 방향이 반대입니다. 스킬을 보이게 하는 건 경로 관례이고, 이 키는 스킬을 끄는 수단입니다. 그리고 moai는 이미 그 경로 관례를 지키고 있습니다.

공식 문서가 말하는 것 — 이 키의 용도

To disable skills without deletion, use this in ~/.codex/config.toml:

[[skills.config]]
path = "/path/to/skill/SKILL.md"
enabled = false

설정 레퍼런스 쪽 필드 정의:

[[skills.config]] — Array of skill configurations: path (string, path to skill folder), enabled (boolean)

문서 두 곳이 서로 다르게 적습니다

같은 path 키를 두고, 스킬 작성 문서는 SKILL.md 파일을 가리키는 예시를 보여 주고, 설정 레퍼런스는 "path to skill folder"(폴더)라고 적습니다.

어느 쪽이 참인지 측정하지 않았습니다. 이 축을 구현하는 카드는 이 모호성을 실측으로 먼저 닫아야 합니다(카드 S1). 문서만 보고 한쪽을 골라 구현하면 조용히 아무 스킬도 안 걸리는 배선이 나올 수 있어요.

현재 moai와의 차이

정합 1 — 미러는 이미 옳은 자리에 있습니다.

워크드 예시 — moai가 실제로 만드는 것

internal/template/skill_mirror.go:52:

var mirrorSkillsRelDir = filepath.Join(".agents", "skills")

파일 머리말(:4-5)이 이유를 직접 적습니다 — codex는 .claude/skills/를 보지 않고 <repo>/.agents/skills/를 스캔하므로, 배포하는 스킬마다 이런 심볼릭 링크(원본을 가리키는 바로가기)를 만듭니다:

.agents/skills/<name>  →  ../../.claude/skills/<name>

링크를 못 만드는 플랫폼에서는 실제 폴더 복사로 폴백합니다. 진입점은 WithSkillMirror이고 배포당 1회 돕니다(:171).

그러니까 "moai에 codex 스킬 배선이 없다"는 진술은 거짓입니다. 있습니다 — 다만 설정 키가 아니라 경로 관례를 통한 것입니다.

차이 1 — [[skills.config]]는 읽기만 하고 쓰지 않습니다. internal/codexwiring/skills.go가 자기 주석(:9)에 "READ-ONLY by construction — nothing here writes"라고 적어 뒀습니다. 소비처는 moai doctor의 권고 표면뿐(internal/cli/doctor_codex.go:303,363,475)이고, 발행자는 없습니다.

차이 2 — 종전 판정의 유효 범위. 이게 t502의 핵심입니다.

SPEC-CODEX-SKILL-LOADER-001이 실제로 기록한 것
  • 상태는 completed, 관측 버전은 codex_version_observed: "codex-cli 0.152.1" (progress.md:90).
  • 판정 요지: <repo>/.agents/skills/<name>/SKILL.md는 실제로 로드된다(두 독립 탐침으로 확인).
  • 반면 skills 키의 세 성질(존재 · 값 모양 · 잘못된 값에서의 동작)은 전부 "확인되지 않음"으로 남았습니다(AC-CSL-004).
  • 그래서 skill-loader 매니페스트 행은 documented-drop으로 처리됐습니다 — 이번 회차엔 구현하지 않겠다고 기록하고 뺀 것이지, 조용히 뺀 게 아닙니다.
  • 매니페스트 최상단 codex_measured_version은 "0.147.0"으로 의도적으로 유지됐습니다(agents-codex.yaml:14). 이번에 잰 축이 하나뿐인데 최상단을 올리면 갖지 않은 커버리지를 주장하게 되기 때문이라고 progress.md:118에 적혀 있습니다. 정직한 처리예요.

그래서 무엇이 바뀌었나: 0.152.1 시점에 "확인되지 않음"이던 축이, 현행 문서에서는 path + enabled로 명시 문서화됐습니다. 그때의 기각은 옳았고, 지금은 재검토 대상입니다.

차이 3 — 용도의 방향. 문서상 이 키는 끄는 수단이지 등록 수단이 아닙니다. 등록은 경로 관례가 합니다. 따라서 moai가 이 테이블에 쓸 이유는 "스킬을 보이게 하려고"가 아니라 "특정 스킬을 끄려고"일 때뿐입니다.

축 5 · MCP / statusline 최신 스키마

MCP(Model Context Protocol)는 AI 도구가 외부 프로그램의 기능을 빌려 쓰는 표준 통로예요. moai는 자기 자신을 그런 통로로 codex에 등록해 둡니다. statusline은 터미널 아래쪽에 뜨는 상태 표시줄이고요.

답: MCP 등록은 적법하지만 18개 필드 중 3개만 씁니다. 그리고 플러그인이라는 표면 전체가 통째로 미사용입니다 — 여기가 이번 조사 최대의 발견입니다.

공식 문서가 말하는 것

[mcp_servers.<id>] 전체 필드:

command, args, cwd, env (map), env_vars (array), url (for HTTP servers), bearer_token_env_var, http_headers, http_headers_helper, enabled, required, startup_timeout_sec, tool_timeout_sec, enabled_tools, disabled_tools, default_tools_approval_mode, tools.<tool>.approval_mode, tools.<tool>.output_token_limit

최상위 테이블 전체: [agents], [mcp_servers.<id>], [permissions.<name>], [[skills.config]], [hooks], [tui], [otel].

현재 moai와의 차이

정합 1 — MCP 등록은 적법하고 보수적입니다. internal/codexwiring/configtoml.go:11-22가 없을 때만 이걸 씁니다:

[mcp_servers.moai]
command = "moai"
args = ["mcp-server"]
default_tools_approval_mode = "writes"

차이 2 — statusline 허용목록은 문서로 검증할 수 없습니다.

"없다"를 정직하게 쓴 자리

그런데 이번 조사에서 공식 문서는 이 토큰들을 열거하지 않았습니다. 고급 설정 문서를 읽었지만 "does not enumerate valid status-line item identifiers or tokens"였어요.

그러니 이 목록은 문서로는 검증 불가합니다. 결함은 아닙니다 — 주석 자체가 "no blind upstream tracking; additions are an explicit judgment at documentation-refresh time"라고 정책을 밝혀 뒀거든요. 기록된 선택입니다. 다만 갱신 시점을 정하는 트리거가 없어서, 그게 카드 M3입니다.

  3. 공식 훅 이벤트는 12종, moai는 11종 — 누락은 Interrupt 하나.
  4. [[skills.config]]는 공식 문서화된 실재 키(path+enabled)이며 비활성화 수단으로 기술된다. moai는 읽기만 하고 쓰지 않는다.
  5. 스킬 탐색 경로는 .agents/skills이고, moai는 이미 그 경로에 미러를 만든다.
  6. agents TOML 필수 3필드를 11본이 모두 충족한다. model·skills.config·[agents]는 미배선.
  7. codex 플러그인 표면은 0.153.4에 실재하며 moai는 전혀 쓰지 않는다.

증거 (Evidence)

  • 재현 명령과 출력은 각 축에 명령·file:line과 함께 인용.
  • 부재 주장 3건은 대조군을 동반: M1 0 ↔ codex_task 115파일 · EventInterrupt 0 ↔ EventStop 검출 · codex-plugin 0 ↔ codexwiring 22파일.
  • 공식 인용 7페이지 전부 WebFetch로 본문을 읽었다. 검색 요약만 있는 페이지는 인용하지 않았다.
  • 서브에이전트가 만든 리포 인벤토리의 핵심 4건은 내가 직접 재측정해 일치를 확인했다. 재측정하지 않은 항목은 Gaps에 든다.

기준 귀속 (Baseline)

  • CLI: codex --version → codex-cli 0.153.4.
  • 문서: 2026-09-07 조회본. 버전 스탬프 없음.

미관측 (Gaps) — 10건

"안 잰 것"을 빠짐없이 적는 게 이 절의 목적입니다. 여기 없는 것을 다음 카드가 근거로 삼으면 안 됩니다.

  1. skills.config의 path 값 모양(파일 vs 폴더) — 두 공식 페이지가 서로 다르게 기술. 실측 안 함 → S1
  2. 미adapted 5종의 0.153.4 발화 여부 — 종전 관측은 0.152.1 이전 것 → H2
  3. Interrupt의 실제 발화 조건과 페이로드 — 목록에 있다는 것만 확인
  4. moai가 발행하는 훅 핸들러의 matcher/async 유무 — 근거를 못 찾았을 뿐, 없다고 단정 안 함
  5. agents TOML에 model을 안 싣는 것이 의도인지 — 판정 안 함
  6. codex 빌트인 explorer가 Claude Explore를 갈음하는지 — 추론일 뿐 측정 안 함
  7. statusline 29토큰이 0.153.4 소스 열거형과 아직 일치하는지 — 문서가 열거하지 않아 문서로는 검증 불가, 소스도 확인 안 함
  8. 서브에이전트 인벤토리 중 내가 재측정하지 않은 항목 — 결론을 지지하는 데 쓰지 않았거나 보조적으로만 씀
  9. 플러그인 설치가 기존 3중 침습을 실제로 대체 가능한지 — M2는 문서상 가능성이지 실증이 아님
  10. 로컬 config.toml의 notify = [..., "turn-ended"] — 문서는 agent-turn-complete 하나만 적는데 실제 파일엔 다른 값. 조사 안 함

잔여 위험 (Residual risk)

  • 문서에 버전 스탬프가 없어 0.153.4와 문서 사이 시차를 배제할 수 없다. 문서가 앞설 수도, 뒤질 수도 있다.
  • learn.chatgpt.com으로의 이전이 진행 중이라 문서 구조가 또 바뀌면 인용 URL이 깨질 수 있다. 원 주소를 함께 남긴 이유다.
  • 로컬 ~/.codex/ 상태는 이 머신 한 대의 관측이다. 규약 판정은 문서 인용에 기댔다.
  • 카드 표의 "규모"는 판단이지 측정이 아니다.
