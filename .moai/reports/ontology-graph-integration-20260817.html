한 줄 결론 — 세 원천이 이미 그래프를 생산하고 있고, 저장만 안 합니다. 새로 만들 것은 세 원천을 한 파일로 쓰는 writer 하나와, 그 위를 걷는 ~50줄짜리 순수 Go BFS 하나뿐이에요.

왜 지금인가 — 7/29 전략 문서가 "그래프의 70%는 이미 갖춰짐"이라 했는데, 오늘 실측해 보니 남은 30%도 대부분 이미 있었습니다. @MX 태그가 코드에 1,808개 박혀 있고, 그중 168개는 코드에서 SPEC으로 가는 엣지예요. internal/mx에는 파서·해석기·LSP fan-in이 전부 구현돼 있고, Callsite 타입은 이미 JSON 직렬화 태그를 달고 있습니다.

2. @MX가 그래프의 앵커인 이유

온톨로지의 최대 위험은 "낡은 엣지가 자신 있게 틀린 답을 낸다"입니다. 7/29 문서도 §위험에 "거짓 엣지 전파"로 적어뒀어요. 그런데 @MX는 이 위험이 구조적으로 없습니다.

외부 그래프@MX 태그
저장 위치edges.jsonl 등 별도 파일코드 주석 안
파일이 옮겨지면엣지가 끊어짐따라 이동
함수가 리팩터링되면경로가 어긋남같이 수정됨
갱신 주체별도 재생성 필요코드 편집자가 자연히
리뷰에 보이나안 보임diff에 그대로
★

그래서 외부 그래프가 흔들려도 @MX에서 다시 맞출 수 있습니다. 태그 이름이 @MX:ANCHOR인 게 우연이 아닌 것 같아요.

이것이 Tier 0에 @MX를 먼저 얹는 이유입니다 — 가장 안 썩는 층부터 깔고, 잘 썩는 층(코드 구조 엣지)은 그 위에 재생성 가능한 파생물로 둡니다.

3. codemaps는 생산자입니다

"codemaps를 온톨로지 기반으로 재구축하면 낫나"는 방향이 반대예요. codemaps는 그래프를 소비하는 게 아니라 생산합니다.

이미 이렇게 내고 있어요 — --format json, go list -deps -json + go doc, 그리고 문서에 적힌 "Dependency adjacency list (who imports whom)".

바꿀 게 아니라 버리지 않는 것이 답입니다. 다만 codemaps가 소비자도 되면 이득이 둘 생겨요:

  • 증분 갱신 — 전체 go list -deps 재계산 대신 바뀐 부분만
  • @MX 속성 얹기 — "이 모듈의 WARN 개수", "DEBT가 어디 몰려 있나"
4. 가능해지는 질의 — 지금은 못 하는 것들
# 요구사항에서 코드로
"REQ-X를 구현한 코드는?"       → SPEC ← @MX:SPEC 역방향 → 심볼

# 코드에서 요구사항으로 (임팩트 분석)
"이 함수 고치면 어느 SPEC이?"  → 심볼 → fan_in → @MX:SPEC → SPEC

# 부채 상환 우선순위 자동 도출
"@MX:DEBT 중 fan_in 높은 것"   → 영향 큰 부채부터

# 미연결 탐지
"코드 참조가 0인 SPEC"         → 관계를 확인할 수 없는 SPEC 목록
⚠

마지막 질의의 결과를 오독하면 안 됩니다. 실측하니 디스크의 SPEC 디렉터리가 626개인데 @MX:SPEC이 참조하는 고유 SPEC은 39개였어요.

이걸 "94%가 미구현"으로 읽으면 틀립니다. 626개 중 대부분은 문서·규칙·하네스 변경 SPEC이라 코드가 없는 게 정상이고, 완료돼 아카이브된 것도 많아요.

정확한 서술은 이겁니다 — "코드→SPEC 엣지가 39개뿐이라 나머지는 관계를 기계적으로 확인할 수 없다." 미구현이 아니라 미연결입니다. 산출물에도 이 문구를 넣어야 커버리지 수치가 없는 결함으로 둔갑하지 않습니다.

5. v3.1.1 범위
M1

edges.jsonl writer

codemaps json + @MX 추출 + SPEC depends_on을 한 파일로 씁니다. 추출기 3종이 전부 기존 코드라 신규는 writer 하나뿐이에요.

형식은 한 줄 = 엣지 하나. 서버 0 · DB 0 · cgo 0이고 git이 diff를 낼 수 있습니다 — 이게 이 형식을 고른 이유예요. 성능이 아니라 운영 비용입니다.

신규 writer 1추출기 기존git diff 가능
M2

순수 Go BFS reader

find_callers / blast_radius를 ~50줄로 노출합니다. 7/29 문서가 권한 Tier 0 그대로예요.

에이전트가 이 파일을 직접 읽으므로 매번 go list -deps를 돌릴 필요가 없고, 그만큼 토큰이 줄어듭니다.

~50줄읽기 전용토큰 절감

CLI 표면 — 선택지 둘 (run 단계 판단)

7. 리스크

마감 라운드에 신규 기능 높음

v3.1.1은 마감 중입니다. 신규 기능은 회귀 위험을 새로 만들어요.

완화 — 신규 코드가 writer + reader 둘뿐이고 기존 경로를 건드리지 않습니다. 읽기 전용 산출물이라 회귀 표면이 좁아요. 그래도 v3.1.1 CI 전량 통과가 게이트입니다.

거짓 엣지 전파 높음

틀린 관계 하나가 멀티홉 질의로 증폭됩니다. 7/29 §위험이 이미 지적한 것이에요.

완화 — @MX를 앵커로. 외부 엣지는 스냅샷이 아니라 재생성 가능한 파생물로 유지해 언제든 다시 만들 수 있게 합니다.

엔티티 해석 오류 중간

과잉 병합(다른 걸 같다고) · 과소 병합(같은 걸 다르다고).

완화 — 심볼 식별자를 file:line:symbol로 고정하고 추론 병합을 금지합니다.

커버리지 수치 오독 중간

626 대 39가 "94% 미구현"으로 읽히면 없는 결함을 만듭니다.

완화 — 산출물에 "미연결 ≠ 미구현"을 명시하고, 이 수치를 결함 주장의 근거로 쓰지 않습니다.

과잉 엔지니어링 중간

Tier 0으로 충분한데 sqlite나 그래프 DB를 먼저 만드는 것.

완화 — Tier 0 고정. Tier 1(sqlite) · Tier 2(그래프DB)는 한계 도달 전 금지입니다.

LLM 생성 질의 쓰기 권한 낮음

모델이 만든 질의가 그래프를 수정하면 오염이 번집니다.

완화 — 금지. 읽기 전용 + 검증. 7/29 §위험의 조항을 그대로 승계합니다.
