moai-mcp로 Codex ↔ Claude 세션이
서로 통신할 수 있나?

TL;DR — 지금은 안 됩니다. 그리고 MCP 프로토콜만으로는 원리적으로도 안 됩니다. MCP는 한 클라이언트 ↔ 한 서버의 요청/응답 규약이지, 서로 다른 두 에이전트 사이의 메시지 중계를 정의하지 않아요. 현재 moai-mcp가 실제로 하는 일은 Claude → codex 단방향 위임 (codex_task·codex_audit)뿐이고, 그마저도 codex를 자식 프로세스로 새로 띄우는 방식이라 "이미 돌고 있는 codex 세션"에 말을 거는 게 아닙니다.

다만 공식 문서에 명시된 틈이 하나 있어요 — Claude Code의 세션별 inbox 소켓은 스크립트·훅이 직접 포스트할 수 있게 열려 있습니다. 여기에 도구를 하나 붙이면 codex → Claude 단방향 알림은 만들 수 있습니다. 현재 moai에는 그 배선이 0건입니다.

지금 실제로 오가는 것

먼저 용어 하나만 풀고 갈게요. MCP (Model Context Protocol)는 AI 도구에게 "쓸 수 있는 도구 목록"을 넘겨주는 규약이에요. 식당으로 치면 메뉴판입니다 — 손님(AI)이 메뉴를 보고 주문하면 주방(서버)이 만들어 내주는 구조죠. 메뉴판은 옆 테이블 손님에게 쪽지를 전달해 주지 않습니다. 이 한 문장이 이 보고서의 전부예요.

현재 moai mcp-server가 노출하는 도구는 17개이고, 그중 codex 계열은 5개입니다. 방향은 전부 한쪽입니다.

codex_job_status / _result / _cancel백그라운드 job 상태 조회·회수·취소Claude → codex

왜 안 되는지 — 6단계

각 항목을 눌러서 펼치면 근거가 나옵니다. 앞의 3개는 공식 문서, 뒤의 3개는 이 저장소에서 직접 확인한 값이에요.

1 MCP는 1:1 연결이다공식 스펙

MCP 공식 아키텍처 문서는 이렇게 씁니다 — 호스트(Claude Code 같은 AI 앱)는 서버마다 전용 클라이언트를 하나씩 만들고, 각 클라이언트는 전용 연결(dedicated connection)을 유지합니다.

그리고 결정적인 문장: "stdio 전송을 쓰는 로컬 MCP 서버는 통상 단일 클라이언트를 서빙한다" (Local MCP servers that use the STDIO transport typically serve a single MCP client).

즉 Claude가 붙은 moai 서버와 codex가 붙은 moai 서버는 같은 프로그램이지만 서로 다른 프로세스가 됩니다. 옆 테이블과 메뉴판을 공유하지 않는 거예요.

2 서버가 클라이언트에게 말 걸 수단이 거의 없다공식 스펙

MCP에서 서버가 제공하는 것은 tools · resources · prompts 3가지. 반대로 클라이언트가 제공하는 것은 현재 elicitation(사용자에게 추가 입력 요청) 하나뿐입니다.

예전에 있던 sampling(서버가 클라이언트의 LLM을 빌려 쓰기)과 logging은 프로토콜 버전 2026-07-28에서 deprecated 됐어요.

남은 elicitation조차 같은 연결 안에서 그 사용자에게 묻는 용도지, "다른 클라이언트에게 전달"이 아닙니다. 중계(relay) 프리미티브는 스펙에 아예 없습니다.

3 codex 스레드는 외부로 말을 걸 수 없다OpenAI 공식

codex의 app-server 문서를 확인했습니다. 두 가지가 명확해요.

(가) 클라이언트가 codex 프로세스를 소유합니다 — 외부 클라이언트가 spawns and owns 하는 구조라, 이미 실행 중인 codex 세션에 나중에 끼어드는 게 아닙니다. thread/start로 새 스레드를 열거나 thread/resume으로 기존 스레드를 다시 여는 것뿐이에요.

(나) 문서에는 codex 스레드가 codex 바깥의 에이전트나 세션에 메시지를 보내는 메커니즘이 없습니다. API는 thread/turn 관리와 도구 연동에 한정됩니다.

왜 중요하냐면: stdio 서버는 자기를 띄운 부모 프로세스하고만 파이프로 대화합니다. Claude가 띄운 moai 서버와 codex가 띄운 moai 서버는 메모리를 1바이트도 공유하지 않습니다. 상태를 나누려면 디스크(파일)를 거쳐야 하고, 그건 통신이 아니라 게시판에 메모 붙여놓기에 가깝습니다.

6 Claude Code의 메시징은 Claude Code 전용이다Anthropic 공식

Claude Code에는 세션끼리 대화하는 기능이 실제로 있습니다 — ListAgents로 찾고 SendMessage로 보냅니다 (v2.1.224+, macOS·Linux).

그런데 목록에 뜨는 대상이 문서에 못박혀 있어요: ① 이 세션 안의 서브에이전트 ② 같은 머신의 다른 Claude Code 세션 ③ 내 클라우드 세션 ④ Remote Control로 연결된 다른 머신의 세션.

codex는 이 목록의 어디에도 해당하지 않습니다. 발견 방식이 "Claude Code 세션이 디스크에 자기를 등록하고 inbox 소켓을 바인딩"하는 구조라, 그 등록을 하지 않는 프로그램은 애초에 보이지 않아요.

유일하게 열린 틈 — inbox 소켓

여기부터가 실제로 쓸모 있는 부분이에요. "안 된다"로 끝나지 않는 이유입니다.

Claude Code 공식 문서에는 세션의 inbox 소켓(inbox socket)을 설명하는 절이 따로 있고, 그 절의 도입부가 이렇게 시작합니다 — "스크립트나 훅이 세션에 포스트하게 하고 싶을 때 이 절을 읽으라". 즉 Claude가 아닌 프로그램이 Claude 세션에 메시지를 넣는 것을 공식적으로 상정하고 있습니다.

세션은 두 개의 환경변수를 내보냅니다:

환경변수내용
CLAUDE_CODE_MESSAGING_SOCKET그 세션의 inbox 소켓 경로 (/status의 Peer address 행에도 표시)
CLAUDE_CODE_MESSAGING_TOKEN세션별 토큰. 접속 첫 줄에 {"type":"auth","token":"…"}로 보냄

단, 자기 세션의 자식만 우대받습니다. 문서는 "own-child" 규칙을 둬서, 그 세션이 직접 낳은 프로세스(훅·Bash 명령)가 포스트한 메시지만 검증 후 바로 전달합니다.

그 밖에서 온 것은 일반 peer 메시지로 취급되어 수신 세션의 crossSessionInbound 설정(accept/hold/refuse)을 따릅니다. 기본값에서는 승인 대화상자가 뜰 수 있고, 5분(dialogExpiry) 내 응답이 없으면 버려집니다.

FAQ

그럼 지금 codex한테 일을 시키는 건 되는 건가요?

네, 그건 잘 됩니다. codex_task로 작업을 주고 결과를 받고, background: true로 오래 걸리는 일을 맡긴 뒤 codex_job_status로 진행을 볼 수 있어요.

resume_last: true를 주면 이 프로젝트에서 마지막으로 쓴 codex 스레드를 이어서 씁니다. 다만 "내가 다른 터미널에서 돌리고 있는 codex"에 접속하는 건 아닙니다 — moai가 기록해 둔 스레드 ID를 다시 여는 것이고, 프로세스는 새로 뜹니다.

codex를 MCP 서버로 만들어서 Claude에 붙이면 되지 않나요?

붙일 수는 있지만 질문의 답은 되지 않습니다. 그렇게 하면 Claude가 codex를 도구로 쓰는 구조가 되는데, 그건 지금 codex_task가 하는 일과 방향이 같아요 — 여전히 Claude → codex 단방향입니다.

참고로 OpenAI는 초기에 codex를 MCP 서버로 노출하는 실험을 했지만, MCP의 요청/응답 모델이 스트리밍 diff·승인 흐름·스레드 지속성·서버발 요청을 감당하지 못해 클라이언트 연결용으로는 app-server를 쓰도록 방향을 잡았습니다.

Claude 세션끼리는 되는데 왜 codex만 안 되나요?

발견(discovery) 방식 때문입니다. Claude Code 세션은 시작할 때 디스크의 파일에 자기를 등록하고 inbox 소켓을 바인딩합니다. ListAgents는 그 파일들을 읽어서 목록을 만들어요.

codex는 그 등록을 하지 않으니 존재 자체가 보이지 않습니다. 같은 이유로, 컨테이너 안의 세션과 호스트의 세션도 서로 못 봅니다 — 파일시스템이 다르니까요. (같은 컨테이너 안 두 세션끼리는 됩니다.)

메시지를 보낼 수 있게 되면 뭐가 위험한가요?

Claude Code 문서가 이미 선을 그어놨고, 그 선을 그대로 따르는 게 좋습니다:

① 메시지는 승인이 아니다 — 다른 세션에서 온 메시지는 권한 프롬프트에 대신 답할 수 없습니다. ② 설정을 못 바꾼다 — 다른 세션이 요청했다는 이유로 권한 설정이나 CLAUDE.md를 바꾸지 않습니다. ③ 슬래시 명령은 실행되지 않는다 — 텍스트로 도착할 뿐입니다. ④ 권한 프롬프트는 그대로 뜬다.

추가로 루프 방지도 들어 있어요 — 반복 메시지 rate limit, 짧은 시간 내 동일 메시지 폐기, 세션당 대기 50개 상한. 두 세션이 서로 메시지를 주고받는 무한 루프는 저절로 멈춥니다.

"통신"이라는 말을 어디까지 인정해야 하나요?

구분해서 보시는 게 좋아요. 세 가지가 전부 다릅니다.

위임(delegation) — A가 B를 도구로 불러 결과를 받는 것. 지금 되는 것.
공유 상태(shared state) — 둘 다 같은 파일을 읽고 쓰는 것. 경로 A로 가능.
메시징(messaging) — 상대가 지금 하던 일 중간에 끼어드는 것. 경로 B가 필요.

보통 "세션끼리 통신"이라고 할 때 기대하는 건 세 번째인데, 실제 업무에서 필요한 건 두 번째인 경우가 많습니다.

스스로 확인해 보려면 뭘 쳐보면 되나요?

네 가지를 직접 확인하실 수 있어요:

① Claude Code 세션에서 /list-agents (또는 /peers) — 목록에 codex가 없다는 걸 눈으로 확인.
② /status — Peer address 행에 이 세션의 소켓 경로가 보입니다.
③ grep -E '^\[mcp_servers' ~/.codex/config.toml — moai가 없음을 확인.
④ grep -n ServeStdio internal/cli/mcp_server.go — stdio 전용임을 확인.
