# GPT 게이트웨이 웨지 복구 안내 (운영자용)

> 대상: moai 런처의 GPT 게이트웨이 세션을 운영하는 운영자와 유지보수자.
> 근거: SPEC-GATEWAY-WEDGE-REROOT-001 (카드 t700), t672 실측 보고(`.moai/reports/t672/`).
> 이 문서는 운영자용 복구 절차다. 게이트웨이 400 응답 본문의 안내 문구는 변경되지 않으며, 복구 경로는 여기에만 문서화된다.

---

## 1. 웨지 클래스 (wedge class)란 무엇인가

GPT 게이트웨이 대화에서 **일시적 상류 장애**(HTTP 502, 마스크된 400 등)가 한 턴(turn)을 실패하게 만들면, 게이트웨이는 그 턴의 영수증(receipt) 후보를 발행(publish)하지 않는다. 그런데 클라이언트(호스팅된 Claude Code) 트랜스크립트에는 그 어시스턴트 턴이 **기록돼 있을 수 있다** — 스트림이 끊기기 전에 일부 내용을 이미 받았다면 더욱 그렇다.

이 상태를 **웨지(wedge)** 라고 부른다. 웨지가 생긴 대화는 이후 **모든 재생(replay)이 영수증 체인 검증에 실패해 400으로 거부**된다. 거부 자체는 정상 동작이다 — 게이트웨이의 역사 승인 계층이 발행된 적 없는 경계를 막는 것이다. 문제는 이 거부가 다른 체인 불일치와 구분 없이 표시됐다는 것이고, 긴 수명의 대화가 "새 대화를 시작하세요" 안내만으로 죽는 것이었다.

웨지의 형태는 **접미 꼬리 divergence**다: 트랜스크립트와 발행된 영수증 체인의 차이는 **맨 끝의 발행되지 않은 어시스턴트 경계**(및 그에 의존하는 tool_result) 하나뿐이고, 그 앞은 모두 진짜 발행 체인 접두어다.

## 2. 복구 절차 (recovery procedure)

웨지가 의심되는 대화 — 계속 400 chain 사유로 거부되는 대화 — 에 대해, 사용자가 **명시적으로** 런처 복구를 요청한다:

```bash
# 세션 id를 지정해 재뿌리(re-root) 후 이어서 진입
moai cc --resume <세션-UUID> --reroot
```

동작:

1. 런처가 대화 기록(conversation record)이 가리키는 네이티브 트랜스크립트에서 **마지막 어시스턴트 경계**(API 오류 표시 행은 경계로 세지 않는다)와, 그 경계의 tool_use에 묶인 **의존 tool_result 행**만 제거한다.
2. 일반 user 턴, 그 앞의 발행된 접두어, 터미널 API 오류 표시 행은 **전혀 손대지 않고 원래 순서대로 보존**된다.
3. 제거 직전에 두 파일이 트랜스크립트 옆에 생긴다:
   - `<트랜스크립트>.reroot.json` — 시도 표시(attempted 플래그 + 제거 원본의 preimage 다이제스트)
   - `<트랜스크립트>.reroot-aside.jsonl` — 제거된 행의 원본 그대로 보존 사본
4. 복구 후 평범한 `--resume` 이어서 진행되며, 재뿌리된 트랜스크립트는 게이트웨이가 이미 허용하던 꼬리 절단(tail-truncation) 형태라 **검증기가 그대로 받아들인다**.

게이트웨이 상태(영수증 저장소, 루트, 계보)는 **전혀 읽거나 쓰지 않는다** — 복구는 클라이언트 소유 내용만으로 이뤄지며, 수용 집합은 검증기 변경 없이 그대로다.

**자동 수술은 없다(REQ-WRR-005).** 400 거부가 와도 트랜스크립트는 절대 자동 수정되지 않는다. `--reroot` 요청이 있을 때만 복구가 실행된다. 체인 사유 분류만으로는 웨지 형태를 확정할 수 없기 때문에, 사람의 확인이 필요하다.

## 3. 단일 시도 한계 (single-shot bound)

웨지 사건 하나당 **재뿌리 시도는 정확히 한 번**이다. 첫 시도와 함께 기록되는 시도 표시는 트랜스크립트 옆 `.reroot.json`에 **영속적으로** 남으므로, 새 프로세스가 같은 기록을 읽어도 두 번째 제거는 일어나지 않는다. 시도 소진 후 다시 `--reroot`를 내면 아무 것도 제거되지 않고 고정 안내 문구만 돌아온다.

이 한계는 UX 편의가 아니라 **보안 성질**이다: "거부될 때까지 잘라내기" 반복은 발행 체인의 끝을 탐침하는 오라클이 된다. 두 번째 시도가 필요한 사건은 복구 대상이 아니며, 아래 5절의 비복구 형태다.

## 4. 비파괴 한계 (non-destructive bound)

제거된 내용은 **하드 삭제되지 않는다**. 트랜스크립트를 고치기 **전에** `.reroot-aside.jsonl`에 원본 그대로 보존되며(aside-before-replace), 언제든 참조·복원할 수 있다. 사용자가 부분 스트리밍된 내용을 보았을 수 있기 때문에, 복구가 데이터를 파괴하는 일은 없다.

## 5. 복구할 수 없는 형태 (non-recoverable shapes)

이 정책은 **끝에 붙은 발행되지 않은 경계** 형태만 복구한다. 다른 형태는 여전히 기존 사유 체인(chain / reasoning / lineage)으로 거부되며, 복구가 고칠 수 없다:

| 형태 | 결과 |
|---|---|
| 중간(역사 중앙) 경계 삭제, 머리/중간 편집 | 제거로 접두어 체인이 복구되지 않는다 — chain 사유 거부 유지 |
| 위조(forged)·외래 항목 | 네 갈래 결합(Prefix/Previous/Opaque/Items)이 어느 위치에서든 거부 |
| reasoning 봉투 제거(stripped) | reasoning 사유 거부 유지 |
| 계보 누락(lineage miss — 빈 루트 vs 빈 재생 아님) | lineage 사유 거부 유지 |
| **끝에 붙은 위조/제거된 경위** (웨지와 클라이언트 측에서 구분 불가) | 같은 단일 시도 절차로 **제거는 가능**하나, 제거된 내용은 **어떤 재생에도 다시 수용되지 않는다** — 남은 진짜 접두어만 수용된다. 사용자 확인(명시 요청)과 비파괴 보존이 이 구분 불가능성의 안전장치다 |

참고: 웨지의 꼬리 뒤에 일반 user 턴이 이어진 트랜스크립트는, 복구 후 네이티브 완료 게이트(complete 판정)가 이어서 진입을 거부할 수 있다. 이 경우 보존 사본으로 원본을 참조하고, 아래 6절의 fork 경로가 정식 대안이다.

## 6. 계보 누락의 정식 경로 — launcher fork

lineage 사유 거부("no recorded history exists for this session")의 유일한 정식 해결은 **런처가 주도하는 fork**다:

```bash
moai cc --resume <부모-세션-UUID> --fork-session
```

fork는 부모 영수증 저장소의 게이트웨이 자체 스냅샷으로 자식 루트를 만드는 **게이트웨이 상태 변경 복구의 유일하게 허용된 인스턴스**다(REQ-WRR-008의 다섯 조건을 모두 충족). 요청 메타데이터가 영수증 루트를 선택하거나 씨를 뿌리는 경로는 존재하지 않는다.

## 7. 요약

| 질문 | 답 |
|---|---|
| 언제 쓰나 | 계속 400 chain 거부되는 대화, 마지막 턴이 상류 장애로 실패했던 이력이 있을 때 |
| 무엇을 지우나 | 끝의 발행 안 된 어시스턴트 경계 + 그에 의존한 tool_result 뿐 |
| 몇 번까지 | 사건당 1회 (프로세스를 다시 시작해도 1회) |
| 데이터 손실 | 없음 — 보존 사본에 원본 유지 |
| 게이트웨이 영향 | 없음 — 영수증 상태 불변, 검증기 불변 |
| 자동 실행 | 안 됨 — `--reroot` 명시 요청에만 |
