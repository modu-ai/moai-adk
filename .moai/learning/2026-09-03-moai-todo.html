근거의 출처를 먼저 밝힙니다

이 노트는 지금 열려 있는 체크아웃의 소스를 근거로 쓰지 않았습니다. 그 체크아웃(main, 7ad9f8534)은 origin/develop보다 1547 커밋 뒤져 있어서, 여기서 설명하는 코드의 상당수가 아예 존재하지 않습니다.

그래서 대상을 둘로 고정했습니다 — ① origin/develop의 파일(git show origin/develop:<path>로 직독), ② 설치된 바이너리 v3.2.0-rc.0의 실제 동작(--help 및 실행 결과). 두 출처가 일치하는 사실만 적었습니다.

그리고 중요한 한 가지: SQLite 전환 커밋 18a2a6978은 git tag --contains가 공백을 반환합니다. 즉 아직 출시되지 않았습니다. 최신 태그는 v3.1.2이고, 이 기능은 릴리스 후보 바이너리에만 들어 있습니다.

01한 문장 요약

moai todo는 MoAI 칸반의 위임 채널입니다. 세션끼리 주고받는 메시지가 아니라, 디스크에 있는 단 하나의 큐가 "누가 무엇을 할 차례인지"를 결정합니다.

비유 · 병원 접수대

큰 병원을 떠올려 보세요. 진료실이 여러 개고 의사도 여럿입니다. 그런데 "다음 환자 누구죠?"를 의사끼리 말로 주고받는다면 어떻게 될까요. 한 명이 자리를 비우면 그 말은 사라집니다. 두 사람이 같은 환자를 부르기도 하고요.

그래서 병원은 접수대에 대기표를 쌓아둡니다. 의사가 바뀌어도, 퇴근했다 돌아와도, 대기표는 그 자리에 그대로 있습니다. 누가 몇 번을 불렀는지도 적혀 있고요.

moai todo가 정확히 그 접수대입니다. 그리고 대기표 한 장이 카드(card) — 이 문서에서 계속 나올 단어입니다.

02왜 필요했나 — 메시지로는 안 되는 이유

MoAI는 세션을 여러 개 띄워서 씁니다. 리드(lead) 세션 하나가 지휘하고, 레인(lane) 세션 여럿이 실제 작업을 하는 구조예요. 세션끼리 메시지를 보낼 수 있는 기능도 있습니다.

그런데 그 메시지에는 도착 보장이 없습니다. 플랫폼(윈도우 네이티브)에 따라 채널 자체가 없기도 하고, 특정 설정에서는 조용히 꺼지기도 합니다. 그리고 전달된 메시지는 주장이지 관측이 아닙니다 — "다 했어요"라는 말과 실제로 끝난 것은 다른 사실이니까요.

03카드의 일생 — 상태 4개와 되돌리기

카드 한 장은 언제나 네 가지 상태 중 하나에 있습니다. 그리고 모든 전이에 역방향이 있습니다 — 이게 이 설계에서 제일 마음에 드는 부분입니다.

stateDiagram-v2
  [*] --> queued : add
  queued --> picked : next <n>
  picked --> queued : unpick <n>
  queued --> dropped : drop <n> <reason>
  dropped --> queued : undrop <n>
  queued --> archived : done <n>
  picked --> archived : done <n>
  archived --> queued : undone <n>
  archived --> [*] : 영구 보존
상태뜻보이는 곳
queued대기 중. 운영자가 지명하기를 기다림기본 목록, next 후보
picked지명됨. 보드에 올라가 작업 중기본 목록, statusline
dropped버림. 사유와 함께 남아 있음list --dropped에서만
archived마감됨. 별도 테이블로 이동history에서만
설계 감상 · drop과 done은 다른 일이다

drop은 버린 카드를 사유와 함께 남깁니다. 텍스트 앞에 [DROPPED — 사유] 가 붙고, 기본 목록에서는 개수 한 줄 뒤로 숨습니다. done은 끝난 카드를 아카이브로 옮깁니다. 둘 다 삭제가 아니라서, undrop과 undone이 바이트 단위로 동일한 복원을 보장합니다.

undone은 카드만 되살리지 않고 그 카드를 지목하던 판정 기록(finding)도 함께 되살립니다. 기록만 잃는 복원은 "복원했다"고 말하면서 조용히 뭔가를 버리는 것이니까요.

카드를 바꾸는 동사 락 1회 쓰기

동사하는 일 · 안전장치
add <텍스트>카드 추가. --pick은 추가와 지명을 한 번의 락 쓰기로 처리, --force는 정확 중복을 강제 통과(강제했다는 사실이 기록됨)
next <n>지명. --spec <SPEC-ID>로 SPEC 부착, --expect <접두>로 엉뚱한 카드 지명 방지
unpick <n>지명 취소
done <n>마감(아카이브 이동). --expect, --require-landed (함정 2번 주의)
undone <n>마감 취소. id가 이미 다른 카드에 재발급됐으면 거부 — 한 id가 두 카드에 걸치는 게 원래 실수보다 나쁘니까
edit <n> <텍스트>텍스트만 교체. id·생성시각·상태·SPEC은 보존 — done 후 재추가와 달리 카드의 정체성이 안 바뀝니다
move <n>순서 이동. --top/--bottom/--before <m>/--after <m> 중 정확히 하나 필수 — 없거나 둘이면 추측하지 않고 에러
drop <n> <사유>버림. queued만 가능 — picked는 먼저 unpick. undrop이 못 되돌릴 것은 애초에 안 가져감
undrop <n>버림 취소. [DROPPED — …] 접두 제거. state가 권위라, 손으로 표시한 카드는 텍스트 그대로 복귀
export-json레거시 backlog.json 내보내기 — 다운그레이드 대비용. 마이그레이션 역행이 아니라 시점 복사본

기록만 하는 동사 카드 불변

동사하는 일
analyze큐 전체를 다시 분석해 판정 기록을 남김. 카드는 하나도 안 바뀝니다

--expect 가 왜 중요한가 (실제 예시)

카드 번호는 사람이 헷갈리기 쉽습니다. t450을 닫으려다 t405를 닫으면, 되돌릴 수는 있어도(undone) 그 사실을 알아채기까지가 문제죠.

# 그냥 닫기 — 잘못 눌러도 그대로 실행됨
moai todo done 450

# 카드 텍스트 앞부분을 함께 못 박기
moai todo done 450 --expect "[lane-10, t367"
# → 텍스트가 그 접두로 시작하지 않으면 거부. 파일은 손대지 않음

--expect는 done·edit·drop·undrop·next에 전부 있습니다. "내가 생각한 그 카드가 맞나"를 기계가 대신 확인해 주는 장치입니다.

한 단어 카드는 왜 add 를 명시해야 하나

moai todo는 모르는 첫 토큰을 만나면 두 갈래로 갑니다.

  • 한 단어(moai todo lst) → 에러 오타난 동사로 봅니다. 오타가 조용히 카드가 되면 안 되니까요.
  • 두 단어 이상(moai todo fix the flaky gate) → 카드 추가 문장으로 봅니다.

그래서 진짜로 한 단어 카드를 넣고 싶으면 moai todo add "리팩터링"처럼 동사를 명시해야 합니다. 오타를 시끄럽게 만드는 대가로 치르는 불편입니다.

거부되는 모양이 하나 더 있습니다: moai todo pick t151처럼 동사꼴 단어 + 카드 id는 폴스루하지 않고 에러가 납니다(알려진 동사 목록을 알려줍니다). 문장 중간에 id가 섞인 카드는 정상 추가됩니다.

05저장소 — 왜 JSON에서 SQLite로 갔나

예전에는 큐 전체가 JSON 파일 한 장이었습니다. 지금은 SQLite 데이터베이스 파일입니다.

비유 · 장부 한 권 vs 서랍장

JSON 한 장은 공책 한 권입니다. 한 줄을 고치려면 공책을 통째로 펴서 새로 옮겨 적어야 해요. 두 사람이 동시에 적으면 한 사람의 글씨가 통째로 사라집니다.

SQLite는 칸이 나뉜 서랍장입니다. 한 칸만 열어 고칠 수 있고, 자물쇠도 서랍장이 직접 관리합니다. 무엇보다 고치다 만 상태로 끝나지 않습니다 — 다 되거나, 아무것도 안 되거나 둘 중 하나예요.

엔진 설정 — 세 가지가 왜 그 값인가

설정값이유
journal modeWAL읽는 쪽이 쓰는 쪽을 막지 않게. statusline은 매 렌더마다 카운트를 읽는데, 그게 쓰기를 막으면 안 됩니다
busy_timeout5000ms 이상다른 프로세스가 쓰는 중이면 기다립니다. 곧바로 실패하면 레인이 헛되이 재시도하게 되니까
트랜잭션IMMEDIATE쓰기 잠금을 시작할 때 잡습니다. 중간에 승격하다 실패하는 경로를 아예 없앰
드라이버modernc.org/sqlite순수 Go 구현이라 CGO_ENABLED=0으로도 빌드됩니다 — 크로스 컴파일이 깨지지 않음

스키마 — 테이블 4개 + 메타

items             seq(위치) · id · text · added_at · spec_id · state
findings          subject_id · related_id · relation · source · score · note · at
archived_items    items와 같은 컬럼 + position
archived_findings archive_seq · position + findings 컬럼
meta              schema_version=1 · last_seq=475
주의 깊게 볼 점 · seq는 id 번호가 아니다

items.seq는 배열 위치이지 t475의 475가 아닙니다. move로 순서를 바꾸면 배열 순서와 id 순서가 갈라지는데, 저장해야 하는 계약은 배열 순서거든요. id의 무결성은 UNIQUE(id)와 meta.last_seq가 따로 지키므로 seq를 위치로 써도 안전합니다.

06큐가 하나인 이유 — 워크트리 해석

워크트리(worktree)는 같은 저장소를 여러 폴더에 동시에 펼쳐 두는 git 기능입니다. MoAI 레인은 각자 워크트리에서 일하죠. 그런데 .moai/state/는 gitignore돼 있어서 primary 체크아웃에만 존재합니다.

실제로 났던 사고 · 2026-08-17

primary에는 카드 30장이 있는데, 링크드 워크트리에서 moai todo를 부르면 "큐가 비었음"이 나왔습니다. 큐가 갈라진 겁니다 — 위임 채널이 두 개가 되면, 두 세션이 서로 다른 현실을 보게 됩니다.

07중복 분석기 — 거절은 딱 한 경우만

같은 카드를 두 번 넣는 일은 흔합니다. 그래서 add는 넣기 전에 기존 큐와 텍스트를 견줍니다.

판정조건결과
exact정규화 텍스트가 완전히 같음추가 거절 --force로만 통과
near토큰집합 Jaccard 유사도 0.80 이상기록만 추가는 됨
none그 아래그냥 추가
Jaccard 유사도 0.80이 무슨 뜻인가 (직접 계산해 보기)

토큰집합 Jaccard는 두 문장을 단어 집합으로 만든 뒤 겹치는 단어 수 ÷ 전체 단어 수로 계산합니다. 순서는 안 봅니다.

A = "pre-commit go vet 패키지 해석 오류"
B = "pre-commit go vet 패키지 해석 실패"

A의 단어집합 = {pre-commit, go, vet, 패키지, 해석, 오류}   (6개)
B의 단어집합 = {pre-commit, go, vet, 패키지, 해석, 실패}   (6개)

교집합 = {pre-commit, go, vet, 패키지, 해석}              (5개)
합집합 = 위 5개 + {오류, 실패}                            (7개)

Jaccard = 5 / 7 = 0.714  →  0.80 미만  →  none (기록조차 안 남음)

단어 하나만 달라도 0.80을 넘기려면 문장이 꽤 길어야 합니다. 임계값이 일부러 높게 잡힌 것이죠.

설계 결정 · 오차가 비대칭이다

임계값을 낮게 잡으면: 판정 기록이 카드보다 많아집니다 → 운영자가 목록을 안 읽게 됩니다 → 기능이 없느니만 못한 상태가 됩니다.

임계값을 높게 잡으면: 근사 중복 하나를 놓칩니다 → 그건 이 기능 도입 전과 똑같은 상태입니다. 손해가 아니라 제자리죠.

두 손해의 크기가 다르니, 높은 쪽으로 기울인 겁니다. 0.80은 그 판단의 결과입니다.

그리고 분석기는 '뜻'을 보지 않는다

분석기는 텍스트만 봅니다. 같은 뜻을 다른 말로 쓴 두 카드는 none이고, 이건 나중에 메꿀 구멍이 아닙니다. 이 계층의 오탐은 정당한 카드를 거절해서 운영자가 일을 잃게 만드니까요.

뜻을 판단하는 건 에이전트 계층(todo relate)의 몫이고, 거기서는 결과가 거절이 아니라 기록입니다. 사람이 읽고 판단할 자료로 남을 뿐, 아무것도 막지 않습니다.

08pr — 이미 누가 하고 있진 않나

카드를 배차하기 전에 물어야 할 게 있습니다: "이거 이미 PR 올라가 있지 않나? 이미 머지되지 않았나?" moai todo pr이 그 질문에 답합니다. 아무것도 쓰지 않습니다 — 카드도, 기록도, 캐시도, 락도.

결과뜻해석
linked열린 PR 하나가 이 카드 id를 담고 있음확신도 exact(PR 제목에서 읽음) / inferred(PR 본문 하나에서 읽음)
ambiguous여러 PR 본문이 담고 있음후보를 전부 나열하고 고르지 않음
landedorigin/main 이력이 이 카드를 지목주의: "무언가가 착지"이지 "마지막 단계가 착지"가 아님
no-link아무도 시작 안 함배차 가능
unknown질문 자체를 못 함(ref 없음·git 없음·질의 실패)not-landed의 증거가 아님

착지 검사는 로컬 git이라 gh(GitHub CLI)가 없어도 동작합니다. gh가 없거나 로그인 안 됐거나 오프라인이면 링크 열만 비고, 저하됐다는 사실은 stderr에 남으며, 종료 코드는 0을 유지합니다.

09운영자 경계 — 누가 무엇을 결정하나

여기가 이 기능의 정치입니다. 기술보다 중요할 수 있어요.

[HARD] 지명은 운영자의 행위다

리드 세션은 미리 고르지 않고, 추론한 우선순위로 재정렬하지 않고, "맨 위 것부터 시작" 같은 기본값을 붙이지 않습니다.

그리고 빈 큐는 정당한 상태입니다. 일을 발명하라는 신호가 아니라, 그냥 할 일이 없다는 사실이에요.

그럼 일괄 승인은?

가능합니다. 운영자가 카드 여러 장을 지목하거나 "순서대로 다 소진해"라고 말할 수 있어요. 그건 한 번에 몰아서 한 지명이지, 리드가 대신 고른 게 아닙니다. 다만 그게 주는 권한은 딱 그것뿐 — 카드 추가 권한도, 재정렬 권한도 아닙니다.

상시 발행원 — 딱 하나

상시 발행원(standing source)은 "매번 물어보지 말고, 끝나면 카드 하나 만들어 둬"라고 운영자가 미리 한 번 승인해 둔 워크플로입니다. 승인이 먼저인 건 그대로고, 바뀌는 건 언제 주느냐일 뿐입니다.

현재 /moai project 하나뿐이고, 다섯 조건이 전부 구속합니다.

  1. 실행당 1장. 문서당도, 기능당도, 발견당도 아님
  2. 파생이지 발명이 아님. 그 실행의 harness-spec.yaml에서 텍스트를 끌어옴 — 운영자가 인터뷰에서 한 말을 다시 적는 것. 끌어올 게 없으면 아무것도 안 만들고 그 사실을 보고
  3. 앞에 표시. [PROJECT] 접두 — 목록에서 "워크플로가 낸 카드"와 "사람이 친 카드"가 한눈에 구분됨
  4. 발행한 id를 보고. 완료 보고에 t<n>이 나옴 — 만들어진 즉시 보임
  5. 시작은 별도 지명. 카드는 queued로 들어갈 뿐, 작업이 시작되진 않음

TODO 주석, 열린 이슈, 감사 결과, 리포트 마일스톤 — 전부 발행원이 아닙니다. 운영자에게 보여주고, 운영자가 원할 때 카드를 요청합니다.

12함정 6가지

1. backlog.json을 큐로 읽는 것

정규 경로에 backlog.json이 있어도 그건 큐가 아닙니다. 낡은 export이거나 레거시 잔재이고, 내용은 임의로 오래됐을 수 있습니다. 이 저장소 실측: backlog.db는 9/3 21:00, backlog.json은 9/2 10:54 — 하루 이상 차이 납니다.

이 함정을 막는 방식이 인상적입니다. 그 파일을 쓴 범인을 끝내 특정하지 못했기 때문에, 청소로는 재발을 막을 수 없었어요. 그래서 읽는 쪽이 말하게 만들었습니다 — moai todo 계열 동사가 stderr에 한 줄 고지를 냅니다. 범인이 누구로 밝혀지든 통하는 방어입니다.

고지가 stderr인 것도 이유가 있습니다: stdout은 기계 표면이에요(--json을 foreman 루프가 읽습니다). 한 바이트도 달라지면 안 됩니다.

2. done의 착지 판정 기본값은 unknown이다

--require-landed를 주지 않으면 착지 질의를 아예 실행하지 않습니다. 그리고 모든 실행이 stdout에 한 줄을 찍습니다:

done t450 landing=landed|not-landed|unknown

플래그가 없으면 unknown입니다. "가드가 통과했다"와 "가드가 실행되지 않았다"는 다른 사실이고, 이제 같은 바이트로 나오지 않습니다. 이 구분이 없으면 "통과했다"고 착각한 채 카드를 닫게 됩니다.

그리고 --require-landed조차 한계가 명시돼 있습니다: "이 카드를 지목한 무언가가 그 ref에 착지했나"에 답할 뿐 "이 카드의 마지막 단계가 착지했나"에는 답하지 못합니다. run 커밋과 sync 커밋을 구분하지 못하거든요.

3. pr의 landed를 완료로 읽는 것

2번과 같은 뿌리입니다. landed는 "무언가가 착지"이지 "이 카드가 끝났다"가 아닙니다. 실제로 이 저장소의 t472 카드가 바로 이 문제를 다룹니다 — picked인데 이미 착지한 카드가 쌓이는데, 착지 판정이 원리상 불가능해서 정리가 안 되는 상황이요.

4. unknown을 not-landed로 읽는 것

unknown은 "질문을 하지 못했다"는 뜻입니다 — ref가 없거나, git이 없거나, 질의가 실패했거나. "착지하지 않았다"의 증거가 아닙니다.

이건 MoAI 전체를 관통하는 원칙의 한 사례입니다: 부재는 증거가 아니다. 실패 신호가 없다고 해서 검사가 통과한 것이 아니듯이요.

5. 한 단어 카드가 에러로 튕기는 것

moai todo 리팩터링 → 에러. 오타난 동사로 봅니다.
moai todo add "리팩터링" → 추가됨.

불편해 보이지만 의도된 거래입니다 — 오타를 시끄럽게 만드는 대가로 치르는 값이에요. moai todo lst가 조용히 "lst"라는 카드가 되는 쪽이 훨씬 나쁩니다.

6. moai todo pick t151 형태

동사꼴 단어 + 카드 id 조합은 폴스루하지 않고 에러가 납니다(알려진 동사 목록을 알려줍니다). pick은 없는 동사고(next가 맞습니다), 이걸 카드 텍스트로 받아들이면 오타가 큐에 쌓이니까요.

반면 문장 중간에 id가 섞인 카드는 정상 추가됩니다: moai todo t151 관련 회귀 테스트 추가 → 카드가 됩니다.

답을 보지 말고 먼저 스스로 답해 보세요. 막히는 문항이 있으면 그 장으로 돌아가시면 됩니다.

Q1. 리드가 레인에 보낸 메시지가 전달되지 않았습니다. 보드는 멈추나요?

멈추지 않습니다. 위임은 메시지가 아니라 디스크의 큐로 이루어지기 때문입니다. 메시지는 "새 카드 나왔어요" 하는 알림일 뿐이고, 레인은 큐를 직접 읽습니다. 그래서 2장 그림에서 점선(메시지)이 딱 하나뿐인 겁니다.

Q2. picked 상태의 카드를 drop하려 합니다. 어떻게 되나요? 왜 그렇게 설계됐을까요?

거부됩니다. drop은 queued에서만 가능하고, picked 카드는 먼저 unpick해야 합니다.

이유는 되돌리기 보장입니다 — undrop이 복원하는 상태는 queued인데, picked에서 바로 drop을 허용하면 undrop이 원래 상태로 못 돌려놓습니다. "undrop이 복원하지 못할 것은 애초에 가져가지 않는다"는 규칙이에요.

Q3. moai todo done 450을 실행했더니 landing=unknown이 나왔습니다. 이 카드는 착지하지 않은 건가요?

알 수 없습니다. --require-landed를 주지 않았으므로 착지 질의 자체가 실행되지 않았습니다. unknown은 "착지하지 않음"이 아니라 "묻지 않음"입니다.

이 구분이 왜 중요할까요? 같은 unknown 바이트가 "가드 통과"로 오독되면, 착지하지 않은 카드를 닫아 놓고 닫았다고 믿게 되기 때문입니다.

Q4. 근사 중복 임계값을 0.80에서 0.50으로 낮추면 무슨 일이 벌어질까요?

판정 기록이 카드보다 많아집니다. 관련 없는 카드끼리 계속 엮이고, 운영자는 목록을 읽지 않게 되고, 결국 기능이 없느니만 못한 상태가 됩니다.

반대 방향(놓치기)의 손해는 기능 도입 전과 같은 상태일 뿐이라 훨씬 가볍습니다. 오차가 비대칭이라 높은 쪽으로 기울인 겁니다.

Q5. 링크드 워크트리에서 moai todo를 실행하면 어느 큐를 보나요? 그렇게 만든 이유는?

primary 체크아웃의 큐를 봅니다. git common dir의 부모가 primary 루트인데, 그 값은 어느 워크트리에서 물어도 같기 때문입니다.

이유: .moai/state/는 gitignore돼서 primary에만 있고, 워크트리가 각자 큐를 가지면 위임 채널이 갈라집니다. 실제로 2026-08-17에 primary 30장 vs 워크트리 "비었음" 사고가 있었고, 이 해석은 그 사고의 결과물입니다.

Q6. workflow.todo.enabled: false로 두면 moai todo add가 동작하나요?

동작합니다. 이 플래그가 끄는 것은 가이던스 표면뿐입니다 — SessionStart 라인, statusline 세그먼트, 스킬의 자동 라우팅. 명령은 계속 등록되고 모든 동사가 정상 동작하며, 명시적 /moai todo도 실행됩니다.

플래그는 안내를 끄지 기능을 없애지 않습니다. 명시적 호출을 거부하거나 조용히 무시하는 건 의도된 동작이 아니라 결함입니다.

Q7. items.seq가 t475의 475가 아니라 배열 위치인 이유는?

move 때문입니다. 순서를 바꾸면 배열 순서와 id 순서가 갈라지는데, 저장해야 하는 계약은 배열 순서입니다(레거시 JSON이 보존하던 것이 그거였으니까요).

id의 무결성은 UNIQUE(id)와 meta.last_seq가 따로 지킵니다 — 둘 다 seq를 읽지 않으므로, seq를 위치로 써도 id는 안전합니다.
