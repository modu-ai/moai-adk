## §F Milestones

### M1 — the manifest schema and the state table (least reversible)

The two decisions worth the most review attention. Every later milestone reads them, and changing the table after 18 entries exist means re-deciding all of them.

- Define the manifest schema: **kind**, locator, expected events, window, measured quantity — **five fields** (REQ-GSM-002) — plus the release-cycle-conditional form (REQ-GSM-004). `kind` belongs in the schema-definition bullet, not only in the field-shipping bullet below: row 1 of the state table decides on it, so an entry missing it is undecidable and a four-field completeness check lets it reach the classifier.
- Fix the measured-quantity vocabulary at exactly three values with the conclusion set each admits (REQ-GSM-003).
- **Author the state table as the normative artifact** (REQ-GSM-006) — **8 rows, 7 values**, each value distinguishable on at least one observable axis, **and a `Flipped by` cell per row naming the delivering milestone and the M1 field it depends on** (every row, including rows whose dependency is inherited from a sibling branch — an under-declared cell is invisible to the delivery check).
- **Re-derive the enumeration rather than reviewing the table.** Walk the two inputs (manifest entries; disk enumeration) through their binary splits per REQ-GSM-006's stated method and compare the result against the rows. This is not a formality, and it has now paid **three times**. At v0.2.0 it found the deleted-subject condition the table had missed, and that condition produced a **wrong value** rather than an empty cell. At **v0.6.0 it found a precedence defect with the table already complete**: an entry whose subject is gone *and* whose query errored satisfies both row 8 and row 2, and the split order as written decided it row 2 — a permanently non-retryable case handed a "retry" action, the same two-states-one-label shape row 8 exists to close, surviving in the branch the v0.4.0 carve-out did not reach. Closed by leading the entry axis with the disk check and widening the carve-out to every query outcome; **no row and no value were added.** At **v0.8.0 it paid a third time, one branch lower**: the axis tested *are there qualifying runs?* before it tested whether the entry's own declared condition excuses their absence, so a **correctly-quiet subject with an aged run still visible** — `release.yml` between releases, an entry AC-GSM-004 mandates — satisfied row 4 and classified `STALE`. Again a wrong value rather than an empty cell, again invisible to a totality proof over rows, and this time **retention chose the label**: the same state read `STALE` while the aged run was visible and `OK` once retention consumed it. Closed by asking *is there a qualifying run **inside the window**?* and placing the declared-condition test as a single node immediately after it, ahead of the aged-versus-absent distinction; **again no row and no value were added**, and the M1 dependency cells of rows 4, 5 and 6 were corrected to declare all three fields their decisions now read. Check totality in **three** directions before populating the census: every row maps to exactly one value, every value is reachable from at least one row (REQ-GSM-007), and — the direction the v0.6.0 finding lives on — **every entry reaches exactly one row**, which is decided by the split order rather than by the rows. A complete table read in the wrong order is still wrong. An uncovered condition must appear as a missing row, never as a sentence.
- **Ship the three M1 fields the table's rows depend on**, and check them against the table rather than against a flip-list count: the `kind` field (row 1), the window field plus the measured-quantity value (rows 3 and 4), and the release-cycle-conditional field (rows 5 **and 6** — they are the two branches of one test and depend on the same field). **A missing dependency here does not leave a cell empty — it makes the cell produce the wrong value.** Row 5 without its conditional field silently becomes row 6, and every correctly-quiet release-only subject is reported as an anomaly on every sweep. Rows 2, 7 and 8 declare no M1 field: they depend on M2's query path and disk enumeration, which is why their cells name M2 alone rather than under-declaring.
- Apply the subject-agnostic shape test: each entry carries kind, locator and cadence as data. If accepting a second-kind entry requires changing the schema or either vocabulary, the schema has hardcoded its subject — reshape it now (B-0's sibling failure mode).
- Choose the manifest path outside `.moai/config/` (B-5).
- Populate the census: one entry per workflow file, 18 of 18, including the two release-only subjects.

### M2 — the classifier

- Query per subject; never a repository-global listing (REQ-GSM-005).
- Decide every entry by the table (REQ-GSM-006). The classifier is table-driven, so the **8**-row fixture in AC-GSM-007 *(read "7-row" until v0.7.0 — the pre-`ORPHANED` figure, a transcribed count that survived the v0.4.0 row addition and both later sweeps; derive it, `grep -c '^  | [0-9] |' spec.md` → 8)* is a direct test of the artifact rather than of a paraphrase of it.
- Row 2 — a query that did not return classifies `UNRESOLVED`, never `UNKNOWN` (B-1).
- Rows 4, 5 and 6 — **the declared condition is consulted before the aged-versus-absent distinction, not after it.** Build the branch in the table's order: *a qualifying run inside the window?* → row 3; otherwise *does the declared condition excuse the absence?* → row 5; otherwise *any qualifying runs at all?* → row 4 or row 6. Building it the other way round — window first, declared condition only on the zero-run branch — is the v0.8.0 defect, and it classifies every correctly-quiet release-only subject `STALE` for as long as its last run stays inside `gh run list` retention, then flips it to `OK` when retention consumes it. Rows 5 and 6 remain the two branches of one test on identical observable input; row 4 is now the third.
- **Run the enumeration-integrity check before the entry axis, and suppress row 8 when it fails** (REQ-GSM-010, REQ-GSM-006). Build it in this order or the leading disk split reads an input nothing has checked: enumerate; then, for every declared disk-enumerable entry **absent from the enumeration**, run a **direct existence test of that entry's own locator** — a per-subject point test, not a second call to the same enumeration, or it inherits the same defect; if any such subject is **present**, or the enumeration returned zero files, the enumeration **fails integrity**, no entry classifies `ORPHANED`, and the result is refused its all-clear on the integrity failure. On a passing enumeration the point test is what distinguishes a genuinely deleted subject (absent under the point test → row 8 stands) from one the enumeration missed. **This adds no M1 field** — the locator is REQ-GSM-002's second field.
- Rows 7 and 8 — the set comparison against disk enumeration, **in both directions** (REQ-GSM-008), row 8 evaluated **behind the integrity gate above**. The entry→disk direction is the one that was missing: run history outlives a deleted workflow, so without it a declared entry whose subject is gone is decided by stale history into `STALE` or a false `OK`.
- Refuse an all-clear when the queried count is zero, **or** the enumeration fails the integrity check above (REQ-GSM-010, B-2). A zero-check alone passes a partial enumeration — 3 of 18 files is non-zero, produces no `UNDECLARED` for the 15 unseen, and reports all-clear about the wrong set. **Do not implement the tolerance as a count of the evaluator's own findings**, which is what v0.8.0 specified and what v0.9.0 removed: an entry missing from the enumeration is exactly what produces an `ORPHANED` finding, so a *declared − enumerated beyond `UNDECLARED` + `ORPHANED`* term is identically zero for every partial enumeration and can never fire. The corroborating point test is a second, independent observation and is what makes the comparison bite.

- Fold every classification to the three-value surface vocabulary per the table's `Surface fold` column; **never emit `fail`** (REQ-GSM-013). The boundary is `UNREADABLE` → `ok` (meaningless — the comparison never applied) versus `UNKNOWN`/`UNRESOLVED` → `warn` (incomplete — it applied and could not finish). Adopting card t326's leniency wholesale, folding all uncertainty to `ok`, reproduces this card's own subject inside its solution.

### M3 — the result and its contract

**Rewritten at v0.6.0 against the landed consumer (B-9).** Until t333 closed, M3's job was to emit a result *conforming to a paragraph*. It is now to satisfy a **compiled interface with tests behind it**, which makes every clause below decidable by the compiler or by an existing test rather than by reading §B — and which adds one deliverable M3 previously did not have: replacing the stub.

- **Implement `guardliveness.Producer`.** The signature is fixed: `Produce(ctx context.Context, act Activation) (Result, error)`, in `internal/guardliveness/evaluator.go`. `Activation` carries exactly one field, `Root` — no changed-file list, no subject hint, and nothing that could be read as a reason to skip. The producer receives no prior result, and that is load-bearing (see the third-input bound below).
- **Emit `guardliveness.Result` in its carried shape** (`internal/guardliveness/contract.go`): `Entries []Entry` and `Clean *Designation`. Per entry, `Classifications` holds **exactly one** value and `Subject` names what was evaluated. `Clean.Values` holds **exactly one** value — that is REQ-GSM-012's designator obligation discharged concretely, and the three shapes it forbids are already named on the consuming side (`ErrDesignationAbsent`, `ErrDesignationNull`, `ErrDesignationMultiValued`), with `ErrEntryClassificationCount` for the per-entry clause. A result that trips any of them is refused by `Partition` with a nil set rather than an empty one, so the failure is loud instead of an all-clear.
- **Survive the JSON round trip.** `store.go` persists the result between the refresh that produced it and the **later** activation that renders it, so the shape must serialize and deserialize unchanged. A field that round-trips wrongly arrives at the consumer as a contract violation that never happened — the tags on `Entry`, `Designation` and `Result` are load-bearing, not decorative. Verify by save-then-load, not by inspecting the in-memory struct.
- **Carry `Entry.Surface`, and do not expect anyone to read it.** The fold (REQ-GSM-013) is emitted for the operator and for this SPEC's own internal-versus-surface contract. The consumer **deliberately never consults it** — measured on `52c3fe590`: `.Surface` has zero non-test reads across `internal/guardliveness/` and `internal/hook/` — because more than one classification folds to the clean surface value while only one classification is clean, so a partition read from the fold would treat `UNREADABLE` as nothing-to-report. Emitting the field is required; relying on it being read is a seam violation.
- **Replace the stub at its single wiring site.** `internal/hook/session_start_guard_liveness.go:38` currently reads `var guardLivenessProducer guardliveness.Producer = guardliveness.Unwired()`. M3 names this producer there instead. `Unwired()` is a producer rather than a nil check on purpose — a nil check would put a branch short of the query layer and make the production path conditional on the seam existing, which is the absent-execution shape this whole family is about. **Do not replace it with a conditional wiring.** The pre-flight measurement in §C establishes that this is the only production site.
- **Carry the missed expectation on every row-4 `STALE` entry** (REQ-GSM-006 row 4, verified by AC-GSM-007 (d)). The entry carries the manifest entry's **declared window** and **declared measured quantity**, copied rather than described, so the values compare equal field-against-field. **This obliges an additive field on `guardliveness.Entry`**, which today has three — `Subject`, `Classifications`, `Surface` — and no place for an expectation. The addition names no classification value, so §B's invariant survives it; its JSON tag is load-bearing for the same store round trip the rest of the shape is, so verify by save-then-load. It is a **cross-SPEC write**, the second M3 carries: record it beside the stub replacement rather than discovering it at implementation time. **Carrying is the whole obligation here** — the consumer's render prints `Subject` alone, so the field arrives and is dropped; making it visible is the sibling's render and out of scope (`spec.md` §D, residual in `acceptance.md` §D.7).
- Emit the measurement timestamp and the count set, with **each count traced to a consumer** (REQ-GSM-009, B-4).

**The third input, checked and bounded rather than assumed away.** REQ-GSM-006's totality claim is bounded at two inputs (manifest, disk enumeration), and §D.7 warns that a third would open conditions the derivation cannot reach. The store's persisted-result round trip and the *"the advisory may be one activation stale"* property are the obvious candidates, so both were checked on `52c3fe590`. **Neither is a third input to classification.** `Activation` has exactly one field and the producer receives no prior result, so nothing persisted can reach a classification decision; the prior result is read by the **render** — to lead with what changed (the sibling's REQ-GDL-007) and to state the measurement's age (REQ-GDL-006) — which is surfacing, and out of scope here (`spec.md` §D). **Milestone map check — deliberately not a union count, and deliberately not a transcribed number.** The check is stated as a **derivation**: *every `### AC-GSM-` heading in `acceptance.md` appears in some flip list below*, **and** each listed milestone can actually deliver what it is assigned. A transcribed count is what went stale here once — this section read "All 15 criteria" while `acceptance.md` carried 16, so the sentence auditing the map was itself wrong, which is worse than the reverse because this sentence is the SPEC's own guard against that failure. The second half is the one that matters: a union count answers "is every criterion listed?" and is structurally blind to "can that milestone deliver it?", which is exactly how T4 escaped the predecessor's repair — every criterion was listed, and one sat at a milestone whose own vocabulary did not yet contain the value it required.

Three criteria are clause-split because they genuinely span milestones, and splitting them is what keeps the map honest rather than merely complete: AC-GSM-003 and AC-GSM-005 have schema halves at M1 and classifier halves at M2; **AC-GSM-007 spans all three** — its delivery clause (c) is checked at M1 against the schema, its classification clauses (a)(b) land at M2, and its carried-expectation clause (d), added at v0.7.0, lands at **M3**, because the carrier is the emitted result shape rather than the classification. A three-milestone split is not an irregularity to tidy: the three clauses ask three different questions, and collapsing them onto one milestone is precisely the assignment error the column exists to catch. The state table's own `Flipped by` column is the artifact this check reads — it is the only place the per-cell answer lives.

## §G Anti-patterns to avoid

- **Adding a classification rule as a sentence instead of a row.** B-0. The table is normative; prose that extends it silently recreates the uncovered-condition failure.
- **Reusing `UNKNOWN` as a general "could not determine" bucket.** Its implied action is *look again with a longer window*, which is wrong advice for an auth failure and meaningless for a kind with no reader. Two states with different implied actions under one label is the defect that produced this SPEC.
- **Guarding the query side and not the disk side.** B-2. `UNDECLARED: 0` is indistinguishable between a complete census and an enumeration that found nothing.
- **Building the classifier to read outcomes only.** "For each manifest entry, fetch its runs and judge them" is accurate about the entries it holds and silent about the files it does not. The set comparison is not an add-on to that loop — it is what makes the loop's green informative.
- **Carrying a count nothing consumes.** B-4.
- **Writing an expectation whose one number measures two events.** "Fires every N days" awards full marks to a guard that runs faithfully and catches nothing.
- **Designating a second clean value.** It would break the sibling SPEC's contract silently: every criterion there would still pass while its advisory under-fired (AC-GSM-015).
- **Mirroring the manifest into the template tree.** B-6.
