## §A Context and Problem

### A.1 Where this SPEC came from, and why the split ran along this seam

`SPEC-GUARD-LIVENESS-001` asks *when did this guard last fire, and was it supposed to have fired by now?* Three audit iterations converged on the surfacing half of that question and never converged on this half. The auditor's own accounting:

- The **surfacing model** converged — both prior mutants were re-run at iter-3 and neither could be revived.
- The **state model** did not. D2, D5, N2, T2 and T4 are one family, and each repair relocated the defect rather than closing it: narrowing `UNKNOWN`'s meaning left the excluded state with nowhere to go; adding a fifth value to receive it left a sixth state uncovered; declaring the set closed in one requirement while another routed entries into it produced a contradiction between two requirements over the very classification the trigger is defined on.

The lesson the auditor drew, and this SPEC adopts as its authoring method: **prose is what let a five-value vocabulary cover at least six states without anyone noticing.** A sentence defining a classification reads complete in isolation. Only a table, with one row per condition the mechanism can encounter, makes an uncovered condition visible as an empty cell.

### A.2 The defect this whole family exists to catch

*Absent execution is not suppressed failure.* Nothing runs, so nothing can go red, and a mechanism reports success accurately about a set that had silently become the wrong set. An exit code of zero means *everything selected passed*; it does not mean *everything that should have passed, passed*. **Green is accurate and uninformative at the same time.**

The empirical instances grounding this — a deployment lag that made a landed fix never run, two guards whose `pull_request` trigger stopped matching after the git-flow transition, a default run listing that hides low-frequency guards, a guard that fires and does nothing, and a `-run` selector naming two tests that did not exist — are recorded in `SPEC-GUARD-LIVENESS-001` §A.2 through §A.7 and in `.moai/reports/t333/trigger-axis-observation.md`. They are not restated here; this SPEC's job is the mechanism, and the mechanism's correctness condition is that **it must not reproduce the defect at its own layer**.

### A.3 The three findings inherited as starting material

These arrive unresolved from the parent SPEC's iter-3 audit. They are the work, not the background.

- **T2 — a failed forge query has no admissible classification.** Two requirements disagreed about the extent of the "could not interpret" value: one routed *every* non-retention failure into it, the other defined it as *kind has no reader* only. A workflow entry whose query **errors** — the single most likely degraded run in production — fell in the gap between those two sentences, and the acceptance criteria assumed a classification the requirements forbade. Resolved here by the state table: the error case is its own row with its own value (§C.2, row 2).
- **N2's unresolved half.** The fifth value repaired the no-reader hole and left the more common one open. The state table is the structural fix — a hole is now an empty cell rather than a sentence nobody wrote.
- **T4 — the plan's own vocabulary went stale under a repair.** The five-value closed set landed in the requirement layer and never reached the plan's milestone body, and a criterion was scheduled at a milestone that could not deliver it. Addressed here by making the table the single artifact both layers cite (§C.2) and by clause-splitting criteria across milestones where they genuinely split (`plan.md` §F).

### A.4 The correctness condition this SPEC must meet at its own layer

An evaluator that reads outcomes only for entries its manifest already lists **is** the defect: accurate about what it examined, silent about what it never examined. Two requirements exist for that reason and are load-bearing rather than housekeeping — REQ-GSM-008 compares the manifest against the disk enumeration, and REQ-GSM-010 refuses an all-clear when either input to that comparison came back empty. The audit found the query side guarded and the disk side not (T1); both are guarded here.

## §B The published contract

`SPEC-GUARD-LIVENESS-001` consumes exactly three clauses from this SPEC, and nothing else:

> every entry in an evaluation result carries exactly one classification; exactly one value of that vocabulary means *nothing to report* (the **clean** value); the advisory fires on any other.

REQ-GSM-012 is this SPEC's obligation to hold up that contract. The consuming SPEC does not name the vocabulary, does not know how many values it has, and does not decide any entry — so **this SPEC may add, rename, or re-decide classifications freely, provided exactly one clean value continues to exist.** That is the whole coupling, and it is why the two SPECs are independently implementable rather than one blocking the other.

The asymmetry is worth stating plainly: the consuming SPEC can verify that its own trigger uses the clean/non-clean partition, but it cannot verify that exactly one clean value exists. That half of the contract is verified here, by AC-GSM-015.

### B.1 The contract has a landed consuming implementation, and it is compiled rather than prose

**Measured on `52c3fe590`, this tree, this run.** Card t333 closed (`status: completed`), so the three clauses above are no longer only a paragraph the two SPECs agree on — they are a Go interface with tests behind it, and this SPEC's deliverable is now written **against a fixed signature** rather than against a description of one.

What exists, by file:

| Surface | File | What it fixes |
|---|---|---|
| `Producer` interface — `Produce(ctx context.Context, act Activation) (Result, error)` | `internal/guardliveness/evaluator.go` | the seam itself: this SPEC's deliverable is a `Producer` implementation and nothing else |
| `Entry` / `Designation` / `Result`, all JSON-tagged | `internal/guardliveness/contract.go` | the result's carried shape, clause by clause |
| JSON persistence round trip | `internal/guardliveness/store.go` | the result travels from the refresh that produced it to a **later** activation that renders it, so the shape must survive serialization |
| `Unwired()` and its single wiring site | `internal/guardliveness/evaluator.go`; `internal/hook/session_start_guard_liveness.go:38` | the stub standing in until this deliverable lands — the one line M3 replaces |

**REQ-GSM-012's designator obligation is now discharged concretely.** The abstract requirement — *the result shall carry a machine-readable designation of which value is clean* — has one satisfying shape on this tree: `Result.Clean` is a `*Designation` whose `Values` slice holds **exactly one** value. The consumer's `Partition` refuses the other three shapes by name (`ErrDesignationAbsent`, `ErrDesignationNull`, `ErrDesignationMultiValued`), which is the consuming half of REQ-GSM-012's symmetric obligation made mechanical. `Entry.Classifications` is a slice for the same reason: a violation of the exactly-one clause must be *representable* so it can be refused, and `ErrEntryClassificationCount` is the refusal.

**The vocabulary is still not named there, and that is measurable rather than asserted.** A value-token grep over the consuming package returns nothing:

```
$ grep -rnE '\b(STALE|UNDECLARED|UNREADABLE|UNRESOLVED|ORPHANED)\b' internal/guardliveness/ internal/hook/session_start_guard_liveness.go
$ echo $?
1
```

So this SPEC retains the freedom §B claims: it may add, rename, or re-decide classifications without touching a line of the consumer, provided exactly one clean value continues to exist.

**`Entry.Surface` is carried and deliberately never consulted, and this SPEC must not read that as a second partition channel.** The consumer's own comment says why — more than one classification folds to the clean *surface* value while only one classification is clean (`UNREADABLE` folds to `ok`; only `OK` is clean), so a partition taken from the fold treats every entry in that gap as nothing-to-report. Measured: `.Surface` has **zero** non-test reads across `internal/guardliveness/` and `internal/hook/` (`grep -rn '\.Surface' … | grep -v _test.go` → rc=1). The fold (REQ-GSM-013) is therefore emitted for the operator and for this SPEC's own internal-versus-surface contract, **not** for the consumer's partition — and a future change that made the consumer read it would be a seam violation, not an optimization.

## §C Requirements (GEARS)

Budget: Tier M ≤ 16 requirements. **Count: 13.**

### C.1 The manifest — where firing expectations are written

- **REQ-GSM-001** — The system shall carry a guard-liveness manifest declaring one expectation entry per workflow file under `.github/workflows/`. The manifest shall live outside `.moai/config/`, because `moai update` deletes that root wholesale and a manifest lost on update is a liveness record that itself silently stops. The manifest shall hold its watched set as **data** — each entry carrying its kind, its locator, and its expected cadence — and shall not be shaped so that only a forge workflow can occupy an entry.
- **REQ-GSM-002** — Each manifest entry shall carry **five** fields: the subject's **kind**, its locator, the triggering event or events under which firing is expected, an expectation window, and exactly one measured quantity. `kind` is listed here rather than only in REQ-GSM-001's data-shape clause because row 1 of the state table decides on it: an entry missing `kind` is undecidable, and a field-completeness check that omits it lets such an entry through.
- **REQ-GSM-003** — The measured-quantity vocabulary shall be exactly `fired-at-all`, `fired-with-effect`, and `verdict-rendered`, where `fired-with-effect` excludes runs whose conclusion is `skipped` or `cancelled`, and `verdict-rendered` additionally requires a terminal `success` or `failure`. Each entry shall name exactly one, and **no entry shall be written whose single number is asked to measure both whether a guard fired and whether a firing caught anything** — these are different axes, and a guard that runs faithfully and catches nothing scores full marks on the first.
- **REQ-GSM-004** — Where a subject is legitimately expected to be quiet outside a release cycle, its entry shall declare that condition explicitly rather than being omitted, so "correctly quiet" is a recorded expectation rather than an absence a reader must infer.

### C.2 The state table — the normative classification artifact

- **REQ-GSM-005** — When the evaluator runs, it shall query run history **per subject**, and shall not derive any subject's last-fired time from a repository-global run listing. The global listing is measurably incapable of answering the question for a low-frequency subject, and its incapacity is invisible from inside it.

- **REQ-GSM-006** — The evaluator shall decide every entry it encounters by the **state table below, which is normative**. The table is the artifact; the prose around it describes it and does not extend it.

  **How the enumeration was derived, so a reader can re-run it rather than trust the table.** The mechanism has exactly two inputs — a manifest of declared entries, and a disk enumeration of workflow files — so the condition space is the product of two axes, and each axis is partitioned by successive binary splits until every branch terminates:

  - **Entry axis** (a declared manifest entry), evaluated **only on an enumeration that has passed REQ-GSM-010's integrity check**: **is the entry's kind disk-enumerable, its named subject absent from the disk enumeration, and that absence corroborated by a direct existence test of the entry's own locator?** (yes → row 8) · does its kind have a reader? (no → row 1) · did the query return a result? (no → row 2) · **is there a qualifying run inside the expectation window?** (yes → row 3) · (no) **does the entry's declared condition excuse the absence?** (yes → row 5) · (no) are there qualifying runs at all? (yes → row 4 · no → row 6).
  - **Disk axis** (a workflow file on disk): does a manifest entry name it? (no → row 7) · (yes → routes to the entry axis).

  Each split is exhaustive over its branch, so the table is total **over these two inputs**. That is a bounded claim and §D.7 records its bound: a third input would open conditions this derivation cannot reach.

  **The enumeration-integrity check is a gate on the derivation, not a ninth row — it runs before the entry axis, and a failed check suppresses row 8 rather than being tolerated by it.** The entry axis's leading split reads the disk enumeration, so it inherits whatever that enumeration got wrong; REQ-GSM-010's integrity check is therefore evaluated **first, over the enumeration as a whole**, and only a passing enumeration is admitted as the split's input. On a failed check the leading split is **suppressed for every entry** — no entry classifies `ORPHANED` — and the result is refused an all-clear on the integrity failure itself. The two consequences are deliberately asymmetric, because the two directions fail differently: row 8 emits *destructive* advice (delete the entry) on a subject that is in fact present, so it is suppressed; row 7 merely emits *fewer* findings, and every finding it does emit is still sound — a file it names is genuinely on disk and genuinely undeclared — so it is not suppressed, and the completeness it loses is what the refused all-clear reports.

  **This is a v0.9.0 finding, and it is the same defect family one layer out from the axis.** Leading the entry axis with the disk check (v0.6.0) made the axis's *first* decision depend on an input whose integrity nothing had yet checked, so a partial enumeration — a wrong glob returning 3 of 18 files — satisfied the leading split for the 15 entries whose subjects **exist**, decided them ahead of rows 1-6, and classified them `ORPHANED`: *delete the entry* for 15 correct entries. Re-deriving the axis cannot surface this, because the axis is sound; what was unsound is the input. The gate is the correction, and the corroboration clause below is what makes the gate decidable.

  **The disk check leads the entry axis, and its position is normative rather than stylistic.** More than one split can be satisfied at once — an entry whose subject is gone *and* whose query errors satisfies row 8's condition and row 2's — so totality over rows is not enough on its own: every **entry** must also reach exactly one row, which is what a split order decides. Row 8 leads because it is the only permanently non-retryable condition on the axis: once the subject is gone, every later split's implied action is wrong for it. Reading the axis in any other order routes that entry to row 2 and hands the operator *"retry; check credentials"* for a subject no retry can bring back.

  **The leading split is gated on the enumeration's integrity, the same shape as the sentence gating it on `kind`.** Two guards now sit ahead of it, and they answer different questions: `kind` asks *is this entry the sort of thing a disk enumeration can judge at all?*, integrity asks *is this disk enumeration fit to judge anything?*. Row 8's cell and this derivation are worded to make **one** claim rather than two — the condition is *absent from the disk enumeration and corroborated absent by a direct test of the locator*, not the weaker *no longer on disk*, which the enumeration is only a proxy for. The earlier split said *absent from the enumeration* while row 8's cell said *no longer on disk*; those coincide only while the enumeration is complete, and a table-driven implementer builds the proxy.

  **This is a v0.6.0 finding, produced by re-running the derivation rather than reviewing the table.** The v0.4.0 repair placed the disk check **last** and patched the collision with a carve-out scoped to *not-found* queries only — leaving the error branch deciding row 2, which is the same two-states-one-label defect row 8 was added to close, surviving one branch over. It did not present as an empty cell, and no row was missing: the table was total and the reading order was wrong. The correction is an ordering and a widened carve-out; **no row was added and no value was added.**

  **And a v0.8.0 finding, from the same instruction, on the branch below it — the declared condition was reachable only through the zero-runs branch.** The axis tested *are there qualifying runs?* before it tested whether the entry's own declaration excuses their absence, so an entry that is **correctly quiet and still has an aged run visible** satisfied row 4 and classified `STALE`. `release.yml` between releases is exactly that entry, and `AC-GSM-004` mandates it. Two properties make this the SPEC's own named failure shape rather than a wording preference: it is the **false-alarm direction on a healthy subject** — the outcome the paragraph below the table names as row 5's sharp hazard, arriving even though the M1 field ships — and **retention selected the label**, because the same real-world state reads `STALE` while `gh run list` still returns the last release's run and `OK` once retention consumes it. One state, two labels, chosen by an artefact of the query rather than by the subject, which REQ-GSM-007 forbids. Closed by making the window test ask **is there a qualifying run *inside the window*?** and placing the declared-condition test as a **single node immediately after it**, ahead of the aged-versus-absent distinction that then separates rows 4 and 6. Rows 4, 5 and 6 carry the resulting conditions; **no row was added and no value was added**, and the count is unchanged at 8 rows (`grep -c '^  | [0-9] |' spec.md` → 8).

  **The leading split is guarded on `kind` deliberately.** Only a disk-enumerable kind can be judged absent from a disk enumeration, so an entry of a kind the enumeration does not cover skips this split and routes onward. No second kind ships (§D Out of Scope), which makes the guard presently vacuous — it is stated so that adding one does not silently classify every non-workflow entry `ORPHANED`. §D.7 carries this as a bound.

  **Row 8 is the proof that the derivation is worth stating.** The table asserted totality at v0.2.0 and a by-construction re-derivation broke it on the first attempt: nothing covered a declared entry whose subject had been deleted. It is the mirror of row 7 and derivable from the same two inputs — not an unforeseeable eighth condition — and it did not present as an empty cell. Run history outlives a deleted workflow, so the condition fell through to `STALE` (advice to investigate a subject that no longer exists) or, on a recent enough run, to `OK` — **a false clean, the worst direction**. Its degraded form landed in row 2, putting a permanently non-retryable case under a "retry" action, which is the two-states-one-label defect REQ-GSM-007 forbids. A table that claims totality is only as good as the method that produced it, which is why the method is now stated beside it.

  **Row 2 carve-out, stated over every query outcome rather than over one of them.** Where the disk enumeration confirms a declared subject is gone, the entry classifies `ORPHANED` (row 8) **whatever its query did** — returned not-found, errored, timed out, or was never issued. Row 2 covers a query that could not be completed **for a subject that still exists** and may therefore succeed later; row 8 covers an entry no query outcome can rehabilitate. The earlier wording carved out only the *not-found* case, which left the error case deciding row 2 and is the defect this version corrects.

- **REQ-GSM-013** — Every classification shall declare its **surface fold** — the value it becomes in the three-value surface vocabulary `ok` / `warn` / `fail` — and the fold shall be the `Surface fold` column of the table above. #### C.2.1 The fold, and what was reused from card t326 rather than re-derived

Three SPECs now answer one question — *what do you call an entry you cannot judge?* — and three independent answers would make three vocabularies. Card t326 has a landed implementation, so it was read before this table was fixed.

**Re-measured at v0.6.0 on `52c3fe590`, this tree, this run — and the two-baseline apparatus this section used to carry is gone.** Earlier versions pinned every t326 citation to `origin/develop` at `ec15ec2cd` and warned that those surfaces were *absent from this SPEC's baseline*, so reading the wrong tree would report a landed feature as missing. On `52c3fe590` that warning is **false**: `ec15ec2cd` is an ancestor (`git merge-base --is-ancestor ec15ec2cd HEAD` → rc=0), and so is the old baseline `091966c55` (rc=0). Every cited surface is present here — `internal/binlag/`, `internal/cli/uikit/types.go`, `internal/cli/doctor.go`, `internal/hook/session_start_binary_lag.go` — so all citations below are read from the working tree at `52c3fe590` and no second pin is needed.

**What was reused.** Two things, both adopted with citation rather than re-derived:

- **The never-emit-`fail` discipline** (REQ-GSM-013). t326's reason transfers exactly: a routine check that can fail the process turns a healthy installation into a reported fault. This SPEC's consumer is explicitly non-blocking, so the same conclusion holds for the same reason.
- **The leniency principle.** t326's `gitCompare` comment records that *five* paths report not-applicable or otherwise-fine rather than a problem, and that "that leniency is deliberate and must not be narrowed: each narrowing turns a perfectly healthy downstream installation into a reported fault." Row 5 of this table is that principle applied here — a declared-quiet subject between releases is *fine*, not unknown — and row 1 folds to `ok` on the same reasoning.

**What did not fit, and this is the more useful finding.** The *vocabulary* does not transfer. Measured against t326's four values, **four of this SPEC's seven** have no counterpart (`UNKNOWN`, `UNRESOLVED`, `UNDECLARED`, `ORPHANED`) and one of t326's four has none here (`Divergent`, an ancestry relation with no meaning for firing history). The two SPECs answer structurally different questions: t326 decides an **ancestry relation on one binary**, this SPEC decides **set membership and history across N subjects**. Adopting t326's four values would have forced the three set-and-history states into `not-applicable`, which is the collapse that failed the predecessor three times.

**And the leniency principle has a boundary this SPEC must draw, because the two subjects diverge exactly here.** t326 folds uncertainty toward `ok`; this SPEC exists because *uncertainty folded to green is the defect* (§A.2). The boundary is the difference between **meaningless** and **incomplete**:

- `UNREADABLE` (row 1) is **meaningless** — no reader exists, so the comparison was never applicable. It folds to `ok`, exactly as t326's `not-applicable` does.
- `UNKNOWN` and `UNRESOLVED` (rows 2 and 6) are **incomplete** — the comparison was applicable and could not be completed. They fold to `warn`, diverging from t326.

Folding the incomplete cases to `ok` would reproduce this card's own subject inside its solution: a mechanism reporting green about a set it never learned. The leniency principle is adopted for the meaningless case and explicitly not extended to the incomplete one.

- **REQ-GSM-007** — The classification vocabulary shall be exactly the closed set `OK`, `STALE`, `UNKNOWN`, `UNDECLARED`, `UNREADABLE`, `UNRESOLVED`, `ORPHANED`, and **each value shall be distinguishable from every other on at least one observable axis** — its implied action, its surface fold, or its cleanliness under the published designator (REQ-GSM-012). **Totality binds in both directions**: every row of the table shall map to exactly one value (no entry condition is unclassifiable), and every value shall be reachable from at least one row (no value is an unused option). A value no entry can receive is a defect in the evaluator; **an entry no value can receive is a hole in the state space**, and the second direction is the one that has actually failed — twice now, at `UNRESOLVED` and again at `ORPHANED`.

  The distinctness clause reads *on at least one observable axis* rather than *by implied action*, because the stricter wording was satisfied only by prose. `UNREADABLE` and `OK` carry textually different implied actions that are operationally identical ("None until a reader exists" versus "None") and both fold to `ok`. What actually separates them is **cleanliness**: `OK` is the clean value, `UNREADABLE` is not, and the designator carries that difference to any consumer. Naming the axis makes the distinction checkable instead of rhetorical, and §D.7 records that `UNREADABLE`'s distinctness rests on that axis alone.

- **REQ-GSM-008** — The evaluator shall compare the manifest against the disk enumeration **in both directions at runtime**: where a workflow file exists on disk with no manifest entry it shall classify `UNDECLARED` (row 7), and where a manifest entry names a workflow file **absent from the enumeration whose absence a direct existence test of that entry's locator corroborates** it shall classify `ORPHANED` (row 8) — the same condition row 8's cell and the §C.2 derivation state, worded identically in all three places at v0.9.0 so no reader can build the weaker *no longer on disk* proxy from one of them. Both directions run **behind REQ-GSM-010's enumeration-integrity gate**; on a failed gate the entry→disk direction is suppressed while the disk→entry direction is not, because a degraded enumeration makes the first mis-report and the second merely under-report. This is the **set comparison**: it asks whether a subject *was in the set that was examined, and should have been*, rather than reading outcomes only for subjects the manifest already knew about. An evaluator without it reproduces the defect at its own layer — accurate about what it looked at, silent about what it never looked at.

  The second direction is stated because its absence was not visible as a gap. AC-GSM-001 already asserted a two-directional set difference, but that is an **M1 census check run once at authoring time**; the runtime requirement was one-directional, so the criterion layer claimed a symmetry the requirement layer did not implement. A declared entry whose subject was deleted therefore reached the classifier and was decided by run history that outlives the deletion.

### C.3 Result integrity

> **REQ-GSM-013 (the surface fold) is defined above, in §C.2 beside the state table**, out of numeric sequence and deliberately so — the fold is a column of that table and reads wrong apart from it. This pointer exists so a reader scanning §C.3 for the missing id finds it rather than concluding it is absent.

- **REQ-GSM-009** — When the evaluator emits a result, it shall carry its own measurement timestamp, the count of workflow files its disk enumeration returned, the count of entries declared, the count successfully queried, and a per-value count for each classification. **Every carried count shall have a consumer** — a count that is rendered and consumed by nothing is field-level inertness, and the audit found two such counts in the predecessor.
- **REQ-GSM-010** — The evaluator shall not report an all-clear while its successfully-queried count is zero, **or its workflow-file enumeration fails its integrity check** — where the enumeration **passes integrity** only when it returned **at least one file** and **no** declared entry of a disk-enumerable kind that is absent from it is found **present** by a direct existence test of that entry's own locator, and **fails integrity** otherwise. The zero-file case is therefore an integrity failure and not merely an all-clear refusal: absent that, a wrong working directory would enumerate nothing, every locator would corroborate as absent against the same wrong root, and every declared entry would classify `ORPHANED` on a result that was correctly refused its all-clear. The integrity check shall be evaluated **before the entry axis runs** (REQ-GSM-006), and a failed check shall **suppress row-8 classification** rather than be tolerated by it. Both inputs to the set comparison can degrade, and an enumeration that silently returns empty — wrong working directory, a path constant, a permissions failure — makes `UNDECLARED: 0` indistinguishable between "census complete" and "the evaluator never looked".

  **The tolerance term is stated over a second, independent observation of the disk rather than over the evaluator's own findings, and that is the whole of the v0.9.0 correction.** The earlier wording refused an all-clear when declared and enumerated *"differ by more than the manifest's own `UNDECLARED` and `ORPHANED` findings account for"* — a term computed from classifications the degradation itself produced, so the degradation laundered itself. Walk it on `AC-GSM-012`'s own fixture (ii): declared 18, enumerated 3, difference **15**; `UNDECLARED` 0; `ORPHANED` **15**, every one of them a correct entry mis-classified by the ungated leading split. 15 is not *more than* 15, so the guard was satisfied and did not fire — on the exact partial enumeration it was written for. **Any term computed from the classifications is circular in this way, for any partial enumeration, and not only for this fixture**: an entry missing from the enumeration is precisely what produces an `ORPHANED` finding, so the miss count and the finding count move together by construction and their difference is identically zero. Corroboration breaks the circle because it is a **different measurement of the same fact** — a per-subject point test of the named locator, not a re-run of the enumeration, so it cannot inherit the enumeration's own defect.

  **The check separates the two states a bare count cannot, and it leaves the legitimate case reachable.** A declared entry absent from the enumeration is either (a) a subject genuinely deleted, or (b) a subject the enumeration missed; a count of 18-against-17 is identical in both, which is why a count alone can only be made safe by refusing both — and refusing (a) would close the false `ORPHANED` by making the true one unreachable, which is relocation rather than repair. The point test decides between them directly: **absent under the point test → genuinely gone → row 8 stands; present under the point test → the enumeration missed it → integrity fails, row 8 is suppressed, and the guard fires.** Where both hold at once — one subject truly deleted and others missed — integrity fails and row 8 is suppressed for **all** entries including the true orphan, deliberately: an enumeration known to be wrong is not a basis for advising a deletion, and the refused all-clear reports the degradation instead.

  **A zero-check alone is the card's own defect at a lower dose.** An enumeration returning 3 of 18 files — a wrong glob, a partial permissions failure — is non-zero, passes a zero-check unremarked, yields no `UNDECLARED` finding for the 15 it never saw, and reports all-clear about a set that had silently become the wrong set. The guard therefore tests that the *right* thing happened, not merely that *something* did; the comparison is nearly free because REQ-GSM-009 already carries both counts.
- **REQ-GSM-011** — The evaluator shall not write to the repository working tree, commit, push, open an issue, or mutate any forge state. It reads and reports.
- **REQ-GSM-012** — The result shall satisfy the published contract (§B): every entry carries exactly one classification; **exactly one value — `OK` — denotes *nothing to report***; and **the result shall carry a machine-readable designation of which value that is** — a result-level clean-value designator, or an equivalent per-entry cleanliness flag — so a consumer can identify clean entries without knowing any value's name. This SPEC may add, rename, or re-decide classifications provided those clauses continue to hold, and the consuming SPEC cannot verify them, so they are verified here.

  **The producing side owes the consumer a well-formed designation, and the consumer owes it a defined refusal.** This SPEC shall emit exactly one designated clean value on every result; the consuming SPEC's REQ-GDL-013 refuses an all-clear on a result whose designation is absent, null, or multi-valued. The two clauses are the same guard from opposite ends — neither side may be green about an input it could not read — and they mirror this SPEC's own REQ-GSM-010, which refuses an all-clear while the queried count is zero or the enumeration returned nothing.

  **The designator is what the seam actually rests on, and it is not redundant with the surface fold.** More than one classification folds to the clean *surface* value — `UNREADABLE` folds to `ok` (REQ-GSM-013) while `OK` alone is the clean *classification* — so a consumer reading the fold would under-report. Emitting the designation is therefore the producing half of a symmetric obligation whose consuming half is `SPEC-GUARD-LIVENESS-001` REQ-GDL-001 clause (iii)/(iv); neither half is sufficient alone, and a change to one without the other is exactly the cross-seam drift the split exists to make visible.
