The GEARS obligation lives in spec.md §C; nothing here restates a requirement as GEARS. 25 criteria cover 25 requirements one-to-one (Tier L ceiling 25); sub-labelled criteria (`a`/`b`) belong to their parent and count once.
>
> **Two-cell discipline (verification-completeness §2).** Each criterion carries a RED-now cell (what is red on the pre-change tree and why) and a green path (which milestone flips it). **Tree pin for every RED-now cell without its own pin: `9495566efa15331f10135469d86313e8b1c1733c`** (document-level pin; branch `WT-d2-moai-worktrees`; the tree audited in iteration 3 and measured again in the iteration 3 correction round, where the grep cells of AC-WHR-001, 002a, 004, 012b and 019 were re-observed). No cell carries its own pin.
>
> **Classification.** `RB` = release-blocking: the RED-now cell is **Observed here** with all four elements — the command (one plain invocation), its verbatim stdout, its exit code as its own field, the tree pin — plus the expected-green observable (the command's output once the work is done). `RB*` = release-blocking once its M0 cell is recorded: the red can be observed only by a Go test or fixture that does not exist at plan time (plan time ran no Go command); unadopted until then (verification-completeness §2.1), and demoted to `RG` at M0 if the cell cannot be made red. `RG` = regression guard: green by design, a guard and not a gate of new work.
>
> **Test layout.** Unless a criterion names another form, "test" means a Go test in the touched package using `t.TempDir()` repositories and a temporary `MOAI_HOME`; no test touches the real `~/.moai`, the real repository's worktrees, or global git config. Selectors are listed count-first (a `-list` count precedes each `-run`) so an absent test cannot pass as an empty sweep. Observation commands below are plain single commands; the exit code in each cell is the exit code of the quoted command. A no-match `grep` exits 1 and a `grep -c` that counts 0 exits 1; the observing harness prints no status line for a grep exit of 1, so a grep cell's code is derived from its stdout (empty, or `0` for `-c`, with empty stderr) and was printed explicitly by the iteration 3 audit for the same pattern without the test-file exclusion, while a non-grep cell (`ls`, `moai`) shows its own code. Every grep over `internal` that must find production code passes `--exclude='*_test.go'`: the M0 baseline commit and the TDD red tests of M1 and M6 put the searched literals into test files before any production code exists, and a cell that a test file can turn green measures nothing.

## §C. Edge cases (each is covered by an AC above or recorded as a Gap)

- Repository with zero legacy trees: `migrate` prints "0 moai-made trees" and exits 0; `update` prints nothing new.
- Tree whose directory name contains a space or non-ASCII: the sanitizer touches only the project key; tree names are validated as today (`validateNewWorktreeName`, `new.go:56-63`).
- `MOAI_HOME` relative or unset: `paths.MoaiHome()` already disregards a relative value and falls back to `$HOME/.moai` (`paths.go:67-76`).
- A tree being created while a migration runs: creation and migration serialize on the existing factory step lock for card trees (`factory.AcquireFactoryStepLock`, `factory_card.go:762`); non-card creation during `--apply` is recorded as a Gap, not assumed safe.
- Interrupted `--apply` (process killed between steps): the journal entry is written before the move with a status per step, so `--verify` classifies the tree and `--rollback` or a re-run converges (AC-WHR-017a/018); a kill between the move and the settling move-list line is answered by the intent line (AC-WHR-012b step 9).
- Windows paths: unmeasured (OQ-4).
- A lane parked without a live process or session when its tree moved: it finds the new path through the rebound card record, or through the move list from the old path held in its dispatch pointer (AC-WHR-012b).
- A running `moai update` and a manual `migrate --apply` at the same time: serialized by the one migration lock; the second mover moves nothing and reports why (AC-WHR-017b). A mover that finds the lock held after a crash of the first: both locks are OS-held and released with their holder's process, so a killed holder does not block (asserted in AC-WHR-017b steps (3) and (4) with a helper process the test kills), and a launcher write during a re-key is serialized by the state-file lock (step (2)).
