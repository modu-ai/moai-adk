# SPEC-CODEX-SKILL-DISABLE-001 — 구현 계획

카드: **t502** · Tier M · Class C · cycle_type **tdd**

## §A 맥락

`~/.codex/config.toml` 의 `[[skills.config]]` 는 이미 두 손이 닿아 있다 — 읽는 손(`internal/codexwiring/skills.go`, t451)과 지우는 손(`internal/cli/codex_skills_prune.go`, t506). 이 카드는 **쓰는 손 하나**를 더 만든다: 사용자가 이름으로 지목한 스킬 하나를 codex에서만 끄는 엔트리 발행기.

새 손이므로 결함 수정이 아니다. 그리고 사용자 HOME에 쓰는 손이므로, 안전 성질 셋(기본 비활성 · 명시 opt-in · 멱등 비파괴)이 기능 자체보다 먼저 온다.

## §B 선행 측정으로 닫힌 질문들

이 절이 v0.1.0에서 담고 있던 미해결 표식 3건은 **모두 측정으로 닫혔다**. 근거는 `.moai/reports/t502/gate-path-shape.md`(19셀, `CODEX_HOME` 격리, `codex-cli 0.153.4`). 표식 토큰은 이 파일에 한 번도 남아 있지 않다 — 닫혔다는 사실을 적으면서 토큰을 그대로 쓰면 그것을 세는 검사가 자기 문장을 미해결로 읽는다.

### 미러는 한 모양이 아니다 (전제, 측정됨)

`internal/template/skill_mirror.go` 의 `mirrorOneSkill`(:198-245)은 **네 갈래**로 끝난다.

| 결과 | 조건 | 미러 경로에 심링크가 있는가 | 측정 상태 |
|---|---|---|---|
| `MirrorModeSymlink` | 정상 경로(멱등 재실행 포함) | 있다 | 측정됨 (proj-S) |
| `MirrorModeCopy` | `os.Symlink` 실패 시 폴백 — 실제 사본 | 없다 (진짜 디렉터리) | 측정됨 (proj-C) |
| `MirrorModeSkipped` | 심링크가 아닌 실엔트리가 이미 그 자리를 차지 | 그 자리는 사용자 것 | **copy와 구별 불가** — 아래 참조 |
| `MirrorModeFailed` | 링크 제거·디렉터리 생성·사본 실패 | 쓸 수 있는 미러 항목이 없다 | 미측정(Gaps) — 게이트할 대상 자체가 없다 |

`.agents/skills/` 는 이 저장소에 **존재하지 않는다**(t502 워크트리·primary 체크아웃 양쪽 `ls` exit 1). 미러는 배포 실행이 만드는 산물이지 체크아웃이 만드는 것이 아니므로 **부재는 평범한 상태**이고, 그래서 REQ-CSD-011은 그 경우만 종료 코드 0으로 둔다.

**`MirrorModeSkipped` 에 대한 v0.1.0의 주장은 철회한다.** 「skipped ⇒ 해소 실패 ⇒ 거절 경로」는 측정이 반증했다 — 사용자 실엔트리가 `SKILL.md` 를 품은 디렉터리이면 파일시스템 모양이 복사 모양과 구별되지 않아 **정상 로드되고 정상 차단된다**(C0/Clit). 해소는 성공한다. 남는 유보는 좁다: 실엔트리가 `SKILL.md` 를 품지 **않은** 경우(빈 디렉터리, 동명의 일반 파일)는 미측정이고, 그 하위 사례에서만 해소 실패가 성립할 수 있다.

### 닫힌 답 1 (Q-a) — 게이트는 realpath 정규화 파일 비교다

문자열 비교가 아니다. 결정적 셀은 **E2**: 미러와 경로 성분을 **하나도 공유하지 않는** 별개 심링크로 쓴 엔트리가 실제로 로드된 스킬을 껐다. 문자열 매칭으로는 설명되지 않는다. E1(`./..` 철자)·E3/E8(`/private` 접두)이 정규화 범위를 보강한다.

따라서 「리터럴 표기가 통한다」는 말은 **문자열이 맞아서가 아니라 같은 실파일로 해소되기 때문**이다. 표기 선택은 언제나 "어느 실파일로 해소되느냐"로 판단한다.

### 닫힌 답 2 (Q-b) — 두 미러 모양 모두에서 묶이는 표기는 하나뿐

| 표기 | 심링크 미러 | 복사 미러 | 공통 |
|---|---|---|---|
| 리터럴 `<projectRoot>/.agents/skills/<n>/SKILL.md` | 차단 (Slit) | 차단 (Clit·E8) | **✓** |
| 해소 `.claude/skills/…` | 차단 (Sres) | **무효 (Cres)** | ✗ |
| 디렉터 모양 | 무효 (E4) | 무효 (E5) | ✗ |
| 상대경로 | 미측정 | 무효 (E6) | ✗ |

**발행 표기 확정: `<projectRoot>/.agents/skills/<skill>/SKILL.md` — 절대·파일 모양.** `.claude/…` 를 골랐다면 심링크 미러를 쓰는 저자의 기계에서는 동작하고 복사 폴백 사용자에게서는 조용히 죽었을 것이다.

### 닫힌 답 3 — 후보 루트는 성질로 지목한다, 번호로 지목하지 않는다

관측된 루트 목록은 `r0`/`r1`/`r2` 라는 라벨을 달고 나오지만 **그 번호는 환경에 따라 재배치되는 상대 라벨**이다 — t504의 실환경 관측과 t502의 격리 관측이 이미 서로 다른 배치를 보였다. SPEC과 구현은 루트를 **무엇인지로** 부른다:

| 루트 | 성질 | 이 SPEC에서의 지위 |
|---|---|---|
| 프로젝트 미러 (`<projectRoot>/.agents/skills`) | cwd 기준. moai 미러가 노리는 통로 | **발행 대상** |
| 사용자 홈 미러 (`~/.agents/skills`) | 사용자 홈. **`CODEX_HOME` 격리를 통과해 루트로 들어온다** (실측; 이 기계에 19개 항목) | 모호성의 실제 원천 — 같은 이름이 여기와 프로젝트에 동시에 있을 수 있다 |
| codex home 스킬 (`$CODEX_HOME/skills`) | codex 자신의 컨벤션 | 이 SPEC의 발행 대상 아님 |
| 플러그인 루트 | 플러그인 배포물 | 범위 밖 |

홈 미러가 격리를 뚫는다는 사실이 REQ-CSD-011의 모호 분기를 가설이 아니라 **실재하는 경로**로 만든다. 후보 루트의 최종 집합·순서는 run-phase M2에서 이 표를 근거로 확정한다.

## §C CLI 배치 결정

**결정: 새 루트 커맨드 `moai skills`, 하위 동사 `disable`, 계층 지정 플래그 `--codex` 를 필수로.**

```
moai skills disable <skill-name> --codex [--force]
```

`--codex` 를 필수로 두는 것이 곧 REQ-CSD-001(명시 opt-in)의 기계적 표현이다. 사용자의 HOME에 쓰는 순간, 그 쓰기 대상 계층을 사용자가 호출문에 적어 넣게 만든다.

### 검토한 대안과 기각 사유

| 안 | 내용 | 판정 |
|---|---|---|
| A. `moai codex skills disable` | 런처 `codexCmd` 에 동사 추가 | **기각.** `codexCmd` 는 `DisableFlagParsing: true` 인 런처이고(`internal/cli/codex_launcher.go:293` 부근), 동사 조회가 `runCodex` 안의 손수 만든 `codexVerbRouting` 맵 + `len(head) > 1` 이면 usage 실패라는 **한 토큰 형태**에 묶여 있다(`codex_launcher.go:344-368`). `disable <name>` 은 두 토큰이라 그 형태를 깨고, `--force` 도 손으로 파싱해야 한다. 게다가 진단 출력이 바이트 정확히 시험되고 있다(`SilenceErrors`/`SilenceUsage` 주석이 그 이유를 명시). 새 기능 하나를 위해 회귀 위험이 가장 높은 파일을 여는 거래 — **받지 않는다.** |
| B. `moai clean --codex-skills` 확장 | 쌍둥이와 같은 집 | **기각.** `clean` 의 계약은 **제거**다(`newCleanCmd` 는 스코프 하나만 받고 `--home` 과 상호배타). 비활성화는 제거가 아니라 **저작(엔트리 추가·갱신)** 이다. 같은 파일을 만진다는 이유로 반대 의미의 동사를 제거 커맨드에 넣으면, 다음 독자가 `clean` 이 파일에 내용을 **쓴다**는 것을 알 길이 없다. |
| C. `moai config ...` | 설정 커맨드에 태우기 | **기각.** `moai config` 는 moai 자신의 `.moai/config/` 계층을 다룬다. 사용자 HOME의 codex 파일을 여기에 넣으면 두 계층이 한 동사 뒤에서 섞인다. |
| D. 프로젝트 config 키(`codex.disabled_skills`) | 선언형 | **운영자가 이미 기각.** 프로젝트 설정이 사용자 HOME에 쓰기를 유발하면 「그 순간 사용자가 요청하지 않은 쓰기」가 되어 성질 (a)·(b)와 정면 충돌하고, 이 머신의 유령 49건과 같은 부채를 다시 만든다. |

### 배치 결정의 잔여 위험

`skills` 라는 루트 이름은 넓다 — 장래에 Claude Code 쪽 스킬 조작 동사가 생기면 같은 이름 아래로 들어오게 된다. 그것은 결함이 아니라 **의도한 자리**로 본다(계층은 언제나 플래그로 명시되므로 `moai skills disable X --codex` 와 가상의 `--claude` 가 한 지붕 아래 공존할 수 있다). 다만 이 카드는 `--codex` 하나만 구현하고, 다른 계층 플래그는 만들지 않는다.

### 순수 함수 시그니처(형태만, 확정은 run-phase)

```
// content in → content out + 항목별 판정
func upsertCodexSkillDisable(content []byte, skillPath string) ([]byte, codexSkillDisableVerdict)
```

`codexwiring.SplitConfigLines` → `ParseSkillEntries` 로 기존 엔트리를 읽고, 경로 일치 엔트리가 있으면 그 구간의 `enabled` 줄만 교체, 없으면 말미에 두 키를 가진 엔트리를 덧붙인 뒤 `JoinConfigLines` 로 되돌린다. 이미 `false` 면 **입력 바이트를 그대로 반환**한다(prune의 `if !removed { return content, ... }` 와 같은 규율 — 왕복 결함이 no-op으로 위장하지 못하게).

### 러너

`runCleanCodexSkills` 의 골격을 그대로 따른다: `resolveCodexHomeDir()` → config 경로 조립 → 읽기 실패는 fail-open 안내 → dry-run 보고 → `--force` 시 선백업(`.bak-<UTC>`, 0600) + sha256 출력 → 쓰기 → 결과 보고.

**한 곳에서 갈라진다 — 대상 파일의 퍼미션 모드.** prune 은 `os.WriteFile(cfgPath, pruned, 0o600)` 으로 무조건 0600을 쓴다. 이 동사는 그러지 않는다: 기존 파일이면 `os.Stat` 으로 읽은 모드를 유지하고(`os.Chmod` 로 되돌리거나 모드를 보존하는 쓰기 경로를 쓴다), 새로 만들 때만 0600을 쓴다(REQ-CSD-032). 「비파괴」를 표제로 내건 동작이 사용자의 `0644` 를 말없이 조이는 것은 그 표제와 어긋나기 때문이다. prune 쪽 동작은 이 카드에서 **바꾸지 않는다**(REQ-CSD-051) — 두 동사가 이 축에서 달라지는 것은 의도된 차이이며, prune 의 무조건 0600 이 옳은지는 t506 소관이다.

| 사용자 손 편집 config 파괴 | 미인식 줄 보존(REQ-CSD-033), 선백업, dry-run 기본 |
| codex 버전 드리프트 — t504는 0.153.4 한정 | 판정서에 측정 버전을 스탬프하고, 발행 동사의 도움말에 「이 동작은 codex가 이 키를 어떻게 읽느냐에 달려 있다」는 사실을 남긴다 |

## §F.1 예산 초과 — 기록된 예외 (리드 판정)

**현재 수용 기준은 17개, Tier M 상한은 16개다.** 요구사항은 16/16으로 상한 안에 있다.

초과의 원인은 명확하다 — 운영자의 **D-N2 판정**(해석 불가·모호는 0이 아닌 종료 코드, 미러 부재만 0)이 세 거절 사례에 **서로 다른 종료 코드**를 부여했고, 그 순간 셋은 서로 다른 것을 단언하게 되어 합칠 수 없게 됐다. 감사가 방금 요구한 수리가 만든 초과이며, 상한은 문서가 부푸는 것을 막으려고 있지 그 수리를 되돌리려고 있지 않다.

**통합은 검토했고 기각했다.** 검토한 후보는 AC-CSD-011(해석 불가)과 AC-CSD-012(모호)의 병합이다 — 둘은 **같은 성질**(0이 아닌 종료 코드 + 바이트 불변)을 서로 다른 Given 둘에 대해 단언하므로, 감사 D-N1이 지적한 손상(두 **성질**이 한 판별 셀 아래로 들어가 한쪽이 무방비가 되는 것)과는 모양이 다르다. 그럼에도 기각한 이유는 그 둘이 겉보기에 구별되지 않기 때문이다: 기준이 16개이고 아무 기록도 없는 문서를 나중에 읽는 사람은 자기가 보는 것이 어느 모양인지 알 길이 없다.

**이것은 상한 완화가 아니라 기록된 예외다.** 다시 열려면 위 논거를 반박해야 한다 — 숫자만 보고 줄이는 것이 이 절이 막으려는 행위다.

## §F.2 세는 것은 구조에 앵커한다

[HARD] 이 SPEC 산출물에 대해 주장하는 모든 카운트·스캔은 **구조**(표제, 정해진 토큰 위치)에 앵커한다 — 주변 산문이 똑같이 적을 수 있는 맨 id나 마커 토큰에 앵커하지 않는다.

근거는 이 카드에서 한 개정 안에 **두 번** 발생한 실측이다. acceptance.md 는 id 스캔 패턴을 예산 기록 본문에 그대로 적어 그 스캔이 자기 문장을 세었고(17 → 18), plan.md 는 마커가 닫혔다고 쓰면서 마커 토큰을 그대로 써서 마커 스캔이 자기 문장을 미해결로 읽었다(0 → 1). 둘 다 **안전해 보이는 방향으로** 수를 부풀렸다 — 검사가 실패하는 게 아니라 조용히 틀린다.
