## 1. Problem

The landing path accepts a re-measure record when one command exited 0 on the candidate tree (`internal/factory/integration_remeasure.go:135` `ValidateRemeasureRecord`; for a command that is not `go test -json` it keeps command and exit code only, :185-193, :698). Nothing records which calls were required, that each ran to the end, or that all of them passed on one tree. Observed (`research.md` §3): landed tree `1a3dc230c35ca0e2a997fc0fc3ac9444eb1f9198` (card t1680) was gated by one script-wrapped record with `structured_required=false`.

For a SPEC card the merge-readiness sync-audit condition reads only `sync_status: complete` from progress (`internal/factorylane/merge.go` `checkSyncAudit`), so an earlier PASS can stand for the audit of a later HEAD. The operator decided (board `2c51`) that `complete` binds the verdict, and the required backend's receipt, to the card's current HEAD. An audit receipt records no commit today (`internal/auditreceipt/store.go:166-177`; writer `internal/cli/mcp_audit_receipt.go:60-100`, called after the backends from `mcp_codex.go:2112, 2163` and `mcp_convergence.go:928`); board `0577` P4 approves adding the audited commit to new receipts. No Go code parses a receipt id from a verdict file today (`ParseVerdictLine`, `store.go:1223`, reads the final-message verdict line), and measured sync-audit verdict files of merge-ready SPEC cards cite receipts in mixed forms (`research.md` §10).

## 2. Terms

- **Candidate tree / HEAD** — tree and commit of the card branch tip being landed. **Integration branch** — the branch named by the held window record or else by the common-root integration configuration (`configuredIntegrationBranch()`, `internal/cli/integration.go:291`). A project with neither has not opted in to the git-flow window, and for the gate that means off (REQ-LVM-017); the merge verb's own fallback to `develop` is not used to decide the gate.
- **Derivation** — the pure function that computes a card's required calls from the candidate: the merge-base diff, `go list` over base and candidate, the repository's test sources, and the declared environment. The producer and the verifier run the same code.
- **Manifest** — the stored result of a derivation. **Call**, **attempt**, **package terminal event** (the `go test -json` event with `Action` pass, fail or skip and no `Test` field, per `Package`).
- **Gate-complete on tree T** — the manifest is current (REQ-LVM-016) and every call has a counted attempt on T whose terminal events cover the call's whole package set, zero missing, none failed, non-zero executed-test count per package unless the manifest recorded `no_test_files`.
- **b2cd scope** — the Go packages the card changed (test-only and package-directory non-Go changes included) plus the Go packages that import them, each run whole with no `-run`; the one narrowing allowance is `internal/cli` (rule 35e9). Machine-local board rulings, committed to the tree by this SPEC.
- **Structured form** — one `moai integration remeasure --call <call-id> -- go test … -json …` per manifest call.
- **Equals HEAD** — the audited commit is exactly the card's current HEAD commit. There is no tolerance: an ancestor of HEAD, whether its diff to HEAD is empty, patch-identical or confined to `.moai/reports/<card-id>/`, does not equal HEAD (boards 0577 P3 and 5d4d).
- **Bound receipt** — a receipt whose audited-commit field equals HEAD (REQ-LVM-009/010).

## 3. Requirements (GEARS)

- **REQ-LVM-001 (event).** When the manifest producer runs for a card, it shall derive and write a manifest listing: one call that runs each changed Go package whole (`go test -count=1 -p 1 -json`), where a package counts as changed when a file under its directory changed, test-only, embedded and testdata files included; one such call for each direct importer of a changed package (non-test, test and external-test imports); one such call for each package that embeds a file belonging to a changed package directory; for every changed non-Go file outside a Go package directory, the reader calls found by a search of the repository's test sources, or a zero-readers record naming the search command and its empty result; and, for a deleted package, a record comparing the base and candidate package graphs instead of a call; and, when the card changes `go.mod`, `go.sum`, `go.work` or `go.work.sum`, one such call for every Go package of the module (these four files are repository-wide inputs: they are never routed through the reader search, and the 35e9 narrowing does not apply to a call selected only by them). Each call shall record its identifier, exact command, and resolved package set; a call for `internal/cli` alone may carry a `-run` narrowing and shall name it as the 35e9 allowance.
- **REQ-LVM-002 (event).** When a manifest call is executed in the structured form, the re-measure verb shall write an attempt record carrying a unique attempt ID, the call identifier, the exact command argv, the exit code, for every package in the stream its terminal event and its count of executed tests, the candidate tree SHA, the card HEAD SHA, the base, an environment fingerprint (GOOS, GOARCH, CGO_ENABLED, the effective GOFLAGS as resolved by `go env` — environment, `GOENV` file and `go env -w` settings included —, toolchain version, build tags, declared environment variables), the start and end times, the judging build identity, and a termination class.
- **REQ-LVM-003 (event).** When an attempt ends by signal, by timeout, or with a stream that ends on a truncated line, the verb shall classify it as aborted and retain its record, and an aborted attempt shall never count as a pass; a later execution of the same call shall be a new attempt with a new ID that does not overwrite the aborted record, and only the most recent completed attempt per call on the same tree shall count.
- **REQ-LVM-004 (ubiquitous).** The completeness verifier shall report gate-complete only when the manifest is current (REQ-LVM-016), every call has a counted attempt on the candidate tree, each counted attempt exited 0 with a terminal event for every package of the call's resolved set (zero missing), no failure, and a non-zero executed-test count per package unless the manifest recorded `no_test_files` for it; for a manifest of zero calls it shall require the derivation evidence of REQ-LVM-013; the most recent record alone shall never decide the verdict.
- **REQ-LVM-005 (event).** When any of the following holds, the verifier shall refuse readiness: (1) the manifest is missing; (2) a call has no counted attempt; (3) a call's only record is a script-wrapped command with no recognized package report; (4) the stream lacks the terminal event of an expected package; (5) the stream is cut mid-line; (6) the attempt is aborted; (7) the attempt names a different tree or HEAD than the candidate; (8) the environment fingerprint differs from the manifest's, or the effective GOFLAGS — recorded at derivation and at the attempt — carries any test-selection, test-truncation or test-shaping flag (`-run`, `-skip`, `-failfast`, `-short`, `-list`, `-shuffle`, `-count`, `-timeout`, `-p`, `-parallel`, `-cpu`, `-bench`, `-fuzz`), which no manifest call may use through the environment even when derivation and attempt match (the 35e9 narrowing lives in the call's argv only, never in GOFLAGS); (9) a changed non-Go input has neither reader call nor zero-readers record; (10) the b2cd scope cannot be derived; (11) a counted package executed zero tests where the manifest does not allow it; (12) the attempt's command differs from the manifest call's command — exact argv equality of the `go test` segment after dropping leading environment assignments and an `unset … &&` scrub segment, any other segment, pipe or compound refusing, and a `-run` selector accepted only on the `internal/cli` call that names 35e9.
- **REQ-LVM-006 (ubiquitous).** The completeness verifier shall be the single verifier consulted by the merge step, by `moai factory complete`, by merge-readiness condition (d) and by `moai integration manifest verify`, and while the gate is on a record from a command that carries no recognized package report shall not satisfy any of them.
- **REQ-LVM-007 (state).** While the gate is not on (REQ-LVM-017), the landing path shall behave exactly as it does today; the key `workflow.landing_gate.enabled` shall ship false in the distributed template; and the narrowing allowance list shall ship containing `internal/cli` only and shall not be widened by this SPEC.
- **REQ-LVM-008 (event).** When `moai factory complete` evaluates a card while the gate is on, it shall locate the card's verdict — for a SPEC card the newest `sync-audit*.md` under `.moai/reports/<card-id>/` (highest `-iter<N>`, a name without it counting as iteration 1, then latest modification); for a SPEC-less card the file `.moai/reports/<card-id>/verdict.md` that its readiness path already reads — shall refuse when none exists, and shall refuse unless the verdict's audited commit equals HEAD and the verdict is admitted by the shared verdict predicate with the configured required backends; a verdict for any earlier commit shall not substitute, even when the change since is empty or patch-identical, and a commit made after the audited commit shall refuse whatever paths it touches.
- **REQ-LVM-009 (event).** When an audit call is entered, the entry point shall capture the HEAD of the audited tree and the review target the call names before the backends run, and when the receipt writer records the receipt it shall stamp them as the additive fields `audited_commit` and `audit_target`, leaving `audited_commit` empty when the audited tree's HEAD differs at write time; every call site of the writer (`mcp_codex.go` twice, `mcp_convergence.go` once) shall pass the captured values; the writer shall never rewrite or delete an existing receipt, and a receipt without the fields shall remain a valid record read as unbound.
- **REQ-LVM-010 (event).** When `moai factory complete` evaluates a card while the gate is on, it shall refuse unless at least one receipt cited by the verdict qualifies — looked up at the store root of the audited tree (for a config-orphaned worktree, the primary checkout), readable, a codex or multi-backend audit receipt, with `tree_root` equal to `auditreceipt.Canonical` of the audited tree's path (symlinks resolved, else cleaned — the normalization the writer applies, `internal/auditreceipt/treeroot.go:37`; not the store root), an empty unmet-gate field, codex verdict pass, and an audited commit equal to HEAD — and a failed or inconclusive extra cited receipt shall be recorded without blocking and shall never replace the qualifying one; an absent, unreadable, older-HEAD, empty-diff-ancestor, empty-commit, legacy, other-tree or unmet-gate receipt shall each fail to qualify.
- **REQ-LVM-011 (ubiquitous).** The landing rules shall name, in the committed rule files and their template mirrors, the structured form and the commands a lane runs (`moai integration manifest derive`, `moai integration remeasure --call`, `moai integration manifest verify`), the restart of an aborted call as a new attempt, that the gate state is read from the committed content of the integration branch, the notice `gate_state_unreadable`, the rule that no evidence or progress backfill commit lands after the audited SHA (bookkeeping is committed before the final audit), and the prerequisite that the governed landing commands are invoked by path from a binary built from the landing HEAD's main and that the receipt-writing server runs a build containing REQ-LVM-009.
- **REQ-LVM-012 (ubiquitous).** The branch carrying this SPEC's milestones shall never enable the gate in the repository's own configuration; the enabling shall be a separate later commit on the integration branch after the SPEC has landed and a binary built from the landing HEAD is in use, changing the one configuration path only; and the reversal of that key shall land as an ordinary one-path card through the gated path — its derived manifest holding the reader calls of the configuration file (tests in this repository read `.moai/config/sections/workflow.yaml`) and the audit binding of REQ-LVM-008/010 intact — not through any bypass.
- **REQ-LVM-013 (event).** When a card changes no Go package, changes none of `go.mod`, `go.sum`, `go.work` and `go.work.sum`, and the derivation finds no reader call, the manifest shall be empty and shall carry the derivation evidence — the changed-path list, the `go list` proof that no Go package directory contains a changed path, and the reader-search result — and the verifier shall admit the card only when re-derivation yields the same evidence; a missing, stale or inconsistent evidence block shall refuse, and the audit binding of REQ-LVM-008/010 shall apply unchanged. A card that changes any of those four module files shall never be admitted as a zero-call card.
- **REQ-LVM-014 (event).** When a lane runs `moai integration manifest derive --card <id>`, the producer shall write the manifest to `.moai/state/remeasure/manifests/<card-id>.json` under the shared integration root; a re-run after a re-absorb shall replace it (attempts bound to the superseded manifest identity stop counting); `moai integration manifest show` shall print it; and `moai integration manifest verify --card <id>` shall print the verifier's verdict with the failing class named and the gate state with its source (`gate: on|off (source: <branch>:<path> @<sha>)`), exiting non-zero on refusal.
- **REQ-LVM-015 (ubiquitous).** The gate shall not skip or weaken any audit check, shall not accept an earlier PASS for a later HEAD, shall not allow a manifest call to select fewer tests than its whole package outside the named `internal/cli` allowance, by argv or through the effective GOFLAGS, shall not write the integration branch except through the existing merge step, shall not widen any default permission or narrowing allowance, and shall treat every undecidable reading as refusal.
- **REQ-LVM-016 (event).** When the verifier evaluates a card, it shall re-run the derivation on the candidate under the environment recorded in the stored manifest (GOOS, GOARCH, CGO_ENABLED, the effective GOFLAGS, build tags, toolchain) and refuse a recorded environment whose effective GOFLAGS carries a flag of REQ-LVM-005 class 8, never under the verifier process's own environment, and refuse as the thirteenth reject class unless the stored manifest equals the derived one — every derived call present with the same command and package set, and the non-Go input records and graph comparisons equal — so that a manifest derived at an earlier HEAD that omits a package changed since, or a reader found since, is refused; a manifest that equals the derivation shall remain valid across later commits that do not change the derived set (its attempts stay bound to tree and HEAD, so the calls are re-run).
- **REQ-LVM-017 (state).** When any landing command evaluates whether the gate is on, it shall resolve the integration branch as the held window record's branch, else the configured integration target; with none configured the project has not opted in and the gate shall read off; with one configured whose ref cannot be resolved the command shall refuse the landing with the named error `gate_state_integration_branch_unresolvable` (fail-closed: the merge step cannot run without that branch, so no landing is wedged, and repairing the branch configuration or ref needs no landing); with the branch resolved it shall read the committed blob `<integration-branch>:.moai/config/sections/workflow.yaml`, consult no working tree, and tell an absent path (an existence check, `git cat-file -e`) from a failed read: an absent path, an absent key or an explicit false shall read off, an explicit true shall read on, and a failed read of a present path, an unparseable file or a non-boolean value shall read on with the notice `gate_state_unreadable` and an audit row (a landing that satisfies the gate, including the card that repairs the file, is still admitted); a card branch's copy of the key shall have no effect, and an enabling or reverting commit on the integration branch shall take effect when it lands, whatever commit the primary checkout is on. For the mutating commands (`complete`, the merge step) a refusal exits non-zero before any state changes; for the read-only evaluations (merge-readiness condition (d), `manifest verify`) the named error is the printed refusal and the exit is non-zero, nothing being written; REQ-LVM-007 keeps holding because today's merge verb already stops at `integrationMergeWorktree` for a missing configured branch.
- **REQ-LVM-018 (event).** When the gate is on, `complete` shall take the cited receipt ids from the located verdict file's single machine line `audit_receipt: rcpt-<id>[,rcpt-<id>…]` (ids matching `rcpt-[a-z0-9]{20,40}`, split on commas, no other characters) for a SPEC card and for a SPEC-less card alike, and shall refuse when the line is missing, duplicated, empty, `none` or malformed, or when a cited id is absent from the store; the sync-audit protocol and the audit artifact convention, with the template mirror of the protocol, shall state the `audit_receipt machine line`.

## 5. Constraints and prerequisites

- C1. Git-flow window path only; the github-flow pull-request edge (`internal/cli/factory_card.go:2071-2073`) is not touched.
- C2. Existing audit checks are consumed as they are; this SPEC adds readers, the receipt commit field and bindings, never a bypass.
- C3. The gate ships off in the template and stays off on this SPEC's branch (REQ-LVM-012). Piece A lands under the current rules; its own landing is not the gate's first live use.
- C4. No time estimates; milestones are ordered by dependency.
- C5. **Prerequisites, not steps of this card** (board `0577` P1): a gate counts as on only where the judging build contains it. The governed commands (remeasure, `complete`, merge step) are invoked by path from a binary built from the landing HEAD's main, never through a PATH-resolved installed binary that may lag; no reinstall is implied. The MCP server that writes receipts must run a build containing REQ-LVM-009 before a receipt is accepted as bound.
- C6. Cards already merge-ready at the switch are not re-audited for it: each still takes the HEAD-confirmation audit at landing (board `2c51`) and, with the gate on, needs a verdict carrying the `audit_receipt` machine line and a bound receipt, which that new audit produces; its landing re-measure is done in the structured form. Measured transition picture: `research.md` §10.
- C7. The integration branch name is read from the common-root configuration as ruled (board `470c`); that read is not the gate key and is unchanged by this SPEC.

## 8. Exclusions

### Out of Scope — landing paths and policy

- The github-flow pull-request delivery edge, CodeRabbit gating, and CI-side verification.
- Skipping or shortening the HEAD confirmation audit for any reason, patch-id equality included.
- Train stacking, a second writer of the integration branch, queue admission, lane leasing and card classification.
- Re-auditing cards because of the switch itself, reinstalling the installed binary, and moving or fixing the primary checkout.

### Out of Scope — verification content

- Choosing which tests a card should add; the manifest records what the b2cd rule requires.
- Forwarding the child stdout of `moai integration remeasure` (the known swallow defect); a script-wrapped call does not satisfy the gate while it is on.
- Reusing a record across a moved integration tip, and any base-equals-tip relaxation.

### Out of Scope — slot subsystem and views

- Slot capacity, load and memory headroom, wall-clock-bound package exclusion, a slot wrapper verb, any change to lease liveness semantics.
- A ready-to-land view and landing metrics.
