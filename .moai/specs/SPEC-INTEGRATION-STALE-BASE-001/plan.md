### B.2 The gate function (proposed `factory.EvaluateBaseFreshness`, new file `internal/factory/base_freshness.go`)

Input: `{Root, Dir (candidate tree), CardID, IntegrationBranch, RequestedBranch, K, Enabled}` plus a git-runner seam (the `MergeStepSeams.Git` shape, `integration_merge_step.go:129-135`). Output: `{Applicable, Admit, Behind, Tip, Tree, Cause}` plus the rendered refusal text.

1. Applicability: `Applicable` only with a non-empty `CardID` and `Dir` on a branch (its full HEAD ref, read from the tree with `git symbolic-ref --quiet HEAD` and compared with `refs/heads/<configured integration branch>`) other than the configured integration branch and not detached; exit 1 of `symbolic-ref --quiet` means detached HEAD and is not applicable, and any other failure of the read is uncertain and admits with one cause line. Otherwise the gate admits **silently** (REQ-ISB-001: not applicable is not uncertainty, and a leader acquiring for a batch must stay quiet). An unresolvable or missing integration branch is **uncertain, not inapplicable**: with an applicable call it admits with exactly one line naming the cause, like any other step 2-3 failure (REQ-ISB-009, AC-ISB-009).
2. If `RequestedBranch` is non-empty and differs from `IntegrationBranch`, refuse (gate off: advise) with the reason naming both branches, before anything else is read. Otherwise `tip = git rev-parse --verify integrationBranchRef(<branch>)`, that is `refs/heads/<branch>`, the spelling `RunRemeasure` also uses for its base (an empty or unresolvable `<branch>` takes the same uncertain path); `tree = git rev-parse HEAD^{tree}` (as `headTreeSHA`); any git failure admits with the line `base-freshness: not measured — git: <err>`.
3. `rec, err = ReadRemeasureRecord(Root, tree)`; `err == nil` then `ValidateRemeasureRecord(rec)`. A failure here is the record refusal (message 2) and ends the evaluation (L cannot be measured without a stored base).
   With a valid record: `git merge-base --is-ancestor <rec.Base> <tip>`; non-ancestor is stale (message 1 with L reported as `unrelated`). Otherwise `L = git rev-list --count --first-parent <rec.Base>..<branch>`.
4. Verdict: refuse when the record step failed (message 2) or when `L > K` / non-ancestor (message 1).
5. `Enabled == false` turns a refusal into the advisory line `base-freshness (advisory, gate off): would refuse — <cause>` and admits.

`git rev-list --count --first-parent` is the landing count of spec.md §A.3 (measured 40 versus 664 for the same range in the pinned tree).

### B.4 K greater than zero (what it means, and what it does not)

K only decides entry. At `K = 0` (shipped) the entry check equals the merge step's cause 2. At `K > 0` a lane up to K landings behind may queue behind a live holder and re-absorb and re-measure while it waits (the merge step reads the record for the tree pinned at merge time, `:321`), so K buys queue-wait slack and not a relaxed merge. The merge step stays exact; `AC-ISB-010` pins that. Promotion-time staleness (a lane fresh at entry, stale at promotion) stays governed by cause 2: the grant gate type carries only a card id (`integration_window_ops.go:369`), and resolving a card's worktree there would pull the factory record into the window-queue package; Out of Scope in spec.md §C and decision-index Q3.

### B.5 Fail-open versus fail-closed (constraint 5)

**Decision: fail-open on uncertainty, fail-closed on positive evidence.** Refuse only when the gate has positively measured `L > K` or positively found no valid record for a determinable tree. Any inability to measure in an applicable call (config unreadable, K negative, git error, integration branch unresolved) admits and prints one line naming the cause; the not-applicable cases (no card id, cwd on the integration branch or detached) admit silently (B.2 step 1).

Justification: (i) the gate is an early, cheap refusal in front of an authority that is itself strict (`integration_merge_step.go:321-335`), so a wrongly-admitted lane costs one window turn that cause 1 or 2 then refuses and releases; a wrongly-refused lane costs a blocked landing with no in-band escape; (ii) the same posture is stated by the nearest sibling (`integration_settings_drift.go:253-258`: "a lane blocked from integrating because git could not be run is a worse failure than an unmeasured tree that says so in its output"); (iii) `CandidateHoldRefusal` fails closed on an unreadable store (`integration_window_ops.go:396-409`), but that gate guards a verdict that exists nowhere else, while this gate duplicates a check that the merge step enforces anyway. The refusal layer is additionally opt-in (`enabled: false`), so an operator who wants the fail-closed variant can request it as a follow-up SPEC; this SPEC does not provide one.
