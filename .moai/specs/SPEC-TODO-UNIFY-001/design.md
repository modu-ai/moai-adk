## §D.2 The warning alias (REQ-TU-001 to REQ-TU-003)

**Shape.** `NewGTDCommand` keeps building from `newTodoCmd()`. After M4 it adds nothing else (the stage verbs are on the todo tree), so `gtd` is the todo tree under another name, which is what REQ-TU-001 states.

**The warning (revision 3: printed from the run step, not from a pre-run hook).** Cobra v1.10.2 orders `execute` (`func (c *Command) execute` at `command.go:905`, re-read this revision, `research.md` §R.11) as: parse flags (`:919`), return on a help flag (`:935`), `ValidateArgs` (`:968`), the persistent pre-run hook (`:985`), the local pre-run hook (`:999`), **`ValidateRequiredFlags` (`:1007`) and `ValidateFlagGroups` (`:1010`), then the run step (`:1014`)**. Iteration 2 found that a warning placed in the pre-run hook (`:985`) therefore prints before a missing-required-flag refusal and before a flag-group refusal: three stage verbs carry required flags (`capture --event`, `clarify --disposition`, `organize --class`, `gtd.go:98,121,158`) and `--auto`, `--auto-lane`, `--auto-leader` are mutually exclusive (`todo.go:356`), so `gtd capture x` would warn and then refuse. The design therefore changes where the warning is printed rather than narrowing REQ-TU-003: `NewGTDCommand` builds the tree from `newTodoCmd()` and then walks it once, wrapping the `RunE` of every runnable command (the parent and every verb; no command in the two trees sets `Run`: `git grep -n -w -F 'Run:'` over the constructor files printed two lines, both the `Run` field of `factory.GitLandedQuerier` (`todo.go:1534`, `todo_pr.go:237`), not a cobra command, and `git grep -n -E '\.Run\s*='` over the same files printed nothing, exit 1; the positive control `git grep -c -w -F 'RunE:'` printed 5, 1, and 6 for `gtd.go`, `gtd_answer.go`, and `todo.go`; research.md E-22) with a function that writes the warning and then calls the original handler. The run step is reached only after argument, required-flag, and flag-group validation and after both pre-run hooks, so every refusal that precedes the handler (a mistyped verb, a missing argument, an unknown flag, a missing required flag, a conflicting flag group, and the lane guard's refusal, which lives in the persistent pre-run hook) prints no warning and is byte-identical to the `todo` form's. "Exactly one" holds per construction: the wrapper keeps a per-command-tree `warned` flag in the closure `NewGTDCommand` creates (a package variable would carry over between tests that build several trees in one process), so a handler that calls another command's `RunE` internally cannot print twice. The text goes to the command's stderr, never stdout, and follows the existing deprecation convention (`Warning:` prefix; precedent `warnDeprecatedAgentModelFlags` in `agent_model_flags_retired.go`). Its first line is `Warning: moai gtd has been renamed to moai todo`; it names the `moai todo` spelling of what was run (the verb token is taken from the executing command's path) and states removal one release after the release that first carries the warning. Stderr order for an executed invocation is the pre-run hook's own notices (`warnTempOriginQueueRefusal`, `todo.go:337`), then the warning, then the handler's stderr; the parity test therefore compares the `todo` stderr with the warning block removed.

**The removal statement** is one constant. AC-TU-001 asserts the warning contains it and that it is not empty, so an unset constant cannot ship. No release number is hard-coded (Q2).

**Why not hide `gtd`.** The existing help-parity test requires `gtd --help` and `todo --help` bodies to be equal modulo the name; hiding the command from the root listing removes the discoverability the grace period exists to give. Not done; revisitable.

**Why the lane guard still sees the right name.** `todoSurfaceName` already reports the spelling the operator typed, so the guard's refusal text stays truthful under both names.

**Dependency-initialisation.** `gtd` is not in `trivialCommands` and must not be added: the queue verbs read dependencies, and a warning alias that skipped initialisation would diverge from the `todo` form.

## §D.3 The substitution mechanism (REQ-TU-009 to REQ-TU-011)

Hand-editing 67 files and about 244 lines is the failure mode the card names. The mechanism is one script, `scripts/gtd-to-todo-substitute.sh`, POSIX `sh` plus `sed` without `-i` (write to a temporary file and move it, so it behaves the same on macOS and Linux), driven by a class table and an allowlist file. Whether `sh` is available to the test on every CI runner is not measured; the test fails loudly rather than skipping if it is absent, and the script moves to a Go helper in that case (decided at M7 RED).

**Class table.**

| Class | Token forms | Action |
|-------|-------------|--------|
| S1 prose command | `moai gtd <word>` where `<word>` is a queue verb (the 26 present plus the `spec` verb M3b registers plus the six stage verbs, 33 in all, every one registered on `todo` once M3b and M4 have landed) or end of token | `moai todo <word>` |
| S2 slash | `/moai gtd`, `/moai:gtd` | `/moai todo`, `/moai:todo` |
| X1 reviewed edits | argument vectors (`'moai', 'gtd'`), environment variable names (`CUTOVER_GTD_LIST_CMD`), in-tree error and help strings | not touched by the script; edited in M7 with their own tests |
| E1 history | `.moai/specs/**`, `.moai/reports/**`, `CHANGELOG.md` | excluded |
| E2 binary | any path `git grep -I` treats as binary | excluded |
| E3 recorded fixtures | `internal/cli/testdata/codex-rollouts-t1171/**`, `internal/template/testdata/binding_ledger.json` | excluded |
| E4 internals | Go identifiers `GTD*`, `gtd_*` names, `gtd-<hex>` ids, `.moai/gtd/`, the `internal/factory/gtd_*.go` and `backlog_gtd_schema.go` contents, and the path `workflows/gtd.md` wherever it is named | excluded (Q3) |

| E6 always-loaded | `AGENTS.md`, `internal/template/templates/AGENTS.md.tmpl` | excluded from M8; edited by hand in M9 |

The earlier class that renamed `workflows/gtd.md` and merged the `moai-gtd` docs-site pages is dropped: the path is an identifier (`research.md` §R.10) and the pages are URLs; both wait for the removal release.

**The input set** is `git ls-files` intersected with the S1 and S2 patterns minus E1 to E6, never a filesystem walk, so untracked scratch cannot be touched.

**Dry-run contract.** `--dry-run` prints one line per file (`would-change <path> <count>`) and a total, changes nothing, and exits 0. The set it prints must equal the pre-flight set (E-01) minus the excluded classes; M8 compares the two sets and stops on any difference.

**Idempotence (REQ-TU-010).** After `--apply`, a second run prints a total of 0 and `--apply` changes no file (`git status --short` empty for the touched paths).

**Residual ledger (REQ-TU-011).** `TestNoResidualGTDSpelling` walks the tracked guidance corpus (S1 and S2 scope, same exclusions), reads the allowlist file the script reads, and fails on any `moai gtd` or `/moai gtd` outside it. Safeguards: it asserts the swept file count is at least 5,000 (an empty sweep is not a pass); it asserts every path E-01 printed that is not in E3 or E6 is among the swept set; and a fixture containing a planted `moai gtd add` line proves the test can go red. It runs in the ordinary suite, so a later edit that reintroduces the spelling is caught by CI without anyone asking.

**Docs-site obligations in the same batch.** Four locales change together; the locale-parity baseline is not extended; the docs-site verification recipe (warning-free build, parity, URL and emoji scans) runs before the batch is accepted.

## §D.4 The six stage verbs (REQ-TU-004 to REQ-TU-006)

All six are absorbed (Q1): the constructors stay where they are and their registration line moves from `NewGTDCommand` to `newTodoCmd`; the `gtd`-only registration line is deleted, so `gtd` inherits the verbs through the shared tree. The mistyped-verb guard builds its known-verb list from the tree, so no separate list changes. No inventory table is produced: nothing is deleted, so there is no disposition to measure beyond the one flag below.

**The verb count (revision 3, D18).** Baseline, measured on a `moai` built from this tree at HEAD `3dc1052f6f`: `moai todo --help` lists 26 verbs and `moai gtd --help` lists 32 (the 26 plus the six stage verbs); the listing was counted by a script over each help page's COMMANDS block (`research.md` §R.2 E-19, E-20). The expected sets are 26 + 1 (`spec`, registered by M3b, plan §E) + 6 (the stage verbs, registered by M4) = **33 on each tree**. Run order is M2b, M3b, M4 (`plan.md` §A), so the count AC-TU-004 pins is read after both have landed; between M3b and M4 the `todo` tree holds 27 and the `gtd` tree 33, and no criterion is read in that window. The test enumerates the tree's own subcommands (`newTodoCmd().Commands()`, which carries no cobra-generated `help` or `completion` entry because those exist only on the root) and compares the set of names with the literal 33-name list in the test.

**Lane classification (REQ-TU-006).** `reflect` reads through a read store (`ReflectGTDStore` over `newTodoReadStore`); its `--rebuild-projection` flag calls `BuildPrivateGTDProjectionFromStore`, which creates temporary files and renames them into the projection directory (`internal/graph/gtd_private.go:179`, `:264`, `:273`), so the flag form writes. The guard therefore admits `reflect` only when that flag is absent and refuses the flag form with the standing text; `capture`, `clarify`, `organize`, `engage`, and `answer` write (queue rows, GTD tables, or the answers directory) and stay refused. AC-TU-006 enumerates the table, so a verb added later without a classification fails the test instead of inheriting the refusal by default.

**Guidance executes (REQ-TU-005).** `TestGuidanceVerbsResolve` extracts every `moai todo <word>` and `moai gtd <word>` token from the queue guidance corpus (the workflow skill in both trees, the router skill, the READMEs, the docs-site queue pages, and the help `Long` texts) and resolves each against the command tree. A token that resolves to no verb fails with its file and line. This is the t1590 clause as a standing test, not a one-time check.

## §D.5 The lane's own-card done (REQ-TU-015 to REQ-TU-017, REQ-TU-020, REQ-TU-021, REQ-TU-025)

**Two layers, deliberately.** The guard decides whether a lane may attempt `done`; the verb decides whether the close is evidenced.

1. *Guard layer.* In `todoRefuseLaneMutation`, a lane session's `done` is admitted when the single argument names the card the lane currently holds. "Holds" is read from the same record the dispatch path writes (the queue's current-dispatch record and the factory assignment whose owner label equals the lane's normalised label). Any other argument, any other verb, or an unreadable record is refused with the existing refusal text, so REQ-TU-016's matrix is the old behaviour plus one admitted shape.
2. *Verb layer.* When the caller is a lane session, `done` behaves as if `--require-landed` were set: it asks the existing landing predicate (the closed two-form evidence set of the auto-done scan) and refuses without evidence. This reuses `AutoDoneDecide`'s evidence forms and misfire guards rather than restating them.

**The automatic receipt (REQ-TU-017; Q5, leader-confirmed 10-18 conditional).** The gate is unchanged: `VerifyBinding` still demands the leader role marker, an issuer that is not the performing owner, the card uuid, the run, the version, and an equal non-empty evidence hash. What changes is who may mint, and only at one moment: **inside the factory write transaction of the closing edge T29** (`FactoryDB.Transition`, whose DSN takes the write lock at BEGIN, `card_transition.go:351`). Iteration 2 (D16, D17) showed that a verifier which reads the card's working tree and trusts the record file's name is satisfiable with stale or mismatched evidence, so revision 3 changes both what is read and where.

**Where the facts are read from.** Every fact is read from a git object the factory row names, never from the card's worktree files or `HEAD`. The row carries the merge commit (`MergeSHA`, recorded by T16 after `verifyMerge` checked it) and the evidence commit (`EvidenceSHA`, recorded when the card entered `sync-audit`, T11). A commit and its tree are immutable once named, so a lane that edits its working tree, moves its branch, or amends a file cannot change what a fact reads, **provided the read is made so that git hands back the named object and nothing else**. Revision 3 did not guarantee that, because it named the existing `gitRead`, which trims the output and does not disable replacement objects; the reader below (revision 4, D31) does, and a lane's replacement ref, graft file, or shallow file is then either ignored or refused. The only mutable inputs are the card row, which is read inside the transaction, and the re-measure record file, which is read once inside the transaction (see TOCTOU below).

| (2a) the merge is the recorded two-parent merge | re-check, as T16 did: `rev-list --parents -n 1 <MergeSHA>` shows three fields, and `<MergeSHA>^{tree}` equals `<MergeSHA>^2^{tree}`; the second parent is the card tip | `verifyMerge`'s own reads, repeated at issuance, through the raw reader below |

**The reader (revision 4, D31).** The existing `gitRead` (`card_evidence.go:19-34`) runs plain `git -C <dir> <args>` and returns `strings.TrimSpace(string(out))`. It is right for the one-line answers the older edges read and is left unchanged. For facts 2 and 3 it is wrong in two ways, both reproduced in a throwaway repository (`research.md` §R.16): (1) trimming the whole output of a NUL-separated list strips leading whitespace from the FIRST path, so a card-authored path ` .moai/reports/<card>/x` (a top-level directory whose name begins with a space) reads as `.moai/reports/<card>/x` and passes the reports-boundary test of 2c; (2) a replacement ref in the shared repository changes what a named commit reads as: with `refs/replace/<E>` pointing at a commit that carries the card tip's tree, `git diff --name-only -z E T` printed nothing, while with `--no-replace-objects` (or `GIT_NO_REPLACE_OBJECTS=1`) it listed the changed paths, and `git rev-parse E` still printed `E`, so the names the row records give no sign of it. A third rewriting mechanism is not covered by that option: a graft file or a shallow file in the shared git directory made the tip commit parentless under the default and under `--no-replace-objects` alike, and both files resolve to the common git directory from a linked worktree (`git rev-parse --git-path info/grafts` and `--git-path shallow` printed paths under the main checkout's `.git`), so a lane's own tree reaches them. Either could rewrite the parent count of 2a and the first-parent comparison of 2c.

The fact evaluator therefore makes every git read through one new function, `gitReadRaw`, placed beside `gitRead` in `card_evidence.go`: it runs `git -C <dir> --no-replace-objects <args>` with `gitenv.Env()` and returns standard output as bytes exactly as printed, with no trimming; a caller that wants text trims explicitly, and a caller that parses a `-z` list splits on NUL and compares each entry as printed. The evaluator calls no other git reader (a test scans its source: it names no `gitRead(` and names `gitReadRaw(` at least once, so an empty scan cannot read as a pass). Before any fact is read it resolves `git rev-parse --git-path info/grafts` and `--git-path shallow` and, when either names an existing file, issues nothing (fail-closed; a repository that really is shallow reads as absent evidence and the leader approves by hand). The option is chosen over the environment variable because it sits in the argument vector, where a test can assert it; git(1), read locally (`man git`), says of it: "Do not use replacement refs to replace Git objects. This is equivalent to exporting the GIT_NO_REPLACE_OBJECTS environment variable with any value." The residuals, named: a lane able to rewrite the object store itself is outside this reader (the SPEC's standing residual is a lane-authored verdict anyway); and the graft and shallow check is made before the reads, so a lane that writes such a file inside the few milliseconds of the evaluator's reads could still pass it. The window is inside the factory write transaction and needs a writer in the shared git directory at that moment.

**Why fact 2c is "the card adds nothing but its reports after the audit, main excepted", and what it lets through.** The rule must admit the flows lanes run today and nothing wider, and measuring three landed cards (`research.md` §R.14) found two flows, so the first rule tried was too narrow. Let `A` be the paths in which the card tip differs from the audited (evidence) commit and `D` the paths in which the card tip differs from the merge's first parent (the integration tip the merge lands on, so `D` is the card's total contribution to main). The rule is: every path in `A` ∩ `D` lies under `.moai/reports/<card-id>/`. A path in `A` but not in `D` holds, at the card tip, exactly what the integration branch holds, so it came from main (an absorption after the audit), not from the card; a path in both was changed after the audit and differs from main, so only the card can have authored it, and the only such paths admitted are the card's own report files, because the verdict file is committed after the commit it names.

Measured with `ad_rule.py` (a script that runs `git -C <own path> diff --name-only --no-renames -z` for both sets): **t1856 and t1837** (audit at the absorbed head, evidence committed after): `A` = 2 paths (the card's `sync-audit.md` and `verdict.md`), the narrow rule R1 "all of `A` under reports" and the rule above (R2) both pass. **t1812** (audit first, then main absorbed, then re-measure and landing, the landing-train order of board record `d-20261018T012631Z-2918`): `A` = 254 paths (the absorbed main content), `D` = 5, `A` ∩ `D` = 2, R1 fails with 252 violations and R2 passes with 0. So "card tip equals the audited commit" refuses all three, R1 refuses the landing-train flow, and R2 admits all three while still refusing the case the audit raised: a PASS recorded at an early commit followed by a lane code commit changes a path that is in `A` and in `D` and not under reports, so it is refused. The revision-2 rule ("`audited_sha` is an ancestor of the integration branch") admits that case. What R2 does not do: it does not claim the audit saw the absorbed main (it did not); the interaction of the absorbed content with the card's code is what fact 3 measures, a re-measure of the integrated tree against the first parent. A lane that edits a file after the audit to content neither audited nor on main, or resolves an absorption conflict by taking its own version, is refused and falls to the leader. Two over-refusals are accepted in the fail-closed direction: a file that both the card and main changed in different hunks after the audit lands in `A` ∩ `D` even though the absorption was clean (a three-way tree comparison would admit it; it needs `git merge-tree`, a newer git than the rest of the verifier assumes, so it is not taken), and a card whose verdict files are numbered by a scheme the existing `-iter<N>` pattern does not read (`sync-audit-r2.md` to `sync-audit-r4.md` beside `sync-audit.md` in the t1794 report directory, read from the t1812 diff listing) ties at iteration 1 and reads as absent. Both fall to the leader's manual approval. The git reads run while the transaction holds the factory write lock; T16's own `verifyMerge` already does the same inside its transaction (`card_transition.go:715-716`), so the lock duration of a handful of local `git` reads is an existing pattern, not a new cost class.

**Why fact 3 compares the fields.** `ReadRemeasureRecord` deliberately returns `rec.Tree` and `rec.Base` as written (the file name is the key, not the content), and `ValidateRemeasureRecord` checks only that they are non-empty full SHAs. So a record stored under the merged tree's file name that names another tree validates today. `VerifyRemeasureBinding` closes that for the automatic path. The base rule is equality with the merge's first parent: the T16 tree-equality check (`:313`) is satisfiable only when the card tip already holds the integration tip the merge is made onto, so the re-measure's absorbed base (`git merge-base <integration> HEAD`, `RunRemeasure`, `integration_remeasure.go:688-689`) is that tip. Measured on the three cards of §R.14: the record's `tree` equals the merged tree and its `base` equals the merge's first parent in all three (t1856, t1837, and t1812, whose audit predates the absorption). A flow where they differ (the integration branch moved after the re-measure) fails the fact and falls to the leader, whose remedy is a fresh absorb and re-measure.

**TOCTOU.** The check and the use are one transaction, not one held integration window: the window is a coordination signal whose `acquire` is not atomic (`.claude/rules/local/gitflow-lane-protocol.md` §3), so nothing here relies on it. Inside `Transition` the order is: load the row, verify the edge's own guards (decider, landing reachability), then, when the request carries the automatic-issuance flag set by the close helper and the store holds no receipt for the (card, run) and no revocation, evaluate facts 1 to 3, insert the receipt (`issuer` `auto`, `issuer_role` `leader`, the row's version and `EvidenceSHA`), and run the existing `verifyTransitionApproval`, which now finds the receipt; the commit then writes the edge and re-stamps the receipt to the post-transition version. Any failure before the commit rolls back the receipt with the edge: no orphan receipt remains and no edge commits without one. The facts that are git objects, read raw with replacement objects off, cannot change between check and use (the graft and shallow check is the one exception, named in the reader paragraph above); the card row cannot change because the transaction holds the write lock; the record file is read once, and a later overwrite of that file does not un-issue a receipt that the transaction already wrote (a later invalid re-measure of the same tree is what REQ-TU-025's revocation is for). A receipt issued in a separate, earlier transaction would break the first property (an orphan receipt after a refused edge), which is why AC-TU-016 carries a rollback row.

If any fact is absent the transaction issues nothing, the edge is refused with the gate's receipt-absent error, and the card waits for `moai factory approve` (the leader's manual path, still lane-refused). A receipt that already exists for the (card, run), leader-issued or stale, is never overwritten by the automatic path: it is verified as it is, and a refusal stands until the leader re-issues. The receipt is written with `Issuer: "auto"` and `IssuerRole: leader` (the role marker is what the gate accepts; the issuer string is what distinguishes it). `CanonicalApprovalOwnerLabel("auto")` is `auto`, which never equals a lane label, so the performer-is-not-approver clause holds without change.

**The kind is carried by a value the manual path cannot write (revision 4, D30).** Iteration 3 (P11) found that the string alone does not distinguish: the table is keyed `(card_uuid, run_id)` with replace-on-conflict and `moai factory approve --issuer` forwards any non-empty string, so a leader receipt carrying `auto` was indistinguishable from an automatic one, and an exclusion "keyed on the `auto` issuer" could have revoked it, against REQ-TU-025. The writers of the table were enumerated: `git grep -n -E 'INTO leader_approvals|UPDATE leader_approvals' -- internal cmd ':!*_test.go'` printed `leader_approval.go:173` (the insert in `IssueLeaderApproval`) and `card_transition.go:849` (the re-stamp, which sets `factory_version` only), and `IssueLeaderApproval` has one non-test caller, `leader_approval_gate.go:350` (research.md E-25). So one function is the whole manual path, and the narrowest correct mechanism is to reserve the value there: **`IssueLeaderApproval` refuses an issuer equal to `auto` after trimming, compared without regard to case, with `ErrApprovalIssuer`, writing nothing**, so `moai factory approve --issuer auto` (and `AUTO`) fails and a row whose issuer is `auto` can only have been written by the automatic path's own unexported transaction-level insert. A separate column was considered and not taken (§D.9). Two cases the key leaves, both stated: (i) a leader receipt written after an automatic one for the same card and run replaces it (replace-on-conflict) and carries the leader's issuer, so it is no longer an `auto` receipt and a standing revocation row does not touch it; (ii) a row that already carries `auto` from before this change cannot be told from an automatic one: no tracked code writes it (`git grep -n -E 'Issuer: *"auto"' -- internal cmd ':!*_test.go'` printed nothing, E-25), and M2a's pre-flight counts such rows in the project's factory store and returns a blocker report on a non-zero count rather than assuming none exist.

**Revocation (REQ-TU-025).** A revocation record keyed by (card uuid, run id) lives beside the receipt store (an additive table owned by M2a). The verifier excludes an `auto` receipt that has a revocation row, which reads as receipt-absent; the issuing function refuses while a revocation row exists for the pair; a leader-issued receipt is unaffected because the exclusion is keyed on the issuer `auto`, which the manual path refuses to write (a revocation recorded for a card whose receipt is leader-issued blocks later automatic issuance for the pair and leaves that receipt valid). The revocation surface is a leader-only flag of `moai factory approve`; the lane refusal that verb already applies covers it.

**What this reverses, named (D23).** The draft `SPEC-FACTORY-COMPLETION-RECOVERY-001` states REQ-FCR-014 ("No lane surface shall mint a receipt, invoke the reaper, or reassign a card", `spec.md:102`), and the code carries it in three places: the `@MX:REASON` of `newFactoryApproveCommand` (`leader_approval_gate.go:282`, "any second minting path would break the lane boundary this verb enforces") and two doc comments in `leader_approval.go` (`:9-13`, `:144-148`). The lane's own-card `done` is a lane surface, and it now causes a receipt to be minted. REQ-TU-017 is therefore a deliberate, narrow exception: the receipt is minted by the transition transaction (not by a lane-callable verb: `IssueLeaderApproval` keeps its leader-only role check and is not called; a new unexported transaction-level insert writes the row), only for `merged-local` cards, only on the three facts, and revocably. Which text wins: this SPEC's, for the one path REQ-TU-017 defines, because the leader confirmed it on 10-18 and the draft is `status: draft` and unrun; everywhere else REQ-FCR-014 stands, and the draft is not edited here. M2a updates the three code comments to name the REQ-TU-017 path, and its pre-flight re-reads the draft's status: if the draft has moved to `in-progress` or `completed`, M2a returns a blocker report naming REQ-FCR-014 instead of resolving by guess (`plan.md` §C item 3, §H). REQ-FCR-016 (no recovery path completes a card) is not reversed: the auto-done scan and the lane's `done` are completion paths gated by evidence, not recovery paths (reaper, watchdog, reassign).

**The close helper and its order (REQ-TU-020).** Shared by the lane path and the scan: (1) if the factory row is `merged-local`, request edge T29 with the row's expected version, decider `audit`, the card's backlog uuid, and the automatic-issuance flag; inside that one transaction the facts are evaluated and the receipt issued (§D.5 above), the transition's own receipt gate verifies it, and the commit re-stamps it to the post-transition version, the chain already used for T18 and T20; a receipt the leader issued earlier is found by the same gate and used as it is; (2) archive the queue row under the held gate, whose verification reads the re-stamped receipt. No factory transaction is held while waiting for the queue lock. **Recovery.** A failure after step 1 and before step 2 leaves the factory row `done` and the queue row open: the helper exits non-zero naming both records. A repeat of the same act finds the factory row already `done`, skips step 1, and completes step 2 under the re-stamped receipt; a failure the other way (step 1 refused) leaves both unchanged and no receipt behind. The factory edge goes first on purpose: the reverse order archives the queue row and leaves a factory row no live card references, which no retry can reach. A queue row left open after step 2 is also closable by the scan, since the re-stamped receipt verifies. A factory row in another state (for example `pushed`) skips step 1: it is not requested, not moved (its row stays byte-identical), and is named in the log; with no automatic receipt for it (fact 1 fails), the queue row closes only under a leader-issued receipt that verifies against that row's own version, and with none the close is refused as receipt-absent (AC-TU-014 carries both rows).

**The log row (REQ-TU-020).** The close appends a row to the existing execution log with `source` set to a new label for the lane path (the scan keeps `auto-land`) and the receipt issuer (`auto`, or the leader's label for a leader-issued receipt), so the automatic paths are distinguishable and a reader of the log can tell which receipts were issued without a leader act. The issuer is read back from the receipt store after the edge commits, not assumed from the path that requested it, so a leader-issued receipt used by the lane's `done` is logged under the leader's label. `todo undone` currently pairs its reversal row with the scan's log rows; M2b extends that pairing to the new label.

**The ten-card criterion (REQ-TU-021).** A fixture builds a queue and factory record with twelve cards, ten with landing evidence, the three facts, and a `merged-local` row, and two without landing evidence; it runs the closing acts and asserts exactly the ten end `done` in both records with no operator input and the two stay open (the negative control). At sync, a live read-only command lists the ten most recent cards with landing evidence and their states, and the sync record carries its output; any card whose factory row is not `merged-local` is named there as outside this SPEC's edge, and for every card that does not close the listing names the first absent fact. The listing is expected to show absent facts, not only closes: of eight integration merges sampled at revision 3, three (t1856, t1837, t1812) carry a committed `sync-audit.md` in the card tip and five (t1857, t1852, t1793, t1776, t1732) carry no `.moai/reports/<card-id>/` at all (`research.md` §R.14), and a card without a committed verdict stays with the leader's manual approval by design (fail-closed). The criterion "done is automatic for the most recent ten landed cards" is therefore met only for ten cards whose branches commit their evidence; the fixture proves the mechanism and the live listing reports the rate. That dependence on lanes committing their evidence under `.moai/reports/<card-id>/`, a path `.gitignore:235` ignores, is a known debt (KD-1, `plan.md` §H and `decision-index.md`): fact 2 stays, the SPEC does not require report commits, and a card without a committed verdict is never closed automatically.

## §D.7 The spec_id setter (REQ-TU-022 to REQ-TU-024)

**Why two carriers.** The queue row's `SpecID` is what `contract_report` reads; the factory card's `spec_id` is what kickoff reads (`<worktree>/.moai/specs/<spec_id>`). A setter that wrote one would leave the other empty, which is the observed double repair.

**Which states (revision 3, D20).** The wedge the setter exists for is a card that was **leased** without a spec_id whose SPEC the lane authored afterwards (board record `d-20261010T001732Z-d4e8`: the leader stamped `leased` rows t1616, t1619, t1620 by a conditional UPDATE on an empty spec_id). Iteration 2 found that refusing `leased` and later states left that wedge to the database repair. The identifier is read by exactly two guards, the plan-audit verdict admission at `plan-audit → kickoff` (`card_evidence_readers.go:185-188`, which refuses an empty or malformed `SpecID`) and the audit kickoff at `kickoff → run` (`card_audit_kickoff.go:31`, which builds the SPEC directory path from it), so a first fill is useful from the pick through `kickoff`. The first-fill set is therefore `picked`, `assigned`, `leased`, `plan`, `plan-audit`, and `kickoff`; `run` and every later state are refused for a first fill, because the last guard that reads the identifier lies behind them and every factory version bump there would stale an in-flight receipt or merge verification for nothing. Terminal states are always refused. The queue row leaves `picked` only through `unpick` (back to queued) or `done` (archived): the other state-changing verbs act on queued cards (`hold` "Park a queued card", `drop` "Discard a queued card", `moai todo --help` of the tree built at HEAD `3dc1052f6f`, read from the help text and not exercised), so "queue row `picked`" holds across the whole range and is the queue-side precondition. Set-once makes the wider range safe: the setter never replaces a held value, so the pointer swap the pick-time freeze guards against (`card_picked.go:184-186`, "its hints and pointers change only while picked") cannot happen through it.

**Flow (set-once per carrier).** Under the queue lock the verb: reads the queue item and requires queue state `picked`; validates the identifier with the homestate pattern `^SPEC-[A-Z0-9]+(?:-[A-Z0-9]+)*$` (so the setter and the existing field-update gate cannot disagree); reads the factory row if one exists and requires its state in the first-fill set above (or, for a completing repeat, any non-terminal state, see below); and applies the per-carrier rule before any write: empty is filled, equal is skipped, different refuses the whole call. It then opens one factory write transaction through a new homestate function. Inside that transaction the function loads the card, sets `spec_id`, bumps the version, appends a `card.fields` event, and runs the queue write in the transaction's pre-commit step (the seam `TransitionRequest.BeforeCommit` already provides for transitions, `card_transition.go:286`, used so a caller can keep the queue's dispatch record in step), then commits. The queue lock is held across all of it, the same order the claim path uses (queue lock, then factory write).

**Failure behaviour.** A failure of the queue write inside the pre-commit step rolls the factory transaction back: both carriers unchanged. A failure of the factory commit after the queue write succeeded leaves the queue carrier set and the factory carrier empty: the verb exits non-zero naming both carriers, and a repeat with the same identifier finds the queue carrier equal (skip) and the factory carrier empty (fill) and succeeds. In that half-written state a different identifier is refused by the per-carrier rule. No sequence leaves a carrier holding a value other than the requested one. The window is one commit wide and the repeat is the recovery; no automatic recovery runs. Fault seams for the two cases follow the existing `cardTransitionFault` pattern (a package variable the test sets).

**The completing repeat (revision 3, D21).** Iteration 2 found that a half-write can be overtaken: lease acquisition needs no spec_id (`guardLeaseAcquire` checks the registered worker and the owner label only, `card_transition.go:582-604`), so between the failed attempt and the leader's repeat the card can move from `assigned` to `leased`, and under the revision-2 state rule the repeat was then refused with the factory carrier still empty. Two measures close it. First, the first-fill set now includes the lease-holding states up to `kickoff` (§D.7 "Which states"), so the lease edge and the stage edges `leased → plan → plan-audit` leave the repeat admitted. Second, the repeat that **completes** a pair (the identifier already held by exactly one carrier, equal to the requested one) is admitted in every non-terminal state: it replaces no held value, and refusing it would leave a divergent pair that no verb can repair. A half-written card cannot pass `plan-audit → kickoff` (the verdict admission refuses an empty factory spec_id), so the only states beyond `kickoff` it can reach are the ones a Class A or B card reaches directly (`leased → run`, T4b admits `run` while the stage is empty), plus the side states `needs-decision`, `blocked`, and the terminal ones. A terminal card is refused: nothing reads the identifier of a finished card, so the divergence is inert there, and the refusal is stated (REQ-TU-023). The version bump the completing repeat makes in a late state stales a receipt bound to the old version (the leader re-issues, the existing re-issue-replaces semantics), which is the recorded cost of the rare case.

**Set-once is the safety property.** The existing freeze ("hints and pointers change only while picked") protects a card whose lane has already started from a pointer swap. The setter never swaps; it fills an empty value, and only before the `run` stage (a completing repeat excepted). A mutant that overwrites a non-empty value fails AC-TU-021.

## §D.9 Alternatives considered and not taken

- **Keep `gtd` as a fully supported alias.** Rejected by the card; it also keeps every guidance surface bilingual.
- **Delete `gtd` now.** Contradicts the one-release grace.
- **Delete the unused stage verbs.** No in-tree caller is not evidence of no use; the tree holds no usage telemetry, five tests pin the CLI path, and deleting removes a documented user-facing feature (Q1).
- **Rename internals and the workflow document with the user-facing name.** Changes persisted formats and identifiers named by rule `paths:` keys, an embed line, and a recorded fixture; separate change (Q3).
- **A SessionEnd observer for automatic done in this SPEC.** Adds a hook under the advisory-check discipline and overlaps t1639 (Q4).
- **A receipt policy that waives the receipt on landing evidence alone.** Removes the gate; the chosen form keeps the gate and proxies it by machine verification (Q5).
- **A lane own-card done that stays on the leader's receipt.** Leaves the ten-card criterion unreachable without a leader act (Q5).
- **Overwrite-capable spec_id edit.** Would reopen the pointer-swap hazard the freeze exists for.
- **Narrow REQ-TU-003 instead of moving the warning (D19).** Printing from the pre-run hook and stating that required-flag and flag-group refusals carry the warning is accurate but leaves `gtd capture x` printing a deprecation notice before an error, and makes the alias's refusals differ from the `todo` form's for the three stage verbs that have required flags. Moving the print to the run step costs one wrapper walk in `NewGTDCommand` and makes the stated boundary true by construction.
- **A verdict corroborated by an audit receipt id (D16, the auditor's "prefer").** `internal/auditreceipt/store.go:15` is a store written by the MCP server, so a fact a lane cannot author exists in principle. Not taken: the sync-audit verdict file carries no machine-readable receipt line today (the `AUDIT-VERDICT:` line with `receipts=` travels in the chat message, `.moai/reports/t1856/sync-audit.md` says so), receipts are minted only where a required backend is configured, and requiring one would be a fourth fact outside the leader-confirmed shape. The lane-authored-verdict residual remains and is named in `research.md` §R.14.
- **Issue the receipt in a separate transaction, or under the integration window (D16 TOCTOU).** A separate transaction leaves an orphan receipt after a refused edge and a gap between the check and the use; the integration window is a coordination signal with a non-atomic `acquire`. The edge's own transaction is the only boundary that makes the facts, the receipt, and the edge commit together.
- **Require the card tip to equal the audited commit.** Refuses every landed flow measured (the verdict file is committed after the commit it names: t1856, t1837, t1812).
- **Require the whole evidence-to-tip diff to lie under the card's reports directory (R1).** Admits t1856 and t1837 and refuses t1812 (252 paths of absorbed main fall outside the directory), i.e. the landing-train order (audit, absorb main, re-measure, complete) would never earn an automatic receipt. The A ∩ D rule of §D.5 admits all three.
- **Admit the setter in every non-terminal state for a first fill.** Simpler to state, but a version bump at `merge-ready` or later stales receipts and merge verification for a card whose SPEC lookup is already behind it; only the completing repeat gets the wide admission.
- **A second known-verb list for the mistyped-verb guard.** The tree already is that list.
- **Resolve the push gate's branch with `factoryResolveIntegrationBranch` (D29, the audit's first alternative).** Its no-configuration answer is the card worktree's own branch, which `complete` refuses and which does not contain the merge commit (§D.6); the guard would still refuse where removed T18 admitted.
- **An explicit `--integration-branch` flag on `decide` (D29).** Exact, and it mirrors `acquire --branch`, but a repository without configuration would then need an input removed T18 never asked for, so the no-configuration row of AC-TU-018 could not hold; it also adds a flag to the verb and to the MCP handler that shares `factoryDecideCards`.
- **Derive the branch from the merge commit's subject (D29).** The merge step writes `Merge <card branch> into <branch> (card <id>, integration merge)` (`internal/factory/integration_merge_step.go:399`); parsing it is exact for tool-authored merges but makes a commit-message format an interface and is a text inference.
- **Persist the integration branch on the card row or in the merge edge's event evidence (D29).** Exact, but it changes the merge edge, which the audit confirmed, for a case the empty-value test covers.
- **A separate `auto` column for the receipt kind (D30).** Works, but it migrates a shared table and the flag must be cleared on replace-on-conflict (a leader re-issue after an automatic receipt would otherwise inherit it and become revocable); the reserved value is one comparison in the one function that is the whole manual path.
- **Harden only the diff read (D31).** A replacement ref or a graft reaches the parent count, the tree equality, and the blob read as well; one reader for every read is simpler than a per-read list.
