# SPEC-HNS-PREFIX-RENAME-001: Harness User-Artifact Prefix Rename (`harness-*` → `hns-*`)

## HISTORY

| Version | Date | Author | Description |

## §A Goal / Context

### A.1 What

Rename the **user-owned harness artifact naming prefix** generated by the `/moai harness` v4 Builder from `harness-<name>` to `hns-<name>`. The rename spans four layers:

1. **Template Builder contract** — the GENERATE-phase artifact naming contract in the Builder docs (`harness-builder.md`, `harness-build-entry.md`, `moai/SKILL.md`, `moai-meta-harness/SKILL.md` + classified secondary docs) emits `hns-<name>-*` names for all six artifact types.
2. **Go recognition logic** — `moai update` preservation, `moai harness list/edit/remove/doctor`, `moai doctor` skill layers, frozen-guard, and prefix-conflict detection recognize `hns-*` as the new canonical user-owned prefix **in addition to** the two legacy generations (`harness-*`, `my-harness-*`).
3. **CI guards** — namespace-leak and split-harness guards cover both `harness-*` and `hns-*` patterns.
4. **Existing local artifacts** — this repo's 3 dev-only specialists, 3 `harness-moaiadk-*` skills, and 1 Runner JS are renamed to `hns-*` form with all cross-references updated.

Directory structure is UNCHANGED: `.claude/agents/harness/`, `.claude/commands/harness/`, and the `/harness:` command namespace keep their names. Only artifact-name prefixes change.

### A.2 Why

- The `harness-` artifact prefix collides visually with six non-artifact "harness" namespaces (`moai-harness-*` template skills, `harness-spec.yaml`, `.moai/harness/` state, `harness.yaml` config, `/harness:` commands, `moai harness` CLI verbs), causing repeated classification errors in audits and sweeps. `hns-` is a visually distinct, grep-unambiguous prefix — it has zero case-sensitive matches anywhere in the production/artifact tree today (live-grep evidence in plan.md §B.2) — and it conforms to the Claude Code lowercase-kebab skill/agent naming convention.
- Precedent: SPEC-V3R6-HARNESS-NAMESPACE-V2-001 already built the dual-recognition mechanism for the `my-harness-*` → `harness-*` migration (REQ-HNS-004 exact-`HasPrefix`, REQ-HNS-005 legacy window). This SPEC extends that mechanism by one generation rather than inventing a new one.
- Backward-compatibility is a hard user requirement: existing user projects with `harness-*` artifacts must NEVER be deleted by `moai update`.

### A.3 Confirmed decisions (closed — do not re-open)

- New prefix: **lowercase `hns-`** (replaces `harness-` in artifact names only). The lowercase form is a final user decision (plan-audit iteration 2): lowercase-kebab matches the Claude Code skill/agent naming convention, so no runtime-acceptance probe and no fallback branch exist. The SPEC ID (SPEC-HNS-PREFIX-RENAME-001) and all REQ/AC ID tokens keep their uppercase forms — IDs are not artifact names.
- Scope: templates + local, full sweep, including local artifact renames in this repo.
- Backward compatibility REQUIRED: recognition of BOTH `harness-*` (legacy) and `hns-*` (new); `my-harness-*` third-generation recognition (existing REQ-HNS-005 window) must not regress.

### A.4 Prefix-generation matrix (normative)

| Artifact surface | New canonical | Legacy gen-2 (preserved) | Legacy gen-3 (preserved) | Preservation mechanism |
|---|---|---|---|---|
| Skills | `.claude/skills/hns-*` | `.claude/skills/harness-*` | `.claude/skills/my-harness-*` | prefix match (`update.go`, `frozen_guard.go`) |
| Runner workflows | `.claude/workflows/hns-*.js` | `.claude/workflows/harness-*.js` | — | prefix match (`update.go`) |
| Specialist agents | `.claude/agents/harness/hns-<name>-*-specialist.md` | `.claude/agents/harness/harness-<name>-*-specialist.md` | — | directory-level (`.claude/agents/harness/` — unchanged) |
| Thin commands | `.claude/commands/harness/<name>.md` | — | — | directory-level (unchanged; command filenames carry no prefix) |
| Verify skill | `hns-<name>-verify` | `harness-<name>-verify` | — | skills prefix match |
| Manifest `runner_workflow` | `hns-<name>-run.js` | `harness-<name>-run.js` | — | doctor reference-integrity |

Note: agents and commands are preserved at the **directory level** in `update.go`, so the rename requires NO update-preservation change for those two surfaces — only skills and workflows prefixes gain `hns-` recognition there. File-level prefix matching in `v4lifecycle.go`, `doctor.go` (harness), `doctor_harness.go`, `doctor_skills.go`, `prefix_conflict.go`, and `frozen_guard.go` DOES require dual-pattern extension.

## §B Requirements (GEARS)

### Group A — Builder GENERATE contract (templates + live mirrors)

- **REQ-HPR-001** The Builder GENERATE contract docs (template `internal/template/templates/.claude/skills/moai/workflows/harness-builder.md`, `harness-build-entry.md`, `.claude/skills/moai/SKILL.md`, `.claude/skills/moai-meta-harness/SKILL.md`, and their live mirrors) shall specify `hns-<name>-*` artifact names for all six generated artifact types: thin-command Runner reference, Runner Workflow `.claude/workflows/hns-<name>-run.js`, specialist agents `.claude/agents/harness/hns-<name>-*-specialist.md`, companion skills `.claude/skills/hns-<name>-*/`, verify skill `hns-<name>-verify`, and the manifest `runner_workflow` field value `hns-<name>-run.js`.
- **REQ-HPR-002** **When** any of the four contract docs is edited, the editing milestone shall restore template↔live byte-parity for that doc pair before the milestone closes.
- **REQ-HPR-003** The rename shall not alter any non-target harness token (see §D Out of Scope): `moai-harness-learner`, `moai-meta-harness`, `harness-spec.yaml`, `.moai/harness/`, the `/harness:` command namespace, the `.claude/commands/harness/` and `.claude/agents/harness/` directory names, `harness.yaml`, the `moai harness` CLI verb set, `handle-harness-observe*` hook names, the CLAUDE.md `<!-- moai:harness-start/end -->` markers, the `harness-generated` catalog tier label, and generic prose uses of the word "harness".
- **REQ-HPR-004** **When** the template sweep executes, every one of the remaining template files matching `harness-` (29 files at plan-time baseline) shall receive a recorded rename-target / non-target disposition (recorded in progress.md §E.2), and only rename-target files shall be edited.

### Group B — `moai update` preservation (dual-pattern)

- **REQ-HPR-005** The `moai update` user-owned path classifiers in `internal/cli/update.go` shall recognize `.claude/skills/hns-*` and `.claude/workflows/hns-*.js` as user-owned, in addition to the existing `harness-*` and `my-harness-*` recognitions.
- **REQ-HPR-006** **When** `moai update` runs against a project containing artifacts of any prefix generation (`hns-*`, `harness-*`, `my-harness-*`), the update shall preserve every such artifact (backup + preserve; zero deletions, zero modifications).
- **REQ-HPR-007** `moai update` shall not delete or modify any artifact under `.claude/skills/hns-*`, `.claude/skills/harness-*`, `.claude/skills/my-harness-*`, `.claude/workflows/hns-*.js`, `.claude/workflows/harness-*.js`, `.claude/agents/harness/`, or `.claude/commands/harness/`.
- **REQ-HPR-008** All new prefix recognitions shall use exact `strings.HasPrefix` path-segment comparison (never `strings.Contains`), so that template-managed `moai-harness-*` skills are never misclassified as user-owned (carry-over of the REQ-HNS-004 discipline to the `hns-` generation). Matching is byte-exact and case-sensitive; no case-folding variant is added.
- **REQ-HPR-009** The harness protection surfaces in `internal/harness/frozen_guard.go` (protected-prefix list) and `internal/harness/prefix_conflict.go` (prefix recognition + suffix trim) shall recognize `hns-` alongside both legacy prefixes.

### Group C — `moai harness` CLI verbs

- **REQ-HPR-010** `moai harness list` shall enumerate harness entries whose artifacts carry either the `hns-<name>*` or the `harness-<name>*` naming (dual-pattern artifact matching in `internal/cli/harness/v4lifecycle.go`).
- **REQ-HPR-011** **When** `moai harness edit` or `moai harness remove` targets a harness `<name>` whose on-disk artifacts carry either prefix (or a mix of both generations), the verb shall resolve and operate on all of that harness's artifacts regardless of prefix generation.
- **REQ-HPR-012** `moai harness doctor` reference-integrity checks shall recognize specialist references matching both `hns-<x>-specialist` and `harness-<x>-specialist` — a dual-pattern extension of `runnerSpecialistRE` in `internal/cli/harness/doctor.go` (plan-time literal `harness-[a-z0-9-]+-specialist`; extended form `(harness|hns)-[a-z0-9-]+-specialist`). Runner resolution requires NO dual-pattern change: `Doctor` resolves the Runner from the manifest `runner_workflow` value via a prefix-agnostic path join, so a `hns-<name>-run.js` manifest value resolves as-is (ground truth verified at plan time; run-phase re-verifies the anchor).
- **REQ-HPR-013** The `moai doctor` skill layers shall handle both prefixes: `internal/cli/doctor_skills.go` shall classify `hns-*` skill directories as user customization (INFO), and `internal/cli/doctor_harness.go` shall include `hns-*` directories in the L1 trigger scan and resolve `skills:` references carrying the `hns-` prefix.

### Group D — CI guards

- **REQ-HPR-014** `internal/template/split_namespace_test.go` (sentinel `SPLIT_HARNESS_NAMESPACE_LEAK`) shall assert embedded-template-tree absence for BOTH the legacy dev-only names (`harness-{release-update,github,release}*`) AND the renamed forms (`hns-{release-update,github,release}*`), across the commands/agents/workflows dimensions it already covers.
- **REQ-HPR-015** `internal/template/namespace_protection_audit_test.go` shall reject embedded template skills carrying the `hns-` prefix in addition to the existing `harness-*` rejection.
- **REQ-HPR-016** **Where** the embedded template FS is distributed, no `hns-*`-named artifact file or directory shall exist in it; `hns-` may appear in the distributed set only as contract-doc prose (the Builder naming contract).
- **REQ-HPR-017** The existing preservation/namespace test suites (`update_safety_test.go`, `update_namespace_harness_v2_test.go`, `update_namespace_harness_v4_test.go`, `update_preserve_my_harness_test.go`, `update_preserve_inventory_test.go`, `inventory_test.go`, `update_security_m2_test.go`, `internal/cli/harness/v4lifecycle_test.go`, `internal/cli/harness/doctor_test.go`, `doctor_skills_test.go`, `doctor_harness_test.go`) shall gain `hns-` cases exercising the new recognition paths, and all pre-existing legacy-prefix cases shall continue to pass unmodified in their assertions.

### Group E — Local artifact rename (this repo)

- **REQ-HPR-018** The three dev-only specialist agents shall be renamed via `git mv` to `.claude/agents/harness/hns-{github,release,release-update}-specialist.md`, with each file's frontmatter `name:` field updated to the `hns-` form.
- **REQ-HPR-019** The three local skills shall be renamed via `git mv` to `.claude/skills/hns-moaiadk-{best-practices,dev-reference,patterns}/`, with each `SKILL.md` frontmatter `name:` field updated to match.
- **REQ-HPR-020** The Runner shall be renamed via `git mv` to `.claude/workflows/hns-release-update-run.js`, and its internal self-referential strings (header comment, specialist-name strings) shall be updated to the `hns-` forms.
- **REQ-HPR-021** **When** the local rename lands, all live-tree cross-references shall be updated consistently: `.claude/commands/harness/{github,release-update,release}.md` subagent + Runner references, `.claude/commands/harness/release-update/manifest.json` (`agent_file`, `runner_workflow` fields), any `skills:` frontmatter references in the four unprefixed specialists (`cli-template`, `hook-ci`, `quality`, `workflow`), and the concrete artifact-name examples in `.claude/rules/moai/development/skill-authoring.md` (live + template mirror). Consistency is verified by `moai harness doctor` exiting 0 and a scoped stale-reference sweep returning zero matches (AC-HPR-011).
- **REQ-HPR-022** The local rename shall not rewrite historical artifacts: `.claude/worktrees/**` snapshot copies, `.moai/specs/**` (other SPECs), `.moai/reports/**`, and memory files remain untouched.

### Group F — Doctrine, neutrality, and closure

- **REQ-HPR-023** `.moai/docs/harness-namespace-doctrine.md` and `.moai/docs/dev-only-commands-isolation.md` shall state the updated namespace policy: `hns-*` is the canonical user-owned artifact prefix; `harness-*` and `my-harness-*` are recognized legacy generations that `moai update` preserves; the Builder emits `hns-` only.
- **REQ-HPR-024** **While** template files are edited, template neutrality (CLAUDE.local.md §25 content classes) shall be preserved: no internal SPEC IDs, REQ tokens, audit citations, internal dates, or commit SHAs may be introduced into `internal/template/templates/**`.
- **REQ-HPR-025** CLAUDE.local.md §21/§24 pointer text shall NOT be edited by any agent in this SPEC; the required pointer updates shall be reported to the user as a flagged follow-up list.
- **REQ-HPR-026** **When** all milestones complete, `make build` shall succeed and `go test ./...` shall pass on the merged tree.

## §C Non-Functional Constraints

- **Ordering invariant (deletion hazard)**: Go recognition (Group B/C, milestone M2) MUST land before the local artifact rename (Group E, milestone M3). Renaming first would leave `hns-*` artifacts unprotected against an intervening `moai update` — the exact hazard the namespace doctrine historically warned about.
- **No behavior change for legacy artifacts**: every existing legacy-prefix test assertion continues to pass; the change is strictly additive recognition plus contract-doc emission wording.
- **Reachability-based acceptance**: acceptance criteria verify matching-logic reachability (go test runs, `moai harness doctor` exit codes, E2E preservation sandboxes) — bare token-presence greps are not sufficient evidence (see acceptance.md §D.2).

## §D Exclusions (Out of Scope)

The following are explicitly out of scope for this SPEC and MUST be preserved verbatim.

### Out of Scope — Template-managed `moai-*` harness namespaces

- `moai-harness-learner` skill (name, directory, catalog entry)
- `moai-meta-harness` skill (name, directory, catalog entry)
- The `moai-harness-*` embedded allowlist semantics in `embedded_namespace_test.go`

### Out of Scope — Non-artifact harness identifiers

- `harness-spec.yaml` bridge file and field names
- `.moai/harness/` state directory
- `harness.yaml` config section and the `moai harness` CLI subcommand verb set
- The `/harness:` command namespace and the `.claude/commands/harness/` directory name
- The `.claude/agents/harness/` directory name (only file prefixes inside it change)
- `handle-harness-observe*` hook wrapper names and `settings.json` hook entries
- CLAUDE.md `<!-- moai:harness-start -->` / `<!-- moai:harness-end -->` markers
- `TierHarnessGenerated = "harness-generated"` catalog tier label in `internal/template/catalog_loader.go`
- Generic prose uses of the word "harness"

### Out of Scope — Historical and ephemeral artifacts

- `.claude/worktrees/**` stale agent-worktree snapshot copies
- Prior SPEC directories under `.moai/specs/**` and reports under `.moai/reports/**`
- Auto-memory files and lessons

### Out of Scope — Legacy prefix retirement

- Sunsetting the `harness-*` or `my-harness-*` recognition windows (deprecation-window closure is a separate follow-up chore SPEC)
- Migration tooling that auto-renames end-user projects' `harness-*` artifacts to `hns-*` (recognition-based backward compat is the chosen path; an explicit migration command is not built here)

### Out of Scope — Maintainer-local docs edits by agents

- CLAUDE.local.md §21/§24 body edits (flagged to the user per REQ-HPR-025; the file is user-owned)
