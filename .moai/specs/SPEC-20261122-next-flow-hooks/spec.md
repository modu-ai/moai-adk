# the NeXT-Flow hook set: session start without git, a widened tool preflight split into a fail-open and a blocking duty, and the Issue-era hooks removed

## Intent

The Claude hook set still carries the Issue era. The claim-verify guard (`moai claim-verify . --hook` before Bash) keys on `issue/<n>` lane branches that no longer exist, so it almost never fires; the hook-receipt handler (`moai hook-receipt` after Bash) writes a log whose 4 MiB cap this project reached on 2026-11-20, so nothing has been recorded since. The session start (55 to 71 ms measured) starts `git` twice to name a lane branch and a claim record nobody acts on. Meanwhile the audit of the integration-branch guard measured that `git branch -C` moves the branch with no reference transaction at all, so a Claude-side backstop is wanted: from a Claude session, the calls that move, copy, rename, delete or push the integration branch shall be refused before they run.

This SPEC reshapes the set per section 4-1 of the hooks, rules and skills report (2026-11-22), the whole-docs report (`claude-code-native-redesign-2026-11-22.md`, sections 3-2, 4-2, 4-3, 15-34, 16-1) and the card's decision notes: the two Issue-era entries are removed; the generic hook set lives in each Claude config folder's `<config>/settings.json` the user picks — never in a project's `.claude/settings.json` by default — and every generated hook exits 0 at once outside a moai project (user decision on the install place; user-scope hooks run in every project regardless of workspace trust, so worktree sessions are covered without a tracked settings file); the session-check duty reads files only (the git HEAD file, the integration-branch record in the common git folder, the worktree's card from the local ledger) and answers within 20 ms; the tool preflight keeps its refusals, replaces the Issue claim-token rule with a read-only ledger reservation check, refuses writes and reference moves from read-only agent types, and is split into an ordinary fail-open duty and a dangerous-call duty that the generated settings carry with `onFailure: "block"` (Claude Code v2.1.295+, hooks.md), so a missing or crashing moai blocks only those calls. The entries are hardened per report 16-1: exec form with the absolute binary path, a `Bash|PowerShell` matcher that also catches Monitor (2.1.314), command splitting like the permission rules, refusal by exit 2 only, never `updatedInput`. The same guarded commands are offered as `permissions.deny` rules on the user's pick, and the update preview names each config folder its hooks part writes. The user picked the fail-open/blocking split (2026-11-22, recorded on the card) revising the earlier fail-open-everything pick for the dangerous part only; no SessionEnd hook.

## Non-goals

- Removing the Codex and OMP hook adapters and the lane Stop hook: the withdrawn-host cards own that work; this SPEC changes the shared base set only as far as the Claude set requires.
- The project-scope values of a project's `.claude/settings.json` — `worktree.baseRef`, key-file `Read` denies, the `permissions.ask` push rule of the report's project table — they stay with their own cards and picks; the hook set writes none of them.
- Installing into every config folder on the machine: only the folders the user picks at install or update (the packaging decision); a folder nobody picked gets no hooks.
- The reference-transaction guard, the landing command and the drift check in card land: landed slices. This SPEC adds the Claude-side backstop of the same refusals only.
- The pre-push receipt and the test-selection work: the remote-copy and test-selection cards.
- A SessionEnd hook and WorktreeCreate, UserPromptSubmit or Stop hooks: the report's design and the user's picks keep them out; the edit-diagnostics opt-in entry stays as it is.
- Moving every HOME state file off the retired folder: the path-root card owns the whole move. Here only the engine log stops using it.

## Requirements

- REQ-1: When the dangerous-call duty checks a Bash call that deletes — rm, rmdir, find -delete, find -exec rm or git clean — the dangerous-call duty shall resolve every named target past absolute paths, the home folder, .., links, the known variables, wrappers and a shell's -c script and refuse the call when a target lies outside the session's worktree and the temp folder · failure: none — /bin/rm, a bash -c script, an env prefix, an xargs hand-off and $HOME spellings are each refused for a target outside both roots, a target inside the worktree or the temp folder passes, and an rm with no resolvable target is left to the ordinary duty.
- REQ-2: When the hook writer renders the generic Claude hook set, the hook writer shall emit no claim-verify entry and no hook-receipt entry and set onFailure to block on the dangerous-call entry alone · failure: none — the planned settings hold neither removed command, no other generated entry carries an onFailure field, and an installed settings file that still holds a removed entry plans as an update that removes it.
- REQ-3: When the session-check duty reports the state of the worktree named by the input's cwd, the session-check duty shall read the checked-out branch from the git HEAD file and the integration branch's name from the record in the common git folder and the worktree's card from the local ledger, each read only and with no subprocess started · failure: none — a detached HEAD, an unborn branch, an absent record, an absent ledger, a folder outside git and a poisoned PATH that fails every program each answer with the fact named in fixed wording and the answer unchanged.
- REQ-4: When the session-check duty answers, the session-check duty shall put the answer inside the documented hookSpecificOutput additionalContext and hold the conversation-language line, the after-compaction advice that restates the card facts of the worktree, a sessionTitle built from the SPEC id or the branch name, a pointer at `moai card show` and the MOAI_* variables the flow needs written to the host's CLAUDE_ENV_FILE, with no Issue, claim or reservation wording · failure: none — text outside additionalContext is silently ignored by the host, no Issue number, claim record or reservation word appears in the answer, the title holds no card number, and the exported variables are plain NAME=value lines the host's shell reads.
- REQ-5: When the ordinary tool-preflight duty checks a call, the ordinary tool-preflight duty shall refuse the same calls the tool-preflight refuses at the base of this change · failure: none — the engine's existing tool-preflight tests pass unedited and no refusal is dropped.
- REQ-6: When the hook writer renders an entry, the hook writer shall write every entry in exec form with the absolute path of the moai binary as command and the duty's arguments as the args array and no shell between · failure: none — no entry holds a shell string, a path placeholder or a relative binary name, and an entry whose command path holds spaces still runs.
- REQ-7: When the host matches a tool call or a session start, the generated entries shall catch the shell tools through a Bash|PowerShell matcher that also catches Monitor commands since Claude Code 2.1.314, the write tools through an Edit|Write|NotebookEdit matcher and the session start through a startup|resume|clear|compact matcher · failure: none — a PowerShell command and a Monitor command reach the preflight duties, a tool of any other name does not, and the session-check duty runs on start, resume, clear and compaction only.
- REQ-8: When a guard reads a Bash command line, the guard shall split the line into its commands the way the permission rules do and unwrap timeout, nice, nohup and xargs wrappers and read the commands that follow a cd · failure: none — a guarded call hidden behind a separator, a wrapper or a cd prefix is still refused, and the default builds' bfs and ugrep search commands are never misread as dangerous.
- REQ-9: When a duty refuses a call, the refusing duty shall answer with exit code 2 alone and never modify the tool input · failure: none — exit 0 and exit 1 never refuse a call, no duty ever returns updatedInput (the host denies an input that changed after auto mode reviewed it), and the refusal's reason is the fixed sentence.
- REQ-10: When the dangerous-call duty checks a Bash call whose branch -c, -C, -m, -M or -D, update-ref or push names the recorded integration branch in any letter case, behind git -C or with an absolute path, or a call that recursively deletes outside the project tree or writes a guarded settings file, the dangerous-call duty shall refuse the call · failure: none — the branch refusal names the recorded spelling and the landing command, the others carry a fixed reason, and the same verbs naming another branch, an ordinary push of a lane branch and an edit of a source file pass.
- REQ-11: When the tool-preflight duty checks a call whose agent type is read-only, the tool-preflight duty shall refuse a file write and a reference move and record the agent in the deny line · failure: none — the deny line names the agent type and a short hash of the agent id, never a raw id, and a read-only agent's read call passes.
- REQ-12: When the tool-preflight duty checks a commit in a project with a local ledger, the tool-preflight duty shall refuse the commit when a path it touches is covered by the live reservation of another holder, reading the ledger only · failure: none — a commit inside this session's own reservation passes, and the issue-branch claim-token rule and its wording are gone.
- REQ-13: When the engine writes its log, the engine shall write no line under the retired home folder · failure: none — a HOME whose state root still carries the retired name logs on the project side only, and reading still reads the retired place for lines written before.
- REQ-14: When the update preview shows the guarded commands, the hook writer shall offer the permissions.deny rules beside the hook set into the same config folder, applied only on the user's pick at the preview · failure: none — the rules refuse a force push, reset --hard, a forced clean, --no-verify, add -A and the integration-branch calls of the dangerous-call duty, no rule widens access, nothing is written without the pick, and the rules and the duty's verbs come from one table.
- REQ-15: When moai installs or updates the generic hook set, moai shall write it into each Claude config folder's settings.json the user picks, write no hook entry into a project's .claude/settings.json by default and name each folder and every entry the change adds or removes in the preview · failure: none — a project's settings file keeps its own values untouched, and a change-free layer says so and still names the folders.
- REQ-16: When the input's cwd is not a moai project, every generated hook shall exit 0 at once with no output and no write · failure: none — the cost for a project that does not use moai is one process start, and no log line, no ledger read and no answer text is produced.
- REQ-17: When a session starts in a .claude/worktrees worktree, the generated hook set shall reach that session from the config-folder settings · failure: none — user-scope hooks run regardless of workspace trust, so no tracked settings file is needed, and one measured worktree session is recorded in the Result.

## Decisions

- D-1: The split of the preflight is two duties on one event: `tool-preflight` keeps the ordinary refusals and is generated without `onFailure`, and a new duty `dangerous-preflight` carries the dangerous refusals and is generated with `onFailure: "block"` as its own matcher group. Both run in parallel per the host docs and the most restrictive answer wins, so a deny from either blocks the call.
- D-2: The recorded integration branch is read through the one reader of the reference-guard module (the record in the common git folder, the profile value only when no record exists). A repository with neither has no integration-branch refusals: there is no name to protect.
- D-3: The read-only agent types are the base agents whose definitions disallow the write tools (moai-plan, moai-research, moai-audit today); the list lives beside the agent definitions and changes with the agent-set card, not here.
- D-4: The guarded settings files are the project's `.claude/settings.json`, the project's `.claude/settings.local.json` and the config folder's `<config>/settings.json`. All three are written only on the user's pick at a preview; the dangerous-call duty refuses writes of them, and the hook writer never writes a project settings file by default.
- D-5: The agent is recorded in the deny line as its agent type and the first 16 hex digits of the sha256 of its agent id, the same treatment a session id gets; a raw host id never enters the log.
- D-6: The ledger reservation check replaces the Issue claim-token rule: it reads the reservation rows with a live lease and refuses only when the covering reservation's holder is not the session the call names. Merges by the landing command are not `git commit` tool calls and never meet it.
- D-7: The 20 ms budget covers the duty's own work in process; the host's process start (about 7 ms measured in the report) is outside it and is covered by the one measured host run in the Result.
- D-8: The `permissions.deny` rules and the dangerous duty's verbs come from one table in the code, so the two layers cannot drift; the rules use the host's permission-rule syntax, are narrowing only and are written into the picked config folder on the user's pick alone.
- D-9: On a HOME whose state root still resolves to the retired name the engine log stays on the project side and never creates the retired folder; the read path keeps both places for lines written before the move. The full state move is the path-root card's.
- D-10: The session-check answer goes inside `hookSpecificOutput.additionalContext` (text outside it is silently ignored), keeps the after-compaction advice restating the card facts instead of the Issue-era resume comment, sets a `sessionTitle` from the SPEC id or the branch name (2.1.152+, no card number), and keeps the language line with its one source in HOME.
- D-11: The ordinary checks stay fail-open when moai is missing or crashes (the user's first pick, unchanged for them); only the dangerous duty blocks on its own failure, per the user's revised pick. The recovery when the blocking check fails is to restore moai or start the session with `claude --safe-mode`.
- D-15 (coverage note 6240): The session-check duty exports the MOAI_* variables the flow needs through the host's `CLAUDE_ENV_FILE` (plain `export NAME=value` lines, appended so other hooks' lines survive) and answers `reloadSkills: true` when it learns an update applied inside the running session (whole-docs report 4-1: the installed skills would otherwise stay invisible until a restart).
- D-17 (user decision, note 6278, 2026-11-22, after the rm incident): the deletion check is the dangerous duty's first rule. rm, rmdir, find -delete, find -exec rm and git clean resolve their targets — absolute paths, the home folder, .., links, the known variables ($HOME, $TMPDIR), wrappers (env, xargs) and one level of a shell's -c script — and refuse any target outside the session's worktree and the temp folder; the entry already carries onFailure block. Official basis: permissions.md:261-271 (Bash rules are not a boundary), hooks.md:846-853 (exit 2 / deny blocks), hooks.md:940-988 (onFailure block, 2.1.295+).
- D-16 (coverage note 6240): No `permissions.ask` push rule is written: lanes push their own SPEC branches and the reference guard with the pre-push check protect the integration branch (leader default, recorded 2026-11-22). The deny rules of REQ-14 stay.
- D-12: The generic hook set lives in each picked config folder's `<config>/settings.json` (the install-place decision, report 15-34): user-scope hooks run in every project of that folder regardless of workspace trust, so `.claude/worktrees` sessions are covered with no tracked settings file; every entry names the moai binary by absolute path in exec form, so one entry works in every project and worktree; and the exit-0 rule bounds the cost for projects that do not use moai to one process start (report 4-3).
- D-13: A refusal is exit code 2 with the fixed reason on stderr — the documented deny object may accompany it — because exit 0 never approves and exit 1 never blocks; and no duty ever returns `updatedInput`, which auto mode denies as a changed input.
- D-14: The guards read a Bash line the way the permission rules do (report 4-2): split on `&&`, `||`, `;`, `|`, `&` and newlines, unwrap `timeout`, `nice`, `nohup` and `xargs`, and read commands after a `cd`; the default builds' `bfs` and `ugrep` search commands must not be misread as dangerous.

## Risks

- A `permissions.deny` rule written too narrowly can miss a form of a guarded command (the host's Bash rule matching is best-effort). The dangerous duty is the second layer on the same table (D-8), and a test derives both from it.
- The in-process budget test measures the duty alone; the real per-call cost adds one process start. The measured-once number in the Result is the honest end-to-end figure, as the report's own measurements were.
- The read-only agent list is fixed: a user's own read-only agent type is not covered until the agent-set card lands; the refusal names the type, so the gap is visible.
- The ledger reservation check can refuse a commit by the leader inside the primary when a path is reserved by another holder; the leader lands through the landing command, whose merges are not tool commits, and a genuine conflict is exactly what the check is for.
- A config folder the user did not pick gets no hooks, and its sessions run without them; the preview lists the folders it writes so the gap is visible.
- A moved or removed moai binary leaves the absolute-path entries broken: the ordinary checks fail open, but the dangerous entry then blocks its calls in every project of that folder until moai is restored or the session starts with `claude --safe-mode` (D-11).
- Removing the receipt handler stops the `hooks.jsonl` evidence the hooks-status field `fired` reads; that field reads the engine log too and keeps working, and the removed receipt log is left where it is (the archive work owns it).
- The requirement count sits above the checker's twelve-requirement comfort on purpose: the independent review ordered one requirement per hardening item, so the size warning is accepted, not split.
