## §A Background

The usage log `usage-log.jsonl` is appended by the harness-observe hooks (`internal/harness/observer.go`) and pruned lazily from the same hook process: after the append, `PruneStaleEntries` runs and, when the on-disk attempt stamp `<log>.prune-state` is older than one hour, takes an exclusive `flock` on that file, writes the stamp, archives events older than 30 days into `<YYYY-MM>.jsonl.gz`, and replaces the log by rename. Card t1425 (urgent, class B, no SPEC) made this single-writer; its audits left the seven items below open. The stamp-before-work ordering (t1425 F1) and the orphan `usage-log-*.tmp` sweep are already on this tree and are not touched here.

Facts about the platform primitives the design rests on, all OBSERVED by scratch probes on darwin this plan phase (Linux and Windows not observed):

- `Lstat` of a symbolic link reports the link's own owner (uid 501), not its target's (uid 0, a link to `/etc/hosts`). Re-observed in this revision with a user-created link to `/`: the link's own owner uid 501, the target's owner uid 0, effective user id 501 (ledger E-026); the iteration-2 audit measured the same (its probe P-OWN). Root-owned symbolic links exist at `/var`, `/tmp` and `/etc` on darwin (ledger E-027; Linux not observed).
- A file opened read-only fails `Truncate(0)` (`invalid argument`) and `WriteAt` (`bad file descriptor`), so the stamp write fails without any file-system fault.
- An exclusive create over a dangling symbolic link fails (`file exists`) and does not create the link's target.
- A user without privilege cannot make a file owned by another user (`chown 0 <file>`: `Operation not permitted`), so a portable test cannot construct a foreign-owned state entry without a seam.

Three further facts bound the design:

- **`internal/lockfile` has seven non-test importers on this tree** (grep of `internal/lockfile"`): `internal/contract/receipt/store.go`, `internal/cli/settings.go`, `internal/cli/glm_tools.go`, `internal/cli/taskledger/taskledger.go`, `internal/harness/retention.go`, `internal/escalation/lock.go`, `internal/hook/agentmemory.go`. The `@MX:ANCHOR` text in `lockfile_unix.go` names only three; any change to that package is a change for all seven.
- **`SPEC-AGENT-TEAM-RETIRE-001` is `status: completed` (v0.1.2)**; its REQ-ATR-001 requires the Windows in-process-mutex limitation comment preserved verbatim, and the `@MX:NOTE` in `lockfile_windows.go` says behaviour preservation is the contract and the file is not to be silently upgraded to `LockFileEx`. A change there goes through that SPEC's amendment path (`completed → in-progress (amendment)` with `amendment_of:` and an `## Amendments` row), not through this SPEC.
- **A FIFO as a state path cannot exercise the stamp-write branch** (an earlier scratch probe on darwin that called the open and the lock directly, not the production entry point: opening a FIFO `O_RDWR` succeeds and `flock` on it returns `operation not supported`). Through `PruneStaleEntries` the lock step is never reached, because the call blocks earlier, in the lock-free pre-check (the FIFO row above, OBSERVED). The read-only-handle fact above is the portable alternative for the stamp-write branch (§B D5).

Boundary and terminator rule (REQ-HRH-006, REQ-HRH-007):

- The measured prefix is the log as it stands when the pruner opens it. Only whole, newline-terminated lines inside the prefix are classified as kept or stale. The bytes after the last newline inside the prefix (a final line with no terminator) and every byte appended afterwards form the tail, which is copied verbatim and unclassified.
- The replacement log is the kept lines (each terminated by one newline, as today) followed by the tail. When the tail is non-empty and does not end with a newline, the pruner adds exactly one newline. The replacement is therefore empty or newline-terminated, the property OBSERVED at base, so the next append starts its own line and is never glued onto a carried fragment.
- A partial last line (an append observed mid-write, or a damaged final line) is carried whole, exactly once, with that terminator. If its writer completes later against the old file, the remainder is lost (part of the residual window) and the fragment stays in the log as an unparsed line that later prunes keep verbatim (t1433 behaviour). Whether a concurrent append can be observed half-complete on the target file systems was not observed.
- Consequence, stated rather than hidden: a final line that has no terminating newline is not classified in this prune. It is classified by the first later prune that finds it terminated: through the terminator the pruner adds when it rewrites the log (which it does when the log holds any other stale event), or through an append that completes the line. When that final line is the only stale event, the prune returns without a rewrite (nothing was classified as stale) and adds no terminator, so a damaged unterminated tail can stay unclassified; this is stated, not pinned by a test. Malformed lines inside the prefix keep today's rule: kept verbatim.
- The tail is read once, immediately before the rename. Events appended after that reading, and events written by a process that opened the old file before the rename, are the residual window.

**Why C closes the window (reasoned from the code; the contract test and the probe are the observation).** A faulty entry E is removed only by a healer that holds the heal lock and, while holding it, finds the path still holding E. A winner that removed E and created its fresh file F does so in this order: remove E (under the lock), release the lock, create F exclusively (the path is absent, so a creation cannot succeed while E is present). A waiter that takes the lock afterwards finds either the path absent (nothing to remove; it creates exclusively and loses or wins the creation race, an "already exists" result sending it to inspect again) or F (not the inspected E: no removal; it opens F). No removal can hit F, because a removal needs the path to hold the inspected entry and, once E is gone, nothing equal to E in identity, type, mode and modification time can reappear. The lock is held only across the re-inspection and the removal: it is released before the replacement is created and before the state file is locked, so it is never held across a prune (AC-HRH-006 d).

**Heal-lock design [0.4.0].** Names are suggestions; the criteria bind behaviour.

1. *Where it is taken.* Only on the heal path, after the ownership check of the state-path entry passes. The common path (a valid regular state file, or an absent entry created exclusively) never opens, creates or locks the heal lock (AC-HRH-006 c). The lock-free pre-check functions and the append path are untouched (REQ-HRH-008, AC-HRH-009).
2. *Where it lives.* A retention-local file `<log>.prune-heal` (constant `pruneHealSuffix`, next to `pruneStateSuffix`), locked by a retention-local build-tagged helper in `internal/harness`, not by `internal/lockfile`: that package has only a blocking `Lock` and no try-lock (READ, `lockfile_unix.go`), REQ-HRH-012 keeps every file under it byte-identical, and the ruling did not lift that. The helper lives in two new files, `retention_heal_unix.go` (`//go:build !windows`) and `retention_heal_windows.go` (`//go:build windows`), defining the same unexported symbol.
3. *Bounded wait.* The helper polls a non-blocking exclusive `flock` (`LOCK_EX|LOCK_NB`, the syscall package `lockfile_unix.go` already uses) every `pruneHealPoll` (10 ms) until `pruneHealWait` (2 s), measured on the real clock and not the injected `nowFn`, so a mock clock cannot stretch or skip it; `EWOULDBLOCK` means "held, poll again", any other error means "unusable". Why 2 s: the harness-observe hooks are killed at 5 s (§A F6 row, READ); one prune took up to 1.79 s on a 65.8 MB log (t1425 lane, reported in the card dispatch, not re-measured); a waiter that waits the whole 2 s and then proceeds needs about 3.8 s in total (an arithmetic on those two figures, not a measurement), under the kill, whereas a bound near 5 s would leave no room for the prune. The holder keeps the lock for two system calls, so a waiter waits the full bound only when the holder stalls. The value is an engineering choice and was NOT measured under load (decision-index Q9).
4. *Fail closed.* When the heal lock cannot be used the heal is not attempted: the state-path entry stays untouched, the prune is skipped before any stamp is written (so the next hook event attempts again, rather than one interval later), the pruner returns an error naming the heal-lock path and writes one `[WARN] harness/retention:` line naming it to standard error, the form of REQ-HRH-004. "Cannot be used" covers a wait that passed the bound, an unusable heal-lock entry (below), a failed create or open of the heal-lock path (for example a state directory that does not permit creating the file) and any `flock` error other than `EWOULDBLOCK` (for example a file system without `flock`: reasoned, not observed). [0.4.1] The returned error wraps the underlying operating-system error wherever the failure has one (a failed create, open or lock call), so that a permission failure stays recognizable with `errors.Is`; a timeout and a refused entry have no such cause and wrap nothing. The wrap is what keeps the existing read-only-directory test of AC-HRH-003 (b), which asserts `errors.Is(err, fs.ErrPermission)`, green once the heal lock reroutes that case: its state directory is read-only, so the heal-lock file cannot be created and the heal fails closed at the heal lock before the removal step is reached (observed against a draft model, ledger E-048); the removal arm is pinned separately by AC-HRH-003 (c).
5. *The heal-lock file as hostile input.* It sits in the project directory beside the state file whose symbolic-link fault F4 closed, so it gets the same care. The pruner inspects it without following links (`os.Lstat`). Absent: it creates it exclusively with mode 0600 (`O_CREATE|O_EXCL`, never follows a link, never truncates; an "already exists" result sends it to inspect again). A regular file: it opens it read-write without create and without truncate, with `O_NOFOLLOW|O_NONBLOCK`, then requires that the opened file is regular and the same file as the inspection (`os.SameFile`) before locking. A symbolic link, a directory, a FIFO, a socket, a device, any entry the owner check reports as not owned by the current user, or an open that fails: fail closed. At most three inspections, as for the state file. The ownership rule is the state file's: the check is the pruner's one owner-check function (`ownerCheck`), asked about the heal-lock path, before the lock is taken. The pruner never removes, replaces, truncates, chmods or heals the heal-lock entry, in any case: a damaged heal-lock entry stays for the operator, and the heal stays off with a warning each attempt.
6. *The FIFO decision (so that this card adds no new hang path).* The decisive rule is "inspect with `Lstat`, open only a regular file": a FIFO planted at the heal-lock path is never opened, so it cannot block (AC-HRH-016, case c, asserts the outcome: fail closed and return within the bound). The open flags `O_NOFOLLOW|O_NONBLOCK` are defence in depth for a link or FIFO swapped in between the inspection and the open: the open then fails (link) or returns at once (FIFO, OBSERVED on darwin, E-032 P3) and the post-open regular-file check refuses it. That interleaving cannot be forced without a seam and is not pinned by a test; Linux behaviour is not observed. The FIFO-at-the-state-path hang (§A, §E) is a different path, still recorded and not repaired.
7. *Windows twin.* `retention_heal_windows.go` defines the same symbol, creates no file and acquires no exclusion. [0.4.1] It is also unreachable in production: on Windows the owner check answers "not owned" for every entry (`retention_owner_windows.go:8`, tree `0206c6225`, READ), and `healStateEntry` returns at the ownership check, with the warning of D4.b, before any removal or heal-lock call, so a faulty state-path entry is left in place with a warning and no heal runs there. There is therefore no heal window on Windows and no need for a heal lock there; the twin would matter only if a Windows ownership lookup were added (Out of Scope, §E), and REQ-HRH-010 requires the source to say that and to carry the sentence "heal lock gives no exclusion on Windows". The earlier F5 limit (no cross-process lock for the prune itself, D1) is unchanged. This is a reading of the code, not a runtime observation: Windows runtime not observed; build and vet only.
8. *The new artifact.* `<log>.prune-heal` is a persistent zero-byte file, created on the first heal and never removed by this code. The repository's `.gitignore` ignores the state file by exact path (`.gitignore:352`, `.moai/harness/usage-log.jsonl.prune-state`); the heal-lock path is not ignored at this tree (`git check-ignore -v` exits 1, ledger E-042), so the run phase adds `.moai/harness/usage-log.jsonl.prune-heal` beside it. The distributed template `.gitignore` carries no `.prune-state` entry (grep of its `harness` and `prune` lines: only an unrelated line), so the heal lock follows the state file's treatment there and the template is not changed.

**Residual after the change, by evidence.** On Unix the single-healer guarantee holds for processes that honour the heal lock (reasoned; the contract test and the probe observe it, E-036, and the post-fix probe is an expectation until the run phase measures it). On Windows no heal runs at all (item 7), so there is no heal window there to close, and the F5 limit for the prune itself is unchanged [0.4.1]; the window remains against any older binary that heals without the lock (not observed). A heal-lock timeout or an unusable heal-lock entry skips that prune attempt and warns; retention resumes when the condition clears (no stamp is written, so the next hook event retries). The heal-lock file is a new persistent artifact. That the lock is held across the removal, and not released before it, is pinned by the probe and by review, not by a deterministic test (no seam sits between the re-inspection and the removal). The 2 s bound is not measured under load; the run phase measures the sum of the prune duration and the heal-lock wait once under load and reports any observation above the 5 s hook timeout to the leader (§D, Definition of Done 15) [0.4.1]. A draft model of this design (an overlay in `.moai/reports/t1432/amend-drafts/proto/`, not the implementation), run through the same probe as the pre-fix control, counted 0 removals in 20000 trials (ledger E-051); that is an observation of the model, and the post-fix evidence is the run phase's own probe run (Definition of Done 10) [0.4.1].

## §C Requirements (GEARS)

- **REQ-HRH-001** (Event-driven, item F4): When the prune state path (`<log>.prune-state`) is a symbolic link whose own owner is the current user — the owner recorded on the link itself, read without following it, never the owner of the entry it points at — the retention pruner shall leave the link's target unmodified, shall replace the link with a regular state file it creates at that path, and shall continue the prune; the guarantee holds for a link whose target does not block a read-only open (a link to a FIFO does, §F).
- **REQ-HRH-002** (Event-driven, item F7): When the prune state path is a regular file owned by the current user that the retention pruner cannot open for reading and writing because of a permission error, and the directory permits the current user to remove it, the pruner shall replace it with a regular file it can lock and shall continue the prune.
- **REQ-HRH-003** (Event-driven, item F7 boundary): When the prune state path cannot be used and cannot be replaced under REQ-HRH-001 or REQ-HRH-002 — because the entry is not owned by the current user (for a symbolic link: because the link's own owner is not the current user, whatever its target's owner), because its owner cannot be determined, because it is a directory, because a regular file cannot be opened for a reason other than a permission error, or because the directory does not permit its removal — the retention pruner shall skip the prune, return an error naming the failure, and leave the usage log, the archive directory and the state-path entry (a symbolic link's target included) byte-identical to their state before the call; a FIFO or another special file at the state path is outside this requirement (§F).
- **REQ-HRH-004** (Event-driven, item F7 / Q4 warning): When the retention pruner declines to replace a symbolic link or a regular file at the prune state path because the entry is not owned by the current user (for a symbolic link: because the link's own owner is not the current user) or its owner cannot be determined, the pruner shall write one warning line naming that path to standard error; where the platform does not expose per-user file ownership, the pruner shall treat every entry's owner as undeterminable.
- **REQ-HRH-005** (Event-driven, item F4 / F7 concurrency; rewritten 0.4.0): When the retention pruner is about to remove a prune state path entry it inspected, it shall first acquire the heal lock exclusively, so that no other healer holds it, in any mode, at the same time [0.4.1], shall re-inspect the entry while holding the lock, and shall remove the entry only if it is still the entry the pruner inspected before it took the lock; an entry that is no longer that entry, such as a state file a concurrent healer created while this pruner waited, it shall leave in place and re-inspect, so that a state file created by a healer that held the lock first is not removed by this pruner; the pruner shall release the heal lock before it locks the state file, and shall not open, create or lock the heal lock when the state path holds a healthy regular file or is absent.
- **REQ-HRH-006** (Event-driven, item event loss): When event lines are appended to the usage log after the retention pruner measured it and before the pruner takes its final reading ahead of the replacement, the pruner shall carry those bytes, verbatim and in their original order, after the kept lines of the replacement log.
- **REQ-HRH-007** (Ubiquitous, item event loss): The replacement usage log shall be empty or end with a newline, and a final line that lacks a terminating newline when the retention pruner measures the log shall be carried whole, exactly once, unclassified and unmodified apart from the added terminating newline.
- **REQ-HRH-008** (Ubiquitous, item event loss): The observer's event-append path and the retention pruner's pre-lock path (the in-memory interval check, the stamp read and the log existence check; at base `PruneStaleEntries`, `readStamp`, `readStampFile` and `stampIsFresh`) shall add no lock, no file open and no system call beyond those present at base `1e2151a38`.
- **REQ-HRH-009** (Ubiquitous, item event loss): The retention pruner's source documentation shall state that a residual window remains between its final tail reading and the replacement rename in which an appended event is lost, and shall not state that events appended during the whole read-to-rename interval are lost.

## §F Risks and unobserved items

- **Partial last line at the tail boundary** (D3 B): an appender's single write may be mid-flight when the pruner takes its readings. Mitigation: the boundary is the last newline inside the measured prefix and the replacement is terminated (REQ-HRH-007); whether a concurrent `O_APPEND` write can be observed half-complete on the target file systems is not observed, so `plan.md` M1 tests the boundary rule deterministically rather than claiming anything about the kernel.
- **Residual loss window remains** (D3 B): an event appended between the final tail reading and the rename, or by a writer that opened the old file before the rename, is still lost. Stated in REQ-HRH-009; not eliminated.
- **Heal burst and the heal lock** (D4.c C; replaces the 0.3.0 "Heal burst" bullet, which accepted a residual gap between the last re-inspection and the removal) [0.4.0]. After the change: (1) on Unix the single-healer guarantee holds for processes that honour the heal lock (reasoned; E-036 and the post-fix probe observe it, the latter an expectation until the run phase measures it); (2) on Windows no heal runs (the owner check refuses every entry, so a faulty state-path entry is left in place with a warning), hence there is no heal window and no heal-lock reach there, and the F5 limit for the prune itself is unchanged [0.4.1]; the window remains against a binary older than the change; (3) a heal-lock timeout or an unusable heal-lock entry skips that prune attempt with a warning, no stamp is written, so the next hook event tries again, and retention of a faulty-entry log stays off while the condition persists; three disclosures [0.4.1]: (3a) the 2 s bound applies per acquisition and is not cumulative: a call that acquires the lock more than once (at most three inspections) can wait up to 2 s each time, so the 4.5 s ceiling of AC-HRH-015 holds for a lock held throughout one acquisition, and a chain of late acquisitions is contrived and not measured; (3b) a heal-lock entry planted at `<log>.prune-heal` (a symbolic link, a directory, a FIFO or a foreign-owned file) together with a faulty state-path entry keeps retention off for that log until an operator removes the heal-lock entry, which is the state at the card's base (a faulty state-path entry disabled retention silently) and is now visible through the warning; the common path never touches the heal lock, so a planted entry alone denies nothing; (3c) deleting `<log>.prune-heal` by anything other than this code (an operator `rm`, `git clean -X` once the path is ignored) while a healer holds it lets a second healer lock a new file: the two-inode shape, outside the guarantee, as is a process that does not honour the lock; (4) the heal-lock file is a new persistent zero-byte artifact; (5) the 2 s bound is an engineering choice, not measured under load, and the production frequency of both the window and the timeouts is not measured; (6) that the lock covers the removal is pinned by the probe and by review, not by a deterministic test, because no seam sits between the re-inspection and the removal. A leftover heal-lock file is harmless to the common path, which never opens it.
- **Time-of-check gap** (D4): between the inspection and the open of a regular file the entry can be swapped for a link; the open then reaches the target without truncating it, and the post-open identity check refuses before any stamp write. This window cannot be forced without a seam and is not pinned by a test (reviewer-read at plan.md M2). [0.4.0] The heal-lock file has the same gap between its `Lstat` and its open: a link or FIFO swapped in there is refused by `O_NOFOLLOW|O_NONBLOCK` and the post-open regular-file check; not pinned by a test, reviewer-read at plan.md M8.
- **Warning volume** (D4.b A): the warning repeats once per prune attempt while a foreign-owned entry persists, which is the hook-event rate; whether hook standard error reaches a user was not measured. [0.4.0] The heal-lock warning repeats the same way while a heal-lock timeout or an unusable heal-lock entry persists.
