## §A 배경 — 카드의 관측은 맞지만 카드의 프레이밍은 틀렸다

카드 t518은 축 3을 "`moai spec lint <SPEC-ID>`가 ID를 파일 경로로 해석해 `ParseFailure`를 낸다"고 적었다. 관측은 이 트리에서 그대로 재현된다. 그러나 **그것을 "약속을 어긴 구현"으로 읽으면 수리가 엉뚱한 곳을 겨눈다** — `internal/cli/spec_lint.go:28`의 선언은 `Use: "lint [spec.md...]"`이고, 이 명령은 애초에 **파일 경로를 받는다고 스스로 밝히고 있다**. 구현은 자기가 약속한 것을 지키고 있다.

그러면 결함이 없는가. 있다. 다만 결함은 하나가 아니라 둘이고, 둘 다 실재한다.

### 측정 — 대조쌍, 파이프 없는 종료 코드 판독

이 워크트리, 커밋 `0b1e27877`, 바이너리 `moai-adk v3.2.0-rc.0`. 명령을 파일로 리다이렉트한 뒤 `echo $?`를 **별도 문장**으로 읽었다(파이프로 끊긴 `$?`는 마지막 스테이지를 읽는다 — 이 저장소가 반복해 기록한 오류다). 증거 전문: `.moai/reports/t518/id-arg-control-pair.txt`.

| # | 인자 형태 | 명령 | 결과 | rc |
|---|---|---|---|---|
| 1 | ID | `moai spec lint SPEC-AC-COUNT-DISCRIMINATOR-001` | `ERROR ParseFailure … LINE 1` · `1 error(s), 0 warning(s)` | 1 |
| 2 | 경로 (**대조군**) | `moai spec lint .moai/specs/SPEC-AC-COUNT-DISCRIMINATOR-001/spec.md` | `0 error(s), 1 warning(s)` | 0 |
| 3 | 디렉터리 | `moai spec lint .moai/specs/SPEC-AC-COUNT-DISCRIMINATOR-001` | `ERROR ParseFailure … is a directory` | 1 |

**대조군이 성공한다.** 따라서 1과 2의 차이는 인자 모양에 귀속된다 — 도구 전체의 고장도, 그 SPEC 문서의 결함도 아니다.

### 실제 결함 1 — 형제들 사이에서 계약이 어긋나 있다

`moai spec` 아래 서브커맨드의 인자 선언(측정: `grep -hn 'Use:[[:space:]]*"' internal/cli/spec*.go`):

- `close SPEC-ID` — ID
- `status <SPEC-ID> <new-status>` — ID
- `view <SPEC-ID>` — ID
- `lint [spec.md...]` — **경로**

넷 중 셋이 ID를 받는다. `moai spec view SPEC-X`를 방금 친 사용자가 `moai spec lint SPEC-X`를 치는 것은 오용이 아니라 **일관성에서 나온 추론**이다. 어긋남 자체가 결함이고, 그 대가를 지금은 사용자가 치른다.

### 실제 결함 2 — 실패가 도움이 안 되고, 게다가 유형이 틀렸다

인자 모양 실수가 **문서 단위 lint finding**으로 나온다. `ParseFailure`, ERROR 등급, `LINE 1` — SPEC 문서 자체의 진짜 결함과 표에서 모양이 구별되지 않는다. 출력은 "이건 SPEC-ID처럼 보인다. `.moai/specs/<ID>/spec.md`를 말한 것 아닌가?"라고 말하지 않는다.

그리고 위 측정 [4]가 보여주듯 **[1]과 [4]의 출력은 사실상 같다** — 오늘의 도구는 "인자를 잘못 썼다"와 "그런 SPEC이 없다"를 구별하지 않는다.

더구나 이 명령의 `Long` 도움말은 이미 종료 코드 계약을 스스로 정의하고 있다: `0 성공 / 1 에러 발견 / 2 linter 크래시 / **3 잘못된 인자**`. 측정 [5]가 그 3번 통로가 실재함을 보인다. 인자 모양 오류는 **이미 있는 통로**로 보내면 되는데 findings 표로 새고 있다.

### [HARD] 판별식 정규식의 동명 충돌 — 가장 조용히 잘못될 지점

`internal/cli` 패키지에는 **이미 `specIDPattern`이 있다.** 이름이 같고 뜻이 다르다:

| 심볼 | 위치 | 정규식 | 성질 |
|---|---|---|---|
| `specIDPattern` | `internal/spec/lint.go:952` | `^SPEC(-[A-Z][A-Z0-9]*)+-\d{3}$` | 앵커 있음, 3자리 강제, 엄격 |
| `specIDPattern` | `internal/cli/spec_status.go:18` | `SPEC-[A-Z0-9-]+-[0-9]+` | **앵커 없음**, 자릿수 무제한, 느슨 |

느슨한 쪽은 **부분 문자열에 매치된다** — `dir/SPEC-A-001.md` 안의 `SPEC-A-001`을 잡는다. 원래 용도가 git 커밋 메시지에서 SPEC-ID를 긁어내는 것이므로(`spec_status.go:248`) 앵커가 없는 것이 옳다. 그러나 **인자 판별식으로 재사용되면 경로를 ID로 오독한다** — plan.md D1이 스스로 "이쪽이 더 나쁘다"고 이름 붙인 방향이다.

**확정 사실(재측정, 추정 아님)**: `internal/spec`의 `specIDPattern`은 소문자 시작 = 비공개이므로 `internal/cli`에서 import할 수 없고, 공개로 바꾸는 것은 `internal/spec` 편집이라 REQ-SLI-008이 금지한다. **따라서 사본 경로가 유일한 선택지이며, 사본은 새 이름을 가져야 한다.** 이름의 거처(로컬 사본이냐 공유 boundary 패키지냐)는 §H 미해결 결정이다.

이 SPEC을 작성하며 자기 문서에 lint를 돌리는 과정에서, 카드가 묻지 않은 사각지대를 하나 더 측정했다. 발견을 조용히 버리지 않기 위해 여기 남긴다.

- `internal/spec/parser.go:67`의 `findACSectionStart`는 `##` 제목에 **영어 단어 `acceptance`가 들어 있을 때만** AC 절을 찾는다. 한국어 제목(`## §D 수용 기준`)은 절 자체가 발견되지 않는다.
- `internal/spec/parser.go:218`의 AC ID 문법은 `AC-[A-Z0-9]+-[0-9]+-[0-9]+`(숫자 그룹 **둘**)에 콜론을 요구한다. 저장소가 실제로 쓰는 `AC-SLI-001` / `AC-SLB-001a` 꼴은 어느 쪽도 만족하지 않는다.

**대조군으로 귀속을 확정했다.** 이 SPEC과 무관한 기존 문서에서 같은 실패가 난다:

```
moai spec view SPEC-AC-COUNT-DISCRIMINATOR-001
→ Parse error: acceptance criteria section not found.   (rc=1)
```

따라서 이것은 이 SPEC이 만든 결함이 아니라 **코퍼스 전역의 기존 동작**이다. 그 귀결로 이 SPEC의 `spec.md`에는 `CoverageIncomplete` 자문 경고가 **REQ 수만큼** 남는다 — 형제 SPEC에도 같은 이유로 자기 REQ 수만큼 남아 있다. 두 문서 모두 error는 0이다. **v0.5.0 시점의 재유도값**(파이프 없음): 이 SPEC rc=0 · `0 error(s), 9 warning(s)` / 형제 rc=0 · `0 error(s), 14 warning(s)`, 전부 `CoverageIncomplete`. **v0.4.0까지는 8 / 13이었고**, 두 값은 각각 REQ-SLI-009 · REQ-SLB-014 신설을 따라 함께 움직였다 — 옛 값을 지우지 않고 이동으로 적는다. 경고 수가 REQ 수를 따라간다는 것이 이 절의 요점이며, 그래서 이 수치는 고정값이 아니라 **REQ 수의 함수**다.

이 결함을 여기서 고치지 않는 이유는 두 가지다. (1) 반경이 `internal/spec`이라 형제 SPEC의 파일 영역이고, 두 카드가 같은 파일을 만지면 서로의 측정이 귀속되지 않는다. (2) 형제 SPEC의 범위에도 들어 있지 않다 — 그 SPEC은 REQ 수집기와 modality 판정을 다루지, **AC 수집기**를 다루지 않는다. 어느 카드도 소유하지 않던 이 자리는 **후속 카드 t528**이 받는다(§E 참조).

### 이 SPEC이 고르는 것 — 그리고 기각하는 것

두 결함을 **둘 다** 고친다. 우선순위는 다음과 같고, 되돌릴 수 있게 나눈다.

- **주(主)**: SPEC-ID 인자 해석. `lint`를 형제들과 같은 계약으로 맞춘다. 경로 형태는 계속 받는다(추가이지 대체가 아니다).
- **부(副)·되돌림 안전망**: 해석이 실패했을 때 — 즉 그런 SPEC이 진짜로 없을 때 — 의 진단. 인자 유형 오류로 분류하고(종료 코드 3), 시도한 경로를 이름 붙여 말한다.

**기각한 선택지를 기록한다.**

1. *진단만 고치고 해석은 하지 않는다* — 기각. 계약 어긋남(결함 1)이 그대로 남고, 사용자는 매번 "그건 경로로 쓰세요"를 읽는다. 다만 이 선택지는 **부분 롤백 지점**으로 살아 있다: 주(主)를 되돌려도 부(副)만으로 오늘보다 낫다.
2. *해석만 하고 진단은 두지 않는다* — 기각. 해석이 도입되면 실패 경로가 오히려 더 헷갈린다(해석된 경로가 없는 것인지, 인자를 잘못 쓴 것인지).
3. *`lint`를 ID 전용으로 바꾸고 경로 형태를 폐기* — 기각. **기각 근거는 「대조군」이다**: 경로 형태는 이 SPEC의 대조군이고, 대조군이 움직이면 어떤 측정도 귀속되지 않는다(REQ-SLI-004가 이를 동결한다). ~~"훅·CI·`--json` 소비자가 이미 쓴다"~~ — **이 논거는 정정한다.** 이 저장소를 훑으면(`.github/` · `.claude/hooks/` · `scripts/` · `Makefile` · `.moai/config/`) 기계적 소비자는 단 하나, `.github/workflows/spec-lint.yml:58`의 `go run ./cmd/moai spec lint --strict`이며 **인자를 하나도 넘기지 않는다.** 배포판 사용자 프로젝트의 CI/훅은 이 트리에서 원리적으로 확인 불가이므로 **미검증**으로 라벨한다. 결론은 독립적으로 유지되고 논거만 바뀐다.
4. *디렉터리 형태(측정 [3])를 범위 밖으로 미룬다* — 기각. 같은 해석기가 같은 비용으로 처리하고, 미루면 **인자 모양이 하나 더 남는다** — 오늘 고치는 것과 같은 결함이 축소판으로 남는 셈이다. 브리핑이 언급하지 않은 항목이므로 이견으로 명시한다(§G).

## §E 범위 밖

이 SPEC이 만들지 **않는** 것을 먼저 못 박는다. 아래 항목은 out of scope다.

### Out of Scope — 축 1·2: REQ 수집기와 modality 판정

- 표 형식 REQ 미수집(축 1)과 비영어 modality 무판정(축 2)은 형제 SPEC `SPEC-SPEC-LINT-BLIND-AXES-001`이 소유한다.
- 이 SPEC은 `internal/spec` 아래 어떤 파일도 편집하지 않는다(REQ-SLI-008). **두 SPEC이 같은 파일을 편집해서는 안 된다** — 반경이 겹치면 두 카드의 측정이 서로에게 귀속되지 않는다.

### Out of Scope — 경로 형태의 동작 변경

**[HARD] 이 카드는 `spec_status.go:18`을 통합하지 않는다 — 그 판단과 이유를 여기 적는다.** 그대로 둔다. 이유는 셋이다. ① **그 정규식은 자기 자리에서 옳다** — 용도가 git 커밋 메시지에서 SPEC-ID를 긁어내는 것이고(`spec_status.go:248`), 그 용도에는 앵커가 없는 편이 맞다. 통합은 그것을 고치는 것이 아니라 **부수는 것**이다. ② **반경이 이 카드의 것이 아니다** — `spec status`의 커밋 스캔 동작을 바꾸는 것은 이 카드가 REQ-SLI-004로 동결한 대조군 바깥의 세 번째 동작 축을 여는 일이고, 그러면 이 카드의 어떤 측정도 귀속되지 않는다. ③ **위험의 모양이 다르다** — 남는 위험은 「같은 저장소에 뜻이 다른 두 정규식이 있다」이지 「어느 하나가 틀렸다」가 아니다.

**그래서 남는 위험에 이름을 붙이고 가드를 세운다.** 위험 이름: **동명-이의 재사용 드리프트** — 다음 저자가 「SPEC-ID 정규식」을 찾다가 앵커 없는 쪽을 집어 인자 판별식에 재사용하면, 경로를 ID로 오독한다(`plan.md` D1이 「더 나쁘다」고 이름 붙인 방향). 세 개의 장치가 그것을 막는다: **이름이 다르다**(REQ-SLI-006), **AC-SLI-005의 뮤턴트가 정확히 그 실수를 잡는다**, 그리고 **AC-SLI-010이 `spec_status.go:18`의 리터럴을 동결해** 그것이 조용히 넓어지거나 앵커를 얻는 것을 감지한다. 통합은 후속 카드가 필요하다고 판단하면 별도 결재로 연다.

**이 지명이 바꾸지 않는 것**: 형제 SPEC의 결정들과 무관하며, Implementation Kickoff Approval은 **별개의 미통과 게이트**다. **`AC-SLI-005`는 손대지 않는다** — 그 뮤턴트는 α와 β 어느 쪽에서도 발화한다(픽스처 `SPEC-A-1`은 경로 신호가 없어 판단이 실제로 정규식에서 일어나고, 앵커된 쪽은 3자리 규칙으로 기각·앵커 없는 쪽은 수용한다). 거처가 바뀌어도 **두 정규식이 갈리는 인자**라는 성질은 그대로이기 때문이다. §A.1에 기록된 근처-실패(감사의 대안 `SPEC--1`은 앵커 없는 쪽에서도 매치되지 않아 뮤턴트가 발화하지 못했을 것)도 그대로 둔다.

> **아래 원문은 결정이 열려 있던 동안의 서술이다. 지우지 않고 남긴다** — 후보 비교가 이 결정을 읽는 근거이기 때문이다. (표의 β 행이 적은 「소비자도 이미 셋」은 위 실측 정정대로 `internal/cli` 한정에서만 참이다.)

REQ-SLI-006이 요구하는 앵커된 모양 정규식의 **거처**가 미정이다. `internal/spec`의 `specIDPattern`은 비공개라 import 불가이고, 공개로 바꾸는 것은 REQ-SLI-008이 금지한다(§A 확정 사실). 남은 후보:

| 후보 | 방식 | 강점 | 약점 |
|---|---|---|---|
| α | `internal/cli/spec_lint.go` 안의 비공개 사본 `specIDArgPattern` | 반경이 가장 좁다. plan.md D4("소비자 하나짜리 패키지를 만들지 않는다")와 일치 | `internal/spec` 원본과 두 벌이 된다 — 어긋남 감지 테스트가 필수 |
| β | `internal/cli/specid` 패키지에 모양 검사 함수를 추가(예 `IsCanonical`) | **이 패키지가 이미 「모든 CLI SPEC-ID 경계에서 사용하는 단일 검증 헬퍼」로 선언돼 있다**(`specid.go:3-8` package doc). 소비자도 이미 셋(view/status/close)이므로 「소비자 하나짜리」 우려가 성립하지 않는다. sanitizer와 모양 검사가 한 경계에 모인다 | 패키지의 성격이 「보안 sanitizer」에서 「경계 검증 일반」으로 넓어진다. 기존 세 소비자에 동작 영향은 없으나 의미가 바뀐다 |

**어느 후보를 고르든 REQ-SLI-006의 두 의무는 남는다**: 이름이 `spec_status.go:18`의 동명 심볼과 달라야 하고, 사본이라면 어긋남 감지 테스트가 붙어야 한다. γ를 고르면 REQ-SLI-006과 AC-SLI-005가 함께 다시 쓰여야 한다.

**운영자가 답할 것**: α(로컬 사본)인가 β(공유 boundary 패키지)인가. 이 카드의 기울기는 **β**다 — package doc가 이 패키지를 이미 「모든 CLI SPEC-ID 경계」의 자리로 선언하고 있고, `lint`를 같은 경계에 붙이는 것이 일관된 수다. 다만 패키지 의미 확장은 되돌리기 비용이 있어 운영자 결정으로 올린다.
