## 1. The model being named (rescope 0.4.0: target-holder routing)

```
lane worktrees (branch from local main)
   -> serial landing into main, one card at a time, by the TARGET HOLDER:
        a worktree other than the primary holds main
            -> the integration-window local merge (moai integration merge --card, scoped tests, re-measure), no per-card PR
        only the primary checkout holds main  (THIS repository since 2026-10-21)
            -> moai factory complete opens the card's pull request (pr-open); the LEADER merges it
               (required checks green, a real review artifact present, branch up to date — no --auto);
               a later completion run records merged-pr
   -> about every lead_push_threshold (20) landings: ONE leader release batch
        (the release/main-batch-YYYYMMDD batch PR on the dedicated-worktree route;
         a tagged release batch on the pull-request route)
   -> tagged release from main
```

Standing branches: `main` only. No `develop`. No per-version release branch cut by lanes. The batch cycle is part of the value's definition: `lead_push_threshold` counts card landings (whichever route the target holder selects) toward the leader's release-batch cadence (REQ-AGT-010).

### The design decision (operator-corrected directive, 2026-10-21)

The dedicated `main` integration worktree was abolished on 2026-10-21; the primary checkout now holds `main` (`git worktree list` row 1: `/Users/goos/MoAI/moai-adk-go 28b727065b [main]`, no dedicated main worktree anywhere in the list). Two candidate shapes were assessed:

**(A) Serial local landing without a dedicated tree — REJECTED.** Every variant that keeps the landing verb (`moai integration merge --card`) requires a worktree whose working tree is clean and reserved for the merge; with the primary checkout as the only `main` holder, that contract lands on the shared human/leader surface, which other sessions occupy and which cannot be held clean for a window. A "cleanliness contract on the primary during a window" is unenforceable against concurrent leader/operator sessions, and the per-batch "lightweight landing surface" variant is a dedicated integration worktree by another name — it reintroduces the abolished structure. The serial, verdict-before-landing property the model needs (scoped re-measurement at landing time, remote CI as the authority) cannot be preserved on the shared primary without the wall the operator removed. Rejected honestly: no variant of (A) satisfies the verified structural constraints.

**(B) PR-edge hybrid — CHOSEN.** Under agentic-trunk, `factory complete` runs merge-ready → pr-open (card branch push + pull request, the existing github-flow edge) → merged-pr, with the `--auto` question resolved toward the operator's leader-only-merge principle (below); the batch cycle stays as the leader's bulk action on a cadence of ~`lead_push_threshold` landings, its precise meaning under the pull-request route being the tagged release batch (the batch pull request's original motive — one consolidated CI run — is provided per-PR by the required checks). The routing is a product behavior keyed on the target holder, not a repo-local carve-out: user projects that run a dedicated integration worktree keep the local-merge route and every M1-M5 behavior already implemented for it; this repository, holding `main` only in the primary, takes the pull-request route after the M6 cutover.

**The `--auto` conflict, resolved.** `internal/cli/factory_card_pr.go:444` (the github-flow PR edge) requests `gh pr merge <N> --auto --match-head-commit` — an auto-merge that fires the moment checks pass, in conflict with the operator's leader-only-merge principle (2026-10-19: the leader merges a PR when the 5 required checks pass, a real review artifact exists, and it is up to date). Resolution: the completion path records `pr-open` and issues NO merge request of any kind (`--auto` dropped; the `--match-head-commit` tip pinning stays meaningful only for a merge actually issued, so it moves out of the pr-open path); the leader merges by their own judgment; the existing "run `moai factory complete` again once the pull request merges" path (`factoryObservePRMerge`) records `merged-pr`. This change applies to the pull-request route under agentic-trunk; whether the github-flow edge drops `--auto` identically is the same code site and is fixed with it (one predicate, one call).

Why a new predicate and not widening `IsGitFlow()`: `IsGitFlow()` carries the name and the tests of the git-flow contract (t637 warning text says "git-flow project"); widening it changes what a git-flow reader sees. A sibling method leaves every git-flow assertion untouched (REQ-AGT-001, REQ-AGT-005).

Why the target is not gated by mode: github-flow's target is mode-independent, and `main` is a fact of the model, not a manual-mode key. The legacy develop seam (`DevelopBranch`) stays manual-only because its consumers (session-exit auto-merge, acquire window recording) are opt-in manual-mode machinery (OQ-7).

Why disposition is not a new class: `DispositionGitFlow` is read only as "is it git-flow" inside the loader and diagnostics; `DispositionInvalid` is the one consumers branch on. A fifth class would force every `switch` to learn it for no behavioral difference.

## 4. Sequencing hazard (decision D2; rescope 0.4.0: the bridge is the starting state)

A binary built before M1 reads `agentic-trunk` as invalid: `IntegrationTarget` is empty, `worktree done`/`sweep`, `goal approve`, `factory merge ready`/`complete` and the card diff base refuse an empty target (t1453 M1), the doctor warns, `integration acquire` warns. The original M6 cutover is therefore back in scope with the bridge as its starting state. The installed `moai` is one shared binary and every running `moai mcp-server` keeps the build it started with. Therefore the live value changes only when the single precondition list P1 to P5 of REQ-AGT-017 holds, in this order:

1. M1 to M5 and the M5b delivery-routing delta land with the live value on the bridge `github-flow` (P1: their commits are ancestors of the flip commit).

3. The leader reconnects the running `moai mcp-server` processes and confirms two things (P4). First `moai doctor --check "MCP Server Version"` reads `ok` against the new commit: that row sees only the servers that stamp a record under one project directory (`<project>/.moai/state/mcp-server`, `internal/cli/mcp_server_runtime.go`). 4. The installed binary's doctor, run on a fixture project whose manual workflow is `agentic-trunk`, reports the `Git Strategy Workflow` row `ok` (P3). The installed binary is the subject here, so the judge names `moai` and not a path; the judging build is the installed one and its commit is named next to the tree HEAD (verification-claim-integrity section 2.2).

The cutover is leader-executed (leader ruling, OQ-3): replacing the installed binary affects every session on the machine, so no lane performs it. P5 no longer probes the integration window (no dedicated worktree, no window on the pull-request route): the leader records that no card pull request of this repository sits in `pr-open` awaiting the leader's merge and no `factory complete` run is mid-transition, then runs the flip. AC-AGT-016 is the one criterion that is judged from the leader's recorded evidence, and the sync audit reads that record.
