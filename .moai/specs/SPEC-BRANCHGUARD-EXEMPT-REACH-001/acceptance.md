### AC-BGX-001 — 최상위 키 집합 전량 기록 (무조건)

**Given** 서브에이전트 컨텍스트의 PreToolUse 페이로드를 관측할 계측기가 배선돼 있고,
**When** 그 계측기가 한 번이라도 출력을 남길 때,
**Then** 그 출력은 페이로드의 **최상위 키 집합 전량**을 **키 단위로 분리된 형태**(JSON 키 목록 또는 한 줄 한 키)로 담아야 하고, 판정서는 그 키 목록을 원문으로 인용한다. 그 목록에 반드시 존재하는 키(`hook_event_name`, `session_id`)가 포함돼 있는 것이 **계측기의 양성 대조**다.

**[HARD] 키 단위 분리가 형식 요건인 이유**: 이 목록은 사람이 읽는 기록이 아니라 **AC-BGX-002 의 비교 입력**이다. 원문 JSON 한 덩어리로만 남기면 그 비교가 다시 문자열 검색으로 퇴화하고, 그 순간 AC-BGX-002 가 막으려는 과다매칭이 되돌아온다.

**[HARD]** 「프로브한 네 철자가 없다」만 기록하고 키 집합을 남기지 않으면 이 AC 는 FAIL 이다. 필드 하나짜리 양성 대조는 **「런타임이 정체성을 안 보낸다」와 「프로브하지 않은 제3의 키로 보낸다」를 가르지 못하며**, 그 구별이 바로 AC-BGX-004 가 결과 (3) 에서 판정해야 하는 것이다. 키 집합이 그 판정의 유일한 근거다.

**실패 조건**: 키 집합이 없으면 이 실행에서 얻은 모든 「필드 부재」 관측은 **무효**이며, 판정은 AC-BGX-005(측정 불가)로 내려간다.

### AC-BGX-002 — 배선 철자 판정 (무조건)

**Given** 계측기가 키 집합 전량과 함께 발화한 상태에서,
**When** 도구로 spawn 된 서브에이전트가 Bash 도구 호출을 1회 이상 발생시킬 때,
**Then** 판정서는 네 철자 **각각**에 대해 「비어있지 않은 값으로 도착 / 부재」를 관측 원문과 함께 기록한다: `agent_type` · `agentType` · `agent_id` · `agentId`.

**[HARD]** 프로브 집합은 **네 철자 전부**다. `agent_type` 과 `agentType` 만 재고 「부재」로 닫으면, 정체성이 `agent_id` 로만 도착하는 세계를 구조적으로 못 본다 — 그것은 camel 철자를 빠뜨렸을 때의 실패 형태와 **같고 필드 이름 하나만 다르다**. 다투는 독트린 문장(`hooks-system.md:114`)이 `agent_id` 와 `agent_type` 을 나란히 이름 대는 이상, 한쪽만 재는 프로브는 그 문장을 검증하지 않는다.

**[HARD] 측정 방법은 grep 이 아니라 키 집합 동등 비교다.** 이 AC 의 판정은 AC-BGX-001 이 남긴 **최상위 키 집합**과 네 프로브 이름을 **정확 일치(exact equality)** 로 대조해 내린다. 포함 관계·부분문자열 검색·정규식 매칭을 판정 근거로 써서는 안 된다.

> **왜 「앵커를 달아라」가 아니라 「키로 비교하라」인가.** 앵커 지시는 레시피에 붙이는 패치이고, 다음 철자 변종에 **말없이 뚫린다**. 이 트리 실측이 그것을 보여준다 — snake 축의 과다매칭원은 `subagent_type` 하나지만(앵커 없는 48 = 실제 28 + 20), camel 축은 **셋**이고 그중 **둘이 대문자 `S` 로 시작한다**:
>
> ```
> $ grep -rnoE '[A-Za-z]*agentType' --include='*.go' --include='*.json' internal/hook/ | sed 's/.*://' | sort | uniq -c
>   22 agentType
>    2 subagentType
>    3 SubagentType
>    2 TestAgentSpawnFixtureCarriesSubagentType
> $ grep -rnoE '(^|[^A-Za-z])agentType' … | wc -l        # 앵커 적용
> 22                                                      # 22+2+3+2 = 29, 정확히 닫힘
> ```
>
> 즉 **「`subagentType` 을 빼라」로 쓴 수정은 대문자 시작 둘을 놓친다.** 키 집합 동등 비교에서는 이 계열 오류가 **구조적으로 불가능**하다 — 키 `"subagent_type"` 은 키 `"agent_type"` 과 같지 않기 때문이며, 새 철자 변종이 생겨도 그 성질은 변하지 않는다.

**[HARD] 오독의 방향이 나쁘다.** 과다매칭은 **더 큰 수**를 만들고, 큰 수는 「더 많이 찾았다」로 읽히며, 아무것도 그것을 신고하지 않는다. 앵커 없는 grep 으로 이 AC 를 판정하면 `tool_input` 안의 `subagent_type` 이 **`agent_type` 도착으로 읽혀** 카드가 결정적으로 **틀린 답(「도달 가능」)으로 닫힌다.**

### AC-BGX-003 — deny 억제까지의 경로 실행 (무조건)

**Given** AC-BGX-002 의 철자 판정이 확정된 상태에서,
**When** `agent_type` 또는 `agentType` 이 비어있지 않은 값으로 도착했을 때,
**Then** `isExemptAgent` 가 true 를 반환하고 `checkBranchState` 가 `BRANCH_GUARD_VIOLATION` deny 를 **반환하지 않음**을 실행으로 보여야 하며, 판정서는 그 실행의 명령과 출력을 인용한다.

**When** 네 철자가 모두 부재할 때,
**Then** 이 AC 는 「해당 없음 — 정체성 미도착」으로 닫고 AC-BGX-004 로 넘어간다.

**When** `agent_id` / `agentId` 만 도착했을 때,
**Then** 이 AC 는 「면제 축은 미발화 — 그러나 정체성 계열 필드는 도착」으로 닫는다. 이것은 「정체성 미도착」과 **다른 상태**이며, 독트린의 기제 서술(AC-BGX-004)과 CODE 분기 성립 여부(AC-BGX-011) 양쪽에 대해 서로 반대 방향의 결론을 함의하므로 세 번째 칸으로 따로 기록한다.

**[HARD]** 코드 판독은 이 AC 를 만족시키지 못한다. 근거는 **경로가 돈 출력**이다.

### AC-BGX-004 — 부정 분기의 기제 일치 검증 (도달 불가 분기)

**Given** AC-BGX-002 가 네 철자 부재 또는 `agent_id` 계열만 도착으로 판정됐거나 AC-BGX-003 이 deny 유지로 판정된 상태에서,
**When** 판정서가 독트린 `main-checkout-branch-guard.md` § Mechanical Enforcement 의 도달-불가 주장을 다룰 때,
**Then** 판정서는 **결론**(면제가 발화하지 않음)과 **서술된 기제**(메인 스레드 런치에서만 채워짐)를 **분리해** 각각 판정하고, 기제가 관측과 다르면 그 불일치를 독트린 결함으로 기록한다. 판정의 근거는 AC-BGX-001 이 남긴 **최상위 키 집합**이며, 그것 없이 이 AC 를 닫아서는 안 된다.

**[HARD] 기제 판정의 세 칸** — 관측을 다음으로 가른다:
- 키 집합에 정체성 계열 키가 **하나도 없음** → 독트린의 기제(런타임이 안 보냄)와 **일치**.
- `agent_id` 계열만 있음 → 독트린의 결론은 맞고 **기제는 틀렸다**(런타임은 보내며, 면제가 읽는 키가 아닐 뿐).
- 프로브하지 않은 제3의 키가 정체성으로 보임 → **기제 미확정**, 그 키를 명시하고 재측정 대상으로 남긴다.

**실패 조건**: 결론 일치만으로 「독트린 정확」이라고 적으면 이 AC 는 FAIL 이다. 마찬가지로 키 집합을 남기지 않은 채 첫째 칸으로 닫으면 FAIL 이다 — 그 관측은 셋을 구별하지 못한다.

### AC-BGX-005 — 측정 불가의 등급 표기 (측정 불가 분기)

**Given** 계측기 배선 또는 서브에이전트 발화가 어떤 이유로든 성립하지 않은 상태에서,
**When** 판정서를 닫을 때,
**Then** 판정서는 결과를 **「미측정」**으로 표기하고, **무엇이 막았는지**(거부 메시지 원문, 부재한 필드, 도달 못 한 단계)를 Gaps 절에 명시한다.

**[HARD]** 「미측정」을 「도달 불가」로 적어서는 안 된다. 선행 카드가 남긴 구분이 바로 이것이며, 지우는 순간 다음 사람이 같은 벽을 처음부터 다시 만난다.

### AC-BGX-006 — 처방 분기점이 수정보다 앞선 커밋 (도달 가능 분기)

**Given** 도달 가능으로 판정된 상태에서,
**When** CODE 또는 DOC 처방을 적용할 때,
**Then** 분기점 결정 기록이 **자기 커밋**에 담겨 있고, 그 커밋이 어떤 처방 커밋보다 **앞선 조상**임을 커밋 그래프가 증언해야 한다(`git merge-base --is-ancestor <결정커밋> <처방커밋>` 의 종료 코드 0, 그리고 두 커밋이 **서로 다름**).

**[HARD]** 같은 커밋에 묶인 쌍은 순서를 증언하지 못한다. 또한 `--is-ancestor X X` 는 종료 코드 0 이므로 **두 SHA 가 다름을 함께 보여야** 한다 — 같은 SHA 로 통과한 검사는 아무것도 증명하지 않는다.

**When** 정당한 `manager-git` 정체성 경로를 입력할 때,
**Then** 면제가 여전히 발화해 deny 가 나오지 않아야 한다.

**배제하는 실패 모드**: 「가드가 전부 거부한다」.

### AC-BGX-007b — 변이 검출 (처방이 CODE 인 경우)

**Given** 같은 코드 변경이 적용된 상태에서,
**When** **사칭 형태** 입력을 줄 때 — 즉 `AgentType == "manager-git"` **이면서 동시에** 서브에이전트 판별 필드가 서브에이전트임을 가리키는 입력,
**Then** deny 가 실제로 발생해야 한다.

**배제하는 실패 모드**: 「가드가 전부 허용한다」.

**[HARD] 사칭 형태의 구성 요건** — 두 조건을 **동시에** 만족해야 한다:
1. `AgentType == "manager-git"` (제로값이 아니다).
2. 판별 필드(AC-BGX-002 가 도착을 확인한 `agent_id` / `agentId`)가 서브에이전트 컨텍스트임을 가리킨다.

**[HARD] 공허 통과 차단** — `AgentType` **제로값**의 서브에이전트 형태 입력으로는 이 AC 를 만족시킬 수 없다. 그 형태의 deny 는 **이미 존재하는 테스트**가 고정하고 있으므로(`internal/hook/branch_guard_flagclass_test.go:250-266` `TestBranchGuardFlagClass_SubagentNegativePath`), 그것으로 「변이 검출」을 주장하면 **아무것도 새로 고정하지 않은 채 통과**한다. 판정서는 새로 추가한 검증이 그 기존 테스트와 **다른 입력**을 쓴다는 것을 명시해야 한다.

**[HARD]** 007a 와 007b 는 **둘 다** 필요하다. 한 방향만 돌리면 두 실패 모드가 구별되지 않는다.

### AC-BGX-011 — 판별자 부재 시 CODE 분기 폐쇄 (도달 가능 분기)

**Given** AC-BGX-002 의 측정이 확정된 상태에서,
**When** 서브에이전트를 식별할 판별 필드(`agent_id` / `agentId`)가 **부재**로 측정됐을 때,
**Then** 판정서는 **CODE 분기를 선택 불가로 선언**하고 그 근거(AC-BGX-007b 의 사칭 형태를 구성할 수 없음)를 명시하며, 분기점(AC-BGX-006)은 **DOC 만** 후보로 두고 진행한다.

**[HARD]** 이 경우 「CODE 로 갔는데 007b 를 만족시켰다」는 보고는 **공허 통과의 신호**다 — 판별자 없이 구성한 사칭 입력은 기존 테스트가 이미 고정한 형태와 같기 때문이다. 그런 보고가 오면 007b 가 아니라 이 AC 가 FAIL 이다.

**When** 판별 필드가 도착으로 측정됐을 때,
**Then** 이 AC 는 「해당 없음 — CODE 분기 구성 가능」으로 닫고 AC-BGX-006 이 두 후보를 모두 검토한다.

### AC-BGX-008 — 환경변수 축의 등급 보존 (무조건)

**When** 판정서나 정정 문안이 그 문장을 다룰 때,
**Then** 환경변수 절반은 **carried-forward-unverified**(이 카드가 재측정하지 않음)로 문장 안에 명시돼야 한다.

**실패 조건**: 환경변수 절반이 「이번에 검증됨」으로 읽히는 문안은 FAIL 이다.

### AC-BGX-009 — 주장 보유 지점 재열거와 동반 이동 (문안이 바뀌는 경우)

**Given** 판정 결과가 §A.2 집합의 문안을 바꾸는 상태에서,
**When** 정정을 적용할 때,
**Then** 다음 넷을 모두 만족한다.

**(1) 재열거는 개수를 움직이는 네 좌표를 **모두** 명시해 보고한다.** 하나라도 빠진 열거는 재현되지 않으므로 이 항목은 FAIL 이다.

| 좌표 | 보고 의무 | 이 축이 실제로 수를 움직인다는 실측 |
|---|---|---|
| **뿌리** | 좁은 뿌리(`.claude`+`internal`)와 저장소 전체 뿌리 **두 수를 모두** | 8 대 20 |
| **패턴** | 쓴 패턴 원문 + 접두 열거가 닫힘을 보인 값 | 이 리터럴은 0 이동, 철자 축은 48 대 28 |
| **시점** | 그 실행에서 잰 **SHA**(`git rev-parse --short HEAD`) | 같은 뿌리·패턴에서 20 · 20 · 21 |
| **추적 범위** | 커밋 트리(`git grep -l`)와 워킹 트리(`grep -rln`) **두 수를 모두** | **19 대 20** (델타는 미추적 `verdict.md`) |

**[HARD] 추적 범위는 「어느 쪽을 썼는지 밝힌다」로 충분하지 않다 — 뿌리와 똑같이 두 수를 모두 적는다.** 같은 뿌리·같은 패턴·같은 SHA 에서 두 명령이 다른 답을 내기 때문이다(실측 19/20). 한쪽만 적으면 읽는 사람은 그 수가 다른 쪽에서 몇인지 알 길이 없고, 그 차이가 바로 이 카드가 두 번 틀린 지점이다.

**[HARD] 어떤 plan 시점 상수도 합격 판정의 비교 대상이 되지 않는다.** §A.2 의 참조값은 **그때의 관측이지 이 AC 의 기대값이 아니며**, 「그 수를 재확인했다」는 합격 사유가 아니다. 이전 수치와 견주려면 **완전 귀속된 측정 둘**을 견준다 — 각각이 위 네 좌표를 모두 달고 있어야 하고, 맨 상수 대 측정값의 대조는 비교가 아니다. 두 측정이 다르면 그것은 불일치가 아니라 **그 사이에 트리가 움직였다는 사실**이며, 두 값과 각각의 좌표를 나란히 적는다. 한쪽을 다른 쪽에 맞추려 하지 않는다.

> **패턴만 흔들고 지나가는 것이 이 항목의 대표 실패다.** 감사가 마크업·대소문자·하이픈·공백을 흔들어 재측정했을 때 이 리터럴의 숫자는 **0만큼 움직였다** — 즉 패턴 변주는 통과의 근거가 되지 못한다. 그럼에도 패턴 좌표를 보고 의무에 남겨 둔 이유는, 「움직이지 않았다」를 **보인 것**과 **재지 않은 것**이 출력으로 구별되지 않기 때문이다.

> 네 좌표를 요구하는 이유는 **이 카드 자신이 그 실수를 했기 때문이다**: iter-2 커밋이 `plan.md` M6 에서 세는 대상 리터럴을 지워 워킹 트리 수를 −1 시켰는데, 같은 커밋의 서술은 +1(판정서 착지) 만 적어 그 사실을 가렸다(§A.2). **세는 주체가 세는 대상을 바꿀 수 있다**는 것이 이 축의 고유 위험이며, 시점 좌표가 없으면 그 변화가 언제 일어났는지조차 복구되지 않는다.

**(2) 반대 주장 보유자 2파일이 집합에 포함돼 있다.** `.claude/rules/moai/core/hooks-system.md` 와 그 템플릿 미러. 이 둘은 `tool-spawned subagent` 를 **0회** 싣기 때문에 어떤 뿌리에서도 이 리터럴로는 안 잡힌다 — **적중이 아니라 구성으로** 집합에 든다. 따라서 동반이동 집합은 **최소 10**이다.

**(3) Go 층 동반이동.** 판정이 deny reason 문안을 바꾸면 `internal/hook/branch_guard.go:604-606`(생산지)과 `internal/hook/branch_guard_test.go:694`(그 문안을 `strings.Contains(reason, "tool-spawned subagents")` 로 고정)를 **함께** 옮긴다. 문서만 고치고 이 테스트를 두면 즉시 깨진다.

**(4) 로컬 `.claude/` 사본과 `internal/template/templates/` 미러를 함께 갱신하고, 템플릿 편집 후 `make build` 를 실행한다.**

**[HARD] 이 AC 의 측정은 grep 을 피할 수 없다 — 그래서 열거로 대체한다.** 여기서 세는 것은 JSON 키가 아니라 산문 리터럴이므로 AC-BGX-002 의 키 집합 동등 비교를 그대로 상속할 수 없다. 대신 **접두 열거**를 쓴다: 세려는 토큰 앞에 무엇이 붙을 수 있는지를 `[A-Za-z]*<토큰>` 형태로 **먼저 열거해 보고**, 과다매칭원을 전부 드러낸 뒤에 앵커를 정한다. 그리고 **열거 합과 앵커 적용값이 정확히 닫히는지**를 보인다(예: 22+2+3+2 = 29). 앵커를 먼저 짐작해서 다는 것은 금지다 — 이 트리에서 camel 축의 과다매칭원 셋 중 **둘이 대문자로 시작**했고, 짐작으로 단 앵커는 그 둘을 말없이 통과시킨다.

**[HARD] 정정 대상이 아닌 것** — 넓힌 뿌리가 데려오지만 손대지 않는다: 닫힌 SPEC 아티팩트(`SPEC-RC-TESTBED-001`, `SPEC-WORKTREE-BRANCH-GUARD-FLAGCLASS-001`), `CHANGELOG.md`, 이 카드의 판정서. 전부 **그 시점의 관측 기록**이며 나중 사실에 맞춰 고치지 않는다.

## §D.1 경계 사례

- **철자가 도착했으나 값이 비어있음**: 「도착」이 아니다. 비어있지 않은 값이어야 AC-BGX-002 에서 「도착」으로 센다. 네 철자 모두에 같은 규칙이 적용된다.
- **키 집합은 남았으나 서브에이전트 호출이 0건**: AC-BGX-005(측정 불가)로 내려간다. 계측기가 도는 것과 대상 컨텍스트가 발생한 것은 별개다.
- **계측기를 셸 래퍼에 넣은 경우 — 「설치본이 판정」 위험은 발생하지 않는다.** PreToolUse 는 `.claude/hooks/moai/handle-pre-tool.sh` 를 통과하고 그 래퍼가 stdin 원문을 `payload=$(head -c 1048576)`(:37)로 **먼저** 보유하므로, 원문 덤프·키 집합 기록은 moai 재빌드도 설치본 치환도 거치지 않는다(§A.4).
- **계측기를 `TraceEntry` 확장으로 넣은 경우 — 그 위험은 되살아난다.** 그쪽은 Go 코드이므로 트리 빌드가 실제로 실행됐음을 보이지 못하면 AC-BGX-005 다. **위험의 부재는 경로에 붙는 성질이지 카드에 붙는 성질이 아니다.**
- **grep 으로 판정한 AC-BGX-002**: 앵커 유무와 무관하게 **무효**다. 이 AC 의 판정 방법은 키 집합 동등 비교로 고정돼 있고, 문자열 검색은 판정 근거가 아니다. 앵커 달린 grep 조차 다음 철자 변종에 말없이 뚫린다.
- **키 집합은 남았으나 원문 JSON 한 덩어리로만 남은 경우**: AC-BGX-001 의 형식 요건(키 단위 분리) 미충족이다. 그 상태에서 비교를 시도하면 문자열 검색으로 퇴화하므로 AC-BGX-005(측정 불가)로 내려간다.
- **과다매칭이 만든 수치를 인용한 경우**: 그 수는 **더 크고**, 큰 수는 「더 많이 찾았다」로 읽히며, 재측정해도 같은 수가 나와 검산에 안 걸린다. 접두 열거로 합이 닫히는지 보이지 못한 수치는 인용하지 않는다.
