# The statusline shows commits ahead of the upstream (↑N) next to behind

## Intent

2026-11-20 사용자 질문("커밋 수를 왜 숨기지?")에서 나온 카드예요. `src/statusline/render.rs` 는 2026-11-11 커밋 827b78594d부터 ahead 수를 일부러 숨겼는데("Ahead is deliberately hidden"), 근거 기록이 없어요. 찾아지는 유일한 출처는 당시 Issue #2376 의 승인 예시 한 줄(`🅱️ v2026.11.0 ↓969 +120` — behind 와 dirty 뿐)이고, 그건 작업이 곧장 원격으로 나가던 시절 상식이었어요. M-Flow(2026-11-20 사용자 결정)에서는 레인이 로컬 통합 브랜치에 먼저 병합하고 원격은 릴리즈 때만 움직이므로, 이제 ahead 가 "병합이 쌓이는 수"를 보여 주는 쪽이에요(오늘 로컬 v2026.11.0 은 origin 보다 100 커밋 이상 앞서요). 이 SPEC 은 ahead 를 `↑N` 으로 보여 주되, ahead 가 0이면 오늘 출력과 바이트 하나까지 같게 유지해요.

## Interview

- Q1: 어디에 숫자를 얻나요? → A: 지금 읽는 git 소스(`git status --porcelain` 헤더 `## <branch>...<upstream> [ahead N, behind M]`)가 이미 ahead 를 주고 있어요. 파서가 behind 만 담았을 뿐이라 새 git 호출은 없어요.
- Q2: 순서와 모양은요? → A: `🅱️ <branch> ↑N ↓N +N` — ahead 가 ↓ 앞, dirty 는 마지막. 색은 지금 branch 색 그대로, 0인 항목은 오늘처럼 생략해요.
- Q3: ahead 0 이면요? → A: 바이트까지 오늘과 같아요. 모든 ahead-0 골든이 재생성 diff 에서 한 글자도 바뀌지 않는 것으로 확인해요.
- Q4: 문서는요? → A: "일부러 숨긴다"는 렌더러 주석을 새 동작 설명으로 바꾸고, 제품 문서(rust-product-path)의 두 번째 줄 기술에 ↑N 을 보태요.
- Q5: goldens 는요? → A: `statusline-claude` 세트를 골든 도구로 재생성하고 diff 를 전수 리뷰해요. `tests/fixtures/statusline`(Go 시대 보관함)은 어떤 도구도 읽지 않는 읽기전용 보관함이라 비목표로 두어요.

## Non-goals

- `tests/fixtures/statusline`(Go 시대 읽기전용 보관함)의 손대기: 어떤 검사도 도구도 그 세트를 읽지 않아요.
- 새 git 호출, 새 상태 수집: 이미 읽은 소스의 필드만 추가해요.
- 원격 조작(push·fetch 추가)과 behind 임계 동작의 변경.

## Requirements

- REQ-1: When the branch is ahead of its upstream, the status line shall show the ahead count as `↑N` before the behind count.
- REQ-2 (REQ-1): IF the ahead count is 0, THEN the status line shall stay byte-identical to the line it renders today.
- REQ-3: The status line shall take the ahead count from the git source it already reads, with no new git call.
- REQ-4 (REQ-1): The line shall keep the order `🅱️ <branch> ↑N ↓N +N` with one colour for the counts, omitting a count that is 0.
- REQ-5: The renderer's doc comment and the product docs shall describe the ahead count the way the code shows it.
- REQ-6: The `statusline-claude` golden fixtures shall be regenerated by the golden tool and reviewed as one whole diff before the change goes READY.

## Acceptance

- AC-1 (REQ-1, REQ-4): `[ahead 5, behind 2]` 와 더러운 파일이 있는 픽스처에서 줄이 `🅱️ main ↑5 ↓2 +N` 순서로 나와요. 단위 시험이 파서(`[ahead 1, behind 2]`, `[ahead 1]` 단독, 빈 괄호)와 줄 순서를 고정해요.
  verify: `cargo test --locked --offline --lib statusline` 와 `cargo test --locked --offline --test statusline_cards`
- AC-2 (REQ-2): ahead 가 0인 모든 골든 케이스가 재생성 diff 에서 바이트 동일로 유지되고, ahead>0 케이스만 `↑N` 이 생겨요.
  verify: `python3 tools/statusline_golden.py --check` (재생성 후 diff 전수 리뷰)
- AC-3 (REQ-3): 파서가 기존 porcelain 헤더의 ahead 를 읽고, git 호출 횟수가 변하지 않아요(수집기 단위 시험이 같은 입력으로 앞·뒤 수를 함께 고정).
  verify: `cargo test --locked --offline --lib statusline`
- AC-4 (REQ-5): 렌더러 주석과 docs/rust-product-path.md 의 두 번째 줄 기술이 ↑N 을 설명해요.
  verify: `grep ↑ docs/rust-product-path.md`

## Decisions

- D-1: `GitStatus` 에 `ahead` 필드를 더하고 `parse_branch_header` 가 헤더의 `[ahead N, behind M]`(및 단독 형태)을 읽게 해요. 소스는 지금 그 헤더를 이미 받고 있으니 호출은 그대로예요.
- D-2: "Ahead is deliberately hidden" 주석은 새 동작 설명으로 바꿔요(숨김 이유가 기록된 곳이 없었으므로 근거도 이 SPEC 의 Intent 가 대신해요).
- D-3: 골든은 `tools/statusline_golden.py` 로만 재생성하고, ahead-0 케이스가 하나도 변하지 않는지 diff 로 전수 확인해요(상태줄 골든의 재발 교훈 적용).
- D-4: 이 변경은 같은 파일의 레이아웃 변경(SPEC-20261120-statusline-layout 개정 2)과 한 커밋으로 함께 착지해요(리더 지시, 2026-11-20): `↑N` 은 줄 2 가지 그룹 안의 뒤 숫자 앞에 서고, 골든과 사용자 예시 시험은 그 커밋 하나가 가져요.

## Risks

- R1: 파서의 괄호 헤더 변형(`[ahead N]`, `[behind N]`, `[ahead N, behind M]`, `[gone]`) 하나라도 어기면 behind 가 오늘과 달라져요 → 변형마다 단위 시험을 먼저 두고 걸치게 해요.
- R2: 골든 재생성 때 ahead-0 케이스가 변하면 REQ-2 위반의 증거가 바로 보여요 → diff 전수 리뷰에서 막아요.
- R3: 같은 파일의 병합 대기 변경과의 충돌 → base 를 그 체인 머지로 둬서 피해요.
