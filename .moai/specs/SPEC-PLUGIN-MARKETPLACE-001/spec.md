## 1. Background and Premise

### 1.1 What this SPEC does and does not do

`moai init` copies the full project scaffold into every project. The Mods design series moves part of
that payload into a plugin distributed through a marketplace. Card t1434 measured what a plugin can
carry (its verdict is the committed table in `.moai/specs/SPEC-PLUGIN-LOAD-SCOPE-001/progress.md §E.2`).
This card (t1435, 2 of 6) only **adds**: a marketplace served by the `modu-ai/moai-adk` repository
itself, a `moai` core plugin whose payload is derived from the template tree, an install step run by
`moai init` and by the three install scripts, and a `moai doctor` check that the installed plugin
version matches the binary. It **removes nothing** from the init payload (init shrink is card t1438).

### 1.2 Inputs and their limits

- Card text (operator instruction 2026-10-02): the repository becomes a marketplace
  (`.claude-plugin/marketplace.json`; for Codex a dual manifest, precedent the moai-cowork
  marketplace); `moai init` and the install script run `claude plugin marketplace add modu-ai/moai-adk`
  and `claude plugin install moai@moai-adk` when `claude` exists, fail-open with guidance on failure,
  Codex likewise; a doctor check compares the binary version with the plugin version.
- The t1434 verdict (claude 2.1.287, codex 0.160.0, 2026-10-02; every claim holds for those two
  versions only). Cells cited below as `R0x` are rows of that table.
- Observations made at base tree 7109e0900 (iteration 0), at tree 3766cef05 (iteration 1 revision) and at tree
  b6a0522a0 (iteration 2 revision; P-42 to P-46). Commands that write a registry ran only under empty scratch config
  homes; nothing was run against the real Claude or Codex profile. The raw commands and outputs are in `research.md`; the deciding lines are quoted in §1.3.
- Not available: the claude.ai design artifact, any authenticated session, any network call from an
  acceptance command. This revision made four read-only network reads, none of them a plugin or marketplace
  command: one documentation fetch (P-13) and three GitHub metadata reads (P-41); see `research.md` §2.

### 1.5 Interactions detected before any code exists

These bind the requirements and are carried as risks in §6. Items 1 and 5 need an authenticated session or
a published release; the others were measured offline.

1. **Two copies until t1438.** The scaffold copy and the plugin copy coexist. R01 shows plugin skills
   listed under a namespaced name; the project commands already list as `moai:<command>` in this
   session's skill listing, and a plugin named `moai` also yields `moai:<command>`. Whether the two
   merge, shadow or collide is UNOBSERVED. The **listing cost of the plugin side is measured** (P-31): the
   tool's projected always-on estimate is about 3,653 tokens for the core-only payload (24 skills + 17
   commands), about 3,286 for the skills alone and about 6,483 for an all-tier payload. The scaffold's own
   listing is built from the same core-tier sources, so a session that lists both pays a figure of the same
   order twice — inferred, not measured, because `claude plugin details` reports plugins only.
2. **MCP decline.** `moai init --non-interactive` leaves no project `.mcp.json` moai entry (P-19) and
   the code comment says an explicit decline is honored absolutely. `--llm gpt` declines it and `--llm both`
   forces it (`init.go:997-1003`). A plugin carrying a `moai` MCP server would start it anyway, because R06's
   suppression needs a project server with the same command to exist.
3. **Bare-name references.** Command and skill bodies call `Skill("moai")` and similar bare names; a
   plugin skill is namespaced. Whether a bare name resolves to the namespaced skill is UNMEASURED and
   becomes load-bearing at t1438.
4. **The doctor re-enters init.** The Agent Emit Embed check runs `init --non-interactive --llm both`
   (P-20); with an install step that command would act on the real profile of both tools.
5. **First-release gap.** `main` carries the new manifests only after the release PR that contains
   them (P-24, P-41: `.claude-plugin` and `plugins` return 404 on `main` today); until then
   `claude plugin marketplace add modu-ai/moai-adk` has no manifest to read.
6. **Installer and binary version skew.** The install scripts download the latest released binary. A script
   served from `main` that calls a verb the latest release lacks fails with an unknown command (P-39 shows
   the base binary's message). The installer must treat that as non-fatal (REQ-018).
7. **A diagnostic that starts a tool writes into the tool's home.** `codex plugin list --json` run against an
   empty `CODEX_HOME` created `tmp/arg0` there (P-34). OD-13 names the alternative that starts no process.

## 3. Constraints

- Tier L: 25 requirements and 25 acceptance criteria (Tier L ceilings 25 and 25, `spec-workflow.md` § SPEC Complexity Tier — both at the ceiling, so any further requirement means splitting the SPEC), with `design.md` and `research.md`. The hand-authored change set is about 45 files against the Tier L guidance of more than 15 — see `plan.md` §3 for the per-milestone list — because manifests, generator, init step, install verb, doctor check, three install scripts, two docs-site copies, an e2e script, three harness scripts, a test-home sandbox, Makefile, release script, workflow and runbook all move. Generated files (the committed payload, several hundred) are not counted. The tier follows the file count, as plan-audit iteration 1 ruled (D7); it was not chosen for the audit budget.
- Template-First: the payload is derived from `internal/template/templates/`; no file is added to the local `.claude/`, `.moai/` or `.agents/` without a template source, and nothing under `plugins/moai/` is edited by hand (it is generated and drift-checked).
- Template neutrality: the payload is derived from files the neutrality CI guard already covers (`.github/workflows/template-neutrality-check.yaml` paths are `internal/template/templates/**`); the committed copy sits outside those paths and is therefore protected by derivation plus REQ-009, not by the neutrality workflow itself.
- Verification uses only scratch-home commands. Every `claude plugin install|marketplace add` and every Codex `plugin add|marketplace add` in an acceptance command runs with `CLAUDE_CONFIG_DIR` or `CODEX_HOME` pointing at an empty directory under the session scratchpad, **a fresh one per criterion** (`acceptance.md` Conventions), and a command that reads a home names both homes. No acceptance command makes a network call (marketplace add uses a local path).
- The worktree guard refuses a command prefixed `HOME=…` and refuses `pwsh` (P-36), and repository doctrine says moving a command into a script file is not a way round it (`.claude/rules/moai/workflow/kanban-dispatch-mechanics.md:105`). So neither an acceptance command nor a harness script sets `HOME`: isolation uses scratch `CLAUDE_CONFIG_DIR`, `CODEX_HOME` and `MOAI_HOME`, the explicit seams of the product, and the protected-set hash of REQ-025. A case that cannot work without a `HOME` override — the real binary's `moai init`, which writes `$HOME/.claude/settings.json` (P-42) — is OD-14 and Gap G-8, not a workaround. PowerShell behavior is not executed locally (Gap G-3).
- The run phase inherits the t1434 forbidden-verb discipline: no install, uninstall, marketplace add, remove, update, enable, disable or configure against any real Claude or Codex home.
- No time estimates; ordering is by priority and milestone sequence.
- Acceptance commands use the plain single-invocation forms measured in this worktree session (P-25): anchored `-run '^Name$'`, no git `$()` nesting, no pipes, redirects or `; echo $?` bundled into one invocation. The `timeout` utility is not used: stock macOS has none.
- The doctor check never starts `claude`, and starts `codex` only for the bounded probe of REQ-021 (default pending OD-13).
