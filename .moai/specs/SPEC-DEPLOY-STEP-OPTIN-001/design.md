# SPEC-DEPLOY-STEP-OPTIN-001 — 설계

이 문서는 요구사항을 실현하는 구조를 적는다. 함수 이름과 자료 구조의 세부는 run 단계가 정한다. 여기서는 판정이 어디서 나고, 어떤 경계에서 다시 판정하며, 어떤 입력이 어떤 결과를 내는지를 고정한다. 키 이름과 위치는 Q1 판정(`workflow.automation.stages.<stage>`), 값 형태는 Q2 판정(닫힌 문자열 `manual`/`auto`)으로 확정되었다. 이 SPEC 은 여섯 단계를 다룬다(Q4=(b): release/deploy 는 후속 SPEC). 근거 번호 `Lnn` 은 research.md 의 증거 원장이다.

## 1. 불변식

1. **한 곳에서 판정한다.** 단계 값은 해석기 하나가 만든다. 실행 경로, 세션 시작 규칙, 산문 워크플로(읽기 동사 경유), 웹 화면이 모두 그 출력을 읽는다. 단계 키를 직접 읽는 코드는 정적 검사로 막는다(AC-DSO-005).
2. **닫힌 쪽으로 푼다.** 명시한 유효한 `auto` 만 `auto` 다. 그 밖의 모든 입력은 `manual` 이다.
3. **판정은 경계에서 다시 한다.** 프로세스 수명 동안 캐시하지 않는다. 판정 비용은 파일 두 개를 읽는 일이다.
4. **끄는 일은 죽이는 일이 아니다.** 경계에서 멈추고, 진행 중 명령·lease·워크트리·증거는 건드리지 않는다.
5. **템플릿은 값을 싣지 않는다.** 기본값은 코드에, 템플릿에는 주석 설명만 있다. 키가 파일에 있다는 사실이 곧 사람이 쓴 값이라는 증거가 되므로 "명시한 값이 예전 기본값과 같은 경우"의 구분 문제가 없다(§6).

## 3. 입력 계층과 출처

| 계층 | 위치 | 출처 라벨 | 우선순위 |
|---|---|---|---|
| 코드 기본값 | 해석기 상수(여섯 단계 모두 `manual`) | `default` | 가장 낮음 |
| project | `.moai/config/sections/workflow.yaml` 의 단계 블록 | `project` | 중간 |
| local override | `.moai/config/local/workflow.yaml` 의 같은 구조(무시되는 디렉터리, L49) | `local-override` | 가장 높음 |

- 기존 8단 설정 해석기(`config.Source`)는 쓰지 않는다. 호출자가 doctor 하나뿐이고(L41) local 경로를 프로세스 CWD 에 상대적으로 읽기 때문에(L40) 웹 서버나 다른 프로젝트 루트를 다루는 호출자에게 맞지 않는다. 새 해석기는 **프로젝트 루트를 인자로 받는** 좁은 읽기 두 개(project, local)만 하고, 출처 이름만 `config.Source` 의 `project`/`local` 과 맞춘다. local 계층 파일 이름은 `loadLocalTier` 가 `.moai/config/local/*.yaml` 을 섹션 파일 이름으로 읽는 방식(L40 주변 코드)을 따른다. 이 트리에는 그 디렉터리가 없다(L42).
- 읽기는 `yaml.Node` 기반으로 한다. 기존 로더는 워크플로 섹션을 읽다 실패하면 섹션 전체를 기본값으로 둔 채 넘어가는 관대한 경로이고(`todo_enabled.go` 의 주석) 중복 키를 구별하지 못한다. 단계 판정에는 맞지 않는다.
- 같은 키가 두 계층에 있으면 local 이 이긴다. 출력에 두 계층의 값을 모두 싣는다(`project_value`, `local_value`) — 웹이 override 를 보여 주려면 필요하다.
- `.claude/settings.local.json` 은 단계 출처가 아니다.
- **정지 표식은 설정 계층이 아니다.** Q9=(b) 판정: 즉시 중지는 설정 값을 쓰지 않고 `.moai/state/` 아래 표식 파일을 쓴다. 해석기는 계층을 읽기 전에 표식을 먼저 보고, 표식이 서 있는 동안 모든 단계를 `manual`(출처 `stop-marker`, 이유 `stop-marker`)로 돌려준다 — local override 도 이긴다. 표식의 유무는 revision 에 들어가지 않는다(표식은 런타임 상태이며 웹이 별도로 보여 준다).

## 4. 해석기 출력과 판정 표

출력(단계마다): `effective` (`manual`/`auto`), `source`, `reason`, `project_value`, `local_value`. 전체에 `revision` 하나.

이유 코드와 입력의 대응:

| 입력 | effective | reason |
|---|---|---|
| 단계 키 없음 / 블록 없음 / 파일 없음 / `.moai` 없음 / 빈 루트 문자열 | manual | `absent` |
| `manual` | manual | `explicit-manual` |
| `auto` | auto | `explicit-auto` |
| null / 불리언 / 숫자 / 시퀀스 / 매핑 | manual | `wrong-type` |
| 문자열이지만 `manual`·`auto` 가 아님(`Auto`, `auto `, `yes`, 빈 문자열, 오타) | manual | `invalid-value` |
| 같은 단계 키가 한 파일에 두 번 | manual | `duplicate-key` |
| 알 수 없는 단계 이름 | (여섯 단계에 영향 없음) | 진단 목록에만 `unknown-stage` |
| 단계 블록이 매핑이 아님 | 여섯 모두 manual | `block-not-mapping` |
| 파일이 YAML 로 파싱되지 않음 | 여섯 모두 manual | `file-unparseable` |
| 파일을 읽을 수 없음 | 여섯 모두 manual | `file-unreadable` |
| YAML 별칭이 가리키는 값 | 별칭을 펼치지 않는다. 값이 문자열 스칼라가 아니면 manual | `wrong-type` |

한 계층의 읽기 실패는 그 계층의 여섯 단계를 `manual`(`file-unreadable`/`file-unparseable`)로 보고 다른 계층은 계속 읽는다. local 계층이 읽히고 어떤 단계에 유효한 값을 말하면 그 값이 이긴다(local 이 project 를 이긴다는 규칙 그대로). 이 조합(project 읽기 실패, local 의 명시 `auto`)은 AC-DSO-004 의 (f) 사례로 고정한다.

결정 Q5=(a)(2026-10-19 판정, Codex 교차): 잘못된 값이 있는 단계만 수동이고 유효한 형제 단계는 그대로 읽는다. 블록 전체가 수동이 되는 경우는 블록 자체를 읽지 못할 때뿐이다(매핑 아님·파싱 불가·읽기 불가). 위 표는 그대로다.

**revision.** 세 계층의 단계 블록을 정규화(단계 이름 정렬, 값 문자열 정규화)해 직렬화한 값의 sha256 앞 12 hex(Q13 (a)). 단계와 무관한 키가 바뀌어도 변하지 않고, 어느 계층이든 단계 관련 입력이 바뀌면 변한다. 해석 불가 입력도 입력 바이트의 일부로 들어간다(읽지 못한 상태 자체가 revision 을 만든다). 정지 표식은 설정 입력이 아니므로 revision 에 들어가지 않는다(§3).

## 5. 경계와 진행 중 작업

- **전달 본체.** `factory_card_pr.go` 의 네 번의 원격 변경 앞에는 이미 `verifyLease` 재확인이 있다(L54). 단계 판정은 같은 자리에 나란히 둔다(한 클로저가 lease 와 정책을 함께 재확인). `push` 는 추가로 `merge-ready → merging` 전이(`:342`) **앞**에서 한 번 더 판정한다. 그래야 수동일 때 카드 레코드의 상태와 version 이 변하지 않는다(AC-DSO-006).
- **재진입.** 같은 카드에 `complete` 를 다시 부르면 기존 재시도 규칙(`merging` 이면 lease 보유자만)을 그대로 따르고, 각 경계에서 정책을 다시 읽는다. 이미 통과한 단계는 레코드 상태(`pr-open` 이상)와 원격 상태(브랜치·PR 존재)로 알 수 있고 다시 수행하지 않는다.
- **끄는 경우.** 정책이 `manual` 로 바뀌면 다음 경계에서 `refused <stage>-manual` 로 멈춘다. 이미 나간 `git push`·`gh` 호출은 취소하지 않는다. lease·워크트리·증거 파일은 지우지 않는다(AC-DSO-012).
- **켜는 경우.** 정책이 `auto` 로 바뀌어도 지난 경계는 되살리지 않는다. 카드는 자기 상태에서 다음 경계를 만날 때 비로소 새 판정을 받는다(AC-DSO-013).
- **정지 표식.** 모든 경계의 재판정은 해석기 읽기를 거치므로(§3) 표식을 함께 본다. 표식이 서면 경계는 단계가 `manual` 인 것과 똑같이 멈추되 메시지에 표식 상태를 댄다. 표식은 명시적 release 로만 지우고 조용히 만료되지 않는다(잊힌 표식이 모든 것을 수동으로 두는 쪽이 안전하다). release 도 감사 기록을 남긴다.
- **전환 기록.** 단계 정책이 허가한 전환(`merge-ready → merging`, `→ pr-open`)에는 판정의 revision 을 레코드에 남긴다. 레코드 스키마 변경은 한 필드 추가이며 기존 레코드는 빈 값으로 읽는다.
- **레인 시작과 세션 시작 규칙.** 스탬프(`MOAI_FACTORY_AUTO_DISPATCH`)는 계속 레인 시작 시점의 값이다. 스탬프는 정책이 `auto` 이고 `--no-auto-dispatch` 가 없을 때만 `auto` 로 찍힌다. 시작 뒤에 정책이 바뀌어도 이미 시작한 레인의 안내문은 바뀌지 않지만, 레인이 `moai factory next` 를 인자 없이 부르는 순간 다시 판정하므로 강제는 경계에서 이뤄진다(L45). 스탬프를 읽는 두 곳은 안내문 선택일 뿐이다(L46).

## 6. update 와 기본값

- **템플릿은 주석 블록만 싣는다.** 단계 값을 싣지 않으므로 3-way 병합의 "사용자 값이 base 와 같으면 새 템플릿 값을 쓴다"(`node_merge.go:449`, L33)가 단계 값에 작동할 일이 없다. 사용자가 쓴 키는 템플릿에 없는 키이므로 항상 보존된다(L34).
- **명시 여부의 구분.** 단계 키가 project 파일에 있으면 사람이나 웹 저장이 쓴 값이다. 웹의 "기본값으로 되돌리기"는 키를 지운다(YAML 패치의 제거 연산). 값을 `manual` 로 쓰는 일과 키를 지우는 일은 의도가 다르고 출처 라벨도 다르다(`project` / `default`).
- **좁은 migration 은 두지 않는다.** 값을 싣는 템플릿이 있었다면 "원본 키 존재 여부와 기존 값·출처 보존"을 위한 migration 이 필요했다. 값을 싣지 않으므로 migration 코드가 없다. 대신 시험이 두 가지를 못 박는다: 낡은 파일에 블록이 없으면 update 뒤에도 여섯 모두 `default`/`manual`(AC-DSO-014), 템플릿이 단계 값을 싣지 못한다(AC-DSO-015).
- **기본값 변경은 호환 파괴다.** 코드 기본값을 `auto` 로 바꾸는 변경은 이 SPEC 의 범위 밖이며 시험 `TestStagePolicy_CodeDefaultsAllManual` 이 여섯 단계 기본값을 고정한다.
- **승인된 로컬 factory 설정.** 이 저장소의 배포본 `workflow.yaml` 은 템플릿과 다른 운영자 파일이다(L56, L25). update 는 이 파일을 템플릿으로 덮어쓰지 않는다. 이 저장소의 레인 전달이 새 해석기 아래에서도 이어지려면 명시 `auto` 가 적혀야 한다. Q8=(a) 판정(2026-10-19, OPERATOR-HELD): project 계층의 추적 파일에 적는다(M6). 판정은 유효하되 실제 설정 파일 쓰기는 운영자 keep-set 이며 별도 운영자 승인을 게이트로 요구한다(리더 재정 2026-10-19 — 승인 전에는 M6 이 (3) 을 건너뛴다). Q3=(a) 와 맞물려 `review_repair: auto` 도 그 키 가운데 하나로 적는다(review gate 를 켠 현재 운영 유지).
- **`AGENTS.local.md`·`CLAUDE.local.md`.** 배포 템플릿에 없다(L35, 양성 대조 L36). 이 SPEC 은 두 파일을 배포하거나 고치지 않는다.
- **템플릿-사본 일치.** `.claude/`·`.agents/`·`.codex/` 아래 변경 파일은 사본과 `diff -q` 종료 코드 0(L55 가 현재 일치를 보인다). `.moai/config/sections/*.yaml` 은 운영자 자신의 파일이라 다르며(L56) 주석 블록의 헤더 줄이 양쪽에 1회씩 있는지로 확인한다.

## 7. 웹 설계

- **스키마.** 여섯 단계를 `workflow` 섹션 아래 닫힌 집합 라디오 필드로 정의한다(`project.continuation` 이 쓰는 `closedSeam` 과 같은 패턴, L16). 영문 옵션 라벨은 그대로 두고 옵션 설명과 영향 설명은 로케일을 따른다.
- **읽기 모델.** 기존 `SchemaCurrentValues` 는 문자열 스칼라 맵이다(L31). 단계 필드는 이 맵 대신 해석기 출력(`effective`, `source`, `project_value`, `local_value`, `reason`)과 페이지 단위 `revision` 을 담는 별도 뷰 구조로 렌더한다. 화면의 어떤 값도 디스크 스칼라를 직접 읽지 않는다.
- **표시.** 단계마다 효력, 출처 라벨, override 표시(local 이 project 와 다른 효력을 만들면), 영향 설명(아래), revision. 영향 설명은 "이 단계가 auto 이면 무엇이 사람 확인 없이 일어나는지"와 "수동일 때 대신 무엇을 직접 해야 하는지"를 한 문장씩 담는다. 예: `push` auto — 레인이 준비 검사를 통과한 카드 브랜치를 원격에 올린다 / 수동 — `git push origin <branch>` 를 직접 한다.
- **저장.** 기존 `POST /save` 흐름에 단계 필드를 더한다. 검증 실패는 기존 방식대로 쓰기를 모두 멈춘다(L28): 단계 값은 닫힌 집합, 중복 필드 거부, 알 수 없는 단계 이름 거부. 쓰기는 project 계층의 한 파일에 대한 YAML 패치(임시 파일 후 rename, L32)이므로 여러 파일에 걸친 부분 실패가 없다. 직렬화는 기존 `saveMu`(L28)가 맡는다. local override 가 고정한 단계에 대한 저장은 거부하지 않는다(REQ-DSO-016, 결정 Q15): project 값만 쓰고 효력은 local 이 그대로이며, 응답과 감사 기록이 `overridden-by-local` 을 알린다. 세 계층 모델에서 project 쓰기는 local 을 이길 수 없으므로 never-overwrite 는 보존되고, 거부하면 override 해제 뒤 적용될 운영자 의사가 기록되지 않는다.
- **응답.** 저장 직후 디스크에서 해석기를 다시 호출해 여섯 단계와 revision 을 응답에 싣는다. 요청 값을 되돌려 주지 않는다.
- **감사 기록.** 추가 전용 한 줄 JSON(Q10 (a)): `ts`, `channel`(`web`), `actor`(운영체제 사용자), `changes`(단계별 `before`/`after`), `result`(`saved`/`rejected`), `reason`, `revision`. 거부도 기록한다. 단일 `write` 로 줄 하나를 쓴다. 기록 실패는 저장을 막지 않지만 응답 배너에 경고를 싣는다(감사 부재를 침묵시키지 않는다).
- **즉시 중지·해제.** Q9=(b) 판정: 설정 값을 쓰지 않고 `.moai/state/` 아래 정지 표식을 쓴다. stop 은 표식을 한 번의 원자적 쓰기로 생기게 하고 감사 기록을 남긴다. release 는 표식을 지우고 감사 기록을 남긴다. 표식은 조용히 만료되지 않는다. 두 경로 모두 POST 전용으로 `routes()` 에 두어 Host·same-origin 미들웨어가 감싸게 한다(L27). 해석기가 표식을 계층 읽기 전에 보므로(§3) local override 를 포함한 모든 계층이 표식 아래 멈춘다. 화면은 표식 상태와 멈추기 전의 단계별 효력·출처를 알린다. 감사 기록은 저장과 같은 JSONL 에 `action`(`save`/`stop`/`release`)을 더해 남긴다(Q10 (a) 필드 유지).
- **권한.** 새 접근 제어 층은 두지 않는다. 기존 루프백 Host 검사와 same-origin 검사(L27)를 단계 저장에도 그대로 적용하고, 웹이 쓰는 계층은 project 하나뿐이다. 역할별 ACL 은 범위 밖이다.
- **t1752·t1644 와의 관계.** 같은 스키마 파일(`schema_sections.go`)에 필드를 더하므로 먼저 착지한 쪽이 기준이 되고 나중 쪽이 다시 맞춘다. 이 SPEC 은 단계 필드 그룹만 더하고 다른 그룹의 정의를 건드리지 않는다.

## 8. 작성자 권고 (참고용, 결정 색인 밖)

결정 색인의 행은 선호 답을 싣지 않는다. 아래는 이 SPEC 을 쓴 에이전트의 검토 의견이며 결정이 아니다. 근거를 같이 적는다. 2026-10-19 판정이 채워졌다(decision-index.md) — Q4·Q7·Q9 의 판정은 아래 권고와 다른 쪽을 택했고, 권고는 기록으로 남는다. 운영자가 판정을 다시 바꾸면 해당 마일스톤의 승인 파일 목록과 시험 이름만 고치면 된다.

- **Q1 (a).** 일곱 단계가 한 파일의 한 블록에 있으면 웹 저장이 하나의 원자적 rename 이고, 읽는 코드가 없는 기존 키(L20)와 이 SPEC 의 새 키가 같은 자리에서 서로 다른 말을 하는 일이 없다. (b) 는 프로필 셋에 일곱 키씩 늘고 모드 전환마다 동의가 바뀐다.
- **Q3 (a).** 규칙 순위 1 이 (b)를 가리키는 이유는 게이트를 켠 배포의 현재 차단을 유지해서다. 그러나 카드의 동의 모델은 단계별 명시이고, (b) 는 웹에 키가 없는 단계가 `auto` 로 나타나 "단일 판정·단일 출처" 불변식을 깬다. 이 저장소처럼 게이트를 켠 배포는 Q8 의 명시 `auto` 한 줄로 현재 동작을 유지한다.
- **Q4 (a).** 카드가 일곱 단계를 열거했고 웹이 여섯만 보이면 "release/deploy 는 자동화된다"는 오해의 여지가 생긴다. 비용은 키 하나와 정적 검사 하나이고 동작은 바꾸지 않는다. 규칙 순위 3 은 (b)를 가리킨다. (판정은 (b) — 권고와 다름.)
- **Q5 (a).** 카드 문언이 "지정되지 않은 단계"를 수동으로 읽으라고 했다. 오타 하나가 다른 단계의 유효한 동의를 지우면 사용자는 켜 둔 자동화가 멈춘 것을 모른다. 이유 코드가 단계마다 붙으므로 웹이 어느 단계가 왜 수동인지 보인다.
