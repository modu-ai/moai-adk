## §F Milestones

### M1 — Group (a): profile persistence (decision-heavy)

Decisions to settle while writing (highest change-likelihood first):

1. **Storage location.** Proposed: project-root `.design-dna/` directory —
   `profiles/<slug>.json` + an `active` marker file naming the selected slug.
   Rationale: profiles describe one product's design, so they version with the
   project; the directory is outside MoAI's managed namespaces (no `moai
   update` interaction) and outside the skill dir (survives skill
   reinstall — the property ADR 0006's marker-first design protects). Rejected
   alternatives to record in the reference: in-skill storage (dies on update);
   home-global-only (invisible to the repo); token-merge (the copy-race shape
   upstream rejected).
2. **Marker shape.** A one-line marker naming the slug (upstream: project-root
   `.diagram-design` marker). Keep it a file the skill defines and documents;
   no tooling beyond Read/Write is introduced.
3. **Metadata header.** Small fixed fields: origin reference (URL/screenshot
   note), schema version, extraction date is the PROJECT's data (a user
   artifact), not a template-internal date — neutrality binds template files,
   not user-generated profiles; state this distinction in the reference.

Then author `references/diagram-profiles.md` (REQ-1..REQ-5: mechanism,
marker-first resolution incl. no-marker = no-guess, slug grammar, header,
load-time schema check + "not observed" backfill, confirm-before-overwrite +
verify-by-re-read), add the SKILL.md pointer section (Phase 2 save hook,
Phase 3 start-from-profile), mirror both files.

### M2 — Group (b): importer references (decision-heavy)

Decisions to settle while writing:

1. **Procedure, not scripts.** The reference documents the pipeline the
   reading agent executes: decode container (drawio) → read source as data →
   build IR (nodes/edges/labels/groups; no coordinates) → set the four dials →
   run the numeric layout pass from scratch → author → lint. Upstream's
   extractors justify the ORDER (extract first, never eyeball), not shipped
   code.
2. **Routing composition.** State explicitly: Step 0's routing table still
   decides where a diagram lives; import is invoked when the caller wants an
   image deliverable from an existing source; on delivery the source is
   replaced/removed in the same change (REQ-10). This is the one-home rule
   extended to migration, not a routing-table exception.
3. **Fidelity ledger shape.** A short per-import block: nodes/edges in source,
   in output, merged/collapsed/dropped with one-line reasons, budget-overrun
   resolution (zone/split per the detail ceilings), and the recorded
   check-svg pass.

Then author both importer files (REQ-6..REQ-11; import-drawio carries the four
container shapes + decode-first, REQ-8), add the two SKILL.md table rows marked
opt-in (REQ-12), mirror all three files.

## §G Anti-Patterns

- Writing an importer reference that renders or embeds the source format
  (mermaid-in-SVG) — the migration ENDS the source, never preserves it.
- Carrying source geometry "because the layout was already good" — the render-
  fix loop this skill exists to remove; layout is always recomputed.
- Adding the importer mention to `description`/`when_to_use` "so it triggers
  better" — routing drift; the body table row is the discoverability surface.
- Putting the profile store inside the skill directory or `.moai/` — both are
  wiped/managed by `moai update` semantics; REQ-2's read-in-place property
  exists precisely to avoid that.
- Inventing t166 diagnostic codes to "pre-align" the ledger wording — write
  quality-rule numbers (authoring.md §2.5) only; align codes at run-phase.
- Growing SKILL.md sections instead of reference files (500-line ceiling;
   progressive disclosure — SKILL.md is the index, references are the body).
