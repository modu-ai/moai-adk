# a reference-transaction guard keeps the integration branch moving only through the landing command

## Intent

`card land` (SPEC-20261121-card-land) moves the integration branch with one compare-and-swap, but nothing stops any other git command from moving it: a lane that runs `git branch -f`, a commit made in a worktree that has the branch checked out, a `reset --hard` or a `fetch` into it all move the one branch every landing is measured against. The audit of the landing command also left one open item for this slice: a stop between the move and the close leaves the branch moved and no ledger row of the move.

This SPEC is slice 1b of SPEC-20261121-flow-skeleton: a git `reference-transaction` hook that refuses every create, move and delete of the integration branch unless a short record written by the lander names exactly that move, plus the case and alias rules of the integration branch's name, plus the ledger row that `card land` writes before it moves the branch. The protected name is one value for the whole repository, kept in a record in the common git folder, because the profile that names the integration branch is a tracked file and every worktree reads the one of its own branch (after the later rename, a lane branch cut before it would name the old branch). The merge of a head onto the tip in a scratch worktree and the land evidence are the slice after this one; the master SPEC's plan text still calls the land evidence slice 1b and is revised with that slice.

Measured on this machine in scratch repositories (git 2.54.0, `reference-transaction` hook that only logs): the old value the hook reads is zero whenever the caller did not name one, so the guard resolves the current value itself; `git pack-refs --all` and `git gc` send two transactions, first `zero → value` and then the prune of the loose copy as `value → zero` with the loose file present, the packed entry equal to the current value and the old value named; `git branch -D` sends `zero → zero` for a loose-only and a packed-only ref; `git symbolic-ref` sends the new value as `ref:<target>`; the hook runs twice per state when the loose and the packed store both change; and a hook at the `committed` state can run `update-ref` and recreate a deleted ref. The leader measured that the hook, placed in the shared hooks folder, fires for the primary worktree and every linked worktree and refuses all eleven ways of moving the ref that were tried, that an environment variable is no pass, and that a lower-case alias of a mixed-case branch overwrote the branch's own file on a case-insensitive file system and lost the branch.

## Non-goals

- The merge of a head onto the tip in a scratch worktree, the land evidence and any check of an audit verdict: the slice after this one.
- Every moai command that takes a branch name accepting any spelling of the integration branch's name, the refusal on the pre-push side and every remote ref: they belong to the remote copy step, because no remote copy of the integration branch exists yet.
- Installing the hook file. The hook text is provided here as bytes; the managed-hook installer of the go-path-removal work adds it as a third managed name by a pair request on that module. Installing it in the real repository is a change of repository protection and waits for the user's pick, so until then the text is installed by hand in test repositories only.
- Removing a case variant that already exists. The guard and the landing command report it; removing it is a later moai action under the user's pick, never a hook bypass.
- A defence against a caller that edits `.git` or removes the hook on purpose: the guard stops accidents, not sabotage (the hook-guard rules already refuse `core.hooksPath` on a command line).
- Closing the one measured gap of the prune rule (D-3): a later slice may restore the ref from the `committed` state.
- Changing the recorded name: the rename of the integration branch is its own later action and writes the record; this slice writes it only when it is absent.

## Requirements

- REQ-1: When git prepares a reference transaction that creates, moves or deletes the integration branch, the reference guard shall refuse it unless the intent record names exactly that ref, the value the ref has now and the new value, and the current value is an ancestor of the new value · failure: none — a refusal exits non-zero before any ref changes and names the missing or mismatching part, a creation needs the record but no ancestor test, no record ever allows a deletion, and a replayed or rewound move is refused.
- REQ-2: When a reference transaction leaves the integration branch at the value it already has, including the prune of its loose copy after packing, the reference guard shall let the transaction pass · failure: none — a delete that names no old value, a loose ref that is not packed and a packed ref with no loose copy are deletions and are refused.
- REQ-3: IF a reference transaction creates, moves or deletes a branch under refs/heads whose name differs from the integration branch's name only in letter case, or begins with such a spelling and a slash, THEN the reference guard shall refuse it with a message that names the right spelling and the command to use · failure: none — nothing is written, no alias or second branch is ever created, and the answer of the landing command names a variant that already exists.
- REQ-4: IF a reference transaction makes a ref under refs/heads symbolic to the integration branch or to a case variant of its name, or makes the integration branch itself symbolic, THEN the reference guard shall refuse it · failure: none — a worktree's HEAD that points at the integration branch is not a ref under refs/heads and stays allowed.
- REQ-5: When git runs the hook, the hook text shall start the guard only for a transaction that has a line naming a ref under refs/heads whose name equals the recorded name ignoring case or begins with it and a slash, or a line whose old or new value is a symbolic value that points at that name or below it, at the prepared and committed states, and refuse that transaction naming the cause when the moai program cannot be found or cannot run · failure: none — every other transaction and every other state exits 0 without starting any program, a repository with no record is not protected and passes, and a guard that is missing never lets a transaction on the recorded branch pass unchecked.
- REQ-6: When the card land command moves the integration branch, the card land command shall write the intent record, readable and writable by its owner only, before the reference update and remove it when the call ends · failure: none — an older file with wider rights is replaced by a private one, a record left by a stopped call is replaced by the next call, and a move the guard refuses is reported with the guard's own message and not as a moved tip.
- REQ-7: When the card land command has made every check of the close, the card land command shall write one ledger row that names the branch, the tip read, the candidate and the caller before it moves the branch · failure: none — a call that refuses before the move writes no row, an update that git or the guard refuses leaves the row and nothing else, a rerun for the same card, candidate and tip writes no second row, and a close refused after the move leaves the row as the ledger record of the move.
- REQ-8: When the reference guard or the landing command needs the integration branch's name, the reference guard module shall read it from the record in the common git folder through one function, which takes the profile's value only for a repository that has no record and then writes it as the record · failure: none — no record and no profile value leaves nothing to protect, and a profile that disagrees with the record is reported and never obeyed.
- REQ-9: When a transaction that the intent record allowed has committed, the reference guard shall remove the record · failure: none — the same record cannot allow a second move, and a transaction that aborted leaves the record to the lander that wrote it.
- REQ-10: When the installer asks for the hook, the reference guard module shall provide the hook text as bytes of a POSIX shell script · failure: none — the text holds no spelling of any branch name and finds moai on the path and then in the user's moai folder.
- REQ-11: When a worktree's checked-out profile names another integration branch than the record, the reference guard shall still refuse every move of the recorded branch from the one record, which the hook text and the program read the same way (its first line with the blanks and the carriage return trimmed, accepted only as a full branch reference) · failure: none — a line that is not a full branch reference protects nothing in either, the refusal and the answer of the landing command report the disagreement, and the branch the profile names is not protected by it.
- REQ-12: When git prepares a reference transaction that deletes a branch while the last operand of the git command line that runs the hook is the integration branch, the hook text shall refuse that transaction and put back the reflog that git moved aside before the delete · failure: none — the source branch of a rename onto the integration branch keeps its value and its reflog, a delete under a command line that does not name the integration branch passes, and a caller whose parent process is not a git command line is not seen (Risks).

## Decisions

- D-1: The guard's entry is an action of the card command, `card guard <state>`, read from the hook's arguments and standard input (decision D-1 of the flow skeleton: no new top-level word). It is run by git and by nothing else; the hook text is provided as bytes by the module.
- D-2: The guard decides on the value the ref has now, resolved by the guard from git, and never on the old value the hook reads: that value is zero when the caller named none.
- D-3: A transaction that deletes the integration branch passes as a prune only when the loose file exists, the packed store holds the same value as the resolved current value and the transaction names that value as its old value; every other delete is refused. Measured with git 2.54.0 by the audit and again in the slice: git sends a delete together with a `0 0` companion transaction that this rule refuses first, so `git update-ref -d <ref> <value>` after `git pack-refs --no-prune` is refused and the earlier note of a gap was wrong; the loose-copy and packed-value conditions are tested by calling the guard with the one prune line.
- D-4: The intent record is one JSON file in the common git folder, `moai/land-intent`, with `ref`, `old`, `new`, `by` and `at`, written by a temporary file and a rename, mode 0600, and single use. The `old` value is zero for a creation. A record carries no expiry: a stale record can allow only the one fast-forward the lander had checked, and the next call replaces it.
- D-5: Case variants are refused for create, move and delete, deletion included: on a case-insensitive file system deleting a variant's file deletes the branch's own. The names are compared by lower-casing both; a name that begins with a variant and a slash is refused for the same reason (a folder where the branch's file is). The message names the profile's spelling and the landing command.
- D-6: A symbolic update is read from the new value of the transaction line (`ref:<target>`, measured with git 2.54.0).
- D-7: When the hook has to start the guard and cannot find or start moai it refuses that transaction: a guard that fails open is a guard that is off without a word. Only a transaction that names the recorded branch, a variant of it or a symbolic value that points at one of them reaches this point (D-10), so a git client with no moai on its path still commits on every other branch; the hook text looks in the path and then in the user's moai folder.
- D-8: The start row is the free event kind `card.land_started` with branch, tip, candidate and caller, written in the one transaction that runs the checks of the close, so it refuses for the same reasons as the close and no schema or table changes. One row exists per card, candidate and tip; a rerun finds it and writes none.
- D-9: The order of a landing call becomes: checks, the start row, the intent record, the reference update, removal of the record, the close. A stop at any point leaves one of: nothing moved, a row without a move (the next call proceeds), or a move with its row (the next call closes).
- D-10: The hook filters in shell before it starts anything: it reads the recorded name, lower-cases it and the whole transaction once with the ASCII lower-casing of `tr`, reads the lines with the shell's own `read`, and starts the guard only for an equal name, a name that begins with it and a slash, or a symbolic value that points at such a name (an old or new value of `ref:` followed by it). The guard repeats the comparison in full; the filter may only start the guard too often, never too rarely, for ASCII names.
- D-11: The record is one file in the common git folder, `moai/integration-branch`, holding the full reference (`refs/heads/<name>`) on one line, written by a temporary file and a rename. It is written by the landing command and by the setup that installs the hook, from the profile read in the primary worktree, and only when it is absent; a lane's checked-out profile never writes it. A profile that disagrees with it is reported on the guard's refusal and in the answer of `card land`, and the record wins. Changing the record is the action of the later rename.
- D-12: The start row is written before the update, so a refused update (the branch moved, a lock file, the guard) leaves exactly that one row; the landing command's earlier tests that asserted an unchanged ledger after such a refusal assert one new event of that kind instead.
- D-13: The delete of the source of a rename comes in a transaction of its own before the integration branch is touched. Measured with git 2.54.0: `branch -M side Integ` sends the delete of `side` with its reflog moved to `logs/refs/.tmp-renamed-log`, then a `0 0` delete of the target, which this guard refuses, and git does not put `side` back. A transaction cannot say what it is part of, so the hook looks at its parent process, which is the git command, and refuses a branch delete when the last word of the command that is not an option (a `--` and a word that starts with `-` are skipped) equals the recorded name ignoring case or its full reference, so `git -C <name> branch -D tmp` passes (audit N-14); with no `ps` it reads `/proc/<pid>/cmdline`, and with neither it cannot see the command, and the transaction that deletes the source and creates the protected name in one go still hits the main path; it then moves the reflog file back to the source's own log when that file is there and the source has none. The check costs one `ps` and nothing for a transaction with no branch delete.
- D-14: The hook takes the common git folder from its own path (`<common>/hooks/<name>`) when the record is there and asks `git rev-parse --git-common-dir` only otherwise (a relative `$0`, as git gives it in the primary worktree, is resolved against the current folder, audit N-16), as for a hook under `core.hooksPath`: git gives the hook no `GIT_DIR`, and the question cost 14 ms of every run (measured).
- D-15: `git branch -c` and `-C` write the copy with the files backend's own code, outside a reference transaction, so no hook runs (measured with git 2.54.0, loose and packed; AC-20 pins it). The defence is in layers: the landing command refuses a branch that is not where its own newest start row left it (SPEC-20261121-card-land REQ-12), and the tool's preflight hook (another card) refuses `branch -c`, `-C`, `-m`, `-M`, `update-ref` and `push` that name the integration branch from an agent session. A copy still moves the branch until the next landing finds it.

## Risks

- A rename onto the integration branch from a caller whose parent process is not a git command line (a library or an editor that writes references itself, libgit2 tools and IDEs) still loses the source branch, and the leader chose to document it with the recovery (the source's value is in the reflog of the integration branch's last landing and in `git reflog`; put it back with `git branch <name> <sha>`) and to build no journal (option B of the card note): the guard refuses the later `0 0` delete of the target and git does not put the source back (audit B-1). The hook cannot see the connection there; the command-line path is covered (D-13).
- The restore of the reflog relies on the file name `logs/refs/.tmp-renamed-log` of the files backend; with another backend or another name the reflog stays aside and the value of the source still survives.
- `git branch -c` and `-C` move the integration branch with no hook call (D-15, AC-20); the next `card land` refuses the drift and names the way back. Between the copy and that landing the branch is wrong, and a hand-made fast-forward is accepted as no drift. The rename check reads the command line of the hook's parent and looks at its last operand, so a command that ends with the integration name while it deletes some other branch is refused with the rename message; this is rare and the message names the way out.
- With neither `ps` nor `/proc` the hook cannot see the command, and the source of a rename onto the integration branch is lost as in the first item; a transaction that deletes the source and creates the protected name together is still refused. A machine with no `ps` is not one this project's agents run on.
- The hook runs twice per state when the loose and the packed store both change. The shell filter (D-10) starts the guard only for a transaction that touches the recorded branch, a variant or a symbolic value, so an ordinary commit starts no program; the filter lower-cases ASCII only, so a branch name with non-ASCII letters is not covered by it, and the cost of the filter itself is measured in the slice, not assumed.
- The hook is a shell process that git starts for each state of each transaction: a commit starts it 7 times and a branch switch 12 times (measured), so even an early exit costs about 5 ms a run and the rest of the cost is the one lower-casing and one `cat`; the numbers are in the Result.
- A hook installed with a moai that lacks `card guard` refuses every transaction on the recorded branch (it fails closed) and passes the rest; the installer ships the hook only with a moai that has `card guard` (its own work). An existing loose case variant makes `pack-refs` report a failure without failing (audit N-9), a stale intent record lets one fast-forward through (N-10) and `core.hooksPath` pointing elsewhere bypasses a hook not installed there (non-goal).
- A repository with no record is unprotected: the hook has no name to filter on. The setup that installs the hook writes the record, and until it exists the first landing call writes it; a hook installed by hand in a test repository needs the record written by the test.
- A test that creates a case variant cannot rely on the file system: a case-sensitive file system creates it, a case-insensitive one refuses a loose collision. The tests use the packed state, where the guard alone decides, and assert the message and the absence of the second branch.
- git before 2.28 has no `reference-transaction` hook, and the symbolic form was measured only with git 2.54.0; the installer's check of the git version is part of its own work.
- After the hook is installed the leader's own fast-forward merge of the integration branch in the primary worktree is refused. The leader lands with `card land`; the card operations document says so.
