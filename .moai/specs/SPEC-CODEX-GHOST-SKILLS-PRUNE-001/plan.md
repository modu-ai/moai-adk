# SPEC-CODEX-GHOST-SKILLS-PRUNE-001 — 구현 계획

정렬 원칙: 되돌리기 어려운 결정을 앞에, 기계적인 단계를 뒤에. §A 와 §B 가 사람이 실제로 이견을 낼 수 있는 두 결정이고, §F 이후는 그 결정이 정해지면 따라오는 작업이다.

## §A 결정 1 — 동사가 어디에 사는가

**결정: `moai clean` 에 스코프 플래그를 하나 더 붙인다 — `moai clean --codex-skills [--force]`.**

세 후보를 실제 소스를 읽고 비교했다.

### 후보 (c) — clean 계열의 형제 [채택]

`internal/cli/clean.go` 의 `newCleanCmd` 는 평범한 cobra 명령이다: `GroupID: "tools"`, `RunE`, 그리고 cobra 가 파싱하는 두 개의 불리언 플래그 `--force`(기본 dry-run) 와 `--home`(스코프 선택). `--home` 은 **"불리언 플래그 하나로 두 번째 스코프를 고르고, 그 스코프 전용 러너(`runCleanHome`)로 분기한다"** 는 선례를 이미 만들어 놓았다.

채택 근거:

1. **이미 심사를 통과한 파괴적 동사의 모양이 여기에 있다.** `clean_home.go` 는 허용목록 전용 스캐너, 후보를 만든 **바로 그 순회 안에서** 상의하는 단일 가드 술어(`isCarvedOut`), dry-run 기본 + 명시적 `--force`, 그리고 `@MX:WARN` 마커까지 갖췄다. 이 카드의 안전 경계(§C.3)는 구조적으로 같은 문제 — "허용목록 밖은 손대지 않는다" — 이므로 새 모양을 발명할 이유가 없다.
2. **`--force` 를 손으로 파싱하지 않아도 된다.** cobra 가 파싱한다.
3. 단순성 사다리에서 2단(이미 있는 패턴 재사용)에 멈춘다.

형태:

```
moai clean --codex-skills            # dry-run: 제거 적격 항목을 열거만
moai clean --codex-skills --force    # 백업 후 실제 제거
```

`--home` 과 `--codex-skills` 를 동시에 준 경우는 사용법 오류로 거절한다 — 스코프는 하나다.

### 후보 (a) — `moai codex` 동사 확장 [기각]

`internal/cli/codex_launcher.go` 를 읽고 기각했다. 두 가지가 걸린다.

- `codexCmd` 는 `DisableFlagParsing: true` 다. 플래그가 전부 손으로 파싱된다(`stripSpawnFlag`, `stripCodexWorktreeFlag`, `splitCodexDashDash`). `--force` 를 붙이려면 파괴적 플래그의 파싱을 손으로 짜야 하고, 그것은 이 카드에서 가장 비싼 실수를 가장 검증이 얇은 곳에 놓는 일이다.
- 그 파일의 머리주석이 **"The launcher never writes: no directory is created, no file mutated (REQ-CL-013)"** 라고 못박고 있다. 여기에 쓰기 동사를 넣는 것은 착지한 요구사항을 뒤집는 일이며, 그러려면 이 카드가 아니라 `SPEC-CODEX-LAUNCHER-001` 의 개정이 먼저다.

### 후보 (b) — `moai doctor` 수리 경로 [기각]

브리프가 상정한 것보다 이 후보는 **더 약하다.** `internal/cli/doctor.go:58` 에 `--fix` 플래그가 있기는 한데 도움말이 `"Suggest fixes for detected issues"` 이고, 실제로 수리를 실행하는 경로는 doctor 계열 어디에도 없다. 즉 이 후보는 "기존 수리 표면에 한 줄 얹기"가 아니라 **doctor 에 없던 실행 표면을 새로 만드는 일**이다. 게다가 `doctor_codex.go` 머리주석의 "The check READS only ... never touches the user-layer ~/.codex/config.toml" 을 정면으로 뒤집는다. 진단이 스스로 고치기 시작하면 `moai doctor` 를 무해한 조회로 부를 수 없게 된다.

## §B 결정 2 — 지울 줄의 범위를 무엇이 알려주는가

**이것이 브리프와 실제 소스가 어긋나는 지점이다.**

브리프는 "선언된 줄 범위를 정확히 제거하라"고 지시한다. 그런데 `ParseSkillEntries` 가 돌려주는 `SkillEntry` 는 `Path` 와 `Enabled` **두 필드뿐이고 줄 번호를 담지 않는다.** 파서만 재사용해서는 어느 줄을 지울지 알 수 없다.

선택지 둘:

- **B-1 [채택] `SkillEntry` 에 줄 범위를 더한다.** `StartLine` / `EndLine`(0-기반 반열림 구간)을 추가한다. 필드 추가는 여전히 읽기다: REQ-CGP-016 은 파서가 **쓰지 않을 것**을 요구하지 도구가 되지 말라고 요구하지 않는다.
- **B-2 [기각] 프루너가 자체 줄 스캔을 한다.** 파서와 같은 헤더/테이블/여러 줄 리터럴 규칙을 두 번째로 구현하게 된다. 두 구현이 갈리는 순간 프루너는 파서가 항목으로 보지 않는 줄을 지운다. REQ-CGP-001 이 분류기에 대해 금지한 것과 정확히 같은 실수를 파싱 축에서 저지르는 셈이다.

### §B.1 정정 — 파서는 extent 를 갖고 있지 않다

이 계획서의 v0.1.0 은 파서가 "헤더에서 열어 다음 테이블 헤더에서 닫는 extent 개념을 이미 갖고 있다"고 적었다. **그 문장은 사실이 아니었고, plan-audit iter-1 의 D2 가 이를 적발했다.** 원문을 지우지 않고 여기에 정정을 붙인다.

`internal/codexwiring/skills.go:106-143` 이 실제로 들고 있는 것은 **닫힘 사건 하나**다 — `skills.go:131` 에서 `inEntry` 가 false 로 토글되는 것뿐이고, 줄 인덱스를 기록하지 않으며 어느 줄이 항목에 속하는지 관측하지 않는다. "기록만 하면 된다"가 아니라 **없는 것을 새로 만드는 일**이다.

따라서 B-1 의 실제 의무:

1. **범위는 헤더 줄부터 닫힘 시점까지의 모든 줄을 포함한다** — `openDelim` 분기(`skills.go:113-125`)가 삼킨 줄도 포함한다. 그 분기는 switch 를 통째로 건너뛰므로, "마지막으로 매치된 키 줄"을 끝으로 삼으면 여러 줄 리터럴이 잘리고 닫는 `"""` 가 고아로 남는다.
2. **EOF 는 닫힘이다.** 파서는 `inEntry` 가 true 인 채로 루프를 빠져나온다(`skills.go:141`). 파일 끝의 항목은 그래서 안전하지만, 범위 계산이 EOF 를 명시적으로 닫힘으로 다루어야 그렇다.
3. **꼬리 빈 줄은 범위에서 제외한다.** 빈 줄을 삼키면 항목 사이 간격이 조용히 달라져 REQ-CGP-015 를 어긴다. 제거 후 연속 빈 줄이 남는 것은 허용한다 — 아무것도 잃지 않는 쪽이 예쁘게 만드는 쪽보다 낫다.

### §B.2 범위 안의 내용물 — 완벽한 범위를 노리지 않는다

D2 가 든 세 위험(항목 안의 여러 줄 리터럴, `path`/`enabled` 아닌 키, `anyTableRe` 가 `["x", "y"]` 를 테이블 헤더로 오독하는 것)은 **범위 계산을 더 정교하게 만들어서 풀지 않는다.** 임의의 손편집 TOML 위에서 범위를 완벽히 맞히려는 시도는 이 카드가 감당할 수 없고, 한 줄 어긋나면 사용자가 쓴 줄을 지운다.

대신 **REQ-CGP-018** 로 문제를 뒤집었다: 범위 안에 인식되지 않는 줄이 하나라도 있으면 그 항목은 적격에서 탈락한다. 인식되는 줄은 헤더 / `path` / `enabled` / 빈 줄 / 온전한 주석 줄, 다섯 종류뿐이다.

이 규칙이 세 위험을 한꺼번에 닫는다:

- ~~여러 줄 리터럴의 어느 줄도 다섯 종류에 들지 않으므로 → 탈락, 지우지 않음.~~ **이 문장은 거짓이다 — plan-audit iter-2 E2.** 원문을 남기고 정정을 붙인다: 리터럴에 삼켜진 줄은 얼마든지 다섯 종류처럼 **생길 수 있다.** 실제로 `"""` 를 홀수 번 담은 주석 줄이 리터럴을 열고, 그 리터럴이 뒤의 `[[skills.config]]` 헤더와 `path` 줄을 삼키면, 그 범위를 텍스트로 훑을 때 보이는 것은 헤더·`path`·주석 — 전부 "다섯 종류"다. 텍스트 판정으로는 탈락하지 않고, 지우면 삼켜진 멀쩡한 등록이 함께 사라진다. → **판정식을 파서 상태로 옮긴다**(아래 §B.3).
- 다른 키의 대입도 다섯 종류에 들지 않으므로 → 탈락. 앞 테이블로의 재귀속이 원천적으로 일어나지 않는다.
- `["x", "y"]` 이어쓰기 줄은 범위를 일찍 닫는데, 그러면 그 줄은 범위 **밖**이 되어 남는다. 하지만 그 항목은 이미 다섯 종류 아닌 줄(배열을 시작한 키 대입)을 범위 안에 갖고 있으므로 탈락한다.

주석 줄을 인식 목록에 넣은 것은 결정이다 — 항목에 달린 주석은 그 항목과 함께 사라지는 것이 사용자의 기대에 가깝다. 대신 **줄 전체가 주석인 경우만** 인식하며, 키 뒤에 붙은 꼬리 주석은 키 줄의 일부다.

탈락은 실패가 아니라 보고 항목이다. 세지 않고 조용히 넘기면 사용자는 유령이 남았다는 사실을 모른다.

### §B.3 판정식은 파서 상태다 — 겉모양이 아니다

§B.2 의 "다섯 종류" 목록은 **의도는 맞고 판정식이 틀렸다.** 다섯 종류를 나열하면 구현자는 자연히 범위의 텍스트를 다시 훑게 되고, 텍스트 재훑기는 구멍을 닫지 못한다.

실행으로 확인한 반례(2026-09-07, 이 트리 `ace1c5440`, `ParseSkillEntries` 직접 호출):

```toml
[[skills.config]]        # L0
path = "/gone"           # L1
# uses """ in prose      # L2  ← multilineOpener 가 여기서 리터럴을 연다
[[skills.config]]        # L3  ← 삼켜짐
path = "/exists"         # L4  ← 삼켜짐
# and """ again          # L5  ← 리터럴이 닫힌다
[other]                  # L6
```

결과는 `ENTRIES=1`, `path="/gone"`. `/exists` 는 파서에 **보이지 않는다.** 그 유령의 범위는 L0..L5 이고, 그 안에 멀쩡한 등록이 들어 있다. 텍스트로 훑으면 헤더·`path`·주석뿐이라 탈락하지 않는다. 헤더 없는 좁은 변형(삼켜진 구간이 맨 `path` 줄만 담은 것)도 `ENTRIES=1` 로 같았다 — **"범위당 헤더 하나" 제한은 이 구멍을 막지 못한다.**

원인은 `multilineOpener`(`skills.go:83-90`)가 주석을 벗기지 않고 줄 전체에서 `"""` 를 센다는 것이다. 그래서 주석 한 줄이 리터럴을 연다.

~~**결정: 파서가 각 항목에 대해 "이 범위 안에 `openDelim` 분기(`skills.go:113-121`)가 소비한 줄이 있었는가"를 boolean 으로 보고한다.** 프루너는 그 플래그를 읽을 뿐 범위의 텍스트를 다시 해석하지 않는다. 사실을 아는 유일한 주체가 파서이므로, 추론하게 두지 않고 보고하게 만든다.~~

**이 결정은 두 군데가 틀렸다 — plan-audit iter-3 F2.** 원문을 남기고 정정한다.

**틀린 곳 1 — 운반체가 좁다.** boolean 하나는 위험 (a)와 (d)만 답한다. (b) 미지의 키와 (c) `anyTableRe` 과다매치에 대해서는 그 플래그가 `false` 로 읽히고, 범위는 "깨끗하다"고 판정되어 항목이 **삭제된다** — (b)의 미지 키가 앞 테이블로 재귀속되는 바로 그 손실이다. 동시에 같은 문장이 프루너의 텍스트 재해석을 금지하므로, 이 계획서를 문자 그대로 따르는 구현자는 **REQ-CGP-018 을 만족시킬 방법이 없다.**

**틀린 곳 2 — "파서만이 그 사실을 안다"는 (b)·(c)에 대해 거짓이다.** `skills.go:133-138` 을 보면 `case inEntry:` 아래에 `path` / `enabled` 두 정규식 분기뿐이고 else 가 없다 — **빈 줄, 온전한 주석 줄, 미지의 키가 전부 같은 무동작 경로로 떨어진다.** 지금의 파서는 그 셋을 구분하지 못한다. 즉 이것은 파서가 이미 쥐고 있는 사실을 보고만 하면 되는 문제가 아니라, **파서가 새로 계산해야 하는 판정**이다.

**정정된 결정: 파서는 항목마다 다섯 갈래 전부 + 삼킴 분기를 포괄하는 판정을 계산해 보고한다. 운반체는 boolean 이 아니라 `FirstUnrecognizedLine int` — 범위 안에서 처음으로 인식되지 않은 줄의 인덱스이며, 전부 인식되었으면 `-1`.**

인덱스를 고른 이유는 REQ-CGP-018 이 이미 "인식되지 않는 줄이 있어 건너뜀"이라는 **보고 의무**를 지고 있기 때문이다. boolean 은 건너뛰었다는 사실만 전하고, 인덱스는 **어느 줄 때문인지**를 전해 사용자가 손으로 판단할 수 있게 한다. 같은 값 하나가 판정과 보고를 동시에 만족시키므로 추가 비용이 없다.

계산 위치는 파서다. 프루너로 옮기면 다섯 갈래 분류가 두 번째 구현이 되고, 그것이 §B.2 가 기각한 B-2 다.

### §B.4 같은 실수의 세 번째 판본 — 다음 사람에게

iteration 1 D2, iteration 2 E2, iteration 3 F2 는 **한 실수의 세 판본**이다. 매번 모양이 달라서 새로운 문제처럼 보였지만 공통 구조는 하나다:

> **판정을 내리는 자리에, 그 판정을 내릴 사실이 아직 없다.**

- **D2** — 범위를 "파서가 이미 가진 extent"로 계산하려 했다. 파서에는 extent 가 없었다(닫힘 **사건**만 있었다).
- **E2** — 인식을 "줄의 겉모양"으로 판정하려 했다. 겉모양은 삼켜진 줄을 구분하지 못했다.
- **F2** — 인식을 "삼킴 boolean"으로 판정하려 했다. boolean 은 (b)·(c)를 구분하지 못했고, "파서만 안다"는 전제 자체가 그 둘에 대해 거짓이었다.

세 번 모두 **텍스트나 가정에 대해 규칙을 쓰고, 실제로 판정하는 사실은 누군가 새로 계산해야 하는 것**이었다.

[HARD] 네 번째가 나오면 새로운 문제로 취급하지 말고 이 가족의 일원으로 인식한다. 판별 질문 하나로 족하다 — **"이 규칙이 참조하는 사실을, 지금 이 코드가 실제로 계산하고 있는가?"** 답이 "아니오"이거나 "아마도"이면, 규칙을 다듬을 것이 아니라 그 사실을 계산하는 자리를 먼저 정해야 한다.

## §C 결정 3 — 제거를 어떻게 수행하는가

줄 범위 집합을 모아 **한 번에** 원본 줄 배열에서 걸러낸다. 각 항목마다 파일을 다시 읽고 쓰지 않는다 — 중간 상태가 관측되면 줄 번호가 어긋난다.

### §C.1 `splitLines` 는 줄 끝 상태를 잃는다 — 확인 대상이 아니라 이미 아는 사실

v0.1.0 은 이것을 "먼저 픽스처로 확인한다"며 미뤘다. 미룰 일이 아니다. 소스를 읽으면 지금 답이 나온다(`internal/codexwiring/configtoml.go:204-209`):

```go
func splitLines(body string) []string {
	if body == "" {
		return nil
	}
	lines := strings.Split(strings.TrimSuffix(body, "\n"), "\n")
	return lines
}
```

`TrimSuffix(body, "\n")` 때문에 `"a\n"` 과 `"a"` 가 **똑같은** 슬라이스 `["a"]` 를 낸다. 어떤 재조립 규칙을 고르든 두 상태 중 하나는 바이트가 틀리게 나온다. CRLF 도 같은 자리에서 마지막 `\r\n` 이 `\r` 로 깎인다.

**결정: 재조립기는 `splitLines` 의 출력만으로 만들 수 없다.** 원본에서 두 값을 따로 떠서 운반한다 — (a) 마지막 줄 뒤에 개행이 있었는지, (b) 줄 구분자가 `\n` 인지 `\r\n` 인지. 이것이 REQ-CGP-019 다.

재조립 무손실성은 §D 의 M1 에서 **단위 함수 수준**으로 검증한다(AC-CGP-013). 항목이 0건인 설정을 end-to-end 로 돌려서 확인하는 방식은 쓰지 않는다 — REQ-CGP-017 이 그 경우 아무것도 쓰지 않을 것을 요구하므로, 파일이 그대로인 이유가 "재조립이 무손실이어서"가 아니라 "재조립이 아예 돌지 않아서"가 되고, 그 통과는 아무것도 주장하지 않는다. (plan-audit iter-1 D1.)

### §F.1 stat 씨앗은 재사용이 아니라 신규 작업이다

run 단계에서 발견하지 않도록 여기에 못박는다. `internal/cli/doctor_codex.go:426` 은 `_, serr := os.Stat(statPath)` 로 **표준 라이브러리를 직접** 부른다. 주입 지점이 없다. 다른 이름의 stat 씨앗이 `internal/cli` 어딘가에 이미 있는지는 plan 단계에서 확인하지 않았으므로(plan-audit 의 Gaps 도 같은 것을 미검증으로 남겼다), M2 의 첫 작업은 **그 확인**이고, 없으면 프루너가 자기 씨앗을 만든다.

그래서 이 축의 비용은 "이미 있는 씨앗을 쓴다"가 아니라 "씨앗을 만든다"다. 이것을 재사용으로 잘못 견적내면 M4 가 통째로 밀린다.

**skip 은 실패다.** indeterminate 픽스처를 플랫폼 조건으로 건너뛰면 AC-CGP-003 의 4번 부류가 발화하지 않고, 발화하지 않은 부류는 뮤턴트가 뒤집을 대상이 없으므로 must-pass 인 AC-CGP-004 가 **달성 불가**가 된다. 그 상태는 "기록된 미검증 간극"이 아니라 **AC-CGP-004 의 FAIL** 이다. 계획서가 선택지로 제시해선 안 되는 것을 v0.1.0 이 선택지로 제시했고(plan-audit iter-1 D5), 그 줄은 위 §F 표에서 제거했다.
