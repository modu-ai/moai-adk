# SPEC-APPJS-IIFE-GUARD-001 — 구현 계획

> 절 순서는 **되돌리기 비용이 큰 결정부터**다. 위에서부터 읽으면 검토가 필요한 판단이 먼저 나오고, 아래로 갈수록 기계적인 작업이 된다.

---

## §A 결정 1 — 규칙을 순수 함수로 뽑는다 (가장 되돌리기 비싼 결정)

**문제:** AC 가 2방향을 요구한다. 정방향(실제 app.js 는 통과)은 쉽다. **역방향(돌연변이는 실패)** 이 설계를 정한다 — Go 테스트가 "이 규칙이 결함을 거부한다"를 어떻게 스스로 보이는가?

**채택:** 규칙을 **문자열을 받아 위반 목록과 검사 대수를 돌려주는 순수 함수**로 구현한다.

```
// 형태만 제시 — 이름과 정확한 시그니처는 run-phase 소관
scanBareHandlerScope(src string) (violations []…, checked int)
```

그러면 두 테스트가 같은 함수를 서로 다른 입력으로 부른다.

- 정방향: `readEmbeddedAsset(t, "app.js")` 를 넣고 `len(violations) == 0 && checked > 0` 을 단언
- 역방향: **같은 소스를 메모리에서 변형한 문자열**을 넣고 위반 1건이 `stampRefreshed` 와 그 줄 번호를 지목함을 단언

**기각한 대안:** 테스트가 디스크의 `app.js` 를 실제로 고쳤다가 되돌리는 방식. 임베드된 사본을 읽으므로 애초에 반영되지 않고(REQ-AIG-006), 테스트가 작업 트리를 쓰는 것 자체가 §6 격리 규율 위반이며, 실패 시 파일을 더럽힌 채 끝난다. **어떤 경우에도 디스크의 app.js 를 쓰지 않는다** (REQ-AIG-010).

**왜 이것이 가장 비싼 결정인가:** 순수 함수로 뽑지 않으면 역방향 AC 를 만족시킬 길이 사실상 없고, 나중에 구조를 바꾸려면 테스트 전체를 다시 쓰게 된다.

## §B 결정 2 — 돌연변이를 테스트 안에서 만드는 방법

역방향 입력은 **테스트가 런타임에 합성**한다. 골든 파일로 돌연변이 사본을 커밋하지 않는다 — 사본은 원본이 움직이면 즉시 스테일해지고, 그 스테일을 아무도 알려 주지 않는다.

합성 절차(프로토타입에서 실측한 그대로):

1. 임베드된 `app.js` 를 줄 단위로 나눈다
2. `stampRefreshed` 를 bare identifier 핸들러로 넘기는 등록 줄을 **찾아서** 지운다 (줄 번호 727 을 상수로 박지 않는다 — §A 와 같은 이유)
3. 그 줄을 첫째 IIFE 안(예: `initConsole` 의 `htmx:afterSettle` 등록 바로 뒤)에 끼워 넣는다
4. 다시 합쳐서 `scanBareHandlerScope` 에 넘긴다

**전제 단언을 먼저 건다:** 2단계에서 대상 줄을 못 찾으면 돌연변이가 만들어지지 않은 채 "위반 0" 이 나오고, 테스트는 조용히 **공허하게 통과**한다. 그러므로 대상 줄을 찾지 못하면 `t.Fatal` 로 즉시 죽인다.

## §C 결정 3 — 파일 배치: 신규 파일

**채택:** `internal/web/appjs_iife_scope_test.go` (신규).

**`appjs_reinit_test.go` 를 확장하지 않는 이유 셋:**

1. **성질이 다르다.** 기존 파일은 "initConsole 이 두 이벤트에 **바인딩되어 있는가**"를 지킨다. 새 규칙은 "등록이 **어느 스코프에** 있는가"를 지킨다. 한쪽이 실패해도 다른 쪽은 무관하다.
2. **부피가 맞지 않는다.** 기존 파일은 ~50줄이고 `strings.Contains` 세 줄이 본체다. 새 가드는 스팬 스캐너·선언 탐색·돌연변이 합성까지 100줄 안팎을 데려온다. 합치면 기존 계약이 보조 코드에 묻힌다.
3. **실패 메시지의 출처가 모호해진다.** 파일이 분리돼 있으면 `go test -run` 으로 한쪽만 겨눌 수 있고, CI 로그에서 어느 계약이 깨졌는지가 파일 이름만으로 갈린다.

기존 파일은 **한 줄도 건드리지 않는다** (REQ-AIG-009).

## §D 결정 4 — 규칙의 판별식 세 조각

세 조각 모두 프로토타입에서 실측으로 확인됐다(spec.md §B.4).

| 조각 | 판별식 | 근거 |
|---|---|---|
| IIFE 스팬 | 컬럼 0 의 `(function` 로 열고, 컬럼 0 의 `})();` 로 닫는다 | spec.md §B.1 — 파일에 이 형태가 정확히 둘 |
| bare handler 등록 | `\.addEventListener\(\s*"[^"]*"\s*,\s*([A-Za-z_$][A-Za-z0-9_$]*)\s*\)` | 함수 표현식은 `(` 로 시작하므로 이 패턴에 걸리지 않는다 → REQ-AIG-005 가 정규식으로 충족된다 |
| 선언 위치 | `\b(?:function\|var\|let\|const)\s+<name>\b` 가 어느 스팬 안에서 매치되는가 | spec.md §B.3 의 세 선언을 전부 정확히 찾음 |

**스팬 밖의 등록은 건너뛴다.** 두 IIFE 어느 쪽에도 속하지 않는 줄(현재는 없음)은 판정 대상에서 제외하고, 그 사실이 `checked` 에 반영되지 않게 한다.
