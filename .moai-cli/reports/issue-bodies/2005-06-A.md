# [RC1][실행 소유권과 통합] 06-A 단일 리더와 Issue claim 계약 구현

> **P08 결정(2026-11-08 16:4x)**: RC1 기본 claim 방식은 **⑤ GitHub Issue 댓글 claim(주)** + **① 리더 로컬 journal/OS lock(보조)**. 아래 REQ·AC는 그 결정 기준으로 다시 썼다. 남은 HOLD는 lease 길이·heartbeat 수치만.

## 목표와 사용자 가치
`moai-cli`에 단일 writer가 쓰는 작은 durable claim journal을 구현해, 한 Issue(task)에 유효한 owner가 최대 1명만 존재하고, 각 attempt가 단조 증가 epoch·base revision·worktree identity·write scope·승인 snapshot digest를 함께 고정하며, 같은 Issue에 대한 두 번째 claim은 기존 owner·상태를 돌려받고 거부되게 한다. 세션은 이 journal을 거치지 않고 Issue를 임의 claim하지 않는다. GitHub assignee는 리더가 add API로 표시만 한다. 사용자 가치: 중복 구현·stale 결과 수용을 로컬에서 구조적으로 차단하고, 리더·세션·독립 reviewer·통합 owner가 같은 식별자(task_id·attempt·epoch)로 대화할 수 있게 된다.

## 비목표와 범위
비목표: 여러 컴퓨터 사이의 원자적 CAS(설계 §8 '로컬 파일의 rename·lock은 여러 컴퓨터 전체의 CAS가 아니다'), lease 만료에 따른 자동 reclaim/takeover(P08 결정됨(⑤+①, lease 수치만 HOLD)), heartbeat 주기·만료 수치 확정(P11 HOLD), GitHub Issue 본문·label 변경, SQLite backend, 원격 Git ref·Actions concurrency 기반 claim(P08 선택지로만 기록). 범위: 신규 `src/claim.rs`(명칭 제안), `src/main.rs` 하위 명령 추가, `tests/` fixture, `docs/rust-product-path.md` 계약 절, `skills/moai/workflows/run.md` preflight 1단계 문구. 상태 위치는 `<project>/.moai-cli/` 또는 `~/.moai-cli/`(HOLD 참조)만 사용.

## SPEC 요구(GEARS)
- REQ-06A-01 [Ubiquitous] 시스템은 claim record에 `schema_version`, `task_ref`(provider, host, repository_id, issue_id, issue_number), `logical_key`, `owner`{kind, id, host_id}, `attempt`, `epoch`, `base_revision`, `worktree`{common_dir, git_dir, path, head}, `write_scope[]`, `spec_ref`{id, revision, digest}, `state`, `effects[]`, `last_observed_at`를 기록해야 한다.
- REQ-06A-02 [Ubiquitous] 시스템은 같은 `task_ref`에 대해 `state ∈ {assigned, running, verifying, pr_ready, in_review, blocked, handoff_pending, uncertain}`인 record를 동시에 2개 이상 두지 않아야 한다.
- REQ-06A-03 WHEN 세션이 claim을 요청하면, 시스템은 journal의 exclusive lock(`File::try_lock`)을 획득한 뒤 기존 유효 owner를 검사하고, 없을 때만 `epoch = max(epoch)+1`로 새 record를 추가하며, 있을 때는 기존 owner·state·epoch를 반환하고 record를 변경하지 않아야 한다.
- REQ-06A-04 WHEN journal 쓰기가 일어나면, 시스템은 임시 파일에 전체 내용을 쓰고 fsync 후 rename으로 교체하거나 append 뒤 fsync하여, 중단 시 이전 내용 또는 새 내용 중 하나만 관찰되게 해야 한다.
- REQ-06A-05 WHEN lock 획득이 `WouldBlock`이면, 시스템은 대기하지 않고 `busy` 결과를 반환해야 한다(기다림·재시도 정책은 호출자 몫).
- REQ-06A-06 IF 같은 호스트의 두 프로세스가 동시에 같은 `task_ref`를 claim하면, THEN 정확히 하나만 `claimed`를 받고 다른 하나는 `already_owned`(기존 owner·epoch 포함)를 받아야 한다.
- REQ-06A-07 WHERE journal 경로가 네트워크 파일시스템이거나 심볼릭 링크를 거치면, 시스템은 경고를 기록하고 원자성을 보장한다고 보고하지 않아야 한다(심볼릭 링크 journal 경로는 거부).
- REQ-06A-08 [Ubiquitous] 시스템은 claim 결과를 GitHub assignee·label·댓글에 쓰지 않아야 하며, 표시(projection)는 리더가 별도 명령으로 요청할 때만 `add` 의미의 API로 수행해야 한다(이 Issue 범위에서는 호출 안 함, 의도만 record의 `effects[]`에 적는다).
- REQ-06A-09 [Ubiquitous] 시스템은 `.moai/`, `~/.moai/`, `.claude/` 아래에 어떤 파일도 만들거나 읽어 판단에 쓰지 않아야 한다.
- REQ-06A-10 WHEN 같은 입력으로 claim 조회(`show`)를 반복하면, 시스템은 바이트 동일한 출력을 내고 journal을 변경하지 않아야 한다.
- REQ-06A-11 [Ubiquitous] 시스템은 출력 JSON에 `coordination_scope: "single-host"`와 `cross_host_atomic: false`를 명시해 호출자가 범위를 오해하지 않게 해야 한다.

## claim
