# [RC1][실행 소유권과 통합] 06-B 중단 재조회와 명시 handoff 검증

## 목표와 사용자 가치
06-A의 claim record를 입력으로, 세션 중단(crash·터미널 종료·host 무응답) 뒤에 (1) 이전 owner의 실제 상태를 로컬 PID 한계 안에서만 조회하고, (2) 결과 불명 외부 효과(PR·댓글·Issue 변경)를 operation ID와 원격 GET으로 reconcile하며, (3) 이전 worktree의 미커밋 변경을 보존한 채, (4) 리더의 명시 handoff로만 새 epoch의 attempt를 만들고 옛 epoch의 publish 의도를 거부(fencing)하는 절차를 `moai-cli`에 구현·검증한다. 사용자 가치: 중단이 중복 PR·댓글이나 미커밋 작업 손실로 이어지지 않고, 인계가 '추정'이 아니라 기록된 증거 위에서 일어난다.

## 비목표와 범위
비목표: 무응답·timeout·heartbeat 만료만으로 이전 writer 종료를 판정하는 자동 takeover(P08 HOLD), 원격/cloud task의 종료를 로컬 PID로 추정(설계 §8 '다른 host나 cloud task의 종료 증거로 확대하지 않는다'), `git stash`/`reset`/`clean`으로 dirty 변경 정리(branch guard·사용자 변경 보존 원칙), GitHub 쓰기(댓글·PR 생성은 07-C·06-C), SQLite. 범위: `src/claim.rs` 확장 또는 `src/handoff.rs`(제안), `claim-handoff`·`effects-reconcile` 하위 명령, fixture, 문서.

## SPEC 요구(GEARS)
- REQ-06B-01 WHEN 리더가 `claim-handoff`를 요청하면, 시스템은 대상 record의 현재 epoch·owner·state를 읽고, `from_epoch`가 현재 epoch와 다르면 `stale_request`로 거부해야 한다.
- REQ-06B-02 WHILE 이전 owner의 `owner.kind == local-process`이고 같은 host_id이면, 시스템은 기록된 pid·process_start 식별자로 생존 여부를 조회하고 결과를 `alive|dead|indeterminate`로 기록해야 한다; 다른 host_id나 `owner.kind ∈ {remote-task, ci}`이면 로컬 조회를 하지 않고 `not_applicable`로 기록해야 한다.
- REQ-06B-03 IF 생존 조회 결과가 `alive` 또는 `indeterminate`이면, THEN 시스템은 `--force-explicit` 같은 리더의 명시 플래그와 사유 문자열 없이는 handoff를 거부하고 `handoff_pending`으로 표시해야 한다(무응답 자동 takeover 금지).
- REQ-06B-04 WHEN handoff가 진행되면, 시스템은 이전 worktree 경로에서 `git status --porcelain=v2 -z`·`git rev-parse HEAD`·`git stash list` 출력을 record에 보존 증거로 저장하고, 어떤 `git reset|checkout --|stash|clean|worktree remove`도 실행하지 않아야 한다.
- REQ-06B-05 WHEN handoff가 승인되면, 시스템은 `epoch+1`의 새 record를 쓰고 이전 record를 `handed_off{to_epoch, reason, evidence}`로 종결하며, 이전 worktree는 `git worktree lock --reason "handoff from epoch N"` 의도를 effects에 기록(실행은 호출자 승인 범위)해야 한다.
- REQ-06B-06 [Ubiquitous] 시스템은 외부 쓰기 전 `effects[]`에 `{operation_id, kind, intent_digest, state: intended}`를 기록하고, 응답 후 `{response_id, observed_state, state: confirmed}`로 갱신하며, 둘 사이에서 중단된 효과는 `uncertain`으로 남겨야 한다.
- REQ-06B-07 WHEN `effects-reconcile`이 실행되면, 시스템은 `uncertain` 효과마다 stable marker(operation_id를 포함한 본문 marker 또는 head branch 이름)로 원격을 GET 조회하고, 발견되면 `confirmed`+원격 ID, 미발견이 확인되면 `not_performed`로 바꾸되 같은 효과를 자동 재생성하지 않아야 한다.
- REQ-06B-08 IF publish 의도 등록 요청의 epoch가 record의 현재 epoch보다 작으면, THEN 시스템은 `stale_epoch`로 거부하고 요청 내용을 `stale_results[]`에 진단 자료로만 보관해야 한다.
- REQ-06B-09 WHERE 원격 조회가 rate limit(403/429, retry-after)로 실패하면, 시스템은 retry-after 이후에만 재시도하고 그 전까지 효과 상태를 바꾸지 않아야 한다.
- REQ-06B-10 [Ubiquitous] 시스템은 handoff·reconcile 결과를 `passed|failed|not_run|blocked|uncertain`으로 구분해 출력하고, 조회하지 않은 항목을 성공으로 표기하지 않아야 한다.

## 구현 계획
1. 1. PLAN: 06-A record schema 위에 `effects[]`·`stale_results[]`·`liveness` 필드와 handoff 상태전이(assigned/running → handoff_pending → handed_off; uncertain → reconciling → confirmed/not_performed/blocked)를 GEARS로 고정. P08 HOLD 결과(명시 플래그 요구 여부) 반영.
2. 2. liveness 조회 모듈: 같은 host_id·local-process에 한해 pid+process_start(또는 boot_id)로 조회. 구현 수단은 HOLD(아래) — std만으로는 이식적 PID 조회가 없음.
3. 3. `effects` API: `effect-intend`(operation_id 발급, 의도 digest 기록), `effect-confirm`(response_id·observed_state), `effects-reconcile PROJECT --task <ref> [--remote-probe <cmd>]` — 원격 조회는 fixture에서 가짜 probe 명령으로 대체, 실제는 `gh api` GET(읽기)만 사용.
4. 4. `claim-handoff PROJECT --task <ref> --from-epoch N --reason <text> [--force-explicit]`: REQ-06B-01~05 순서로 검사·기록; git 명령은 읽기 전용(`status`, `rev-parse`, `stash list`)만 호출하고 변경 명령은 effects에 의도로만 적는다.
5. 5. fixture: 임시 git repo+worktree 생성(`git init`, `git worktree add`), dirty 3종 주입, 가짜 프로세스(`sleep`) pid로 alive/dead 케이스, intended-only 효과 주입 후 reconcile(가짜 probe가 200/404/429+retry-after 응답).
6. 6. 문서: `docs/rust-product-path.md` 'Handoff and reconcile' 절(단일 host 한계·PID 범위·exactly-once 비주장), `skills/moai/workflows/sync.md` 5단계와 연결.
7. 7. 로컬 검증 전부 실행·기록 → 독립 AUDIT → PR(`Refs #2006`, base v2026.11.0).
