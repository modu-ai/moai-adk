# [RC1][Rust 실행과 저장] 01-B 파일 적용과 rollback receipt 구현

> **HOLD 전제 주의** — 4단계 임시 receipts 경로(<project>/.moai-cli/receipts/)는 P09 HOLD → 결정 전 보류.

## 목표와 사용자 가치
관리 파일을 적용할 때 (1) baseline(마지막으로 MoAI가 쓴 내용)/current(지금 파일)/new(렌더링) 3-way 비교와 expected hash 재확인으로 사용자 수정을 절대 덮지 않고, (2) 같은 filesystem의 임시 파일 + fsync + rename(또는 exclusive create) + 디렉터리 fsync로 파일 단위 원자성·내구성을 확보하며, (3) 파일마다 before/after hash·결정·결과를 담은 per-file receipt를 남겨 중간 실패 시 '이번 요청이 바꾼 관리 변경만' 되돌릴 수 있게 한다. 현재 `agents.rs::write_replace`가 임시파일·sync_all·hard_link/rename·디렉터리 sync까지는 하지만 receipt가 없고(partial apply는 stderr만), hard link 없는 FS 미검증, exit code 0/1뿐이다. 이 Issue가 03-A/03-C(맞춤 생성)·04-B/04-C(UPDATE와 부분 실패 복구)의 공통 적용 엔진이 된다.

## 비목표와 범위
비목표: 여러 파일 전체의 트랜잭션 원자성 주장, 임의 텍스트의 자동 3-way 병합(충돌 자동 해결), SQLite journal, 다중 host lock, 대형 artifact 저장소(P09), 원격 publish/reconcile(ST-03 remote 부분), Go 세대 파일 변경. 범위: `src/` 적용 엔진(가칭 `apply.rs`)과 receipt 타입, `agents_apply`/`apply`의 엔진 공용화, receipt 저장 경로(HOLD-B1 결정 후), 복구 명령(가칭 `apply-recover --receipt <id>`) 1개, fixture.

## SPEC 요구(GEARS)
- REQ-01B-01 (Ubiquitous) 시스템은 파일마다 baseline_sha256(마지막 MoAI 기록)·expected_sha256(plan 시점 current)·rendered_sha256(new)을 비교해 `create|append|merge|unchanged|conflict` 중 하나로 결정해야 하며, current가 baseline과 다르고 템플릿이 바뀐 경우는 `conflict`로 두고 어떤 바이트도 쓰지 않아야 한다.
- REQ-01B-02 (WHEN) apply 직전 대상 파일의 실제 sha256이 plan의 expected_sha256과 다를 때, 시스템은 해당 파일과 이후 파일을 적용하지 않고 `stale_target`을 receipt에 기록해야 한다.
- REQ-01B-03 (Ubiquitous) 기존 파일 교체는 '대상과 같은 디렉터리의 고유 임시 파일 생성(create_new) → write → sync_all → rename → 부모 디렉터리 sync_all' 순서를 따라야 하며 임시 파일은 실패 시 제거해야 한다.
- REQ-01B-04 (WHEN) 대상이 없는 신규 생성일 때, 시스템은 exclusive 의미(현재 hard_link 또는 HOLD-B2로 결정된 primitive)로 publish해야 하며, 그 사이 대상이 생기면 `exclusive_create_refused`로 실패하고 임시 파일을 제거해야 한다.
- REQ-01B-05 (WHERE) 임시 파일과 대상이 다른 filesystem/mount에 있을 때(EXDEV 등), 시스템은 copy+delete로 대체하지 않고 실패를 보고해야 한다.
- REQ-01B-06 (Ubiquitous) 각 파일 적용 결과는 receipt 항목(path, decision, before_sha256, after_sha256, published:bool, error?)으로 기록되어야 하고, receipt는 대상 파일 publish 뒤에 append되어야 하며 receipt 자체도 REQ-01B-03 절차로 기록해야 한다.
- REQ-01B-07 (WHEN) 다중 파일 적용이 중간에 실패할 때, 시스템은 이미 publish된 파일을 되돌리지 않고 `partial`과 적용 목록을 반환해야 하며, 전체 성공으로 표시하지 않아야 한다.
- REQ-01B-08 (WHEN) 사용자가 receipt로 복구를 요청할 때, 시스템은 receipt의 after_sha256과 현재 파일 hash가 같은 파일만 before 내용(또는 삭제)으로 되돌리고, 그 사이 변경된 파일은 `user_changed_since_apply`로 건너뛰고 보고해야 한다.
- REQ-01B-09 (Ubiquitous) 시스템은 `.moai/`·`~/.moai/`·Go 설치 경로 아래의 어떤 파일도 receipt 대상·복구 대상으로 삼지 않아야 한다.
- REQ-01B-10 (Ubiquitous) 재실행 시 변경이 없으면 모든 파일이 `unchanged`이고 receipt에 publish 항목이 0개여야 한다(diff 0).
- REQ-01B-11 (WHEN) 적용 중 symlink·reparse point·special file이 대상 또는 부모 경로에 나타날 때, 시스템은 거부하고 이유를 기록해야 한다(기존 target() 규칙 유지).
