# Leader rules

The detail behind the "Leader rules" section of `CLAUDE.md`. The leader is the session the user talks to: it supervises the lanes, relays what a lane cannot post, lands audited heads and keeps the decisions log. The division of work, the autonomy levels `full` and `semi` with the keep-set and the paste-ready `/goal` line are defined once in `docs/design-review/autonomy-modes-spec.md` §2, §5, §6 and §7 (written for the Issue ledger; where it says claim comment or Issue, read the card reservation and the card). Where a rule moved here from the earlier `CLAUDE.md`, `docs/claude-md-rule-provenance.md` names the line it came from.

## What a round reads

Evidence, not status labels:

- The cards: `moai card list`, `moai card next`, `moai card inbox` (the lane notes that wait for the leader) and `moai card show` for the reservation, notes and criteria.
- Many cards, the reservations or single notes: `moai card query` (reads only, one JSON answer). `--card C-n,C-m` gives each card's head, newest verdict, head verdict and open criteria, and `--notes N` adds the headers of its newest notes. `--reservations` lists every reservation that holds a card, one with an ended lease included, with its session and worktree. `--note <id>` gives the whole text of a note. The leader reads the ledger through the `moai card` commands and never opens the ledger file itself.
- `ListAgents`: who is live, busy or idle, and duplicate names.
- Each lane worktree's `git status --short`, and the lane's last reported command and exit code.
- Stage changes come from the ledger and git (reservation, branch, landed head), never from a lane message or an idle notice alone.

Ownership is the card reservation, never a local file or a message. The earlier `assignments.json` cache (`docs/design-review/assignments-schema.md`) is not written by any code today, so a round reads the ledger.

## When a round runs

On every ledger state change (a READY, a verdict, a block, a recovery) and, as a safety net, every 30 minutes (user pick 2026-11-24, recorded in the decisions log; it replaces the earlier 5-minute loop). The user's decision of 2026-11-08 that the leader always keeps checking lane progress stands. The profile's `leader.pr_check_interval_secs` (default 300) belongs to the `moai leader` loop tool and is not changed by this rule. A hand-off message holds the card id, the changed state and the decision needed, nothing else.

## What a round does

1. Reservation mismatch: a lane that writes without a live reservation of its card (`moai card check` does not answer `allowed: true`) is told to stop, and what differed is recorded as a note on that card.
2. Repair: write it as a card note with `assignee-hint: agent-N` addressed to a free lane that is not the author. The hint grants nothing: ownership comes from that lane's own reservation, and one writer per branch holds.
3. Stalled lane: a lane idle without a reason, or busy past its reported step with no report, is asked for its actual last command and exit code; a block is recorded and raised to the user.
4. Refill: keep a next card ready for every lane, in this order: (1) a ready card whose blockers are all closed; (2) a card whose only open blocker is a head already in the leader's landing queue; (3) a line of `docs/later.md` turned into a card, only while the work cap allows it (a line that does not reproduce is deleted); (4) when none exists, tell the waiting lane why (which landing or HOLD it waits on) and which card is reserved for it.
5. Each round and its outcome go into the dispatch journal. A dispatch names the card's write scope, acceptance criteria and expected checks at once; the lane asks only for a path outside the scope. The work cap is the cards in work plus the cards waiting for a check, at most twice the lanes; at the cap the leader opens no card and sends resting lanes to audit and help land.
6. Keep HOLD cards out of ready: a card with a HOLD or an unmet prerequisite is withdrawn with `moai card withdraw` (the reason names the HOLD or the prerequisite), so no lane takes it and gives it back; `card take` refuses a withdrawn card naming that reason.

## What the leader never does

- Invents work outside the ledger and its recorded backlog, splits one card between two writers, creates a new or duplicate writer, or lifts a HOLD to make work. A card that needs a HOLD answered waits for the user while the lane takes another.
- Uses a duplicate session found after a restart: it freezes until the operator assigns it.
- Publishes new cards from a report before the user confirms the report; each such card's body is mirrored with a "사용자 결정" section, and a card that edits a design page takes "sha256 of the corrected copy plus the leader's read-back" as its acceptance. Lanes get only `.md` paths in tracked locations, so a report moves to a tracked path such as `docs/design-review/` before its cards are issued.

## Naming a lane branch

The leader makes the lane worktree and its branch before the lane has picked its SPEC name, and the SPEC-first hook reads the branch name as the SPEC id (`spec/<slug>-<yyyymmdd>` for `SPEC-<yyyymmdd>-<slug>`). So the leader names the branch `spec/<slug>-<yyyymmdd>` after the card's own words, with the date of the day it is made, and tells the lane that name in the dispatch. A lane never renames the branch. When the SPEC the lane writes has another slug or date, the lane adds one line `branch: spec/<slug>-<yyyymmdd>` (the branch it is on, written exactly) to the SPEC's frontmatter, best while the SPEC is still a draft so the approval covers it; the hook reads that SPEC for the branch while its status is `draft` or `approved` (the folder name equal to the `id:`, the line inside the frontmatter's closing `---`, one level under `.moai/specs/`, no link followed; two SPECs naming one branch are refused). It looks for the line only when no reading of the branch name has a SPEC file of its own. A branch with no SPEC and no such line stays refused: code waits for a SPEC (`SPEC-20261124-lane-branch-after-spec`).

## Bundles, clearing and the whole suite

- A landing batch is 2 to 4 audited heads (`moai card land-batch`), one head alone only for a risk or an exception; a head that fails the batch check is dropped and the rest ships. The heads of a release (`release/<40hex>`) are a release bundle, never called a batch.
- Clear after every card: a READY, REPAIRED or MERGE-READY note and a `LANE-DONE` line hand a card back and are never done. The leader reads the ledger and the lane screen and sends `/clear` through `orca terminal send` to the exact existing window only when the ledger shows the lane's card done or released and nothing is open (no card in review, no live reservation, no run of the lane's own, no unsaved change, no prompt on the screen). After `/clear` it confirms the new session is ready, sends the next line once and reads the new reservation back (the ACK); with no ACK it inspects and does not send again. Stages: `skills/moai/references/flows/next-flow.md`.
- Every five landings the leader runs every Rust test on the integration tip once; a run of exactly the same checks on that tip is not repeated, and risk and release evidence stays. A red test stops landings until it is fixed.
- Lease: a card reservation lasts four hours unless `--lease-secs` says otherwise (14400 seconds by default); expiry is displayed only. The holder of an ended reservation that nobody reclaimed or swept keeps it at the same generation with `moai card renew`; `moai card reclaim` takes over a card whose reservation has ended for another session.

## Landing and the release pull request

- Landing a card is `moai card land <card> --head <40hex> --by leader`, after the verdict is on the card (`moai card verdict`, recorded by the auditing session, never by the leader for it). The verdict is written by a session that wrote none of the change; a verdict by the author does not count, and a posted FAIL stops the landing at every tier. A second FAIL of one card is the leader's decision, not a re-audit; landing closes the card.
- A hand merge of another branch into the integration branch is never made: a branch that is not a card head (for example `main` after a release) comes back only through `moai card land-sync <branch> --spec <SPEC-ID> --by leader`, behind its gates: the registered leader session, a branch the profile's `work_flow.sync_sources` lists, an approved SPEC and a full wide check before the one move.
- The primary checkout stands on the integration branch, and the landing brings it along: after the move it runs `git read-tree -m -u` there, and the answer's `worktree_follow` says `followed`, `finished` (a stopped call run again) or `none`, with `kept_changes` counting the tracked changes it left alone. A tracked change of the checkout stops the landing only where it overlaps a path the landing changes (a staged edit, an unstaged edit or a deleted file at that path; the refusal says `N of its M tracked change(s)` and names the paths), because git keeps every other change and brings a file deleted at a changed path back without a word; changes at other paths are someone's own work and stay as they are, so never stash, reset or commit them to clear a refusal. A merge, rebase or other operation in progress, a HEAD that is not the tip, a file no commit tracks at a path the head adds, a sparse checkout, a skip-worktree or assume-unchanged entry, a submodule entry or a second worktree on the branch refuses before the first write with its reason and next step; clear the cause and run the same call again. After the move a failed follow keeps the card open and the same call finishes it.
- A `stale_base` head is merged by the lander in a worktree of its own, never in the primary checkout: `git worktree add -b land-<name> <primary checkout>/.claude/worktrees/land-<name> <integration branch>` (an absolute path, from outside every card worktree), enter it with `EnterWorktree` and its `path`, run `git merge --no-ff <head>` there so the tip is the first parent, end the message with the trailers `moai trailers` prints and confirm them with `git interpret-trailers --parse`, then get that exact merge head its checks and its verdict as the Landing section of `flows/next-flow` says and land it with `moai card land <card> --head <merge head> --by leader`. The merge worktree does not lift a refusal for overlapping tracked changes: the landing follows only the worktree that has the integration branch checked out, so the way out is the owner committing or discarding those changes on a branch of their own, or a worktree of the lander's own that has the integration branch checked out (git allows the branch in one worktree only).
- A bundle verdict is written by a lane that wrote none of the bundle's commits, and its note names that lane (`agent-N`) and its `Moai-Session` value (`moai trailers --spec <SPEC-id>`, run in the auditor's own worktree). `audit-gate` counts a PASS only when it names an auditor lane or `Moai-Session` that is not an author of the commits (rule `non-author-pass`, `src/audit_gate.rs`), so a verdict by the leader's own subagent, which names no auditor lane, does not count.
- The release pull request is the only pull request. Procedure: read the verdict's first line; verify the head equals the audited SHA and the merge-base equals the base tip (else `gh pr update-branch` and audit again); after the verdict re-run the `audit-gate` run (`gh run rerun <run id>`); post `moai/audit=success` with the verdict comment as `target_url` only when that job succeeded on the same head, never on the strength of a green `ci` and a PASS comment alone; then `gh pr merge --auto --merge`.
- After every `update-branch`, compare the changed lines with the audited delta before asking for a delta audit: when both sides changed the same line the same way (for example a fixed array length), git merges silently and the build can break; registries such as `OPERATIONS` are length-free slices for that reason.
- An audit dispatch names its caps: no whole `cargo test`, no `python3 -m unittest discover` (about 38 minutes), named test modules only (a light audit runs none; tier 2 at most two).
- Both autonomy levels keep the ruleset, the independent audit, no secrets in logs, no hook or permission bypass and the preservation boundaries of `CLAUDE.md` unchanged.
- Known gap: all sessions share one GitHub account, so the status source cannot be pinned (an audit-only GitHub App is a later HOLD).
