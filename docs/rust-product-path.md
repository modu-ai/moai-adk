# Rust product entry point: first M1 slice

The root Cargo package builds `moai-cli` version `2026.11.0-rc.1`. It directly executes project profile planning/creation and package integrity selection in Rust. It neither invokes the Python adapter nor calls an existing `moai`. `experiments/rc-cli` remains historical experiment evidence, not the product entry point. This is an incomplete RC, not a release or host installation.

The Rust toolchain is pinned by `rust-toolchain.toml` (1.94.1 with clippy and rustfmt) for local sessions and CI alike; rustup installs it on first use where only another toolchain name (such as `stable`) is present.

## Internal invocation contract

- `moai-cli project-plan PROJECT`: typed JSON profile on stdin; JSON plan on stdout. No writes.
- `moai-cli project-apply PROJECT --plan-digest DIGEST --permission-reference REFERENCE`: the exact plan on stdin. Digest binds protocol, target path identity, expected target bytes, action and profile. Exclusive creation only (temp + hard link), or unchanged result; both outcomes write a per-request receipt (Issue #1989, 01-B). The reference is required caller metadata; actual authorization must be enforced by the invoking host, not inferred from the string.
- `moai-cli package-inspect PACKAGE`: read-only full support-tree digest preview.
- `moai-cli package-resolve PROJECT --repo-package PACKAGE --user-package PACKAGE`: an explicit profile pin requires the supplied repository package and exact digest. Missing/mismatched pinned packages fail without fallback. Without a pin, only the supplied user-level package is selected. No implicit home scan or host activation occurs.

- `moai-cli agents-plan PROJECT`: typed JSON request on stdin (`protocol_version`, `language` `en|ko`, `workflow_reference` repo-relative directory that must exist — a direct `agents-plan` always checks this; only `generation-plan` naming its own output location skips it, see the generation section — `local_file` `none|ignored|tracked`); JSON plan on stdout. No writes. Reads the existing `.moai-cli/project.yaml` and `.moai-cli/manifests/generation.json`.
- `moai-cli agents-apply PROJECT --plan-digest DIGEST --permission-reference REFERENCE`: the exact plan on stdin. Re-plans against the current tree, refuses stale or altered plans and any plan with a `conflict` file, writes target files before the manifest, and reports `partial apply` with the applied list on a mid-sequence failure. Every publish is followed by its receipt entry; the result carries the receipt id (Issue #1989, 01-B).
- `moai-cli apply-recover PROJECT --receipt ID --permission-reference REFERENCE`: reverts exactly the files the named apply request published — a created file is removed again, a replaced file is restored from the before bytes stored with the receipt — and only while the file's current bytes still match the receipt's `after` digest; a file changed since the apply is skipped as `user_changed_since_apply`, never overwritten (REQ-01B-08). Paths naming `.moai/` or the receipt store are refused (REQ-01B-09); every path is checked before anything changes. A failure after at least one file was reverted (a missing or altered backup, a failed remove or replace) is `partial` with the message `partial apply: recover <id> reverted [..]; failed at <path>: <reason>; skipped [<path>: <reason>, ..]; not attempted [..]`; a failure before any revert keeps its own error (Issue #2072).
- `moai-cli baseline-inventory PROJECT [--go-baseline-commit SHA] [--go-repo REPO]`: read-only baseline (Issue #1985). One JSON on stdout with `baseline`, `inventory`, `claude_diff` and `checksums` (shasum-compatible text); writes nothing, never follows symlinks, reads the Go baseline with `cat-file`/`ls-tree` only and records home entries as existence only. Every git call removes the caller's `GIT_DIR` and the other #2033 variables and fixes `LC_ALL=C` (`identity::scrub_git_env`), so PROJECT is the repository read; a git failure other than "not a git repository" is `git_failed` (`git failed: <path-free summary>`, Issue #2054; tests: `tests/baseline_git_env.rs`). The library also exports `tree_digest(root, excludes) -> Result<String, String>` (format `moai-tree-v1`), the tree digest other Issues call instead of re-implementing. Details: `docs/baseline-rc1.md`.
- `moai-cli identity PATH`: read-only clone/workspace identity (Issue #1988), described below.
- `moai-cli claude-doctor PROJECT`: read-only prediction of whether Claude Code reads `AGENTS.md` for a session started in `PROJECT` (Issue #1992); rules in `docs/claude-adapter-contract.md`.

### Output envelope (01-C #1990, user decision 2026-11-08)

Every internal operation prints exactly one JSON object on stdout:

- success: `{"protocol_version": 1, "operation": "<name>", "ok": true, "result": {...}}`
- failure: `{"protocol_version": 1, "operation": "<name>", "ok": false, "error": {"kind", "message", "retryable", "next_actions"?}}`

`audit.delta`의 계산된 report는 이 envelope를 그대로 사용하되 `pure_merge`만 exit 0이다.
`manual_delta`·`replay_conflict`·`refused`는 `ok: true`와 exit 1을 함께 반환한다.
이 경우 `ok`는 계산 성공이며 기계적 동등성이나 AUDIT PASS가 아니다.
실제 입력/Git/I/O 실패는 기존 `ok: false` error envelope와 exit 1, 사용법 오류는 exit 2다.

stderr carries one human line: the same `message` for an operation failure, clap's first line for a command-line error. Exit codes stay 0 (ok), 1 (failure) and 2 (command-line error, `kind: usage`). Callers tell failures apart by `kind`, 15 in all:
- the 00-D list: `usage`, `invalid_input`, `input_too_large`, `unsupported_protocol_version`, `stale_plan`, `permission_reference_missing`, `not_found`, `conflict`, `partial`, `io`, `internal`;
- `git_failed` (Issue #2033): `identity` found git, but git failed for a reason other than "not a repository", for example a `safe.directory` ownership refusal. Not retryable. `plan-admit` and `run-verify` read `HEAD` the same way (Issue #2043).
- `blocked` and `transport` (07-A #2008, `forge.read`; see the GitHub TODO reader section). These additions follow #1990 HOLD-C2 / REQ-01C-02 (r27).
- `unavailable` (Issue #2345): another process holds an advisory lock the command needs, including claim-journal and message-store locks. The kind is set at the lock-wait raise site through `contract::OpError`, never classified from message text. Retryable.

The journal busy contract covers all 12 locking operations: `claim-acquire`, `claim-release`, `claim-handoff`, `effect-intend`, `effect-confirm`, `effects-reconcile`, `queue-next`, `worktree-apply`, `scope-check`, `pr-body-render`, `pr-confirm` and `layout-apply` (#2464 adds the omitted layout operation). They return `ok: false`, kind `unavailable`, `retryable: true`, exit 1 and the same `JOURNAL_LOCK_BUSY` message on stdout and stderr. The tool does not wait; the caller retries the unchanged request with bounded backoff and an attempt or deadline cap, reporting `unavailable` when its cap is exhausted. A busy `layout-apply` does not copy stores or switch the layout pointer; after the lock is released, the same confirmed plan can be applied.

`retryable` is true only for `io`, `transport` and `unavailable`, the kinds where resending the unchanged request can succeed. It never authorizes blindly repeating an uncertain external write: message operations re-read their durable attempt and the remote first. `next_actions` appears only on `stale_plan` and `partial` from an `*.apply`, and names the matching `*.plan`. On the String-classified path, a message no rule recognises is `internal`, never a guessed kind; typed operations retain their raise-site kinds. The envelope message for a command-line error names no argument value; stderr keeps clap's line for people.

Registry rules (D8 #2254, to keep parallel branches from colliding on one line). The operation name of a command comes only from `fn operation(&Command)` in `src/main.rs`, an exhaustive `match`: a new `Command` variant without an arm does not compile (it used to panic at run time). A command line that does not parse gets its operation by parsing the word's subcommand once with its required arguments filled in, so no second word table exists; the bin test `every_subcommand_word_maps_to_one_operation` checks that every subcommand word maps to exactly one name. New enum variants, match arms and table rows go at their alphabetical place, never at the end. A new String-classified module checks its error mapping locally; typed modules assert consumer-visible kinds directly. The shared case lists in `src/contract.rs` and `src/forge/mod.rs` stay as they are and get no new rows.

Not enveloped: `--help` and `--version`, the launchers, and command lines whose first word names no internal operation (clap's own output and exit 2), because no operation can be attributed to them. There is no `request_id`: the decided envelope has none. The input types (`Profile`, `Plan`, `AgentsRequest`, `AgentsPlan`) are unchanged, so a caller passes an envelope's `result`, not the envelope, to the matching `*.apply`.

Skill-side names: `skills/moai/SKILL.md` refers to the contract only as "a plan digest plus a caller-supplied permission reference", and `references/routes.json` marks SETUP and UPDATE as the only routes with `requires_binary: true`. No workflow file names a subcommand or operation yet, so there is nothing to rename on the skill side. Read against the workflow text (an interpretation, not a binding): `setup.md` steps 5-6 (per-file preview, hash re-check, apply) correspond to `project.*` and `agents.*`, and `update.md` steps 2-3 (package digest comparison, baseline/current/new diff) to `package.*` and `agents.plan`.

These commands are internal contracts for future native skill adapters. Users are not required to manually invoke them for SETUP. Host discovery, trust verification and skill invocation remain not_run.

### Identity and state-root resolver (`identity`)

`moai-cli identity PATH` reports where a path sits in git and which state roots apply to it. It writes nothing and follows no symlink. Boundaries come only from `git rev-parse --path-format=absolute --git-common-dir --git-dir --is-bare-repository --is-inside-work-tree` (and `--show-toplevel` inside a work tree), run with a fixed argv, `LC_ALL=C`, and `GIT_DIR`/`GIT_WORK_TREE`/`GIT_COMMON_DIR`/`GIT_INDEX_FILE`/`GIT_NAMESPACE`, the injected-config variables `GIT_CONFIG_PARAMETERS`/`GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_*`/`GIT_CONFIG_VALUE_*` and the discovery variables `GIT_CEILING_DIRECTORIES`/`GIT_DISCOVERY_ACROSS_FILESYSTEM` removed (Issue #2033); stderr is read only to classify a failure, and only its first line, cut before any quote or path separator, can reach the output; whether `.git` is a directory or a gitfile is never inspected. `--path-format` needs git 2.31 or later.

The result is one flat JSON object inside the envelope's `result` (exit 0). When git runs but fails for any reason other than "not a git repository" (a `safe.directory` ownership refusal, a damaged repository, oversized or non UTF-8 output), there is no result: the envelope carries `error.kind: git_failed` with the message `git failed: <path-free summary>` and exit 1 (Issue #2033).

| Field | Meaning |
|---|---|
| `identity_status` | `ok`, `no_git` (git reported "not a git repository") or `git_unavailable` (no `git` on PATH). Anything but `ok` leaves every identity field `null`; nothing is guessed |
| `workspace_kind` | `primary` (common dir equals git dir), `linked` (a `git worktree`), `bare`, or `git_dir` (inside a non-bare `.git` directory) |
| `clone_anchor`, `workspace_git_dir`, `work_tree` | canonical absolute paths of the common dir, the git dir and the top level (`work_tree` is `null` for `bare` and `git_dir`) |
| `clone_id`, `workspace_id` | `sha256:` of the canonical common dir and git dir; two worktrees of one clone share `clone_id` and differ in `workspace_id` |
| `project_id`, `profile_status` | from `.moai-cli/project.yaml` when present: `present`, `missing` or `unreadable` |
| `project_state_root` | `<work_tree>/.moai-cli`; `null` without a work tree |
| `home_state_root` | `$HOME/.moai-cli`; `null` without `HOME` |
| `id_derivation`, `writes` | `sha256-canonical-path-v0`; always `false` |

A symlinked input path, a symlinked `<work_tree>/.moai-cli` or a symlinked `~/.moai-cli` is refused with exit 1, as are a missing path and a file; error messages never echo the path. The Go generation's `.moai/`, `~/.moai/` and `MOAI_HOME` are never returned.

## Profile v2 and key-level reconfigure (03-A)

```json
{
  "schema_version": 2,
  "project_id": "example",
  "purpose": "Build an accessible editor",
  "tools": ["Rust"],
  "development_methods": ["TDD"],
  "hosts": ["claude", "codex"],
  "interview_revision": "r2026-11-08.1",
  "decisions": [
    {"id": "d1", "topic": "tools", "value": "Rust", "source": "user", "scope": "project"}
  ]
}
```

The seven v1 keys keep their v1 rules. An optional `package_pin` is `sha256:` plus 64 lowercase hexadecimal digits, obtained with package-inspect; null/mismatched pins are not an instruction to fallback. `interview_revision` (at most 128 characters) links the profile to one interview run. `decisions` (at most 32 records) keep what the interview decided: `id` (project-id charset, at most 80 characters), `topic`, `value` and `scope` (at most 256 characters each) and `source`, one of `repo`, `user` or `default` — the candidate-selection basis 03-B consumes. Every string runs through the same portable filter as v1 (paths, credential shapes and control characters refused), unknown input keys are rejected, no free-form transcript is persisted and input values are not echoed in diagnostics. This conservative filter is not a universal secret detector; the host must review interview answers before supplying them.

A `project-plan` input must carry `schema_version` 2 (REQ-03A-08); v1 files stay readable with the new fields defaulted. The plan decides per key with a baseline/current/desired three-way table and reports `action` — `create`, `update`, `unchanged` or `conflict` — plus a `delta` of sorted key lists (`added`, `changed`, `removed`, `unchanged`, `conflict`). The baseline is the profile the last `project-apply` wrote, recorded in `.moai-cli/manifests/profile-baseline.json`; a missing, unreadable or foreign record means no baseline, every key is then treated as user-edited, and any pending change lands on `conflict` — with one exception: `schema_version` is MoAI-owned schema state, never user content (leader decision on the #2052 audit), so a v1 file upgrades to v2 without a baseline while every other key keeps the conservative rule. A key the user edited away from the baseline keeps the user value when the input agrees with the baseline; a key the user edited that the input also changes is marked `conflict`, and applying a conflict plan writes nothing. A plan also lists `drift` (#2590): the sorted managed keys whose value in the current file differs from the baseline, so a hand edit after an apply is visible even when `action` is `unchanged`; the key is left out when there is no baseline, no file, or no difference, and it is part of the plan digest.

`project-apply` on an `update` plan re-verifies the file hash against the plan's `expected_sha256`, replaces the file through a temporary-file rename, keeps user-preserved keys and unknown user keys, and then rewrites the baseline record; a baseline-record failure after the file write is reported as `partial apply`. The apply result carries `state`, `profile_digest`, `interview_revision`, `host_verified: false` and a `next_actions` note stating that the `generation.json` `profile_sha256`/`interview_revision` update belongs to the 03-C generation apply. The serializer emits JSON syntax, a YAML 1.2 subset, with `serde_json` running `preserve_order` (Issue #1992, leader RC1 decision H1 = B): a created file follows the schema field order, and an update keeps the existing file's key order with `delta.added` keys appended at the end. General YAML (comments, anchors, block style) keeps its v1 refusal — "existing YAML requires preservation review" — until the lossless-editing HOLD is decided. No AGENTS or host settings are written by these commands.

Known gaps: project.apply records 01-B receipts (merged REQ-01B-01/06/08/10 mirrored at the merge: refused conflict receipts, per-publish entries with before bytes under `.moai-cli/receipts/<request-id>.before/`, zero-publish unchanged receipts); the deeper unification — running the profile path's publish through `apply::publish_replace`/`publish_exclusive` and reconciling `expected_sha256` with the receipt before/after digests — stays a reported follow-up; the baseline record is best-effort trust (an apply wrote it, a hand-edited one cannot be authenticated, and every inconsistency degrades decisions toward conflicts); a v1 file without a baseline record upgrades its MoAI-owned `schema_version` and adds the v2 keys, but any value the input would change still conflicts until a recorded apply establishes the baseline; rename atomicity and permission preservation are verified on macOS fixtures only (Windows/Linux not_run).

The package digest algorithm `moai-package-tree-v1` frames sorted UTF-8 relative paths and file bytes with big-endian u64 lengths and a domain prefix. It covers SKILL.md and support files; symlinks, special files, oversized files/trees, deep nesting and nonportable paths are refused. It proves observed content identity, not authenticity or host compatibility. Package paths are explicit input rather than final install-layout decisions. Concurrent tree mutation and symlink swaps are not OS-level atomic snapshots.

## Project-unit skill copy (`project-skill-plan` / `project-skill-apply` / `project-skill-revert`, I5 #2242)

## AGENTS.md managed section (agents-plan / agents-apply)

`AGENTS.md` stays user-owned. The generator owns only the block between `<!-- moai:managed:begin id=moai-workflow -->` and `<!-- moai:managed:end id=moai-workflow -->`; bytes outside the block, including CRLF line endings and a missing final newline, are preserved. Per file the plan decides with a baseline/current/new comparison on digests: the baseline is the block the generator last wrote (recorded in `.moai-cli/manifests/generation.json` `owned_files[].baseline_sha256`), current is the block found in the file, new is the rendered block.

| Baseline | Current block | Decision |
| --- | --- | --- |
| none | absent | `create` (no file) or `append` (file exists) |
| none | present, equals new | `unchanged`; adopted as baseline on apply (recovery after a partial apply) |
| none | present, differs | `conflict` (unowned block) |
| recorded | equals baseline | `merge` (replace the block only) |
| recorded | equals new | `unchanged` |
| recorded | edited or removed, template unchanged | `unchanged` (user edit or deletion respected) |
| recorded | edited or removed, template changed | `conflict`; nothing is applied |
| any | duplicate, unterminated or orphaned markers | `conflict` |

A removed block is never restored: the plan stays `unchanged` and reports the deletion in the file's `detail` and in `warnings` ("managed block absent; user deletion preserved").

`AGENTS.local.md` is opt-in through `local_file`. `ignored` creates it once and appends a `# moai:managed:begin id=moai-local` section to `.gitignore` unless a line equal to `AGENTS.local.md` or `/AGENTS.local.md` already exists (effective git ignore status is not verified; no git command is run). `tracked` creates it once and adds no ignore rule. The file is never modified or recreated afterwards.

Rendered profile values are checked before any write: a value containing `<!--`, `-->` or `moai:managed:` is refused, and the spliced result must contain exactly one managed block whose bytes equal the rendering. New files are published by writing a uniquely named temporary file and hard-linking it to the target, which fails if the target appeared meanwhile; existing files are replaced by rename. Both publishes stage the temp in the target's directory (`create_new`), write and `sync_all` it, re-verify the target, then publish and `sync_all` the parent directory; a rename across filesystems is refused, never downgraded to copy+delete, and a failed publish leaves no temporary file behind (REQ-01B-03..05). ## GitHub TODO reader (`forge-read`, 07-A #2008)

`moai-cli forge-read PROJECT` takes `{"schema_version":1,"owner","repo","state":"open|closed|all","include_comments":true,"config":{…}}` on stdin (unknown keys rejected) and is an internal operation (`forge.read`) under the Output envelope rules above: `main` wraps the result with `contract::success`, a failure becomes `contract::failure` with the kind `contract::classify` derives from the message, exit 1, and stderr carries the same message.

Error kinds:
- From the 00-D vocabulary: `invalid_input`, `input_too_large`, `unsupported_protocol_version` (request `schema_version`), `not_found` (404 or a missing project directory), `io` (poll state) and `internal`.
- Added to `contract::Kind` by this adapter (#1990 HOLD-C2 / REQ-01C-02 (r27) allows additions when they are recorded):
  - `blocked`: authentication failed (401), access denied (403), or a rate limit outlived the retry budget. In the CLI envelope `blocked` is always `retryable: false`: resending the same request at once cannot succeed, because it needs new credentials, a permission change, or waiting until the reset. Only the library value `ForgeError.retryable` is `true` for the rate-limit case, so a library caller knows waiting will help. That value is not in the envelope.
  - `transport`: gh is missing, gave no HTTP response, did not answer within the call bound, or the response had an unexpected status. It is `retryable: true`.
- Call bound (#2048): each `gh api` call runs in its own process group and is bounded by `GhTransport.timeout` (`GH_TIMEOUT`, 60 s, unmeasured). Past it the whole group is ended, so a grandchild holding the output pipes cannot keep the caller waiting, and the call fails as `gh transport: gh did not answer: timed out after <ms> ms`. Output readers get 2 s after gh ends. Callers that already treat a transport failure on a write as uncertain (07-B, 07-C) see this as one more transport failure. Test: `tests/forge_cli.rs` `transport_times_out_on_stalled_gh`.
- Every forge message carries its kind's phrase (`forge blocked: `, `gh transport: `, …). The unit test `every_error_kind_matches_the_contract_classifier` checks that `ForgeError::kind` and `classify(message)` agree, and the contract table test lists the forge messages.

What one run does:
- It sends GET requests only, one at a time: the repository (for `repository_id`), then the Issue list, then the Issue comment list (`sort=updated&direction=asc&per_page=100`).
- Every page after the first is the `Link: rel="next"` URL sent byte for byte; the client never builds page numbers.
- Every URL already seen is re-sent with `If-None-Match`. A 304 is answered from the cached projection, and `cache_hit` is true when every page came back 304.
- The next `since` cursor is the newest `updated_at` read minus `overlap_s`. It comes from the data rather than the clock, so a repository with no changes is asked the same URL again and answers 304. Items repeated by the overlap are deduplicated by id, keeping the newest copy.
- Pull requests in the Issue list are kept with `kind: pull_request`. Comments keep only id, node_id, issue number and `updated_at` — no body, no login.

Each item carries `ref = (provider, host, project{owner, repo, repository_id}, issue{id, node_id, number}, updated_at, etag)`. Identity is `(provider, host, repository_id, issue.id)` (`forge::identity`): names are display data and `number` is never a key.

Retries follow GitHub's headers:
- `retry-after` first.
- Otherwise `x-ratelimit-remaining: 0` waits until `x-ratelimit-reset`.
- Any other 403/429 that is a rate limit waits `60 s << attempt`.
- After `max_retries` waits the result is `blocked`: `retryable: false` in the envelope, `ForgeError.retryable == true` in the library. 401 and other 403s are `blocked` at once, with `retryable: false` in both.

The config is visible in every result:
- `overlap_s` 60 and `max_retries` 3 are interim values (leader, 2026-11-08).
- `poll_interval_s` is unmeasured (P11) and has no default; `x-poll-interval` wins when present (`next_poll_after_s`).
- `max_pages` 50 is a safety bound.

Poll state is `PROJECT/.moai-cli/forge/poll-state.json`, written as a temporary file plus rename. Symlinked or non-directory state folders are refused, nothing is written under `.moai/`, and nothing is written when the run fails. A state file for another repository is ignored and replaced on the next success.

Transport is `gh api -X GET -i <URL>` (RC1 interim decision: no new crate; the same path as the 00-B collector). The token stays in gh's keyring or the caller's `GH_TOKEN`; this program never reads it, and token-shaped text is redacted from any gh stderr it surfaces. gh exits 1 on 304 and on 4xx while still printing the status line and headers, so the parsed status line decides, not the exit code (observed with gh 2.92.0 on 2026-11-08). `MOAI_FORGE_GH_BIN` swaps the gh executable and exists for tests only. Risk: whoever sets it chooses the program that runs, so it must never be set on a product path. It is accepted only as an absolute path to an existing file; anything else is `invalid_input`, so a bare name cannot resolve to another program through PATH.

`forge::write::Writer` holds the edit-preserving write helpers for 07-B/07-C; it has no CLI command here.
- Labels change only through `POST …/labels` (add) and `DELETE …/labels/{name}` (remove one). Assignees change only through `POST`/`DELETE …/assignees`. There is never a PATCH or PUT of a whole set.
- Each write re-reads the issue first and returns `conflict` without sending anything when `updated_at` or the body digest differs from the caller's last read. GitHub does not support conditional requests on unsafe methods, so this re-read is the guard.
- Writes are kept at least one second apart.

Tests (`tests/forge_cli.rs`) replay synthetic fixtures from `tests/fixtures/forge/` with an injected clock, or point the CLI at a stub gh. They use no network and never sleep.

Not verified here:
- write helpers against the live API;
- comment pagination and 304 on a busy live repository;
- GitLab (`iid`, "on or after" `updated_after`, keyset pagination) — the reference schema leaves room for it but nothing is implemented;
- whether `since` should move from the Issue list to `updated` sort plus local filtering for very large repositories.

## Durable lane/leader messages (`message-*`, #2390 S1)

Decision 6774899518 row 21 chooses **local plus Issue comments**, not a host adapter's
send attestation. The public serde types in `src/message.rs` are the report/request
schema; unknown fields are refused. `message-record` and `message-reconcile` take
`{"message": Message}`. `message-ack` additionally requires the expected
`payload_digest` returned by the record. A complete example record request is:

```json
{
  "message": {
    "schema_version": 1,
    "report_id": "r1",
    "project_id": "p1",
    "task": {
      "owner": "org", "repo": "repo", "repository_id": 1,
      "issue_id": 2, "issue_node_id": "I_2", "issue_number": 3,
      "task_id": "task:3", "revision": "rev1"
    },
    "sender": {"actor_id": 11, "session_id": "agent:one"},
    "receiver": {"actor_id": 22, "session_id": "leader"},
    "owner_epoch": 1, "leader_epoch": 1, "event": "report",
    "candidate_digest": "sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "created_at": "2026-11-11T00:00:00Z",
    "approval_refs": [], "hold_refs": [],
    "payload": {"text": "hello"}
  }
}
```

The whole message is immutable for its `report_id`: a different task/revision,
sender/receiver, epoch, event, candidate, creation time, reference or payload is a
conflict, never an update. `report_id` and `project_id` are portable names of at
most 64 bytes because they enter file names/markers. Task/session/revision IDs
are nonempty, control-free literal data, including punctuation and Unicode;
they are neither paths nor commands. Numeric identities and epochs are positive.
The candidate is a caller-declared SHA256 digest, not artifact verification.
`created_at` is declared UTC creation time, not proof of delivery. Payload digest
is `crate::digest` over compact UTF-8 serde_json bytes after recursively sorting
object keys; array order and serde_json number representation are retained.

Each checkout stores `.moai-cli/messages/{outbox,inbox}/<report_id>.json`.
Intent and actual attempt observations (`attempts`, `attempted_at`,
`response_status`, `observed_at`) are persisted with sync plus temporary-file
rename before a POST; the persistent `.lock` is an OS advisory lock, not a PID
lease or authority to take a task. An unheld file survives process exit and does
not block restart. No stale file is deleted to acquire the lock.

`queued` requires a fresh matching Issue report; it is **not** an ACK.
`received` records this checkout's authenticated, explicit receiver action.
`received_ack` requires a matching receiver-authored remote ACK. Result fields
include these flags, `state`, `report_id`, `payload_digest`, `record_comment_id`
and `ack_comment_id`; `business_acceptance` and `business_completion` stay false.
Reconciliation only observes the remote and updates local journals: it does not
create a receiver action, ACK, claim transfer or business acceptance.

Every comment page is checked, with exact first/end marker boundaries, immutable
context/digest and numeric GitHub author IDs. Before publication `/user` must
match the expected actor. A shared GitHub account's session name remains a
declaration, not native-host receipt or cryptographic session identity. Identical
duplicate comments are one logical packet; observed conflicts block mutation.
Cross-host atomicity and exactly-once delivery are not guaranteed.

Pagination stays within the exact Issue comments collection; foreign next URLs
are refused before GET. Cyclic or malformed next links fail closed. ACK and
reconciliation leave existing receipt files unchanged on these traversal errors.

A response-lost publication can succeed only after a fresh matching read.
Otherwise record/ACK return a typed error and retain the attempt; reconciliation
may report `publish_unknown`. Transport/408/5xx uncertainty never permits blind
republication. A definite rejected 4xx other than 408 is `blocked`; only a new
explicit invocation, after fresh target/context/actor/permission checks, can make
another attempt with the same ID. No invocation automatically retries POST.

CLI stdin retains its 64 KiB bound. The actual rendered comment, markers and
newlines included, reuses `forge::report::DEFAULT_MAX_BODY_CHARS` (65,535
characters, a conservative unmeasured bound, not a newly documented API limit).
The shared credential-shape filter checks decoded strings and object keys before
payload persistence/publication; it is not a general secret/privacy detector.
Permission references remain caller metadata: the invoking host owns real
authorization and disclosure review. No user drafts or unrelated files are
collected. Known symlinks/traversal are refused, not a race-proof sandbox claim.
S1 has no host/Hide wake, daemon, dispatch disposition, ownership takeover or
user-settings/home migration.

### Directory durability and failed-sync restart boundaries (#2462 P2)

Before any remote request, all three message operations validate/create each
`.moai-cli/messages/{outbox,inbox}` directory and sync both its parent and itself.
This includes the existing project directory, `.moai-cli`, `messages`, `outbox`,
and `inbox`. The same calls run on `AlreadyExists`: an earlier interrupted
invocation may have left a visible path whose parent entry was never synced.
Every journal replacement still syncs its temporary file, renames it, then syncs
the containing directory. Open/sync errors propagate as `io`; an unsupported
directory sync is a refusal, never a successful durability claim. No platform
silently skips this directory barrier.

| Injected directory-sync failure | Observed effect | Next invocation after the fault is removed |
| --- | --- | --- |
| New or existing parent chain, sender or receiver | `io`, remote calls/POST count unchanged; no journal publication | Re-sync the complete chain, perform fresh context/actor/remote checks, publish once |
| Sender intent or pre-attempt observation replacement | `io`, POST count zero, persisted `attempted:false` | Fresh checks may publish once |
| Sender attempted replacement before POST | `io`, POST count zero, visible journal has `attempted:true` | Conservatively refuse another POST while publication is absent |
| Record or ACK outcome replacement after POST | `io`, one POST already issued, attempted state retained | Hidden publication never causes another POST; a later matching GET reconciles it |
| Reconcile parent-chain sync | `io`, no remote call, existing receipt bytes unchanged | Reopen and reconcile after re-syncing; never POST |

Permanent Unix unit tests trace successful mkdir and directory-sync calls and
assert the complete chain at the actual synthetic Transport POST boundary.
Fault injection covers both new and pre-existing paths, both publishers and
receipt replacement phases. These are syscall/invocation restart models, not a
physical power-cut experiment or a guarantee about faulty hardware or every
filesystem. The test observer and fault injector are compiled only for Unix unit
tests; production has no environment switch to bypass synchronization.

Official sources read 2026-11-11: [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)
explains that file syncing does not by itself persist its parent directory entry;
[Rust File::sync_all](https://doc.rust-lang.org/std/fs/struct.File.html#method.sync_all)
describes content/metadata synchronization and errors that dropping a file can
ignore. Adopt explicit directory sync and error propagation. This follows the
OS/filesystem synchronization contract; actual power-loss and Windows runtime
validation are not_run. Retrieval UTC and full HTML SHA256 are recorded with the
PR repair evidence in `sources.json`; the live Rust docs version is distinct from
the locally compiled 1.94.1 toolchain.

Sources read 2026-11-10: [GitHub Issue comments](https://docs.github.com/en/rest/issues/comments),
[Rust rename](https://doc.rust-lang.org/std/fs/fn.rename.html) and the
[Idempotent Consumer pattern](https://microservices.io/patterns/communication-style/idempotent-consumer.html).
Retrieval times/checksums and the user-decision link are recorded in #2390

## Claim journal and Issue comment claim (`claim-*`, 06-A #2005)

One task is claimed by at most one owner. The P08 decision (2026-11-08) is ⑤ the GitHub Issue comment claim as primary and ① a single-host journal as the same-host serializer. The claim record (REQ-06A-01) carries `schema_version`, `task_ref`, `task_key`, `logical_key`, `owner`, `attempt`, `epoch`, `base_revision`, `worktree{common_dir, git_dir, path, head}`, `write_scope`, `spec_ref`, `comment_id`/`claim_token`, `lease_until`, `state`, `effects[]` and `last_observed_at`.

`moai-cli claim-acquire PROJECT` takes a typed JSON request on stdin (unknown keys rejected): `schema_version`, `task_ref` (`provider`, `host`, `owner`, `repo`, `repository_id`, `issue_id`, `issue_number`), `logical_key`, `owner{kind, id, host_id?}`, `attempt?`, `base_revision` (40 lowercase hex), `write_scope[]`, `spec_ref{id, revision, digest?}`, `lease_until?` (RFC3339 Z; default now + 4h), `projection_intents[]` (recorded as intents only — a claim never writes assignees, labels or the Issue body, REQ-06A-08/17) and `expected_epoch?`. Under the journal lock the order is: journal owner check (REQ-06A-03), live-comment check, one comment POST, a post-POST re-read that settles the cross-host race — the smallest live comment id wins (REQ-06A-13; a concurrent claimant can pass the same pre-check between our GET and our POST, so the POST alone decides nothing) — and only then the journal append. The loser keeps its posted comment (it is inert under the smallest-live-id rule, and deleting it is no authorized claim write) but records nothing. Outcomes as `result.outcome` (`ok: true`, exit 0):

- `claimed` — the journal accepted the record and exactly one claim comment was posted (REQ-06A-12); the returned comment id and the token `Moai-Claim: <issue>#<comment-id>` are recorded in the record. A live winning comment with the caller's own session value is adopted instead of duplicated only when this journal recorded posting that comment id (#2165, REQ-A6-01); without that proof see `uncertain`.
- `already_owned` — the journal holds an active record (returned unchanged, REQ-06A-03), or a live comment of another session has the smaller comment id (REQ-06A-13); the loser wrote nothing (`foreign_owner` names the winner).
- `expired` — the active record's lease has expired; takeover is never automatic, the operator decides (06-B) (REQ-06A-16).
- `uncertain` — the comment was posted (its id is named in `notes`) but the post-POST re-read failed or does not show it, so the winner cannot be judged; nothing was journaled. Re-check with `claim-show` and the issue comments; the resolution lives in the comment ledger (`coordination_scope` stays `cross-host-eventual`). Also returned, with nothing posted or journaled and `foreign_owner` naming the comment, when the winning live comment carries the caller's session value but this journal has no record of posting it: a same-named live session may own it (#2165, REQ-AM-04). A claim the leader posted on a lane's behalf is therefore not adopted by a later `claim-acquire`; importing such a relay claim needs its own path.

A held journal lock is not an outcome: every journal-writing operation (`claim-acquire`, `claim-release`, `claim-handoff`, `effect-intend`, `effect-confirm`, `effects-reconcile`, `queue-next`, `worktree-apply`, `scope-check`, `pr-body-render`, `pr-confirm`) answers the one failure envelope with kind `unavailable`, `retryable: true`, exit 1, the shared message `journal busy: the claim journal lock is unavailable (another process holds it); …`, and the same line on stderr (Issue #2345; REQ-06A-05 busy-never-waits; tests `tests/journal_lock_busy_cli.rs`). Before #2345 `claim-acquire`, `claim-release` and `queue-next` answered a `busy` outcome (`ok: true`, exit 0) while the 06-B/06-C ops answered a `conflict` error the classifier made non-retryable. Retry rule (AC-2): the caller retries the unchanged command after a bounded wait — a fixed backoff (10–100 ms is the documented convention, not a product behaviour) under a hard cap of attempts or a deadline — and reports `unavailable` when the cap is out; the tool itself never waits and a lease is never taken over by waiting.

`claim-show PROJECT --task KEY` reads the journal read-only (no lock, no creation) and is byte-identical when repeated at one instant (REQ-06A-10; the clock is read only for the `expired` flag, #2166); `KEY` is the 16-hex `task_key` an acquire returned (sha256 of `provider|host|repository_id|issue_id`). `claim-release PROJECT --task KEY --epoch N [--reason R]` closes the active record as `cancelled` when the epoch matches; a wrong epoch is a `conflict` error carrying `stale epoch` (AC-06A-2). Every output names `coordination_scope` (`cross-host-eventual` for claims decided by a comment, `single-host` for journal-only results) and `cross_host_atomic: false` (REQ-06A-11).

The journal root is `<git common dir>/.moai-cli/claims/` — `journal.log` (append-only, one JSON event per line, fsync; the authority), `<task_key>.json` (temp + fsync + rename; a human-readable cache written after the log) and `.lock` (`File::try_lock`, advisory). Deriving the root from the common dir (01-A) gives one journal per clone across all worktrees and keeps git status clean. It is an interim location (@MX:NOTE in `src/claim.rs`): the state-root map belongs to P09/01-B, and 06-B must migrate records if it moves. A torn append (no trailing newline) and an orphaned `.json.tmp-*` file are ignored — the last complete line wins; a corrupt complete line is an `io` error. Symlinked journal paths are refused (REQ-06A-07); a symlink swap between the check and the open is a residual risk of the advisory local model. The filesystem type is detected best-effort (`stat`); on NFS/CIFS the note warns that atomicity and locking are not guaranteed, and the fallback says the guarantee holds only on local filesystems. NFS behaviour itself is not fixture-verifiable here (not_run).

`lease_until` defaults to now + 4h (`claim::DEFAULT_LEASE`, rc.2 #2166, decisions 00:5x 2026-11-09) when the request omits it or sends it empty; an explicit value wins. The heartbeat numbers stay HOLD (P08/P11). An expired lease never produces an automatic takeover (REQ-06A-16, REQ-A7-02): `claim-show` only reports `expired: true` for an active record whose lease has passed.

Manual handoff after expiry (#2166): (1) the lane or the leader runs `claim-show PROJECT --task KEY` and sees `expired: true` with the record's `epoch`; (2) the leader decides the handoff and runs `claim-handoff PROJECT --task KEY --from-epoch <epoch> --reason <text>` (06-B below), which opens the next attempt at `epoch + 1`; (3) the decision is recorded in the Issue's owned comment and in `docs/decisions-*.md`. Expiry alone never starts step 2.

Token transport (REQ-06A-14) and verification: the claim token travels in the branch name (suffix `c<issue>-<comment-id>`, since branches cannot carry `#`), in every commit's `Moai-Claim: <issue>#<comment-id>` trailer and in the PR body. `claim::verify_claim_token(issue_number, comment_id, carriers)` is the leader's read-side check (REQ-06A-15): a missing branch, a commit without the trailer, a commit carrying a different (stale) token, or a PR body without the token is a reason; the verdict passes only when all three carriers agree.

Error kinds follow the envelope table: `unsupported_protocol_version` (request `schema_version`), `invalid_input` (validation, symlinked journal path), `conflict` (`stale epoch`), `io` (journal read/write/replace), `git_failed` (the HEAD read), `not_found` (404 on the comment POST), `transport`/`blocked` (from the forge read path). GitHub access reuses the 07-A read path (`forge::Client` over `GhTransport` or `RecordedTransport`); the only write a claim performs is the one comment POST (AC-06A-11/13).

Tests (`tests/claim_cli.rs`) cover: 8-process concurrency (one `claimed`, the rest `already_owned`, one journal event), epoch monotonicity and stale-epoch rejection, torn-write recovery, symlink refusal, byte-identical `show`, lowest-live-comment-id wins, no-other-writes, token carrying/verification, expiry naming the operator, and the Go-path preservation hashes. Not verified here: any live GitHub write (live not_run — a real claim comment is posted through the real `gh` only in production use), Windows `LockFileEx` behaviour, NFS/CIFS/locking semantics on network filesystems.

### Free cards (`queue-free`, #2675)

`moai-cli queue-free PROJECT` takes `{schema_version, owner, repo}` on stdin and lists, read only, the open cards a lane may take. It reads every open Issue (GET, pages of 100) and puts each one, pull requests excluded, into exactly one bucket, in this order: `held` (a label named `needs:decision`, `hold` or `<axis>:hold`, case ignored — whole names only, so `threshold` does not hold a card), `epics` (title `][EP-`), `blocked` (a `Blocked-By:` line names an Issue that is still open), then — after reading that card's comments with the same claim replay as `queue-next` (releases and handoffs close the claim they name) — `reserved` (an outstanding handoff names its recipient), `claimed` (a live claim; the lowest live comment id is shown) or `free`. A free card carries `why`: `unclaimed` (no claim line ever), `released` (every claim released) or `expired` (only expired claims remain; the holder, comment id and lease are shown, and taking it over still needs a handoff line or decision D2's timeout conditions). Held cards, epics and blocked cards cost no comment read. The answer always states its count: `free_count` and a `summary` line `free <n>건 (inspected …, claimed …, reserved …, held …, epics …, blocked …)`, so an empty result reads `free 0건` and is never confused with missing output; a failed read is an error, never an empty list. Tests: `tests/queue_cli.rs` (`queue_free_*`, recorded exchanges); a live GitHub run is not_run.

### Self-claim of the next card (`queue-next`, rc.2 A2 #2161)

`moai-cli queue-next PROJECT` takes `{schema_version, owner, repo, milestone, claim{owner, base_revision, write_scope[], spec_ref, lease_until}}` on stdin and claims the next card without a leader dispatch (`docs/design-review/autonomy-modes-spec.md` §3 steps 1-6). It reads the repository and every open Issue (GET only; the remote is the source of truth), keeps the given milestone, skips pull requests, epics (title `][EP-`) and cards whose `Blocked-By:` line names an Issue that is still open, and orders the rest by parent epic (`상위: #N`) then number. Under one journal lock for the whole run it calls the `claim-acquire` body per candidate with `task_ref` and `logical_key` (the title's second bracket, else `issue-<n>`) filled in. Before acquire, each candidate's comments are read: a card that already carries any `moai-claim:` comment, live or expired, is not a candidate and goes to `skipped` as `{issue, reason: "claimed", claimed_by, comment_id, lease_until, expired}` with nothing posted (REQ-A2-01, REQ-A2-02, REQ-A7-02 — no automatic takeover); only a card this journal already holds an active record for goes to acquire regardless. A foreign claim that appears between that read and the POST (`already_owned`) is listed in `lost_to` and the next candidate is tried, with nothing journaled for the lost card; `claimed`, `uncertain`, `expired` or an active record of this session stops the run. No candidate is `idle`; every candidate lost is `exhausted`. Its only GitHub write is the claim comment POST: the state label and the owned report `상태:` line are recorded as projection intents and returned as `not_run`, because RC1 applies no state labels (`.github/moai/labels.yml`) and the report comment belongs to `forge-report`. Not handled: a local assignments file is not read. Tests (`tests/queue_cli.rs`, `src/queue.rs` unit tests) cover the contest (one POST per card, loser moves on and journals nothing), expired and live foreign claim comments (skipped, POST 0), blocked-card exclusion and the idle case; a live GitHub run is not_run.

### Leader supervision tick (`leader-tick`, rc.2 A3 #2162)

`moai-cli leader-tick PROJECT` takes `{schema_version, owner, repo, base_branch, lanes[]}` on stdin (`lanes`: the free lanes in preference order, which the leader reads from its session list). It is GET-only on GitHub: the open PRs into `base_branch`, then per PR its `mergeable_state`, the `moai/audit` status and the CI check run on the current head (named `ci`, or `rc-ci` before #2563; the newest run under either name decides), and the claim and `AUDIT … verdict:` comments of the Issue the PR `Refs`. It compares each PR's observation with the previous tick in `.moai-cli/forge/leader-tick.json` (temporary file + rename) and reports only the PRs that changed, plus PRs that closed; an unchanged PR is not reported, and a `mergeable_state` of `unknown` on the same head is not a change. For a changed PR that needs a repair (a `FAIL` verdict on the current head, a failed CI check, or a `dirty` merge state) it drafts an `assignee-hint` comment for the first free lane that is not the PR's author (the claim comment's winner) and a one-line repair Issue title; posting them is the leader's act through `effect-intend` → `gh` → `effect-confirm`. The interval is the profile key `leader.pr_check_interval_secs` (default 300 — a user-chosen value, not a measured one); the tick reports it and its source and never sleeps. Not done here: regenerating `assignments.json` (a follow-up card), branch-only progress (`in_progress` is not probed), a live GitHub run (fixtures only). Tests: `tests/leader_cli.rs` (report then skip then report again across ticks, hint target excludes the author, interval default and profile value) and unit tests in `src/leader.rs` and `src/profile.rs`.

### Lane status table (`lane-status`, rc.2 A11 #2265)

`moai-cli lane-status PROJECT` takes `{schema_version, owner, repo, base_branch, issues[1..50], lanes[0..50]: {session, name?, pane?: {state: working|permission_prompt|input_pending|unreachable|usage_limit, source, observed_at, until?}}, pending_decisions[]: {issue, source, recorded_at}}` on stdin. It reads, GET only, the open PRs into `base_branch`, each named Issue and its comments, the state of each `Blocked-By:` Issue outside that set, and the commit list (with each commit message) and the conversation comments of each PR that `Refs` a named Issue; locally it reads `git worktree list --porcelain` (scrubbed git). It writes nothing anywhere, so the same remote gives the same table. A row is one (session, Issue): ownership from `claim_verify::evaluate` (holder comment, epoch, lease, live; a handoff whose recipient has not claimed yet gives the recipient a `handoff` row), the open PR with its head and branch, the lane worktree (`issue/<n>-…`), and a phase with the record it came from — `handoff`, `waiting` (PASS on the head), `pr_open` (no verdict on the head), `implementing` (FAIL on the head, a lane worktree, or an owned report `상태: running` after the claim) or `claimed`. Idle causes come from records only: caller pane observations (`unreachable`, `permission_prompt`, `input_pending`, `usage_limit` — held at a usage limit, with the caller's `until` in the evidence, #2668; `working` means not idle), caller-recorded pending decisions (`user_decision`), an open blocker (`waiting_prerequisite`), `waiting_audit`, `waiting_integration`, `no_ready_card`, `ready_card_unassigned`, and `unknown` when nothing supports one (for example an active card with no pane observation). Duplicate, out-of-order and unreported heads are judged by the PR's commit order (at most 250 commits, per the GitHub REST reference), never by comment ids or times; a SHA outside the PR is counted in `ignored_shas`. Assignment drafts pair a lane without a card with a ready Issue (no claim line, no open blocker) and are never posted. Research record: `docs/design-review/lane-status-a11-2026-11-10.md`. Tests: `tests/lane_status_cli.rs` and unit tests in `src/lane_status.rs`.

Audit columns (#2403 item 3): a row with a PR carries `audit`: `head`; `reservations` — every whole-line `moai-audit-claim: lane=<lane> head=<40 lowercase hex>` on the PR, each with `comment_id`, `current` and `state` (`current`, or `stale` for a reservation on an older head) (names the PR's current head); `winner_on_head` — `{lane, comment_id}` of the current-head holder by the same rule as `audit-claim` (`audit_claim::holder_of`, #2499): the lowest-id reservation, moved by the last `moai-claim-handoff: comment=<that reservation id> to=<lane> by=leader` line on the PR (then `comment_id` is the handoff's), or null; `winner_via` (`reservation`\|`handoff`), `winner_reservation_id`, and `winner_is_author` — whether an `author_sessions` entry is the same lane as the holder under the lane name rule; `lane_name_rule` names that rule; `verdict_on_head` — the last `AUDIT … verdict: PASS|FAIL` line naming the current head, read from the PR's comments first and then the Issue's, with `source` `pr` or `issue`; `author_sessions` — the sessions of the claim comments named by `Moai-Claim: <this Issue>#<id>` lines in the PR's commit messages (every epoch, so a repaired PR lists both the original and the repair session; tokens for other Issues are ignored), the sessions that may not audit that head; and `unresolved_claim_ids` — token ids that are not a claim comment on the Issue. A row without a PR has `audit: null`. The phase still reads verdicts from the Issue only (unchanged); nothing is assigned or posted.

#### Additive communication observation (#2390 S6)

The input and all existing output fields retain their meanings. `lane-status` adds this top-level metadata-only object; message payload values are not returned:

```text
communication: {
  available: bool,
  observed_at: i64,
  lanes: [{
    session,
    sent_reports: [{
      report_id, issue, event, to, record_comment_id, ack_comment_id,
      received_ack, ack_alert, elapsed_secs
    }],
    received_acks: [{report_id, issue, ack_comment_id}],
    unacknowledged_report_ids: [string],
    dispatches: [<S2 dispatch-check JSON plus issue, from, to>]
  }],
  errors: [{issue, reason}]
}
```

`sent_reports` selects the canonical S1 wire sender's `session_id`, not the GitHub comment author's login. `received_acks` lists explicit receiver ACKs of that lane's **sent** reports; it does not list reports the lane received, infer receipt from publication, or imply acceptance. Named lanes and discovered message actors are included with deterministic ordering. Generic events, `dispatch` and `dispatch-decision` remain distinct.

Sources are the existing Issue/comment GET snapshots with complete pagination. Shared list readers follow GitHub's `Link rel="next"` verbatim, including its normal transition from `/repos/{owner}/{repo}/...` to `/repositories/{id}/...`; S6 collection validation must not truncate the existing status table or other readers.

Only `communication` validates the captured comment-page source URLs: each must name the original slug collection or `https://api.github.com/repositories/<verified repository id>/issues/<n>/comments`. One live repository identity GET is needed when an S1 marker is detected or a comment-page source needs repository identity verification (including a numeric alias without message packets). The comment pages are not fetched again. A different repository id, host or collection makes the communication observation unavailable rather than manufacturing an ACK.

Canonical S1 message validation, operation marker/digest, numeric publisher identity, target and actual repository/Issue context must agree. GitHub authors identify accounts; session IDs are declarations, not independent session authentication. Exact duplicate publications are deduplicated deterministically. Immutable report-ID conflicts are checked before event/context filtering. Relevant malformed packets, conflicts or incomplete observations make `communication.available=false` with generic `{issue, reason}` errors, without replacing the old lane-status output or fabricating an ACK.

The five-minute target uses the server record comment's `created_at`, never `Message.created_at`: at 299 seconds without explicit receipt the alert is `waiting`; at 300 (N) and 301 (N+1) it is `unacknowledged`; an explicit matching receipt is `received`. Future time is unknown; malformed timestamps or arithmetic overflow make the observation unavailable/unknown, never elapsed zero or a fabricated timeout.

Dispatch metadata reuses the S2 checker against the frozen GET snapshot, not a second live read or a parallel acceptance reducer. Receipt is not acceptance; an older superseded dispatch is not a current assignment. S2's observation-only flags and revision/decision rules remain intact. This is GET-only observation with no filesystem writes, host transmission/wake, scheduled delivery, takeover or claim/audit gate changes. S3, the S4 remainder, S5, host transport and audit gate linkage remain **HOLD**.

### Audit reservation (`audit-claim`, rc.2 #2403 item 1)

`moai-cli audit-claim` takes `{schema_version, owner, repo, pr, head, lane}` on stdin. It reads, GET only, the PR (it must be open and `head` must be its current head), the PR's commits (at most 250, per the GitHub REST reference) and the comments of the Issue its body `Refs`, to find the authors: every `Moai-Claim: <issue>#<id>` trailer resolved to the `session` of that claim comment. The author match compares the lane with the claim `session=` name by the lane name rule (#2499, `audit_claim::NAME_RULE`, echoed in `author_rule`): a name `<lowercase letters>-<digits>-<fragment>` (fragment of ASCII letters and digits, such as `pr-1-hB` or `agent-22-2293`) is lane `<letters>-<digits>`, and any other name (`lane-t74`, a UUID, a second fragment) matches byte-exact only (before #2499 every match was byte-exact, leader answer #2403 comment 6784934128). The same rule decides whether the lane already holds the head. A lane that is an author is refused (`conflict`), and a trailer whose claim comment is not a claim line refuses the call (`blocked`), so an unreadable author is never taken for a non-author. Then it reads the PR's comments. The holder of a head is the `moai-audit-claim: lane=<lane> head=<head>` line with the lowest comment id (user decision, #2403 comment 6784520362); the leader moves it only with `moai-claim-handoff: comment=<reservation id> to=<lane> by=leader` on the PR (the last such line counts; a prose release is not read). If the lane already holds the head the answer is `reserved` with no write; if it has a line but another holds the head, `lost`; if another lane holds it, `held_by`; otherwise it posts one line, re-reads once, and answers `reserved` or `lost` by the same rule. A POST whose result is unknown, or a re-read that does not show the posted id, gives `uncertain` (re-running is safe: it reads first). It never edits or deletes a comment, posts no status and assigns nothing. Only `outcome: reserved` lets the lane start the audit. Tests: `tests/audit_claim_cli.rs` and unit tests in `src/audit_claim.rs`.

### 로컬 merge delta 증거 (`audit-delta`, #2403)

`moai-cli audit-delta [PROJECT] --pass-head SHA --tip SHA --head SHA`는 네트워크 없이
로컬 commit 세 개만 읽는다. PROJECT 기본값은 `.`이고 Rust API는
`inspect(project: &Path, request: Request) -> Result<Report, String>`이다.
`Request`는 `pass_head`, `tip`, `head`를 소유하는 `String` 필드로 받는다.
모든 SHA는 40자리 소문자 hex의 commit OID여야 한다. ref·range·option·tag peeling은
허용하지 않으며 누락 객체·tag·비commit 객체는 입력 오류다.

HEAD의 실제 tree와 순서 있는 부모를 먼저 읽고, 부모가 정확히 `[pass_head, tip]`인
두 부모 merge만 재현한다. 부모 0~1개는 `refused/not_merge`, 3개 이상은
`refused/octopus`, 두 부모의 값이나 순서가 다르면 `refused/parent_mismatch`다.
정상적인 `--no-ff` ancestor-parent merge는 이 조건을 만족하면 허용한다.

원본 checkout·index·refs·config·worktree·object DB는 변경하지 않는다.
dirty checkout과 linked worktree도 허용하며 공통 object store는 읽기만 한다.
보안 생성된 외부 임시 bare 저장소가 alternates로 원본 객체를 빌려 읽고,
Git 기본 merge 알고리즘의 `merge-tree --write-tree --name-only -z --no-messages`를
실제 두 부모에 적용한다. 새 객체는 임시 저장소에만 생기며 반환 전에 정리한다.
사용자/시스템 Git 설정, 외부 merge driver·hook·filter, lazy fetch·network는 실행하지
않는다. 이것은 과거 작성자의 머신별 merge 설정을 재현한다는 뜻이 아니다.

결과의 `schema_version`은 1이다. `pass_head`, `tip`, `head`는 입력 OID,
`actual_parents`는 실제 순서의 OID 배열, `actual_tree`는 후보의 tree OID다.
`replayed_tree`와 `replay_exit`는 재현 tree와 Git exit 0/1이며, 거절 시 null이다.
Git exit 1은 실행 오류가 아니라 `replay_conflict` 증거이고 `conflicted_files`는
NUL 구분 출력에서 읽은 충돌 경로다. clean 재현 tree가 후보 tree와 같으면
`pure_merge`, 다르면 `manual_delta`다. 충돌은 tree 일치 여부와 무관하게
`replay_conflict`다.

`manual_delta`는 tree 불일치 여부(`bool`), `manual_text_hunks`는 numeric text
numstat의 비영 값 존재 여부(`bool`)다. 재현하지 않은 거절에서는 둘 다 null이며,
충돌 report에서도 수동 변경 판정은 null이다. binary·mode-only 차이는 text hunk가
아니므로 tree 차이와 별도로 읽어야 한다. `tip_changed_files`와 `pass_changed_files`는
각각 tip→head, pass_head→head이고 `manual_changed_files`는 replayed_tree→actual_tree다.
파일 항목은 `{path, status}`이며 status는 `A|M|D|T`, rename 탐지는 하지 않는다.
UTF-8 경로의 tab·개행을 보존하며 표현할 수 없는 출력은 오류로 처리한다.
`refusal`은 거절에서만 `{code, message}`, 그 외에는 null이다.
`writes`는 `{source: false, temporary_scratch: true}`, `network`는 `"none"`이다.
임시 정리 실패는 성공으로 숨기지 않고 I/O 오류로 반환한다.

`pure_merge`만 exit 0이다. `manual_delta`, `replay_conflict`, `refused`는
계산된 `ok: true` report와 exit 1이며 `ok`는 AUDIT PASS가 아니다.

### Claim re-verification before commit and push (`claim-verify`, rc.2 A9 #2255)

The claim line keeps its RC1 head, `moai-claim: session=<id> epoch=<n> lease_until=<utc>`, and gains appended tokens written by the one generator `claim::render_claim_line`: `lane=`, `issue=`, `branch=`, `at=` (UTC) and `relay=true` when another session posted the line (absent means not relayed, so a line with no extra fields — what `claim-acquire` posts — is the RC1 line byte for byte; a session that cannot confirm its id writes `session=unverified`). Readers of the RC1 form ignore the extra tokens. Two machine lines close a claim: `moai-claim-release: comment=<id> by=<who>` and `moai-claim-handoff: comment=<id> to=<session> by=<who>`; this code renders and parses them and posts neither (the one claim POST is unchanged). `claim_verify::evaluate` re-reads every comment and decides, in comment-id order: claim lines from authors outside `allowed_authors` are `author_mismatch`, unreadable lines (bad lease, missing fields, a closing line that names no earlier claim) are `malformed`, a second claim with the same session and epoch is `duplicate`; all three are ignored and reported (REQ-A9-02). The holder is the lowest claim not closed by a release or handoff. A live holder that is the caller gives `owner`; another live holder gives `not_owner` with `lost_to` (REQ-A9-01); an expired holder gives `stale` to everyone, the holder included, with `auto_assigned: false`, because time alone never reassigns the Issue (REQ-A9-03); a closed own claim gives `closed`; a recorded comment id that is not on the Issue gives `uncertain`; otherwise `no_claim`. `claim-verify` makes one paginated GET and succeeds only on `owner`; every other verdict is a classified error (`not owner`, `closed`, `no claim` → `conflict`; `stale`, `uncertain` → `blocked`). `--hook` is the host `PreToolUse` guard. It allows every call except a Bash segment whose first word (after `NAME=value` assignments) is `git` running `commit` or `push` — `echo git commit` is not a git run. In a worktree with an active claim record in this clone's journal it verifies that record's claim. Without a record — the claim was posted for the lane, not by `claim-acquire` — a worktree on a lane branch `issue/<n>-…` is still guarded: the Issue comes from the branch, owner and repository from the GitHub `origin` URL, and the claim comment id from the `Moai-Claim: <n>#<id>` token in the commit command's message (`git commit`) or with the highest comment id among the Issue's tokens on the branch's first-parent commits, merges included (`git push`; a renewal's token may sit only on a merge commit); no token, a token for another Issue only, or a non-GitHub origin is `uncertain` and refuses (fail-closed), with the next action — get the claim comment id — in the message. Other branches and a detached HEAD are not lane worktrees and pass, with the reason. On `git push` every lane-written commit on the branch's first-parent line since the base (the record's `base_revision`, else the commits on no other `origin` branch — the integration branch need not share history with the default branch, as `v2026.11.0` and `main` here do not; with no other remote branch every commit is checked and the push refused) must carry a token of the caller's claim or of an earlier claim of the Issue closed by a handoff line, so commits of a previous epoch stay valid after a takeover; merge commits are not checked (decision 2026-11-09 06:02, #1975), nor are the merged-in commits of other cards (`trailer missing` → `invalid_input`). A refusal exits 2, the code both hosts treat as blocking. `queue-next` now drops claims closed by a release or handoff line, so a released card is a candidate again. The MODE-AGENT workflow runs `claim-verify` before every commit and push (`skills/moai/workflows/mode-agent.md` step 6). Limits: every lane posts through one shared GitHub account, so a forged `session=` from an allowed author is indistinguishable from a real one; `hooks-apply` (#2260) writes the guard as the `PreToolUse` (matcher `Bash`) hook `moai-cli claim-verify . --hook` for both hosts; a guard that times out (10 s) does not block, so the workflow step stays the boundary. Tests: `tests/claim_verify_cli.rs` (concurrent, late-visible competitor, uncertain, duplicate, forged author, handoff and release, stale, restart, malformed lines, agreement with `resolve_winner`, the op over recorded exchanges, the hook in temporary repositories including the trailer check, the handoff epoch tokens, a lane branch without a claim record for commit and push, and the binary's exit 2 on both paths) and `src/queue.rs` `released_claims_do_not_hold_the_card`.

## Stalled-claim re-inspection and explicit handoff (`claim-handoff`, `effect-*`, `effects-reconcile`, 06-B #2006)

Everything here runs after a human decision — the leader's explicit `claim-handoff` request with a reason IS the approval. No timeout, heartbeat or silence ever decides that a writer is dead (P08 (a): the lease has no numbers; takeover is always named, never automatic).

`moai-cli claim-handoff PROJECT --task KEY --from-epoch N --reason TEXT [--force-explicit] [--host-id ID]` (operation `claim.handoff`; stdin none):
- Reads the record first. `--from-epoch` different from the record's current epoch is refused as `stale_request` (`conflict`, REQ-06B-01) even against a closed record; an inactive record whose epoch matches reads back as outcome `unclaimed`.
- Liveness (REQ-06B-02) is probed **only** for a `local-process` owner whose `host_id` matches `--host-id`: `ps -p <pid> -o lstart=` under `LC_ALL=C` answers existence and start time in one call; a differing start time is a reused pid (`dead`), a missing pid is `dead` only on `ps`'s own "no such process" answer (exit 1 with no output and no error text), any other `ps` failure (another exit code, or error text on stderr) is `indeterminate` and needs `--force-explicit` (#2349), and no recorded pid or start time is honestly `indeterminate`. Every other owner kind (`remote-task`, `ci`, or a foreign `host_id`) is `not_applicable` and never probed. The result is recorded as a `liveness` effect entry.
- An `alive` or `indeterminate` owner is refused without `--force-explicit`: the record is marked `handoff_pending` (still active, still blocking) and the outcome is `handoff_pending`/`blocked` (REQ-06B-03). With the flag and a reason the handoff proceeds; a `dead` owner needs no flag, the evidence stays in the record.
- Evidence (REQ-06B-04) is read-only git in the previous worktree: `status --porcelain=v2 -z`, `rev-parse HEAD`, `stash list`, stored as a `worktree_evidence` entry. No `reset`, no `checkout --`, no `stash`, no `clean`, no `worktree remove` runs anywhere in this module; a missing worktree path is recorded as `unavailable` rather than guessed.
- The closure (REQ-06B-05) writes the record back as `handed_off` with `to_epoch` (= current epoch + 1), the reason and the evidence in its effects, plus a `worktree_lock_intent` entry (`git worktree lock --reason "handoff from epoch N"`, state `intended` — the lock itself is never executed here; running it is the caller's approval scope). The `to_epoch` record is written by the next `claim-acquire` (the journal hands out max+1), so publish intents below `to_epoch` are fenced from then on.

`effect-intend` (`effect.intend`): records a publish intent in the record's `effects[]` **before** the external write is sent — `{"kind": <publish kind>, "operation_id", "intent_digest", "state": "intended", "epoch", "marker"}` — with the 07-B outbox formats (`op_id`, the `moai:op` HTML-comment marker) and the intent digest over the stdin payload. A request whose `--epoch` is below the record's current epoch is fenced: `stale_epoch` refusal (`conflict`), the request kept only as a `stale_result` diagnostic (REQ-06B-08). Intents attach to an active record; the same key with the same payload is the same intent (idempotent), with a different payload a conflict; when that existing intent is `uncertain` (its result was lost) the answer is `outcome: needs_reconcile, verdict: blocked` with a note to run `effects-reconcile` first, never a passed intent that would invite a second send (#2392 D3-C) — draft-ietf-httpapi-idempotency-key semantics borrowed locally, never sent to GitHub. `effect-confirm` (`effect.confirm`) moves an intended effect to `confirmed` (with `response_id` and the observed outcome) or to `uncertain` (the interrupted case); one confirm per intent.

`effects-reconcile PROJECT --task KEY [--remote-probe CMD]` (`effects.reconcile`): for every `uncertain` effect, queries the remote by its stable marker (GET only) and moves it to `confirmed` (marker found; the remote id recorded) or `not_performed` (marker confirmed absent). It never re-creates anything — the function has no write path at all. The built-in probe routes each kind to its remote source and fetches each source once: comment-borne kinds (`comment_post`) are judged from one comment-list GET, a `pr_create` is judged from the pull list (#2107 — the HOLD (a) gh-api-GET path, so no probe script is needed for 06-C's intent): when the claim record knows its branch, the narrow `pulls?head=<owner>:<branch>&state=all` query runs first — the value is percent-encoded (RFC 3986 with a deliberately smaller safe set: unreserved characters plus `:` and `/` stay raw, so the query hazards `#` `&` `+` `=` `%` and non-ASCII cannot truncate or inject into the query, #2133) — and a hit confirms with zero full-list GETs (#2126); an empty answer falls back to the full-list GET over **all** pull requests (`state=all` — a merged or closed PR carrying the marker is still evidence of creation, so scanning only open ones would report a false absence, #2116); a failed head lookup stays `uncertain` (no fallback on a failed lookup). Marker matching compares the parsed operation identity (`moai:op` and `moai-op` spellings are the same marker, #2099), and more than one remote artifact carrying the same identity is ambiguous — the state stays `uncertain` with the count in the reason. The pull scan keeps the 50-page cap: a scan that hit the cap before seeing every page is never a confirmed absence — the effects stay `uncertain` instead of `not_performed` (#2116). Unknown kinds stay unjudgeable by the built-in path (the conservative default, #2099). `--remote-probe` replaces both built-in lookups with a command contract: exit 0 + `{"remote_id": ...}` is found, exit 4 is confirmed absent, exit 5 + a seconds integer is rate limited. A rate-limited probe leaves every effect state unchanged until retry-after (REQ-06B-09): the built-in path waits and retries through the forge read path and reports `blocked` after the budget, the command path reports `blocked` with the seconds and writes nothing. The journal is written once, only when at least one effect moved, so a second identical run is byte-identical (AC-06B-5). Every output carries a `verdict` classified `passed|blocked|uncertain|not_run`; nothing not probed is ever reported as success (REQ-06B-10).

Effect and bookkeeping entries live in the record's existing `effects[]` array: publish effects carry `operation_id` + `state ∈ {intended, confirmed, uncertain, not_performed}`; bookkeeping entries are `liveness`, `worktree_evidence`, `worktree_lock_intent`, `stale_result`, `handoff`. The only claim-schema additions are additive and serde-defaulted: `Owner.pid`/`Owner.process_start` (06-B liveness) and the `handed_off` state value — old records deserialize unchanged.

The liveness probe (std + `ps`) is the interim HOLD choice (no new crates; macOS `lstart` only — Linux/Windows start-time formats differ and are not fixture-verified here). PID reuse is mitigated by the start-time comparison, not eliminated. Fencing binds only what goes through `moai-cli`: a host that runs `gh pr create` directly bypasses the epoch check — "publish goes through effect-intend" is a workflow rule, not a mechanical enforcement (RC limit, documented). Real GitHub round trips for reconcile are not_run (fixtures use fake probes; the built-in comment lookup is exercised through RecordedTransport only). Tests: `tests/handoff_cli.rs`.



## Worktree per claim and PR linkage (06-C #2007)

One claim gets one branch and one linked worktree, and its PR body carries the evidence it is judged by.

- `worktree-plan` computes the branch `<prefix>/<issue>-<logical_key>-e<epoch>` (REQ-06C-01; Issue first since #2336, like the lanes' `issue/<n>-<key>`, so the claim guard reads the same Issue) and the path, and changes nothing. The default path is the lanes' location `<primary>/.moai-cli/worktrees/<issue>-<logical_key>` (user decision, `docs/decisions-2026-11-08.md` 16:5x→17:0x); `--path` takes any other location as given (REQ-06C-12). The primary worktree is read from `git worktree list --porcelain`, never inferred from a `.git` shape. **HOLD:** the branch prefix is undecided, so `--branch-prefix` is required and has no default. The REQ-06C-01 layout differs from the lanes' current `issue/<n>-<key>` and from 06-A's `claim_branch_suffix` (`c<issue>-<comment_id>`); the user decides how they relate.
- `worktree-apply --plan-digest` re-derives the plan and refuses a different digest (`stale_plan`). It then looks for an existing owner itself: the branch used by any worktree (`branch_in_use`), a worktree locked for the same task (`task_has_worktree`), the branch ref present (`branch_exists`), or the path present (`path_exists`). Any of these returns `decision: conflict` with the existing worktree, and nothing runs; `--force` is never used (REQ-06C-03). Otherwise it runs `git worktree add --lock --reason "moai claim <task_key> e<epoch>" -b <branch> <path> <base_sha>` and measures the identity with `git rev-parse --path-format=absolute --show-toplevel --git-common-dir --git-dir HEAD`. The primary worktree's HEAD, branch and index are never written (REQ-06C-04).
- `scope-check` compares the claim's `write_scope` with every other active claim in the local journal. Matching is std-only (no new dependency): an exact path, a directory prefix, `**` for everything below and `*` within one segment; character classes and braces are not supported. `Cargo.lock`, `Cargo.toml`, `.github/**`, `.moai-cli/manifests/**` and `AGENTS.md` are shared interface paths by default (REQ-06C-06). An overlap returns `scope_conflict{other_task, overlap[]}` and `blocked(reason=scope_conflict)`; `--integration-order <task key | logical key | #issue>` allows the conflict with that task (REQ-06C-05). A `pr_ready` claim whose PRs have all closed (#2404) is not a conflict candidate: for each overlapping `pr_ready` claim — and only those, so no overlap makes no forge call — the PR numbers come from its confirmed `pr_create` effects' `response_id` (read as a number when all digits) and each is looked up with `GET pulls/{n}` before the journal lock. The claim is listed under `skipped_ended` only when it has at least one confirmed `pr_create`, every one is `closed` (merged or not) and none is `intended` or `uncertain`; a lookup error, a 404, a missing `state`, a non-numeric response id or a non-GitHub task keeps the conflict with `pr_status.pr_state: "uncertain"` and the reason. The other lane's record is never changed. Known limit: work that continues under the same claim after its last PR closed, with no new `pr_create` intent yet, is counted as ended. `scope::overlap` is the public interface 05-B's private `plan::paths_overlap` is meant to move to; that swap is a 05-B follow-up and `src/plan.rs` is unchanged here.
- `pr-body-render` renders the body described in `docs/pr-contract.md` (changed paths from `git diff --name-status <base>...HEAD`) and returns it with the operation marker `<!-- moai-op pr_create:<repository_id>:<task_key>:<epoch> -->` (the form `forge::outbox::parse_op_markers` reads, r33). With `--task` it also records the 06-B intent `effect-intend{kind: pr_create}` for the same operation (`operation_id` `pr_create-<repository_id>-<task_key>-<epoch>`, recorded marker `<!-- moai:op pr_create:… -->`). Both markers parse to one operation; the intent payload names the PR (task, epoch, issue, base branch) rather than the body, so a re-render after a new commit is the same intent. The candidate SHA is the project's HEAD at render time. A further PR under the same claim epoch is rendered with `--pr-seq N` (N >= 2, default 1): its local id becomes `<task_key>-<N>`, so it has its own operation (`pr_create-<repository_id>-<task_key>-<N>-<epoch>`), intent and marker, while the first PR's marker is unchanged (#2329). `pr-confirm` refuses, as a conflict, an ACK whose response id differs from the one an operation is already confirmed with.
- **Records.** Every command returns its change as `record_update_request`. With `--task` (a record in the local journal) the change is committed through 06-B's public `Journal::commit` under the journal lock, as events added beside 06-A's own: `worktree_recorded` (the measured identity becomes `record.worktree`, REQ-06C-02), `scope_check` (`blocked` with a `scope_conflict` effect, or an `integration_order` effect, REQ-06C-05), `effect_intend` at render (REQ-06C-09), and `pr_ready` only at the PR's ACK (REQ-06C-11, "PR 개설·ACK"): `pr-confirm` confirms an intended `pr_create` effect through 06-B's `effect_confirm`, or takes one a reconcile already confirmed, and only a confirmed effect moves the record to `pr_ready`; an `uncertain` ACK leaves the state for `effects-reconcile` to resolve first. The record must still be at its epoch and active, and a command whose change leaves the record as it was writes no event (`record_update.applied: false`). Nothing here moves a record to `integrated`. Reconcile stays `effects-reconcile`'s job for an `uncertain` effect. Since #2101 its built-in comment lookup does not judge a `pr_create`: it leaves the effect `uncertain` and reports `not_run` (or `blocked`) with a `--remote-probe` note, so finding a PR by its body marker takes a `--remote-probe` command that matches the recorded operation to the body's `moai-op` marker (`tests/claim_record_cli.rs` shows one). A confirmed reconcile is then taken by `pr-confirm`.
- **Record files are input, not authority.** `--record <file>` reads a claim that never went through the local journal (a claim the leader relayed). It must come with `--claim-comment <file>` (the Issue comment JSON, `id` and `body`), and it is refused when the comment id, session, epoch, lease or claim token differ from that comment.

## Label sync (`labels-plan` / `labels-apply`, #2434 decision 40)

`.github/moai/labels.yml` — the list `github-apply` writes, plus the `area:` labels a project adds — is the source of truth for the repository's labels, and `moai-cli` syncs them; nobody creates labels by hand in GitHub's page. Module `moai_cli::forge::labels`, tests `tests/labels_sync.rs` (recorded exchanges and a fake clock; no network, host observation not_run).

- **File.** There is no YAML crate (#2013 ②A), so the parser accepts exactly the product shape: `schema_version: 2` and one `labels:` list whose items are `- name:` followed by two-space `color:` and `description:`, with plain or single-quoted values. Anything else — this repository's own `reused`/`added` list included — is refused, never skipped. Names are at most 50 characters and unique ignoring case; colours are six hex digits; descriptions are at most 100 characters (GitHub's limits).
- **Plan.** GET `/repos/{o}/{r}/labels?per_page=100`, following `Link` pages. Each listed label is `create`, `update` (colour, description or the case of the name differ; the update renames to the file's name) or `unchanged`; names compare ignoring case, colours without `#` and case, and a null description equals an empty one. A remote label the file does not list is reported in `unlisted` and never deleted.
- **Apply.** Needs the plan digest and a permission reference, re-plans from the file and the remote and refuses a different digest (`stale`), then sends POST (create) and PATCH (update, name percent-encoded) one second apart through the adapter's backoff. A failed write stops the run: with a write already sent it is a `partial` apply naming what was created and updated, with none it is a `stale_plan` (the remote changed since the plan); both point at `labels.plan`, and a new plan lists only what is left.

## Requirement contract: GEARS and legacy EARS (05-A #2001)

`moai_cli::spec` is a library API only; no subcommand exposes it yet (its name waits for the 01-C output contract). Tests: `tests/spec_contract.rs` with fixtures under `tests/fixtures/spec/`.

- `parse_gears(id, text)` splits `[Where …] [While …] [When …] <subject> shall <behavior>` (GEARS reference page, 2026-01-14) into a typed `Requirement`: `where` and `while` lists, `when`, `subject`, `behavior`, `condition_kinds` in order of appearance. Text without exactly one `shall`, an empty subject or behavior, text before the subject that is not a clause, or clauses out of the Where, While, When order fail with a byte offset and a reason that never quotes the input. `observable_result`, `acceptance_refs` and `source_refs` are never filled with defaults.
- `import_ears(markdown)` imports legacy requirements in the SPEC layout (`- **REQ-X-001 (label)** — text`, running to the next blank line or id line). It keeps the original text, the id, the label as `classification`, and a `source_range` (1-based lines and a byte range that slices the text back out), identifies one of the six EARS patterns, and converts nothing: `If … then` stays as written and adds an `unresolved` entry asking whether the condition is an event or a state. The result is marked `syntax: EARS-import`; re-running it gives the same bytes.
- `validate(doc)` reports four separate axes: `syntax` and `structure` (`passed|failed`, from the 00-D verdict vocabulary), `semantic` (`unknown` until `record_semantic_review` records a model review, then `reviewed`; `semantic_source: model-finding`) and `execution` (always `not_run`; acceptance runs in VERIFY). The semantic and execution types have no `passed` value. Structure fails on duplicate ids, an `acceptance_refs` entry that names no criterion, a `source_refs` entry that names neither a requirement nor a criterion of the same document (an RC1 reading of "source"), or a criterion no requirement references.
- `content_digest(doc, canonical)` is `sha256:<64 hex>` over requirements, acceptance, scope, policy revision and verification commands; `approve` records it as the snapshot `<spec_id>@<revision>`, and `amend` opens the next proposed revision without touching the approved one. The canonical serialization is HOLD (P06 / HOLD-00D-5): the interim `SortedKeys` (compact serde_json with sorted keys, no new dependency) sits behind the `Canonical` trait and differs from RFC 8785 JCS on number formatting.
- Input text over 64 KiB, control characters other than line breaks and tabs, secret-shaped strings (the profile `portable()` list, with `sk-` counted only at the start of a word) and personal absolute paths (`/Users/`, `/home/`, `~/`, `C:\`) are refused without echoing values. Repository-relative paths, other paths and `:` are allowed, because they appear in requirement text normally (REQ-05A-08 as redefined in #2001 r26).

Known gaps: only English GEARS keywords and `shall` are recognized; commas inside a clause rely on the next segment starting with a keyword; EARS pattern identification is word-based and does not prove the sentence is well formed; the importer was checked against a small self-made corpus, not the full legacy SPEC set; 05-A output is not validated against a 00-D JSON Schema, because 00-D defines no requirement schema and the validator is HOLD-00D-2.

## PLAN and task DAG admission (05-B #2002)

`moai_cli::plan` builds the plan for an approved 05-A snapshot and decides RUN admission; `plan-admit PROJECT` (a temporary name until P06) reads an `AdmissionRequest` on stdin (`protocol_version`, `spec`, `tasks`, `approval`, `expected_revision`, `capabilities`), reads the project's `git rev-parse --verify --end-of-options HEAD^{commit}` with an argv array and the same environment cleaning as `identity` (`GIT_DIR` and the other #2033 variables removed, `LC_ALL=C`; Issue #2043), and writes nothing. A git failure other than "not a git repository" or a missing commit is `git_failed` (`git failed: <path-free summary>`). A `ready`, `stale` or `blocked` decision is a successful result (`ok: true`, `result.decision`); the failure envelope is for malformed input, an unsupported `protocol_version` (`kind: unsupported_protocol_version`) or a repository that cannot be read. Tests: `tests/plan_admission.rs` with fixtures under `tests/fixtures/plan/`.

- `build_plan(spec, tasks, expected_revision)` is pure. The order is Kahn's algorithm with ties broken by task id, so the input order of tasks does not matter; on a cycle the order is empty and `cycles` lists the strongly connected components (Tarjan), so a task that only depends on a cycle is not reported as part of it (leader decision 2026-11-08 on the HOLD). `structure` fails on duplicate task ids and on `depends_on` or `verifier_refs` entries that name no task or criterion. A task is `blocked` with `verifier-missing`, plus a suggested preceding task, when it has no verifier reference or a referenced criterion's verification is not one of `command`, `test`, `property`, `manual-review` with a non-empty selector. Two tasks whose write paths overlap (equal, or one a directory prefix of the other, after removing `./` and a trailing `/`) with no dependency path between them are listed in `parallel_conflicts`; that is a warning about running them in parallel, not a refusal. This check is a private, temporary implementation: the write-scope interface belongs to 06-C #2007. `execution` is always `not_run`.
- `plan_digest` is the 05-A canonical form (`SortedKeys`, HOLD with 05-A) over the snapshot reference and digest, the expected revision and the tasks sorted by id.
- `admit(request, current_revision)` re-reads what the approval and the pin rest on. `stale`: the snapshot digest no longer matches its content, the approval names another snapshot reference or digest (an approval of revision 1 is not reused for revision 2), or the repository's commit differs from `expected_revision`. `blocked`: the spec is not approved, the approval is revoked or does not allow `run`, a cycle, a structure failure, a missing verifier, or a task bound to a host outside `capabilities`. Only `ready` returns `pinned`, one `{spec_ref, plan_digest, task_id, expected_revision, scope, approval_ref}` per task in order, for 05-C. The approval record names what was approved; it never grants host permissions, and its approver stays opaque (owner and epoch belong to 06-A).

Known gaps: the expected revision is a commit id, so uncommitted changes are not seen (the tree-id alternative and a porcelain-v2 overlay are not implemented); write-path overlap is string-based and sees neither symlinks nor case-insensitive filesystems; approval expiry is not modelled; parallelism limits from host capabilities are not computed; the plan is not stored anywhere (where it would live is P09, owned by 01-B #1989).

## RUN methodology and real VERIFY (05-C #2003)

`run-verify PROJECT` (a temporary name until P06) reads a `RunRequest` on stdin: `protocol_version`, `intent` (`RUN`), `request_id`, `task_id`, `attempt_id`, an opaque `owner`, the `pinned` contract the caller holds, the 05-B `admission` request, `method`, an optional `phase`, `verification` (`commands_ref`, `timeout_ms`, both required), an optional `baseline` and the change's `diff_paths`. It reads the project's `HEAD^{commit}`, runs `plan::admit` again and compares the caller's pinned contract field by field with what 05-B admits now (`run.rs` mirrors `PinnedContract`, which has no `Deserialize`). A mismatch returns `stale` or `blocked` with reasons and runs nothing. Tests: `tests/run_verify.rs` with fixtures under `tests/fixtures/run/`.

- **Method.** `change_strategy` (`tdd`, `bugfix`, `preserve`, `contract`, `eval`, `docs`) and `domain_modeling` (`not-required`, `required`) are separate fields; the older single `legacy_mode` maps `tdd` to `tdd`/`not-required` and `ddd` to `preserve`/`required` and is kept in the receipt. The required evidence comes from a fixed table: tdd red, green, regression; bugfix repro-fail, fixed, regression; preserve baseline, after, intent-diff; contract contract-tests, migration, rollback; eval trials; docs schema, links, smoke; plus domain-invariants when domain modelling is required. A `phase` must be one of the strategy's steps; under `preserve` a request without a phase is the `baseline` step (#2392 decision row 13, F1b). Under `preserve`, any step after `baseline` is blocked without a baseline (`baseline-missing`), and a baseline handed in on stdin as `baseline` JSON is a self-report, so it does not unlock it either (`baseline-untrusted`). The trusted baseline is one `run-verify` stored (#2392 D1, decision row 13 = A): a `preserve` baseline run's receipt is written to `<git common dir>/.moai-cli/receipts/run/<attempt_id>.json` — beside the claim journal and outside every tree digest — by a temporary file and a hard link that never replaces an existing name, and the answer's `baseline_store` reports `stored`, `path`, `digest` (sha256 of the file) and `trust`, or `stored: false` with a reason (`attempt-id-exists`, `attempt-id-not-a-safe-file-name` — 1 to 128 of `A-Z a-z 0-9 . _ -`, no leading dot — `not-a-git-repository`, `store-unwritable`). A later step names it with `baseline_ref: {attempt_id, digest}`; the runner reads the file again and is blocked with `baseline-digest-mismatch` when the sha256 differs, `baseline-missing` when there is no file, and `baseline-untrusted` unless the receipt is a passed `runner-receipt` of `preserve`'s `baseline` step with the same attempt id, task, spec digest and plan digest. The file is unsigned: a writer on this host can replace it together with its reference, and the store says so. `audit-reduce` re-runs through `run` and stores nothing.
- **Commands.** Only the approved snapshot's `verification_commands` run, chosen by index. Each is split on ASCII whitespace into argv and spawned without a shell; single and double quotes group words and are removed, the other quote is literal inside them, adjacent parts join, and an unterminated quote is not runnable (no escapes, no expansion; #2392 decision row 18 — a structured argv input comes later). It runs with the inherited environment and `PROJECT` as working directory. A command whose first token is a `VAR=value` assignment, an option, or a path (`/` or `\`) is not runnable, judged on the first word after quote removal, and the request is blocked before anything starts (`command-not-runnable`).
- **Receipt.** `producer.kind` is `runner-receipt` only for receipts this runner produced; `ingest_self_report` turns agent-written JSON into `self-report` whatever it claims, and only runner receipts are admissible evidence. A receipt binds `task_id`, `attempt_id`, `spec_ref`, `spec_digest`, `plan_digest`, `base_revision`, `tree_digest` (00-A `tree_digest` with `.git` and `target` excluded, taken before the commands run), `policy_digest` (sha256 of the snapshot's `policy_revision`, null without one), `toolchain` (`rustc -V`, `cargo -V` from `PROJECT`), method, phase, required evidence, `oracle_changes` and one entry per declared check. A check records argv, start, end and duration, exit code, `timed_out`, `cancelled` (always false: there is no cancel path yet), `spawn_error`, the sha256 of stdout and stderr (the output itself is not kept), its test filters (arguments after `--`) and the sums of its `test result:` lines. A declared check the request did not run is `not_run`, and so is a check that exited 0 while its `test result:` lines sum to 0 passed and 0 failed: it tested nothing (#2392 decision row 19; a complete output without such lines keeps its exit-code result). A check that exited 0 but whose stdout or stderr was not fully read within the grace period (`output_complete=false`, digests null) is `not_run` too: its evidence cannot prove a test ran (#2392 F5c, user decision A). It keeps `exit_code: 0` and `output_complete: false`, which tell it apart from a check that never ran (`exit_code` and `output_complete` null). On unix each command runs in its own process group; when it ends or times out the whole group is killed (`kill -KILL -- -<pgid>`, as argv), so a background child cannot keep the runner waiting, and the output readers are waited for at most 2 seconds after that. Output not read by then leaves `output_complete: false` and a null digest. Without process groups (non-unix) only the bounded wait applies.
- **Summary.** `failed` when a check failed, else `not_run` when one did not run, else `unknown` when the change touched the oracle (`tests/`, any `fixtures/` or `golden/` directory, `*_test.py`), else `passed`. Freshness: `stale_reasons` reports `tree-changed`, `spec-changed` and `policy-changed`, and `revalidate` lists the tasks to verify again.
- **RED.** `red_confirmed` is set only for the `red` step of `tdd` and the `repro-fail` step of `bugfix`: true when something failed and every failure is a test failure. Failure classes are read from exit status and output text, environment signs first:

| Class | Sign |
| --- | --- |
| environment-failure | spawn error (`not-found`, `permission-denied`, `spawn-failed`), timeout, or output containing `could not compile`, `error[E`, `failed to download`, ``failed to get ` ``, `could not resolve host`, `spurious network error`, `failed to load manifest`, `no such command`, `ImportError`, `ModuleNotFoundError` (pytest, unittest) |
| test-failure | output containing `test result: FAILED`, `panicked at` or `AssertionError`, or a pytest `E` detail line starting with `assert` (#2392 decision row 20; other runners stay unclassified) |
| unclassified | any other failure; never counted as RED |

- **Retry budget.** `budget_exhausted` stops once `max_attempts` attempts ran and the last ones failed on the same checks; there is no default and no budget means no retry decision. `remaining_evidence` lists the steps still missing: only runner receipts count, the RED step (`red`, `repro-fail`) is settled by that step's receipt with `red_confirmed: true` rather than by a pass, and every other step by a passed receipt of that step (#2392). The caller holds the attempt history.

Known gaps: receipts other than a `preserve` baseline, and command output, are not written anywhere (P09, owned by 01-B #1989); failure classes are a text heuristic (libtest JSON is unstable) and `--list` is not run, so the test selection is the filters and the summed counts; the stored `preserve` baseline is unsigned, so it binds content by digest but does not resist a same-host writer; the tree digest is taken before the run, so a command that writes in `PROJECT` (a new `Cargo.lock`, for example) makes the receipt stale at once; receipts are unsigned and claim no tamper resistance.

## Cost breakdown over run/verify receipts (D5 #2191)

`cost-report` reads `{protocol_version: 1, receipts: [Receipt…]}` on stdin (the same receipt JSON `run-verify` emits, aggregated over as many receipts as the caller holds) and returns one breakdown per cost item, aggregated separately per producer kind under `by_producer` and every row tagged with its evidence `basis` (REQ-D5-01): for `runner-receipt` receipts, check outcome counts and durations are `measured` (from the receipts' own `duration_ms` and start/finish timestamps; samples without a duration are counted as `samples_missing`, never filled) and external backend calls are `structural` zero — the runner spawns local commands only and has no network path; for `self-report` receipts the same rows are `self_reported` (what the reporter claims, not a runner measurement) and the external backend call count is `absent` (`count: null`), since nothing establishes it; a producer kind with no receipts is `null` rather than a zero-filled row, so an empty group asserts no basis; each `per_receipt` row carries its producer's `basis`; every receipt arrives as caller JSON, so the report and each row say `producer_declared_by: caller` while the groups keep this aggregation (#2392 decision row 16); tokens are `absent`, because a receipt carries no token source and nothing is estimated in its place. The `estimates` array is always empty in this report: a row would only appear there if a future card introduced a real estimation source. The op executes nothing, writes nothing, and reads no project directory. Tests: `tests/run_verify.rs` `cost_report_aggregates_fixture_receipts` (two runner fixture receipts: 4 checks, 400 ms total, wall span p50, basis rows, structural zero, absent tokens, empty estimates), `cost_report_tags_self_report_receipts_self_reported` (the same fixture as a self-report: `self_reported` rows, absent external calls, no `measured`/`structural` anywhere) and `cost_report_keeps_mixed_producers_apart` (one of each: runner totals count runner receipts only).

## Context bundle and native decisions (07-D #2011)

Read-only context for a task, bound to one working tree, and a log of the judgments a workflow made. No command here opens a network socket, and every result says `network: disabled`.

- **Snapshot.** `snapshot-describe` reports `base_commit` (`HEAD^{commit}`), `worktree_path` (the git top level) and `dirty_overlay_digest`: one sha256 over every tracked path that differs from `HEAD` (`git status --porcelain=v1 -z --untracked-files=no --no-renames`), framed with the path, a tag (file, symlink target, submodule, deleted) and the file's own sha256, or for a changed submodule its checked-out commit. Untracked files are not part of it. A submodule with uncommitted changes of its own, or one whose `HEAD` cannot be read, cannot be represented, so the snapshot is `unknown` with that reason instead of a stable-looking digest. Outside git or without a commit, `base_status` is `unknown` with a reason. Git runs with `identity::scrub_git_env`, so caller variables that redirect or reconfigure git are removed (#2033, #2043).
- **Bundle.** `context-bundle` takes `{protocol_version: 1, items: [{path, start_line?, end_line?, reason}], budget?: {max_bytes?, max_items?}}`. Items are in priority order. Each kept item carries `path`, `range` (1-based, inclusive), `content_sha256` of exactly the returned bytes, `bytes`, `lines`, `reason`, `freshness: fresh` and `content`. A path is `blocked_sensitive` and never read into the output when a component matches a secret name (`.env`, `.env.*`, `*.pem`, `*.key`, `*.p12`, `id_rsa*`, `id_ecdsa*`, `id_ed25519*`, `.netrc`), when `git check-ignore` says the requested path or the in-tree file it resolves to is ignored (a symlink alias of an ignored file is ignored too), or when it, or the file a symlink resolves to, lies outside the tree; a symlink onto a secret name is blocked too. Missing, non-text, oversized (over 4 MiB) or out-of-range items are `unreadable`. Both go to `omitted[]` with the requested range, the reason and a cause.
- **Budget.** `budget` and both of its keys are optional (#2184, REQ-C8-01). A missing `max_bytes` comes from the profile key `context_max_bytes` in `.moai-cli/project.yaml`, else the 256 KiB default (`context::DEFAULT_MAX_BYTES`; user decision 01:1x(11-09)); the output names where it came from in `budget.max_bytes_source` (`request`, `profile` or `default`). A missing profile means the default; an unreadable profile, or `context_max_bytes: 0`, is an error, never a guess. `max_items` has no default. A budget is never enlarged on its own. The per-host token measurement that may later replace `bytes_div_4` is framed in `docs/context-token-measurement.md` (not_run). When an item does not fit, it and every later item go to `omitted[]` as `budget_truncated`, so a dropped item never outranks a kept one, even if a later one would still fit.
- **Tokens.** `tokens_estimate` is `{value: ceil(bytes / 4), method: "bytes_div_4", model_scope: "none"}`: an estimate, never a measurement. Measured usage comes only from the host (Claude Code statusline `context_window`, Codex `model_context_window` or `/status`) and is recorded as such in a decision record, per host, never compared or added across hosts.
- **Verify.** `context-verify` takes `{protocol_version: 1, base_commit?, dirty_overlay_digest?, items: [{path, range, content_sha256}]}` (a bundle's item objects can be passed as they are; stdin is limited to 64 KiB, so drop `content` from large bundles). Each range is re-read through the same checks; a changed digest, a missing file or a now-blocked path is `stale` with `reread_required: true`. `snapshot_freshness` compares the current base and overlay with the given ones.
- **Decision record.** `decision-record PROJECT --run <id> --permission-reference <ref>` validates one record from stdin and appends it as a JSON line to `.moai-cli/decisions/<id>.jsonl`. Fields: `schema_version` 1, `decision_source` (`native` only; separate judging backends are P10 HOLD), `host` (`claude`|`codex`), `input_digest` (`sha256:`), `options` (1 to 32), `chosen` (one of the options), `rationale_ref?`, `confidence` (`unknown`|`stated`; a stated one is not a measured probability), `authority` (only `none`: a judgment is a candidate next step, never permission, a passed test or done), `recorded_at`, `context_usage_source?` (`{host, field, value?}`, the record's own host only). Unknown fields are refused.

Leader RC1 decisions (2026-11-08, user confirmation recommended): P10 native only; token method `bytes_div_4` plus host-reported source fields; budget required with no default (superseded by the user decision 01:1x(11-09): 256 KiB default, profile override, #2184); F13 graph/MX left to a later Issue. Known gaps: the session halves of the acceptance (a PLAN→RUN on each host leaving decision records) are not run from a lane; `ignore_check` is `unavailable` when git cannot answer and ignored files are then not blocked; secret detection is by name only, not content; a tracked path hardlinked to an ignored secret file is not caught either — canonicalize resolves symlinks only, and `git check-ignore` answers on paths, never inodes (`resolve` in `src/context/mod.rs` compares none), so such an alias is read into the bundle (07-D audit finding, known limitation); the overlay excludes untracked files; the decision log has no rotation or locking beyond append; the plan and run workflows describe the records but no host projection calls the operation yet.

## Independent AUDIT and completion admission (05-D #2004)

`audit-reduce PROJECT` (a temporary name until P06) is the auditor's own run. It reads an `AuditInput` on stdin: `protocol_version`, `request_id`, the `candidate` under audit (`commit`, `tree_digest`, `workspace_id`), the 05-C `run` request, `required_checks` (indexes into the snapshot's verification commands; required), the author's `self_reports`, `findings`, an optional reviewer `opinion` (`pass` or `fail` with a summary), the `reviewer`, `waivers_allowed` and `waivers`, and the PR as `gh api …/pulls/<n>` JSON (`pr`, fetched by the caller) or `pr_lookup_failed`. It observes PROJECT itself (`HEAD^{commit}`, the 00-A tree digest without `.git` and `target`, the 01-A `identity` workspace id, `rustc -V`/`cargo -V`), re-runs the verification through 05-C, and decides with the pure `audit::reduce`. Receipts on stdin are self-reports and never count; only the receipt of the auditor's own run does (leader decision D1, 2026-11-08). Tests: `tests/audit_admission.rs` and the PLAN→AUDIT chain in `tests/workflow_e2e.rs`, fixtures under `tests/fixtures/audit/`.

The decision, first match wins:

| Condition | `admission` | `status` | Reason |
| --- | --- | --- | --- |
| reviewer not independent (table below) | blocked | blocked | `independence-missing` |
| PROJECT has no workspace id | held | unknown | `workspace-unknown` |
| PROJECT's workspace id differs from the candidate's | rejected | failed | `foreign-workspace` |
| PROJECT's commit or tree differs from the candidate (a reviewer edit makes a new candidate; PROJECT is observed again after the checks ran, so a check that changes the tree is caught too, #2392 F8) | rejected | stale | `candidate-changed` |
| PR `head.sha` differs from the candidate commit | rejected | stale | `pr-head-mismatch` |
| PR lookup failed or the JSON has no `head.sha` | held | unknown | `pr-lookup-failed` |
| reviewer opinion contradicts the evidence, either way | held | unknown | `opinion-conflicts-with-evidence`, also added as a finding |
| the receipt's summary is `unknown` (the change touched the oracle) | held | unknown | `oracle-changed` |
| a required check is not `passed` and not waived | rejected | the worst of failed, blocked, stale, not_run, unknown | `must-pass-not-met` |
| an input finding has severity `critical`, `high` or any value other than `medium`, `low`, `info` (case-insensitive) | held | unknown | `blocking-finding-open` (#2392 decision row 17) |
| otherwise | admitted | passed | — |

- **Must-pass.** Each required check takes its status from the auditor's runner receipt: `passed`, `failed`, `not_run`; `unknown` when the receipt lacks task, attempt or start and end times (REQ-05D-01); `stale` when the receipt's tree, spec, plan or policy digest or toolchain differs from the approved contracts and what the auditor observed (listed in `stale_receipts`); `blocked` or `stale` when 05-C ran nothing. Results are never averaged: one non-passing required check rejects.
- **Independence** (leader decision H1, conservative until 02-B/02-C measure more; the reviewer fields are self-declared, recorded and judged by this table, not verified): Claude `fresh` and any `separate-session` are independent; Claude `fork`, Codex `fresh` (subagent context inheritance is undocumented) and Codex `fork` proceed with a recorded limitation; `same-session`, an unknown host or an unknown sharing value is blocked. A reviewer that is not read-only proceeds with the limitation that an edit makes a new candidate. The verdict's `independence_basis` is `self-declared` for this reason (#2392 decision row 14, stage 1); deriving author and reviewer from the candidate's claim trailer and the host session id is stage 2.
- **Waivers.** Only with `waivers_allowed`, only for `quality` gates (`check:<index>` of a required check), only before `expires_at` (`YYYY-MM-DDTHH:MM:SSZ`, compared with the current UTC time). `security`, `secret` and `permission` gates are never waivable. A waived check keeps its original status in `must_pass` with `waived: true`; every waiver is recorded with its outcome (`waived` or `refused`) and refusal reason.
- **Opinions** are never evidence: agreement changes nothing, disagreement holds the verdict. Semantic review is a native host reviewer only (leader decision H2); the reducer receives findings and calls no API.

Known gaps: the verdict is not stored anywhere (P09, owned by 01-B #1989); everything on stdin, including the reviewer identity and the candidate, can be forged, and local digests are not signatures; the PR binding compares JSON the caller fetched and makes no network call; Codex independence stays a limitation until measured; a large `AuditInput` can exceed the 64 KiB stdin limit.

### The user default key `launcher.role_access` (#2413; option A decision 6778672356, design 6781812681)

The role default above is the user's to choose per machine: the user-only `~/.moai-cli/config/launcher.yaml` key `launcher.role_access` accepts exactly `full` or `prompt` — `{"launcher":{"role_access":"prompt"}}` — and an absent file, absent key or unresolved home means `full`, so a machine without the setting keeps the existing output, notes and argv byte for byte (`session::role_full_access`). The home is `HOME` or, on Windows, `USERPROFILE` when `HOME` is unset or empty (`key_vault::home`, the existing cross-platform convention); only when neither resolves is there no user file. The file is read through the project's explicit JSON-subset convention — the `profile::read_profile` rule, `serde_json` — never general YAML: anything JSON cannot express (anchors, block scalars, multiple documents) is malformed and refused. Precedence is CLI `--permissions` > the user key > `full`; project configuration is never read for this choice, and a roleless session gets no permission flag under either value. An unusable setting refuses the launch before the host starts and before any agent number is taken: an unknown value, a non-string or `null` `role_access`, a `launcher` or root that is `null` or not an object, malformed JSON-subset syntax, or an existing file that is unreadable or not a regular file (a directory, symlink or FIFO, checked with `symlink_metadata`, so a FIFO is never opened). The refusal is one stderr line and exit 1, naming the condition — never the file's contents or a raw error value — and there is no silent `full` fallback: the key is validated on every launch, roleless too and under `--permissions`, where it cannot change the argv. No note, flag or output field reports the choice. Tests: `tests/launcher_permissions_setting.rs` (a temporary HOME; both values, `--permissions` over each, every refusal shape, roleless unchanged), `--dry-run` only.

### `agent-N` numbering (#2359; resolves #2361)

`-a` without `--name` is named `agent-N` (same decision). N is counted per project — one clone with all its worktrees, whichever host (`cc`, `glm`, `codex`) opens the session — and only increases: a number is never handed out twice, also when several launches start at once. The store is `<clone common dir>/.moai-cli/sessions/agent-seq` (one decimal line, the last number handed out), next to the claim journal (`claim::journal_root`), so every worktree of a clone shares it and git never lists it; `.lock` beside it is the `File::lock` target. A launch takes the lock (a concurrent launch waits rather than fails), reads the last number, writes last + 1 (temp file, fsync, rename) and starts the host as `agent-<last + 1>`; the options are composed first, so a launch refused anyway (a blocked `glm`, an invalid option) takes no number. `--dry-run` reads the store without the lock and shows the number the next launch would take, consuming nothing; `--name` and `-l` never touch the store. When the store cannot be used — a path that is not a regular file (a FIFO is never opened), a symlink, content that is not one decimal number, the last number `u64::MAX` — the launcher exits 1 with a message naming the store and `--name`; it never falls back to `agent-1`. Functions: `session::agent_seq_dir`, `peek_agent_number`, `take_agent_number`. The P09 home layout (`layout::switched_dir`) is not applied to this store. `MOAI_CLI_TEST_AGENT_SEQ_HOLD_MS` (tests only, at most 2000) holds the lock between read and write so the concurrency test can show the lock is what keeps numbers apart. Tests: `tests/launcher_agent_numbering.rs` (stub `claude` / `codex` on PATH in a temporary git project: count-up across hosts, dry run, `--name` / `-l`, refused launches, 8 concurrent launches, N → N + 1 from a seeded store up to `u64::MAX`, malformed / directory / FIFO / symlink stores, a first launch outside a repository initializing it, worktrees sharing one counter). A folder that is not a git repository is initialized first (next section), so numbering always finds a clone common dir; when git is missing from PATH or the folder is HOME or the root, the launch stops before numbering.

## Installation receipt and `install-inspect` (04-A #1998)

moai-cli records one installation receipt per installed binary at `~/.moai-cli/installations/<install_id>.json` (REQ-04A-01). The schema is fixed: `schema_version` (1), `product` (`moai-cli`), `generation` (`rust-rc`), `channel`, `version`, `binary_path` (absolute; the user home is normalized to the `~` token), `binary_sha256` (`sha256:<hex>`, the lib.rs `digest` form), `installer_owner` (`direct|cargo|homebrew|msi|unknown`), `protocol_version` (the 01-C contract version), `created_at` and `updated_at` (RFC3339 UTC, second precision). Unknown keys are refused on read and no field may carry a credential-shaped value (the shared `SECRET_SHAPES` token list of the profile filter). `install_id` is the lowercase hex sha256 of the canonical absolute binary path (`sha256-canonical-path-hex-v0`; hex only, so the file name is valid on Windows, where identity's `sha256:`-prefixed form is not). The channel is derived from the version string (`-rc` → `rc`, else `stable`) and is provisional until the P12 release matrix decides channel naming.

`moai-cli install-inspect --json` is read-only (REQ-04A-02; `--json` is accepted for the REQ's invocation form, the envelope is always JSON). It reports the PATH resolution of `moai` and `moai-cli` (first entry wins: path, sha256, and whether `--version` produced output — each resolved binary is spawned exactly once with the single argument `--version` (at most two probes in one run: one for `moai`, one for `moai-cli`), stdin closed, stdout capped at 4 KiB, killed after 5 s), every receipt under `~/.moai-cli/installations/` with its match state (`self`, `stale_receipt` or `foreign`), self-identification, and the existence of the Go generation's paths (`~/.moai`, `<cwd>/.moai`), probed with existence checks only. It creates and modifies nothing — read-only here means it writes nothing, not that it runs nothing: the PATH probe executes code, namely whatever binary PATH resolves to under the expected name runs at inspect time (a hostile PATH entry would execute; the code itself flags this as `@MX:WARN` on `probe_version`). If you do not want the binaries on your PATH executed, do not run `install-inspect`, or sanitize `PATH` first and then invoke it. Self-identification (REQ-04A-03) requires BOTH the receipt's `binary_path` (its `~` token expanded) and `binary_sha256` to match the running executable; a path match with a different digest is reported `stale_receipt` and never rewritten (REQ-04A-06 — the explicit update path belongs to 04-B). The running executable is identified by the regular file its path resolves to, so calling it through a link (the installed layout `~/.moai-cli/path/moai-cli`, decisions L165) gives the same receipt and `install_id` as the target; a link to a non-file or a dangling link is refused (#2495). `install-inspect` also reports `self.invoked_exe` (the path the platform gave before resolution) and `self.invoked_via_link`; macOS reports a link the binary was started through, Linux already resolves it, so the flag is false there. The library's `record_receipt` (no CLI surface until the installer lands) is exclusive-create: a rerun with identical identity fields reports `unchanged` and touches nothing, a different receipt under the same id is refused.

The Go 3.x updater's selection rules are characterized, not implemented: `tests/install_cli.rs` ports them line by line (moai-adk-go `internal/update/checker.go` L34-89 and L324-347, `internal/cli/deps.go:430-450`) against the recorded feed `tests/fixtures/go-releases-sample.json` (`https://api.github.com/repos/modu-ai/moai-adk/releases?per_page=15`, recorded 2026-11-08T10:57:53Z, fields filtered to what the checker reads plus `draft`/`prerelease`). What the table records: a `moai-cli-v<version>`-tagged prerelease passes neither channel's filter (RC channel: `go-v`/`v`-prefixed tags of the `/releases` list, first item wins; stable channel: `/releases/latest`), so the decided tag namespace keeps Rust prereleases out of the Go updater's view; a final (non-prerelease) `moai-cli-v<version>` is the exception: `/releases/latest` applies no prefix filter, so a final published with the `make_latest` default (true) becomes latest and the stable check fails, which is why a final is published only with `--latest=false` (`docs/release-attestation.md` operator approval item 6; `tests/release_suite.rs` `rust_final_release_hides_newer_go_release_from_stable_clients`, E6 #2198); a plain `v2026.11.0-rc.1` would be selected by the RC channel and read as an available update, because the version comparison strips prerelease suffixes; a non-prerelease plain `v2026.11.0` would be selected by both channels. Two recorded-feed facts the table surfaces: the first entry is a draft (`v3.1.3`, `draft=true`) and drafts are not checked, so an authenticated RC-channel client selects it (anonymous callers see `v3.1.2` first); and a selected release without a `checksums.txt` asset makes the Go checker fail with `ErrChecksumUnavailable` instead of downloading. A release in another repository never enters either feed (the checker's URL is compiled to `api.github.com/repos/modu-ai/moai-adk/releases`, deps.go:36, :443-450).

Not run here: publishing any release or tag (08-D #2015 owns release workflows), the cargo-dist installer itself, Windows/Linux path and self-replacement behavior (Mac fixtures only; no Windows/Linux claims — E3 #2195 later added `src/self_update.rs` and a build-only Windows CI job, see `docs/support-matrix.md`), and any contact with a real Go installation beyond the recorded public API response.

## Host projection UPDATE (`update-plan` / `update-apply`, 04-B #1999)

`moai-cli update-plan HOME STAGE` inventories the host projections — Claude `~/.claude/skills/moai/` and Codex `~/.agents/skills/moai/` (design-verified paths; project-level projections are a P04 HOLD) — and computes, per file, a three-way action (`create|update|unchanged|conflict|preserved|remove_blocked`) from baseline (the ownership manifest of the latest host receipt), current (bytes on disk) and new (the staged package). It never writes. A structurally unsafe host (symlinked projection path, special or oversized files, unwritable directory, cross-filesystem projection) is `blocked` with a reason while the other host's plan is still produced (REQ-04B-02). The plan carries `plan_digest`, `source_version`, `target_version`, `package_digest` (`moai-package-tree-v1`), `protocol_range`, `expected_file_hashes`, `rollback_manifest` and `scope`, and is bound to the canonical home, so a replay under another HOME is refused.

`moai-cli update-apply HOME STAGE --plan-digest D --permission-reference R` (plan on stdin; every `*-apply` that takes a plan reads it under a 16 MiB plan bound instead of the 64 KiB request bound, since a plan grows with the package's file count — #2349) recomputes the plan and refuses any other digest, then applies host by host: pending receipt (written through the 01-B publish engine, temp + fsync + rename) → per-file unique temp + fsync + rename via `apply::publish_replace`/`publish_exclusive`, each re-verifying the target before publishing → full re-verification → committed receipt at `~/.moai-cli/installations/<install_id>/hosts/moai/<host>.json` (the `install_id` comes from 04-A's public `plan_receipt`). A failed host keeps its `pending` receipt and the PRE-apply ownership manifest — a crashed apply surfaces as per-file conflict, never as a silent overwrite (recovery is 04-C) — and hosts that already committed are never rolled back. Results report per-host `status ∈ {applied, unchanged, conflict, blocked, failed}`, per-file actions with before/after digests, `reload_required ∈ {no, yes, unknown}` with its documented basis (Claude: live reload, `/reload-skills` only when the top-level skills directory was just created; Codex: auto-detect, restart if not shown), and `host_loaded: false` / `execution_verified: not_run` until 08-C measures the hosts. A rerun over an applied state is all-`unchanged` and byte-identical. Projections are independent copies — symlinks are refused, never followed (REQ-04B-08) — and user files are reported `preserved` or `remove_blocked`, never deleted or overwritten (REQ-04B-09). Host config keys (`settings.json`, `config.toml`) are out of this scope (P04 HOLD). Not implemented: live host reload measurement (08-C), self-update of the moai-cli binary itself.

A14 (#2286) gives host receipts and known-good copies a namespace named after the skill folder, `hosts/<SKILL_DIR>/`; with the final skill name it is `hosts/moai/`. Receipts in older namespaces (pre-A14 `hosts/<host>.json`, rc-era `hosts/moai-cli/`), their pending work and copies remain untouched and cannot provide a baseline or recovery input for the `skills/moai` projection; an rc-era `skills/moai-cli` root is left in place. A pre-existing `skills/moai` whose files the current receipt does not own — for example an earlier-generation (Go-era) MoAI `moai` skill — makes the host `blocked` as an unmanaged existing package; the reason adds that moai-cli will not replace it on its own and that the user may move it aside or run the confirmed backup-then-replace procedure below (decision row 22). Codex's generated default prompt and invocation metadata use `$moai`, matching Claude's `/moai`. `tests/update_cli.rs::legacy_receipts_cannot_supply_the_new_skill_baseline_or_recovery`, `legacy_receipts_do_not_own_a_go_era_moai_tree`, `go_type_moai_blocks_the_install_and_stays_untouched` and `tests/skill_name_collision.rs` exercise these cases.

**Version folders (#2521).** `install_id` comes from the binary path, so every build installed in the decided layout `~/.moai-cli/versions/<version>/bin/moai-cli` (decisions L165) is a new installation. A build in that layout therefore also reads the `hosts/moai/<host>.json` receipts of the other `versions/` folders (each id derived from the same path shape) and takes the one that finished last, its own included, as the baseline; the plan names it in `receipt_from`, and apply writes the new receipt under its own id without touching the earlier one. A build outside the layout neither adopts nor lends a receipt; a linked version folder or receipt directory lends nothing, nor does a version folder whose name is not UTF-8 (it is skipped, never failing the plan — #2543); an earlier folder's pending receipt newer than every finished one, an unreadable one, or two folders finishing in the same second block the host instead of guessing. A HOME whose receipts already sit under per-version ids is read the same way, as long as the earlier version folder is still present; a removed folder lends nothing and the host stays `blocked` as before.

**One-line update (#2522).** `moai-cli update` applies the skill package installed with the binary: the release layout puts it at `<version folder>/skills/moai`, beside `<version folder>/bin/moai-cli`, and the command finds it from the canonical executable path (a missing or linked folder is an error that points to `update-plan`/`update-apply`). It always computes the `update-plan` preview first and writes nothing without a confirmation: in a terminal it shows a per-host summary and asks once (`[y/N]`, only yes applies); elsewhere it returns the preview with `confirm_with` = `moai-cli update --confirm <plan_digest>`, and that run applies only while a fresh recompute still has the same digest. A plan that would write nothing — every host blocked (an unmanaged folder, a pending receipt) or unchanged — is shown with `nothing_to_apply: true` and no question; a confirmed run reports `applied: true` only when its result status is `applied` or `partial`, so a confirmation that wrote nothing says `applied: false` (#2540). Apply goes through `update-apply` unchanged, so the unmanaged-folder block, user-edit conflicts and pending receipts keep their rules; a backup-then-replace still needs `update-apply --confirm-backup-replace`. Since #2638 the command installs the whole user layer from one package snapshot: the skill copies, the base agents (`agents-home-plan`/`apply`, rendered from `<version folder>/agents`, which sits beside `skills/moai` outside the skill tree since #2721; a missing or linked folder is an error) and the `moai-routing` section of `~/.claude/CLAUDE.md` and `~/.codex/AGENTS.md` (`home-routing-plan`/`apply`). The preview carries one top-level `plan_digest` over the three plan digests, the only value `--confirm` accepts; a confirmed run recomputes all three and compares it before any write, and refuses when the section was read from another package than the staged one; the agents are read from `<version folder>/agents`, outside the staged skill package, and a change there changes the agents plan digest (`agents_digest`), so the confirmation no longer matches. A host whose skill copy is blocked — or did not apply — gets no agents and no section (an agent host that reads the shared `~/.agents/skills` copy follows the Codex copy), and a package without `references/home/routing.md` leaves the section out; each is named in `skipped`. The result carries each part's receipt and the command that reverts it. Downloading a new release, signature checks and replacing the binary are stage 2 (after a release is published) and are not part of this command.

**Backup-then-replace (#2483, decision row 22).** When a host is blocked only by an unmanaged existing package (the scan is otherwise clean, no receipt owns anything there, nothing is pending), `update-plan` adds `backup_then_replace` to that host: `source_root`, every `source_files` entry (`path`, `sha256`, `mode` — the permission bits), `source_file_count`, `source_tree_sha256` (one digest over the sorted path/sha/mode list), `backup_root` (`~/.moai-cli/backups`), `backup_layout`, `replace_with` (package digest and file count) and `confirm_token` = `backup-replace:<host>:<first 16 hex of source_tree_sha256>`. The host stays `blocked` and the plan writes nothing; every other plan is byte-identical to before (the field is left out). `update-apply … --confirm-backup-replace <token>` (repeatable; a token the plan did not offer refuses the whole apply before any write) runs it for that host only: re-scan equal to the preview → exclusive `~/.moai-cli/backups/<UTC>-<host>/` (a name already taken in the same second moves on to `<UTC>.2-<host>` … `<UTC>.16-<host>`; with all 16 taken, or on any other error, the host fails before anything moves and the message names the cause — #2505) → `MANIFEST.json` (the source files) → pending receipt carrying `backup` (directory, manifest sha256, tree sha256) → the package files are created by exclusive publish in `<backup>/incoming` and verified (#2505) → the original folder is moved whole into `<backup>/moai` by a same-filesystem rename (no byte rewritten, nothing deleted; a failed rename leaves it in place) → the moved tree is checked against the manifest (moved back on a mismatch) → `<backup>/incoming` is renamed to the projection root (on a failure the original is moved back) → the files are verified in place → committed receipt owning the new files. The host reports `status: replaced` and `backup_dir`. Before the first move the projection is untouched; the only moment it holds neither the original nor the whole package is the gap between the two renames, where it is absent, never partly written (#2505). A failure at any point leaves the original or the backup intact and the host `pending`. `recovery-plan` gives such a receipt (pending or committed) a `restore_backup` row instead of per-file classes: `original_at` `backup` with action `restore_backup` when the backup tree matches the manifest and the projection holds only files this receipt created; `original_at` `root` with action `release` when the original never moved; otherwise action `none` with `reason` (`backup_unavailable`, `manifest_mismatch`, `backup_mismatch`, `symlink`, `user_changed`, `original_missing`), reported as a conflict and never written. `recovery-apply` moves the installed package aside into `<backup>/replaced` (never deleted), moves `<backup>/moai` back, verifies it byte and mode against the manifest (a mismatch fails the recovery: no `RESTORED.json`, the receipt is not marked recovered), writes `<backup>/RESTORED.json`, and marks the receipt `recovered` with an empty ownership manifest, so the next plan sees the folder as unmanaged again. This is the only recovery that acts on a `committed` receipt; ordinary updates keep REQ-04C-05. A later ordinary update writes a receipt without `backup`, after which the restore is no longer offered. Failure injection for the tests is a debug-build-only seam (`MOAI_CLI_TEST_FAULT=after_backup|mid_stage|mid_replace|corrupt_after_move|corrupt_after_restore`, and `MOAI_CLI_TEST_BACKUP_STAMP` for the folder time stamp); release builds never read them. Running it on a real HOME, and when, is a user decision (HOLD on #2483): replacing the folder swaps the `/moai` skill of every running session. `tests/update_backup_replace.rs` covers both hosts in temporary HOMEs.

**Backup retention, cleanup and restore guidance (#2505).** moai-cli never deletes or prunes a backup folder; there is no retention period or count limit, the same as for the known-good copies. Each `~/.moai-cli/backups/<UTC>[.<n>]-<host>/` holds `MANIFEST.json` and, depending on how far the run got: `moai` (the original folder, until restored), `incoming` (a staged package left by a run that failed before its final rename), `replaced` (the package moved aside by a restore) and `RESTORED.json` (the restore record). A folder is safe to remove by hand when it holds `RESTORED.json` (the original is back in place) or when it holds no `moai` (the original never moved); one that still holds `moai` without `RESTORED.json` is the only copy of the original — keep it. `recovery-plan` offers the restore only while the host receipt still carries `backup`; after a later ordinary update has written a new receipt, the restore is no longer offered and the backup folder stays. To put such an original back by hand: move the current projection folder aside (never delete it), move `<backup>/moai` to the projection root (`~/.claude/skills/moai` or `~/.agents/skills/moai`, on the same file system), and compare each file's sha256 and mode with `MANIFEST.json`; the next `update-plan` then reports the folder as unmanaged again. Tests: `tests/update_backup_replace.rs` (`a_rerun_in_the_same_second_gets_its_own_backup_folder`, `the_sixteenth_backup_name_is_the_last_one_tried`, `a_failure_while_staging_leaves_the_original_in_place`, `the_projection_is_absent_never_partial_between_the_two_moves`, `a_successful_replace_leaves_no_staging_folder`, `a_restored_folder_that_differs_from_the_manifest_is_not_marked_restored`).

### Recovery of a pending host (`recovery-plan` / `recovery-apply`, 04-C #2000)

A host whose receipt is `pending` is `blocked` in `update-plan` ("host receipt is pending; run recovery-plan first") until it is recovered; the other hosts plan and apply as usual (REQ-04C-04). `moai-cli recovery-plan HOME` writes nothing. It reads every host receipt (`receipt_status` none, committed, recovered, pending, or blocked for a damaged or symlinked receipt or projection) and classifies each file of a pending host by its current bytes, never by the receipt's `published` flag:

- `matches_after`: this request's change. A created file has `action: remove`; a replaced file has `action: restore` when its known-good copy `~/.moai-cli/installations/<id>/hosts/moai/<host>/known-good/<sha256 hex>` exists, is a regular file and hashes to the name.
- `matches_before`: not applied.
- `conflict`: `no_known_good`, `user_changed`, `symlink` or `not_a_regular_file`; preserved.
- `missing`: the file is gone; preserved.

`moai-cli recovery-apply HOME --plan-digest D --permission-reference R` (plan on stdin) refuses any other digest (`stale_plan`) and re-verifies each file right before removing or replacing it. It never writes a committed host. A host left without conflicts becomes `recovered` (a third receipt status, read like `committed`); a host with conflicts stays `pending`. Each run writes `<host>.recovery.json` beside the receipt: `reverted`, `conflicts`, `failed`, `not_attempted`, status `recovered|pending|failed`.

The result is `status: success|partial` with per-host `version_before`, `version_after`, `applied`, `failed`, `recovered` and `conflicts`; remaining conflicts make it `partial`. A failure part way stops there and is never retried. With something already reverted it is `partial apply: recovery <host> reverted [..]; failed at <path>: <reason>; conflicts [..]; not attempted [..]`; before any revert it is `conflict in recovery: ...`.

## SPEC auto-archive eligibility planner (`archive-plan`, D1 #2187)

`moai-cli archive-plan PROJECT [--grace-days N]` is the dry-run half of the decided auto-archive (decisions 2026-11-09 00:5x: eligible = terminal + 90-day inactivity, pending evidence and holds excluded; the automatic move is allowed but is a later issue). It scans `<project>/.moai-cli/specs/<SPEC-ID>/` directories read-only and reports JSON: `scanned`, `eligible` (spec id, terminal status, last activity RFC3339, activity source `git|mtime`), `excluded` (spec id, status, reason), `grace_days` with `grace_source` (`request|profile|default`), `cutoff`, `now`, `network: disabled`, `writes: none`. A SPEC is eligible iff its `spec.md` frontmatter status is terminal (`completed|superseded|archived|rejected` — the Go-inherited terminal set), its last activity is strictly before `now − grace_days` (default 90; profile key `archive_grace_days` overrides, `--grace-days` overrides the profile), and neither pending evidence (`evidence: pending`) nor a preservation hold (`hold: true`) is recorded. Hold·evidence values are normalized before the comparison (quotes stripped, case folded); a value outside the marker contract (`hold: yes`, `evidence: complete`, …) excludes as `ambiguous_hold`/`ambiguous_evidence`, and any form the flat parser cannot read excludes the whole block as `ambiguous_frontmatter` — an indented key, a line without `key:`, a marker key not spelled exactly `key: value` (`hold : true`, `"hold": true`, `hold:true`), the same marker key twice (YAML would keep the last value), or a flow mapping naming a marker key (`meta: {hold: true}`); a marker the parser cannot read is never "no marker" (design §12: 애매한 상태 제외; #2187 audit fixes). A readable non-terminal status is listed as `not_terminal`, so "looked at, not a candidate" is visible. Missing or unparseable status and missing time information are excluded with `ambiguous_status`/`missing_time_info`, never guessed. Last activity is one git pass over the specs tree (newest commit time per directory), falling back to the newest file mtime outside git; both are recorded in the plan. The cutoff is strict: activity exactly at `now − grace_days` stays in the grace window. An explicit REQ link is never proof of meaning, and this planner never weakens an approved SPEC (REQ-B1-01 vocabulary applies to its report). The plan also carries `plan_digest`, a digest of the `eligible` list alone (`now`/`cutoff` change every run), which `archive-apply` binds to; the move itself is the next section (D2 #2188).

## Archive move, restore and search (`archive-apply`, `archive-restore`, `archive-search`, D2 #2188)

Decision 2026-11-09 00:5x allows the automatic move as long as it hashes, reads back and can restore. The design §12 detail text is not part of the design snapshot this repository holds, so the decision row, the Issue body and the gap-analysis row 12 are the contract used here.

`archive-plan` excludes directory names that `archive-restore` cannot accept as `invalid_spec_id`: an id must be nonempty ASCII alphanumeric plus `-`, `_`, or `.`, and cannot start with `.`. Spaces, non-ASCII names, `+`, and hidden staging directories remain at the source. `archive-apply` recomputes this same plan before any move; every eligible id therefore meets the restore input contract.

- `moai-cli archive-apply PROJECT --plan-digest D --permission-reference R [--grace-days N]` (`archive.apply`) recomputes `archive-plan` and refuses unless its `plan_digest` equals `D` (`stale or altered plan; re-preview required`, `next_actions: ["archive.plan"]`). For each eligible SPEC, in plan order: (1) hash before the move — a manifest of every file (relative path, sha256, size) and subdirectory; symlinks and special files are refused; (2) copy into a unique staging directory under `.moai-cli/archive/specs/`; (3) read back — the staging copy's manifest must equal (1), else `readback digest mismatch; move cancelled, original kept` (REQ-D2-01); (4) the source must still equal (1), else `source changed during apply; move cancelled, original kept`; (5) rename staging to `.moai-cli/archive/specs/<SPEC-ID>/`, write `<SPEC-ID>.manifest.json` beside it with an exclusive create, and add the index entry to `.moai-cli/archive/index.json` (`spec_id`, `status`, `archived_at`, `path`, `manifest_digest`, `file_count`) — the index entry is the pointer; (6) only then remove the source directory. A failure in (1)-(5) removes the staging copy, keeps the source and stops; SPECs moved earlier in the same run are reported as `partial apply: archived [..]; failed at <id>: ..`. An existing destination or index entry is refused (`exclusive create refused`). The result lists the archived entries; `state` is `applied` or `unchanged`.
- `moai-cli archive-restore PROJECT --spec ID --permission-reference R` (`archive.restore`) looks the id up in the index (a single path component; unknown ids are `not_found`), refuses an existing `.moai-cli/specs/<ID>`, checks that the manifest file's digest equals the index entry and that the archived copy still matches the manifest (`digest mismatch; restore refused` otherwise), then runs the same copy-readback-rename into `.moai-cli/specs/<ID>/` and only afterwards removes the index entry, the manifest file and the archived copy.
- `moai-cli archive-search PROJECT --query Q` (`archive.search`) is read-only and non-vector: a case-insensitive substring match over the index's `spec_id`/`status` (`source: "index"`) and over the lines of archived UTF-8 files (`source: "file"`, `path`, 1-based `line`). The query is 1 to 256 characters (`SEARCH_QUERY_CHARS_MAX`, counted in characters); at most 200 hits are returned (`SEARCH_RESULTS_MAX`) and `truncated: true` marks a cut. Only archived SPECs are searched.
- Bounds inherited, not new: the index and each manifest file are read through the shared 256 KiB state-file bound (`apply::read_opt`), so a very large archive index is refused rather than truncated.
- Search rejects invalid index ids and any index `path` that differs from `.moai-cli/archive/specs/<ID>` (`archive index invalid`, `invalid_input`). It derives the directory from the validated id instead of following the stored path; relative traversal and absolute paths are refused.
- After manifest and index publication, apply checks the source manifest once more immediately before removal. A changed, missing or unreadable source stops removal with `partial apply`; the verified archive and index remain, and the command does not remove the changed source. This final check is exercised by a deterministic `apply_with_before_remove` test seam.
- Gaps: file permission bits ride on `fs::copy` and are not part of the manifest; directory removal in step (6) is not atomic — an interrupted removal leaves a verified archived copy and its index entry, and the half-removed source is then reported by `archive-plan` as `ambiguous_status` once its `spec.md` is gone (while `spec.md` remains, the SPEC stays eligible and the next apply refuses it on the existing index entry); nothing schedules `archive-apply` (it is an explicit command).

The final manifest check narrows the concurrent-write window but does not close the check-to-removal race or lock writers. A write after that check can still be lost during removal; this command does not guarantee an atomic move against concurrent writers. Rust 1.94.1 [`remove_dir_all`](https://doc.rust-lang.org/1.94.1/std/fs/fn.remove_dir_all.html) also permits partially completed removal when another writer changes the directory. Full writer exclusion or a stronger filesystem protocol remains a gap.

## Explicit SPEC links (C5 #2181, library only)

`moai_cli::spec_links::extract` emits C4 records from explicit tags, test declarations and commit protocol lines; it adds no CLI operation and never infers file-to-test links. Test discovery skips Rust/Python comments and string literals, keeps complete Rust attribute blocks across blank lines, and qualifies test identities with their enclosing Rust modules or Python classes/functions. Requirement IDs come only from the leaf test name, not its enclosing scope. Evidence retains the original source line and content digest. Macro-generated Rust tests are not expanded.

Rust string discovery recognizes ordinary `"`/`b"`/`c"` literals and raw `r`/`br`/`cr` literals. Raw strings do not process backslash escapes and close only at a quote followed by the opening number of hashes, including zero; a trailing backslash cannot consume the closing quote or the following real test. Regression fixtures check both exclusion of declarations inside literals and preservation of following declarations/missing-code diagnostics, including extraction of this repository's fixture source without false `verifies` edges. This follows the [Rust Reference string/byte/C token rules](https://doc.rust-lang.org/reference/tokens.html#raw-byte-string-literals) (checked 2026-11-10). Tag-line grammar, inferred-link count, and C4 output schema are unchanged.

Only regular tracked source files supply evidence. A tracked symlink is reported as `unreadable_file` before its contents are read; changing its external target cannot change extracted links. The existing raw commit-body rules (`Moai-Claim: <issue>#<id>` and `Refs: #<issue>` as exact decimal-ID lines) are unchanged.

Git inventory and history reads use the shared `identity::scrub_git_env` policy, so inherited repository selectors such as `GIT_DIR` and `GIT_WORK_TREE` cannot replace the explicitly requested project's evidence. A separate test process compares the complete extraction against the uncontaminated result while both variables point at another repository; it does not mutate the test runner's shared environment. This is repository-selection isolation, not isolation from global or system Git configuration.

```json
{"dispatch_id":"job1","revision":1,"previous":null,"scope":["src/example.rs"],"completion":["tests pass"],"audit":null}
```

`dispatch_id` is an opaque nonblank, control-free task identity. `revision` is a positive u64 and equals `message.task.revision` in decimal. `scope` and `completion` are nonempty arrays of nonblank, control-free strings. They are recorded criteria, not permission grants or filesystem enforcement. The message still carries S1 task, sender/receiver, owner/leader epoch, candidate/payload digests, references and creation timestamp. Revision1 has no predecessor. Later revisions are exactly previous+1 and require `previous: {report_id, payload_digest, comment_id}` from the observed preceding dispatch. The dispatcher identity/leader epoch and dispatch id/audit target remain fixed within a chain; owner epoch cannot decrease. A leader-epoch change needs an explicitly separate task/chain; S2 does not infer continuity or transfer ownership.

For an audit task, `audit` is `{pr: positive_integer, head: "40 lowercase hex"}` and `message.task.task_id` must be exactly `audit:#<pr>@<head>`. An `audit:` key without this binding is refused. This is task identity observation, not reservation or author-independence verification; those remain the audit-claim owner's responsibility.

`dispatch-ack PROJECT --permission-reference REF` takes `{dispatch: Message, decision: Message}`. `dispatch` is the exact assigned packet. `decision` is a separate S1 message with a different report id, `event: "dispatch-decision"`, identical task/revision/candidate/epochs/references and reversed sender/receiver. Its closed payload is:

```json
{"dispatch_report_id":"d1","dispatch_payload_digest":"sha256:<64 lowercase hex>","disposition":"accepted","reason":"explicit receiver decision"}
```

Disposition is exactly `accepted`, `deferred` or `rejected`; a nonblank control-free reason is mandatory. One immutable decision packet is allowed per dispatch revision. Repeating the exact packet is idempotent; changing a decision requires an explicit new assignment revision. The operation first freshly observes the current revision and validates the whole decision before any write, then publishes the S1 received ACK, rechecks revision, and separately records the decision. A failure between these steps can leave received=true with no decision. Retrying re-reads both publications; unknown POST outcomes use S1's durable attempt/no-blind-retry rule. An ACK or decision for another revision, receiver, digest, candidate, epoch or reference cannot count. A stale revision can be observed but `dispatch-ack` refuses it. A subsequent concurrent revision can still race a POST: the final read reports superseded/conflict and never grants permission for an action.

`dispatch-check` takes `{dispatch: Message}` and performs remote GET only, without touching local files. It validates repository/Issue numeric identity, the exact Issue comment collection, complete pagination, S1 canonical wire/marker/digest and numeric GitHub authors. It groups every observed dispatch/receipt/decision for the same project/task into a contiguous revision chain. Same-revision different packets, missing/wrong predecessor, inconsistent server id, malformed timestamp/wire, orphan received ACK/decision and conflicting dispositions fail closed. Identical duplicate publications count once using the lowest comment id; predecessor references must use that canonical id. Checks on an older exact packet return `superseded:true` and identify the current packet/revision/digest separately. Missing publication is blocked, never treated as received.

Output includes `dispatch_id`, `requested_revision`, `current_revision`, `current_report_id`, `current_payload_digest`, `record_comment_id`, `queued`, `received_ack`, `disposition` (null without explicit decision), `decision_comment_id`, `superseded`, `observation_current`, `ack_alert`, `elapsed_secs` and `observed_at`. `claim_authorized`, `ownership_transferred`, `audit_gate_integrated`, `cross_host_atomic`, and `business_completion` are always false. `c3` is `observation_only_gate_integration_unfulfilled`. `accepted` never means started, result reported, integrated, or owner.

The five-minute target uses the **server-observed current record comment's created_at**, never the caller's message timestamp or terminal/host send success. At 299 seconds `ack_alert=waiting`; at 300 seconds without received ACK it is `unacknowledged`. A received ACK yields `received` even while disposition=null. Future server time gives elapsed=null, alert=unknown and observation_current=false. Missing/malformed timestamps or incomplete/failed reads return a typed error, not a successful timeout judgment. This is on-demand observation, not scheduled alert delivery. Silence and timeout never grant a claim or permission to reassign.

Limits: session strings are declarations; GitHub author identity proves an account, not an independent session. A complete paginated read is not an atomic snapshot, and the later POST is not CAS. `dispatch-check` has no persistent high-water cache: a previously unseen newer revision deleted remotely cannot be detected by an older caller; retain exact revision packets and the S1 journals, and re-read at the consumer boundary. S2 does not protect a manual external verdict POST, block every later mutation, or close C3's gate requirement. Host delivery, real keys/homes, physical crash durability on every filesystem, and Windows runtime require separate verification.

Official REST sources read 2026-11-11: [Issue comments](https://docs.github.com/en/rest/issues/comments?apiVersion=2022-11-28) supplies comment id/author/body/created_at; [pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api) requires following Link pages before complete observation. Adopt: exact collection Link traversal and numeric id/server timestamp observation; reject: assuming the first page is complete or a successful POST response is a received/accepted ACK. Source retrieval time and HTML SHA256 are preserved with the implementation evidence. No new dependency is added.
