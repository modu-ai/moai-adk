# `lane-next`

operation `lane.next` · 코드 `src/ops/lane_next.rs`, `src/lane_next.rs` · Issue #2831, #2873

`lane-next --lane NAME --repo OWNER/REPO [--tip BRANCH] [--wait SECS] [--shared-lanes N] [--dir .] [--snapshot FILE] [--explain]` 는 이 레인이 **지금 할 일 하나**와 그 근거를 낸다. 매번 GitHub 에서 다시 읽어 계산하므로, 정지·압축 뒤 첫 실행도 놓친 일을 낸다. 순서(#1975 6855190942): P0 tip 빨강(#2831 D8(a): 모음 check `ci`/`rc-ci` 는 따로 보지 않고 취소된 job 도 빼고, 남은 job 이 그 커밋에서 실패만 했을 때 빨강 — 새 push 가 macOS 를 취소해 모음 `ci` 가 failure 인 경우는 빨강이 아님. 마지막으로 끝난 tip 커밋까지 first-parent 로 최대 10개를 거슬러 읽음. 본문에 `moai-tip-repair:` 줄이 있는 열린 PR 이 있으면 그 PR 저자만 자기 PR 로 고치고, 다른 레인은 `waiting` 에 `tip_repair_open` 으로 적힌 채 다음 순위로 감 — #2873 N2) → P1 내 PR(예전 head 의 감사 FAIL 뒤 head 가 바뀌었는데 그 FAIL 뒤에 재감사 요청 댓글 — 첫 줄 `REPAIR`·`재감사 요청`·`re-audit request` — 이 없으면 `request_reaudit`, 지금 head 의 감사 FAIL, 충돌, CI 실패 — #2933 S3) → P1 내가 감사 예약한 PR(판정 없음, 내 판정 뒤 head 가 바뀜, 재감사 요청 댓글 — 지금 head 40자와 함께) → P1 감사자 없는 남의 PR(초안 아님) → P1 지금 head 의 마지막 판정이 PASS 이고 그 head 의 CI 가 초록인데 아직 열린 PR(초안 아님, 내 PR 도 — 저자도 사유를 보고 할 수 있음): `unstick_passed_pr` — `moai gate-loop --once --dry-run`(쓰기 0)으로 게이트가 멈춘 사유를 읽고 할 수 있는 것(update-branch 요청 등)을 함, 예전 head 의 PASS·빨강·대기 CI 는 아님(#2933 S3) → 내 `LANE-BLOCKED … kind=decision` 뒤에 `LEADER-DECISION` 이 달린 스레드(그 뒤에 `DECISION-APPLIED <결정 댓글 id>` 줄이 있으면 이미 반영한 것이라 빼요 — #2873 N11) → P2 내가 claim 한 카드(내 열린 PR 이 없고, 결정 대기가 아니고, claim 뒤 `pr-wait:` 줄이 있는데 내 PR 이 없으면 `open_draft_pr` — 상한 때문에 못 연 가지를 초안으로 열라는 할 일, 리더 결정 #1975 6870150891. 그 claim 을 본문 `Moai-Claim:` 에 담은 PR 이 병합됐으면 — `pr-wait` 보다 뒤에 병합됐거나 시각을 모르면 — 초안 대신 `card_pr_merged`: 카드가 끝났으면 닫기 대조표와 claim 해제, 아니면 이어서 — #2873 N8) → P2–P4 아무도 claim 하지 않은 열린 Issue. P2 의 claim 카드와 P2–P4 의 열린 Issue 는 **시작 가능한 것만** 낸다(#2901): `goal-block`·`queue-free` 와 같은 판정 함수 하나(`src/startable.rs`)가 차례로 `held`(이름이 `needs:decision`·`hold`·`<축>:hold` 인 라벨, 이름 전체만 — `threshold` 는 아님) → `keep_set`(`goal-show` 의 활성 목표 제외 목록, 로컬 파일이라 요청 0) → `epic`(제목 `][EP-` 또는 GitHub 의 열린 하위 Issue) → `blocked_by`(본문 `Blocked-By:` 줄이 가리키는 열린 Issue 또는 GitHub 의 열린 선행 Issue) → `blocked_by_unknown`(열린 Issue 목록이 100개를 넘어 오래된 것부터 일부만 읽었을 때, `Blocked-By:` 가 읽은 마지막 번호보다 큰 Issue 를 가리키면 그 상태를 모르므로 닫힌 것으로 보지 않음 — PR #2916 리뷰)를 보고, 걸리면 그 카드는 `skipped` 에 `{issue, reason, …}` 로 적고 다음으로 간다. 열린 Issue 에서는 남이 claim 한 것도 `reason: claimed` 로 적는다. 그래서 HOLD 카드만 claim 한 레인도 다음 자유 카드를 받는다(#2345). 내 PR·내 claim 은 `Moai-Claim: <issue>#<comment>` 와 그 댓글의 `moai-claim: session=<lane>` 로, 감사 예약은 `moai-audit-claim: lane=<lane> head=<40hex>` 로, 판정은 첫 줄 `AUDIT #… head <40hex> … verdict: PASS|FAIL` 로 읽는다. `LANE-BLOCKED` 줄은 레인 이름을 담거나 레인이 claim 한 스레드에 있어야 그 레인 것이다.

GitHub 와 로컬 clone 은 읽기만 한다. 쓰는 것은 빈 읽기 횟수 하나뿐이다(아래 `--max-empty`, #3005 P8). 한 번 읽기에 GitHub 요청은 최대 30(높은 순위부터 읽고, 모자라면 `partial` 에 무엇을 못 읽었는지 적는다). 열린 PR 과 그 댓글(PR 마다 최근 100개), 레인의 검색 두 개, 오래된 열린 Issue 100개(본문·라벨·하위 Issue 수·선행 Issue 포함 — 위 판정에 쓰고, 100개를 넘으면 `partial` 에 적음)는 GraphQL 요청 하나로, PR 의 claim Issue·레인 스레드·열린 Issue 의 댓글과 병합된 참조 PR 은 Issue 25개마다 GraphQL 요청 하나로 읽는다(#2873 N1). 그래서 PR 이 40개여도 요청 수는 몇 개로 일정하다. 댓글까지 자세히 읽는 열린 Issue 는 시작 가능한 것 가운데 오래된 25개(GraphQL 요청 하나 분량)라서, 앞쪽 몇 개가 HOLD 이거나 남이 claim 했어도 그 뒤를 찾고 요청 수는 그대로다. 시작 가능한 Issue 가 25개보다 많으면 `partial` 에 `only the oldest 25 startable open Issues read in detail` 을 적는다(#2933 P-3). 레인이 병합·닫기 대조표가 없는 카드에 live claim 을 2개 이상 가지면(자기 PR 로 기다리는 카드도 셈, 위 판정에 걸린 `held` 등 시작 가능하지 않은 카드와 결정 대기 카드는 세지 않음 — #2954 감사 B1) 새 Issue 를 고르지 않고 `waiting` 에 `{reason: card_cap, cards, limit: 2}` 를 적는다(#2933 E). REST 로는 tip 판정, 내 PR 의 check run, 그다음 지금 head 에 PASS 가 있는 남의 PR 의 check run(리더 결정 C 기본값 — 예산이 모자라면 `partial` 에 `CI of PR #n: request budget (30) spent`), 최근 100개 밖의 claim 댓글만 읽는다. `--wait` 는 할 일이 생길 때까지 ⌈3600 × 30 × N / 2500⌉초마다 다시 읽는다(3600초 이하). N 은 한 토큰을 같이 쓰는 레인 수로 `--shared-lanes`(기본 10 → 432초, 1–50)이며, 그만큼 레인이 같이 돌아도 GitHub 시간당 5,000건의 절반(2,500) 안이 된다(#2873 N9). 결과에 `poll_secs` 로 적는다. `--tip` 이 없으면 열린 PR 들이 가장 많이 겨누는 base 를 tip 으로 쓴다. `--snapshot` 은 저장한 스냅숏(JSON)으로 판정만 한다. 결과: `lane`, `next`(`priority`·`kind`·`target`·`action`·`evidence` 또는 `null`), `waiting`(답이 아직 없는 결정 요청, 열린 tip 수리 PR, 카드 상한 `card_cap`, 레인의 기다림 기록 `lane_waiting` — 아래 #2933 S6), `skipped`(건너뛴 카드와 이유), `pr_skipped`(건너뛴 PR 과 이유 — 내 PR 에 고칠 것이 없으면 `own_no_blocker`, 초안이면 `draft`, 감사 예약이 있으면 `audit_reserved` 와 예약한 레인 `by`·댓글 `comment`, #2933 S1; `unstick_passed_pr` 가 될 PR 은 넣지 않음, #2933 S3), `end_condition`(`{open_prs, startable, met}` — 열린 PR 0 이고 시작 가능한 열린 Issue 0 이면 `met: true`, 남이 claim 한 카드도 남은 일로 센다. 목록을 못 읽었거나 일부만 읽어 수를 모르면 `null`), `partial`, `api_calls`, `writes: false`, `rounds`, `now`(판정 시각 UTC — 스냅숏의 `now`, GitHub 에서 읽을 때는 시계; 스냅숏에 없으면 키가 없음). `--explain` 이면 `explain` 에 건너뛴 PR 마다 한 줄, 건너뛴 Issue 마다 한 줄, 마지막에 `end_condition` 한 줄을 더한다(#2933 S1). 사람용 한 줄은 stderr 가 터미널일 때만, GitHub 에서 읽은 글은 넣지 않는다. 4단계(감사자 없는 PR)에서 예약 줄은 없는데 `감사`/`audit` 로 시작하는 첫 줄에 `head <hex>`(7자 이상, 지금 head 의 앞자리와 같음)를 담은 다른 형식의 댓글이 있으면 `reserve_audit` 를 내지 않고 `waiting` 에 `{number, reason: "foreign_audit_record", comment, head}` 를 적은 뒤 다음 PR 로 간다(#2973 T2). 그 댓글은 판정으로 세지 않는다: 판정은 여전히 첫 줄 `AUDIT #<n> … head <40hex> … verdict: PASS|FAIL` 뿐이고 병합 게이트 규칙은 그대로다. 옛 head 를 가리키는 기록이나 6자 이하의 head 는 무시한다.

④ 둘째 감사자 요청(#2933 S4): 4단계에서 남의 감사 예약(`moai-audit-claim`)이 있는 PR 이 다음을 모두 채우면 `audit_reserved` 로 건너뛰지 않고 `request_second_audit`(P1)를 낸다. 감사자 없는 PR 을 모두 살핀 뒤(③ 다음)이고 `unstick_passed_pr`·Issue 앞이다. (1) 지금 head 를 보유한 레인이 있고(보유자는 `audit-claim` 과 같은 규칙 `audit_claim::holder_of` 로 읽는다: 그 head 를 가리키는 예약 중 댓글 id 가 가장 낮은 것이고, 리더의 `moai-claim-handoff: comment=<예약 id> to=<레인> by=leader` 줄이 있으면 마지막 줄이 가리키는 레인이다. 예전 head 만 가리키는 예약은 낡은 것이라 기존 규칙 그대로) 그 head 에 판정(`AUDIT #… head … verdict:`)도 다른 형식의 감사 기록도 없다. (2) `now` − 보유를 준 댓글(예약, 넘김이 있으면 그 넘김 댓글)의 시각이 1800초 이상이다(29:59 는 아니고 30:00·30:01 은 맞다). (3) 보유자가 그 댓글 뒤로 1800초 이상 말이 없다: 모든 레인이 같은 GitHub 계정이라 작성자로는 못 가리므로, 그 댓글 뒤 댓글 가운데 보유자 이름이 낱말로 들어 있는 것(`agent-3`·`lane=agent-3`·`by=agent-3`)을 활동으로 보고 가장 늦은 시각부터 센다. 이름은 `audit-claim` 과 같은 `audit_claim::same_lane` 으로 견주므로 `agent-3-59cb6a`·`session=agent-3-59cb6a` 같은 세션 표기도 `agent-3` 이고, `agent-33`·`agent-3x` 는 아니다. 그 레인의 push 는 head 가 바뀌어 (1)에서 걸린다. 넘김이 있으면 시계는 넘김 댓글에서 새로 시작한다(방금 넘겨받은 감사자를 바로 바꾸지 않음). 시계(`now`)나 예약·활동 댓글의 시각을 모르면 사실로 치지 않고 기존대로 `audit_reserved` 다. 예약한 레인 자신에게는 내지 않는다. 할 일의 `action` 은 PR 에 정확히 한 줄 `moai-audit-takeover-request: comment=<예약 댓글 id> lane=<내 레인> head=<40hex>` 를 올리라는 것이다. 같은 예약·같은 head 에 보유를 준 댓글 뒤의 요청이 이미 있으면 할 일 대신 `waiting` 에 `{number, reason, comment, request_comment, by, head}` 를 적는다(`comment` 는 예약 댓글 id): 요청 댓글 id 가 가장 낮은 레인이 이기며(그 레인에게는 `takeover_requested`, 나머지에게는 `takeover_lost`), 이긴 요청도 리더의 `moai-claim-handoff … by=leader` 줄이 있어야 효력이 생긴다. 레인이 스스로 인수하지 않으며 게이트 G2 는 바뀌지 않는다(사용자 결정 6784520362). 리더가 넘기면 새 `moai-audit-claim` 은 필요 없다: `audit-claim`/`reserve` 는 넘겨받은 레인이 이미 보유자라고 답하고 아무것도 쓰지 않는다. 그래서 넘겨받은 레인은 3단계의 보통 `audit` 할 일(넘김 댓글 뒤 판정이 없으면 `audit`, 지금 head 로 판정이 있으면 재감사 요청만)을 받고 `waiting` 의 `takeover_*` 는 사라진다. 처음 예약한 레인과 나머지 레인은 감사할 일이 없고, 그 PR 은 새 보유자와 넘김 댓글 id 로 `audit_reserved` 다(`pr_skipped` 의 `by`·`comment`). 넘김 뒤 새 보유자도 30:00 말이 없으면 ④ 가 다시 열리고, 넘김 댓글보다 앞선 요청은 이전 회차라 읽지 않는다.

⑤ 수리 도움 제안(#2933 S5): 4단계에서 남의 PR 이 다음을 모두 채우면 `audit_reserved` 로 건너뛰지 않고 `offer_repair_help`(P1)를 낸다. ④ 다음, `unstick_passed_pr` 다음이고 Issue 앞이다. (1) 그 PR 의 가장 새 판정(어느 head 든)이 지금 head 의 FAIL 이다. 그 뒤에 push 가 있으면 head 가 달라지고, 더 새 판정이 있으면 그것이 가장 새 판정이라서 걸린다. (2) `now` − FAIL 댓글 시각이 1800초 이상이다(29:59 는 아니고 30:00·30:01 은 맞다). (3) 저자 레인(`author_lane`)이 FAIL 뒤로 1800초 이상 그 PR 에 말이 없다: ④ 와 같게 FAIL 뒤 댓글 가운데 저자 레인 이름이 낱말로 들어 있는 것을 그 레인의 활동으로 보고 가장 늦은 시각부터 센다. 이름은 ④ 와 같은 `audit_claim::same_lane` 으로 견주므로 `agent-29-59cb6a`·`session=agent-29-59cb6a`·`agent-29-hBp17:` 도 `agent-29` 이고 `agent-299`·`agent-29x` 는 아니다. 제안 줄의 `lane=` 과 감사자 이름을 견줄 때도 같다. 시계(`now`)나 FAIL·활동 댓글의 시각, 저자 레인, FAIL 때의 감사 보유자를 모르면 사실로 치지 않고 기존대로 `audit_reserved` 다. 저자 레인 자신과, FAIL 때의 감사 보유자(판정을 낸 감사자 — 재감사는 그 레인 몫)에게는 내지 않는다. 감사 보유자는 ④ 와 같은 `audit_claim::holder_of` 를 **FAIL 댓글 앞의 댓글들**에 적용해 읽는다: 지금 head 를 가리키는 예약 중 댓글 id 가 가장 낮은 것이고, FAIL 보다 앞에 올라온 리더의 `moai-claim-handoff: comment=<예약 id> to=<레인> by=leader` 줄이 있으면 마지막 줄이 가리키는 레인이다(넘겨받은 레인이 재감사를 맡으므로 그 레인에게는 제안이 없고, 다른 레인에게는 그 레인 이름이 `failed_by` 로 간다). FAIL 뒤에 올라온 넘김은 보유를 옮기지만 이미 낸 FAIL 의 감사자를 바꾸지는 않는다 — 한계: 그 경우 `failed_by` 는 FAIL 당시의 보유자이고, 넘겨받은 레인은 3단계의 보통 `audit` 할 일이 먼저 온다. 할 일의 `action` 은 PR 에 정확히 한 줄 `moai-repair-help-offer: pr=<번호> lane=<내 레인> fail=<FAIL 댓글 id> head=<40hex>` 를 올리라는 것이다. 이 줄은 **제안일 뿐**이다. 저자 레인이 그 PR 에 댓글로 동의하거나 리더가 `moai-claim-handoff … by=leader` 줄로 그 레인을 지정하기 전에는 저자의 가지에 push 하지 않는다. 같은 FAIL·같은 head 에 제안이 이미 있으면(다른 PR·다른 FAIL·다른 head 를 가리키는 줄과 저자 레인 자신의 줄은 세지 않음) 할 일 대신 `waiting` 에 `{number, reason, comment, offer_comment, by, head}` 를 적는다: 제안 댓글 id 가 가장 낮은 레인의 제안이 서며(그 레인에게는 `help_offered`, 나머지에게는 — 아직 제안하지 않은 레인도 — `help_offer_lost`), 그때는 목록이 다음으로 간다. 제안 줄은 판정도 감사 예약도 다른 형식의 감사 기록(`foreign_audit_record`)도 아니다.

기다림 기록(#2933 S6): 레인이 CI·감사·shell·회신을 기다리며 Issue 나 PR 에 남기는 줄 `waiting: <무엇> since <UTC>`(UTC 는 `YYYY-MM-DDTHH:MM:SSZ`)를 읽어 `waiting` 에 `{reason: "lane_waiting", number, what, since, age_secs, comment}` 로 적는다. 줄은 댓글의 줄 첫 칸에서 시작해야 하고(댓글의 첫 줄이거나 그 뒤 어느 줄이든, 들여쓴 줄은 아님), 모든 레인이 같은 계정으로 쓰므로 **그 레인 이름이 낱말로 든 댓글**(`names_lane`, ④·⑤ 와 같은 `same_lane` — 세션 표기 `agent-3-59cb6a` 도 `agent-3`, `agent-33` 은 아님)의 줄만 그 레인 것이다. 레인이 live claim 을 가진 Issue 와, 레인이 저자이거나 감사를 예약한(보유한) PR 만 읽는다. 번호마다 가장 새 기록 하나만 적고, 그 뒤 같은 레인의 다른 댓글은 지우지 않으며, 더 뒤의 `waiting: done` 또는 `waiting: -` 줄(`since` 는 있어도 없어도 됨)만 지운다. 한 댓글에 줄이 여럿이면 마지막 줄이 이긴다. `since` 가 없거나 UTC 모양이 아닌 줄은 기록이 아니라서 무시하고, 그 줄이 앞의 올바른 기록을 지우지도 바꾸지도 않는다. `<무엇>` 은 제어문자를 뺀 뒤 160자(바이트가 아니라 글자)에서 자른다(160자는 그대로, 161자는 자름). `age_secs` 는 `now` − `since`(0 아래는 0)이고, `now` 를 모르면 `null` 이다(시계는 읽지 않음). **정보일 뿐이다**: 할 일을 만들거나 막지 않고 ①–⑤·Issue 고르기의 순서와 `next`·`skipped`·`pr_skipped`·`end_condition` 을 바꾸지 않으며, 다른 `waiting` 항목 뒤에 번호 순으로 붙는다. `--explain` 에는 넣지 않는다.

빈 읽기 한도(#3005 P8): `--max-empty N`(1–1000, 기본은 GitHub 읽기에서 6, `--snapshot` 은 이 값을 줄 때만 셈, 0 이면 세지 않고 아무것도 쓰지 않음)이면 읽기마다 셋 중 하나로 가른다. **일 있음** — `next`, `waiting` 항목, 또는 내 열린 PR 이 `pr_skipped` 의 `own_no_blocker` 인 읽기(CI·감사를 기다리는 중이라 일이 진행 중): 횟수를 0 으로 되돌린다. **빈 읽기** — 일이 없고 GitHub 가 빠짐없이 답했으며(`partial` 이 비었고 `end_condition.met` 이 `true`/`false`) 그 읽기: 1 을 더한다. **읽을 수 없음** — `partial` 이 비어 있지 않거나 `end_condition.met` 이 `null` 인 읽기: 더하지도 되돌리지도 않고 파일도 쓰지 않으며 `idle.not_counted` 에 이유를 적는다. 횟수는 `<git common dir>/.moai-cli/lane-idle/<레인>__<owner>__<repo>.json`(레인·저장소마다 파일 하나, 4096바이트 넘으면 읽지 않음)에 두고, N번째 빈 읽기에서 `status: idle_limit` 와 `idle.line`(`LANE-IDLE lane=… checks=… last=… restart=…`)을 낸다. `--wait` 는 N번째 빈 읽기에서 끝난다(기다림이 다 지나기를 기다리지 않음); 한 호출 안에서 일 있음 읽기가 나오면 그 뒤 빈 읽기부터 다시 센다. git clone 이 아니면 `idle.counting: false` 이고 멈추지 않는다. 이 값을 쓰는 호출은 `writes: true` 이다.
