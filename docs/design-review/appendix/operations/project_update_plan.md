- `leftovers`(#2936 L2b, in English like the code): a read-only list of `{path, fact, note: "not removed by update"}` for what earlier generations leave and no step removes: `.moai-cli/` once the state lives in `.moai/`, a root Go `CLAUDE.md` with Go proof while no Go `.moai/` is there for `go-state` to move it with (the `claude-md` step moves it only when the user picks `replace`; the row's `note` stays the same), and a `.moai/.update.lock` whose recorded pid is not alive (`kill -0`, nothing is killed). The list never changes `all_unchanged` and never offers a deletion. `go-state` held by Go references in `settings.local.json` says the file, the key names, that the update does not edit it, and the command to run after the user's edit (`moai project-update-plan`).
- `undo_order`(#2936 E1, in English like the code): how to take the chain back, last applied first — `{rule, steps: [{step, commands, note?}], other_steps}`. Every preview prints it. The order is not a matter of taste: `go-state-revert` is refused ("AGENTS.md is conflict") while the generation step's `AGENTS.md` is still in place, and that file has a receipt of its own (`agents_receipt` in the `generation-apply` result) that the generation receipt's undo does not cover. Run in the printed order with the ids the apply results printed, the project is back to its start bytes (`tests/update_end_to_end_cli.rs`); what the steps added — receipts, `.moai.rust-<UTC>/`, the Codex and OMP files, which have no revert command — stays. `undo_order` also prints `stays` (what the commands do not take away: receipts, `.moai.rust-<UTC>/`, the files of the three steps without a revert command) so a finished undo is not read as "everything is back". The user-layer `moai update --confirm` result prints `revert_order`, the keys of `revert` in the one order they are safe to run (`update::REVERT_ORDER`: home, cleanup, keys, hooks, style, routing, agents; only the commands that exist). The terminal screen reads the same function, and `skills/moai/workflows/update.md` step 6 tells the agent to undo only in that order and to read each revert result's `skipped`: a revert that answers `reverted` with a `skipped` entry did not undo that part (Codex's `~/.codex/AGENTS.md` keeps the routing section when routing is reverted before style). That top-level `reverted` next to a `skipped` entry is not changed here (#2936 U7).

`SPEC-20261125-update-next-say-ask-chain` · 코드 `src/project_update.rs`, `src/project_update/guide.rs`. 세션이 `state`·`apply`·`preview.choices`·`reason` 을 맞춰 읽지 않고 단계마다 따로 묻지 않아도 되도록, 이미 찍힌 값에서 정해지는 사실을 더한다. 아무것도 쓰지 않고(프로젝트도 HOME 도 그대로), 위의 필드와 값은 하나도 바뀌지 않는다(`all_unchanged` 식 포함). 새 키는 `workflows/update.md` 가 아직 읽지 않는다: 그 글은 다음 조각이다.

- 단계마다 `next`(`apply`·`ask`·`wait`·`report`·`none` 중 하나), `say`, `decline` 이 붙는다. `next` 는 `guide::next_of` 가 위에서부터 첫 규칙으로 정한다: `unchanged`·`skip`·`optional` 이면 `none`; `blocked` 이고 이유가 기다림 표(`BEHIND`: 이유 → 그 이유가 말하는 앞선 단계)에 있으면 `wait`(표에 없는 이유의 `blocked` 는 `report`); `ready`·`needs_decision`·`conflict` 이고 선택지가 있거나 명령에 `<warning-confirmation>`·`--confirm-replace` 가 있으면 `ask`; 선택지도 그 낱말도 없이 명령이 있으면 `apply`(명령이 있는 `needs_decision` 도 `apply`); 그 밖은 `report`.
- `say` 는 영어 한 줄이다. 단계 id·상태 낱말·이슈·명령 이름을 담지 않고(`guide.rs` 시험이 고정) `reason` 을 되풀이하지 않는다(오류 문구가 들어갈 수 있다). 하는 일·고를 것·이미 최신인 이유·막힌 이유·기다림·거절이 각각 한 문장이고, 표에 없는 단계는 일반 문장을 쓴다. `decline` 은 그 단계 `preview.decline` 객체의 복사이고 없으면 `null` 이다(거절 기록은 `SPEC-20261125-update-declined-steps` 의 몫).
- 최상위 `ask`: 실행할 수 있는 단계(`next` 가 `apply` 또는 `ask`)가 하나라도 있으면 객체 하나, 없으면 `null`. `question` 과 `options`(`apply`(추천)·`choose`·`leave`; `steps` 가 비면 `choose`(추천)·`leave`) 에 이어 세 목록을 싣는다. `steps`: 찍힌 순서대로 `next` 가 `apply` 인 단계와, `ask` 이면서 확인 낱말 없는 추천 선택지가 있는 단계, 항목은 `{step, say, guarded, pick}`(`pick` 은 추천 선택지 id, `apply` 단계는 `null`). `follows`: `next` 가 `wait` 인 단계, `{step, say, guarded, after}`(`after` 는 그 단계가 뒤에 서는 `steps` 의 단계 id, 비어 있을 수 있다). `picks`: 나머지 `ask` 단계, `{step, say, guarded}`. `guarded` 는 `go-settings`·`go-state`·`reports`·`claude-settings`·`hooks`·`claude-settings-merge` 에서만 참이다.
- 최상위 `chain`: `apply_order` 는 `ask.steps` 의 id 를 같은 순서로, `preview_again` 은 다른 단계가 뒤에 서는 실행 단계마다 `{after, then}` 하나(`then` 은 그 뒤에 기다리는 단계 id). `ask` 가 `null` 이면 두 목록 다 비어 있다(`chain` 은 `null` 이 아니다).
- 최상위 `finish`: `ask` 가 `null` 일 때만 `{say, open}`, 아니면 `null` — 둘 중 정확히 하나만 객체다. `open` 은 `next` 가 `report` 또는 `wait` 인 단계의 `{step, next, say}` 목록이고, `say` 는 `all_unchanged` 이면 남은 것이 없어 묻지 않고 끝난다는 문장, 아니면 스스로 실행할 단계가 없어 묻지 않고 끝나며 `open` 의 단계는 살펴봐야 한다는 문장이다.
