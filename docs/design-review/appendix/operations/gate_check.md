# `gate-check`

operation `gate.check` · 코드 `src/ops/gate_check.rs`, 규칙 `src/gate.rs`, 수집 `src/gate_collect.rs` · Issue #2674 S1·S1b, #2777(G8)

`gate-check` 는 표준 입력의 PR 스냅숏(댓글, check run, PR·tip 변경 파일, merge-tree 결과, Self-Audit 검사 결과, 판정 base 가 아는 커밋인지, 사용자가 확인한 REVIEW.md PR 번호, PR 커밋의 저자 세션 `pr_authors`, tip 의 push CI 판정 `tip_ci`, 본문의 수리 표지 `tip_repair`, `Moai-Claim` 트레일러가 없는 PR 커밋 목록 `commits_without_claim`, 본문의 claim 줄 여부 `body_claim`, 이 PR 아래의 열린 PR 목록 `stacked_below`)으로 리더 병합 게이트 규칙 G8, G1·G2, G9·G10, G3, G4, G11, G12, G5~G7 을 차례로 본다. G9(#2674 R1)는 마지막 판정의 감사자가 이 PR 커밋의 `Moai-Claim` 트레일러가 가리키는 claim 의 세션(저자)이 아닌지 본다. 스냅숏의 `pr_authors` 가 없으면 모른다는 뜻이라 멈춘다. G10·G11(감사 6864692054 B1)은 지운 `flow-gate-verdict` 의 `commit_claim_lines`·`pr_body_claim` 을 옮긴 것이다. G10 은 병합 커밋이 아닌 PR 커밋마다 git 이 읽는 `Moai-Claim` 트레일러가 있는지 본다(트레일러 칸 밖의 claim 줄은 읽지 않는다). 목록이 없으면 모른다는 뜻이라 멈춘다. G11 은 PR 본문에 `Moai-Claim: ` 줄이 있는지 본다. G12(#2859)는 쌓은 PR 이 아래 PR 의 감사 안 된 head 를 tip 에 들이지 못하게 한다: 이 PR 이 들여올 커밋(`merge base..head`) 중 다른 열린 PR 의 커밋이 있으면, 그 PR 의 마지막 판정이 PASS 이고 그 판정 head 가 들여올 그 PR 의 가장 새 커밋들을 품어야(같거나 조상) 하며, 그 판정의 감사자가 그 커밋들의 저자가 아니고(G9 와 같은 규칙) 그 커밋마다 `Moai-Claim` 트레일러가 있어야(G10 과 같은 규칙) 한다. 아니면 아래 PR 번호와 커밋을 이유에 적고 멈춘다. 이미 병합된 아래 PR 은 열려 있지 않고 커밋도 tip 에 있어 대상이 아니다. 스냅숏에 `stacked_below` 가 없으면 모른다는 뜻이라 멈춘다. 모두 맞으면 `pass: true` 와 판정 base·허용한 겹침 파일을, 아니면 `pass: false` 와 멈춘 규칙(`rule`)과 이유를 낸다. 네트워크·git 을 읽지 않고, 상태 게시·병합을 하지 않는다. 규칙 표는 Issue #2674 댓글 6849084101. 판정은 첫 줄이 `AUDIT #` 로 시작하는 댓글뿐이다(본문 중간에 인용한 줄은 판정이 아니다). 예약 철회는 첫 줄 `moai-audit-claim 철회: <레인> (<예약 id>)` 형식만 읽는다.

`gate-check --pr N [--repo OWNER/REPO] [--dir .] [--tip refs/remotes/origin/v2026.11.0] [--review-confirmed 1,2]` 는 스냅숏을 직접 모은다(S1b): PR head·본문·댓글(쪽 넘김)·head 의 check run, 열린 PR 목록과 이 PR 이 커밋을 들여오는 아래 PR 의 커밋 목록·댓글(G12)을 GitHub 에서 GET 으로 읽고, 로컬 저장소에서 `merge-tree`·변경 파일·판정 base 존재·겹친 `docs/` 의 양쪽 추가 줄 보존·병합 tree 의 manifest sha256 을 잰다. PR 본문의 `## Self-Audit` 절은 이 바이너리 안의 같은 검사(`pr-self-audit-check` 와 같은 규칙, `self_audit::check`)로 보고, 통과하지 못하면 G4 에서 멈춘다. Python 은 필요 없고 저장소마다 같다(#2708. 전에는 저장소의 `tools/check_pr_self_audit.py` 를 돌리고 그 파일이 없으면 멈췄다). 가져오기(fetch)는 하지 않는다: head 가 로컬에 없으면 `refs/pull/N/head` 를 먼저 가져오라는 오류를 낸다.

G8(tip 빨강 멈춤, #2665·#2777)은 맨 앞에서 본다. 수집은 tip 커밋의 check run 을 모든 시도(`filter=all`)까지 읽고, `cancelled` 와 아직 도는 시도를 뺀 뒤 `flow::tip_ci_judgment`(필수 `ci`)로 판정한다. tip 의 CI 가 아직 돌거나 취소만 있으면 첫 부모를 따라 이전 tip 커밋을 최대 10개(`TIP_WALK`) 읽고, 처음 완료된 CI 가 판정한다(`decided_by`). 읽기 실패나 10개 안에 완료된 CI 가 없으면 `unknown`. `red` 면 본문에 `moai-tip-repair:` 줄이 있는 PR 만 통과하고, `unknown`(또는 `tip_ci` 없음)이면 수리 PR 도 멈춘다. `flaky`(같은 커밋에서 실패 뒤 재실행 성공)와 `green` 은 통과한다. 취소는 실패로 보지 않는다(`tip_ci_judgment` 에 넘기기 전에 뺀다): 새 push 가 앞 실행을 취소하므로 취소는 코드에 대해 말하지 않는다.

기계적 delta(#2833): 마지막 판정이 PASS 인데 그 head(H)가 지금 head(N)와 다르면, 수집은 `gate_collect::mechanical_delta` 로 N 이 H 에 base 가지만 합친 것인지 잰다 — H 가 N 의 조상, H 뒤 tip 에 없는 커밋은 모두 병합 커밋(PR 저자의 새 커밋 없음), merge base 대비 PR 파일 집합이 두 head 에서 같음(병합이 PR 밖 파일을 바꾸지 않음), 파일마다 `git patch-id --stable`(`--binary` diff)이 같음(PR 쪽 줄을 바꾼 해결은 다름), 파일 200개(`MAX_DELTA_FILES`) 이하. 결과는 스냅숏 `auto_delta`(`from`·`to`·`ok`·`detail`·파일별 patch-id)다. G1 은 `ok` 이고 `from`=H·`to`=N 이고 모든 파일의 patch-id 가 같을 때(게이트가 다시 확인) H 의 PASS 를 N 의 것으로 인정하고, 통과 결과에 `auto_delta` 근거를 낸다. 이때 G2(감사 예약)·G3(풀리지 않은 FAIL)은 H 를 본다 — delta 가 H 의 FAIL 을 넘기지 않는다. N 의 CI 는 G5 가 그대로 본다. delta 가 있으면 G6 의 tip 변경 파일은 N 과 tip 의 merge base 부터 센다(N 이 이미 합친 tip 변경은 겹침이 아니다). 하나라도 맞지 않으면 G1 이 이유(`not a mechanical delta: …`)와 함께 멈춘다.
