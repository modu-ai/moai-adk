# `spec`

operation `spec` · 코드 `src/ops/spec.rs`, `src/spec_doc.rs`, `src/spec_take.rs`, `src/spec_close.rs`, `templates/spec/full.md`, `templates/spec/minimal.md` · SDD 생애 주기 계획(2026-11-17) SDD-1·SDD-2·SDD-7·SDD-8, SPEC-20261117-spec-tooling, SPEC-20261118-spec-take, SPEC-20261118-spec-close

`spec <동작>` 은 프로젝트의 SPEC 문서 `<project>/.moai/specs/<SPEC-ID>/spec.md` 를 만들고, 검사하고, 목록으로 보이고, 하나를 JSON 으로 보여 주고, 그 SPEC 의 가지에서 일을 시작하고(`take`), 합쳐진 SPEC 을 닫는다(`close`). 낱말 하나에 동작이 중첩돼 있고 봉투의 `operation` 은 항상 `spec`, 동작은 결과의 `action` 으로 나간다. **`take`·`close` 말고는 어떤 동작도 프로그램을 실행하지 않고, `take --push`·`--draft-pr` 말고는 네트워크에 나가지 않는다**: `verify:` 명령은 읽기만 하고 돌리지 않는다. 각 동작의 도움말 첫 문장은 `Writes one new SPEC.`, `Reads only.`, `Writes the branch.` 또는 `Writes the SPEC.` 이다.

## `spec.md` 형식 (`src/spec_doc.rs`)

- **앞머리**: 첫 줄 `---` 와 닫는 `---` 사이의 `key: value` 줄. 완전한 YAML 이 아니고 우리가 쓰는 모양만 읽는다: 한 줄 값, `null`(`~`·`Null`·`NULL` 도; 키가 없는 것과 같다), `approval` 의 들여 쓴 줄 또는 한 줄 흐름 맵 `{by: …, at: …, basis: "…", digest: …}`(따옴표 안의 쉼표·콜론은 값; 감사 B2). 키는 `id`, `title`, `status`, `revision`(1 이상 정수, 앞자리 0 거절), `created`(`YYYY-MM-DD`), `parent`(선택, SPEC id), `approval`(`by`·`at`·`basis`·`digest`). 다른 아는 키에 맵·목록을 주면 `fm_shape`. 모르는 키는 경고 `fm_unknown_key` 이고 오류가 아니다. **`cards:` 는 오류 `fm_cards`**: 개인 카드 번호는 공유되는 SPEC 에 들어가지 않는다(연결은 카드 쪽에 둔다).
- **id**: 새 모양 `SPEC-<yyyymmdd>-<slug>`(실제 달력 날짜, 슬러그 48자 이하). Go 세대 `^SPEC(-[A-Z][A-Z0-9]*)+-[0-9]{3}$` 는 읽기만 하고 쓰지 않는다. 폴더 이름은 id 와 같아야 한다(`id_folder`).
- **상태**: `draft`·`approved`·`completed`·`superseded`·`rejected`·`archived`. `approved`·`completed`·`superseded` 는 `approval` 네 칸이 모두 있어야 한다(`approval_missing`, `approval_field`; `at` 은 정확히 `YYYY-MM-DD` 인 실제 날짜, 뒤에 시각을 붙이면 거절; `null` 은 빈 칸). Go 세대 상태(`planned`·`plan_ready` → `draft`, `ready-for-run`·`in-progress`·`implemented`·`implemented-pending-sync`·`sync-started` → `approved`, `backfilled` → `completed`, `retired` → `archived`)는 새 낱말로 읽고(`status_as`) `status_legacy` 로 알린다: Go id 에서는 경고, 새 id 에서는 오류.
- **절**(`##` 제목, 영어): `Intent`·`Requirements`·`Acceptance`·`Scope`·`Plan` 은 언제나 필요하다(최소 SPEC). `Non-goals` 나 `Risks` 가 하나라도 있으면 완전한 SPEC(`form: full`)이고 둘 다 필요하다. `Decisions`·`Result` 는 선택. `Interview` 도 선택이지만, 새 형식 id 이고 `created` 가 2026-11-19 이후이며 상태가 `approved`·`completed`·`superseded` 인 SPEC 은 이 절이 없으면 오류 `interview_missing` 이다. 절의 줄은 `- Q<n>: <질문> → A: <답>`(화살표는 `->` 도 된다) 또는 혼자 선 `- none: <10자 이상의 이유>` 이고, 그 밖의 목록 줄은 `interview_entry`(위 상태에서는 오류, 그 밖에는 경고)이다. 절은 `digest` 밖이고 검사는 모양만 본다. 모르는 `##` 는 경고 `section_unknown`, 두 번 나온 절은 `section_duplicate`, 비어 있는 `Intent`·`Plan`·`Non-goals`·`Risks` 는 `section_empty`. 울타리 코드(```` ``` ````·`~~~`) 안의 제목은 글이다. 본문 언어는 작성자 마음이다.
- **요구**: `- REQ-<n>: <GEARS 문장>` 을 `spec::parse_gears` 로 읽는다(영어 키워드 `Where`/`While`/`When … shall …`, 본문은 한국어도 됨). EARS 의 원치 않는 동작 형태 `- REQ-<n> (REQ-…): IF <조건>, THEN <주어> shall <동작>` 도 받는다(`kind: "unwanted"`; `IF`·`THEN` 은 대소문자 무관, 쉼표는 없어도 됨; `When <조건>, <주어> shall <동작>` 으로 바꿔 같은 `parse_gears` 규칙을 거친다). 문장이 아니면 `req_gears`(이유만 말하고 글은 되풀이하지 않음; 비밀 모양·개인 절대 경로도 여기서 거절), 번호가 겹치면 `req_duplicate`, 하나도 없으면 `req_missing`. GEARS 문장은 통과 조건이다(권고가 아님).
- **실패 경로 규칙**(사용자 결정 2026-11-17): `When` 트리거가 있는 GEARS 요구마다, 같은 SPEC 안에 그 REQ 를 괄호로 가리키는(제대로 읽힌) IF/THEN 요구가 있거나, 그 REQ 줄 **끝**에 `· failure: none` 메모가 있어야 한다(뒤에는 ` — 이유` 만 올 수 있다; 메모는 본문에서 빠진다; 문장 중간이나 `·` 없는 `failure: none` 은 메모가 아니다, 감사 N5). 없으면 **오류** `req_failure_path`: 실패 경로가 없는 트리거는 아무도 쓰지 않은 요구라 어떤 AC 도 그것을 확인할 수 없고, 면제는 메모 한 줄이면 되기 때문이다(Go 세대 SPEC 에서는 다른 규칙처럼 경고). IF/THEN 요구가 없는 REQ 를 가리키면 `req_ref_unknown`. `Where`·`While` 만 있는 요구에는 이 규칙이 없다.
- **수용 기준**: `- AC-<n> (REQ-…): <관찰 결과> · verify: `<명령>`` 또는 `manual: <누가 무엇을>` 또는 `unknown: <이유>`. 꼬리표는 AC 줄 안(앞이 공백이나 `·`)에 두거나, 다음 AC 가 나오기 전까지의 그 AC 아래 줄 가운데 **꼬리표로 시작하는 줄**(목록 기호 `- ` 는 무시)에 둔다. 처음 찾은 꼬리표 하나만 읽고, 꼬리표로 시작하지 않는 줄 안의 `verify:` 는 꼬리표가 아니다(감사 N3: 문서를 코드에 맞춤). 없으면 `ac_no_verify`, `unknown:` 은 경고 `ac_unknown`, 번호가 겹치면 `ac_duplicate`, 없는 REQ 를 가리키면 `ac_ref_unknown`. 괄호 안 참조는 범위 `REQ-1…REQ-10`·`REQ-1..REQ-10` 을 펼쳐 읽는다(뒤로 가는 범위·섞인 접두어·1000개 넘는 범위는 글자 그대로라 `ac_ref_unknown`; 감사 B2). AC 글과 `verify:`·`manual:`·`unknown:` 값에는 요구와 같은 글 검사(비밀 모양·개인 절대 경로·제어 문자)를 해서 걸리면 `text_unsafe`(이유만 말한다; 감사 N2).
- **범위**: `- write: `a`, `b``·`- read-only: …`·`- forbidden: …`. 경로가 없는 꼬리표 줄(`write:`)은 그 아래 목록의 종류를 정하고, 꼬리표 없는 목록 항목은 `write` 다. 경로가 있는 꼬리표 줄은 그 아래 들여 쓴 비목록 줄로 이어질 수 있다(다음 목록 항목이나 빈 줄까지). 절대 경로(`/`·`\`·`~`·`C:`)는 `scope_absolute`, `..` 구간은 `scope_parent`, 그 밖에 비밀 모양·개인 경로는 `text_unsafe`, `write` 경로가 없으면 `scope_empty`.
- **덜 쓴 글**(감사 B3): `[NEEDS CLARIFICATION` 이 든 줄은 `needs_clarification`, 내장 템플릿의 자리 표시(`<trigger>`·`<first step>` 처럼 템플릿에 있는 `<…>` 그대로)가 남은 줄은 `placeholder`. 상태가 `approved`·`completed` 면 오류, 그 밖에는 경고. 울타리 코드 안과, 템플릿에 없는 `<…>`(`<state>`·`REQ-<n>` 등)는 상관없다.
- **크기 예산**(감사 B3): 요구가 12개를 넘으면 `size_requirements`, 400줄을 넘으면 `size_lines` 경고(오류가 아니다; 큰 일은 `parent` 로 이은 여러 SPEC 으로 나눈다, 결정 U-D).
- **digest**: 요구·수용 기준·범위에 대한 `spec::content_digest`(`show` 의 `digest`). 승인할 때 `approval.digest` 에 적고 PR 본문에도 되풀이한다. 승인 뒤 요구·기준·범위가 바뀌면 `approval_digest` 오류 — `revision` 을 올리고 다시 승인한다. 다른 글(의도·계획 등)은 digest 에 들지 않는다. 파일이 자기 git blob id 를 담을 수는 없어서 blob id 가 아니라 내용 digest 다.
- **마감(`--closure`)**: 상태가 `completed`(`closure_status`), `## Result` 가 있음(`closure_result`), 모든 AC 가 `- AC-<n>: met …` 또는 `withdrawn …`(`closure_open`), Result 가 없는 AC 를 가리키지 않음(`closure_unknown`).
- **Go 세대 SPEC**(Go id): 읽기·앞머리 블록·id·상태 코드만 오류로 남고 나머지는 경고로 내려간다(마감 검사는 예외 없이 오류). 1,000개가 넘는 옛 SPEC 이 `check --all` 을 막지 않게 하려는 것이다.
- **읽기 한도**: `spec.md` 는 일반 파일이어야 하고(링크는 따라가지 않음: `O_NOFOLLOW`, 연 파일과 `lstat` 의 장치·inode 비교), 256 KiB(262,144 바이트)까지, UTF-8. 넘으면 `read_too_large`, 링크·폴더는 `read_not_file`, 없으면 `read_missing`, UTF-8 이 아니면 `read_utf8`. SPEC 폴더나 `.moai`·`.moai/specs` 가 링크여도 들어가지 않는다.

- 템플릿은 바이너리에 들어 있다(`include_str!`, `templates/spec/`). 키와 제목은 영어, 자리 표시(`<…>`)는 작성자가 채운다. 새 템플릿은 `check` 를 오류 없이 통과한다.
- `spec new` 는 `.moai/` 가 없는 프로젝트(`.moai-cli` 프로젝트 포함)에도 `.moai/specs/<ID>/` 를 만들고, 표식은 쓰지 않는다. **`.moai/` 에 진짜 폴더 `specs/` 하나만 있으면 상태가 아니다**(감사 B1, 리더 결정 2026-11-17): SPEC 을 추적하는 저장소의 새 클론이 바로 이 모양이라, `state_root::classify` 와 `project-detect` 의 `go_state` 는 이것을 `.moai/` 가 없는 것처럼 읽는다(판정 `none`, `unknown` 이 아님; `state_root::specs_only`). 그래서 `spec new` 앞뒤로 판정·`project-detect`·`project-update-plan` 의 답이 같다. 프로젝트 첫 설정(`adopt_new`)은 이 폴더를 그대로 두고 표식만 더하고, `.moai-cli` 상태를 새 `.moai/` 로 옮기는 `go-state-apply` 는 이 폴더 안으로 옮기며, 그 되돌리기는 `.moai/` 를 치운 뒤 `specs/` 만 `.moai/specs` 로 돌려놓는다. `specs/` 옆에 다른 것이 하나라도 있으면 예전 판정(`unknown` 등) 그대로다. `.moai` 가 링크이거나 `interrupted`·`refuse` 면 거절하고, 폴더를 만든 뒤 길 위의 폴더가 링크로 바뀌었으면 파일을 쓰기 전에 거절하고 만든 폴더를 치운다(감사 N7).
- `check` 의 거절 문장은 오류를 50개까지 적고, 51개부터는 `; and N more (spec show <id> lists them)` 를 붙인다(감사 N4 경계 시험).
- 아직 없는 동작: 승인 기록 쓰기, SPEC 보관. 카드 연결은 `moai card spec`(SDD-4)과 `spec take --card`.
